# M-10 ③ 모델 버전 비교 결과의 ERD 시각화 (1차)

> 2026-11-12. M-10 (구조 변경 비교·시각화) 가운데 **③ 모델 버전 간 비교의 ERD 표시**만 구현했다.
> ① 원본 스냅샷 A ↔ B, ② 물리 모델 ↔ 최신 원본 스냅샷은 선행 기능(AI-1·AI-2, M-4)이 없어 손대지 않았다 — 8장.
> DB 변경 없음 (Flyway 변경 없음). 모델 버전의 저장 구조와 비교 판정(M-9 3차, [기록 12장](model-change-history-m9.md))은 그대로다.

## 1. 기존 구조 분석

| 확인한 것 | 결과 |
|---|---|
| 버전 스냅샷만으로 과거 ERD 를 그릴 수 있는가 | 된다. 스냅샷은 `대상 종류 → [{id, name, state}]` 이고 테이블(스키마 포함)·컬럼(타입·길이·NULL·기본값·PK)·관계(컬럼 쌍, 순서대로)·엔터티·속성·식별자·논리 관계가 모두 있다. 연관 대상은 ID 와 그 시점의 이름이 함께 있다. **배치(노드 위치)는 없다** — 배치는 모델과 따로 사용자별로 저장한다(M-2 D-15) |
| 비교 결과에 객체 식별자가 유지되는가 | 된다. 내부 ID 로 짝짓는다. 이름 변경 = 같은 객체의 수정, 지우고 같은 이름으로 다시 만들면 삭제 + 추가. 이름이 같다고 같은 객체로 보지 않는다 |
| 삭제된 객체를 복원해 보여 줄 수 있는가 | 된다. 삭제된 객체는 기준 버전의 상태(`before`)로 그린다 |
| 기존 ERD 컴포넌트를 읽기 전용으로 다시 쓸 수 있는가 | 화면 전체(`PhysicalErdPage`, `LogicalErdPage`)는 조회·배치 저장·편집이 묶여 있어 그대로는 안 된다. **노드와 관계선은 다시 쓸 수 있다** : `TableNode` 는 이미 따로 있었고, 엔터티 노드·논리 관계선·물리 관계선 만들기는 화면 파일에서 떼어 냈다 (동작은 그대로) |
| 논리 ERD 와 물리 ERD 가 같은가 | 다르다. 물리는 컬럼 쌍마다 컬럼 연결점으로 선을 긋고, 논리는 관계 하나에 선 하나·양 끝 참여 수·Crow's Foot 표기다. 변경 판정과 화면 틀은 같이 쓰고 노드·선만 각각의 것을 쓴다 |
| 기존 배치 좌표를 다시 쓸 수 있는가 | 쓰지 않는다. 저장된 배치는 "지금의 모델 전체" 를 사용자가 놓은 것이라 변경 영역만 뽑으면 서로 멀리 흩어지고, 삭제된 객체의 자리는 없다. ELK 자동 배치를 쓰고 저장하지 않는다 |
| 큰 모델의 전체 렌더링을 막을 수 있는가 | 기존 API 로는 안 된다. 비교 API 는 달라진 객체만 주고(달라지지 않은 컬럼·이웃 테이블이 없다), 스냅샷 API 는 버전 전체(2,000 테이블에서 48 MB)를 주며, 현재 모델을 같은 모양으로 주는 API 는 없다. → 조회 API 하나를 더했다 (2장) |

## 2. 서버 — `GET /api/modelVersion/compare/erd`

기존 구조로 풀 수 없는 것(달라지지 않은 컬럼·이웃, 현재 모델, 범위 제한)만 더했다. 저장 구조·비교 판정은 새로 만들지 않았다.

- `baseId`, `targetId`(없으면 현재 모델), `kind` = `PHYSICAL` · `LOGICAL`, `focusType`·`focusId`(선택), `limit`(기본 100, 최대 300).
- **판정은 버전 비교와 같은 코드다.** `ModelVersionService` 의 비교를 "두 모델 읽기(`models`)" 와 "대상 종류 하나의 짝짓기·판정(`diff`)" 으로 나누고, 목록 비교(`compare`)와 ERD 범위(`compareErd`)가 같이 쓴다. 권한 확인(`version()` : 로그인한 프로젝트의 버전만)과 오류 코드(`MODEL_VERSION_NOT_FOUND`, `INVALID_MODEL_VERSION`)도 같은 경로다.
- 응답 : `nodes[]` = `{ node, items[], extras[] }`, `edges[]`. 객체 하나는 비교 목록의 `Change` 와 같은 모양이고, 그리는 데 필요한 달라지지 않은 객체가 `UNCHANGED`(변경 전후 같은 값)로 함께 온다.
  - 물리 : node = 테이블, items = 컬럼 전부, extras = **달라진** 인덱스·제약조건, edges = 관계.
  - 논리 : node = 엔터티(모든 논리 모델), items = 속성 전부, extras = 식별자 전부(식별자 표시에 필요), edges = 논리 관계.
- **범위 (큰 모델)** : 모델 전체가 아니라 변경 영역만 준다. 달라진 노드 = 자신이 달라졌거나 컬럼·속성·인덱스·제약조건·식별자가 달라진 것. 우선순위 `지정한 객체가 속한 노드 → 그 이웃 → 달라진 노드 → 달라진 관계의 양 끝 → 달라진 노드의 이웃` 순으로 `limit` 개까지 담고, 달라진 노드가 다 들어가지 못하면 `truncated`. 관계는 범위 안의 노드에 한쪽이라도 걸린 것(상대가 범위 밖이면 선은 못 그려도 FK 표시와 상세에 쓴다).
- 조회만 한다 : 읽기 전용 트랜잭션(REPEATABLE_READ), 버전도 현재 모델도 배치도 쓰지 않는다. `ModelVersion` 은 `@Immutable` 그대로다.
- 권한 : 컨트롤러의 `VIEWER` 이상. 복구 세션은 기존 규칙대로 막힌다.
- 한계 : 응답은 줄었지만 서버는 비교할 때처럼 두 모델 전체를 메모리에 올린다 (M-9 12.9 의 큰 모델 과제 그대로).

## 3. 화면 — 버전 비교 대화상자의 [ERD 비교]

기존 비교 화면(`versionDialogs.tsx` 의 `CompareView`)은 그대로 두고 보기 전환만 더했다 : **변경 목록**(기존) | **ERD 비교**.

```text
기준 버전 → 비교 대상                                  [변경 목록 | ERD 비교]
추가 n · 삭제 n · 수정 n · 변경 없음 n                  (변경 요약, 기존)
[물리 ERD (n) | 논리 ERD (n)]  + 추가  − 삭제  ~ 수정  읽기 전용  [전체 보기]
┌ 달라진 객체 ┬ 변경 전 · 기준 버전 ────┬ 변경 후 · 대상 버전 / 현재 모델 ┐
│ ~ TB_A      │                         │                                 │
│ − TB_B      │   (React Flow)          │   (React Flow)                  │
│ + 관계 FK_1 │                         │                                 │
└─────────────┴─────────────────────────┴─────────────────────────────────┘
고른 객체의 달라진 내용 (변경 목록과 같은 줄, 같은 변경 전후 표)
```

- **변경 전후 나란히** : 삭제된 객체는 변경 전에만, 추가된 객체는 변경 후에만, 수정된 객체는 양쪽에 그 시점의 이름·값으로 그린다.
- **같은 배치·같은 보기 위치** : 변경 전후를 합친 그래프로 ELK 자동 배치를 한 번 계산해 양쪽에 같이 쓴다(노드 높이는 컬럼이 많은 쪽). 한쪽을 확대·이동하면 다른 쪽도 같이 움직인다. 같은 객체는 항상 양쪽의 같은 자리에 있다. 배치는 저장하지 않는다.
- **변경 목록 ↔ ERD** : 변경 목록에서 객체를 펴면 [ERD 에서 보기] 가 있다(테이블·컬럼·관계·인덱스·제약조건·엔터티·속성·식별자·논리 관계). 누르면 ERD 비교로 넘어가 그 객체가 속한 테이블·엔터티를 가운데에 놓고 선택하며, 아래에 그 객체의 변경 전후가 펴진다. 범위(`limit`) 밖의 객체면 그 객체부터 다시 받는다(`focusType`·`focusId`). ERD 왼쪽의 달라진 객체 목록과 노드·관계선을 눌러도 같다.
- 스키마·논리 모델·매핑의 변경은 ERD 에 그리지 않는다 — 변경 목록의 상세 비교로 본다(지시 5.5).

### 3.1 변경 상태 표현

색만으로 구분하지 않는다. 기존 색 토큰(`--gh-success`·`--gh-danger`·`--gh-accent`)과 `Label` 을 쓰고 새 디자인 체계는 없다.

| 상태 | 노드 | 컬럼·속성 행 | 관계선 |
|---|---|---|---|
| ADDED | 테두리 + 배지 `+ 추가` | 행 배경 + 이름 앞 `+` | 색 + 굵게 + 선 위 글자 `+ 추가` |
| REMOVED | **점선** 테두리 + 배지 `− 삭제` + 이름 취소선 | 행 배경 + `−` + 취소선 | `− 삭제` |
| MODIFIED | 테두리 + 배지 `~ 수정` | 행 배경 + `~` | `~ 수정` |
| UNCHANGED | 보통의 ERD 노드 | 표시 없음 | 보통의 선 |

- 테이블 자신은 그대로여도 **컬럼·인덱스·제약조건이 달라졌으면 `~ 수정`** 으로 강조한다. 달라진 관계만 걸린 테이블은 강조하지 않고 관계선이 변경을 나타낸다.
- 테이블 이름을 바꾸면 그 테이블의 모든 컬럼이 들고 있는 테이블명(`tableName`)도 따라 바뀐다. 비교 판정은 M-9 그대로(컬럼마다 수정)지만 **ERD 에서는 이것만으로 컬럼을 강조하지 않는다** (변경 목록에는 그대로 나온다).
- 소속 스키마가 바뀐 테이블은 부제에 그 시점의 스키마명을 적는다. 논리는 여러 모델을 한 화면에 그리므로 엔터티 부제에 모델명을 적는다.
- 컬럼이 20개를 넘어 다 그리지 못하는 노드는 달라진 행을 먼저 그린다. 축소하면 컬럼을 생략하는 것은 기존 ERD 와 같다.
- 복합 FK 는 컬럼 쌍이 하나만 달라져도 관계가 `~ 수정`(`columns`)이다. 관계는 수정 API 가 없어(삭제 후 재등록) 화면으로 만든 변경은 보통 `− 삭제` + `+ 추가` 로 나온다 — ID 가 다른 관계를 이름·구성이 같다고 같은 관계로 보지 않는다.

### 3.2 읽기 전용

- `nodesDraggable`·`nodesConnectable`·`elementsSelectable` 을 모두 끄고 삭제 키도 없다. 되는 것은 확대·축소·이동·선택뿐이다.
- 화면에 등록·수정·삭제·배치 저장 버튼이 없고, 부르는 API 는 `GET /api/modelVersion/compare/erd` 하나다. 편집 권한이 있는 사용자도 여기서는 편집할 수 없다.
- 과거 스냅샷을 바꾸는 API 는 서버에 없다(M-9).

## 7. 하지 않은 것과 한계

- 큰 모델(수천 테이블)의 실측은 하지 않았다. 화면이 받는 양은 `limit` 로 묶였지만 서버는 두 모델 전체를 읽는다(M-9 12.9).
- 달라진 노드가 `limit` 를 넘으면 ERD 는 일부만 그린다. 나머지는 변경 목록에서 골라 간다 — ERD 안에서 쪽을 넘기는 기능은 없다.
- 이름 변경 **후보** 추정은 없다. 내부 ID 가 같으면 수정, 다르면 삭제 + 추가로만 본다. (원본 스냅샷 비교 ① 에서는 ID 가 없어 후보 표시가 필요하다 — 그때의 과제)
- 과거 버전 하나만 ERD 로 보는 화면(비교 없이)은 만들지 않았다.
- 인덱스·제약조건, 매핑은 ERD 에 그리지 않는다(테이블의 `~ 수정` 과 상세·변경 목록으로 본다).
- 영어 화면의 변경 배지는 기존 변경 목록과 같은 문구(`Add`·`Edit`·`Delete`)를 쓴다.

## 8. 남은 M-10

| 구분 | 상태 | 선행 기능의 준비 상태 |
|---|---|---|
| ① 원본 스냅샷 A ↔ B | 미구현 | **준비 안 됨.** AI-1(메타데이터 저장 구조·스냅샷)과 AI-2(MCP 수집·동기화)가 미구현이다 — 외부 DB 연결, 원본 카탈로그 테이블, 수집 작업 모델이 모두 없다. 비교할 스냅샷 자체가 없다 |
| ② 물리 모델 ↔ 최신 원본 스냅샷 | 미구현 | **준비 안 됨.** M-4(역공학 결과 가져오기)가 미구현이고 M-4 도 AI-1·AI-2 를 기다린다 |
| ③ 모델 버전 간 | **ERD 표시까지 구현 (이 문서)** | — |

①·② 를 만들 때 다시 쓸 수 있는 것 : 변경 표시가 있는 노드·관계선(`diff`), 변경 전후 두 화면과 보기 위치 맞춤(`VersionErd`), 범위 제한 방식(달라진 노드 + 이웃, 지정 객체 우선). 다시 쓸 수 없는 것 : **객체 짝짓기** — 원본 카탈로그에는 Lexorma 의 내부 ID 가 없어 이름·스키마로 짝지어야 하고, 이름 변경은 후보로만 보여야 한다(로드맵 M-10 변경 항목).

정책 결정이 필요한 것 : 달라진 노드가 `limit` 를 넘을 때 ERD 안에서 나눠 보는 방식, 관계 "수정" API 를 둘지(지금은 삭제 + 재등록이라 비교에서 삭제 + 추가로 보인다), 프로젝트 삭제 시 버전 보존(M-9 13.3 그대로).
