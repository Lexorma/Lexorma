# 초기 마이그레이션 통합 · 스키마 단위 TABLE/VIEW 식별

2026-11-13. 예전 Flyway V0~V6 을 V0·V1 로 합치고, TABLE·VIEW 이름의 유일성 범위를 **프로젝트 → 스키마**로 바꿨다 (D-25 변경, 로드맵 D-03). M-4 원본 역공학·동기화가 실제 DB 처럼 `public.tb_user` 와 `archive.tb_user` 를 함께 다룰 수 있게 하는 데이터 모델 정비다. 역공학·동기화 자체는 구현하지 않았다.

## 1. 결정

| 항목 | 내용 |
|---|---|
| 식별 | TABLE `TBL_SN`·VIEW `VIEW_SN` 내부 ID(PK)는 그대로. 소속은 `SCHM_SN`(필수, 프로젝트 전체에서 유일한 스키마 ID) |
| 이름 유일성 (D-25 변경) | 기존 : 프로젝트 안에서 TABLE·VIEW 이름 하나 → **변경 : 스키마 안에서 하나**. `UX_TBL_01 (SCHM_SN, TBL_NM)`, `UX_VIEW_01 (SCHM_SN, VIEW_NM)`. 다른 스키마·다른 프로젝트에는 같은 이름 가능 |
| 공통 이름 공간 | 같은 스키마의 TABLE·VIEW 는 이름을 나눠 쓴다. 저장 테이블이 달라 UNIQUE 로는 교차 중복을 막을 수 없으므로 **스키마 이름 공간 잠금 + 서비스 검사** (별도 이름 레지스트리 테이블은 두지 않았다 — 4장) |
| 승인 대기 이름 (D-26 유지) | 변경 요청은 이름을 선점하지 않는다. 승인 때 **요청한 스키마**에서 다시 검사하고, 겹치면 400 `SAVED_DATA_EXISTS` 로 거절 (확정 정의·요청·이력·다른 객체 그대로) |
| PK 를 바꾸지 않은 이유 | 관계·인덱스·제약·VIEW 참조·매핑·이력·모델 버전·ERD 배치가 모두 내부 ID 로 이어져 있다. `SCHM_SN` 을 PK 에 넣으면 이 연결과 스냅샷 비교를 모두 바꿔야 하고, 스키마 이동이 ID 변경이 된다 |
| 프로젝트 정합 | 등록·이동할 스키마는 `SchemaService.resolveSchema(projectId, schemaId)` 로만 정한다 → 다른 프로젝트 스키마는 `SCHEMA_IS_NOT_DEFINED` |

## 2. 기존 구조 분석 (변경 전)

- **마이그레이션** : V0 스키마, V1 예제, V2 원본 인덱스 표현식(AI-2b), V3 인덱스 출처·변경 요청·`IDX_YN` 이관(M-14), V4 고급 인덱스, V5 LEXORMA 예제 인덱스(임시 테이블 `TMP_IDX_SEED`), V6 VIEW 모델·예제(M-15). V2~V6 은 `ALTER TABLE … ADD COLUMN`·새 테이블·COMMENT·예제 INSERT·데이터 보정 UPDATE 를 섞어 가졌다. PostgreSQL·H2 는 시퀀스 문법과 세션 테이블 컬럼 타입만 다르다.
- **이름 제약** : `TB_TBL` 에는 이름 UNIQUE 가 **없었다** (서비스만 검사), `TB_VIEW` 는 `UX_VIEW_01 (PRJ_SN, VIEW_NM)`. 교차 중복은 `ObjectNamespace` 가 프로젝트 기본 스키마 행을 잠그고 프로젝트 단위로 검사했다.
- **이름으로 테이블을 찾던 곳** : 테이블 등록·수정·엑셀 업로드의 중복 검사, 테이블 이름 변경 때 참조 테이블명 일괄 변경(프로젝트 전체 이름 일치), 참조 테이블명 → `REF_COLUMN` 관계 동기화(프로젝트에서 그 이름이 하나일 때), 테이블 DDL·통합 DDL 의 참조 PK 조회, 컬럼 엑셀 업로드의 테이블명, 컬럼 등록 화면의 테이블·참조 테이블 자동완성, VIEW 의 이름 충돌·모델 밖 참조 확인, 물리명 추천의 충돌 판단, 물리 ERD 의 새 테이블 위치 지정.
- **ID 로 이어져 바뀔 것이 없던 곳** : FK·인덱스·제약(테이블 ID), VIEW 참조(테이블·VIEW ID), 논리·물리 매핑, 변경 이력·모델 버전(내부 ID 비교), ERD 배치 JSON(노드 키 = 테이블 ID), 원본 카탈로그(독립).

## 3. 이름 기반 참조 (`TableNameResolver`)

참조 테이블명(`RFRNC_TBL_NM`)과 컬럼 엑셀의 테이블명은 `테이블명` 또는 `스키마명.테이블명` 이다. 모든 곳이 같은 규칙을 쓴다 (관계 동기화, 테이블 DDL·통합 DDL, 이름 변경 때 참조 갱신, 컬럼 등록·일괄 편집·엑셀 검증).

1. `스키마명.테이블명` → 그 스키마의 테이블 (대소문자 무시)
2. `테이블명` → 참조하는 테이블과 **같은 스키마**에 있으면 그것
3. 없으면 프로젝트에서 그 이름이 **하나뿐일 때** 그것 (예전 데이터 호환 : 다른 스키마의 테이블을 이름만으로 참조하던 것)
4. 여러 스키마에 있으면 **모호** : 새로 적거나 바꾼 값은 거절 ("스키마명.테이블명으로 적어주세요"), 이미 확정된 `REF_COLUMN` 관계의 대상이 후보 안에 있으면 그 관계를 유지한다 — **확정된 FK 를 이름으로 다시 추론해 다른 테이블로 바꾸지 않는다**. DDL 은 모호한 이름의 FK 를 만들지 않고 경고한다.

- 테이블 이름 변경·스키마 이동 : 바꾸기 전 기준으로 이 테이블로 정해지던 참조 테이블명만 고친다 (`스키마명.` 을 붙였던 것은 새 스키마명으로). 다른 스키마의 같은 이름을 가리키던 참조는 그대로.
- 스키마명 변경 : `옛스키마명.` 으로 적은 참조 테이블명을 새 이름으로 고친다. 관계는 내부 ID 라 그대로.
- 컬럼 엑셀 업로드 : 테이블명이 여러 스키마에 있으면 `스키마명.테이블명` 으로 적어야 한다 (아니면 업로드 전체 거절, 예전처럼). 컬럼의 `TBL_NM` 에는 실제 테이블명이 들어간다.
- 화면 : 참조 테이블 자동완성·컬럼 등록의 테이블 목록은 같은 이름이 여러 개일 때 `스키마명.테이블명` 으로 보이고, 같은 이름이 여러 개면 자동 선택하지 않는다. `/api/selectColumn/table/{keyword}` 는 `스키마명.테이블명` 검색을 받는다.
- 물리명 추천 : 충돌은 매핑된 테이블의 스키마(매핑이 없으면 기본 스키마)의 같은 이름만 본다.

## 4. 잠금과 동시성

- **스키마 이름 공간 잠금** = 그 스키마 행의 배타 잠금 (`ObjectNamespace.lock(projectId, viewGraph, schemaIds)`). 한 트랜잭션에서 필요한 스키마를 **한 번에** 잠그고, 순서는 **기본 스키마 → 나머지 스키마 ID 오름차순** (전역 순서라 교착 없음). 그다음 테이블·VIEW 행.
- **VIEW 참조 그래프 잠금** = 기본 스키마 행. VIEW 의 등록·수정·변경 요청 처리·삭제와 테이블 삭제는 스키마와 관계없이 함께 잡는다. 이유 : VIEW 참조는 스키마를 넘고, 순환 검사(A→B, B→A 를 서로 다른 스키마에서 동시에)와 "참조 대상 삭제 ↔ 참조 추가"는 스키마 잠금만으로 직렬화되지 않는다.
- **경로별 잠금**

  | 경로 | 잠그는 이름 공간 |
  |---|---|
  | 테이블 등록 / 엑셀 업로드 | 그 스키마 / 기본 스키마 |
  | 테이블 수정(이름 변경·스키마 이동) | 지금 스키마 + 옮길 스키마 (잠근 뒤 행을 다시 읽어 그사이 이동되었으면 거절) |
  | 테이블 삭제 | VIEW 참조 그래프 + 테이블들의 스키마 |
  | VIEW 등록·수정·변경 요청 처리·삭제 | VIEW 참조 그래프 + 지금·옮길(요청한) 스키마 |
  | 스키마 이름 변경·삭제 | 그 스키마 행 (같은 행이라 그 스키마의 등록·이동과 직렬화) |
  | 승인·인덱스·제약·관계·매핑 | 잠그지 않는다 (이름을 바꾸지 않음, 행 잠금만) |

- 결과 : 다른 스키마의 TABLE 등록·이름 변경·엑셀 업로드는 서로 기다리지 않는다. VIEW 쓰기는 프로젝트 안에서 차례로 처리된다 (참조 그래프 때문, 짧은 트랜잭션).
- **레지스트리 테이블 대안 (택하지 않음)** : `(SCHM_SN, OBJ_NM)` UNIQUE 를 가진 공통 이름 테이블을 두면 DB 가 교차 중복을 막지만, TABLE·VIEW 의 모든 쓰기 경로·이력·버전·삭제·마이그레이션에 동기화 행이 더해지고 행 두 곳의 정합을 다시 지켜야 한다. 이미 있는 잠금 + 각자의 UNIQUE 로 동시 요청에서도 같은 스키마의 TABLE·VIEW 중복이 생기지 않는 것을 테스트로 확인해 기존 구조를 재사용했다.
- 같은 종류끼리는 DB UNIQUE 도 막는다 (서비스를 거치지 않는 쓰기 포함).

## 5. DDL·ERD

- 기존 생성기 그대로 : 기본 스키마가 아닌 객체는 `스키마명.이름`. 같은 이름의 테이블이 두 스키마에 있어도 `CREATE TABLE MBR` / `CREATE TABLE ARCHIVE.MBR` 로 따로 나오고, 인덱스·FK 도 내부 ID 로 맞는 테이블에 붙는다.
- 통합 DDL Export (M-11) : 참조 테이블명은 테이블마다 자기 스키마 기준으로 정한다. **"스키마명 포함" 의 이름이 기본이 아닌 스키마 이름과 같아** 두 모델 스키마가 실제 DB 의 한 스키마로 합쳐지는데 같은 이름 객체가 있으면 **만들지 않는다** (오류). 겹치는 이름이 없으면 경고만 한다. 이름 충돌 경고는 스키마 단위 그대로.
- ERD : 노드 ID = 테이블 ID 그대로(배치 저장 데이터 유지). 같은 이름이 여러 스키마에서 함께 보이면 노드 제목 앞에 스키마명을 작게 붙인다. 새 테이블 위치 지정은 등록한 스키마로 좁혀 찾는다. 상세 패널·VIEW 패널은 원래 스키마를 보여 준다.

## 6. V0·V1 통합

- **V0** = 예전 V0 + V2~V6 의 스키마 변경을 최종 정의로 : `TB_SRC_IDX.CND_CN`, `TB_SRC_IDX_COL`(`SRC_COL_SN` null 허용, `EXPR_CN`, `SORT_CD`), `TB_TBL_IDX`(`IDX_SRC_CD` not null 기본값 없음, `DRVN_COL_SN`, `CND_CN`, `UX_TBL_IDX_01`), `TB_TBL_IDX_COL`(`COL_SN` null 허용, `EXPR_CN`, `SORT_CD`), `TB_IDX_CHG_DMND`, `TB_VIEW`·`TB_VIEW_COL`·`TB_VIEW_RFRNC`·`TB_VIEW_CHG_DMND`(시퀀스·인덱스·FK·COMMENT). 컬럼 순서는 예전 `ALTER … ADD` 순서와 같다. 이번 정책으로 `IX_TBL_01 (SCHM_SN)` → `UX_TBL_01 (SCHM_SN, TBL_NM)`, `UX_VIEW_01 (PRJ_SN, VIEW_NM)` → `(SCHM_SN, VIEW_NM)`, `IX_VIEW_01 (SCHM_SN)` 제거(UX 의 앞부분과 같아 불필요).
- **V1** = 예전 V1 + V2~V6 의 예제를 **원래 순서 그대로** 6)~10) 구역으로 (시퀀스에서 받는 예제 ID 가 예전 설치와 같다). 예전 V1 행을 고치던 보정 UPDATE 4개(`TB_SRC_IDX_COL.SRC_COL_SN`·`TB_TBL_IDX_COL.COL_SN` 컬럼의 NULL 허용, 대응 논리 속성의 필수 여부)는 해당 INSERT 에 합쳤다. 컬럼 인덱스 여부 → 출처 COLUMN 인덱스 변환(예전 V3)은 예제 데이터를 만드는 단계로 남겼다. 예제 인덱스 목록은 V0 의 `create index` 와 같게 고쳤다 (`UX_TBL_01`, `UX_VIEW_01`, `IX_VIEW_01` 없음 → 예제 인덱스 90개, 구성 컬럼 129개).
- 두 벤더 파일은 PostgreSQL 을 기준으로 만들고 H2 는 시퀀스 문법(`next value for`)과 세션 테이블만 다르다.
- **동등성 검증 (일회성, 기록)** : 빈 DB 에 예전 V0~V6 과 새 V0·V1 을 각각 적용하고 정규화 덤프(테이블·컬럼 순서·타입·NULL·기본값·COMMENT·PK·인덱스·FK·시퀀스, 시각 컬럼을 뺀 모든 행)를 비교했다 — **H2·PostgreSQL 18 모두** 차이는 의도한 것뿐 : `IX_TBL_01`→`UX_TBL_01`, `UX_VIEW_01` 컬럼, `IX_VIEW_01` 없음, 그에 따른 예제 인덱스 행 1개 감소와 뒤 인덱스·인덱스 컬럼 ID 이동(`SQ_TBL_IDX` 현재값 50 감소). 나머지 데이터·ID·COMMENT 는 같다.
- 제거 : `V2__source_index_expression.sql`, `V3__index_management.sql`, `V4__index_advanced.sql`, `V5__lexorma_index_seed.sql`, `V6__view_management.sql` (양 벤더). 업그레이드 경로 테스트 `IndexMigrationV3Test`·`ViewMigrationV6Test` 와 `LexormaIndexSeedV5Test` 의 V4→V5 경우는 대상 파일이 없어져 지웠다 (신규 설치 비교는 `LexormaIndexSeedTest` 로 남겼다).

## 7. 기존 DB 호환성 (주의)

- **이미 V0~V5(또는 V6)를 적용한 DB 는 이 버전으로 기동하지 않는다.** Flyway 검증이 ① V0·V1 체크섬 불일치 ② 적용 이력에 있는데 파일이 없는 V2~V6 으로 실패한다. 데이터는 바뀌지 않는다 (기동 전에 멈춘다).
- 대상 : 로컬 개발 DB(`lexorma` 컨테이너 등), V2~V5 가 들어간 `main`·`dev` 빌드로 만든 설치. **이번 작업은 기존 DB 를 건드리지 않았다** (검증은 새 임시 DB 에서만, `flyway clean`·`repair`·DROP 없음).
- 선택지 (결정 필요, 데이터를 남겨야 하는 설치가 있을 때만) :
  1. **재생성** (지금 정책의 기본) : 개발·검증 DB 는 빈 DB 로 다시 만든다. 예제 외 데이터는 사라진다.
  2. **데이터 이전** : 예전 빌드로 기동한 DB 에서 데이터를 내보내고 새 V0·V1 로 만든 DB 에 넣는다. 스키마 차이는 이번 정책의 인덱스 두 개뿐이라 테이블 단위 이전이 가능하지만, 스키마별 같은 이름이 없는지(프로젝트 단위로 막혀 있었으므로 없다)와 시퀀스 현재값을 맞춰야 한다.
  3. **이력 정리 후 기준선** (예 : `flyway_schema_history` 를 새 V0·V1 기준으로 다시 쓰고 `IX_TBL_01`·`UX_VIEW_01`·`IX_VIEW_01` 을 손으로 바꾸기) : 가능하지만 검증되지 않은 수동 절차라 하지 않았다. `flyway repair` 만으로는 이력이 맞지 않는다.
- 정식 출시 이후의 정책(적용한 파일은 고치지 않고 새 버전을 더한다)은 그대로다. 이번 통합은 출시 전 기준선을 다시 잡은 것이다.

## 8. M-4 역공학에서 쓸 식별 기준

- 모델 객체의 식별 = 내부 ID. 원본과의 대응 = (프로젝트, 스키마, 객체 이름 — 대문자 비교, 원본 카탈로그의 비교 이름 규칙과 맞춤) → 스키마 안에서 하나로 정해진다.
- 원본 스키마 ↔ 모델 스키마는 이름으로 잇되, 모델의 기본 스키마(`DEFAULT`)와 원본의 실제 스키마명(예 : `public`)을 어떻게 대응시킬지는 M-4 에서 정한다 (지금은 DDL 의 "스키마명 포함" 으로만 실제 이름을 붙인다).
- 참조 테이블명 약식 입력(D-04)은 유지했다. 역공학이 만드는 FK 는 관계(ID)로 만들고 약식 입력을 쓰지 않는 것을 권장한다.

## 10. 남은 것

- 기존 DB 전환 (7장, 결정 필요).
- 이름 기반 참조는 `RFRNC_TBL_NM`·컬럼 `TBL_NM`(비정규화 표시값)·엑셀 테이블명에 남아 있다 — 모두 위 규칙으로 해석하고 ID 로 저장되는 관계를 기준으로 한다. 폐기 여부는 D-04.
