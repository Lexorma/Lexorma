- 단계 : 1차 분석·설계 (2026-11-24, 1~14장) → 사용자 확정 AES-D01~D12 (13장) → 2차 서버 구현 (2026-11-25, 15장) → AES-D13~D16 확정 → 3차 서버 최종 보완·화면·실제 Provider·전체 회귀 (2026-11-25, 16장 — M-8 시험 감시 결함으로 완료 보류) → AES-D17~D19 확정 → **최종 검증 보완 (2026-11-25, 17장) — 완료**. 1~15장은 그때의 기록이며, 3차에서 바뀐 것은 16장이 우선한다 (사유 분리·구조화 단계 Tool 요청·서버 맥락·작은 컨텍스트 문구).
- 관리 : completed-work.md [AI-4] AI 공통 실행 안정성 개선 (D-35 는 완료 상태 유지 — 커밋 `95636a3`). D-35 후속 결정 ①(부분 답변)·④(R4 출력 한도)를 여기서 다뤘다. 이 작업으로 풀지 않은 후속은 pending-work.md [AI-4] (17.6).
- 근거 : 코드 읽기 + 측정. 측정은 세션 scratchpad `stab/` (격리 사본으로 만든 최종 JAR `95636a3` = cur 과 D-35 이전 `c1404f0` = base, 임시 H2, D35-FINAL 과 같은 격리 예제 데이터, 이미 실행 중인 로컬 Ollama 0.40.18 `gemma4:e4b` — 외부 전송 없음). Lexorma 와 Ollama 사이에 로컬 기록 프록시를 두어 요청·응답 원문(prompt_eval_count·eval_count·done_reason·thinking)을 남겼다 (`capture-*.jsonl`). 가짜 Provider 재현은 격리 사본에만 둔 측정 테스트 `AiStabilityProbeTest` (저장소에 넣지 않음).
- 표기 : **실측** = Ollama 가 보고한 토큰 수, **추정** = `TokenEstimator` 규칙.

## 1. 배경 — D35-FINAL 에서 확인한 문제

1. 논리 Tool 3개 추가로 Tool 단계 요청의 고정 입력이 늘었다.
2. 추정이 실측보다 크다 (D35-FINAL 1.5~1.9배).
3. 조회가 성공한 뒤에도 다음 요청이 예산을 넘으면 질의 전체가 실패한다 (S12).
4. 관계가 많은 물리 질문(R4)이 출력 한도에서 잘린 경우가 있었다 (원인 미확정이었다).
5. 실제 LLM 의 분할 조회 능력은 예산 때문에 충분히 보지 못했다.

## 2. 현재 실행 구조 (코드 기준)

| 순서 | 위치 | 하는 일 |
|---|---|---|
| 1 | `AiMetadataQueryRestController.query` → `AiMetadataQueryService.query` | 질문 검증(1~1,000자) |
| 2 | `ExecutionContextVerifier.verify(context, "VIEWER")` | 프로젝트·멤버십·역할 |
| 3 | `AiProviderClients.callDefaultWith` | 프로젝트 → 시스템 기본 Provider 확인, SEC-1 연결, 모델 정보(`/api/show` — tools·컨텍스트 길이) |

| 5 | `TokenBudget.plan(modelInfo)` → `TokenMeter` | 컨텍스트 = min(16,384, 모델), 출력 4,096(작은 모델은 비례 축소), 입력 = 컨텍스트 − 출력, 질의 누적 100,000 |
| 6 | `toolCalling` 1단계 : `ChatClient.prompt().system(systemPrompt).user(question).tools(13).advisors(ToolCallingAdvisor, TokenMeter.Advisor)` | 모델 호출 ↔ Tool 실행 반복 (Spring AI `ToolCallingAdvisor` + `DefaultToolCallingManager` — 같은 Tool 4·전체 8, THROW) |
| 7 | `TokenMeter.Advisor.adviseCall` (반복 안, 모델 호출마다) | **보내기 전 `admit`** : 추정 입력 > 입력 상한 또는 누적 + 추정 + 출력 > 100,000 이면 `AI_TOKEN_BUDGET_EXCEEDED` 던짐 → **질의 전체 종료**. 받은 뒤 `record` : 실측 누적, done_reason `length` 면 같은 오류 |
| 8 | `MetadataToolset.Guarded.call` (Tool 마다) | VIEWER 재검증(실패 = 질의 종료) → 읽기 전용 트랜잭션 → 결과 24,000자 판정(넘으면 RESULT_TOO_LARGE 결과 — 질의는 계속) → 실패면 근거 되돌림 → 기록 `session.result` |
| 9 | Tool 함수(`MetadataTools.*`) | 조회 + **근거 기록 `saw`** (응답에 실린 대상) |
| 10 | 모델이 Tool 을 더 부르지 않으면 1단계 끝 → 초안(draft) | 초안이 비면 호출 실패. Tool 결과가 없으면 2단계 없이 근거 없는 답 |
| 11 | `structure` 2단계 : `system(structuringPrompt + parser.format())` + `user(structuringRequest(question, draft, session.results()))` — **Tool 정의 없음** | 결과 원문 합 24,000자 넘으면 뒤를 잘라 "[truncated…]" (재요청 포함). 스키마 실패면 1번 다시, 그래도 실패면 `AI_STRUCTURED_OUTPUT_INVALID` |
| 12 | `EvidenceVerifier.verify(session, evidence)` | VIEWER 재검증 → 근거 판정 (이 질의 Tool 결과·버전·설명 기록) |
| 13 | `QueryResult` 반환 | 답·모델·Tool 기록·근거·사용량(실측·추정)·모드. **저장하지 않는다** (AI-4 답변 저장 없음) |

```
질문 ─▶ 검증(VIEWER) ─▶ Provider·모델 정보 ─▶ 예산 계획
          │
          ▼  1단계 (Tool 13개 정의를 요청마다 실음)
   ┌─▶ [admit 입력·누적] ──X── AI_TOKEN_BUDGET_EXCEEDED ──▶ 질의 실패
   │        │ 보냄
   │   모델 응답 ──[record: done=length]──X── AI_TOKEN_BUDGET_EXCEEDED ──▶ 실패
   │        │ tool_calls?
   │   [호출 상한 4/8] ──X── AI_TOOL_CALL_LIMIT_EXCEEDED ──▶ 실패
   │   [Tool : VIEWER 재검증] ──X── 권한 오류 ──▶ 실패 (보안)
   │   [24,000자] ── 넘으면 RESULT_TOO_LARGE 를 결과로 (계속) · 근거 되돌림
   └── 결과 누적 (근거 saw)
            │ tool_calls 없음 → 초안
            ▼  2단계 구조화 (Tool 정의 없음, 결과 원문 ≤ 24,000자)
       [admit] ──X── 예산 초과 ──▶ 실패      [done=length] ──X── 실패
       스키마 실패 → 1번 재요청 → 실패면 AI_STRUCTURED_OUTPUT_INVALID
            ▼
       근거 검증 ─▶ 응답
```

### 4.3 질의 단위 (실측, cur)

질의 하나 = Tool 단계 2~3 요청 + 구조화 1(+재요청). 실측 prompt 합 5,700~13,000, 출력 합 800~6,000. **누적 상한(100,000)에 닿은 사례 없음** — 실제로 막는 것은 요청 하나의 입력 상한(추정)과 요청 하나의 출력 한도다.

### 4.4 최종 답변(구조화) 예산

- 출력 4,096 은 **요청마다** 따로 정해진다. Tool 단계의 마지막 요청(초안)과 구조화 요청이 각자 4,096 을 쓴다.
- 구조화 요청의 입력은 Tool 단계 동안 **미리 확보하지 않는다**. 구조화 요청은 Tool 정의를 싣지 않고 결과를 다시 넣는 새 입력이다 : 구조화 입력 ≈ 마지막 Tool 단계 입력 − Tool 정의(실측 약 2,100) − 시스템 지시(약 400) + 구조화 지시·스키마(약 1,160) + 초안(최대 4,096). 초안이 길면 Tool 단계는 통과했는데 구조화가 입력 상한을 넘을 수 있다 (계산상 가능, 이번 측정에서는 발생 안 함 — 측정 테스트 B16 은 그보다 먼저 Tool 단계에서 막혔다).
- 구조화 입력의 결과 원문은 24,000자에서 잘린다. Tool 단계 예산(추정 12,288) 안의 결과는 실제로 24,000자를 넘기 어렵다 (B17 : 결과 약 20,000자에서 자르지 않음).
- Tool 단계가 예산으로 중단되면 **구조화로 넘어갈 길이 없다** (예외가 질의 밖으로 나간다).

| B17 | 구조화 입력 24,000자 자르기 (가짜) | 자르지 않음 (결과 약 20,000자) | — | 미재현 |

**B13 (새로 확인한 위험)** : 모델이 알려 준 컨텍스트가 6,144 이하이면 Tool 단계 고정 입력(추정 약 4,600)만으로 입력 상한을 넘는다. D-35 이전에는 고정 입력이 추정 약 3,000~3,500 이라 6,144 컨텍스트 모델도 첫 요청을 보낼 수 있었다 (계산). 지금 등록할 수 있는 Provider 는 Ollama 뿐이고 최근 모델은 대개 8k 이상을 알려 주지만, 작은 컨텍스트 모델로는 질의가 시작되지 않는다.

## 6. R4 원인 분석 (출력 한도)

- 증거 : 실제 실패 3건(D35-FINAL cur 2건, 이번 base 1건)과 이번 cur B02 실패 1건 **모두 구조화 단계**, done_reason `length`, 출력 4,096 중 **생각(thinking) 5,400~7,000자**. 같은 구조화 단계가 생각 없이 답한 경우는 1,457~1,882 토큰으로 끝났다.
- 원인 : Ollama 요청에 `think` 를 보내지 않아(코드에 없음) 생각 기능이 있는 `gemma4:e4b` 가 기본으로 생각한다. 생각 토큰이 같은 `num_predict` 를 쓴다. 생각 길이의 변동이 커서(0~7,000자) 긴 결과(관계·컬럼 목록)를 JSON 으로 옮기는 구조화 단계가 가끔 한도를 넘는다.
- D-35 영향 : 이번에 정해 둔 반복(각 5회)에서 cur 5/5 · base 4/5 — D-35 이전에도 같은 실패가 있다. D35-FINAL 의 cur 1/3 · base 2/2 와 합치면 cur 6/8 · base 6/7 로, **D-35 회귀라는 증거는 없다** (표본이 작아 확률 차이는 판단하지 않는다). 출력 쪽은 D-35 의 입력 증가와 무관한 구조다.
- 재생 실험 (실패한 구조화 요청 원문을 그대로 다시 보냄, 각 3회) : 생각 기본 → 2회 `length` (생각 5,400자), 1회 정상 · **`think:false` → 3회 모두 정상 (출력 1,516~2,506, JSON 파싱 성공)**.
- 개선 후보 (13장 ⑨) : 구조화 단계에만 생각 끄기 (Spring AI 2.0.2 `OllamaChatOptions.thinkOption` 지원 — 새 의존성 없음). Tool 단계의 생각은 Tool 선택에 쓰일 수 있어 유지 (2차에서 실제 비교). 출력 한도 확대·근거 축소는 기본 해결책으로 하지 않는다. 출력 한도 초과 시 오류 문구는 지금 '토큰 예산 초과' 하나라 원인(입력/출력)을 구분하지 않는다 — 문구 보완 후보.

### 7.2 가능 조건 / 불가 조건

가능 : (1) 모델에게 실제로 전달된 성공 Tool 결과가 하나 이상 (2) 실행 컨텍스트 재검증 통과 (3) 구조화 요청의 추정 입력이 상한 안이고 누적 예산이 출력 한도만큼 남음 (4) 마감 시간 안 (5) 중단 사유가 7.1 의 '부분 답변' 줄. 불가 : 결과 없음, 보안·권한 오류, Provider 실패, 구조화 자체가 예산·스키마로 실패 — 이때는 **원래 오류를 그대로** 돌려준다 (부분 답변 실패를 새 오류로 바꾸지 않는다).

### 7.3 대안 비교

| 기준 | A 예산 부족 감지 후 최종 답변 전환 | B 최종 답변 예산 사전 확보 | C 최종 답변용 입력 재구성 | D B+C 일부 결합 |
|---|---|---|---|---|
| 정확성 | 전달된 결과만 쓰면 같음 | 같음 | 같음 (자르기·요약 없이 결과 원문) | 같음 |
| 안정성 | 구조화 자체가 넘칠 수 있음 | 구조화 자리 보장 | 구조화 입력이 Tool 정의만큼 작다 | 둘 다 |
| 사용성 | 좋음 | 조기 중단으로 덜 조회할 수 있음 | 좋음 | 좋음 |
| 변경 범위 | 중 (Advisor 가 예외 대신 '중단' 응답) | 중 (예약 계산) | 작음 — **지금 구조화 단계가 이미 C 다** (Tool 정의 없이 질문·초안·결과로 새 입력) | 중 |
| Provider 호환 | 같음 | 같음 | 같음 | 같음 |
| 근거 검증 | '전달됨' 표시 필요 (8장) | 같음 | 같음 | 같음 |
| 성능 | 호출 추가 없음 (원래 있던 구조화 1번) | 같음 | 같음 | 같음 |

**추천 : D (A + C, B 는 가벼운 형태로)**
1. Tool 단계 Advisor(`TokenMeter`)가 다음 요청을 보낼 수 없으면(입력·누적 초과) 예외 대신 **'중단' 응답**(Tool 호출 없는 합성 응답, 사유 표시)을 돌려 Spring AI 반복을 끝낸다. 호출 상한은 지금처럼 THROW 로 두고 `ToolCallLimitExceededException` 을 잡아 같은 경로로 (RETURN_ERROR_RESPONSE 는 모델이 거절을 받고도 계속 부를 수 있어 쓰지 않는다).
2. 구조화 단계(C — 이미 있음)를 '부분' 모드로 실행 : 지시에 "조회가 끝나지 않았다·사유·확인하지 못한 범위를 답에 적어라", 초안이 없거나 잘렸으면 결과만으로. 결과는 **모델에게 전달된 것만** (8장).
3. B(가벼움) : 구조화 요청을 보내기 전에 그 추정 입력을 계산해 넘으면 부분 답변을 포기하고 원래 오류 — 미리 자리를 떼어 두는 예약은 하지 않는다 (결과 크기를 미리 알 수 없어 조기 중단이 잦아짐).
새 실행 엔진·Agent·라우터 없음. 바뀌는 곳 : `TokenMeter`(중단 신호), `AiMetadataQueryService.toolCalling`·`structure`(부분 모드), 응답 DTO.

## 8. Tool 결과와 근거 기록의 일관성

- 지금 : Tool 함수가 결과를 만들 때 근거를 `saw` 하고, 결과가 모델에게 가는지는 다음 요청의 `admit` 에서 정해진다. 예산 초과면 질의 전체가 실패하므로 지금은 불일치가 드러나지 않는다.
- 부분 답변을 넣으면 생기는 상태 : ① 실행 성공 + 다음 요청에 실려 모델에게 전달 ② 실행 성공 + 그 요청이 예산으로 막혀 **전달 안 됨** ③ 실패·상한 초과 (이미 되돌림) ④ 구조화 입력에서 24,000자로 잘린 결과.
- 제안 : `admit` 이 요청을 통과시킬 때 그 요청에 실린 Tool 결과(메시지의 tool 응답)를 '전달됨' 으로 표시 (세션의 결과 목록에 순번·전달 여부). 부분 답변의 구조화 입력은 전달된 결과만 쓰고, **전달되지 않은 결과가 기록한 근거는 그 호출 직전 체크포인트로 되돌린다** (D-35 의 `discardSince` 를 그대로 쓴다 — Tool 호출마다 체크포인트를 보관). ④ 는 구조화 입력에 넣지 못한 결과의 근거도 같은 방식으로 되돌리는 것을 함께 검토 (지금 구조에서는 사실상 발생하지 않음 — B17).
- 유지 : 실패 호출 근거 제거, 앞 성공 근거 유지, 설명 조회 범위·버전, 다른 프로젝트 차단, 조회하지 않은 대상 거절 — 바꾸지 않는다. 부분 답변의 근거도 같은 `EvidenceVerifier` 를 그대로 지난다.

## 9. 응답 계약 · 화면 (후보)

- `QueryResult` 에 칸 추가 (기존 칸 그대로, 기존 클라이언트는 무시) : `completion` = `{ "status": "COMPLETE" | "PARTIAL", "reason": "INPUT_BUDGET" | "TOTAL_BUDGET" | "TOOL_CALL_LIMIT" | "DRAFT_OUTPUT_LIMIT", "executedTools": n }`. 확인하지 못한 범위는 서버가 정확히 알 수 없으므로(어떤 조회를 더 하려 했는지 모름) 서버 문구는 사유만, 범위 설명은 구조화 지시로 답 안에 쓰게 한다 — 서버가 만든 '한계' 목록은 넣지 않는다.
- 근거 상태(`verification`)와 완료 상태(`completion`)는 독립 : 부분 답변의 근거도 VERIFIED 일 수 있다.
- 실패는 지금처럼 HTTP 오류(422 등) — 부분 답변은 200 + PARTIAL.
- 화면 : `AiAssistant` 답변 블록 위에 기존 안내(`ai-assistant-mode`, 서버 맥락 안내와 같은 자리·스타일)로 "조회가 끝나지 않아 일부만 확인한 답입니다 (사유)" — 한국어·영어, 새 화면·메뉴 없음. 오류 대화상자와 구분 (답이 있으면 오류로 보이지 않게).
- 저장 : AI-4 답변은 저장하지 않으므로 **마이그레이션 불필요**.

## 12. 후속 구현 단계 · 테스트 계획

**2차 (실행·계약)** : `TokenMeter` 중단 신호, 호출 상한 예외 잡기, 부분 구조화 모드, 전달됨 표시와 근거 되돌림, `completion` 칸, 구조화 단계 생각 끄기(⑨ 승인 시), 입력/출력 원인 구분 문구. 결정적 테스트 (가짜 Provider) : 정상 질의 그대로 · 성공 뒤 입력 예산 → PARTIAL · 누적 예산 → PARTIAL · 같은 Tool·전체 상한 → PARTIAL · 초안 length → PARTIAL · 부분 구조화도 예산 초과 → 원래 오류 · 최초 조회 전 예산 → 원래 오류 · 구조화 스키마 실패 → 원래 오류 · 전달 안 된 결과의 근거 거절 · 설명 근거 검증 유지 · 권한 상실 → 오류 · 다른 프로젝트 근거 거절 · Ollama 요청의 think 값.
**3차 (화면 + FINAL 통합 가능)** : 부분 답변 안내 표시 (한국어·영어, 라이트·다크, 1440·1024·375), 실제 Provider : 설명 포함 대규모 조회의 부분 답변·확인 범위 표현, R4 반복(정해 둔 횟수), 물리·사전·논리 질문 회귀, 토큰 사용량 변화, 추가 Provider 호출 비용(부분 답변은 원래 있던 구조화 1번만). 전체 회귀 : H2 build, PostgreSQL 새 빈 DB 2회, 프런트 빌드, 단일 JAR, 브라우저, M-8 간헐 실패 재발 여부.
단계를 2개로 묶는 것을 추천한다 (2차 = 서버 + 계약 + 결정적 테스트, 3차 = 화면 + 실제 Provider + 전체 회귀·문서).

아래 ①~⑫ 는 2차 작업 지시에서 사용자가 확정했다 : AES-D01 = ① D안, D02 = ② 고정 예산 차감 없이 최종 답변 가능 범위를 계속 관리, D03 = ③ 입력·누적 예산·Tool 호출 상한·초안 출력 잘림, D04 = ④ 실제 전달이 확인되고 최종 답변에 넣은 범위만 근거, D05 = ⑤ 서버가 정하는 completion, D06 = ⑥ 기존 오류 유지, D07 = ⑦ TokenEstimator 유지, D08 = ⑧ 16,384 유지, D09 = ⑨ 지원 가능한 Ollama 구조화 단계에서만 thinking 끄기, D10 = ⑩ Tool 정의 최적화 제외, D11 = ⑪ 마이그레이션 없음, D12 = ⑫ 2차 서버 / 3차 화면·최종 검증. 1차의 추천 중 '합성 중단 응답'(7.3 의 1)은 2차 지시(가짜 응답·의미 없는 메시지 금지)에 따라 **전용 예외**로 바꿔 구현했다 (15.2).

## 14. 남은 위험 · 미검증

- 실제 Provider 측정은 한 모델(gemma4:e4b)·한 환경 — 비율·생각 길이는 모델마다 다르다. 다른 Provider 유형은 지금 등록할 수 없다 (Ollama 만).
- 구조화 단계 단독 입력 초과(긴 초안)와 24,000자 자르기는 계산상 가능하나 재현하지 못했다.
- 숫자 과소 추정으로 실제 컨텍스트를 넘는 사례는 측정에서 없었다 (이론 위험).
- 실제 모델이 부분 답변 지시를 지키는지는 2차·3차에서 확인해야 한다.
- 생각 끄기가 구조화 답변의 정확도에 주는 영향은 재생 3회로만 봤다 (JSON 파싱 성공만 확인, 근거 정확성은 미측정).
- 작은 컨텍스트 모델(6,144 이하)은 지금 질의를 시작하지 못한다 (B13).

## 15. 2차 서버 구현 (2026-11-25) — 사용자 검토 대기

확정 정책 AES-D01~D12(13장)로 서버 실행 흐름·응답 계약을 구현했다. 화면(React)·실제 Provider 최종 검증은 3차. 마이그레이션·새 의존성·새 Gradle 모듈·새 설정 없음, 제한값(16,384 / 4,096 / 12,288 / 100,000 / 8 / 4 / 24,000자 / 30초 / 180초)·`TokenEstimator` 그대로.

### 15.2 실행 흐름 (변경 전 → 후)

```
변경 전 : Tool 단계 ─(예산·상한·초안 잘림 예외)─▶ 질의 전체 실패
변경 후 :
 Tool 단계 (TokenMeter.advisor(session::delivered))
   ├ 정상 종료 → 초안 → [모든 결과 원문 ≤ 24,000자 AND 모든 결과+초안 구조화 요청 추정이 지금 예산 안] → 정상 구조화 → COMPLETE
   │                    └ 아니면 → 부분 답변 (초안 없음, 사유 INPUT_BUDGET_EXCEEDED / QUERY_BUDGET_EXCEEDED)
   ├ TokenBudgetExceededException (REQUEST_INPUT / QUERY_TOTAL / OUTPUT_LENGTH)
   │     ├ 첫 요청이면 → 그대로 (기존 오류, B13 은 원인 숫자 문구)
   │     └ 아니면 → 부분 답변 (INPUT_BUDGET_EXCEEDED / QUERY_BUDGET_EXCEEDED / DRAFT_OUTPUT_LIMIT_REACHED)
   ├ Spring AI 호출 상한 응답 (finish reason toolCallLimitExceeded) → 부분 답변 (SAME_TOOL_LIMIT_REACHED / TOTAL_TOOL_LIMIT_REACHED)
   └ 그 밖의 예외 (권한·Provider·시간·SEC-1 …) → 그대로
 부분 답변 : VIEWER 재검증 → 전달된 결과 앞부분 중 가장 긴 가능 범위 선택 → 없으면 최초 사유 오류
           → 쓰지 않는 결과의 근거 지움 → 부분 모드 구조화 (스키마 재요청 1번 규칙 그대로)
           → 실패하면 VIEWER 재검증(실패 = 보안 오류) 후 최초 사유 오류
 근거 검증 (EvidenceVerifier, 기존 VIEWER 재검증 포함) → 응답 직전 VIEWER 재검증 → 응답 (completion)
```

- 종료 제어 : Tool 단계는 **예외로만** 끝난다 (예산 = 전용 예외, 상한 = Spring AI 의 기존 상한 응답). 가짜 Provider 응답·빈 메시지·Tool 결과 조작 없음. 모든 예외를 잡지 않는다 — 부분 답변 대상은 `TokenBudgetExceededException` 과 상한 응답뿐이다. 구조화 단계는 예전처럼 Tool 을 등록하지 않는다 (모델이 불러도 실행하지 않고 거절).
- 1차 추천의 '합성 중단 응답'은 2차 지시의 금지 사항이라 쓰지 않았다.

### 15.3 최종 답변 생성 가능 범위 (AES-D02)

- 후보 = 모델에게 **전달이 확인된** 결과의 앞에서부터 n 개 (n = 전달된 수 … 1). 결과 단위로만 넣고 빼며, JSON 을 자르거나 요약·이름 변경을 하지 않는다.
- 각 후보에 대해 **실제로 보낼 구조화 요청 문자열**(시스템 지시 + 답변 형식 + 사용자 메시지)을 만들어 `TokenMeter.estimate(system, user)` 로 추정하고, `fit` = 입력 상한 · 질의 누적(지금까지 실측 누적 + 추정 + 출력 한도) 판정. 결과 원문 합 24,000자 이하도 조건. 가장 긴 가능한 n 을 쓴다 — 새 결과로 넘치면 그 전 범위로 돌아간다.
- 고정 예산을 미리 떼어 두지 않는다. 실제 요청은 보낼 때 `admit` 이 다시 판정한다 (추정과 실제가 다를 수 있어 성공을 보장하지 않는다 — 넘치면 최초 사유 오류).
- 계산은 부분 답변으로 바꿀 때 한 번 (결과는 최대 8개, 불변이라 Tool 마다 미리 계산한 것과 같은 결과다). 상태는 질의 세션 안에만 있다 (저장소·캐시 없음).
- 정상 흐름도 같은 규칙 : 모든 결과 + 초안이 들어가면 COMPLETE. 아니면 **초안 없이** 앞부분으로 PARTIAL — 초안은 빠진 결과까지 보고 쓴 것이라 넣지 않는다 (1차 B16 은 이제 오류가 아니라 PARTIAL).

### 15.4 구조화 입력 24,000자 처리 (8장)

- 예전 : 결과 블록 단위로 넣다가 넘치면 `[truncated: further tool results omitted]` 를 붙이고 뒤를 뺐다 — 문자열 중간 절단은 없었지만, **빠진 결과의 근거가 남고 완료처럼 보였다**.
- 지금 : 호출자가 결과 단위로 24,000자 안인지 먼저 보고(`fitsText`, 같은 블록 셈), 빠지는 결과가 있으면 부분 답변(근거도 같은 범위). 정상 질의가 모두 들어가면 예전과 같은 요청이다 (결과를 줄이지 않는다). 초안의 8,000자 자르기는 메타데이터가 아니라 모델 문장이라 그대로.
- 서버 맥락(Tool Calling 미지원 모델)도 같은 셈으로 넣지 못한 결과가 있으면 그 근거를 지우고 PARTIAL(INPUT_BUDGET_EXCEEDED). 서버 맥락의 다른 동작은 그대로.

### 15.5 전달 확인과 근거 확정 (AES-D04)

| 상태 | 판정 |
|---|---|
| Tool 실행 성공 | `MetadataToolset.Guarded` 가 결과·근거를 기록 (실패·결과 상한 초과는 그 호출의 근거를 바로 지움 — D-35) |
| 요청에 실릴 후보 | 다음 모델 요청의 대화에 Tool 응답으로 붙음 |
| 예산 판정 통과 | `admit` 통과 — **전달로 보지 않는다** |
| 전달 확인 | 그 요청에 AI 서버가 응답을 돌려줌 (`chain.nextCall` 이 응답을 반환) → 그 요청의 Tool 응답 수만큼 실행 순서 앞부분이 전달됨. 출력 잘림 응답도 요청은 처리된 것이라 전달로 센다 |
| 최종 구조화에 넣음 | 15.3 의 n |
| 제외 | 판정에 막힌 요청의 결과, 호출 실패한 요청의 결과(질의는 Provider 오류로 끝남), 한 응답의 여러 호출 중 상한 앞에서 실행됐지만 대화에 붙지 못한 결과, n 밖의 결과 |

- 근거 = n 개 결과가 남긴 것만 : 부분 답변 직전 `limitEvidenceTo(n)` 이 (n+1)번째 결과 실행 직전의 근거 위치로 되돌린다. 앞 결과가 이미 남긴 같은 대상은 그대로 (근거 기록은 처음 본 스냅숏 유지). 설명 기록도 그 위치로 되돌린다 — 빠진 결과에서만 설명을 본 속성의 `usesDescription` 은 `DESCRIPTION_NOT_RETRIEVED`.
- 사용량은 되돌리지 않는다 (근거 복원과 사용량 기록은 따로다). RESULT_TOO_LARGE·실패 결과는 n 안에 있어도 근거가 없다 (모델에게는 오류 결과로 감).
- D-35 설명 정책(실제 설명을 돌려준 경우만 기록, 조회 때 버전, 등록 여부, `DESCRIPTION_NOT_RETRIEVED`/`NOT_REGISTERED`)은 그대로. 의미 일치 검증·상속 문맥 복합 버전은 도입하지 않았다.

### 15.6 응답 계약 (AES-D05) — 3차 화면 연동 계약

`POST /api/ai/metadata/query` 응답(`QueryResult`)에 `completion` 이 추가됐다 (기존 칸 그대로 — 모르는 클라이언트는 무시하면 된다). 실패는 예전처럼 HTTP 오류.

```json
{
  "answer": "조회가 중간에 멈춰 105개 중 처음 20개만 확인했습니다. …",
  "tools": [{"name": "getLogicalEntityDetail", "status": "OK", "durationMillis": 41}, {"name": "getLogicalEntityDetail", "status": "OK", "durationMillis": 37}],
  "evidence": [{"type": "LOGICAL_ATTRIBUTE", "id": 3011, "name": "루트속성0", "status": "VERIFIED", "reason": null, "source": "TOOL_CALLING"}, {"type": "LOGICAL_ATTRIBUTE", "id": 3036, "name": "루트속성25", "status": "UNVERIFIABLE", "reason": "NOT_RETRIEVED", "source": null}],
  "verification": {"status": "PARTIAL", "total": 2, "verified": 1, "invalid": 1},
  "mode": "TOOL_CALLING",
  "usage": {"modelCalls": 3, "promptTokens": 40, "completionTokens": 18, "estimatedInputTokens": 21000},
  "completion": {"status": "PARTIAL", "reason": "INPUT_BUDGET_EXCEEDED", "executedTools": 2}
}
```
(B09 시나리오의 모양을 따른 예시 — id·시간·추정값은 예시이고 일부 칸(model, durationMillis, structuredRetries, fallback, usage 의 나머지)은 생략. 상태·사유·executedTools·근거 상태는 B09 테스트가 단언한 값과 같다. 정상이면 `"completion": {"status": "COMPLETE", "reason": null, "executedTools": n}`)

| 칸 | 의미 |
|---|---|
| `status` | COMPLETE = 실행 제한으로 멈추지 않고 정해진 절차를 끝냄 (빠짐없는 조회·사실 보증이 아니다) / PARTIAL = 허용된 사유로 멈췄고 전달된 결과 앞부분으로 답함 |
| `reason` | PARTIAL 의 사유 : `INPUT_BUDGET_EXCEEDED` (요청 입력 상한 — 최종 요청의 결과 원문 24,000자 포함), `QUERY_BUDGET_EXCEEDED`, `TOTAL_TOOL_LIMIT_REACHED`, `SAME_TOOL_LIMIT_REACHED`, `DRAFT_OUTPUT_LIMIT_REACHED`. COMPLETE 면 null (이 DTO 는 null 을 그대로 직렬화한다) |
| `executedTools` | 실제 실행 경로에 들어간 Tool 호출 수 = `tools` 중 `REJECTED`(허용 목록 밖 이름)가 아닌 것. 성공·실패·RESULT_TOO_LARGE 포함, 상한으로 실행 전에 막힌 호출 제외. Spring AI 의 상한 계산(대화의 Tool 응답 수, 거절 포함)과 다른 값이고 성공 결과 수·근거 수가 아니다 |

- `verification`(근거 상태)과 `completion` 은 따로다 — PARTIAL 이어도 근거가 VERIFIED 일 수 있다. completion 은 서버가 정하고 모델에게 묻지 않는다 (모델에게는 사유·범위를 사실로 알려 주고 답 안에 적게 할 뿐).
- 3차 화면 : `completion.status == PARTIAL` 이면 답변 위에 안내(사유별 문구, 한국어·영어), 오류 대화상자와 구분. 새 메뉴·화면 없음. `reason` 값은 위 5개로 고정 (늘리면 화면 문구도 늘린다).
- 감사 : 요청 본문 로그는 `/api/ai/**` 라 `[PROTECTED]` 그대로. 서버 로그에 `AI 부분 답변 판정`(사유·실행 수·결과 수·전달 수·넣은 수)·`AI 부분 답변 실패 (최초 사유 유지)`(원인 코드)·`AI 질의 완료`(completion·사유·실행 수) 를 남긴다 — 질문·메타데이터·Provider 요청/응답 원문은 남기지 않는다.

### 15.7 Ollama 생각(thinking) 제어 (AES-D09)

- 판단 : `/api/show` capabilities 에 `thinking` 이 있을 때만 (`ModelInfo.thinking`). 모델 이름으로 짐작하지 않는다. capabilities 가 없으면(알 수 없음) 끄지 않는다 — 예전 요청 그대로.
- 범위 : 구조화 요청(정상·부분·서버 맥락의 구조화 단일 요청)만 Spring AI `OllamaChatOptions.thinkOption(ThinkBoolean.DISABLED)` → Ollama 요청 최상위 `"think": false`. Tool 단계·AI-5·다른 Provider 유형(기본 어댑터는 무시)·MCP 는 그대로. 요청마다 새 옵션 객체라 공유 설정·동시 요청에 영향이 없다 (테스트는 객체가 매번 다르고 일반 옵션에 think 가 생기지 않는 것을 확인).
- 출력 한도 4,096·스키마·파싱·done_reason 판정 그대로 — 생각을 꺼도 잘리면 기존 오류.
- 한계 : 생각을 끌 수 없고 단계(level)만 받는 모델이 `thinking` 을 알려 줄 경우 Ollama 가 `false` 를 어떻게 처리할지 이 환경에서 확인하지 못했다 (설치된 모델은 gemma4:e4b 하나 — 모델 다운로드 안 함). 자동 재호출·Provider 전환은 넣지 않았다.

### 15.8 작은 컨텍스트 안내 (1차 B13)

첫 모델 요청부터 입력 상한을 넘으면 같은 오류 코드(`AI_TOKEN_BUDGET_EXCEEDED`, 422)에 원인 숫자를 붙인다 : "AI 모델 컨텍스트 {적용 컨텍스트} 토큰에서 응답 몫 {출력} 토큰을 뺀 요청 입력 상한 {입력} 토큰이 첫 요청의 추정 입력 {추정} 토큰보다 작아 질의를 시작하지 못했습니다. 컨텍스트가 더 큰 모델을 쓰세요." (영어 있음). 지시·질문·Tool 정의 원문은 넣지 않는다. 추가 조회 중 실패(6,144 처럼 첫 요청은 갔지만 결과를 실을 수 없는 경우)는 결과가 전달되지 않았으므로 기존 문구의 기존 오류. 실행 구조·예산 계산은 바꾸지 않았다.

### 15.9 권한·격리

기존 재검증(질의 시작, Tool 마다, 근거 검증)에 더해 부분 답변 전환 직전·부분 답변 실패 처리 때·응답 직전에 `ExecutionContextVerifier.verify(VIEWER)`. 권한을 잃으면 이미 조회·생성한 답이 있어도 보안 오류(`PROJECT_ACCESS_DENIED` 등)를 그대로 낸다 — 부분 답변 사유로 바꾸지 않고, 부분 답변 실패의 '최초 사유 유지'보다 앞선다. 근거 판정의 프로젝트 격리·조회하지 않은 대상 거절은 그대로.

### 15.11 사용자 확인이 필요한 구현 판단 (확정 정책 안에서 고른 것)

1. **최종 요청의 결과 원문 24,000자로 결과를 빼는 경우의 사유** : 새 사유 코드를 만들지 않고 `INPUT_BUDGET_EXCEEDED`(최종 답변 입력 범위)로 묶었다. 기본 예산(입력 12,288 추정)에서는 Tool 단계가 먼저 멈춰 사실상 생기지 않고, 컨텍스트 설정을 키운 경우에만 생긴다. 따로 구분하려면 사유 하나(예 : `FINAL_INPUT_LIMIT_REACHED`)를 더한다.
2. **정상 흐름(초안까지 끝남)에서 모든 결과 + 초안이 최종 요청에 들어가지 않을 때** : 7.2·AES-D02 에 따라 기존 오류 대신 초안 없이 앞부분 결과로 PARTIAL (1차 B16 → 이제 답이 나온다). 예전처럼 오류로 두려면 이 분기만 되돌리면 된다.
3. **서버 맥락(Tool Calling 미지원 모델)의 24,000자 제외** : 근거를 넣은 범위로 줄이고 PARTIAL(INPUT_BUDGET_EXCEEDED) 로 표시한다 ('전부 본 것처럼 표시하지 않는다'). 서버 맥락은 부분 답변 흐름(재선택·재검증)은 타지 않는다. 결정적 테스트가 없다 (코드 분석만 — 15.12).
4. **구조화 단계에서 모델이 Tool 을 부르는 경우 (기존 동작)** : 구조화 요청에는 Tool 이 없어 거절만 하지만, Spring AI 반복이 같은 이름 상한(4)까지 거절 결과로 모델을 다시 불러 한 구조화 시도가 모델 호출 최대 5번이 된다 (`MetadataToolIntegrationTest` — 기존부터 그랬고 부분 답변에서도 같다). 첫 Tool 호출에서 구조화를 끝내도록 바꿀지는 별도 결정이다 (이번에는 바꾸지 않았다).

### 15.12 미검증 · 남은 위험 (2차 기준)

- 실제 LLM 의 부분 답변 품질(중단 사실·확인 못 한 범위를 답에 적는지, 전체라고 단정하지 않는지)은 보지 않았다 — 3차. 가짜 Provider 테스트는 흐름·계약만 확인한다.
- '응답 반환 직전 권한 상실'(근거 검증과 응답 사이)은 결정적으로 끼워 넣을 지점이 없어 테스트하지 못했다 (코드에 재검증이 있다는 것만 확인). 구조화 중 해제·부분 답변 전환 직전 해제·Tool 실행 중 해제는 테스트했다.
- 서버 맥락 24,000자 제외(15.11-3)는 테스트 없음.
- 동시 요청 옵션 격리는 옵션 객체가 요청마다 새로 만들어지는 것(코드·단위 확인)으로만 봤다. 동시 질의 부하 테스트는 하지 않았다.
- 추정과 실제 토큰이 다르므로 범위 선택이 '가능'이라 해도 실제 요청이 실패할 수 있다 (그때는 최초 사유 오류). 숫자가 많은 결과는 추정이 실제보다 작을 수 있다 (4.2 — 이론 위험, 그대로).
- 생각 기능 모델 중 끌 수 없는 모델의 `think=false` 처리(15.7).
- 작은 컨텍스트 모델(6,144 이하)은 여전히 질의를 시작하지 못하거나 결과를 실을 수 없다 — 안내만 개선했다.

### 16.2 종료 사유와 복수 제한 판정 (AES-D13)

| 사유 | 의미 | 판정 위치 |
|---|---|---|
| `INPUT_BUDGET_EXCEEDED` | 요청별 입력 토큰 예산 부족 | Tool 단계 `admit` (REQUEST_INPUT) / 최종 요청 후보의 `fit` |
| `QUERY_BUDGET_EXCEEDED` | 질의 누적 토큰 예산 부족 | Tool 단계 `admit` (QUERY_TOTAL) / 최종 요청 후보의 `fit` |
| `TOTAL_TOOL_LIMIT_REACHED` · `SAME_TOOL_LIMIT_REACHED` | Spring AI 호출 상한 | 호출 관리자 (`MetadataToolset.LimitAware`) |
| `DRAFT_OUTPUT_LIMIT_REACHED` | Tool 단계 초안 출력 잘림 | Tool 단계 `record` (OUTPUT_LENGTH) |
| `CONTEXT_RESULT_LIMIT_REACHED` | 최종 구조화 입력의 결과 원문 24,000자로 결과 일부 제외 | 최종 요청 후보의 문자 수 판정 (Tool Calling `fitsText`, 서버 맥락 `serverContextIncluded`) |

우선순위 (결정적 테스트로 고정) :
1. **Tool 단계가 먼저 멈췄으면 그 사유**를 유지한다 (최초 사유 보존) — 범위를 고르면서 24,000자로 더 줄어도 바꾸지 않는다 (`toolStopReasonIsKeptWhenTextLimitShrinksRange` : 누적 예산으로 멈춘 뒤 문자 수로 2개로 줄어도 QUERY_BUDGET_EXCEEDED).
2. Tool 단계가 정상으로 끝났으면 **모든 결과(+초안) 후보가 처음 걸린 판정** : 결과 원문 24,000자 → 요청 입력 → 질의 누적 (`bothLimitsInFinalRequest` : 문자 수와 누적이 함께 걸리면 CONTEXT_RESULT_LIMIT_REACHED, 범위는 두 조건을 모두 만족하는 앞부분).
3. 서버 맥락도 2와 같은 순서.
- 개별 Tool 의 `RESULT_TOO_LARGE`(24,000자 결과 상한)는 그대로 모델에게 가는 오류 결과이며 종료 사유가 아니다 (B12 COMPLETE).
- 모델에게 주는 사유 설명도 '조회는 끝났다'(초안 잘림·범위 축소) 와 '추가 조회가 멈췄다'(Tool 단계 예산·상한)를 구분한다 (`stopReason(reason, lookupsFinished)`). 부분 구조화 지시는 중단을 단정하지 않고 '정상 절차를 끝내지 못했다' 로 바꿨다.

### 16.3 서버 맥락 부분 답변 (AES-D15)

- 서버 맥락은 서버가 조회해 구조화 요청 하나로만 모델에게 보내므로 '전달' = 그 요청에 넣은 범위다 (Tool Calling 의 응답 확인 시점을 강제하지 않는다).
- 결과 단위로 앞에서부터, 결과 원문 24,000자 · 요청 입력 · 질의 누적 안의 가장 긴 범위를 넣는다. 빠지는 결과가 있으면 VIEWER 재검증 → 근거를 넣은 범위로 줄임 → 요청 끝에 서버가 정한 범위·사유 안내 → PARTIAL. 하나도 넣을 수 없으면 기존 `AI_TOKEN_BUDGET_EXCEEDED`. 해석할 수 없는 질문(조회 없음)은 예전처럼 COMPLETE.
- `executedTools` : 서버 맥락의 조회는 모델 Tool 호출과 같은 실행 경계(`MetadataToolset.run` → `Guarded`)를 지나 `tools` 에도 실리므로 2차 정의('실제 Tool 실행 경로에 진입한 호출') 그대로 센다 (2차부터의 구현 — 계약을 바꾸지 않았다). 서버 맥락에서 '모델이 부른 Tool 수' 로 읽지 않도록 화면은 예전처럼 '서버 조회' 로 표시한다. 다르게 세려면 사용자 결정이 필요하다 (16.13).
- 서버 맥락의 구조화 요청도 생각 기능 모델이면 `think=false` (구조화 요청이므로 AES-D09 범위).

### 16.4 구조화 단계 Tool 요청 차단 (AES-D16)

- 예전 : 구조화 요청에는 Tool 정의가 없지만 모델이 Tool 을 부르면 Spring AI 반복이 거절 결과(REJECTED)를 붙여 모델을 다시 불렀다 — 한 구조화 시도에 모델 호출 최대 5번.
- 지금 : 구조화 요청의 Advisor(`structuringAdvisor`, Tool 반복 안쪽)가 응답 사용량을 기록한 뒤 응답에 Tool 호출이 있으면 즉시 `AI_STRUCTURED_OUTPUT_INVALID` — Spring AI 가 Tool 을 실행·거절하기 전에 끝나므로 Tool 실행 0, `tools` 기록 없음, executedTools 에 없음. 허용 목록 Tool·여러 Tool·목록 밖 이름 모두 같다.
- 재요청 : 기존 재요청 대상은 '형식(스키마) 오류' 뿐이고, 예전에도 구조화 중 Tool 호출 자체는 재요청하지 않았다 → 이 실패는 재요청하지 않는다 (재시도 범위 확대 없음). 형식 오류의 1번 재요청은 그대로 (`structuringRetryAndPartialToolRequest`).
- 정상 흐름이면 `AI_STRUCTURED_OUTPUT_INVALID`(502), 부분 구조화 중이면 부분 답변 실패 → 최초 사유.
- 효과 : 가짜 Provider 에서 상한 뒤 구조화 단계가 Tool 을 부르는 경우 모델 호출 10 → 6 (`MetadataToolIntegrationTest.limitsAndUnsupportedModel`). 실제 gemma4 31회에서는 구조화 단계 Tool 호출이 없었다.

### 16.5 전달 추적 방식 재검토 (10.2)

Tool 응답 수(대화 전체)로 실행 순서 앞부분을 전달로 보는 방식을 유지한다 — Spring AI 는 Tool 반복마다 대화 전체를 다시 보내고(conversationHistoryEnabled 기본 true), 한 응답의 여러 호출도 순서대로 실행해 같은 순서로 Tool 응답을 붙인다. 같은 Tool·같은 인자를 두 번 불러도 결과는 실행 순서의 다른 칸이라 개수로 정확히 구분된다. 상한 앞에서 실행됐지만 대화에 붙지 못한 결과(한 응답의 여러 호출)는 다음 요청에 없으므로 전달로 세지 않는다 (`batchBoundaryAtTotalLimit`). 호출 식별자 대조는 Ollama Tool 호출에 식별자가 없어(Spring AI 가 만든 값) 더 정확해지지 않아 넣지 않았다.

### 16.6 권한 재검증 (11장)

결정적 테스트 : Tool 실행 중 해제, 마지막 Tool 뒤(부분 답변 전환 직전) 해제, 구조화 요청 중 해제, 서버 맥락 구조화 중 해제, **근거 검증이 끝난 뒤(응답 직전) 해제** — 정상·부분 모두 `PROJECT_ACCESS_DENIED` (`AiExecutionStabilityFinalCheckIntegrationTest` — 운영 코드 후크 없이 Spring 테스트 spy Bean 으로 근거 검증 직후에 끼어든다). 응답 객체를 만든 뒤 HTTP 로 내보내기까지의 일반적인 경합은 보장 범위 밖이다 (재검증과 전송 사이의 짧은 구간).

### 16.7 Ollama 생각 제어 최종

- 적용 : 구조화 요청(정상·부분·서버 맥락)만. Tool 단계·AI-5·다른 Provider·MCP 는 그대로. capabilities 에 `thinking` 이 없거나 capabilities 자체가 없으면 보내지 않는다.
- 끄기 거부 : Ollama 가 `think=false` 를 400 으로 거절하면 기존 AI 호출 실패(`AI_PROVIDER_CALL_FAILED`) 그대로 — 숨기거나 재호출하지 않는다 (가짜 Provider `thinkDisableRejected`). **실제로 끌 수 없는 모델은 이 환경에 없어 실제 검증 안 함** (모델 다운로드 금지). capabilities 의 `thinking` 은 '생각 기능이 있다' 는 뜻일 뿐 '끌 수 있다' 는 보장이 아니다 — 그런 모델이 나오면 구조화 요청이 Provider 오류로 끝난다 (모델명 예외 목록·자동 재호출은 넣지 않는다).
- 동시 질의 격리 : 생각 기능 모델(시스템 기본)과 없는 모델(프로젝트 지정 Provider)로 두 질의를 동시에 — 각자 구조화 요청에만 think=false / 없음, Tool 단계 think 없음, 사용량·근거·completion 분리 (`concurrentQueriesKeepOptions`, 대규모 부하 아님).

**`ConcurrentEditC2` 실패 원인 (이번에 확인)** : 이 시험은 A 의 트랜잭션 연결에서 `pg_stat_activity` 를 반복 조회해 B 의 잠금 대기를 감시한다. PostgreSQL 은 한 트랜잭션 안에서 `pg_stat_activity` 를 처음 읽은 시점 그대로 보여 준다 — psql 로 직접 확인 : A 트랜잭션 첫 조회 0 → B 가 A 의 행을 기다림 → 같은 트랜잭션 재조회 **0**, 별도 연결 1, `pg_stat_clear_snapshot()` 뒤 1. 그래서 감시의 첫 조회가 B 의 대기 시작보다 빠르면 20초 동안 대기를 못 보고 실패한다 (진단 '호출 연결 0 / 별도 연결 1' 과 같다). 제품 결함이 아니라 M-8 시험 감시의 타이밍 결함이며, M-8 기록(modeling-concurrency-m8.md 19.9 '스냅숏 가설 기각')과 다르다. 3차 변경으로 테스트 실행 순서·시간이 바뀌면서(신규 클래스 — 빼면 통과) 자주 드러난 것으로 보이며, AI 코드는 이 시험의 경로(논리 엔터티 승인·수정)를 지나지 않는다. 작업 지시(독립 기존 결함은 고치지 않는다)에 따라 고치지 않았다 — 시험 쪽 수정안은 감시 쿼리 전에 `pg_stat_clear_snapshot()` 을 부르거나 감시를 별도 연결에서 하는 것 (같은 감시를 쓰는 M-8 시험 여러 곳 — `B 가 끝나지도, 잠금을 기다리지도 않았다` 를 던지는 7개 클래스).

### 17.2 M-8 감시 결함 (상세 [modeling-concurrency-m8.md 23장](modeling-concurrency-m8.md))

- 원인 : PostgreSQL 은 트랜잭션 안에서 `pg_stat_activity` 의 백엔드 **목록**을 첫 조회 때로 고정한다 (목록에 있는 백엔드의 대기 상태는 새로 읽힌다). M-8 감시는 A 의 트랜잭션 연결에서 돌아, B 가 감시 첫 조회 뒤 **새 연결**을 열면(풀이 다 쓰인 때) 대기를 못 봤다. 3차의 '스냅숏 고정' 설명(16.15)은 정확히는 '목록 고정' 이다 — 같은 트랜잭션 재조회가 1 을 보는 경우(이미 있던 연결)도 있다는 것을 결정적 재현으로 확인했고, M-8 19.11 탐침의 '기각' 은 그 경우만 본 결과였다.
- 수정 : `ConcurrencyDiagnostics.lockWaitCount` — 같은 연결(`ConnectionCallback`)에서 `pg_stat_clear_snapshot()` 뒤 감시 sql. A 의 트랜잭션 안에서 감시하는 9곳(8개 클래스 + `ModelVersionConcurrency` 1메서드)만 바꿨다. 트랜잭션 밖에서 감시하는 원본·상속·RelationSync 계열은 유지 (M-8 23.4 표).
- 재현 `PostgresLockWaitWatchIntegrationTest` 2건 (PostgreSQL 전용) · `entityApprovalVsEdit` 독립 10회 10/10 · 영향 클래스 13개(114건) 묶음 3회 모두 실패 0. 같은 묶음에 넣어 본 **`RelationSyncDeadlockIntegrationTest.s4TwoRenames`(M-8 의 다른 원인 미확정 간헐 실패)가 3회 중 1회 재발** — 감시가 트랜잭션 밖이라 이번 결함과 무관, 고치지 않았고 해결로 보지 않는다 (최종 전체 2회에서는 통과).

### 17.3 executedTools 최종 계약 (AES-D18)

실제 메타데이터 Tool 실행 경계(`MetadataToolset.Guarded` — 실행 컨텍스트 재검증 뒤 읽기 전용 실행·결과 크기 판정·기록)에 들어간 호출 수. 코드 : `MetadataToolSession.executedTools()` = 기록된 호출 중 `REJECTED` 가 아닌 것.
