# DEC-22 ERD 이미지 · 모델 Export · Import · 다른 프로젝트로 복사

> 2026-11-16 구현 (5차 통합 구현), 2026-11-17 7차 보완 (교환 형식 2 : 모델 VIEW · ERD 배치 — 8장). 정책 : [pending-work.md 7.2](../pending-work.md) DEC-22. 이전 범위(선택 테이블 Excel Export, M-7 매핑, Excel 등록 업로드)는 그대로다. 새 마이그레이션 없음 (7차도 없음).

## 1. ERD PNG · SVG (물리·논리 ERD)

- `features/erd/exportImage.ts` (`useErdExport`) : 툴바의 [PNG]·[SVG]. 지금 ERD 에 올라온 노드 **전체**를 지금 배치 그대로 (화면 밖 포함), 관계선·레이블 포함. 내보내는 동안 `onlyRenderVisibleElements` 를 끄고 노드를 축소 모양이 아니라 자세히 그린 뒤(`useErdExporting` → `useSimpleNodes`), `.react-flow__viewport` 를 노드 경계 + 여백 40px 크기, 확대 1 로 복제한다. 화면의 확대·이동은 바꾸지 않는다.
- PNG 는 캔버스 한도(한 변 16,000px·넓이 1.2억 px) 안에서 최대 2배 해상도 (큰 ERD 는 해상도를 낮춰 잘리지 않게), SVG 는 벡터(노드는 foreignObject). 배경은 지금 테마의 `--gh-canvas`. 파일 이름 `물리-ERD_<프로젝트>_<시각>` / `논리-ERD_<모델 ID>_<시각>` (영어 화면은 영어).
- 라이브러리 `html-to-image@1.11.11` (MIT, React Flow 공식 예제가 쓰는 판) — 버튼을 누를 때만 동적 import 라 기본 번들에 들어가지 않는다. 서버 요청은 없다 (이미 권한을 확인한 ERD API 의 데이터만 그린다).
- 물리 ERD 의 "전체" 는 지금 조회 범위(스키마·검색·페이지, 최대 표시 수)다 — 범위를 넘는 TABLE 은 범위를 바꿔 내보낸다.

## 2. 모델 Export (`GET /api/modelExchange/export`, VIEWER)

- 형식 `{format: "lexorma-model", formatVersion: 2, exportedAt, dbType, counts, model: {종류: [{id, name, state}]}, layouts}` (5차는 형식 1 — 8장의 호환 정책). 내용은 모델 버전·변경 이력과 같은 필드 목록(`ModelChangeRecorder.currentState`) : 스키마, TABLE·컬럼(표준 용어는 ID 와 이름), 관계(컬럼 쌍·규칙), 인덱스·제약조건(구성 컬럼·식), 논리 모델·엔터티·속성·식별자(구성 속성)·논리 관계, 엔터티·속성 매핑. 파일 안의 id 는 파일 안 참조용이다.
- 넣지 않는 것 : 승인 상태(`isApproval` 키 제거), 원본 DB 연결·원본 카탈로그·원본 DB 에서 수집한 VIEW 정의(DEC-16 `TB_SRC_VIEW_DFN`), 비밀번호·키·토큰, 감사 컬럼·사용자·감사 로그. (5차의 형식 1 은 VIEW·ERD 배치도 넣지 않았다 — 7차에 형식 2 로 더함, 8장)

## 3. Import · 복사 (`POST /api/modelExchange/plan` → `/apply`, USER + 대상 프로젝트 관리자·ADMIN)

- 대상 : 로그인 프로젝트 또는 관리하는 다른 프로젝트 (`GET /targets` — 사용 중이고 `ProjectAuthority.canManage`, ADMIN 도 멤버여야 한다). 복사 = 지금 프로젝트의 Export 를 그대로 다른 프로젝트에 가져오기 (화면의 "지금 프로젝트의 모델 (복사)"). 새 프로젝트로 복사하려면 프로젝트 관리에서 프로젝트를 만든 뒤 그 프로젝트를 대상으로 고른다.
- 계획 항목 : TABLE(컬럼·인덱스·제약조건 포함) · 스키마 · 관계 · 논리 모델(엔터티·속성·식별자·관계 포함) · 엔터티 매핑. 상태 NEW / CONFLICT(같은 스키마.TABLE — VIEW 이름 포함 — 또는 같은 논리 모델 이름 : 가져오지 않고 덮어쓰지 않는다) / EXCLUDED(NOT_SELECTED · INVALID · RELATED_NOT_IMPORTED). 관계는 양쪽 TABLE 이, 매핑은 엔터티의 모델과 TABLE 이 모두 NEW 일 때만. 대상에 없는 스키마 이름은 새로 만든다(기본 스키마 아님). 단 대상 프로젝트에 기본 스키마가 아직 없으면(새 프로젝트는 처음 쓸 때 `SchemaService.resolveSchema` 가 만든다) 파일의 `DEFAULT` 는 기본 스키마로 만든다 — 일반 스키마로 만들면 그 뒤 기본 스키마 생성이 같은 이름으로 UNIQUE 위반(물리 ERD 등 500)이 된다 (6차 결함 수정).
- 선택 : `selection.tables`("스키마.테이블")·`logicalModels` — 화면은 계획 표의 체크로 다시 계획한다.
- 확정 : 대상 프로젝트 행 배타 잠금 → 다시 계획 → planToken(대상·파일 해시·선택·항목·경고의 SHA-256) 이 다르면 409 `MODEL_EXCHANGE_STALE` → 직전 모델 버전 `MODEL-IMPORT-<요청 ID>` → `markImport`(변경 이력 그룹 = 같은 이름, 출처 IMPORT) → JPA 로 생성(모델 변경 이력이 그대로 남는다). 한 트랜잭션 : 도중 실패는 전체 롤백.
- 새 ID 로 다시 잇는 참조 : TABLE→스키마, 컬럼→TABLE, 관계→TABLE·컬럼 쌍, 인덱스·제약조건→컬럼, 엔터티→모델, 속성→엔터티, 식별자→속성, 논리 관계→엔터티, 매핑→엔터티·TABLE·속성·컬럼. 표준 용어는 대상 프로젝트의 **같은 이름** 용어에만 (없으면 연결 없이, 경고 `TERM_NOT_FOUND:<연결 수>`). DBMS 가 다르면 경고 `DB_TYPE_DIFFERS`.
- 승인 상태를 물려받지 않는다 : 만드는 객체는 모두 미승인. 컬럼에서 파생되는 참조 관계(REF_COLUMN)와 컬럼 인덱스(COLUMN)는 파일에서 받지 않고 커밋 직전 동기화가 컬럼의 참조 테이블명·인덱스 여부로 다시 만든다 (그 규칙대로 승인 상태로 만들어진다).
- 믿지 않는 입력 : 형식·버전(1)·종류 목록·객체 수(최대 50,000)·번호 중복·값 모양(글자·숫자·참/거짓, 자식 행 목록 한 단계, 1,000행 — 서브타입 구성원 목록은 예외이며 객체 수에 들어간다, 10장)·이름(1~128자, 제어 문자 없음)·텍스트(최대 4,000자)·enum 값을 검사한다. 문장 구분·주석(`;`, `--`, `/*`, `*/`)이 든 SQL 식(기본값·CHECK·인덱스 조건·표현식·정렬)은 가져오지 않는다 (인덱스·제약조건은 빼고, 기본값은 비운다). 요청 본문은 30MB 까지만 읽는다 (`ModelExchangeRestController.read`), 요청 로그에 본문을 남기지 않는다(`@ProtectedLogBody`).
- 오류 코드 : `MODEL_EXCHANGE_INVALID`(400) · `MODEL_EXCHANGE_STALE`(409) · `MODEL_EXCHANGE_FORBIDDEN`(403).
- 화면 : 데이터 품질 관리 > 모델 Export·Import (`/modelExchange`, 메뉴 `model-exchange` VIEWER, 가져오기 `model-exchange-import` USER).

## 8. 7차 보완 : 교환 형식 2 — 모델 VIEW · ERD 배치 (2026-11-17)

정책 결정(7차 지시) : 모델 VIEW 메타데이터와 저장된 논리·물리 ERD 배치를 Export·Import·복사에 넣는다. 원본 DB 에서 수집한 VIEW 정의(DEC-16)는 계속 넣지 않는다 — 모델 VIEW(`TB_VIEW`, M-15)와 원본 VIEW 정의(`TB_SRC_VIEW_DFN`)는 서로 다른 데이터다. 마이그레이션은 없다 (기존 테이블에 행을 만들 뿐이다).

### 8.1 형식·호환

| 항목 | 내용 |
|---|---|
| 형식 버전 | Export 는 `formatVersion: 2`. Import 는 1·2 를 받는다 (`ModelExchangeDto.SUPPORTED_VERSIONS`), 그 밖은 400 |
| 형식 1 파일 | 그대로 가져온다 (VIEW·배치가 없을 뿐 — 가져온 뒤 화면의 자동 배치). 형식 1 파일에 `PHYSICAL_VIEW` 나 `layouts` 가 있으면 400 (형식 1 은 그런 내용을 낸 적이 없다) |
| 형식 2 파일을 예전 서버에 | 형식 버전 검사에서 400 (예전 서버는 1 만 받는다). 5차 이전 서버로 옮기려면 그 서버에서 다시 내보낸다 |
| 새 필드 | `model.PHYSICAL_VIEW` (모델 버전과 같은 필드 목록 : 스키마·이름·논리명·설명·정의 SQL·출력 컬럼·참조 객체), 최상위 `layouts {physical: {nodes, viewport}, logical: [{modelId, nodes, viewport}]}` — 좌표의 키는 파일 안의 TABLE·엔터티 번호 |
| 선택 | `selection.views` ("스키마.VIEW", null 이면 전부 — 예전 화면·클라이언트의 요청은 VIEW 전부) |

### 8.2 모델 VIEW

- 계획 항목 `VIEW` : NEW / CONFLICT(대상 프로젝트에 같은 스키마.이름의 TABLE·VIEW — 덮어쓰지 않는다) / EXCLUDED(NOT_SELECTED · INVALID · UNSAFE_TEXT). 같이 가져오는 TABLE 과 이름이 같거나 파일 안에서 겹치면 INVALID.
- 검사 (파일은 믿지 않는 입력) : 이름은 VIEW 관리와 같은 식별자 규칙(대문자), 논리명 255자·설명 1,000자, 출력 컬럼 1,000개(이름 중복 없음)·참조 200개, 참조 행의 모양. **정의 SQL 은 VIEW 관리 화면과 같은 정적 검사**(`ViewDefinitionSql.check` — 조회 문 하나, 다른 명령·닫히지 않은 따옴표/주석 없음)를 통과해야 하고, 통과하지 못하면 UNSAFE_TEXT 로 그 VIEW 만 빼고 가져온다. 정의 SQL 은 저장만 하고 어디서도 실행하지 않는다 (원본 DB 에 DDL·DML 없음).
- 참조 재매핑 : 참조 대상이 같이 가져오는 TABLE·VIEW 면 새 ID, 아니면 대상 프로젝트의 같은 스키마.이름 객체(기존 객체에 연결 — 계획의 `linked`), 둘 다 없으면 모델 밖 참조(스키마명·객체명만 — `unresolved`). 같이 가져오는 VIEW 끼리 순환하거나 자기 자신을 참조하면 INVALID. 대상 프로젝트 밖의 객체는 가리킬 수 없다 (기존 객체 조회가 대상 프로젝트 범위).
- 만드는 VIEW 는 미승인, ID 새로, 모델 변경 이력(`PHYSICAL_VIEW`, 출처 IMPORT)·직전 모델 버전에 같이 남는다.

### 8.3 ERD 배치

- Export : 내보내는 사용자가 **서버에 저장한** 배치(`TB_ERD_LYT`, `TB_LGCL_ERD_LYT`)만 — 화면에서 움직이고 저장하지 않은 좌표는 들어가지 않는다. 파일에 들어간 TABLE·엔터티의 좌표만 (지워진 객체의 좌표는 뺀다), 화면 위치·확대 비율 포함. 배치가 없으면 `layouts: null`.
- Import·복사 : 새로 만든 TABLE·엔터티의 좌표만 새 ID 로 옮긴다. **가져오는 사용자 본인의 배치에만** 더한다 (배치는 사용자별 저장이다 — 다른 사용자의 배치는 만들거나 바꾸지 않는다).
  - 물리 : 그 사용자의 배치가 없으면 새로 만든다(파일의 화면 위치·확대 비율). 이미 있으면 **기존 좌표는 그대로** 두고 새 노드를 기존 노드 오른쪽(가장 오른쪽 + 600, 같은 위쪽 높이)으로 옮겨 더한다 — 화면 위치는 바꾸지 않는다. 더해서 5,000개(배치 저장 한도)를 넘으면 배치는 가져오지 않는다(`LIMIT_EXCEEDED`). 계획 뒤 그 사용자가 배치를 저장했으면 확정은 409 `MODEL_EXCHANGE_STALE`(planToken 에 배치 버전이 들어간다).
  - 논리 : 새로 만든 논리 모델마다 그 사용자의 배치를 새로 만든다 (같은 이름 모델은 CONFLICT 라 기존 모델 배치는 건드리지 않는다).
  - 계획 항목 `ERD_LAYOUT` (key `PHYSICAL` / `LOGICAL:<모델명>`, counts nodes·ignored), 가져오지 않는 객체의 좌표는 ignored, **파일에 없는 객체를 가리키는 좌표는 무시하고 경고** `LAYOUT_IGNORED:<n>`.
- 좌표 검사 : 유한한 숫자이고 ±10,000,000 안, 확대 0.02~4, 배치 하나에 5,000개 (ERD 배치 저장 API 와 같은 한도). 어기면 파일 전체 400 (`NaN`·`Infinity` 는 JSON 이 아니라 읽기 단계에서 400).
- 배치가 없는 파일(형식 1, 저장한 배치가 없는 사용자의 Export) : 배치를 만들지 않는다 → 화면의 기존 자동 배치.

### 8.4 화면 (`/modelExchange`)

계획 표에 VIEW 행(체크로 고르기, 출력 컬럼·참조·기존 객체 연결·모델 밖 참조 수)과 ERD 배치 행(좌표 수, 가져오지 않는 객체 수), 경고 `LAYOUT_IGNORED`, 사유 `LIMIT_EXCEEDED`. 안내 문구를 형식 2 에 맞게 바꿨다 (ko·en).

## 9. 대형 ERD 이미지 측정과 크기 한도 (7차, 2026-11-17)

## 10. 서브타입 구성원 목록·식별자 구성 검사 (M-6 최종 정책, 2026-11-20)

- **객체 수** : 파일 전체 객체 수 = 종류별 객체 합계 + 서브타입 그룹의 구성원 행 (최대 50,000, `MAX_OBJECTS`). 그 밖의 자식 행(식별자 구성·속성 짝·컬럼 구성 등)은 세지 않고 객체 하나에 1,000행(`MAX_CHILD_ROWS`)까지다.
- **D-53** : 서브타입 그룹의 구성원 목록(`SUBTYPE_GROUP.subtypes`)만 1,000행 제한에서 빼고 위 합계로 막는다 — 구성원 1,001개 이상 그룹도 왕복된다. 구성원 행은 모양·참조 검사와 DB 쓰기 전에 그룹마다 더해 50,000 을 넘는 순간 거절한다. 요청 본문 30MB, 형식 5, 필드 이름·처리 순서 그대로.
- **D-17** : 논리 식별자의 구성 속성은 그 식별자 엔터티의 속성이어야 한다 (상속 속성·다른 엔터티 속성이면 파일 전체 거절). 예전에는 가져오기가 파일 전체의 속성 번호로 찾아 다른 엔터티 속성에 잇거나 조용히 뺐다.
- 기록 : [logical-subtype.md 0.8](logical-subtype.md). 테스트 `ModelExchangeLimitsTest`(검사 계층 경계값), `LogicalSubtypeIntegrationTest.exchangeLargeGroups`(구성원 2·500·999·1,000·1,001·2,000 실제 파일 왕복).
