# Lexorma — 미완료 작업 및 후속 개선

## 1. 문서 개요

- **목적** : 앞으로 구현하거나 검증·결정해야 할 일을 한 문서에서 관리한다. 이미 끝난 범위는 [completed-work.md](completed-work.md) 에 있다.
- **관리 원칙**
  - 다음 작업은 **사용자와 협의해 정한다.** 이 문서의 순서·우선순위는 후보 목록이며, AI 가 여기서 임의로 다음 작업을 골라 시작하지 않는다.
  - 작업 ID 는 기존 로드맵의 것을 그대로 쓴다(`M-n`, `AI-n`, `SEC-1`, `D-nn`, `U-nn`). 한 작업의 남은 범위가 여럿이면 원래 ID 아래에 둔다. 로드맵에 없던 항목만 새 ID(`UI-`, `AUTH-`, `PRJ-`, `COL-`, `AI-MCP` — `AI-MCP` 는 AI 로드맵 단계 번호가 아니다)를 붙인다.
  - 우선순위는 기존 로드맵·기록에 있던 값을 유지한다. 기록에 우선순위가 없던 항목은 **(임시)** 로 표시했다 — 착수 전에 사용자와 확정한다.
  - 완료되면 completed-work.md 로 옮기고 여기서 지운다. 남은 범위가 있으면 그 부분만 남긴다. 같은 일이 다시 나오면 새 항목을 만들지 않고 기존 항목을 고친다.
  - 상세 근거는 각 항목의 "참고 사항"에 연결한 기능 기록에 있다.
  - **문서 구조** : 작업 상태는 이 문서와 [completed-work.md](completed-work.md) 에서만 관리한다. 완료된 작업의 상세 기록은 `completed/`, 진행 중 작업의 상세 설계는 필요할 때만 `ongoing/`(지금은 없음), 상태와 무관한 기술 기준·결정 기록은 `reference/` 에 둔다. `completed/` 에 기록이 있어도 그 기능의 후속이 모두 끝난 것은 아니다 — 이 문서에서 확인한다. 상세 설계가 필요한 작업만 `ongoing/` 에 문서를 만들고, 끝나면 `completed/` 로 옮기며 링크를 함께 고친다. 상태 보고만을 위한 문서는 만들지 않는다.
- **상태 값** : 미착수 · **개발 대기**(정책 확정, 코드 미구현) · 진행 중 · 부분 완료 · 검증 필요(구현 또는 운영 준비 뒤 실증·외부 검토 필요) · 결정 필요 · 보류. **정책 확정과 구현 완료는 다르다** — 7.2 의 결정은 방향만 정한 것이고, 완료는 구현·테스트·문서 검증 뒤 completed-work.md 에만 적는다.
- **최종 갱신일** : 2026-11-19

- **정합성 정리 (2026-11-17)** : 아래 '원본 동기화 확장 — DEC-06·04·05·07' 의 정책 기록은 그대로 두되, **네 가지 모두 구현 완료**(4차 — 이름 변경 매핑 V4·삭제 후보·제약/인덱스 교체·COMMENT 명시적 비우기, 5차 보완·E2E, 6차 교체 롤백, 7차 UNKNOWN 수동 검토 — [source-sync-dec04-05-07.md](completed/source-sync-dec04-05-07.md), [source-rename-mapping-dec06.md](completed/source-rename-mapping-dec06.md), 7.3). **남은 것** : 미착수 — 모델 확장(IDENTITY 변경 가져오기·생성 컬럼·컬럼 순서), 성능(비교 1회 3초 튐·요청당 약 468MB·매핑 상태 이중 계산·큰 스키마 쪽 조회), 테스트(재가져오기 동시성, 기준 연결 복귀, 수천 TABLE 매핑), 화면(수집 실패 코드별 안내·PARTIAL 스키마 목록 API·수집 완료 알림·원본 ERD 배치 저장·매핑 변경 이력), DEC 후속(제약·인덱스 이름 변경 매핑, 참조 관계 연쇄 삭제, VIEW·인덱스·제약 단독 삭제 후보, 식 비교 엔진 개선). 선행 필요 — 다른 DBMS 비교 규칙([AI-2]). **결정 필요** — 원본 VIEW 가져오기([M-15] 와 같은 정책 문제).
- 현재 상태 : 관리 화면·원본 ERD·매핑·비교·가져오기·재가져오기 구현. PostgreSQL 원본만.
- 남은 작업
  - **원본 동기화 확장 — DEC-06·04·05·07 4차 구현 (2026-11-16, 7.3)** : 남은 것은 7.3 각 행과 영어·라이트·390px·DEC-05/07 화면 확정 E2E (DEC-06·04 는 실제 PostgreSQL 원본으로 화면 확정까지 확인). 아래는 정책 기록 — 원본 DB 는 계속 읽기 전용이고 동기화는 모델 데이터만 바꾼다(원본에 DDL·DML 없음). 절차는 모두 비교 → 후보 표시 → 사용자 선택 → 영향 관계·승인 상태 검증 → 변경 계획 미리보기 → 최종 확인 → 모델 반영·이력 기록 (M-4e 의 후보 → 계획 → 반영 구조 재사용). 승인 객체의 무단 변경 금지. **순서 : DEC-06 → DEC-04 → DEC-05 → DEC-07** (이름 변경이 삭제 + 추가로 오인되지 않도록 06 먼저).
    - DEC-06 원본 이름 변경 후보를 사용자가 확인해 원본·모델 매핑으로 저장 (자동 확정 금지). 지금의 "M-4d 비교는 아무것도 저장하지 않고 컬럼 수준 매핑 테이블이 없다" 구조를 바꾸는 결정이다 — 비교 자체는 읽기 전용 그대로, 매핑 저장은 새 테이블(증분 마이그레이션).
    - DEC-04 원본에서 삭제된 객체는 삭제 후보로 표시하고, 사용자가 선택·확인한 **미승인 객체만** 모델에서 삭제 (자동 삭제 금지). M-4e·M-4f 의 "추가·갱신만" 범위를 넓히는 결정.
    - DEC-05 기존 제약조건·인덱스 구성 변경은 **미승인 객체**에 한해 변경 계획 확인 뒤 교체, 승인 객체는 기존 변경 요청 절차(M-14).
    - DEC-07 승인 객체의 원본 COMMENT 는 자동 갱신하지 않는다(승인 취소 후 갱신 — 현행). 원본 COMMENT 삭제는 명시적으로 선택한 경우에만 허용 (이 선택이 새 개발).
  - 모델 확장 : 기존 컬럼의 IDENTITY 변경 가져오기(지금 `NO_FIELD`), 생성 컬럼(`GENERATED ALWAYS AS … STORED`) 지원, 컬럼 순서 가져오기.
  - 다른 DBMS 의 비교 규칙(지금 `PostgresCompareRules` 만), VIEW 가져오기(원본 VIEW 정의 수집 이후).
  - 성능 : 3,000 TABLE 비교 조회의 1회 3초 튐 원인 분석, 비교 요청당 할당 약 468MB 줄이기(버전 JSON 한 번만 읽기 또는 읽기 캐시), M-4c 매핑 상태 이중 계산 최적화, 큰 스키마 TABLE 목록의 쪽 단위 조회.
  - 테스트 : 재가져오기 전용 동시성·기준값 테스트, 기준 연결 복귀 시 재판정, 수천 TABLE 매핑 성능.
  - 화면 : 수집 실패 시 코드별 안내 문구, PARTIAL 수집의 원본 스키마 목록 API, 수집 완료 알림, 원본 ERD 배치 저장·응답 압축, 매핑 변경 이력(지금은 감사 컬럼과 반영 순서만).
- 완료 조건 (로드맵 M-4) : 원본 연결 없이 수집 결과로 물리 모델·ERD 를 만들 수 있고, 재가져오기에서 사용자 데이터가 보존되며, 미등록 항목이 식별된다. 위 항목은 각각 사용자와 범위를 정해 나눠 진행한다.

- 남은 작업 (개발 대기) : MySQL·MariaDB 전 공통 계약(이름 공간·식별자 비교 규칙·드라이버별 속성·테이블 유형·인덱스 접두 길이·CHECK 식 표현), 드라이버 배포 방식·라이선스 확인, 그 드라이버의 SEC-1 소켓 고정, 이어서 Oracle. PostgreSQL VIEW 정의 수집과 저장·표시·마스킹 정책 설계. 수집 결과 화면의 급감 경고.

- **정합성 정리 (2026-11-17)** : 아래 '동시 편집 — DEC-08 … 개발 대기' 는 이전 기록이다. **동시 편집(DEC-08·13)은 3차 구현 완료**(`ModelBase` 공통 계약 — 기준값 `MDFCN_DT`, 행 잠금 뒤 비교, 409 `MODEL_CONFLICT`, 기준값 없으면 400, 화면 입력 보존, 6차에 구성만 바꾼 저장의 기준값 결함 수정·두 계정 브라우저 E2E — 7.3), **무효 FK 진단(DEC-09)도 구현 완료**(모델 구조 진단·물리 ERD 노드 표시). **남은 것 (미착수)** : 관계 전체 수정 API·ERD 수정 버튼(지금은 삭제/규칙 수정 `PUT /api/physical/relation/{id}/rules` 만), 범위 밖 테이블과의 FK 등록, 컬럼 연결점으로 컬럼 쌍 미리 채우기, `REF_COLUMN` 관계 타입 검사, 타입 호환 표의 실제 DBMS 4종 실측, 테이블 승인 API 여러 행의 잠금 순서(P3). **결정 필요** : 관계·식별자 일관성 검증(관계 속성 매핑 또는 같은 표준 용어 정책). 영어 화면 충돌 재현은 논리 모델 화면만.
- 남은 작업
  - **동시 편집 — DEC-08 확정 (2026-11-16, D-09), 개발 대기 (P2)** : 모델 편집에 낙관적 충돌 검사를 단계적으로 도입한다. 클라이언트가 조회 당시 기준값을 보내고 서버가 지금 값과 비교해 다르면 HTTP 409, 사용자의 입력값은 버리지 않고(화면 보존) 재조회·충돌 안내, 승인·변경 요청 정책 유지. `MDFCN_DT` 를 기준값으로 쓰면 정밀도·같은 시각 수정·원자적 갱신(조건부 UPDATE 또는 행 잠금 후 비교)을 검증한다 — 단순히 읽고 비교하는 것만으로 안전하다고 보지 않는다. 이미 있는 기능별 검사(업무 설명 `base`, 용어 `baseTermId`, ERD 배치, AI 제안 `VER_NO`, 가져오기 `planToken`)와 겹치지 않게 공통 계약을 먼저 설계한다. 미승인 VIEW(DEC-13, [M-15])도 같은 계약.
  - 무효 FK — **DEC-09 확정 (2026-11-16, D-04), 2026-11-16 구현** : 사후에 무효가 된 FK 는 모델 수정 자체를 막지 않는다. [모델 구조 진단]이 오류로 표시하고(참조 테이블 없음·모호·PK 없음·복합 PK, 대상이 키가 아닌 사용자 정의 관계 — DDL 이 FK 를 만들지 않는 조건과 같은 판정), DDL Export 는 기존대로 경고한다 — completed-work.md [M-DIAG]. 물리 ERD 노드 자체의 오류 표시는 하지 않았다(테이블 상세의 미확정 참조 표시는 기존). `refTableName` 은 호환용으로 유지(엑셀 L열 계약). `REF_COLUMN` 관계의 타입 검사(P2), 타입 호환 표의 실제 DBMS 4종 실측(P2), 테이블 승인 API 여러 행의 잠금 순서(P3).
  - 관계 수정 API + ERD 수정 버튼(지금은 삭제 후 재등록), 범위 밖 테이블과의 FK 등록, 컬럼 연결점을 이어 컬럼 쌍 미리 채우기, 관계·식별자 일관성 검증(관계 속성 매핑 또는 같은 표준 용어 정책 필요).
- 참고 사항 : [model-integrity-hardening.md 8·11·12장](completed/model-integrity-hardening.md), [erd-editing-m8.md 10장](completed/erd-editing-m8.md), [physical-erd-editing-m8.md 5장](completed/physical-erd-editing-m8.md). 레이아웃 확장은 P3 [M-8-LAYOUT].

- **정합성 정리 (2026-11-17)** : 아래 '현재 상태 : MCP 코드·의존성·테이블은 없다' 와 '개발 대기 (상세 설계 선행)' 는 2026-11-16 이전 기록이다. **구현 완료** — DEC-31 5차([embedded-mcp-dec31.md](completed/embedded-mcp-dec31.md) : V6, 기존 Spring Boot 의 `POST /mcp` 읽기 전용, 기본 꺼짐·서버+프로젝트 이중 켜기, 해시·만료·폐기 토큰과 요청마다 발급자 권한 재확인, 도구 10개, 감사·호출 상한, 화면 `/mcpAccess`), 6차 실제 Claude Code·HTTPS 프록시 확인, 7차 `searchTables` 검색 방식 표시, 8차 `lexorma-ai` 모듈로 이동·Claude Code 재확인. 8.3 의 'UI-HELP 뒤' 순서와 달리 5차 지시로 먼저 구현됐다. **남은 것 (외부 환경 대기)** : 실제 nginx·로드밸런서 뒤 배포, 여러 인스턴스 운영(지금 정책은 단일 서버 — 호출 상한이 인스턴스마다 따로). 미승인 추정 관계 비공개(DEC-21)는 추정 관계 기능([AI-12])이 생길 때 적용.
- 현재 상태 : MCP 코드·의존성·테이블은 없다. 기존 [U-07] 은 **원본 DB 수집용 MCP Connector**(Lexorma 가 MCP 클라이언트, JDBC 를 대체하지 않는 선택 Connector)이고, 이 항목은 반대 방향 — **외부 AI 도구(MCP 클라이언트)가 Lexorma 의 메타데이터를 읽는 것**이다. 둘은 다른 작업이다.
- 지켜야 할 기존 원칙 : 단일 서버(별도 MCP 서버 프로세스를 요구하지 않는다 — [source-tool-architecture.md](reference/source-tool-architecture.md) 원칙 1·6), 원본 DB 도구는 AI 에 공개하지 않는다(AI 로드맵 원칙 12), 프로젝트 범위는 검증된 실행 컨텍스트에서만(`ExecutionContextVerifier`, 도구 인수로 받지 않음), 읽기 전용(쓰기·승인 도구 없음), 요청 로그 본문 보호(`LogBodyPolicy`), AI 없이도 핵심 기능 동작.
- **DEC-31 확정 (2026-11-16)** : 외부 AI 도구가 Lexorma 메타데이터를 조회하는 **선택형 MCP 서버를 기존 Spring Boot 에 내장**한다(별도 MCP 서버 운영 요구 없음). 기본 비활성, 켤 때만 추가 설정, 읽기 전용 Tool 만(기존 AI-4 도구·조회 로직 재사용), 프로젝트 권한·격리 유지, 검증된 사용자 인증 컨텍스트 사용, 원본 DB 직접 접근·DDL/DML 실행 Tool 없음, 비밀번호·토큰·Secret 반환 금지, 요청·응답 본문에 민감정보 기록 금지, 외부 인증 서버·추가 인프라를 필수로 만들지 않음, 미승인 추정 관계(DEC-21) 비공개.
- 구현 전 상세 설계 : 인증 방식, 프로젝트 선택 방식, 토큰 발급·폐기(저장 시 새 테이블 → 증분 마이그레이션), 감사 기록, 접근 제한. [source-tool-architecture.md](reference/source-tool-architecture.md) 원칙 1·6 과 4장(원본 수집용 MCP Connector, [U-07] — 반대 방향)과의 관계를 그 문서에 반영해 두었다.
- 완료 조건 : 정한 인증·전송으로 외부 MCP 클라이언트가 허용된 읽기 전용 도구만 프로젝트 범위 안에서 부르고, 기존 AI-4 의 권한·재검증·감사 규칙을 그대로 지킨다.
