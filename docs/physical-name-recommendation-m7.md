# M-7 3차. 표준 사전 기반 물리명 추천 — 설계 결정과 구현 기록

> [데이터 모델링 로드맵](data-modeling-roadmap.md) M-7 의 마지막 단계(물리명 추천)와 2차 UI 보완의 기록이다. 1차 : [logical-physical-mapping-m7.md](logical-physical-mapping-m7.md), 2차 : [model-mapping-quality-m7.md](model-mapping-quality-m7.md).
> 작성일 2026-11-11. **DB 변경 없음** (Flyway V0~V4 그대로, 새 마이그레이션 없음). 추천은 조회 전용 — 테이블·컬럼의 이름, 논리 모델, 표준 사전, 매핑을 바꾸지 않는다.

## 1. 기존 구조 분석과 결정

| 확인 항목 | 결과 → 결정 |
|---|---|
| 표준 용어의 영문약어 | `TB_STD_TRM` 에 **저장된 값**이다. 화면 등록은 용어명과 단어 수가 같은 약어를 입력받아 각 약어가 표준 단어인지 검증하고(`validateWordCount`·`getStandardTermDomain`), 엑셀 업로드는 약어를 쓰지 않는 프로젝트에서 단어 영문명을 조합해(`toEnglishTermName`) 저장한다. 약어 없이 용어를 등록하는 경로는 없다 → **컬럼명 추천 = 저장된 영문약어.** 약어가 비어 있는 용어(직접 넣은 데이터)는 다시 조합하지 않고 추천 불가로 둔다 — 조합 규칙의 결과가 곧 저장된 약어이기 때문이다 |
| 컬럼명 규칙 | "컬럼명 = 연결한 표준 용어의 영문약어" 하나뿐 (컬럼 등록·일괄 저장·업로드, [M-5 2차](standardization-quality-m5.md)). M-7 2차의 명칭 진단이 이미 이 값을 기대 컬럼명으로 썼다 → 그 계산을 추천 서비스로 옮겨 **한 곳에서** 한다 |
| 테이블명 규칙 | **있다.** 테이블 등록이 쓰는 `TableDesignService.generateTableName` : 한글명을 공백·밑줄로 나눈 단어가 모두 **승인된 표준 단어**면 `프로젝트 접두어 + 단어 영문약어(_ 연결, 대문자)`. 단어 순서는 적은 순서 그대로, 같은 이름의 단어가 여럿이면 승인된 것 우선 → **엔터티명에 같은 규칙을 적용한다.** 결정적이지 않은 부분(붙여 쓴 엔터티명을 단어로 쪼개기, 약어 추측)은 하지 않는다 |
| 논리 엔터티 | 표준 용어·단어를 참조하지 않는다 (이름·설명·승인 상태만). 근거는 **엔터티명 문자열**뿐이다 → 위 규칙으로 나뉘지 않으면 추천 불가 (사유에 걸린 단어를 적는다) |
| 이름 중복 기준 | 컬럼명은 **같은 테이블** 안, 테이블명은 **같은 프로젝트** 안 (`updateTable` 의 `findAllByTableNameAndProjectId`, 스키마 단위가 아니다) → 충돌 판정도 같은 범위 |
| DBMS 식별자 규칙 | `TableDdlGenerator` 는 식별자를 따옴표로 감싸지 않는다 → 지원하는 모든 DBMS 에서 대소문자만 다른 이름은 같은 객체다 → **대소문자 무시**로 비교. 식별자 길이 제한·예약어 규칙은 저장소에 없다 → **판정하지 않는다** (7장) |
| 이름 변경 기능 | 테이블은 한글명을 고치면 테이블명이 다시 만들어지고(`updateTable`), 컬럼은 컬럼 편집(일괄 편집)·컬럼 관리에서 용어를 바꾼다 → 추천 화면은 그 화면들로 **이동만** 시킨다. 새 적용 API 는 만들지 않았다 |
| 문서 | `CLAUDE.md` 는 저장소에 없다 (다른 문서가 인용만 한다) → 갱신하지 않았다 |

## 2. 추천 정책

### 2.1 컬럼명 (`source = STANDARD_TERM`)

추천 컬럼명 = 논리 속성에 연결된 표준 용어의 영문약어 (앞뒤 공백 제거). 속성 1개가 1행이며 매핑 여부와 관계없이 나온다.

| 순서 | 조건 | 상태 | 사유 |
|---|---|---|---|
| 1 | 속성에 표준 용어가 없다 / 용어에 영문약어가 없다 | `UNAVAILABLE` (추천명 없음) | 논리 속성에 표준 용어가 없어… / …영문약어가 없어 기대 컬럼명을 알 수 없습니다 |
| 2 | 매핑된 컬럼의 이름 = 추천명 (대소문자 무시) | `ALREADY_MATCHED` | 현재 컬럼명이 표준 용어의 영문약어와 같습니다 |
| 3 | 엔터티에 매핑된 테이블에서 **이 속성의 컬럼이 아닌 다른 컬럼**이 추천명을 쓴다 | `CONFLICT` | 그 컬럼이 속성 X 에 매핑됨 / 논리 속성에 매핑되지 않은 컬럼 (구분) |
| 4 | 그 밖 | `AVAILABLE` | 현재 컬럼명과 다름 / 속성이 컬럼에 매핑되지 않음 / 엔터티가 테이블에 매핑되지 않음 (구분) |

- 매핑하지 않은 속성도 추천명은 나온다 (현재 컬럼명 없음). 같은 이름의 컬럼이 테이블에 이미 있으면 "새 컬럼으로 만들 수 없는 이름"이라 충돌이다 — 그 컬럼이 매핑 대상일 수 있다는 것은 사유로 알 수 있지만 **자동으로 매핑하거나 후보로 제안하지 않는다.**
- 한 엔터티의 두 속성이 같은 용어를 쓰면 둘 다 같은 추천명이 나온다. 아직 그 이름의 컬럼이 없으면 둘 다 `AVAILABLE` 이다 (추천끼리의 충돌은 보지 않는다 — 7장).

### 2.2 테이블명 (`source = STANDARD_WORD`)

추천 테이블명 = `generateTableName(엔터티명)`. 엔터티 1개가 1행.

| 순서 | 조건 | 상태 |
|---|---|---|
| 1 | 엔터티명에 단어가 없다 / 표준 단어로 등록되지 않은 단어가 있다 / 승인되지 않은 표준 단어가 있다 | `UNAVAILABLE` (걸린 단어를 사유에 적는다) |
| 2 | 매핑된 테이블의 이름 = 추천명 (대소문자 무시) | `ALREADY_MATCHED` |
| 3 | 프로젝트의 **다른 테이블**이 추천명을 쓴다 | `CONFLICT` (엔터티 X 에 매핑된 테이블 / 매핑되지 않은 테이블) |
| 4 | 그 밖 | `AVAILABLE` |

응답의 `words` 에 단어별 변환 결과(단어 → 영문약어, 승인·미승인·미등록), `tablePrefix` 에 프로젝트 접두어가 들어 있다 (추천 근거).

**테이블명 추천이 가능한 조건 :** 엔터티명을 표준 단어를 공백(또는 `_`)으로 띄어 적었을 때. 예제(META-MORA)의 엔터티명은 물리 예제의 테이블 한글명이라 37개 전부 `ALREADY_MATCHED` 다. "회원등급"처럼 붙여 쓴 이름은 그 문자열이 표준 단어가 아니면 추천 불가다.

### 2.3 정합성 명칭 진단과의 관계

```text
표준 용어(영문약어) ─▶ PhysicalNameRecommendationService.recommendColumnName ─┬─▶ 물리명 추천 API (상태·근거·충돌)
                                                                              └─▶ 정합성 비교 NAME 진단 (기대 컬럼명)
```

| 추천 상태 | 명칭 진단 (매핑된 속성만) |
|---|---|
| `ALREADY_MATCHED` | `MATCH` |
| `UNAVAILABLE` | `NOT_COMPARABLE` (불일치로 세지 않는다) |
| `AVAILABLE`·`CONFLICT` | `MISMATCH` — 충돌은 명칭 일치 여부와 다른 개념이라 진단은 "다르다"까지만 본다 |

명칭 진단의 판정·사유 문구는 2차와 같다. M-5 품질 진단(`StandardizationQualityService`)은 건드리지 않았다.

## 3. 백엔드 (`metamora-data` `mapping/`)

| 구성 | 내용 |
|---|---|
| `GET /api/modelMapping/recommendation/column/summary?modelId` (VIEWER) | `total`(모델의 속성 수)·`available`·`alreadyMatched`·`unavailable`·`conflict`. 네 상태의 합 = `total` |
| `GET /api/modelMapping/recommendation/column/data` (VIEWER) | 그리드 형식. 조건 `modelId`·`entityId`·`attributeId`·`columnId`·`status`, 검색 `entityName`(기본)·`logicalName`·`currentPhysicalName`·`recommendedPhysicalName`, 정렬은 같은 네 필드 (기본 엔터티명 → 속성 순서). `modelId` 는 `attributeId`·`columnId` 가 없으면 필수. 1행 : `logicalAttributeId`·`logicalName`·`termId`·`termName`·`termAbbreviation`·`physicalColumnId`·`currentPhysicalName`·`recommendedPhysicalName`·`status`·`source`·`reason` + 모델·엔터티·스키마·테이블 |
| `GET /api/modelMapping/recommendation/table/data` (VIEWER) | 그리드 형식. 조건 `modelId`·`entityId`(`modelId` 는 `entityId` 가 없으면 필수), 검색 `logicalName`(엔터티명)·`currentPhysicalName`(테이블명). 1행 : `logicalEntityId`·`logicalName`·`physicalTableId`·`currentPhysicalName`·`recommendedPhysicalName`·`status`·`source`·`reason`·`tablePrefix`·`words` |
| `GET /api/modelMapping/entity/data` 에 `entityId` 조건 추가 | 그 엔터티 1건만 (4장의 ID 포커스). 기존 조건·응답은 그대로 |
| `PhysicalNameRecommendationService` | 읽기 전용. `recommendColumnName`·`sameName`(static)은 정합성 비교와 공용 |
| `PhysicalNameRecommendationQueryRepository` | 컬럼명 추천은 **상태 조건까지 DB 에서** 걸러 페이징한다 (추천명이 저장된 약어라 SQL 로 판정할 수 있다). 충돌 사유용으로 한 쪽 분량의 "그 이름을 쓰는 컬럼(테이블)"을 1번 더 읽는다 |
| `TableDesignService.generateTableNames` | 여러 한글명을 표준 단어 조회 1번으로 변환. `generateTableName` 과 같은 내부 규칙을 쓴다 (단어 조회 방법만 다르다) |

- 단건 조회용 엔드포인트(`/column/{attributeId}`·`/table/{entityId}`)는 따로 만들지 않고 목록의 `attributeId`·`columnId`·`entityId` 조건으로 대신한다.
- **조회 수 :** 컬럼명 목록 = 모델 확인 1 + 행 1 + 건수 1 + 충돌 이름 1. 요약 = 모델 확인 1 + 상태별 건수 4. 테이블명 목록 = 모델 확인 1 + 엔터티 행 1 + 건수 1 + 표준 단어 1 + 프로젝트(접두어) 1 + 충돌 이름 1. 행마다 조회하지 않는다 (N+1 없음). 정합성 비교와 달리 모델 전체를 메모리에 올리지 않는다.
- 테이블명 목록은 표준 단어 변환이 자바 규칙이라 **상태 조건을 받지 않는다** (엔터티 수는 속성 수보다 훨씬 적다).
- **프로젝트 격리 :** 프로젝트는 항상 로그인 프로젝트. 다른 프로젝트의 `modelId` 는 `LOGICAL_MODEL_IS_NOT_DEFINED`(400), 다른 프로젝트의 `entityId`·`attributeId`·`columnId` 는 결과 0건. 표준 단어·접두어·충돌 테이블도 로그인 프로젝트 것만 본다.

| 매핑 상세 대화상자 | [물리명 추천 보기] 추가 (그 엔터티로 좁힌 추천 탭) |

### 6.1 자동 테스트

## 7. 제약 · 후속

- **식별자 길이·예약어** : 추천명이 대상 DBMS 의 길이 제한(Oracle 30/128, PostgreSQL 63, MySQL 64)이나 예약어에 걸리는지 보지 않는다. DDL 생성에도 같은 검사가 없다. 넣는다면 `TableDdlGenerator` 와 함께.
- **추천끼리의 충돌** : 한 테이블에 매핑된 두 속성이 같은 추천명을 받는 경우, 두 엔터티가 같은 추천 테이블명을 받는 경우는 판정하지 않는다 (지금 그 이름을 쓰는 물리 객체가 없으면 둘 다 추천 가능).
- **붙여 쓴 엔터티명** : 표준 단어 사전으로 문자열을 분해하는 규칙(최장 일치 등)은 모호해서 만들지 않았다. 엔터티에 테이블 한글명이나 표준 단어 구성을 직접 저장하면(논리 모델 확장) 근거가 명확해진다.
- **추천 적용** : 일괄·자동 적용은 없다. 만들 경우 테이블은 `updateTable`(한글명 → 테이블명 재생성, 참조 컬럼·관계 동기화), 컬럼은 승인 정책·관계·인덱스 참조를 거쳐야 한다.
- **테이블명 추천의 상태 조건·요약** : 표준 단어 변환이 자바 규칙이라 없다. 필요해지면 단어 조합 결과를 SQL 로 계산하거나 추천 결과를 저장해야 한다.
- 정합성 비교의 메모리 기반 페이징은 그대로다 (2차 문서 7장).
