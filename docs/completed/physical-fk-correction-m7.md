# M-7 기존 물리 테이블 누락 FK 보정 · 관계 동기화 교착 개선 — 설계 결정과 구현 기록

> [model-mapping-quality-m7.md 9장](model-mapping-quality-m7.md)(구조 정합성 진단), [physical-name-recommendation-m7.md](physical-name-recommendation-m7.md)(물리명 일괄 적용),

> 같은 날 후속 마무리 (사용자 확정 M7-FK-D09~D11 — 14장) : 이름 변경 409 계약 확정, 단일 FK 보정 보류의 M-8 이관, 일반 컬럼 일괄 저장의 PK 삭제 교차 교착 해결, 관계 등록 ↔ FK 보정의 중복 FK 결함 수정.

## 1. 배경

- 논리 → 물리 생성은 이미 매핑된 엔터티의 테이블을 바꾸지 않는다 (P1-a, 15장). 그래서 테이블을 먼저 만들고 나중에 논리 관계·속성 짝을 정하면 물리 FK 가 없다.
  구조 정합성 진단은 이를 `FK_MISSING` 으로 보여 주기만 했다.
- 분석 단계(같은 날)에서 격리 PostgreSQL 18.6 으로 관계 동기화의 **실제 교착 2종(SQLSTATE 40P01)** 을 재현했다 :
  - S4 : 서로 다른 스키마의 테이블 이름 변경 둘. 서로의 새 이름을 미리 참조하는 컬럼이 있을 때 생긴다.
  - S6b : 물리명 일괄 적용 ↔ 그 테이블을 참조하는 501행 엑셀 업로드.

## 3. 관계 표현과 승인 — 지원 유형과 보류 유형

기존 P2 규칙(logical-physical-mapping-m7.md 15장)을 그대로 쓴다.

| 유형 | 표현 | 이번 처리 |
|---|---|---|
| 복합 FK (자기 참조 포함) | 미승인 USER `TableRelation` — `PhysicalModelService.createGeneratedForeignKey` (생성과 같은 경로·검사) | **지원** |
| 단일 자기 참조 FK | 미승인 USER `TableRelation` (같은 경로) | **지원** |
| 자기 참조가 아닌 단일 FK | 자식 컬럼의 참조 테이블명 → 관계 동기화가 `REF_COLUMN` 관계를 만든다 | **보류 (D08)** — `SINGLE_FK_HELD` |

**보류 근거** (실제 저장 데이터로 확인 — `ForeignKeyCorrectionIntegrationTest.approvalPersists`) :

- 관계 동기화(`syncReferenceRelations`)는 `REF_COLUMN` 관계를 **항상 `APRV_YN = true`** 로 만든다. 논리 → 물리 생성이 만든 단일 FK 도 테이블·컬럼은 미승인인데 관계는 처음부터 승인 상태다.
- 같은 관계를 다시 동기화하면 그 행을 유지한다 (ID·승인 상태 그대로). 참조 테이블명을 지웠다 다시 적거나 대상 PK 가 사라졌다 생기면 관계를 지우고 다시 만들어 다시 승인 상태가 된다.
- 즉 참조 테이블명으로 FK 를 보정하면 승인 절차 없이 승인된 관계가 생긴다 (승인 우회). 미승인으로 바꾸려면 REF_COLUMN 승인 구조를 바꿔야 하고, USER 관계로 만들면 P2 규칙을 어긴다 (참조 테이블명 컬럼과 같은 FK 를 두 곳에서 정의). 둘 다 이번 범위 밖이다.
- 진단은 `FK_MISSING` 그대로다. 보정 가능 여부만 `SINGLE_FK_HELD`(정책 보류)로 보이고, 직접 적용 요청도 서버가 400 으로 거절한다. 사용자는 기존처럼 컬럼 관리에서 참조 테이블을 지정할 수 있다 (화면 안내).

**지원 유형의 승인** :

- 만든 관계는 미승인이다 (`createGeneratedForeignKey` 는 승인 여부를 로그인 사용자로 정하지 않는다 — 생성과 같다).
- 실제 확인한 것 : 관계 동기화·자식 테이블 컬럼 등록·자식 테이블 설명 수정 뒤에도 미승인으로 남는다 (통합 테스트). H2 Standalone 앱 재시작 뒤에도 남는다 (11장).
- 승인은 기존 승인 절차(`updateApproval`, 승인 권한자)로만 된다.
- 승인된 **자식 테이블**·**자식 컬럼**은 막는다 (`CHILD_TABLE_APPROVED`·`CHILD_COLUMN_APPROVED` — 승인된 객체는 고칠 수 없다는 기존 규칙). 관리자 요청도 같다.
- 부모 테이블·부모 컬럼은 참조만 하므로 승인돼 있어도 된다.

## 4. 보정 대상과 판정 (`mapping/service/ForeignKeyCorrectionService`)

진단을 다시 구현하지 않는다. `ModelMappingQualityService.structureRows`(구조 정합성 판정, 모델 단위 10개 조회)의 RELATIONSHIP 행에서 기대 자식·부모 컬럼 쌍(짝 순서)을 그대로 쓴다.
진단 상태·건수·의미는 바뀌지 않는다. 보정 가능 여부는 따로 계산한다 — `FK_MISSING` 이 곧 보정 가능은 아니다.

| 진단 코드 | 처리 |
|---|---|
| `FK_MISSING` | 아래 검사를 통과하면 보정 가능 |
| `FK_MATCH`·`FK_ORDER`·`FK_TARGET`·`FK_COLUMNS` | `NOT_MISSING` — 기존 FK 그대로 |
| `FK_AMBIGUOUS`·`FK_SHARED`·`FK_NOT_EXPECTED`·`ENTITY_UNMAPPED`·`ATTRIBUTE_UNMAPPED`·`PAIRS_*`·`PARENT_KEY_MISSING` | `NOT_MISSING` — 보정 불가 |
| `PHYSICAL_FK`(물리 전용)·`INHERITANCE`(상속 구조) | 관계 행이 아니므로 대상 아님 (그대로 둔다) |

`FK_MISSING` 관계의 추가 검사 (막는 사유 `Code`, 행마다 모두 모은다) :

| 코드 | 조건 |
|---|---|
| `INHERITANCE_LINK` | 자식 엔터티의 직계 슈퍼타입이 부모 엔터티 — 상속 FK 는 상속 구조 진단이 다룬다 (상속 FK 가 있으면 진단은 원래 `FK_COLUMNS`). **2026-11-22 M7-INH-01 (D-INH-11) 로 좁힘** : 관계의 FK 구성이 실제 상속 FK 쌍과 같을 때(진단 `INHERITANCE_FK_OVERLAP`)만. 그 밖의 서브타입 ↔ 직계 슈퍼타입 일반 관계는 일반 FK 로 진단·보정한다 (FK-11 기대값 변경 — [inheritance-reference-key-m7.md](inheritance-reference-key-m7.md) 4.4) |
| `SINGLE_FK_HELD` | 자기 참조가 아닌 단일 FK (3장) |
| `CHILD_TABLE_APPROVED`·`CHILD_COLUMN_APPROVED` | 승인된 자식 테이블·자식 컬럼 |
| `REF_COLUMN_CONFLICT` | 자식 컬럼에 참조 테이블명이 있다 (관계 저장 `buildRelation` 과 같은 규칙) |
| `RELATION_EXISTS` | 같은 자식 테이블·부모 테이블·자식 컬럼 순서의 관계(논리 관계 `LOGICAL` 포함)가 이미 있다 |
| `PARENT_KEY_INVALID` | 부모 컬럼이 부모 테이블 PK 가 아니다, 짝 컬럼을 찾을 수 없다 (진단의 PK 전체 기준은 넓히지 않는다 — UNIQUE 참조는 다음 작업) |
| `TYPE_INCOMPATIBLE` | `TableDdlGenerator.isReferenceTypeCompatible` (프로젝트 DBMS 기준, DDL·관계 저장과 같다) |
| `DUPLICATE_COLUMN` | 짝에 같은 컬럼이 두 번 |
| `SHARED_STRUCTURE` | 같은 FK 구성(자식·부모 테이블 + 순서 있는 컬럼 쌍)을 기대하는 다른 논리 관계가 모델에 있다 (골랐든 안 골랐든) — 만들면 `FK_SHARED` 가 되므로 자동으로 고르지 않는다 |
| `NAME_CONFLICT` | 만들 FK 이름(`DbIdentifierRules.foreignKeyName` = DDL `FK_<자식 테이블>_<첫 자식 컬럼>`)이 같은 스키마의 다른 FK 와 같다 (대소문자 무시), 또는 같은 요청 안에서 겹친다 |

- 상속 PK 를 참조하는 일반 관계(부모 = 서브타입) : 진단이 상속 PK 매핑 컬럼으로 정한 쌍을 그대로 쓴다. 단일이면 위 보류 규칙이 적용된다 (`ForeignKeyCorrectionIntegrationTest.inheritance`).
- 기존 물리 모델 보호 : 테이블·컬럼·타입·PK·UNIQUE·CHECK·인덱스·매핑·상속 PK 매핑·원본 매핑·기존 관계(ID·구성·승인)는 바꾸지 않는다. 보정 전후 스냅샷 비교 결과 새 관계 행만 늘었다 (테이블·컬럼 `MDFCN_DT` 까지 같음).

## 5. API

| API | 권한 | 내용 |
|---|---|---|
| `GET /api/modelMapping/quality/foreignKey/status?modelId=&relationshipIds=` | VIEWER | 목록·상세 표시용 보정 가능 여부 (토큰 없음, 최대 100개 — 목록 한 쪽) |
| `POST /api/modelMapping/quality/foreignKey/preview` | USER | `{modelId, relationshipIds}` → `Plan {items, total, correctable, blocked, applicable, planToken}`. 아무것도 저장하지 않는다 (모델 버전도 없음) |
| `POST /api/modelMapping/quality/foreignKey/apply` | USER | `{modelId, relationshipIds, planToken}` → `Result {selected, created, relationIds, versionId, versionName}` |

- 항목(`Item`) : 논리 관계 ID·이름·표시값, 부모·자식 엔터티, 부모·자식 테이블(스키마), 진단 코드, 표현(`USER_RELATION`·`REF_COLUMN`), 자기 참조 여부, 만들 FK 이름, 승인 상태(항상 미승인), 컬럼 쌍(순서·이름·DBMS 타입), 보정 가능 여부, 사유.
- 요청 검사 : 빈 선택·중복 ID·101개 이상·빈 ID 는 400 `INVALID_PHYSICAL_MODEL`.
- 이 모델의 관계가 아니면 400 (같은 프로젝트 다른 모델·없는 ID·삭제된 관계). 다른 프로젝트의 모델이면 `LOGICAL_MODEL_IS_NOT_DEFINED`.
- 요청의 컬럼·참조 테이블·방향은 받지 않는다 — 계획은 서버가 최신 논리 관계·매핑으로 계산한다.
- 상한 100 : 정합성 목록 한 쪽의 최대 크기와 같다. 관계마다 검사 조회는 묶음 조회(컬럼·관계·이름 한 번씩)라 상한은 요청 크기 제한용이다.

## 6. 계획 토큰 · 적용 · 원자성

- 토큰 `fk-correction/1` = SHA-256(프로젝트·모델·DBMS + 관계 ID 순서로 정렬한 항목의 진단 코드·자식/부모 테이블 ID·이름·표현·만들 FK 이름·컬럼 쌍(ID·이름·DBMS 타입)·막는 사유 코드).
  - 승인 상태·참조 테이블명·PK·매핑·기존 FK 는 진단 코드와 사유 코드로 들어간다. 무관한 데이터(설명 등)는 넣지 않는다.
  - 저장하지 않는다 (결정적 계산). 권한 검사를 대신하지 않는다.
- 적용 순서 :
  1. 프로젝트 행 배타 (맨 먼저)
  2. 논리 모델 행 → 자식·부모 테이블 행(ID 순) → 자식·부모 컬럼 행(ID 순), 모두 NOWAIT (`ModelRowLocks`, 바쁘면 409)
  3. 다시 진단·계획 → 토큰 비교 (다르면 409 `MODEL_CONFLICT`)
  4. 막는 사유가 있으면 400 (부분 적용 없음)
  5. 직전 모델 버전 `FKFIX-<요청 ID>` (`ModelVersionService.createBeforeModelChange`, 같은 트랜잭션, 요청당 1개)
  6. 변경 그룹 ID = 버전명 → 관계 생성 → flush
  7. **같은 진단으로 고른 관계가 모두 MATCH 인지 확인** (아니면 전체 롤백)
- 원자성 : 두 번째 FK 생성을 실패시키면 첫 FK·모델 버전·변경 이력까지 모두 롤백된다 (테스트 훅). 409·400 뒤에도 아무것도 남지 않는다.
- 기존 행의 키를 바꾸지 않으므로 FOR UPDATE 강도 잠금은 쓰지 않는다. 관계 INSERT 의 FK 검사(KEY SHARE)는 스스로 NKU 로 잠근 행에만 걸린다.

## 7. 화면 (`features/mapping/foreignKeyCorrection.tsx`, `MappingQuality.tsx`)

- [정합성 비교] → [논리 관계·물리 FK] 범위에서만 보인다. 새 메뉴는 없다. 물리 모델 생성 화면에는 넣지 않았다.
- **FK 보정** 칸 : FK 누락 행만 보정 가능 / 정책 보류 / 보정 불가(첫 사유 + 개수, 전체 사유는 title·상세). 한 쪽의 FK 누락 관계를 상태 API 한 번으로 묻는다 (행마다 부르지 않는다).
- 진단 결과 칸·요약 건수는 그대로다 (보류돼도 `FK_MISSING`).
- 편집 권한(`model-mapping-edit`, USER 이상)일 때만 고르기 칸과 선택 막대가 보인다.
  - 고르기 칸은 보정 가능한 행만 켤 수 있다. 막대 : 선택 수 / 최대 100, 다른 쪽에서 고른 수, 이 쪽 보정 가능 관계 선택, 선택 모두 비우기, [FK 보정 미리보기].
  - 선택은 쪽·검색을 바꿔도 유지된다. 모델이 바뀌거나 진단 범위를 벗어나면 비워진다.
- 미리보기 대화상자 (물리명 일괄 적용과 같은 구성) : 논리 관계, 자식 → 부모 테이블(스키마), FK 컬럼 쌍(순서 번호), 만들 FK 이름과 '미승인 관계', 판정·사유. "기존 FK·컬럼·타입·PK·UNIQUE 를 바꾸지 않는다" 안내.
  - 보정 불가가 하나라도 있으면 적용 버튼이 막히고 [보정 불가 항목을 선택에서 빼고 다시 미리보기] 가 보인다.
  - 확인 문구에 직전 버전(FKFIX-…)·전체 롤백 안내가 있다.
  - 409 면 계획을 버리고 목록을 새로 고친 뒤 [다시 미리보기] 를 안내한다 (자동 재시도 없음).

## 8. 관계 동기화 교착 — 원인과 보완 (M7-FK-02)

### 8.1 잠금 사실 (PostgreSQL 실측)

- 일반 부모 행 잠금(`findForUpdate`, JPA PESSIMISTIC_WRITE)은 `FOR NO KEY UPDATE` 다. FK 검사의 `FOR KEY SHARE` 와 함께 잡힌다. 프로젝트 행 배타(`findByIdForUpdate`)도 실제로는 `FOR NO KEY UPDATE` 이며, 커밋 직전의 프로젝트 `FOR SHARE` 와 충돌한다.
- 테이블 이름·스키마 UPDATE(`UX_TBL_01` 열), 컬럼 이름 UPDATE(`UX_COL_01` 의 생성 열), DELETE 는 `FOR UPDATE` 강도다. 다른 트랜잭션의 KEY SHARE 와 충돌한다.
- 엑셀 업로드는 청크마다 관계 동기화 → flush 를 해서 트랜잭션 도중에 관계 INSERT(KEY SHARE)를 내보낸다. 커밋 직전에 프로젝트 FOR SHARE 를 잡는다.

### 8.2 교착 원인

- S4 : 두 이름 변경이 각자 자기 테이블에 FOR UPDATE(이름 UPDATE)를 쥔 채, 관계 동기화가 상대 테이블 행에 KEY SHARE 를 요청해 순환했다. 프로젝트 잠금이 없어 직렬화되지 않았다.
- S6b : 물리명 적용이 프로젝트를 배타로 쥔 채 이름 UPDATE 로 엑셀의 KEY SHARE 를 **기다렸다**. 엑셀은 커밋 때 프로젝트 FOR SHARE 를 기다려 순환했다. 적용의 행 잠금은 NOWAIT 였지만 NKU 였다. 실제 충돌은 그 뒤의 UPDATE 격상에서 났다.

### 8.3 보완 (`physical/sync/ModelRowLocks` 공통)

| 경로 | 보완 |
|---|---|
| 테이블 변경(`TableDesignServiceImpl.updateTable`)의 이름 변경·스키마 이동 | 잠그기 전에 키 변경 여부를 판정한다 (한글명으로 이름을 다시 만드는 경우 포함). 바꾸면 물리명 적용과 같은 순서다 : 프로젝트 행 배타(맨 먼저) → 스키마 행 NOWAIT(`ObjectNamespace.lockNoWait`, 기본 스키마 먼저) → 테이블 행 **FOR UPDATE NOWAIT**(키 강도) + NKU → 소속 컬럼·참조 컬럼·**새 이름을 미리 참조하던 컬럼** NKU NOWAIT. 잠근 뒤 이름이 바뀌었는데 키 변경 경로가 아니면 409. 설명만 고치는 저장은 예전 그대로다 (프로젝트 행을 먼저 잡지 않는다 — PostgreSQL 테스트로 확인) |
| 물리명 일괄 적용(`PhysicalNameRenameService.apply`) | 이름을 바꿀 테이블·컬럼 행을 **FOR UPDATE NOWAIT** 로 먼저 잡는다. 새 이름을 미리 참조하던 컬럼도 NOWAIT 로 잠근다 |
| 원본 삭제 반영(`SourceDeletionService.apply`, 프로젝트 배타) | 지울 테이블 행과 지울 컬럼 행(컬럼 항목 + 지울 테이블의 모든 컬럼)을 FOR UPDATE NOWAIT — DELETE 도 같은 강도다. 바쁘면 기존 409 `SOURCE_COMPARE_STALE` |
| 누락 FK 보정 | 키를 바꾸지 않으므로 NKU NOWAIT 만 (6장) |

- 키 강도 잠금은 네이티브 `select … for update nowait` 다 (ID 순, 1,000개씩). H2 도 같은 문장을 받는다 (KEY SHARE 구분이 없어 일반 배타 잠금).
- NOWAIT 실패(PostgreSQL 55P03, H2 50200)만 409 `MODEL_CONFLICT` 로 바꾼다. 40P01·UNIQUE·FK 위반은 바꾸지 않는다.
- 프로젝트 배타를 잡은 뒤에는 어떤 행 잠금도 기다리지 않는다 (잡은 뒤 새로 프로젝트 배타를 잡는 구조 없음).
- 쓰지 않은 것 : 일반 저장 전체의 프로젝트 배타, 참조 테이블 무조건 배타, 전역 Java 잠금, Redis, 재시도, 동기화 비동기·별도 트랜잭션, 엑셀 청크별 커밋, UNIQUE·FK 제거.

### 8.4 바뀐 계약 (D06 확정 정책의 결과)

테이블 이름 변경·스키마 이동은 이제 다른 트랜잭션이 같은 행을 잡고 있으면 **기다리지 않고 409** 다. 예전에는 기다렸다가 그 결과를 보고 판정했다.
기다리면 상대의 커밋(프로젝트 FOR SHARE)과 서로 기다리므로 피할 수 없다. 기존 테스트 3개의 기대 결과 코드를 새 계약으로 고쳤다. 무결성 단언(한 쪽만 성공·승인 상태·이름 유지·중복 없음)은 그대로다.

| 테스트 | 예전 | 지금 |
|---|---|---|
| `ModelIntegrityHardeningIntegrationTest.approvalAndUpdateRace` (승인이 행을 잡은 뒤 이름 변경) | `APPROVED_DATA_CANNOT_BE_UPDATE` | `MODEL_CONFLICT` |
| `ViewManagementIntegrationTest.concurrentNames` (VIEW 등록 ↔ 같은 이름으로 테이블 이름 변경) | 실패 쪽 = 이름 중복 | 이름 변경 쪽은 이름 중복 또는 409 |

| 모델 교환 가져오기 | INSERT 만. 커밋 때 동기화가 잠그지 않은 기존 테이블 행에 KEY SHARE | 재현하지 않은 잠재 위험 (아래) |
| 누락 FK 보정 | 없음 | NKU NOWAIT (6장) |

**새로 확인한 교착 (일반 경로)** — 같은 날 후속에서 **해결 (M7-FK-D11, 14장)**. 아래는 분석 당시 기록이다 :

- 컬럼 일괄 저장 A(테이블 TA 의 PK 컬럼 삭제 + TB 를 참조하는 컬럼 추가) ↔ 일괄 저장 B(TB 의 PK 컬럼 삭제 + TA 를 참조하는 컬럼 추가).
- 격리 PostgreSQL 에서 **40P01 3/3** 이었다 (`insert into tb_tbl_rel_col` — 각자 상대가 지우는 PK 컬럼에 KEY SHARE).
- 프로젝트 잠금과 무관한 일반 저장끼리의 순환이다. 고치려면 일반 컬럼 저장의 잠금 규칙을 바꿔야 한다. 예 : 삭제가 있는 일괄 저장도 키 변경 경로(프로젝트 배타 + NOWAIT)로 보내기, 또는 삭제·참조 대상 행을 한 전역 순서로 먼저 잠그기. 어느 쪽이든 '일반 저장 동시성 유지' 정책과 부딪쳐 이번에는 바꾸지 않았다.
- 교착이 나도 PostgreSQL 이 한쪽을 롤백하므로 데이터는 깨지지 않는다 (실패 응답은 일반 오류).

**재현하지 않은 잠재 위험** (분석 당시) : 모델 교환 가져오기·논리 → 물리 생성의 커밋 시 동기화가 다른 트랜잭션이 지우는 중인 PK 컬럼을 참조하는 경우, 컬럼 단건 삭제 ↔ 참조 관계 생성. → 14.5 : PK 컬럼 삭제가 모두 구조 변경 경로(프로젝트 배타)로 바뀌어 앞의 것은 직렬화되고, 뒤의 것은 실제로 실행해 교착이 없음을 확인했다.

- 측정하지 않은 것 : 엑셀 1,000·2,000행, 물리명 일괄 적용, 논리 → 물리 생성.
  - 엑셀·생성은 코드를 바꾸지 않았다. 물리명 적용은 잠금 문장이 테이블·컬럼 종류마다 1개 늘었다.
  - 잠금 대기 시간은 시나리오 테스트(9장)로만 봤다. 메모리 사용량은 재지 않았다.
- 측정 코드는 임시 테스트였고 지웠다.

### 14.1 D09 — NOWAIT·409 계약 확정

- 8.4 의 기존 테스트 3개(`ModelIntegrityHardeningIntegrationTest.approvalAndUpdateRace`, `ViewManagementIntegrationTest.concurrentNames`, `ViewNamePolicyIntegrationTest`)의 기대값이 최종 계약이다 : 테이블 이름 변경·스키마 이동이 승인 처리·VIEW 등록과 겹치면 409 `MODEL_CONFLICT` 일 수 있다.
- 무결성 단언(한쪽만 성공, 승인 상태·기존 이름 보존, 중복 이름 없음, 실패 쪽 전체 롤백)은 그대로이고, 잠금이 풀린 뒤 같은 요청은 정상 처리된다 (S6b 재적용, `d11NoWaitContract`).
- 경합이 없으면 업무 오류 그대로다 : 승인된 테이블의 수정·이름 변경·스키마 이동은 `APPROVED_DATA_CANNOT_BE_UPDATE` (`ModelIntegrityHardeningIntegrationTest` 91~93행), 이름 중복은 기존 중복 오류, FK·UNIQUE 위반은 409 로 바꾸지 않는다.
- 새 공용 잠금 행·잠금 테이블은 없다.

### 14.2 D10 — 일반 단일 FK 보정 보류 확정 · M-8 이관

| FK 유형 | 보정 | 관계 표현 |
|---|---|---|
| 자기 참조가 아닌 단일 FK | **보류** (`SINGLE_FK_HELD`) | REF_COLUMN |
| 복합 FK | 지원 | USER (미승인) |
| 단일 자기 참조 FK | 지원 | USER (미승인) |
| 복합 자기 참조 FK | 지원 | USER (미승인) |

- 진단은 `FK_MISSING` 그대로, 보정 불가 사유 표시, 화면에서 고를 수 없음, 직접 API 요청은 400 — 코드 변경 없음 (E2E 로 다시 확인).
- REF_COLUMN 승인 구조(동기화가 항상 승인 상태로 만든다)는 바꾸지 않았다. 일반 단일 FK 보정·REF_COLUMN 승인 구조 개선·기존 관계의 명시적 수정/삭제·관계 표현 정책 전반은 pending-work [M-8] 로 옮겼다 ([M-REL-APPROVAL] 과 함께 검토).

### 14.3 D11 — 교착 재현과 실제 원인

시나리오 (격리 PostgreSQL 18.6, 실제 서비스 `saveColumnsBulk`, 별도 스레드·트랜잭션·연결, `RelationSyncDeadlockIntegrationTest.d11CrossPkDeletingBulkSaves`) :

- A = 테이블 TA 의 PK 컬럼 `TA_SN` 삭제 + TB 를 참조 테이블로 적은 새 컬럼 추가. B = TB 의 PK 컬럼 `TB_SN` 삭제 + TA 를 참조하는 새 컬럼 추가.
- A 를 관계 동기화 안(flush 뒤)에서 멈추고 B 를 실행, B 가 잠금 대기에 들어간 것을 `pg_stat_activity` 로 확인한 뒤 A 를 놓는다 (sleep 으로 순서를 정하지 않는다).
- 변경 전 비교 : 이번 작업 시작 시점의 작업 트리(FK 보정 구현 포함, D11 수정 없음)를 격리 사본으로 복사해 같은 테스트를 단언 없이 실행 → **40P01 3/3**. 둘 다 `insert into tb_tbl_rel_col` 에서 기다렸다.

실제 SQL·잠금 순서 (서비스 흐름과 PostgreSQL 로그로 확인) :

1. 테이블 행 `findForUpdate` — JPA PESSIMISTIC_WRITE = `FOR NO KEY UPDATE` (상대 테이블 행과는 겹치지 않는다).
2. `releaseColumns` : 매핑·관계·인덱스·제약조건 검사, REF_COLUMN 관계 삭제.
3. 컬럼 DELETE — 지우는 컬럼이 있고 새 컬럼도 있으면 일괄 저장이 여기서 한 번 flush 한다 (같은 이름 재등록 허용). **DELETE 는 키 강도(FOR UPDATE)** 라 이 행을 참조하는 FK 검사의 `FOR KEY SHARE` 와 충돌한다.
4. 새 컬럼 INSERT → `ColumnNameKey.flush`.
5. `syncReferenceRelations` : flush → 새 컬럼의 참조 테이블 PK(상대가 지우는 중이지만 아직 커밋 전이라 보인다)로 REF_COLUMN 관계를 만든다 → `TB_TBL_REL_COL` INSERT 의 FK 검사가 대상 PK 컬럼 행에 `SELECT 1 FROM ONLY tb_col x WHERE col_sn = $1 FOR KEY SHARE OF x` (PostgreSQL 로그의 `while locking tuple … in relation "tb_col"`).
6. 커밋 직전 `ProjectWriteGuard` 가 프로젝트 행 `FOR SHARE`.

순환 : A 는 `TA_SN` 을 DELETE 로 쥔 채 `TB_SN` 의 KEY SHARE 를 기다리고, B 는 `TB_SN` 을 쥔 채 `TA_SN` 의 KEY SHARE 를 기다린다. 프로젝트 잠금과 무관한 일반 저장끼리의 순환이다 (프로젝트 배타는 쓰지 않았다). 정리하면 교착의 조건은 **'PK 컬럼 행의 DELETE(키 강도)를 쥔 트랜잭션'** 이 둘 있고 서로의 PK 를 참조하는 관계를 동기화가 만드는 것이다 — 관계 동기화가 새로 거는 KEY SHARE 의 대상은 대상 테이블 행과 **대상 PK 컬럼 행뿐**이기 때문이다 (`referencedPk`).

### 14.4 선택한 방식 — 방안 A (PK 컬럼 삭제만 구조 변경 경로로)

**구조 변경 판정** : 삭제 대상 컬럼 중 지금 PK 인 것이 있으면 구조 변경이다 (`ColumnInfoRepository.findPkColumnIds` — ID 만 읽는 스칼라 조회라 영속성 컨텍스트에 옛 상태가 남지 않는다). 요청 DTO 가 아니라 DB 의 저장 상태로 본다.

| 요청 | 분류 | 이유 |
|---|---|---|
| 새 컬럼 등록, 설명·타입 등 속성 수정, 참조 테이블명 변경 | 일반 | 키 강도 잠금이 없다 (UPDATE 는 `TB_COL` 의 PK·`UX_COL_01` 열을 바꾸지 않아 FOR NO KEY UPDATE) |
| PK 여부(`PK_YN`) 변경 | 일반 | 같은 이유 — KEY SHARE 와 함께 잡히므로 순환의 고리가 되지 않는다 (14.12 의 '사후 무효 FK' 참고) |
| PK 가 아닌 컬럼 삭제 | 일반 | DELETE 는 키 강도지만 다른 트랜잭션의 동기화가 그 행에 KEY SHARE 를 걸 일이 없다 (REF_COLUMN 대상은 PK 뿐, 그 밖의 관계 등록·보정·생성은 테이블 행 잠금이나 NOWAIT 를 거친다) |
| **PK 컬럼 삭제** (일괄 저장·단건/여러 건 삭제) | **구조 변경** | 14.3 의 조건 |

**잠금 순서 (구조 변경, `ColumnManageServiceImpl.lockForKeyChange`)** — 테이블 이름 변경·물리명 일괄 적용과 같은 규칙 (`physical/sync/ModelRowLocks` 재사용, 새 잠금 유틸 없음) :

1. 프로젝트 행 배타(`ProjectRepository.findByIdForUpdate` — 실제로는 FOR NO KEY UPDATE, 커밋 직전의 FOR SHARE 와 충돌) + `ProjectWriteGuard.lock` — **첫 행 잠금보다 먼저**.
2. 테이블 행 NOWAIT (`tablesNoWait`).
3. 지울 컬럼 행 `FOR UPDATE NOWAIT` (`columnsForKeyChange` — DELETE 와 같은 강도를 미리 잡는다. 다른 트랜잭션이 그 PK 를 참조하는 관계를 만드는 중(KEY SHARE)이면 기다리지 않고 409).
4. 남는 소속 컬럼 NOWAIT — **읽기 전에** 잠그고 잠근 뒤 읽은 상태로 판정·저장한다.
5. 이 테이블을 참조 테이블명으로 가리키는 컬럼 NOWAIT — 동기화가 그 컬럼의 관계를 지우거나 새로 만든다(그 행에 KEY SHARE).

프로젝트 배타를 잡은 뒤에는 어떤 행 잠금도 기다리지 않는다. 이 뒤 동기화가 거는 KEY SHARE(대상 테이블 행·대상 PK 컬럼 행)를 키 강도로 잡을 수 있는 쓰기는 PK 컬럼 삭제·테이블 이름 변경·스키마 이동·컬럼 이름 변경(물리명 일괄)·원본 삭제 반영뿐이고 모두 프로젝트 배타를 먼저 잡으므로, 프로젝트 배타를 쥔 채 막히는 FK 참조 잠금이 남지 않는다. 빈 테이블만 지우는 테이블 삭제는 PK 가 있는 대상 테이블이 될 수 없다.

**최신 상태 재검증 (14번 지시)** : 판정은 잠그기 전이므로 잠근 뒤 다시 본다. 일반 경로로 판정했는데 잠근 뒤 삭제 대상이 PK 면(그 사이 다른 저장이 PK 로 바꿈) 이미 쥔 테이블 행 잠금을 쥔 채 프로젝트 배타를 뒤늦게 요청하지 않고 409 (`ModelRowLocks.busy()`)로 끝낸다 — 트랜잭션 전체 롤백, 재조회 뒤 다시 하면 구조 변경 경로로 간다. PK 를 바꾸는 쓰기(일괄 저장, PK 컬럼 단건 등록·엑셀, 원본 가져오기)는 모두 테이블 행을 먼저 잡으므로, 테이블 행을 잡은 뒤 읽은 PK 여부가 최신이다. 그래서 일반 단건/여러 건 삭제도 이제 소속 테이블 행을 ID 순으로 먼저 잡고(예전에도 `releaseColumns` 가 같은 행을 잡았다 — 시점만 앞당김) PK 여부를 다시 본다. 구조 변경으로 판정했는데 잠근 뒤 PK 가 아니면 그대로 진행한다 (잠금이 더 강할 뿐 안전하다).

**선택하지 않은 것** :

- 방안 B (지울 PK·참조 대상 행을 전역 순서로 먼저 잠그기) : 동기화가 참조할 대상 PK 는 다른 테이블의 커밋 전 상태에 따라 바뀌어 첫 변경 전에 확정할 수 없다 (A 가 잠그기 전에 B 가 새 참조를 적을 수 있다). 참조 대상을 잠근 뒤 다시 계산하면 또 바뀔 수 있어 재검증 고리가 필요하고, 대상 PK 행을 배타로 잡으면 그 테이블의 일반 저장까지 막는다. 기존 키 변경 경로와 다른 두 번째 잠금 규칙이 생기는 것도 피했다.
- 모든 일괄 저장·모든 삭제를 구조 변경으로 보내기 : PK 가 아닌 삭제는 교착 조건이 아니다 (14.4 표). 일반 저장 동시성 정책에 어긋난다.
- 금지 목록(일반 저장 전체 프로젝트 배타, 전역 Java 잠금, 외부 잠금, 잠금 테이블, 동기화 비동기·별도 트랜잭션, 청크 커밋, 제약 제거, 자동 재시도, 짧은 잠금 시간 제한, 40P01 → 409 변환)은 쓰지 않았다. 40P01 은 지금도 409 로 바꾸지 않는다 — 교착 조건 자체를 없앴다.

**오류 계약** : NOWAIT 실패(PostgreSQL 55P03, H2 50200)만 409 `MODEL_CONFLICT`. 경합이 없으면 기존 업무 오류 그대로 — 승인된 PK 컬럼 삭제는 일괄 저장의 행 오류·단건 삭제의 `APPROVED_DATA_CANNOT_BE_DELETED`, 관계·매핑에 쓰인 PK 는 `RELATION_EXISTS` (`d11BusinessErrorsUnchanged`, H2·PostgreSQL).

**바뀐 계약** : PK 컬럼을 지우는 일괄 저장·삭제는 같은 테이블(또는 그 테이블을 참조 테이블명으로 가리키는 컬럼)을 다른 트랜잭션이 잡고 있으면 기다리지 않고 409 다 (예전 : 기다림). 그동안 같은 프로젝트의 다른 쓰기는 커밋 직전 프로젝트 공유 잠금에서 잠깐 기다린다 (구조 변경 비용 — 이름 변경과 같다).

### 14.8 FK 보정 적용 중 동시 변경 — 결함 수정 1건 (`RelationSyncDeadlockIntegrationTest.correctionVersusConcurrentWrites`, PostgreSQL)

보정이 다시 계획·토큰 비교·직전 버전 저장까지 마치고 FK 를 만들기 직전(`createGeneratedForeignKey`)에서 멈춘 사이 다른 쓰기를 실행했다 :

| 다른 쓰기 | 결과 |
|---|---|
| 같은 FK 를 관계 등록(`saveRelation`)으로 | **변경 전 : 기다림 없이 INSERT, 커밋 직전 프로젝트 공유 잠금에서만 기다린 뒤 성공 → 같은 FK 2개 (TOCTOU 결함)**. 변경 후 : 자식 테이블 행에서 기다렸다가 보정이 만든 FK 를 보고 `SAVED_DATA_EXISTS`, FK 1개 |
| 속성 매핑 해제 | 논리 모델 행에서 기다렸다가 성공 (보정 뒤 순서) |
| 관계 속성 짝 변경 | 논리 모델 행에서 기다림 |
| 자식 테이블 승인 | 테이블 행에서 기다렸다가 성공, 보정 FK 는 미승인 그대로 |
| 부모 PK 컬럼 삭제 (구조 변경) | 프로젝트 행에서 기다린 뒤 `RELATION_EXISTS` (매핑된 컬럼), 컬럼 그대로 |

수정 : `PhysicalModelServiceImpl.saveRelation` 이 원본(자식) 테이블 행을 먼저 잠그고(`lockTable` = 기다리는 FOR NO KEY UPDATE) 같은 구성의 관계를 찾는다. 보정은 그 행을 NOWAIT 로 잡으므로, 관계 등록이 먼저 잡으면 보정이 409, 보정이 먼저면 관계 등록이 기다린 뒤 중복으로 거절한다. 같은 테이블의 관계 등록끼리도 직렬화된다 (예전에는 동시에 같은 관계를 둘 다 만들 수 있었다). 관계 등록은 이제 같은 원본 테이블의 일반 컬럼 저장이 끝날 때까지 기다린다. 프로젝트 배타를 쥔 경로는 그 테이블 행을 NOWAIT 로만 잡으므로 새 교착은 없다.

승인 정책 회귀 (기존 `approvalPersists`·`approvedChildBlocked` + E2E·재시작) : 복합·자기 참조 FK 는 생성 직후·관계 동기화·컬럼 등록·테이블 설명 수정·앱 재시작 뒤에도 미승인, 승인된 부모 참조 허용, 승인된 자식 변경 금지(관리자 포함), 일반 단일 FK 직접 요청 400. 이번 잠금 변경은 승인 시점·상태를 바꾸지 않는다.

### 14.12 남은 제한 · 재현하지 않은 위험

> **후속 (2026-11-24, M8-C4b-R1 — [ongoing/modeling-concurrency-m8.md 18장](../ongoing/modeling-concurrency-m8.md))** : 관계 동기화가 새로 만들거나 대상을 바꾸는 REF_COLUMN 관계의 대상 스키마·테이블·PK 컬럼 행을 PostgreSQL `FOR KEY SHARE` 로 **읽기 전에** 잡고 다시 계산한다 (이 장의 KEY SHARE 를 시점만 당긴 것 — 순환 없음 이유는 14.4 그대로). 그래서 아래 '지우는 중인 PK 를 참조하던 일반 저장은 FK 위반(500)' 은 이제 기다린 뒤 관계 없이 성공한다 (`d11PkDeleteVersusReferencingSave`·`d11SingleDeleteOfPk` 기대값 변경). 스키마 이름 변경도 스키마 행을 키 강도로 미리 NOWAIT 로 잡는다. H2 는 커밋 직전 프로젝트 잠금 뒤 재확인. PK 여부 변경(일반 경로)의 사후 무효 FK 는 같은 날 M8-C4b-R2 에서 해결 — 실제 PK 구성을 바꾸는 저장(PK 여부 변경·새 PK 컬럼 포함)도 이 장의 구조 변경 경로로 보내고 테이블 행을 키 강도로 잡는다 (14.4 표의 'PK 여부 변경 = 일반' 은 더 이상 유효하지 않다 — [modeling-concurrency-m8.md 19장](../ongoing/modeling-concurrency-m8.md)). 아래 원래 기록은 그대로 둔다.

- **정책 보류 (D10)** : 자기 참조가 아닌 단일 FK 보정 — pending-work [M-8].
- **바뀐 계약 (D09·D11)** : 테이블 이름 변경·스키마 이동, PK 컬럼을 지우는 일괄 저장·삭제는 같은 행을 다른 트랜잭션이 잡고 있으면 기다리지 않고 409. 그동안 같은 프로젝트의 다른 쓰기는 커밋 직전에 잠깐 기다린다.
- 재현하지 않은 위험 (코드 분석) :
  - 구조 변경 경로는 다른 테이블의 REF_COLUMN 관계 행을 지울 수 있다. 그 관계 행만 고치는 일반 쓰기는 참조 컬럼 행을 함께 고치므로 NOWAIT 잠금(14.4 의 5)에서 409 가 되지만, 관계 행 자체는 잠그지 않는다 — 테이블 이름 변경 경로와 같은 수준.
  - 구조 변경 경로가 새 컬럼을 넣는 사이 다른 트랜잭션이 그 표준 용어를 지우는 중이면(용어 행 FOR UPDATE) 기다릴 수 있다 — 논리 → 물리 생성에도 있던 같은 종류의 위험.
  - PK 여부를 동시에 바꾸는 두 일괄 저장이 서로를 참조하면 PK 가 아닌 컬럼을 가리키는 REF_COLUMN 관계가 남을 수 있다 (교착이 아닌 사후 무효 FK — DEC-09 진단 대상, 예전과 같음).
  - 지우는 중인 PK 를 참조하던 일반 저장·관계 등록은 FK 위반으로 끝나며 응답은 기존처럼 일반 오류(HTTP 500)다 — 409 나 업무 오류로 바꾸지 않았다.
- H2 는 KEY SHARE 를 구분하지 않아 교착 시나리오 13건은 PostgreSQL 에서만 돈다 (H2 에서는 분류·409 계약·업무 오류·판정 재검증 3건).
- `RequestLogStatusHttpTest` 는 이번 PostgreSQL 전체 실행에서 통과했지만 간헐 실패가 해결됐다고 보지 않는다.
- 미검증 : `Dockerfile-h2`, Chromium 외 브라우저, 운영 규모 데이터, 메모리 사용량.

## 후속 : 보조 식별자 참조 FK 보정 (2026-11-22, M7-AK-03)

부모 보조 식별자를 참조하는 관계는 단일 FK 도 `SINGLE_FK_HELD` 없이 미승인 USER 관계로 보정한다 (부모 UNIQUE 가 순서까지 일치해야 — `PARENT_UNIQUE_MISSING`·`PARENT_UNIQUE_ORDER`). 토큰 형식 `fk-correction/2`. 일반 단일 PK FK 보류(D10)는 그대로 — [alternate-key-unique-m7.md](alternate-key-unique-m7.md). 같은 작업에서 UNIQUE 등록(`saveConstraint`)·제약조건 삭제가 테이블 행을 먼저 잡도록 바뀌었다 (그 문서 6장).
