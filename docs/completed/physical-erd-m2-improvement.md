## 1. 작업 목적

M-6 에서 논리 ERD 에 넣은 부분 조회·찾기·관계선 차선·화면 위치(D-52)·배치 보호를, 물리 모델의 성격(스키마, FK 제약조건, 복합 키, 편집 모드, VIEW 노드)에 맞게 물리 ERD 에 적용할 범위를 정한다. 이미 있는 기능은 다시 만들지 않는다.

## 3. 물리 ERD 현행 구조 (2026-11-20 코드 기준, 직접 확인)

### 3.1 백엔드 — `lexorma-data` `com.lexorma.data.erd`

| 구성 | 실제 내용 |
|---|---|
| `controller/ErdRestController` | `/api/erd`, 클래스 단위 `@PreAuthorize("hasRole('VIEWER')")`. `GET /api/erd`(범위), `GET /api/erd/neighbors/{tableId}?depth`, `GET /api/erd/views?schemaId`(VIEW 노드, M-15 — `PhysicalViewService.erdViews`), `GET/PUT /api/erd/layout` |
| `service/ErdService` | 상수 `MAX_TABLES = 300`, `MAX_DEPTH = 3`, `MAX_LAYOUT_NODES = 5000` |
| `service/impl/ErdServiceImpl` | `selectGraph`(page·size 1~300, 검색어 100자, 스키마 프로젝트 확인, count → 테이블 → 컬럼·관계), `selectNeighbors`(단계별 BFS : 단계마다 관계 쿼리 1번, 300 넘으면 그 단계에서 멈춤, 출발 테이블 프로젝트 확인), `selectLayout`(삭제된 테이블 좌표는 빼고 응답), `saveLayout`(요청 version ≠ 저장 version → 409, 기존 좌표 + 요청 좌표 합침, 없는 테이블 요청 거절, 좌표 ±1e7·zoom 0.02~4·5,000개, `saveAndFlush` 의 `@Version`/UNIQUE 위반도 409) |
| `repository/impl/ErdGraphRepositoryImpl` (QueryDSL 프로젝션 — 엔티티 적재 없음) | `countTables`·`findTables`(정렬 : 기본 스키마 먼저 → 스키마명 → 테이블명 → ID, offset·limit), `findTablesByIds`, `findColumns`(컬럼 + 표준 용어명·표준 도메인명 left join — `ColumnInfo.standardTerms` 는 `@ManyToOne` 이라 행이 늘지 않는다), `findRelations`(관계 컬럼 쌍 단위 행 → 관계 ID 별로 묶음, **범위 테이블이 한쪽이라도 걸린 관계 전부** — 상대가 범위 밖이어도), `findLinkedTableIds`(BFS 한 단계), `findExistingTableIds`. 검색 : 테이블 물리명·논리명(`TBL_KORN_NM`)·스키마명 `containsIgnoreCase` |
| `domain/dto/ErdDto` | `Table(id, schemaId, tableName, tableKorName, tableDescription, isApproval, isMasterTable)`, `Column(… dataType, maxLength, precision, scale, isNullable, isPk, isApproval, domainName)`, `Graph(tables, columns, relations, totalCount, truncated)`, `Layout(version, nodes, viewport)`. 관계는 `PhysicalModelDto.Relation(id, relationName, relationType FK/LOGICAL, relationSource USER/REF_COLUMN/IMPORTED/AI_APPROVED, source·target table, columns(쌍), isApproval, deleteRule, updateRule, updated)` |
| `domain/entity/ErdLayout` | `TB_ERD_LYT` (`ERD_LYT_SN`, `PRJ_SN`, `ACNT_SN`, `NODE_PSTN_CN` JSON, viewport 3컬럼, `VER_NO` `@Version`), `UX_ERD_LYT_01 (PRJ_SN, ACNT_SN)` |

- 프로젝트 격리 : 모든 쿼리가 `accountDto.getProjectId()` 로 거른다. 다른 프로젝트 스키마 → `SCHEMA_IS_NOT_DEFINED`, 테이블 → `TABLE_IS_NOT_DEFINED`. 권한 회수는 `ProjectAccessInterceptor`.
- 요청 로그 제외 : `/api/erd/**` (M-2 1차).
- 편집(M-8 3차)은 ERD 전용 API 가 아니라 기존 물리 모델 API(`PhysicalModelService` 등)를 화면에서 부른다 — ERD 조회 경로와 분리돼 있다.

### 3.2 DB (물리 메타데이터 — 관계 표현에 쓸 수 있는 것)

| 테이블 | 관계선·카디널리티에 쓸 수 있는 값 |
|---|---|
| `TB_TBL_REL` (`TableRelation`) | `REL_TYPE_CD` FK / LOGICAL, `REL_SRC_CD` USER / REF_COLUMN / IMPORTED / AI_APPROVED, `DEL_RULE_CD`·`MDFCN_RULE_CD`(NO ACTION·RESTRICT·CASCADE·SET NULL·SET DEFAULT), `APRV_YN`, `DRVN_COL_SN`(REF_COLUMN 동기화 원 컬럼). **FK 1개 = 행 1개** |
| `TB_TBL_REL_COL` | 쌍(`ORGNL_COL_SN` 자식 컬럼 → `TRGT_COL_SN` 부모 컬럼), `COL_ORD` (UNIQUE `(REL_SN, COL_ORD)`) — 복합 FK 의 컬럼 순서 보존 |
| `TB_COL` (`ColumnInfo`) | `NULL_ALWNC_YN`(NULL 허용, **null 가능**), `PK_YN`, `UNQ_YN`(단일 컬럼 UNIQUE), `IDX_YN` |
| `TB_TBL_CNSTRT` + `_COL` | UNIQUE·CHECK 제약조건, UNIQUE 는 컬럼 목록·순서 |
| `TB_TBL_IDX` + `_COL` | `UNQ_YN`, 부분 인덱스 조건 `CND_CN`, 컬럼 대신 식 `EXPR_CN`, 정렬, 출처 USER/COLUMN |
| **저장하지 않는 것** | FK 의 MATCH SIMPLE/FULL/PARTIAL, DEFERRABLE, 부모 쪽 "최소 1건" 같은 업무 참여 수, DBMS 별 NULL 비교 동작(프로젝트의 `DB_TYPE_CD` 만 있다) |

| 파일 | 실제 내용 |
|---|---|

| `ViewNode.tsx` | VIEW 노드 (M-15, 읽기 전용, 참조선은 FK 아님) |

- 화면 위치 : 조회 키(`graphKey`)가 바뀌면 `flow.fitView({ padding: 0.15, maxZoom: 1 })` — 처음 기본 범위는 저장된 viewport 복원, 깊은 링크·새 테이블은 `setCenter`(배율 1). 같은 키 새로고침은 유지. **D-52 와 같은 방향이지만 `fitView` 는 React Flow 의 측정된 노드만 본다** — `onlyRenderVisibleElements` 로 화면 밖 노드가 측정되지 않으면 일부만 맞춘다 (5장 B-1, 측정으로 확인).

코드에서 찾은 추가 차이

- 화면 안 이동 경고 : 논리·물리 모두 `beforeunload` + 자기 화면의 이동 버튼 확인만 있다. 사이드바 메뉴 이동 경고(React Router `useBlocker`)는 **두 화면 모두 없다** (저장소에 `useBlocker` 사용 없음).
- 이웃 탐색이 `LOGICAL` 관계(DB FK 없이 Lexorma 에 정의한 관계)와 출처 `AI_APPROVED`(사람이 승인한 AI 제안)도 따라간다. 추정만 된 관계(승인 전)는 `TB_TBL_REL` 에 없어 탐색에 들어오지 않는다.

## 6. 조회 및 탐색 설계

### 6.1 부분 조회 — 지금 구조 유지 (권장)

- 이미 D-02 대로 구현돼 있다 (기본 100·최대 300, 서버 페이징, 쿼리 4번). 측정상 컬럼 20개 기준 300 테이블 = 컬럼 6,000행·JSON 약 1.9MB·PostgreSQL 91ms·브라우저 2단계 이웃(300개) 0.33초로, 한도를 바꿀 근거가 없다.
- 컬럼이 많은 테이블(예 100컬럼) 은 응답이 컬럼 수에 비례한다 — 측정하지 않았다 (14.3 계획).

### 6.2 테이블 Finder (신규 후보)

- API 후보 : `GET /api/erd/tables?keyword=&schemaId=&size=` (VIEWER) → `{ items: [{id, schemaId, schemaName, tableName, tableKorName}], totalCount, truncated }`, 이름순, `size` 1~50(기본 20). 검색 조건은 범위 조회의 `searchCondition`(물리명·논리명·스키마명, 대소문자 무시, 100자)을 그대로 쓴다 — 같은 규칙이라 결과가 엇갈리지 않는다.
- 화면 : 논리 ERD `EntityFinder` 와 같은 흐름 — 고르면 지금 범위에 있으면 이동, 없으면 그 테이블 기준 1단계 이웃(깊은 링크와 같은 동작).
- 같은 이름 : 결과에 스키마명을 늘 함께 보여 준다 (스키마별 같은 테이블명 허용).
- 컬럼명 검색 : **기본 Finder 에 넣지 않는 것을 권장** — 컬럼 수가 테이블의 20배 이상이고, 이미 컬럼 관리 화면(서버 검색)이 있다. 필요하면 컬럼 관리 → [ERD 에서 보기] 깊은 링크(M-3) 로 간다.

### 6.3 범위 밖 관계 (B-2)

- 대안 A (현행) : 범위 밖 상대 관계를 객체 전체로 준다 — 상세 패널이 바로 보여 준다. 허브에서 응답이 커지고 상한이 없다.
- 대안 B (권장) : 응답의 `relations` 는 양 끝이 범위 안인 것만, 테이블별 범위 밖 관계 **수** `outsideRelations` 를 더하고, 상세 패널은 선택한 테이블의 관계만 `GET /api/erd/tables/{id}/relations` 로 지연 조회. 논리 ERD(`outsideRelationships`) 와 같은 방식.
- 대안 C : A 를 두고 범위 밖 관계 수에 상한(예 테이블당 50)만 둔다.
- 호환성 : `GET /api/erd` 의 응답 의미가 바뀐다 (B). 저장소 안 호출자는 물리 ERD 화면과 HTTP 테스트(`SmokeTest`·`ViewAuthorizationHttpTest`·`ProjectRecoveryLoginTest`)뿐(버전 비교 ERD 는 `/api/modelVersion/compare/erd`), Swagger 는 local·h2-local 에만 열려 있다 — 외부 호출 여부는 알 수 없다. B 를 고르면 필드를 빼지 않고 "범위 밖 관계는 상세 API 로" 를 문서화하거나 쿼리 파라미터로 옛 동작을 남길지 결정이 필요하다.

### 6.4 FK 이웃 탐색

- 현행 : 방향 무관(정·역), 깊이 1~3, 300 한도, 스키마 무관(프로젝트 전체), 관계 종류·출처 무관, 자기 참조·순환·다중 FK 는 같은 테이블로 한 번만(`LinkedHashSet`), 복합 FK 는 관계 1건이라 한 번.
- 권장 : **현행 유지** (기본 1·최대 3·300·양방향·프로젝트 전체). 스키마 범위에서 시작해도 다른 스키마의 실제 FK 를 따라간다 — 물리 FK 는 스키마를 넘을 수 있고, 빼면 관계가 숨는다. 노드에는 이미 같은 이름이 여러 스키마에 있을 때 스키마명이 붙는다.
- 결정 필요 : `LOGICAL` 관계를 이웃에서 뺄지 (권장 : 포함 유지 — 사용자가 저장한 관계이고 추정이 아니다. 점선으로 구분된다). 승인 전 AI 추정 관계는 저장소에 없으므로 들어오지 않는다.
- BFS 공통화 : 물리(`ErdServiceImpl.selectNeighbors`)와 논리(`LogicalModelService.selectNeighbors`)는 약 20행씩이고 "다음 단계 이웃을 주는 함수" 만 다르다. 공용 순수 함수로 뽑을 수는 있지만 이득이 작고 논리 쪽은 상속 연결을 섞는다 → **추출 비권장**(11장).

## 7. 물리 관계선 설계

### 7.1 선의 단위 (B-3)

| 대안 | 설명 | 장점 | 단점 |
|---|---|---|---|
| A 현행 | 컬럼이 보이면 컬럼 쌍마다 선 | 어떤 컬럼이 어떤 컬럼을 참조하는지 그림에서 바로 보인다 | 복합 FK 가 여러 선, 끝 기호 중복, 선 수 증가(측정 : 300 테이블에 선 342개) |
| B FK 1개 = 선 1개, 테이블 연결점 | 논리 ERD 와 같다 | 기호 한 번, 차선 계산이 단순 | 컬럼 연결을 그림에서 잃는다 |
| **C (권장)** FK 1개 = 선 1개, 첫 컬럼 쌍의 연결점에 (컬럼이 안 보이면 테이블 연결점) | 컬럼 위치를 유지하면서 선 하나 | 끝 기호 한 번, 단일 FK 는 지금과 같은 모양 | 복합 FK 의 나머지 쌍은 그림에 없다 → 선택 시 강조된 쌍 컬럼 표시 + 관계 상세에 쌍 목록 |

- 버전 비교 ERD(`VersionErd`)도 `relationEdges` 를 쓴다 — C 로 바꾸면 비교 ERD 도 같이 바뀐다 (같이 바꾸는 것을 권장, 회귀 확인 필요).

### 7.2 카디널리티 — 저장된 제약조건으로 판단할 수 있는 범위

물리 ERD 는 **DB 제약조건으로 확인되는 것만** 그린다. 부모 쪽 "자식이 꼭 있어야 함" 은 FK 로 보장되지 않으므로 그리지 않는다.

| 끝 | 판단 | 규칙 후보 (모두 FK 1개의 컬럼 **집합** 기준) |
|---|---|---|
| 부모 쪽 최대 | 늘 1 | FK 는 부모의 PK·UNIQUE 를 참조한다 (참조 대상이 키가 아니면 이미 무효 FK 진단 대상 — DEC-09) |
| 부모 쪽 최소 (자식이 부모를 꼭 가지는가) | 확인 가능 | FK 컬럼이 **모두 NOT NULL** → 1 (필수). 하나라도 NULL 허용 → 0 (선택). `NULL_ALWNC_YN` 이 null(미입력)인 컬럼이 있으면 **판단 불가** |
| 자식 쪽 최대 (부모 하나에 자식 몇 행) | 확인 가능 | FK 컬럼 집합이 자식 테이블의 PK 컬럼 집합과 같거나, UNIQUE 제약조건·조건 없는 UNIQUE 인덱스(식 없음)·단일 컬럼 `UNQ_YN` 의 컬럼 집합과 같으면 1, 아니면 N |
| 자식 쪽 최소 | 확인 불가 | 늘 0 으로 그리거나(선택) 기호를 비운다 — 결정 필요 |
| 식별 관계 | 확인 가능 | FK 컬럼이 모두 자식 PK 에 들어 있으면 식별, 아니면 비식별 |

예외·판단 불가 (구현 시 규칙 확정 필요)

- 복합 FK 일부만 NULL 허용 : 대부분 DBMS 의 기본 MATCH SIMPLE 에서는 하나라도 NULL 이면 검사하지 않으므로 "선택(0)" 으로 본다. MATCH FULL 은 저장하지 않으므로 가정하지 않는다 → 규칙은 "하나라도 NULL 허용이면 0" (MATCH FULL 이어도 0..1 이라 틀리지 않는다).
- UNIQUE 의 순서 차이 : 집합으로 비교 (UNIQUE (b, a) 도 FK (a, b) 의 유일성을 보장한다).
- FK 보다 많은 컬럼의 UNIQUE : 유일성을 보장하지 않는다 → N. FK 일부 컬럼만 UNIQUE : 부분 집합이 UNIQUE 면 전체도 유일 → 1 (규칙에 넣을지 결정).
- 조건부(부분) UNIQUE 인덱스·식 인덱스 : 보장 범위가 일부라 **N 으로 본다**.
- UNIQUE 컬럼의 NULL : PostgreSQL·MySQL·Oracle(단일) 은 NULL 여러 개를 허용 — 자식 최대 판단(부모 하나당)에는 영향 없음.
- `LOGICAL` 관계(DB FK 아님) : 같은 규칙을 적용할지, 기호 없이 점선만 그릴지 결정 필요 (권장 : 기호 없이 — DB 제약이 없다).

표시 후보 : 논리 ERD 의 Crow's Foot 기호(`EndMarkers`)를 재사용하되, 물리는 "판단 불가" 를 별도 표시(기호 없음 + 상세에 사유). 실선/점선의 뜻이 논리(식별/비식별)와 물리(FK/LOGICAL)에서 다르므로, **물리에서 식별 관계를 선 모양으로 바꾸지 않고**(점선은 LOGICAL 로 유지) 상세·툴팁에 "식별" 을 표시하는 것을 권장.

### 7.3 자기 참조·평행 관계선

- `relationLanes.ts` 를 그대로 쓴다 (관계 ID 순 차선 — 물리 관계 ID 도 `Long`, 같은 순수 함수). 논리의 커스텀 edge(끝점 이동·꺾임·고리) 렌더링은 `logical/erdNodes.tsx` 안에 논리 타입과 섞여 있으므로, 물리용 edge 컴포넌트를 따로 두고 차선 계산·기호(marker)만 공유하는 것을 권장 (11장).
- 선 선택 영역·선택 시 z-order·안정 정렬(ID 순)은 논리와 같은 규칙. 라벨(FK 이름)은 지금처럼 버전 비교에서만.
- 고급 경로 탐색(edge routing)은 [M-8-LAYOUT] — 이번 범위 아님.

## 8. 스키마 조회 설계

- 현행 : 단일 스키마 또는 전체, 기본 스키마 먼저 정렬, 같은 이름은 스키마명 접두어, 스키마를 넘는 FK 는 양 끝이 범위 안이면 선, 아니면 상세 패널.
- 복수 스키마 선택 : 화면·API(`schemaIds`) 모두 바뀌고 이득은 "스키마 두세 개만" 보는 경우뿐 — 검색어·이웃 탐색으로 대부분 대신된다. **비권장(후속 후보)**.
- 범위 밖 관계 수(6.3 B)를 스키마 범위에도 같이 보여 주면 "다른 스키마와 연결됨" 이 드러난다.
- 물리 주제 영역은 만들지 않는다 (지시 범위 밖, 논리 주제 영역을 복제하지 않음).

## 10. 화면 설계

### 10.1 Viewport (D-52 재사용, B-1)

- 범위 키 = 조회 URL (이미 있음). 바뀌면 **알고 있는 좌표·크기(`NODE_WIDTH`, `nodeHeight(min(컬럼 수, 20))`)로 경계를 계산해** `getViewportForBounds` → `setViewport`(`motionMs(200)`, 줄인 모션 0). 같은 키 새로고침·드래그·확대·편집·테마·언어·배치 저장은 유지. 이웃 탐색은 기준 테이블 선택 + 결과 전체, 깊은 링크·새 테이블은 지금처럼 가운데(배율 1). VIEW 노드는 테이블 배치 뒤 오른쪽에 놓이므로 경계 계산에 포함할지 결정 (권장 : 포함).
- 처음 기본 범위의 저장된 viewport 복원(D-15)은 유지.
- 좌표는 바꾸지 않는다 (화면 위치만).

### 10.2 테이블 노드

- 현행 표시 : 물리명, 논리명(한글명)·승인 상태, 컬럼(최대 20 : PK·FK 표시·물리명·데이터 타입(길이·정밀도)·NOT NULL), 무효 FK 배지, 버전 비교 차이 표시. 축소 시 컬럼 생략.
- 측정 : 300 테이블 × 20 컬럼에서 DOM 10,208·힙 20.4MB, 표시 0.33초 — 표시 모드를 새로 둘 근거가 아직 없다. **신규 모드 비권장**, D-02 의 20컬럼·140px 기준값 유지를 권장 (컬럼이 많은 테이블 실측 뒤 재검토 — 14.3).
- 표시하지 않는 것 유지 : UNIQUE·인덱스·표준화 정보는 상세 패널.

### 10.3 상세·화면 연계

- 이미 있음 : DDL 보기, 테이블 상세(승인·수정), 인덱스·제약조건, 컬럼 편집, 컬럼 상세 → 데이터 사전, 관계 상세(승인·삭제·규칙), 테이블 관리·컬럼 관리 ↔ ERD 깊은 링크, VIEW 관리 이동.
- 활용성이 높은 추가 후보 : 테이블 상세 → **논리·물리 매핑 화면**(매핑된 엔터티로) 이동 — 지금은 없다. 관계 상세의 복합 FK 쌍 강조(7.1 C 와 함께).
- 조회 중심 유지 : 편집 기능 확장(관계 수정 API 등)은 [M-8] 그대로.

## 12. 권한·동시성

- 권한 (현행 그대로 권장) : 조회·Finder·이웃·자기 배치 저장 VIEWER (클래스 단위 `@PreAuthorize`), 편집은 기존 물리 모델 API 의 역할(M-8). 공용 배치는 없다. 신규 Finder·관계 상세 API 는 `/api/erd` 아래 → 같은 VIEWER.
- 프로젝트 격리 : 신규 API 도 `accountDto.getProjectId()` 로만, 다른 프로젝트 ID 는 `TABLE_IS_NOT_DEFINED`.
- 동시성 : 배치는 사용자별이라 다른 사용자와 경쟁이 없고, 같은 사용자 여러 탭은 `@Version` 409 (테스트됨). 테이블 삭제 중 저장 → 없는 테이블 좌표 요청은 거절, 저장된 좌표는 조회 때 걸러짐(이미 구현). 조회는 읽기 전용 트랜잭션이라 편집과 경쟁하지 않는다. **새 잠금·수정 일시·revision 은 필요 없다** — 논리 모델 잠금을 복사하지 않는다.

## 13. DB 및 마이그레이션 영향

- 권장안(6.2 Finder, 6.3 B, 7.x 관계선, 10.1 Viewport, 9 정책 1) 은 **DB 변경 없음**. 카디널리티 판단은 기존 컬럼·제약조건·인덱스 값으로 계산한다 (저장하지 않는다).
- 정책 2·3 (스키마별 배치) 을 고르면 V4 : 새 테이블(스키마 × 사용자 배치, PK·FK(스키마·계정·프로젝트)·UNIQUE(스키마, 계정)·인덱스), 기존 `TB_ERD_LYT` 그대로, 스키마·프로젝트 삭제 정리, H2·PostgreSQL 같은 내용, 예제 메타데이터(사전 단어·용어·테이블·논리 엔터티·인덱스) 동기화(`V0SeedMigrationTest`). 단어는 기존(스키마·ERD·레이아웃) 조합 — 실제 명명은 그때 `static/excel/dataPortal.xlsx` 와 기관 표준단어를 대조해 확정한다.

## 14. 이력·버전·교환 영향

- 배치는 모델 정의가 아니다 : `TB_ERD_LYT` 는 변경 이력·모델 버전 스냅샷에 들어가지 않는다 (`ModelChangeRecorder` 대상 아님). 교환 형식 2+ 는 내보낸 사용자의 저장 배치를 `layouts.physical` 로 담는다 — 권장안은 이 형식을 바꾸지 않는다 (형식 5·스냅샷 8 그대로). 정책 2·3 을 고르면 교환에 스키마별 배치를 넣을지 따로 결정(형식 증가 필요).
- 카디널리티·Finder·Viewport 는 조회 표현이라 이력·버전·교환·매핑·물리 생성에 영향 없음.

## 22. 1차 설계 대비 바뀐 것

- 범위 밖 관계(1차 권장 B = 응답 의미 변경) → **D-15 로 예전 응답 유지**, 화면만 새 계약(`relationScope=INNER`)을 쓴다. 1차 17장 결정 15 의 "의미 변경 + 문서화" 는 채택하지 않았다.
- 범위 밖 관계 목록은 테이블의 관계 전체를 관계 ID 순 페이지로 준다 (범위 안·밖을 서버가 나누지 않는다 — 범위는 서버가 모른다). 화면이 범위 밖 줄에 표시한다.
- 카디널리티 규칙(1차 7.2)을 확정 지시대로 바꿨다 : 복합 FK 의 NULL 허용 혼합은 "0" 이 아니라 **판단 불가**(MATCH 미저장), NULL 허용 미입력도 판단 불가, 자식 최대는 "U ⊆ F" (FK 일부 컬럼 UNIQUE 도 1), 무효 FK·LOGICAL 은 모두 판단 불가.
- 이웃 탐색·범위 조회 응답에 `fkColumnIds` 를 더했다 — 범위 밖 관계를 받지 않으면 상대가 범위 밖인 FK 컬럼의 FK 표시가 사라지기 때문 (1차에서 빠뜨린 점).
- 최초 화면 병목(B-6)은 ERD 쪽이 아니었다 (27장) — ERD 코드에서 고칠 것이 없었다.

## 23. 카디널리티 판단 공식 (`erd/service/PhysicalCardinality`, 순수 함수 — 조회 때 계산, 저장하지 않음)

자식 = 관계의 source(참조하는 테이블), 부모 = target. F = FK 컬럼 집합(자식), R = 참조 컬럼 집합(부모). 순서는 보지 않는다.

| 끝 | 규칙 |
|---|---|
| 부모 최대 | R 이 부모의 키 — PK 컬럼 집합과 같음 · 단일 컬럼이 `UNQ_YN` · UNIQUE 제약 또는 고유 인덱스(조건 없음, 키가 모두 컬럼, INCLUDE 제외)와 같음 — 이면 1. DDL 이 FK 를 만드는 조건(`TableDdlGenerator.referencesKey`, 모델 구조 진단의 무효 FK)과 같다. 키가 아니면 **모든 끝 판단 불가** (`INVALID_REFERENCE`) |
| 부모 최소 | F 의 컬럼이 모두 NOT NULL → 1, 모두 NULL 허용 → 0. NOT NULL 은 DDL 과 같은 판단(`isNotNull` : PK · 필수 · NULL 불허). 섞이면 판단 불가 (`NULLABLE_MIXED` — MATCH SIMPLE/FULL 을 저장하지 않는다), NULL 허용이 비어 있고 PK·필수도 아니면 판단 불가 (`NULLABLE_UNKNOWN`) |
| 자식 최대 | 자식의 유일성 키 U(PK · 단일 UNIQUE 컬럼 · UNIQUE 제약 · 위 조건의 고유 인덱스) 중 U ⊆ F 인 것이 있으면 1, 없으면 N (기록된 제약이 여러 건을 막지 않는다는 뜻) |
| 자식 최소 | 늘 판단하지 않는다 — FK 는 부모에 자식이 있음을 보장하지 않는다 (상세에 "확인할 수 없음") |
| 식별 | F ⊆ 자식 PK → IDENTIFYING, 일부만 → PARTIAL, 아니면(PK 없음 포함) NON_IDENTIFYING |
| LOGICAL 관계·컬럼 쌍 없음 | 모두 판단 불가 (`LOGICAL_RELATION`, `COLUMNS_MISSING`) |

- `PK_YN`·`UNQ_YN` 이 비어 있으면 아닌 것으로 본다 (DDL·진단과 같다). 조건부·표현식 고유 인덱스와 일반 인덱스는 근거가 아니다.
- 끝 기호 (`erd/endMarkers.tsx` 공용 정의, `physical-end-*`) : 부모 쪽 = 최소·최대(최소를 모르면 최대 `|` 만), 자식 쪽 = 최대만(`|` 또는 까치발). 판단하지 못한 끝은 기호 없음 — 0·N 으로 바꾸지 않는다.
- 버전 비교 ERD 는 카디널리티를 받지 않는다 (과거 스냅샷을 지금 제약조건으로 판단하지 않음 — 스냅샷 형식은 그대로).

## 24. API (신규·변경)와 호환

| API | 내용 |
|---|---|
| `GET /api/erd` · `GET /api/erd/neighbors/{id}` | `relationScope` 추가 (`ALL` 기본 · `INNER`, 잘못된 값 400). **ALL = 예전 응답 그대로** (범위 밖 상대 관계까지, 쿼리 4번, 새 필드는 `outsideRelations`·`fkColumnIds` null, `cardinalities` 빈 맵). INNER = 양 끝이 범위 안인 관계 + `outsideRelations`(테이블 ID → FK 수) + `fkColumnIds` + `cardinalities`. 탐색 결과(테이블·잘림)는 두 값이 같다 |
| `GET /api/erd/tables?keyword&schemaId&size` (신규) | 찾기 : 범위 조회와 같은 조건·정렬(기본 스키마 → 스키마명 → 테이블명 → ID), size 1~50(기본 20, 밖이면 400 `INVALID_ERD_REQUEST`), `{items:[id, schemaId, schemaName, tableName, tableKorName], totalCount}` |
| `GET /api/erd/tables/{id}/relations?page&size` (신규) | 테이블 하나의 관계 (관계 ID 순 페이지, size 1~100 — 밖이면 400 `INVALID_PAGE_REQUEST`, 목록 정책과 같음) : 관계(컬럼 쌍 전부)·카디널리티·관계에 나온 테이블. 다른 프로젝트 테이블 `TABLE_IS_NOT_DEFINED` |
| `ErdDto.Column` | `isUnique`·`isRequired` 를 뒤에 추가 (필드 추가만) |

- 권한 : 클래스 단위 VIEWER 그대로 (새 API 도). 프로젝트 격리는 모든 쿼리의 `projectId`.
- 범위 밖 관계 수는 DB 집계 : 관계 끝 수(원본 쪽·대상 쪽 `GROUP BY`, 인덱스) − 양 끝이 범위 안인 관계의 끝 수. 범위 밖 관계를 적재하지 않는다. `NOT IN (300개)` 와 `원본 IN … AND 대상 IN …` 은 H2 가 행마다 목록 전체를 비교해 범위 300 에서 약 180ms 였다 → 원본 인덱스로 ID·대상만 받아 걸러낸 뒤 그 관계만 쌍까지 읽도록 나눴다 (H2 179 → 31ms, 29장).

## 25. 화면 — 찾기·관계선·화면 맞춤·이동 경고

- 찾기 : 상세 패널 위, 300ms 멈춘 뒤 검색어마다 캐시(늦은 응답이 덮지 않음), 결과는 `스키마.테이블`. 범위 안이면 그 노드로, 밖이면 그 테이블을 고른 채 1단계 이웃 범위로 (깊은 링크와 같은 흐름). 조회 조건의 스키마를 고른 동안은 그 스키마에서만 찾고 "찾기 범위" 로 표시.
- 범위 밖 관계 : 테이블 상세에 "조회 범위 밖 테이블과의 관계 N개 [목록 보기]" → 20개씩 페이지, 관계를 누르면 관계 상세(카디널리티 포함), 상대 테이블은 [그 테이블 기준 이웃 보기]. 편집으로 관계가 바뀌면 목록 캐시를 버린다.
- 관계선 (`FkEdge`) : FK 하나 = 선 하나, 대표 연결점 = 첫 컬럼 쌍(안 보이면 테이블 연결점), 관계 ID 순 차선(`relationLanes`)으로 끝점·꺾이는 위치·폭을 달리하고 자기 참조는 바깥 고리, 고르는 영역 ±6px, 강조 선은 위에. 툴팁 = 이름·방향·복합 쌍 수·카디널리티·식별·판단 불가 사유. 관계 상세에 "카디널리티 (물리 제약조건 기준)" 와 컬럼 쌍 전부.
- 화면 맞춤 (D-18) : 범위(검색·페이지·스키마·이웃·찾기)가 바뀌면 알고 있는 좌표·크기로 경계를 계산해 맞춘다 (`fitToBoxes`, 동작 줄이기면 즉시). VIEW 노드가 나중에 놓이면 그 범위에서 한 번 더. [전체 보기]·자동 배치 뒤도 같은 계산. 같은 범위 새로고침·편집·드래그·확대는 유지, 처음 기본 범위는 저장된 viewport 복원, 깊은 링크·새 테이블은 가운데(배율 1). 좌표·배치 저장은 바뀌지 않는다.
- **발견·수정한 결함** : 축소 상태로 처음 그린 노드를 확대하면 컬럼 연결점이 새로 생기지만 노드 크기가 같아 React Flow 가 연결점을 다시 재지 않아, 컬럼 연결점에 붙는 관계선이 그려지지 않았다 (새 화면 맞춤이 애니메이션으로 옮기면서 드러남). `TableNode` 가 연결점 구성이 바뀔 때 `updateNodeInternals` 를 부른다 — 버전 비교 ERD 도 같은 노드라 함께 고쳐진다.
- 이동 경고 (D-19, 사용자 확정 : 데이터 라우터) : `App.tsx` 를 `createBrowserRouter`+`createRoutesFromElements`(모듈에서 한 번 생성, Provider 는 레이아웃 경로 `Root`, loader·action 없음)로 바꿨다 — 경로·주소·가드·깊은 링크는 그대로. `useUnsavedChangesGuard(dirty, message)` : `useBlocker`(경로·쿼리가 바뀌는 이동만) → 공통 확인 대화상자 한 번(취소 = 그대로, 변경 유지), `beforeunload`, 로그아웃은 `Header` 가 `hasUnsavedChanges()` 로 먼저 묻는다(프로젝트 변경은 로그아웃 → 다시 로그인뿐이라 같은 경로), 세션 만료·권한 회수(401 처리)는 `navigateWithoutGuard` 로 막지 않는다. 화면 안 이동 버튼·논리 모델 바꾸기는 `confirmLeave` 로 한 번만 묻는다. 적용 : 물리·논리 ERD. 자동 저장·재시도 없음, 저장 실패·409 면 미저장 상태 유지.
