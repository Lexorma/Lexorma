- 등록·수정 정보는 모두 `BaseEntity`(`REG_DT`·`MDFCN_DT`·`RGTR_ID`·`MDFR_ID`, `AuditingEntityListener` 전역 등록).

- 쓰기 직렬화 : 모든 논리 쓰기는 먼저 **논리 모델 행을 잠근다**(`lockModel` = `findForUpdate`) — 이름 중복 검사·낙관적 충돌 검사도 그 뒤.
- 승인 : 승인된 엔터티·관계는 수정·삭제 거절(`APPROVED_DATA_CANNOT_BE_UPDATE/DELETED`), 속성·식별자도 엔터티가 승인이면 거절. 승인은 `requireApprover`(ADMIN·MANAGER·프로젝트 관리자).
- 이력·버전 : `ModelChangeRecorder.TRACKED` 에 `LogicalModel`·`LogicalEntity`(`model`, `entityName`, `entityDescription`, 승인)·속성·식별자·관계(+ 자식 `attributes`)·매핑이 있다. 모델 버전·버전 비교·논리 ERD 비교·**모델 내보내기(DEC-22)** 는 모두 `currentState` 의 같은 필드 목록에서 만든다. 모델 엔터티에 영속 속성을 더하면 `ModelSnapshotFieldCoverageTest` 가 필드 목록 추가를 강제한다.
- 모델 교환 : `ModelExchangeDto.FORMAT_VERSION = 3`, 지원 1·2·3. 형식에 쓰는 객체 종류는 `ModelExchangeService.TYPES` 고정 목록. 논리 배치는 `layouts.logical` (모델별 좌표).
- 예제 데이터 : Lexorma 자기 스키마를 예제(프로젝트 0)로 담는다 — 새 `TB_` 테이블은 COMMENT·데이터 사전 단어/용어·`TB_TBL`/`TB_COL`·예제 논리 엔터티·예제 인덱스를 같은 마이그레이션에 넣어야 `V0SeedMigrationTest`·`SmokeTest`(표준화 품질 0건)가 통과한다.

## 2. 업무 정의

주제 영역 = **한 논리 모델 안에서** 엔터티를 업무 영역별로 묶는 관리용 분류. 모델 경계·관계 의미·물리 스키마와 무관하다. 엔터티 레코드를 복제하지 않는다.

| 구분 | 역할 |
|---|---|
| 프로젝트 | 데이터·권한 격리 |
| 논리 모델 | 업무 데이터 구조 정의 (엔터티·관계의 경계) |
| 주제 영역 | 모델 안 엔터티 분류 (조회·탐색 단위) |
| 물리 스키마 | 실제 DB 객체 네임스페이스 — 주제 영역과 자동 연결하지 않음 |
| ERD 조회 범위 | 화면에 그릴 엔터티 집합 — 주제 영역은 범위를 고르는 조건 하나가 된다 |

## 3. 소속 범위 (D-01)

| | A. 논리 모델별 (권장) | B. 프로젝트 공통 |
|---|---|---|
| 기존 구조 일치 | 엔터티·관계·배치·이름 중복이 모두 모델 단위(`UX_LGCL_ENTT_01`, `UX_LGCL_ERD_LYT_01`) | 모델을 넘는 참조가 새로 생김 |
| 격리 | 모델 잠금 하나로 직렬화 (`lockModel`) | 프로젝트 잠금 + 여러 모델 영향 |
| 교환·복사 | 모델 단위 내보내기·복사와 그대로 맞음 | 모델 하나만 복사할 때 공통 분류를 어떻게 할지 별도 정책 |
| 확장 | 물리 쪽 활용은 매핑 경유(§16 B)로 가능 | 물리 공유에 유리하나 지금 요구 없음 |

권장 A — 근거 : 논리 쓰기 경로 전부가 모델 행 잠금을 기준으로 정합성을 보장하고, 교환(DEC-22)·삭제(모델 단위)·ERD 배치가 모델 단위다.

## 4. 계층 구조 (D-02)

- 비교 : 단일 계층은 순환·이동·하위 포함 조회가 필요 없다. 계층형은 대·중·소분류를 지원하지만 이동·순환·삭제 정책이 생긴다.
- 계층형을 택한다면 **인접 리스트**(`상위 주제 영역 일련번호` 한 칸)로 충분하다 — 근거 : 모델당 주제 영역은 수백 개 규모(§19, 확장 검토 500)라 모델의 영역 전체(id·상위 id·이름·순서)를 한 쿼리로 읽어 메모리에서 트리·경로·하위 집합을 계산하면 된다. Closure Table·Materialized Path 는 이동 시 다건 갱신·추가 테이블이 생기고, 재귀 CTE 는 H2·PostgreSQL 모두 되지만 위 방식이면 필요 없다.
- 순환 방지 : 이동 요청을 모델 잠금 뒤 메모리 트리로 검사 (자기 자신·자기 하위로 이동 거절). DB 로는 자기 참조(`상위 ≠ 자신`) CHECK 만 가능.
- **사용자 결정 필요** : ① 계층형 여부 ② 최대 깊이 (제안 3 — 대·중·소) ③ 상위 영역에 엔터티 직접 소속 허용 여부 (제안 : 허용 — 금지하면 하위가 생기는 순간 기존 소속을 옮겨야 한다) ④ 이름 중복 범위 (제안 : 모델 안 전체에서 대소문자 무시 유일 — 같은 부모 안만 막으면 필터·경로 표시에서 구분이 어렵다).

## 5. 엔터티 소속 방식 (D-03)

| | A. 단일 소속 (권장) | B. 다중 소속 | C. 대표 + 참조 |
|---|---|---|---|
| 집계 | 영역 합 = 분류된 엔터티 수 (중복 없음) | 합계 중복, "고유 엔터티 수" 별도 | 대표 기준 집계 + 참조 별도 |
| 필터 의미 | 명확 | 같은 엔터티가 여러 영역 결과에 | 두 의미 구분 필요 |
| ERD | 영역별 범위 = 소속 엔터티 | 같은 엔터티가 여러 영역 범위에 (배치는 모델 공유라 좌표 충돌 없음) | B 와 같음 + 표시 구분 |
| 교환·이력 | 소속 1행 | n행 | 행 + 유형 |
| 전환 비용 | 소속 테이블의 엔터티 유일 인덱스만 빼면 B 로 넓힐 수 있음 | — | — |

권장 A, 단 **엔터티 테이블의 칸이 아니라 별도 소속 테이블**로 둔다 (§9.2) — 엔터티 승인·수정 일시와 분류를 분리하고 나중에 B 로 넓힐 여지를 남긴다.

## 6. 미분류 (D-04)

권장 A (미분류 허용) : 기존 엔터티는 소속 행이 없을 뿐 그대로이고, 엔터티 등록에 주제 영역을 강제하지 않는다. 화면의 "미분류" 는 저장된 영역이 아닌 **가상 필터**(`소속 행 없음`). 기본 영역 자동 생성·기존 엔터티 자동 배치는 하지 않는다 (마이그레이션은 테이블만 만든다).

## 7. 승인 정책 (D-05)

- 실제 구현 근거 : `saveEntity` 는 승인된 엔터티 수정을 거절하고, 엔터티 수정은 `ModelBase` 로 `MDFCN_DT` 를 비교한다. 주제 영역을 `TB_LGCL_ENTT` 의 칸으로 넣으면 ① 승인된 엔터티는 분류를 바꿀 수 없거나(승인취소 → 분류 → 재승인), ② 분류 전용 API 가 승인 검사를 건너뛰어 "승인된 엔터티 수정 우회" 가 된다. 또 분류만 바꿔도 엔터티 `MDFCN_DT` 가 움직여, 그 엔터티 수정 폼을 연 사용자가 409 를 받는다.
- 권장 A (관리용 분류) : 주제 영역 자체 승인 없음. 소속은 별도 테이블이라 엔터티 행·승인·`MDFCN_DT` 를 건드리지 않으므로 **승인된 엔터티도 분류할 수 있고 우회도 아니다**. 권한은 기존 `logical-model-edit`(USER). 변경은 모델 변경 이력에 남긴다(§17).
- **사용자 결정 필요** : 승인된 엔터티의 분류 변경 허용 여부 (권장 : 허용 — 엔터티 정의가 아니므로). 불허면 소속 저장에서 엔터티 승인을 검사한다 (방안 B).

## 8. 삭제·이동 (D-06)

- 빈 영역(소속 엔터티·하위 영역 0) : 삭제.
- 권장 : 소속 엔터티 또는 하위 영역이 있으면 **거절**(기존 `RELATION_EXISTS` 형식, "주제 영역 {0} 에 엔터티가 {1}개 있습니다"). 비우기는 사용자가 명시적으로 (일괄 해제·이동 기능 §12.5).
- 함께 바뀌지 않는 것 : 엔터티·속성·식별자·관계·매핑·물리 테이블·ERD 배치.
- 연동 삭제 (데이터 보호와 충돌하지 않는 것만) : 엔터티를 삭제하면 그 **소속 행**은 함께 지운다 (엔터티 없는 소속은 의미가 없다 — 지금 속성·식별자를 함께 지우는 것과 같다). 모델 삭제는 지금처럼 엔터티 0일 때만 되며, 그때 주제 영역은 함께 지운다 (**사용자 결정 필요** : 영역이 남아 있으면 모델 삭제를 거절할지). 프로젝트 영구 삭제는 `ProjectDataCleanup` 목록에 추가.
- 이동 : 영역의 상위 변경(순환·깊이 검사), 엔터티 소속 변경. 자동 이동·연쇄 삭제는 하지 않는다.

## 9. 데이터 모델 후보 (**사용자 결정 필요** — 명칭 포함)

### 9.1 명칭

데이터 사전 예제(프로젝트 0)에 `주제`·`영역`·`상위` 단어가 **없다** (`분류` CLSF, `정렬` SORT, `순서` ORD 는 있음). [db-naming-standard.md](../reference/db-naming-standard.md) 규칙상 공공데이터 공통표준단어의 약어를 쓰고, 없으면 기관 표준단어로 정한다. 저장소 안에서 공통표준 약어를 확인할 수 없어 아래는 **후보**다 — 구현 전 공통표준단어 목록에서 확인하고 예제 사전에 단어로 등록한다.

| 단어 | 약어 후보 (확인 필요) |
|---|---|
| 주제 | `SBJ` 또는 `SBJT` |
| 영역 | `AREA` |
| 상위 | `UP` |

| 대상 | 후보 (주제=SBJ 가정) |
|---|---|
| 주제 영역 테이블 | `TB_SBJ_AREA` 또는 논리 접두를 붙인 `TB_LGCL_SBJ_AREA` (권장 : 다른 논리 테이블과 같이 `TB_LGCL_`) |
| 일련번호·시퀀스 | `SBJ_AREA_SN`, `SQ_LGCL_SBJ_AREA` |
| 상위 | `UP_SBJ_AREA_SN` |
| 이름·설명·순서 | `SBJ_AREA_NM`, `SBJ_AREA_EXPLN`, `SORT_ORD` |
| 소속 테이블 | `TB_LGCL_SBJ_AREA_ENTT` (`SBJ_AREA_ENTT_SN`, `SBJ_AREA_SN`, `LGCL_ENTT_SN`) |
| 제약 | `PK_…`, `FK_…_01..`, `UX_…_01..`, `IX_…_01..`, `CK_…_01` (기존 규칙) |

### 9.2 테이블 (권장안 : 모델별 · 인접 리스트 · 단일 소속 별도 테이블)

`TB_LGCL_SBJ_AREA` : `SBJ_AREA_SN` PK · `PRJ_SN` not null · `LGCL_MDL_SN` not null FK → `TB_LGCL_MDL` · `UP_SBJ_AREA_SN` null FK → 자신 · `SBJ_AREA_NM` varchar(255) not null · `SBJ_AREA_EXPLN` varchar(1000) · `SORT_ORD` integer · `REG_DT`·`MDFCN_DT`·`RGTR_ID`·`MDFR_ID`. CHECK `UP_SBJ_AREA_SN <> SBJ_AREA_SN`.

`TB_LGCL_SBJ_AREA_ENTT` : `SBJ_AREA_ENTT_SN` PK · `SBJ_AREA_SN` not null FK · `LGCL_ENTT_SN` not null FK → `TB_LGCL_ENTT` · 등록·수정 4칸.

- 엔터티에 칸 추가안(`TB_LGCL_ENTT.SBJ_AREA_SN`)과 비교 : 쿼리는 조인 하나가 줄지만 §7 의 승인·`MDFCN_DT` 문제, 다중 소속 확장 불가, 엔터티 이력 필드 추가(교환 형식 영향)가 생긴다 → 별도 테이블 권장.
- `PRJ_SN` 을 소속 테이블에도 둘지 : 기존 `TB_ENTT_TBL_MPNG` 는 두고 `TB_LGCL_REL_ATRB` 는 두지 않는다. `ProjectWriteGuard`(커밋 시 프로젝트 공유 잠금)는 엔터티의 `projectId` 로 동작하므로 **검토 중** — 프로젝트 정리 SQL 이 단순해지는 쪽(둔다)을 제안.

### 9.3 정합성 — DB vs 서비스

| 조건 | 보장 위치 |
|---|---|
| 영역·부모·엔터티의 같은 프로젝트·같은 모델 | 서비스 (모델 잠금 뒤 `projectId`·`modelId` 로 읽기). DB 로 하려면 복합 FK + 엔터티 `(LGCL_MDL_SN, LGCL_ENTT_SN)` 유일 인덱스 추가가 필요 — 과하다 (**검토 중**) |
| 자기 자신을 부모로 | DB CHECK + 서비스 |
| 순환·최대 깊이 | 서비스 (모델 잠금 뒤 메모리 트리) |
| 이름 중복 | DB `UX (LGCL_MDL_SN, SBJ_AREA_NM)`(정확히 같은 이름) + 서비스 대소문자 무시 검사 — 엔터티와 같은 방식 (H2 에 식 인덱스 없음, DICT-2 와 같은 이유) |
| 엔터티 단일 소속 | DB `UX (LGCL_ENTT_SN)` |
| 삭제 보호 | FK(소속·하위가 있으면 DB 도 거절) + 서비스 사전 검사(문구) |

### 9.4 인덱스 (예상 쿼리 근거)

- `UX_…_01 (LGCL_MDL_SN, SBJ_AREA_NM)` — 모델별 영역 조회·이름 중복 (모델로 시작하므로 모델별 목록도 이 인덱스로).
- `IX_…_01 (UP_SBJ_AREA_SN)` — FK 삭제 검사 (트리는 메모리라 조회용은 아님).
- 소속 `UX_…_01 (LGCL_ENTT_SN)` — 단일 소속·엔터티별 영역·미분류(`not exists`).
- 소속 `IX_…_01 (SBJ_AREA_SN)` — 영역별 엔터티·영역별 수 집계·FK 삭제 검사.
- 그 밖은 추가하지 않는다 (엔터티 목록은 기존 `UX_LGCL_ENTT_01 (LGCL_MDL_SN, ENTT_NM)` 이 이름순·모델 조건을 맡는다).

### 9.5 Flyway

- 현재 저장소 : `V0__init.sql`·`V1__seed_data.sql`. 이 설계 중 다른 세션이 `V2__remove_default_admin.sql` 을 스테이징했다가 작업 트리에서 지웠다(`AD`) — **다음 번호는 구현 시점에 다시 확인** (기존 V0·V1 은 고치지 않는다).
- 새 마이그레이션 하나에 : 두 테이블·시퀀스·제약·인덱스·COMMENT, 예제 사전 단어(주제·영역·상위)·용어·`TB_TBL`/`TB_COL`·예제 논리 엔터티(+ 관계 속성 짝)·예제 인덱스 행 (기존 규칙, `V0SeedMigrationTest`·`LexormaIndexSeedTest` 고정 수 갱신). 예제 논리 모델(LEXORMA)에 예제 주제 영역을 넣을지는 **사용자 결정 필요** (넣지 않는 것이 "자동 분류 없음" 원칙과 맞다).

## 12. 화면 설계 (D-12)

### 12.1 위치 (권장 : 기존 화면 통합, 새 메뉴 없음)

- `/logicalModel` : 모델 선택 아래 **주제 영역 패널**(데스크톱 왼쪽 열, 엔터티·관계 탭은 오른쪽). 패널 항목 = 전체 · 미분류 · 영역 트리. 고른 항목이 엔터티·관계 목록 조건이 된다 (URL `?subjectAreaId=` / `?unclassified=1` — 기존 `?modelId=` 처럼).
- 새 메뉴(`주제 영역 관리`)안과 비교 : 별도 화면은 모델 선택·엔터티 목록을 다시 만들게 된다 → 통합 권장. **사용자 결정 필요**.
- 375px : 패널을 목록 위 접히는 선택 상자("주제 영역 : 전체 ▾")로 바꾼다.

### 12.2 영역 트리

- 모델 영역 전체를 한 번 읽어 그린다 (수백 개 — 부분 조회 불필요, §19). 새 트리 라이브러리 없이 `ul[role=tree]`·`li[role=treeitem][aria-expanded]` + 화살표 키 탐색, 펼침은 사이드바 하위 메뉴와 같은 grid 0fr↔1fr 180ms(줄인 모션 0). 항목마다 순차 애니메이션 없음.
- 항목 : 이름(긴 이름 줄바꿈) · 하위 포함 엔터티 수. 패널 위 검색(이름, 메모리).
- 동작 (USER 이상) : 등록·수정(대화상자 : 이름·설명·상위·순서) · 삭제(빈 영역만, 확인 대화상자) · 상위 변경(수정 대화상자의 상위 선택 — 끌어 놓기는 후속). 성공은 토스트, 확인·제약은 대화상자 ([ui-motion-guide §7](../reference/ui-motion-guide.md)).

### 12.3 엔터티 목록·분류

- 기존 엔터티 표(서버 페이징·검색·정렬·스켈레톤) 그대로, 열 추가는 "주제 영역" 하나(전체·미분류 조건일 때만 의미 — **검토 중**).
- 분류 : 표에 체크 선택 → [주제 영역 지정] 대화상자(영역 선택 또는 미분류로) → 확인 → 토스트 "{n}개 엔터티의 주제 영역을 바꿨습니다". 한 번 최대 500, 전부 아니면 전무.
- 엔터티 상세 : 기본 탭에 소속 영역 경로("고객 관리 › 회원 관리") · [영역으로 보기] · [영역 ERD]. 분류 변경은 상세의 별도 단추(엔터티 수정 폼과 분리 — §7).
- 엔터티 등록 폼에 영역 선택을 넣을지 : **사용자 결정 필요** (권장 : 넣지 않고, 영역을 고른 상태에서 등록하면 그 영역에 소속 — 같은 트랜잭션, 실패 시 함께 롤백).

## 13. 논리 모델 관리 연계 (§14 상세)

- 필터 : 전체 / 미분류 / 영역(직접) / 영역 + 하위 (D-15 기본값 **사용자 결정 필요**, 권장 하위 포함). 검색·정렬·페이징과 조합 (SQL 조건만 추가 — `LogicalModelQueryRepository` 의 페이지 ID 먼저 → 묶음 집계 구조 유지).
- 수치 구분 : 요약(모델 전체) · 패널(영역 직접 수 / 하위 포함 수 / 미분류 수) · 목록 머리(현재 조건 `recordsTotal`). 단일 소속이라 영역 합계 = 분류된 엔터티 수 (중복 없음).
- 관계 목록 (D-15 **사용자 결정 필요**) : ① 양 끝 모두 영역 안 (ERD 의 "범위 안 관계"와 같음) ② 한 끝 이상 (영역에 걸린 모든 관계) ③ 선택. 권장 : ② 를 기본으로 하고 행에 "영역 밖" 표시 — 관리 화면은 빠짐없이 보는 것이 목적, ERD 는 지금처럼 ①(+ 범위 밖 수).

## 14. 논리 ERD 연계

- 범위에 세 번째 종류 `area` 추가 (`search`·`neighbors` 와 나란히) : 영역 선택 상자 + [하위 포함] + 기존 검색어·페이지(100, 최대 300). 영역 없음(= 전체 모델)이 기본 — 기존 탐색 그대로.
- 범위 안 관계·범위 밖 수 : 기존 `graphPart` 를 그대로 쓴다 (ID 집합만 영역 조건으로 뽑는다).
- 이웃 탐색 (권장 : 전체 모델 기준 그대로) : 영역 범위에서 엔터티 이웃을 열면 지금처럼 모델 전체 관계로 1~3단계 — 다른 영역 엔터티도 실제 관계대로 보인다. 노드에 "다른 영역" 표시(영역명 배지)는 4단계 후보.
- 엔터티 찾기 (권장 : 모델 전체 + 결과에 영역명) — 영역만 찾기는 선택 옵션(**검토 중**). 50 상한 그대로.
- 평행 관계선·자기 참조·Crow's Foot·식별/비식별·참여 수·관계 선택·범례 : 렌더링 경로 변경 없음 (범위만 바뀐다).
- 표시 : 1차는 상단 영역 필터와 범위 문구("주문 관리(하위 포함) · 전체 42개 중 1–42")만. 영역 색·그룹 박스·복합 노드·영역별 자동 배치는 별도 후보 (렌더링·ELK 비용).

## 15. 외부 영역 관계 (D-08)

권장 A : 영역 엔터티만 그리고, 다른 영역과의 관계는 기존 "범위 밖 관계 N" + 이웃 탐색으로. B(외부 엔터티 추가 표시)는 이웃 1단계와 같아 중복 — 필요하면 "영역 + 1단계 이웃" 버튼으로 기존 이웃 탐색을 재사용하는 안을 후속 제안.

## 16. ERD 레이아웃 (D-07)

- 현재 : `TB_LGCL_ERD_LYT` 사용자·모델 1건, 저장은 화면 노드 + 범위를 바꾸기 전에 옮긴 노드를 **합친다**(범위 밖 좌표는 그대로), 버전 409.
- 권장 A(=C 의 1차) : 영역 ERD 는 기존 부분 조회와 같은 "범위" 로 취급, 좌표는 모델 배치를 공유. 영역에서 옮겨 저장하면 전체 모델에서도 그 자리 — 화면에 "배치는 모델 전체와 함께 저장됩니다" 안내. 자동 배치는 지금처럼 화면 노드만 옮기고 저장해야 반영.
- B(영역별 독립 배치)는 새 테이블(모델·영역·사용자) + 영역 삭제·이동·엔터티 이동 시 처리 + 초기 좌표 정책이 필요 — 후속. 기존 배치를 지우거나 자동으로 바꾸지 않는다. **사용자 결정 필요**.

## 17. 물리 모델·매핑 연계 (D-09)

권장 A (논리 전용). 매핑·물리 생성·정합성 비교·품질 진단·물리 스키마는 바꾸지 않는다. 물리 화면에서 "이 테이블의 업무 영역" 보기는 매핑 경유(B) 후속 후보 — 물리 쪽에 중복 저장하지 않는다. 주제 영역명으로 스키마 생성·테이블 이동·스키마명 변경은 하지 않는다. MCP·AI 도구 응답은 1차에서 바꾸지 않는다 (**검토 중** : `getLogicalModel` 에 영역을 더할지).

## 18. 모델 버전·이력·교환 (D-10)

- 이력·버전 : `ModelChangeRecorder` 에 새 대상 유형(`LOGICAL_SUBJECT_AREA`, 소속은 영역의 자식 행 또는 별도 유형 — **검토 중**)을 더하면 이력·버전 스냅숏·버전 비교에 자동으로 들어간다. 단 **내보내기도 같은 `currentState` 를 쓰므로** 같은 작업에서 교환 형식을 함께 다뤄야 한다 — 미루면 형식 3 내보내기에 모르는 유형이 섞이거나(가져오기 거절), 반대로 이력에서 빼면 버전 비교에서 분류 변경이 사라진다.
- 교환 (권장 : 2단계에 포함) : 형식 4 — `LOGICAL_SUBJECT_AREA` 목록(파일 내 id·상위 ref·이름·설명·순서·소속 엔터티 ref). 형식 1~3 파일은 그대로 가져온다(영역 없음 = 미분류). 가져오기는 새 모델에만 만들므로 이름 충돌은 그 모델 안에서만 — 같은 모델로 합치는 가져오기는 기존처럼 CONFLICT. 계층·엔터티 ref 를 새 id 로 다시 맞춘다. 영역별 배치는 없다(D-07 A).
- 최소 범위 제안 : 2단계 백엔드에 테이블·API·이력·버전·교환 형식 4를 함께 (데이터 손실 방지). 버전 비교 화면의 영역 변경 전용 표시는 3단계.

## 19. 성능

| 규모 | 엔터티 | 영역 |
|---|---:|---:|
| 소형 | 100 | 10 |
| 중형 | 1,000 | 50 |
| 대형 | 3,000 | 200 |
| 확장 검토 | 10,000 | 500 |

- 영역 목록 : 영역 전체 1쿼리 + `소속 group by SBJ_AREA_SN` 1쿼리 + 미분류 수 1쿼리 → 하위 포함 수는 메모리 합산. 영역 수와 관계없이 3쿼리 (N+1 없음).
- 하위 포함 필터 : 메모리 트리에서 하위 id 집합(≤ 500) → `SBJ_AREA_SN in (…)` 조인. 재귀 CTE·캐시 없음.
- 엔터티 목록 : 기존 "페이지 ID 먼저 → 묶음 집계" 그대로, 조건은 `exists (소속 …)` / `not exists`. 3,000/10,000 엔터티에서 기존 측정(`LogicalModelManagementPerformanceTest`, `LEXORMA_PERF=true`)에 영역 조건 경우를 더해 H2·PostgreSQL 로 잰다.
- ERD : 영역 조건으로 ID 를 뽑는 쿼리 하나만 바뀌고 `graphPart` 의 쿼리 수 일정 구조 그대로. 300 상한 우회 없음.
- 정렬 : 기존과 같이 이름 + ID (Collation 변경 없음).

## 20. 동시성 (§19.4)

- 모든 영역·소속 쓰기는 **논리 모델 행 잠금 먼저** (기존 `lockModel`) → 같은 모델의 영역 수정·삭제·이동·소속 지정·엔터티 삭제가 직렬화된다. 그래서 "삭제와 소속 지정 동시", "이동 동시로 생기는 순환" 은 잠금 뒤 다시 읽은 트리로 검사하면 생기지 않는다.
- 영역 수정 : `modifiedAt` (`ModelBase.verify`, 409 `MODEL_CONFLICT`). 소속 일괄 지정 : 요청에 엔터티별 기준을 두지 않고(분류는 마지막 요청이 이긴다) **검토 중** — 기준이 필요하면 영역 `modifiedAt` 을 함께 보낸다.
- PostgreSQL 에서만 드러나는 경합이 있었으므로(소스 매핑 사례) 동시 테스트는 PostgreSQL 로도 확인.
