# M-8 완료 정리와 물리 모델 정합성 안정화

M-8(ERD 편집) 1차·2차·3차를 마친 뒤, 구현 중에 찾은 서버 검증 공백과 테스트 환경 문제를 정리한 기록이다.
로드맵은 [data-modeling-roadmap.md](data-modeling-roadmap.md), M-8 기록은 [erd-editing-m8.md](erd-editing-m8.md)(1차·2차)와 [physical-erd-editing-m8.md](physical-erd-editing-m8.md)(3차)에 있다.

DB 마이그레이션·엔티티·API 경로는 바꾸지 않았다. 바뀐 것은 기존 서비스의 검증과 DDL 응답의 필드 1개, 화면 안내다.

## 1. M-8 완료 근거와 후속 이관

로드맵의 M-8 완료 조건은 "ERD 편집 결과가 테이블·컬럼 관리 화면·DDL 과 일치하고, 레이아웃이 복원된다" 이다.

| 확인 항목 | 근거 |
|---|---|
| 논리 ERD 직접 편집 (엔터티·속성·관계·식별자) | 1차·2차 : `LogicalErdEditIntegrationTest`, 브라우저 검증 ([erd-editing-m8.md](erd-editing-m8.md) 4장·9장) |
| 물리 ERD 직접 편집 (테이블·컬럼·FK·인덱스·제약) | 3차 : `PhysicalErdEditIntegrationTest`, 브라우저 59항목 + 이번 27항목 |
| ERD = 테이블·컬럼 관리 데이터 | 같은 API 를 쓴다. ERD 조회·테이블 물리 모델·컬럼 조회 결과를 서로 비교 (통합 테스트, 브라우저) |
| FK·제약조건 관리, DDL 정합성 | 단일·복합·자기 참조·다중 FK, UNIQUE·CHECK·인덱스가 같은 이름·컬럼 순서로 DDL 에 나온다 |
| 권한·승인·프로젝트 격리 | VIEWER·USER·DBA·MANAGER·ADMIN·미승인 사용자, 다른 프로젝트 ID |
| M-7 매핑 보호 | 매핑된 테이블·컬럼 삭제 거절 (통합 테스트 + 이번에 ERD 화면에서 확인) |
| 레이아웃 저장·복원, 부분 조회 보호 | 범위 밖 테이블의 좌표 보존 (3차 필수 시나리오) |

**M-8 은 완료로 본다.** 작업 범위에 함께 적혀 있던 두 항목은 완료 조건에 들어 있지 않고 구현하지 않았으므로, M-8 에서 떼어 별도 과제로 관리한다.

| 분리한 과제 | 원래 위치 | 옮긴 위치 | 내용 |
|---|---|---|---|
| ERD 레이아웃 확장 | M-8 작업 범위 "레이아웃 확장", D-10 "M-8 에서 재검토" | 로드맵 M-8 후속 표, D-10 | 노드 접힘·펼침, 그룹, 한 모델의 여러 다이어그램 뷰, 사용자별 뷰 설정, 큰 ERD 탐색 |
| 동시 편집 정책 | M-8 미확정 사항 D-09, 테스트 시나리오 "동시 편집 충돌" | 로드맵 M-8 후속 표, D-09 | 같은 엔터티·테이블·관계의 동시 수정, 낙관적 잠금 또는 버전, 충돌 안내, 마지막 저장 우선의 위험 |

### 1.1 레이아웃 저장 구조와 확장 가능성 (분석만)

지금 구조 : 물리 ERD 는 `TB_ERD_LYT` 에 **사용자 × 프로젝트 1건**, 논리 ERD 는 `TB_LGCL_ERD_LYT` 에 **사용자 × 논리 모델 1건**. 한 행에 노드 좌표(JSON 문자열 `NODE_PSTN_CN` : 테이블 ID → x·y)와 화면 위치·배율, `@Version` 번호가 있다. 저장은 요청의 노드를 저장된 노드에 합치고(범위 밖 보존) 삭제된 테이블만 뺀다.

- 접힘·그룹 : 좌표 JSON 의 값에 속성을 더하면(예 : `collapsed`, `groupId`) 테이블 변경 없이 넣을 수 있다. 다만 지금 합치기 규칙은 "노드 → 좌표" 만 안다. 그룹은 노드가 아닌 것의 좌표·크기·이름을 저장해야 하므로 JSON 구조를 버전 필드와 함께 바꿔야 한다.
- 여러 다이어그램 뷰 : 지금은 (프로젝트, 사용자) UNIQUE 라 한 사람이 뷰를 하나만 가진다. 뷰 이름·순번 컬럼과 UNIQUE 범위 변경이 필요하다 → **마이그레이션 필요**. 프로젝트 공유 뷰는 소유자·공개 범위와 누가 고칠 수 있는지(D-10)를 먼저 정해야 한다.
- 큰 ERD : 서버는 한 번에 300 테이블까지만 준다(D-02). 접힘·그룹은 이 한도 안에서의 표시 문제이고, 한도 자체는 별도다.

### 1.2 동시 편집 (분석만)

모델 데이터(테이블·컬럼·관계·엔터티 …)에는 버전 필드가 없다. 두 사람이 같은 대상을 고치면 **나중에 저장한 값이 남고 먼저 저장한 사람은 알지 못한다.** 레이아웃만 `@Version` 으로 오래된 탭의 저장을 409 로 거절한다.
ERD 편집은 "저장 → 다시 조회" 라서 화면이 오래된 상태로 남는 시간은 짧지만, 수정 폼을 연 사이에 다른 사람이 바꾼 값은 덮어쓴다. 컬럼 일괄 편집은 한 번에 여러 행을 바꾸므로 영향이 가장 크다.
이 문제는 ERD 가 아니라 테이블·컬럼·논리 모델 관리 화면 전체의 것이다. 버전 필드를 넣으면 모든 수정 API 의 요청 형식이 바뀌므로 M-9(변경 이력)의 이력 저장 방식(D-11)과 함께 설계하는 편이 낫다.

이번에 넣은 행 잠금(2장)은 "승인과 수정이 엇갈려 승인된 테이블이 바뀌는 것" 하나만 막는다. D-09 의 해결이 아니다.

## 2. 승인된 테이블 수정 보호

**문제** : 화면(테이블 상세, 물리 ERD)은 승인된 테이블의 수정 버튼을 막지만, `PUT /api/saveTable` 은 승인 여부를 보지 않았다. 직접 호출하면 승인된 테이블의 이름·설명·스키마를 바꿀 수 있었다. 다른 프로젝트의 테이블 ID 를 보내면 `NullPointerException`(500)이 났다.

**기존 승인 정책** (바꾸지 않았다)

| 대상 | 승인 상태의 의미 |
|---|---|
| 테이블 | 승인 권한자(ADMIN·MANAGER·프로젝트 관리자)가 등록하면 승인, 그 외는 승인 대기. 승인되면 수정·삭제 불가(승인취소 후). **컬럼은 승인된 테이블에만 등록한다** |
| 컬럼 | 승인된 컬럼은 수정·삭제·순서 변경 불가 (`APPROVED_DATA_CANNOT_BE_UPDATE` / `_DELETED`) |
| 관계·인덱스·제약 | 승인된 항목은 삭제 불가. 수정 API 는 없다 |
| 논리 엔터티·관계 | 승인되면 수정·삭제 불가, 엔터티가 승인되면 속성·식별자도 잠긴다 |

**변경** (`TableDesignServiceImpl`)

- `updateTable` : 테이블 행을 잠가(`findForUpdate`) 읽고, 없으면 `TABLE_IS_NOT_DEFINED`, 승인된 테이블이면 `APPROVED_DATA_CANNOT_BE_UPDATE` 로 거절한다. 이름·설명·스키마·마스터 여부·정렬 순서가 모두 이 메서드 하나를 지나므로 한 곳에서 막힌다.
- `updateTableIsApproval` : 같은 행 잠금으로 읽는다. 없는(다른 프로젝트) 테이블은 `TABLE_IS_NOT_DEFINED`.
- 역할과 관계없다. ADMIN 도 승인취소 후에 수정한다 (삭제 정책과 같다).
- 다른 수정 경로 : 엑셀 업로드는 새 테이블만 넣고 기존 테이블은 건너뛴다. 스키마 이동은 `updateTable` 의 `schemaId` 뿐이다. 테이블 일괄 수정 API 는 없다.

**동시성** : 승인과 수정이 같은 행 잠금으로 줄을 선다. 승인이 먼저 잡으면 뒤따른 수정은 승인된 상태를 읽고 거절되고, 수정이 먼저 잡으면 수정이 끝난 뒤에 승인된다(승인자는 직전의 수정을 보지 못했을 수 있다 — D-09 의 범위). H2·PostgreSQL 에서 두 스레드로 확인했다.

## 3. FK 참조 무결성 검증

**문제** : `POST /api/physical/relation` 은 컬럼이 그 테이블의 것인지만 보았다. 키가 아닌 컬럼을 가리키거나 타입이 맞지 않는 FK 가 저장되었다. DDL 생성기는 그런 FK 를 경고와 함께 건너뛰었으므로(키가 아닌 대상) "저장은 됐는데 DDL 에는 없는" 관계가 생겼다.

**변경** (`PhysicalModelServiceImpl.saveRelation`, 판단 기준은 `TableDdlGenerator` 에 두어 DDL 생성과 같이 쓴다)

관계 유형이 `FK` 일 때만 검사한다. `LOGICAL`(논리 관계)은 제약이 아니고 DDL 에 나가지 않으므로 검사하지 않는다. 거절은 `INVALID_PHYSICAL_MODEL`(400)이고 사유 문구에 테이블·컬럼·타입이 들어간다.

### 3.1 참조 대상 키

대상 컬럼 **구성**이 다음 중 하나와 같아야 한다.

| 인정하는 키 | 출처 |
|---|---|
| 대상 테이블의 PK 전체 (단일·복합) | 컬럼의 PK 여부 |
| 고유값 컬럼 1개 | 컬럼의 고유값 여부 |
| UNIQUE 제약 1개의 컬럼 전체 (단일·복합) | `/api/physical/constraint` |
| 고유 인덱스 1개의 컬럼 전체 (단일·복합) | `/api/physical/index` (`isUnique`) |

- 거절 : 일반 컬럼, 복합 키의 일부, 서로 다른 키의 컬럼을 섞은 조합, 키보다 많은 컬럼. 컬럼 각각이 어떤 키에 들어 있다는 것만으로는 인정하지 않는다.
- 컬럼 쌍의 **순서** : 구성이 같으면 키에 정의된 순서와 달라도 받는다. 저장한 쌍(원본 ↔ 대상)이 그대로 DDL 의 `FOREIGN KEY (a, b) REFERENCES t (x, y)` 가 된다. 쌍의 대응은 타입 검사(3.2)가 쌍마다 본다.
- **승인 여부는 보지 않는다.** 승인 대기 중인 UNIQUE 제약도 키로 본다. DDL 이 승인 여부로 거르지 않는 것(4장)과 같은 기준이어야 "등록된 FK = DDL 의 FK" 가 유지된다.
- 스키마가 다른 테이블도 같은 검사를 거친다 (같은 프로젝트 안).
- DDL 생성기도 UNIQUE 제약·고유 인덱스를 키로 인정하도록 맞췄다. 전에는 PK 전체와 고유값 컬럼 1개만 인정해서, 복합 UNIQUE 를 참조하는 FK 는 DDL 에 나오지 않았다.

### 3.2 데이터 타입 호환

지원 DBMS 는 프로젝트의 대상 DB 4종(PostgreSQL·Oracle·MySQL·MariaDB)이다. 컬럼의 공통 타입명을 DDL 생성기와 같은 규칙으로 대상 DB 타입으로 바꾼 뒤 비교한다(문자열 그대로 비교하지 않는다 : `VARCHAR2(10)` 과 `VARCHAR(10)` 은 같은 DB 타입이 된다). **확실한 조합만 받고 나머지는 거절한다.**

| 조합 (대상 DB 타입 기준) | PostgreSQL | Oracle | MySQL·MariaDB |
|---|---|---|---|
| 완전히 같은 타입 (길이·정밀도 포함) | 허용 | 허용 | 허용 |
| 문자 타입끼리 길이만 다름 (`VARCHAR`/`VARCHAR2`, `CHAR`) | 허용 | 허용 | 허용 |
| `NUMERIC`/`NUMBER` 끼리 정밀도만 다름 | 허용 | 허용 | **거절** (고정 소수 타입은 크기가 같아야 한다) |
| 정수끼리 크기가 다름 (`INTEGER` ↔ `BIGINT`) | 허용 (`SMALLINT`·`INTEGER`·`BIGINT`) | 허용 (둘 다 `NUMBER(n)`) | **거절** (정수 크기가 같아야 한다) |
| `CHAR` ↔ `VARCHAR`, `TEXT` ↔ `VARCHAR`, 정수 ↔ `NUMERIC`, 날짜 ↔ 일시, 문자 ↔ 숫자 | 거절 | 거절 (공통 타입이 같은 `NUMBER(n)` 이 되는 경우만 허용) | 거절 |
| DB 고유 타입·해석할 수 없는 타입 (`ENUM(...)`, `GEOMETRY` …) | 같을 때만 | 같을 때만 | 같을 때만 |

- 판단하지 않는 것 : 부호(UNSIGNED), 문자 집합·콜레이션, 타임존 유무. MetaMora 는 이 정보를 컬럼에 두지 않는다. 같은 타입이어도 이 값이 다르면 실제 DB 에서 실패할 수 있다(특히 MySQL).
- 실제 DBMS 는 받아 줄 수 있지만 여기서 거절하는 조합이 있다(예 : PostgreSQL 의 `VARCHAR` ↔ `TEXT`). 확신할 수 없는 조합을 호환으로 처리하지 않는다는 기준에 따랐다. 필요하면 타입을 맞추거나 논리 관계로 등록한다.
- 길이·정밀도만 다른 FK 는 받되, DDL 이 "값이 들어가지 않거나 잘릴 수 있다" 는 기존 경고를 낸다.
- 프로젝트의 대상 DB 를 나중에 바꾸면 이미 등록된 FK 가 새 DB 기준으로는 맞지 않을 수 있다. 다시 검사하지 않는다(DDL 경고로만 드러난다).

### 3.3 적용 경로와 기존 데이터

| 경로 | 적용 |
|---|---|
| 물리 모델 API `POST /api/physical/relation` | 검사 (물리 ERD 의 FK 등록, 복합 FK 포함. ERD 전용 로직 없음) |
| FK 변경 | 수정 API 가 없다. 삭제 후 다시 등록하므로 등록 검사를 지난다 |
| 컬럼의 참조 테이블명(`refTableName`) → `REF_COLUMN` 관계 | 대상은 항상 단일 PK 로 정해진다(기존 동기화 규칙). **타입은 검사하지 않는다** — 컬럼 저장·엑셀 업로드를 막게 되므로 넣지 않았고 DDL 경고로 남는다 (남은 위험) |
| 등록 뒤에 대상 컬럼의 PK·고유값을 풀거나 타입을 바꾸는 것 | 막지 않는다. 관계는 남고 DDL 이 경고와 함께 건너뛴다 (남은 위험) |
| 검증 전에 저장된 FK | **지우거나 고치지 않는다.** ERD·물리 모델 조회에 그대로 나오고, DDL 은 키가 아닌 대상이면 경고와 함께 건너뛰고 타입이 다르면 경고한다. 승인취소 후 삭제할 수 있다 |

화면(FK 등록 폼)은 PK 가 아닌 대상·복합 PK 일부·타입 차이를 미리 알려 주지만 막지는 않는다. UNIQUE 제약·고유 인덱스와 DB 별 타입 규칙을 화면이 다 알지 못하기 때문이다. 판정은 서버가 하고, 거절 사유를 대화상자에 보여 준다.

## 4. DDL 과 승인 상태

**분석** : DDL 생성(`GET /api/selectTable/ddl/{tableId}`)은 승인 여부를 어디에서도 보지 않는다. 승인 대기 테이블, 승인 대기 컬럼, 승인 대기 FK·인덱스·제약이 모두 그대로 나온다. 로드맵은 DDL 을 "출력만" 하는 기능으로 적고 있고(원본 DB 에 반영하지 않는다), 승인 워크플로와 DDL 을 연결하는 문서·테스트는 없다. 3차 통합 테스트는 "승인 대기 FK 도 DDL 에 나온다" 를 기대 동작으로 고정해 두었다. 화면에는 복사 버튼만 있고 배포·다운로드 기능은 없다.

**결정** : 지금의 DDL 은 **설계 중인 모델을 그대로 보여 주는 설계용 DDL** 이다. 출력은 바꾸지 않았다. 승인 대기 항목만 빼면 남은 정의의 뜻이 달라진다(예 : 승인 대기 컬럼을 빼면 그 컬럼을 쓰는 PK·인덱스·FK 가 깨진다).

**보강** : 무엇이 승인 전인지 알 수 있게 했다.

- 응답에 `pendingApprovals`(종류별 한 줄 : 테이블 / 컬럼 / 관계(FK) / 인덱스 / 제약조건)를 더했다. DDL 문자열과 `warnings` 는 그대로다.
- DDL 대화상자는 승인 대기 항목이 있으면 "이 DDL 은 현재 설계 모델 기준이며 승인 대기 항목도 포함합니다." 와 목록을 보여 준다.

**결정이 필요한 것 (하지 않았다)** : 승인된 것만 담는 "승인 기준 DDL" 이 필요한가.

| 선택지 | 영향 |
|---|---|
| A. 지금처럼 설계용 DDL 하나 (안내만) | 변경 없음. 배포용으로 쓰려면 사용자가 안내를 보고 판단 |
| B. 승인 대기 항목이 하나라도 있으면 승인 기준 DDL 생성을 **막는다** | 의미가 분명하다. 승인 전에는 승인 기준 DDL 을 볼 수 없다. 모드 선택(파라미터·화면)이 필요 |
| C. 승인 대기 항목을 **빼고** 만든다 | 의존 관계를 풀어야 한다 : 승인 대기 컬럼이 걸린 PK·UNIQUE·인덱스·FK, 승인 대기 테이블을 참조하는 다른 테이블의 FK. 일부만 빠진 DDL 이 실제 설계와 달라질 위험이 크다 |

B 가 가장 안전하다고 본다. 여러 테이블 DDL·Export(M-11)와 함께 정하는 편이 낫다.

## 5. PostgreSQL 테스트 환경

**문제** : `ProjectAccessRevokeTest` 가 `@SpringBootTest(properties = "spring.datasource.url=jdbc:h2:mem:metamora-revoke…")` 로 H2 주소를 고정했다. PostgreSQL 로 전체 테스트를 돌리면(환경 변수로 드라이버를 바꾼다) H2 주소에 PostgreSQL 드라이버가 붙어 컨텍스트가 뜨지 않았다. 그래서 그동안 PostgreSQL 실행은 테스트를 골라서 돌렸다.

**판단** : H2 전용 테스트가 아니다. 세션(Spring Session JDBC)·권한 회수는 DB 공통 동작이고, 주소를 고정한 이유는 `SmokeTest` 가 admin 비밀번호를 바꾸므로 **데이터를 나누기 위해서**였다.

**변경** : 실행 환경이 정한 DB 종류를 따른다.

- H2(기본) : 전처럼 별도 인메모리 DB.
- PostgreSQL(`SPRING_DATASOURCE_URL` 이 `jdbc:postgresql:` 로 시작) : 같은 검증 DB 안에 실행마다 새 스키마(`revoke_…`)를 쓴다. 접속 주소에 `currentSchema` 를 붙이고 Flyway 기본 스키마를 그 스키마로 지정한다(Flyway 가 만든다). 끝나면 그 스키마만 지운다.
- 재시작을 흉내 내는 두 번째 인스턴스도 같은 설정을 받는다.

**전체 실행 방법** (개발 DB 가 아닌 빈 검증 DB 를 만들어 쓰고 지운다)

```bash
./gradlew clean build                 # H2

# PostgreSQL : 빈 DB 를 만든 뒤
SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:15439/<검증 DB> \
SPRING_DATASOURCE_DRIVER_CLASS_NAME=org.postgresql.Driver \
METAMORA_TEST_POSTGRES_URL=jdbc:postgresql://localhost:15439/<검증 DB> \
./gradlew test -PfrontendPrebuilt=true --rerun
```

`--rerun` 을 빼면 직전 H2 결과가 최신으로 판단되어 테스트가 다시 돌지 않는다. `METAMORA_TEST_POSTGRES_URL` 은 `V0SeedMigrationTest` 의 PostgreSQL 쪽을 켠다(없으면 건너뛴다).

## 6. 물리 ERD 화면 보완

- **같은 두 테이블 사이의 FK 여러 개** : 컬럼이 접힌 상태(축소, 20개를 넘는 컬럼)에서는 관계선이 테이블 연결점으로 모이는데, 두 선이 완전히 겹쳐 캔버스에서 하나만 고를 수 있었다. 선이 꺾이는 위치를 관계마다 달리해 따로 고를 수 있게 했다. (원본과 대상이 같은 높이에 있어 선이 직선이 되면 여전히 겹친다. 그때는 패널의 관계 목록에서 고른다.)
- FK 등록 폼의 안내 문구를 서버 검증에 맞췄다 ("…가 아니면 FK 로 저장되지 않습니다"). FK 일 때만 보인다.

### 7.3 확인하지 않은 것

- 논리 ERD 화면은 이번에 브라우저로 다시 실행하지 않았다(논리 쪽 화면·서비스는 바꾸지 않았고, 통합 테스트는 통과).
- 컬럼 일괄 편집기의 붙여넣기 추가·다른 테이블에서 복사·공통 컬럼 추가·새 표준용어 등록은 하지 않았다(검색해서 추가만).
- 같은 테이블명을 두 스키마에 두는 것은 기존 정책상 불가(D-03)라 "구분" 은 확인할 대상이 없었다. 스키마를 바꿔 가며 저장한 배치의 유지는 3차의 범위 밖 배치 시나리오로 갈음했다.
- 두 사용자의 실제 동시 편집(브라우저 두 개), 큰 ERD 의 반응 속도, Chrome 이외 브라우저, 터치, 820px 보다 좁은 화면, PostgreSQL 을 붙인 상태의 화면.
- Oracle·MariaDB 타입 규칙은 단위 테스트의 표로만 확인했다. **어느 DBMS 에도 생성한 DDL 을 실행해 보지 않았다**(범위 밖). 호환 표는 각 DBMS 문서의 규칙을 옮긴 것이다.
- 100개를 넘는 페이지 경계에서의 편집.
