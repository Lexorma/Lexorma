# M-9 — 모델 변경 이력 (1차 : 기반·물리 모델, 2차 : 논리 모델·매핑·조회 화면)

2026-11-12. 물리 모델(테이블·컬럼·관계·인덱스·제약조건)을 바꾸면 누가·언제·무엇을·어떻게 바꿨는지와 변경 전후 상태를 남기고, API 로 조회한다.
1~10장은 1차(백엔드, 물리 모델) 기록이다. **2차(논리 모델·매핑 이력, 이름 스냅샷, 조회 화면, 성능 측정)는 11장**에 있고, 1차 내용 중 2차에서 달라진 것은 11장이 우선한다.
모델 버전(명명된 기준점)·버전 비교·복원은 구현하지 않았다.

## 1. D-11 결정 — 공통 변경 이력 테이블 + 변경 전후 JSON

| 후보 | 판단 |
|---|---|
| **공통 이력 테이블 + JSON (채택)** | 기존 모델 테이블이 원본 그대로다. 대상 종류가 늘어도 테이블을 더 만들지 않는다. 삭제된 객체의 마지막 상태가 남는다 |
| 엔티티별 이력 테이블 | 물리 모델만 5종, 논리 모델·매핑까지 10종이 넘는다. 모델 컬럼을 바꿀 때마다 이력 테이블도 바꿔야 한다 |
| 변경마다 전체 스냅샷 | 저장량이 크고, 한 객체의 변경을 찾으려면 스냅샷끼리 비교해야 한다 |
| 이벤트 소싱 | 현재 상태를 이벤트 재생으로 만들어야 한다. 기존 조회·DDL·ERD 를 모두 다시 써야 한다 |

- 현재 모델은 기존 테이블에서 읽는다. 이력은 감사·추적용 추가 기록이고, 이력으로 현재 상태를 계산하지 않는다.
- 별도 메시징·비동기 처리는 없다. 같은 DB, 같은 트랜잭션이다.
- AI-1 의 원본 메타데이터 변경 이력(수집한 카탈로그의 ADDED·MODIFIED·REMOVED)은 다른 개념이라 이 테이블을 쓰지 않는다. 방식(공통 테이블 + 전후 JSON)은 그대로 가져다 쓸 수 있다.

## 2. 이력 테이블 (`V5__model_change_history.sql`)

`TB_MDL_CHG_HSTRY` (모델 변경 이력), 시퀀스 `SQ_MDL_CHG_HSTRY`. 추가만 한다.

| 컬럼 | 용어 | 타입 | 내용 |
|---|---|---|---|
| `MDL_CHG_HSTRY_SN` | 모델_변경_이력_일련번호 | BIGINT, PK | |
| `PRJ_SN` | 프로젝트_일련번호 | BIGINT | 조회 권한의 기준 |
| `CHG_GROUP_ID` | 변경_그룹_아이디 | VARCHAR(255) | 한 작업(트랜잭션)의 UUID |
| `TRGT_TYPE_CD` | 대상_유형_코드 | VARCHAR(20) | `PHYSICAL_TABLE` · `PHYSICAL_COLUMN` · `PHYSICAL_RELATION` · `PHYSICAL_INDEX` · `PHYSICAL_CONSTRAINT` |
| `TRGT_SN` | 대상_일련번호 | BIGINT | 대상 객체의 ID (FK 아님 — 대상이 삭제돼도 남는다) |
| `TRGT_NM` | 대상_명 | VARCHAR(255) | 변경 시점의 이름. 컬럼은 `테이블명.컬럼명` |
| `CHG_TYPE_CD` | 변경_유형_코드 | VARCHAR(20) | `CREATE` · `UPDATE` · `DELETE` · `APPROVE` · `REVOKE` |
| `CHG_BFR_CN` | 변경_이전_내용 | TEXT | 변경 전 JSON (CREATE 는 null) |
| `CHG_AFTR_CN` | 변경_이후_내용 | TEXT | 변경 후 JSON (DELETE 는 null) |
| `CHG_SRC_CD` | 변경_출처_코드 | VARCHAR(20) | `USER` · `AUTO_SYNC` |
| `USER_ID` | 사용자_아이디 | VARCHAR(255) | 변경한 사용자의 로그인 아이디 |
| `CHG_DT` | 변경_일시 | TIMESTAMP | 한 그룹의 이력은 같은 시각 |

인덱스 : `(PRJ_SN, CHG_DT)` 프로젝트의 최신 이력, `(PRJ_SN, TRGT_TYPE_CD, TRGT_SN)` 객체별, `(CHG_GROUP_ID)` 그룹.

- 지시서의 `PHYSICAL_RELATIONSHIP` 은 `PHYSICAL_RELATION` 으로 했다. 코드가 `TableRelation`·`relation` 이고, 코드 컬럼이 다른 코드 컬럼과 같은 20자다.
- 원인 객체 컬럼(`CAUSE_*`)은 만들지 않았다. 자동 동기화 관계의 원인 컬럼은 이력 JSON 의 `derivedColumnId` 에 있고, 원인이 된 변경은 같은 그룹에 있다(5장).
- 타입은 기존 도메인과 같게 했다(표준화 품질 진단의 도메인 불일치 0건 유지). 새 도메인은 없다.
- V5 는 CLAUDE.md 의 규칙대로 같은 파일에서 `COMMENT ON`, LEXORMA 예제(데이터 사전 단어 3·용어 10, 물리 테이블 1·컬럼 12, 논리 엔터티 1·속성 12·주 식별자 1), 예제의 논리 ↔ 물리 매핑까지 넣는다. 새 단어 `이력`(HSTRY)·`이전`(BFR)·`이후`(AFTR)는 공공데이터 공통표준단어다. `변경_일시` 는 공통표준용어 그대로다.
- V0~V4 는 바꾸지 않았다. 기존 데이터의 이력을 소급해 만들지 않는다.

### JSON 구조

키는 엔티티 속성 이름이다. **`ModelChangeRecorder` 에 적은 필드만** 들어간다(엔티티를 통째로 직렬화하지 않는다). 연관 객체는 ID 만 `<속성>Id` 로 남긴다. 감사 필드(등록·수정 일시·사용자)와 프로젝트 ID 는 넣지 않는다.

| 대상 | 필드 |
|---|---|
| 테이블 | `tableName` `tableKorName` `tableDescription` `isMasterTable` `sortOrder` `isApproval` `schemaId` |
| 컬럼 | `tableInfoId` `tableName` `columnName` `columnDesc` `dataType` `maxLength` `precision` `scale` `isNullable` `defaultValue` `sortOrder` `isMasterData` `refTableName` `isRequired` `isSensitive` `isPk` `isUnique` `isIndex` `isEncrypted` `example` `isApproval` `standardTermsId` |
| 관계 | `sourceTableId` `targetTableId` `relationName` `relationType` `relationSource` `derivedColumnId` `isApproval` `columns[{sourceColumnId, targetColumnId, columnOrder}]` |
| 인덱스 | `tableInfoId` `indexName` `indexType` `isUnique` `isApproval` `columns[{columnId, columnOrder}]` |
| 제약조건 | `tableInfoId` `constraintName` `constraintType` `checkExpression` `isApproval` `columns[{columnId, columnOrder}]` |

- PK·고유값·인덱스 여부는 컬럼 속성이라 **컬럼 이력에만** 남는다. UNIQUE·CHECK 제약조건은 제약조건 이력, FK 는 관계 이력이다. 같은 변경이 두 곳에 남지 않는다.
- 비밀번호·토큰·접속 정보는 모델 엔티티에 없고 목록에도 없다. 컬럼의 `example`(데이터 예시)은 화면에 보이는 모델 정보라 포함했다.
- **버전 필드는 두지 않았다.** 조회 API 는 저장된 JSON 을 그대로 돌려주므로 나중에 필드가 늘거나 없어져도 예전 이력 조회가 깨지지 않는다(테스트로 확인). 필드 이름을 바꾸거나 값의 뜻을 바꾸는 변경이 생기면 그때 `CHG_DT` 기준 변환이나 버전 컬럼을 넣는다 — 지금 넣으면 쓰는 곳이 없다.
- 이름(테이블명·용어명)은 ID 와 함께 풀어 넣지 않았다. 대상의 이름은 `TRGT_NM`, 컬럼의 테이블명은 `tableName` 에 있다. 용어·스키마 이름은 ID 로 지금 값을 찾아야 한다(2차 화면에서 필요하면 보완).

## 3. 기록 방식 (`data/history/record/ModelChangeRecorder`)

저장 경로마다 "이력 남기기" 를 부르지 않는다. 물리 모델을 바꾸는 경로가 많아서(테이블·컬럼 관리, 물리 ERD, 컬럼 일괄 편집, 엑셀 업로드, 승인 API, 참조 관계 자동 동기화, 테이블 삭제의 연쇄 삭제) 하나라도 빠뜨리면 이력에 구멍이 난다.
대신 참조 관계 동기화(`ReferenceSyncBoundary`)와 같은 구조를 쓴다.

```text
쓰기 트랜잭션 시작 ── 변경 모음(Pending) 등록
   │
   ▼  서비스가 모델을 바꾼다 (어느 경로든)
Hibernate 가 실제로 INSERT·UPDATE·DELETE 를 낼 때 이벤트 발생
   │   · 수정 이벤트는 값이 달라진 엔티티에만 온다
   ▼   · 이전 값·새 값을 받아 객체별로 모아 둔다 (처음 값 = 변경 전)
커밋 직전 ── ① 참조 관계 자동 동기화 (기존)  ② 남은 변경 flush
   │         ③ 객체마다 변경 전 ↔ 끝 상태 비교 → 달라진 것만 이력 저장 (같은 트랜잭션)
   ▼
커밋 (이력 저장이 실패하면 전체 롤백)
```

- **경로를 가리지 않는다.** 엔티티가 실제로 쓰일 때만 불리므로 빠지거나 겹치지 않는다. 새 저장 경로를 만들어도 따로 할 일이 없다.
- **JPQL·네이티브 일괄 UPDATE/DELETE 는 기록되지 않는다**(엔티티 이벤트가 없다). 지금 물리 모델에는 그런 문장이 없다. 만들면 이력을 직접 남겨야 한다.
- 관계의 컬럼 쌍, 인덱스·제약조건의 컬럼은 따로 이력을 만들지 않고 **부모 이력의 `columns`** 로 들어간다. 자식 행만 바뀌어도 부모의 UPDATE 로 남는다.
- 현재 사용자는 `SecurityContext` 의 로그인 아이디다. 로그인 없이 실행된 변경은 `USER_ID` 가 null 이다.

### 실제로 달라진 것만

1. Hibernate 의 변경 감지 : 값이 같으면 UPDATE 이벤트가 없다.
2. 그 위에 **이력 대상 필드만** 비교한다. 수정 일시·수정자만 달라진 저장, 정밀도 `10` → `10.00` 같은 표기 차이는 이력이 아니다.
3. 한 트랜잭션에서 한 객체는 **이력 1건**이다. 여러 번 flush 되어도(엑셀 청크) 처음 값과 끝 값만 본다. 만들었다가 같은 트랜잭션에서 지운 객체는 남기지 않는다.

| 요청 | 이력 |
|---|---|
| 같은 값으로 다시 저장 (여러 번) | 없음 |
| 컬럼 20개 일괄 저장, 2개만 변경 | UPDATE 2건 |
| 컬럼 순서 변경 | 순서가 달라진 컬럼만, 달라진 필드는 `sortOrder` |
| 이미 승인된 것을 다시 승인 | 없음 |
| 자동 동기화를 다시 돌렸는데 달라진 것 없음 | 없음 |
| 검증·권한·승인 상태로 거절된 요청, 롤백된 트랜잭션 | 없음 |

### 작업 종류와 전후 상태

| 작업 | 조건 | BEFORE | AFTER |
|---|---|---|---|
| CREATE | 새 객체 | null | 저장된 상태 |
| UPDATE | 값이 달라짐 | 트랜잭션 전 상태 | 끝 상태 |
| DELETE | 삭제 | 삭제 전 상태 | null |
| APPROVE / REVOKE | **승인 여부만** 달라짐 | 승인 전 | 승인 후 |

전후 상태는 요청 DTO 가 아니라 DB 에 쓰인 값이다. 승인 여부와 다른 값이 함께 바뀌면 UPDATE 1건이다(승인 이력과 겹치지 않는다).
삭제 후 다시 등록은 서로 다른 객체의 DELETE 와 CREATE 다(관계는 수정 API 가 없다).

## 4. 변경 그룹

**쓰기 트랜잭션 하나 = 그룹 하나.** 화면의 요청 한 번이 서비스의 트랜잭션 하나다(컬럼 일괄 저장, 엑셀 업로드 1회, 여러 건 승인 포함).

- 그룹 ID 는 커밋 직전에 만드는 UUID 다.
- 변경 모음은 트랜잭션 동기화에 묶여 있다. 직접 만든 `ThreadLocal` 이 없어서 예외가 나도, 요청이 끝나도 따로 지울 것이 없고 다음 요청으로 새지 않는다. 중첩된 새 트랜잭션(`REQUIRES_NEW`)은 자기 그룹을 갖는다.
- 한 요청이 트랜잭션을 여러 번 쓰는 서비스가 생기면 그룹이 나뉜다(지금 물리 모델에는 없다).
- 부분 성공 정책은 바꾸지 않았다. 컬럼 일괄 저장은 원래 전부 성공하거나 전부 거절한다.

## 5. 자동 동기화

컬럼의 참조 테이블명으로 만드는 관계(`REF_COLUMN`)는 커밋 직전에 자동으로 맞춰진다. 그 결과로 **실제로 바뀐 관계**가 원인 변경과 같은 그룹에 남는다.

- 출처 `AUTO_SYNC` : 대상이 `REF_COLUMN` 관계이면 자동 동기화다(사용자가 직접 바꿀 수 없는 관계다). 그 밖은 `USER`.
- 원인 : 관계 JSON 의 `derivedColumnId`(관계를 만든 컬럼) + 같은 그룹의 컬럼·테이블 이력.
- 동기화가 이력 기록보다 먼저 실행되도록 순서를 고정했다(`ReferenceSyncBoundary` 의 `getOrder`).

| 변경 | 같은 그룹에 남는 것 |
|---|---|
| 컬럼에 참조 테이블명 지정 | 컬럼 CREATE/UPDATE(USER) + 관계 CREATE(AUTO_SYNC) |
| 참조 테이블명 제거·대상 PK 가 사라짐 | 컬럼 UPDATE + 관계 DELETE(AUTO_SYNC) |
| 원본 테이블명 변경 | 테이블 UPDATE + 소속 컬럼 UPDATE(`tableName`) + 관계 UPDATE(이름, AUTO_SYNC) |
| 대상 테이블명 변경 | 테이블 UPDATE + 소속 컬럼 UPDATE + 참조하던 다른 테이블 컬럼 UPDATE(`refTableName`). 관계는 대상 ID·컬럼이 같아 이력 없음 |
| 엑셀 업로드 | 남은 테이블·컬럼 CREATE + 끝에 남은 관계 CREATE. 앞 청크에서 만들었다가 뒤 청크에서 정리된 관계는 없음 |

테이블명 변경으로 따라 바뀐 컬럼(`tableName`·`refTableName`)은 서비스가 직접 고친 값이라 출처가 `USER` 다. 같은 그룹의 테이블 이력으로 원인을 알 수 있다.

## 6. 조회 API (`/api/modelHistory`, 모두 GET · VIEWER 이상)

| API | 내용 |
|---|---|
| `GET /data?page&size&targetType&targetId&action&userId&from&to&changeGroupId` | 로그인 프로젝트의 이력. 변경 일시·이력 ID 내림차순(같은 시각이어도 순서가 고정). `from`·`to` 는 `yyyy-MM-dd`, 종료일 포함. 응답은 그리드와 같은 `{data, recordsTotal, recordsFiltered}` |
| `GET /data?targetType=…&targetId=…` | **객체별 이력** (같은 API 의 조건). 삭제된 객체도 조회된다 — 현재 모델에 있는지 확인하지 않는다 |
| `GET /group/{changeGroupId}` | 한 작업의 이력, 기록된 순서(ID 오름차순) |
| `GET /{id}` | 상세 : 요약 + `before`·`after` JSON |

- 목록은 요약만 준다 : ID, 프로젝트, 그룹, 대상(종류·ID·이름), 작업, 출처, 사용자, 시각, **달라진 필드 이름**(`changedFields`, 생성·삭제는 빈 목록). 전후 JSON 은 상세에서만.
- 모르는 `targetType`·`action` 은 400 이다(조건을 조용히 버리면 전체가 조회된다).
- 수정·삭제·임의 등록 API 는 없다.

### 권한·격리

- 역할은 VIEWER 부터. NOT_APPROVE 는 403.
- 모든 조회가 **이력에 저장된 프로젝트 = 로그인한 프로젝트** 조건을 건다. 다른 프로젝트의 이력 ID·대상 ID·그룹 ID 를 알아도 나오지 않는다(상세는 400 "대상을 찾을 수 없습니다", 목록·그룹은 빈 결과).
- 프로젝트 멤버가 아니게 되거나 역할이 바뀐 세션은 기존 장치(`ProjectAccessInterceptor`, 역할 변경 시 세션 삭제)가 막는다.
- 프로젝트를 삭제해도 이력 행은 남지만 그 프로젝트로 로그인할 수 없으므로 조회되지 않는다.

## 9. 남은 문제·결정 사항

1. **이력 보관 기간·용량 정책이 없다.** 지금은 계속 쌓인다. 엑셀 업로드는 행 수만큼 이력이 생긴다.
2. **프로젝트를 삭제해도 이력은 남는다.** 지울지 보관할지 정해야 한다.
3. 용어·스키마는 ID 만 남는다. 용어를 지우면(컬럼이 쓰는 용어는 지울 수 없다) 예전 이력의 용어 이름을 알 수 없다.
4. 기존 데이터는 이력이 없다. 첫 변경의 `before` 가 그 객체의 가장 오래된 기록이다.
5. `USER_ID` 는 로그인 아이디 문자열이다. 계정을 지워도 이력의 아이디는 그대로 남는다.
6. 스키마(`TB_SCHM`)·공통 컬럼 세트의 변경은 대상이 아니다(지시서의 5종만). 테이블의 스키마 이동은 테이블 이력의 `schemaId` 로 남는다.

## 11. M-9 2차 (2026-11-12)

### 11.1 대상 확장 — 논리 모델·매핑

기록 구조는 그대로다. 서비스 코드는 손대지 않고 `ModelChangeRecorder` 의 대상 목록에 엔티티와 필드만 더했다. DB 변경·마이그레이션은 없다(`TRGT_TYPE_CD` 는 20자 문자열이고 새 코드도 그 안에 든다).

| 대상 코드 | 엔티티 | 필드 (JSON 키) |
|---|---|---|
| `LOGICAL_MODEL` | 논리 모델 | `modelName` `modelDescription` |
| `LOGICAL_ENTITY` | 엔터티 | `modelId`·`modelName` `entityName` `entityDescription` `isApproval` |
| `LOGICAL_ATTRIBUTE` | 속성 | `entityId`·`entityName` `attributeName` `attributeDescription` `dataType` `isRequired` `sortOrder` `standardTermId`·`standardTermName` |
| `LOGICAL_IDENTIFIER` | 식별자 | `entityId`·`entityName` `identifierName` `isPrimary` `attributes[{attributeId, attributeName, sortOrder}]` |
| `LOGICAL_RELATIONSHIP` | 관계 | `modelId`·`modelName` `sourceEntityId`·`sourceEntityName` `targetEntityId`·`targetEntityName` `relationshipName` `relationshipDescription` `isIdentifying` `sourceMin` `sourceMax` `targetMin` `targetMax` `isApproval` |
| `TABLE_MAPPING` | 엔터티 ↔ 테이블 매핑 | `entityId`·`entityName` `tableId`·`tableName` |
| `COLUMN_MAPPING` | 속성 ↔ 컬럼 매핑 | `mappingId` `attributeId`·`attributeName` `columnId`·`columnName` |

- 지시서의 `LOGICAL_TABLE` 은 이 프로젝트의 용어대로 `LOGICAL_ENTITY` 로 했다. 논리 모델을 이루는 모델·식별자·관계도 같은 방식이라 함께 넣었다(빠지면 논리 모델 이력에 구멍이 난다).
- 승인은 엔터티·관계에 있다 → 승인 여부만 바뀌면 `APPROVE`·`REVOKE` (물리 모델과 같은 규칙). 속성·식별자·모델·매핑에는 승인이 없다.
- 속성·식별자·속성 매핑은 프로젝트 ID 컬럼이 없다 → **부모(엔터티·엔터티 매핑)의 프로젝트**로 기록한다. 같은 트랜잭션에서 부모가 지워졌어도 지워지기 전 값에서 가져온다.
- 식별자의 구성 속성은 식별자 이력의 `attributes` 에 순서대로 들어간다(관계의 컬럼 쌍과 같은 방식). 구성이 그대로면 이력이 없다.
- 매핑 : 대상 테이블·컬럼을 바꾸면 `UPDATE`(전후에 이전 대상과 새 대상), 해제는 `DELETE`. 같은 대상으로 다시 저장하면 이력이 없다.
- 대상 이름(`TRGT_NM`) : 속성 `엔터티.속성`, 식별자 `엔터티.식별자`, 관계는 관계명(없으면 `출발 → 도착`), 매핑 `엔터티 ↔ 테이블`·`속성 ↔ 컬럼`.

**변경 경로** : 논리 모델 관리 화면과 논리 ERD 는 같은 `LogicalModelService` 를, 매핑 화면은 `ModelMappingService` 를 쓴다. 모두 엔티티로 저장하고 JPQL·네이티브 일괄 변경은 없다.

| 지시서 항목 | 실제 |
|---|---|
| 엔터티 삭제 시 속성 삭제 | 속성·식별자가 같은 그룹에 `DELETE` 로 남는다 |
| 논리 모델 복사·자동 생성·일괄 변경 | **그런 기능이 없다** (예제는 마이그레이션 SQL 이 넣는다 — 이력 없음) |
| 자동 매핑 | **없다.** 매핑은 사용자가 등록한 것만 있다(추천 화면은 조회 전용) → 매핑 이력의 출처는 모두 `USER` 다. `AUTO_SYNC` 는 여전히 참조 테이블명으로 만든 물리 관계뿐이다 |
| 모델 삭제에 따른 매핑 제거 | **일어나지 않는다.** 매핑된 엔터티·속성·테이블·컬럼은 삭제가 거절된다(매핑을 먼저 해제) → 거절된 요청은 이력이 없다 |
| 논리·물리 동시 변경 | 한 트랜잭션이면 한 그룹 |

### 11.2 이름 스냅샷

1차 이력은 연관 대상을 ID 로만 남겼다. 2차부터 **새 이력**에는 그 시점의 이름을 `<필드>Name` 으로 함께 남긴다.

| 대상 | 이름 |
|---|---|
| 스키마 | `schemaName` |
| 표준 용어 | `standardTermsName`(컬럼) · `standardTermName`(속성) |
| 물리 테이블 | `tableInfoName` · `sourceTableName` · `targetTableName` · `tableName`(매핑) |
| 물리 컬럼 | 관계·인덱스·제약조건의 `columns[]` 안 `sourceColumnName` · `targetColumnName` · `columnName`, 매핑의 `columnName` |
| 논리 모델·엔터티·속성 | `modelName` · `entityName` · `sourceEntityName` · `targetEntityName` · `attributeName` |

- 표준 도메인은 컬럼·속성이 직접 참조하지 않는다(용어를 거친다) → 남기지 않았다. 용어 이름으로 찾는다.
- 이름은 **커밋 직전에 대상 종류마다 조회 한 번**으로 채운다(500개씩). 이벤트 안에서 프록시를 읽지 않는다. 같은 트랜잭션에서 지워진 대상은 지워지기 전 이름을 쓴다.
- 전후가 같은 대상이면 같은 이름이 들어가므로 이름 때문에 변경으로 잡히지 않는다. 대상의 이름만 바뀐 경우(테이블명 변경)는 그 대상 자신의 이력으로 남는다.
- **기존 이력은 고치지 않았다.** 이름이 없는 예전 이력은 화면에서 같은 항목 이름 아래에 `#ID` 로 보인다. 지금의 이름을 찾아 넣지 않는다.
- JSON 은 여전히 버전 필드가 없다. 2차의 변화는 키 추가뿐이라 예전 이력과 함께 읽힌다.

### 11.3 조회 화면 (`/modelHistory`, `lexorma-web/src/features/history`)

- **메뉴** : `데이터 품질 관리 > 모델 변경 이력` (`model-history`, VIEWER). 지시서의 "데이터 관리" 그룹은 없어서, 조회 전용 화면이 모여 있는 기존 그룹에 넣었다.
- **목록** : 변경 일시 · 변경 사용자 · 대상 유형 · 변경 대상 · 작업 · 변경 항목 · 출처 · 변경 그룹. 서버 페이징, 정렬은 서버 고정(변경 일시·이력 ID 내림차순)이라 컬럼 정렬은 없다.
- **조건** : 대상 유형, 작업, 기간(시작일~종료일), 변경 사용자 아이디, 변경 그룹(목록의 그룹 버튼), 객체(상세의 [이 객체의 이력]). 조건이 바뀌면 첫 쪽부터 다시 조회한다. API 는 1차 그대로다(추가한 조건 없음).
- **객체별 이력** : `?targetType=…&targetId=…` 로 열 수 있다. 테이블 상세와 엔터티 상세에 [변경 이력] 버튼을 두었다. 삭제된 객체도 조회된다.
- **상세(비교)** : 행을 누르면 대화상자가 열린다.
  - 생성 = 변경 후만, 삭제 = 변경 전만, 수정·승인·승인취소 = 변경 전·후 두 칸.
  - 수정은 **달라진 항목만** 먼저 보이고 [전체 항목 보기] 로 모두 본다. 달라진 값은 배경색과 함께 변경 전에 취소선을 둔다(색만으로 구분하지 않는다).
  - 연관 대상은 `이름 (#ID)`, 이름이 없으면 `#ID`. 배열(컬럼 쌍·컬럼 구성·구성 속성)은 한 줄에 한 항목, 중첩 객체는 `키 값` 으로 풀어 쓴다.
  - 순서 : 관계의 컬럼 쌍·인덱스 컬럼·식별자의 구성 속성은 순서가 뜻이 있다. **UNIQUE·CHECK 제약조건의 컬럼은 집합**으로 비교한다(서버도 집합으로 본다).
  - 모르는 필드(예전·나중의 필드)는 원본 키와 값 그대로 나온다.
- **변경 그룹** : 상세 아래에 같은 작업의 변경이 기록된 순서로 나오고, 누르면 그 변경으로 바뀐다. 그룹은 트랜잭션 단위다.
- 화면에는 변경 기능이 없다. 영어·다크 모드를 지원한다.

### 11.6 보관·프로젝트 삭제 (정책은 그대로, 분석만)

- 자동 삭제·보관 기한·수정·삭제 없음. 그대로 둔다.

- 결정할 것 : 지운 프로젝트의 이력을 지울지, 관리자용 조회 경로를 둘지. 지금 지우는 기능을 넣으면 "이력은 지울 수 없다" 는 원칙과 부딪친다.

## 12. M-9 3차 — 모델 버전 (2026-11-12)

변경 이력이 "무엇이 언제 바뀌었나" 의 기록이라면, 모델 버전은 "그 시점의 모델이 어땠나" 의 보존이다. 둘은 다른 테이블에 따로 저장하고 서로 만들어 내지 않는다.

| | 변경 이력 (1·2차) | 모델 버전 (3차) |
|---|---|---|
| 만들어지는 때 | 모델이 바뀔 때마다 (서버가 자동으로) | 사용자가 [버전 생성] 을 누를 때만 |
| 담는 것 | 바뀐 객체의 전후 상태 | 프로젝트 모델 전체 |
| 테이블 | `TB_MDL_CHG_HSTRY` | `TB_MDL_VER` |
| 수정·삭제 | 없음 | 없음 |

### 12.1 분석 — 기존 구조와 로드맵

- **M-10 과의 관계** : 로드맵의 M-10 ③ "모델 버전 A ↔ B 비교" 는 "후속, M-9" 로 적혀 있어 이번 범위와 겹친다. 차이 계산과 목록·전후 비교는 여기서 구현했고, M-10 의 "ERD 안의 변경 표시" 만 남겼다(로드맵 표에 반영).
- **기존 이력의 재사용** : 이력 테이블을 버전 저장소로 쓰지 않는다. 대신 이력을 만드는 코드(`ModelChangeRecorder`)의 **필드 목록과 상태 모양**을 그대로 쓴다 — 객체의 상태 JSON 이 이력의 "변경 후" 와 같아서, 이력에 남는 값과 버전에 담기는 값이 어긋나지 않고 화면의 전후 비교 표도 같이 쓴다.
- **이력에서 버전을 재구성하지 않는 이유** : 이력은 기록을 시작한 뒤의 변경만 있고(소급 없음) JPQL 일괄 변경은 남지 않는다. 처음 상태를 알 수 없어 재구성한 모델을 믿을 수 없다.
- **마이그레이션** : 지시서는 "새 마이그레이션 추가" 였지만, 직전에 마이그레이션을 `V0`(스키마)·`V1`(초기 데이터) 두 파일로 합치고 그렇게 관리하기로 했으므로 **V0 에 테이블·COMMENT 를, V1 에 예제 행을 넣었다** (파일은 그대로 2개). 사용 중인 DB 가 없다는 전제다.

### 12.2 저장 방식 — JSON 전체 스냅샷

| 방식 | 판단 |
|---|---|
| **JSON 전체 스냅샷 (채택)** | 한 행에 그 시점의 모델이 통째로 있다. 일부만 저장될 수 없고, 현재 모델 테이블이 바뀌어도(컬럼 추가 등) 옛 버전은 그대로 읽힌다. H2·PostgreSQL 모두 `TEXT` 로 같다. 비교는 메모리에서 한다 |
| 버전별 정규화 테이블 | 모델 테이블 15개를 버전용으로 한 벌 더 두어야 하고, 모델에 필드가 늘 때마다 두 곳을 고쳐야 한다. SQL 로 비교할 수 있다는 장점은 지금 필요하지 않다 |
| 변경 이력에서 재구성 | 12.1 의 이유로 정확하지 않다 |

`TB_MDL_VER` : `MDL_VER_SN`, `PRJ_SN`, `VER_NM`(100), `VER_EXPLN`(1000), `FRMT_VER_NO`(내용 형식 번호, 지금 1), `MDL_CNT_CN`(대상 종류별 객체 수 JSON — 목록은 이것만 읽는다), `MDL_CN`(모델 내용 JSON), `RGTR_ID`, `REG_DT`. `UK_MDL_VER_01 (PRJ_SN, VER_NM)`. 이력 테이블처럼 모델 테이블로 가는 FK 는 없다.

**담는 범위** (`MDL_CN` = 대상 종류 → `[{id, name, state}]`)

| 구분 | 대상 종류 | 내용 |
|---|---|---|
| 스키마 | `SCHEMA` | 이름, 설명, 기본 여부 (이력 대상은 아니지만 모델 구조라 담는다) |
| 물리 | `PHYSICAL_TABLE`, `PHYSICAL_COLUMN`, `PHYSICAL_RELATION`, `PHYSICAL_INDEX`, `PHYSICAL_CONSTRAINT` | 테이블(스키마, 설명), 컬럼(타입·길이·정밀도·NULL·기본값·PK·고유·설명·표준 용어), FK(복합 컬럼 쌍 순서대로), 인덱스(컬럼 순서), UNIQUE·CHECK(컬럼, 조건식) |
| 논리 | `LOGICAL_MODEL`, `LOGICAL_ENTITY`, `LOGICAL_ATTRIBUTE`, `LOGICAL_IDENTIFIER`, `LOGICAL_RELATIONSHIP` | 모델·엔터티·속성·식별자(구성 속성)·관계(양쪽 최소·최대) |
| 매핑 | `TABLE_MAPPING`, `COLUMN_MAPPING` | 엔터티 ↔ 테이블, 속성 ↔ 컬럼 |

- **데이터 표준** : 표준 단어·도메인·용어 원본은 담지 않는다(프로젝트 전체에서 따로 관리되는 데이터다). 컬럼·속성이 참조하는 표준 용어는 ID 와 **그 시점의 이름**으로 남는다. 컬럼의 타입·길이는 컬럼 자신의 값이라 도메인이 나중에 바뀌어도 버전은 그대로다.
- 담지 않는 것 : ERD 배치, 공통 컬럼 세트, 승인 이력, 감사 컬럼(등록·수정 일시).

### 12.3 생성

- `POST /api/modelVersion` `{versionName, description}`. 버전명은 앞뒤 공백을 빼고 1~100자, 형식은 정하지 않는다. 설명은 1,000자까지.
- **일관된 시점** : 생성 트랜잭션을 `REPEATABLE_READ` 로 연다. 모델을 읽는 여러 조회가 같은 시점을 보므로, 만드는 동안 커밋된 다른 사용자의 변경이 일부만 섞이지 않는다(모델 쓰기를 막지는 않는다).
- **부분 저장 없음** : 버전 정보와 내용이 한 행이다. 실패하면 트랜잭션이 롤백되어 아무것도 남지 않는다.
- **이름 중복** : 프로젝트 행을 잠그고 검사한다(논리 모델명과 같은 방식). 마지막 보루는 UNIQUE 인덱스다. 동시에 같은 이름으로 만들면 하나만 저장된다.
- 버전 생성은 모델 변경이 아니라 **변경 이력에 남지 않는다**. 누가 언제 만들었는지는 버전 자체(`RGTR_ID`, `REG_DT`)와 요청 로그에 있다.
- 자동 생성은 없다. 기존 모델의 "첫 버전" 도 만들지 않는다.

### 12.4 조회와 불변성

| API | 권한 | 내용 |
|---|---|---|
| `GET /api/modelVersion/data?page&size` | VIEWER | 목록, 최신 순. 모델 내용은 읽지 않고 객체 수만 |
| `GET /api/modelVersion/{id}` | VIEWER | 버전 정보 |
| `GET /api/modelVersion/{id}/snapshot` | VIEWER | 저장된 모델 내용 그대로 |
| `GET /api/modelVersion/compare?baseId&targetId` | VIEWER | 비교. `targetId` 가 없으면 현재 모델 |
| `POST /api/modelVersion` | USER | 생성 (모델 변경 API 와 같은 역할) |

- 다른 프로젝트의 버전은 ID 를 알아도 "없음" 이다(이력과 같다).
- **수정·삭제·복원 API 가 없다.** 엔티티는 `@Immutable` 이라 코드에서 값을 바꿔도 UPDATE 가 나가지 않는다. 조회는 지금의 모델을 다시 읽지 않고 저장된 JSON 을 그대로 준다.
- 화면의 "저장된 버전" 은 조회만 한다 : 대상 종류를 고르고 이름으로 찾아 객체를 누르면 그 시점의 값이 나온다. 입력·저장 버튼이 없다.

### 12.5 비교

- **대상** : 버전 ↔ 버전, 버전 ↔ 현재 모델. 같은 프로젝트 안에서만(다른 프로젝트의 버전은 조회되지 않는다).
- **객체 식별 = 내부 ID.** 대상 종류와 ID 가 같으면 같은 객체다.
  - 이름을 바꾼 테이블·컬럼·엔터티 → `MODIFIED` (이름 필드가 달라진 것으로 나온다). ID 가 유지되므로 확실하다.
  - 지우고 같은 이름으로 다시 만든 객체 → `REMOVED` + `ADDED`. ID 가 다르므로 같은 객체로 **보지 않는다**(이름이 같다고 짝짓지 않는다).
  - 그래서 "이름 변경 후보" 같은 추정이 없다. 추정이 필요한 것은 ID 가 없는 원본 DB 와의 비교(M-10 ①②)다.
- **판정** : `ADDED`(대상에만 있음), `REMOVED`(기준에만 있음), `MODIFIED`(값이 다른 필드가 있음), `UNCHANGED`. 응답에는 달라진 객체만 변경 전후 상태와 함께 들어 있고, 건수는 전체·대상 종류별로 준다.
- **변경으로 보지 않는 것** : JSON 의 필드 순서, 참조 대상의 이름 스냅샷(`<필드>Name` — 테이블 이름이 바뀌면 그 테이블만 수정이고, 그 테이블을 가리키는 관계·매핑은 수정이 아니다), UNIQUE·CHECK 제약조건의 컬럼 순서(이력과 같은 기준). FK·인덱스·식별자의 컬럼 순서는 뜻이 있어 변경이다.
- 승인 여부(`isApproval`)는 모델 상태의 일부라 달라지면 수정으로 나온다.
- 현재 모델과 비교할 때도 현재 상태를 저장할 때와 같은 JSON 으로 바꾼 뒤 비교한다(숫자 표현 차이로 변경이 생기지 않는다).

### 12.6 화면 (`/modelVersion`, `lexorma-web/src/features/version`)

- 메뉴 : 데이터 품질 관리 > **모델 버전 관리** (모델 변경 이력 바로 아래, 독립 메뉴). 이력 화면의 탭으로 넣지 않은 것은 조건·목록·권한 버튼이 서로 달라서다.
- 목록(버전명, 설명, 모델 규모, 생성자, 생성 일시) · [버전 생성](USER 이상, `canView('model-version-create')`) · [버전 비교].
- 저장된 버전 : 버전 정보 + 대상 종류별 객체 목록 + 객체의 값. [이 버전을 기준으로 비교].
- 비교 : 기준 버전 → 대상(현재 모델 또는 다른 버전), 추가·삭제·수정·변경 없음 건수, 대상 유형·변경 유형·이름 조건, 달라진 객체 목록, 누르면 변경 전후. 전후 표는 변경 이력의 표(`DiffTable`, `diffRows`)를 같이 쓴다.
- 목록은 100건씩 그리고 [더 보기] 로 잇는다.

### 12.9 하지 않은 것과 남은 것

- **과거 버전의 ERD 표시** : 하지 않았다. 논리·물리 ERD 화면은 조회·배치 저장·편집이 한 컴포넌트(각 800줄대)에 묶여 있어, 스냅샷을 그리려면 읽기 전용 캔버스를 먼저 떼어 내야 한다. 과거 버전은 목록과 객체 상세로 본다.
- 버전 삭제·수정, 복원, 병합, 자동 생성, 보관 기간 : 범위 밖(지시).
- **큰 모델** : 내용 조회와 비교가 버전 전체를 메모리에 올린다. 컬럼 5만 개 규모에서 생성 10초, [저장된 버전] 화면이 48 MB 를 받는다. 이 규모를 쓰게 되면 내용 조회를 대상 종류별로 나누고 비교 응답에 쪽 나누기를 넣어야 한다.
- **프로젝트 삭제** : 이력과 같이 버전도 남는다(정책 미정, 11.6 과 같은 문제).
- 버전 사이에 있었던 변경 이력을 묶어 보여 주는 연결은 만들지 않았다. 버전의 `REG_DT` 와 이력의 `CHG_DT` 로 구간을 구할 수 있어 나중에 붙일 수 있다.
- 스냅샷에 담기는 필드는 이력의 필드 목록을 따른다. 모델에 필드를 더하면 `ModelChangeRecorder` 의 목록에 넣어야 이력과 새 버전에 모두 들어가고, 옛 버전에는 그 필드가 없어 비교에서 "추가된 값" 으로 보인다.

## 13. M-9 최종 보완과 완료 (2026-11-12)

### 13.1 스냅샷 필드 완전성

이력과 버전에 담는 필드는 `ModelChangeRecorder` 의 목록 하나다(`recordedFields()` 로 꺼낸다). 엔티티에 속성을 더하고 이 목록에 넣지 않으면 이력에도 버전에도 조용히 빠진다 — 이것을 테스트가 잡게 했다.

- **`ModelSnapshotFieldCoverageTest`** : 대상 엔티티 17개(스키마 1, 이력 대상 12, 자식 행 4)의 JPA 영속 속성을 모두 읽어, 속성마다 ① 담는 필드이거나 ② 사유를 적은 제외 속성인지 확인한다. 어느 쪽에도 없으면 실패하고, 메시지가 "필드 목록에 넣거나 사유를 적으라" 고 알려 준다. 거꾸로 엔티티에 없는 필드·제외 속성, 양쪽에 다 있는 속성도 실패한다(낡은 예외가 남지 않는다).
- **제외 속성과 사유** (테스트 코드에 있다)

  | 속성 | 사유 |
  |---|---|
  | `id` | 객체의 `id` 로 따로 담는다 |
  | `projectId` | 버전·이력 자체가 프로젝트 단위다 |
  | 등록·수정 일시, 등록·수정자 (`BaseEntity`) | 모델 구조가 아니라 운영 정보다 |
  | 자식 행의 부모 연관 (`relation`, `tableIndex`, `tableConstraint`, `identifier`) | 자식 행은 부모 객체의 배열로 담긴다 |
  | 반대쪽 컬렉션 (`TableInfo.columns`, 관계·인덱스·제약조건의 `columns`, `LogicalEntity.attributes`·`identifiers`, 식별자의 `attributes`) | 자식 객체가 자기 쪽에서 담는다 |

- **결과 : 빠진 속성은 없었다.** 처음 실행에서 걸린 것은 위 반대쪽 컬렉션 3개뿐이고 모두 의도한 제외다. 필드 목록은 고치지 않았다.
- **값 보존·정합성** (`ModelVersionIntegrationTest.historyAndVersionAgree`) : 대표 모델(복합 FK·복합 인덱스·UNIQUE·CHECK·식별자·논리 관계·매핑 포함)의 객체 21개마다 **마지막 변경 이력의 "변경 후" 와 버전에 담긴 상태가 JSON 전체로 같은지** 비교한다. 이어서 버전을 만든 뒤 컬럼의 타입·길이·정밀도·소수 자릿수·NULL·기본값·PK 를 바꾸고, 버전에는 만들 때의 값이 남아 있고 비교에는 바뀐 필드만 나오는지 본다.
- 한계 : 테스트는 "엔티티의 속성" 을 본다. 새 **엔티티**(예: 새 종류의 모델 객체)를 만들고 이력·버전 대상에 넣지 않는 것은 잡지 못한다 — 대상 목록(17개)은 사람이 정한다.

### 13.2 화면 최종 확인 (헤드리스 Chrome, PostgreSQL)

- 확인한 화면 : 모델 버전 목록, 버전 생성, 저장된 버전, 버전 비교, 모델 변경 이력 목록·상세(공용 비교 표).
- **고친 것 2가지**
  1. 대화상자 안의 이름 검색창이 3차에서 넣은 폭(220px)이 아니라 줄 전체(768~1,168px)로 늘어나 있었다 — 검색창 기본 규칙의 `flex` 가 이겼다. `flex: 0 0 220px` 로 고쳤다.
  2. 긴 버전명(100자)·설명(1,000자)이 목록의 행을 520~667px 로 늘렸다. 목록에서는 두 줄까지만 보이고(전체는 `title` 과 상세), 상세의 설명은 96px 안에서 스크롤한다.
- 그대로 맞았던 것 : 객체·변경 목록 높이(화면 높이의 52%, 안에서 스크롤), 100건씩 표시와 [더 보기], 빈 상태 문구(버전 없음·해당 유형 없음·조건에 맞는 객체 없음), 1,024px·768px 폭에서 가로 넘침 없음, 변경 이력 화면의 필터·상세.
- 권한 : VIEWER 는 목록·상세·비교 가능, [버전 생성] 버튼 없음, API 직접 호출 403. 다른 프로젝트의 버전은 조회되지 않는다(기존 통합 테스트).

### 13.3 프로젝트 삭제와 이력·버전 (분석만, 정책은 정하지 않았다)

> 이후 결정·구현됨 : 영구 삭제 시 프로젝트 데이터를 모두 지운다 (권고 A). 아래는 당시의 분석이고, 지금의 동작은 [project-deletion.md](project-deletion.md) 에 있다. 버전을 찾지 못했을 때의 오류 문구도 거기서 고쳤다.

- **지금의 동작** : 프로젝트 삭제(`ProjectManageServiceImpl.deleteProject`)는 프로젝트 행과 멤버 행만 지운다. `ProjectDeletedEvent` 를 발행하지만 듣는 곳이 없다. `PRJ_SN` 을 가진 테이블 22개 중 프로젝트로 FK 가 걸린 것은 멤버 테이블뿐이라 삭제를 막는 것도, 따라 지워지는 것도 없다.
- **그래서 남는 것** : 이력·버전만이 아니라 그 프로젝트의 **모든 데이터**(스키마, 테이블·컬럼, 데이터 사전, 논리 모델, 매핑, 공지 등)가 남는다. 실제로 지워 본 결과 프로젝트 0건·멤버 0건, 스키마 1건·버전 2건이 그대로였다.
- **접근** : 남은 데이터는 어디에서도 조회되지 않는다. 모든 조회가 로그인한 프로젝트 ID 로 거르고, 지워진 프로젝트로는 로그인할 수 없으며(`PROJECT_ACCESS_DENIED`), 다른 프로젝트에서 ID 를 알아도 "없음" 이다. 프로젝트 ID 는 시퀀스라 다시 쓰이지 않으므로 새 프로젝트가 옛 데이터를 물려받지도 않는다. **보안 결함은 아니고, 지울 방법이 없는 데이터가 쌓이는 문제다.**
- **정책 비교**

  | 방식 | 장점 | 단점 |
  |---|---|---|
  | A. 함께 삭제 | 구조가 단순하고 고아 데이터가 없다. `ProjectDeletedEvent` 리스너로 모듈 의존 방향을 지키며 구현할 수 있다 | 지운 프로젝트의 이력·버전을 되살릴 수 없다 |
  | B. 삭제 후 보존 (지금) | 아무것도 하지 않아도 된다 | 볼 수도 지울 수도 없는 데이터가 남는다. 보존의 이득이 없다 |
  | C. 논리 삭제 | 되살리기·감사 조회가 가능하다 | 모든 조회·권한·로그인에 "삭제된 프로젝트" 조건이 들어간다. 지금 있는 "비활성화" 와 역할이 겹친다 |

- **권고 : A.** 운영 사용자가 없고 감사 보존 요구도 없다. 되돌릴 여지는 이미 있는 **프로젝트 비활성화**가 맡고, 삭제는 정말 지우는 것으로 두는 편이 단순하다. 다만 이력·버전만이 아니라 프로젝트 데이터 전체에 같은 결정을 적용해야 하므로 M-9 가 아니라 별도 과제다.
- 정하려면 필요한 것 : ① 삭제 전에 내보내기(백업)를 요구할지 ② 지울 범위(모델 데이터 전체인지) ③ 멤버가 관리자뿐일 때만 삭제된다는 지금의 조건을 유지할지.
