# M-8 1차·2차. ERD 편집 기반과 논리 ERD 편집 — 설계 결정과 구현 기록

> [데이터 모델링 로드맵](data-modeling-roadmap.md) M-8 중 **1차(편집 기반, 논리 ERD 의 엔터티·속성 편집)** 의 기록이다. 작성일 2026-11-11.
> **2차(논리 관계·식별자 편집)** 는 6장부터다. 1~5장은 1차 시점의 기록이다.
> **백엔드·DB 변경 없음** (1차·2차 모두 새 API·마이그레이션 없음, Flyway V0~V4 그대로). 3차(물리 ERD 편집)는 하지 않았다 — **M-8 전체는 진행 중이다** (로드맵의 M-8 완료 조건은 물리 ERD 편집·DDL 일치이고 3차에서 충족한다).

## 1. 기존 구조 분석과 결정

| 확인 항목 | 결과 → 결정 |
|---|---|
| 로드맵 M-8 | 로드맵의 M-8 은 **물리** 모델(테이블·컬럼·관계)을 ERD 에서 편집하는 단계로 적혀 있고, 완료 조건도 "테이블·컬럼 관리 화면·DDL 과 일치"다. 논리 ERD 편집은 언급이 없다 (M-6 이 논리 ERD 를 조회용으로 만들었다) → 이번 지시서는 M-8 을 **1차 논리 엔터티·속성 → 2차 논리 관계·식별자 → 3차 물리** 로 넓혀 나눈 것이다. 충돌은 아니고 범위 확장이라 진행했고, 로드맵에 단계를 적었다. **로드맵의 M-8 완료 조건(물리)은 3차에서 충족한다** |
| 논리 ERD (M-6) | React Flow + ELK. 조회 결과가 바뀌면 노드를 다시 만들되 **위치는 화면이 들고 있는 `positions` 에서 가져온다** (저장된 배치 → 끌어 옮긴 위치). 위치가 없는 엔터티만 기존 배치 오른쪽에 자동 배치. `deleteKeyCode={null}`·`nodesConnectable={false}` 로 키보드 삭제·연결이 이미 막혀 있다 → **편집 뒤 "다시 조회"만 하면 기존 노드 위치가 유지된다.** 새로 만든 것은 없다 |
| 논리 모델 API (M-6) | 엔터티·속성 CRUD, 속성 순서(`PUT /entity/{id}/attribute/order`), 표준 용어 연결(속성 저장의 `termId`), 승인, 삭제 제한(관계·식별자·매핑)이 모두 있다 → **새 API 0개** |
| 엔터티 상세 대화상자 | 논리 모델 관리와 논리 ERD 가 이미 함께 쓰고, 속성·식별자·기본 정보 편집과 삭제·승인이 들어 있다. 변경 권한이 있으면 ERD 에서도 편집 버튼이 보였다 → 그대로 재사용하고 **조회 모드에서는 읽기 전용**(`readOnly`)으로 연다 |
| 폼 | 엔터티 등록 폼(`EntityForm`)은 논리 모델 관리 파일 안에, 속성 폼(`AttributeForm`, 표준 용어 검색·연결·해제 포함)은 엔터티 상세 파일 안에 있었다 → 둘 다 **export 해서 ERD 가 같은 컴포넌트를 쓴다** (복사하지 않았다) |
| 배치 저장 (M-6 2차) | `PUT /model/{id}/erd/layout` : 사용자 × 모델 1건, version 으로 충돌 감지, 보낸 좌표를 기존 좌표에 합치고, 지워진 엔터티의 좌표는 조회에서 뺀다 → 그대로 쓴다 |
| 물리 ERD (M-2·M-3) | 같은 노드 스타일·배치 저장 구조·"저장하지 않은 배치" 확인. 테이블·컬럼 편집은 테이블 상세·컬럼 일괄 편집 대화상자를 연다 → 3차에서 **모드 전환과 새 노드 위치 계산**을 같이 쓸 수 있게 `features/erd/editing.tsx` 로 뺐다. 두 ERD 화면을 하나로 합치지는 않았다 |

## 2. 편집 정책

### 2.1 조회 모드 · 편집 모드

| | 조회 모드 (기본) | 편집 모드 |
|---|---|---|
| 들어갈 수 있는 사람 | ERD 를 볼 수 있는 모두 (VIEWER 이상) | 논리 모델 변경 권한(`logical-model-edit` = USER 이상). 권한이 없으면 전환 버튼이 없다 |
| 탐색·배치 | 엔터티·관계 선택, 노드 이동, 자동 배치, 전체 보기, 배치 저장·불러오기, 다른 화면 이동 | 같다 |
| 엔터티 상세 | 읽기 전용 (승인·승인취소 버튼은 승인 권한자에게 그대로 보인다 — 편집이 아니라 승인 절차다) | 편집 가능 (속성·식별자·기본 정보·삭제) |
| 모델 변경 | 없음 | [엔터티 추가], 패널의 [엔터티 수정]·[속성 추가]·[엔터티 삭제], 속성마다 [↑]·[↓]·[수정]·[삭제] |

- 모드는 화면 상태다 (주소·서버에 저장하지 않는다). 모델을 바꿔도 유지되고, 화면을 새로 열면 조회 모드다.
- 2차까지는 변경 권한자가 ERD 의 엔터티 상세에서 바로 편집할 수 있었다. 이제 **편집 모드로 바꿔야** 편집 버튼이 보인다 (실수로 바꾸는 것을 줄이려는 변경). 논리 모델 관리 화면의 엔터티 상세는 전과 같다.
- 노드를 더블클릭하면 엔터티 상세가 열린다 (모드에 따라 읽기 전용 / 편집).

### 2.2 저장 정책 — 모델 데이터와 배치는 따로

| | 모델 데이터 (엔터티·속성) | 배치 (노드 위치·화면) |
|---|---|---|
| 저장 시점 | 폼을 저장하는 즉시, 논리 모델 관리와 **같은 API** | [배치 저장] 을 누를 때 |
| 성공 후 | ERD 조회(`GET /model/{id}/erd`)를 다시 받아 노드·패널을 갱신. 위치는 그대로 | 미저장 표시 해제 |
| 실패 시 | 서버 메시지를 공통 알림으로 보여 주고 **화면은 그대로** (먼저 지우거나 바꾸지 않는다) | 안내 문구 |
| 서로의 영향 | 배치 version·좌표를 바꾸지 않는다 | 엔터티·속성을 바꾸지 않는다 |

- 화면이 먼저 바뀌는 낙관적 갱신은 없다. 서버 응답이 기준이고, 다른 화면·사용자의 변경도 다음 조회(편집 뒤 자동, 또는 [새로고침])에 반영된다. 실시간 동기화·잠금은 없다 (D-09 미결정 그대로).
- **새 엔터티의 위치** : 보고 있는 화면 가운데에서 시작해 기존 노드와 겹치지 않는 가장 가까운 자리 (`findFreePosition`). 기존 노드는 옮기지 않고 전체 재배치도 하지 않는다. 새 노드를 선택·가운데로 옮기고 "저장하지 않은 배치"로 표시한다 — [배치 저장] 을 눌러야 그 위치가 남는다 (누르지 않고 나가면 다음에는 기존 배치 오른쪽에 자동 배치된다).
- **엔터티 삭제** : 서버 삭제가 끝난 뒤 노드를 지운다. 배치의 미저장 상태는 건드리지 않는다. 저장된 배치에 남은 그 엔터티의 좌표는 조회에서 빠진다 (M-6 동작).

### 2.3 삭제·승인 보호 (기존 정책 그대로)

| 대상 | 차단 조건 | 화면 |
|---|---|---|
| 엔터티 수정·삭제 | 승인된 엔터티 (승인취소 후에) | [엔터티 삭제] 비활성 + 사유, 상세의 이름·설명 읽기 전용 |
| 엔터티 삭제 | 관계에 쓰임 | [엔터티 삭제] 비활성 + 사유 |
| 엔터티 삭제 | 물리 테이블에 매핑됨 (M-7) | 서버가 거절 → 서버 사유 알림 |
| 속성 추가·수정·삭제·순서 | 승인된 엔터티는 승인 권한자만 | 버튼 숨김·비활성 |
| 속성 삭제 | 식별자에 포함됨 | [삭제] 비활성 + 사유 |
| 속성 삭제 | 물리 컬럼에 매핑됨 (M-7) | 서버가 거절 → 서버 사유 알림 |

화면이 미리 막는 것은 안내일 뿐이고 판정은 서버가 한다. ERD 는 관계·식별자·매핑을 **대신 지워 주지 않는다.** 표준 용어를 바꿔도 물리 컬럼명·매핑은 바뀌지 않고, M-7 의 정합성 진단·물리명 추천이 다음 조회에 바뀐 용어로 계산된다.

### 2.4 권한

| 역할 | ERD 조회 | 편집 모드 | 비고 |
|---|---|---|---|
| NOT_APPROVE | 불가 (403, 접근 거부 화면) | 불가 | |
| VIEWER | 가능, 자기 배치 저장 가능 | 불가 (전환 버튼 없음, 편집 API 403) | |
| USER·DBA | 가능 | 가능. 자기가 만든 엔터티는 승인 대기 | 승인된 엔터티의 속성은 못 바꾼다 |
| MANAGER·ADMIN (승인 권한자) | 가능 | 가능. 만든 엔터티는 바로 승인 상태 | 엔터티명·설명 변경과 삭제는 승인취소 후 |

새 권한은 만들지 않았다 (`logical-model-edit` 메뉴 권한을 그대로 쓴다).

### 4.2 브라우저 검증

헤드리스 Chrome(별도 프로필, DevTools 프로토콜), 빌드한 `lexorma.jar` 를 `h2-local`(인메모리)·포트 19941 로 띄운 인스턴스. **확인 60건 통과, 콘솔 오류 0** (HTTP 4xx 는 서버 거절·인가를 보려고 보낸 요청).

| 구분 | 확인한 것 |
|---|---|
| 모드 (USER) | 조회 모드가 기본, 편집 모드에서 [엔터티 추가]·안내 표시, 조회 모드의 패널·상세에 편집 버튼 없음, 편집 모드 상세는 편집 가능 |
| 엔터티 | 생성 → 노드 표시·선택·포커스·미저장 배치 표시, 3개 생성 시 기존 위치 유지·겹치지 않음, 중복 이름 서버 오류 안내와 상태 유지, 수정(이름·설명) → 노드 갱신·위치·선택 유지, 삭제 확인(이름 표시)·취소·삭제 후 노드 제거·선택 해제·다른 위치 유지, 관계가 있는 엔터티 삭제 차단 안내, 빈 모델에서 생성 |
| 속성 | 추가(필수, 표준 용어 검색·선택) → 노드·패널 표시, 중복 속성명 오류, 수정(이름·설명·용어 변경) — 폼이 저장된 값으로 열림, 용어 연결 해제, 순서 ↓·↑ → 노드 순서 갱신, 삭제, 식별자 속성 삭제 비활성 + 서버 거절, 매핑된 속성 삭제 시 서버 사유 표시와 상태 유지 |
| 배치 | 배치 저장 → 새로고침 후 새 노드 포함 복원, 삭제 후 저장된 배치에서 그 좌표만 빠짐, 노드 이동 시 미저장 표시, 자동 배치, 저장된 배치 불러오기, Delete·Backspace 로 노드가 지워지지 않음 |
| 모델 전환 | 미저장 배치 확인 → 취소 시 유지 / 확인 시 새 모델 로드·편집 모드 유지·선택 초기화, 돌아오면 저장된 배치로 복원 |
| 다른 화면 | 논리 모델 관리 화면·API 에 ERD 편집 결과가 같게 보임, 옮긴 엔터티 등록 폼 동작, 미저장 배치로 매핑 관리 이동 시 확인, 표준 용어 변경 후 컬럼·매핑 불변 + 물리명 추천 변화 |
| 권한 | VIEWER(전환 없음·편집 버튼 없음·편집 API 403·배치 저장 가능), USER·DBA·MANAGER(편집 모드·인가 통과), 미승인(403·접근 거부), ADMIN(승인된 엔터티 : 삭제 비활성·속성 편집 가능) |
| 화면 | 다크·라이트 모드, 820px 폭(가로 넘침 없음), 영어(편집 모드 문구·엔터티 등록 폼) |

**미검증 (완료로 보지 않음)**

- 화면 설명 문구를 편집 모드에 맞게 고친 것은 타입 검사만 했다 (브라우저 검증 뒤에 고쳤다).
- 두 사용자가 같은 엔터티를 동시에 편집하는 화면 (서버의 모델 행 잠금·중복 검사는 M-6 동시성 테스트가 확인. 화면은 나중 요청이 서버 오류를 받는 구조지만 눌러 보지 않았다).
- 엔터티·속성이 수백 개인 모델에서의 편집 반응 속도 (편집할 때마다 모델 전체를 다시 조회한다).
- 매핑된 **엔터티** 삭제의 서버 사유 표시 (통합 테스트로만 확인. 예제의 매핑된 엔터티는 모두 승인·관계가 있어 화면에서는 버튼이 먼저 막힌다).
- Chrome 이외 브라우저, 키보드만으로 조작, 820px 보다 좁은 화면, 터치 입력.
- PostgreSQL 을 붙인 상태의 화면, 개발 DB 에서 실행 중인 애플리케이션의 화면.

## 5. 후속

### 5.1 M-8 2차 (논리 관계·식별자 편집) 선행 조건과 고려사항

- 선행 조건은 충족돼 있다 : 관계·식별자 API 와 폼(`RelationshipForm` 은 논리 모델 관리 파일 안, 식별자 폼은 엔터티 상세 안)이 있다. 1차처럼 폼을 export 해 같은 컴포넌트를 쓰면 된다.
- 관계선을 끌어서 만들려면 `nodesConnectable`·연결점(`isConnectable={false}`)을 편집 모드에서만 열고, `onConnect` 는 **화면에 선을 추가하지 말고** 관계 폼을 연 뒤 저장 성공 후 다시 조회해야 한다 (참여 수·식별 여부를 선만으로 정할 수 없다).
- 자기 참조, 같은 엔터티 쌍의 여러 관계, 승인된 관계의 수정·삭제 제한, 관계가 있는 엔터티 삭제 차단 안내를 그대로 지켜야 한다.
- 식별 관계와 주 식별자의 일관성(식별 관계면 부모 식별자가 자식 식별자에 포함)은 지금 검증하지 않는다 — 정책 결정이 먼저다.

### 5.2 M-8 3차 (물리 ERD 편집) 고려사항

- 로드맵 M-8 의 완료 조건(ERD 편집 결과가 테이블·컬럼 관리·DDL 과 일치, 승인된 컬럼 수정 거부)은 여기서 충족한다.
- 물리 ERD 는 조회 범위가 부분(스키마·검색·이웃)이고 배치가 프로젝트 단위라, 새 테이블의 위치·범위 밖 테이블과의 관계 표시를 따로 정해야 한다.
- 테이블명은 한글명에서 만들어지고(표준 단어), 컬럼은 승인된 테이블에만 표준 용어로 등록한다. 기존 대화상자(테이블 폼·컬럼 일괄 편집)가 이미 ERD 에서 열리므로 1차와 같은 방식(모드 전환 + 기존 폼 + 다시 조회)을 쓸 수 있다.
- 테이블·컬럼 삭제는 M-7 매핑, 관계·인덱스·제약 참조 보호를 그대로 거쳐야 한다. FK 관계 동기화(`syncReferenceRelations`)를 우회하면 안 된다.

### 5.3 남은 기술적 위험

- **동시 편집 (D-09 미결정)** : 잠금·버전 검사 없이 "마지막 저장이 이긴다". 엔터티·속성 단위 저장이라 충돌 범위는 작지만, 다른 사람이 지운 엔터티를 편집하려 하면 오류 알림 뒤 직접 새로고침해야 한다.
- 편집마다 모델 전체를 다시 조회한다. 큰 모델에서는 변경된 엔터티만 갱신하는 방식이 필요해질 수 있다.
- 새 엔터티의 위치를 저장하지 않고 나가면 다음에 다른 자리에 놓인다 (배치를 자동 저장하지 않는 M-2 결정 D-15 의 결과).
- Undo/Redo·편집 이력이 없다 (M-9).

## 6. 2차 : 논리 관계·식별자 편집 — 분석과 결정

| 확인 항목 | 결과 → 결정 |
|---|---|
| 관계 도메인·API | `POST /relationship`(id 없으면 등록, 있으면 수정)·`DELETE /relationship/{id}`·`PATCH …/approval/{bool}`. 항목 : 관계명(선택)·설명·**출발(source)·도착(target) 엔터티**·식별 여부·양쪽 참여 수(`sourceMin..sourceMax`, `targetMin..targetMax`, 최대 null = N). 출발 = 참조되는 쪽(부모), 도착 = 참조하는 쪽(자식) → **새 항목을 만들지 않고 이 DTO 그대로** 쓴다 |
| 관계 정책 | **자기 참조 허용, 같은 두 엔터티 사이의 여러 관계 허용**(중복 검사 없음), 출발·도착은 같은 논리 모델의 엔터티여야 함(`INVALID_LOGICAL_MODEL`), **수정에서 출발·도착 변경 허용**, 승인된 관계는 수정·삭제 불가(승인취소 후), 승인 권한자가 만들면 바로 승인 상태. 관계 편집은 엔터티의 승인 상태와 무관하다 → 화면도 그대로 따른다 (막지 않는 것을 화면이 따로 막지 않는다) |
| 식별자 도메인·API | `POST /identifier`·`DELETE /identifier/{id}`. 주 식별자는 엔터티당 1개, 보조 식별자 여러 개, 속성 1개 이상(복합·순서 유지), 같은 엔터티의 속성만, 이름 중복 불가. 승인된 엔터티의 식별자는 승인 권한자만 바꾼다. 식별자를 지워도 속성은 남는다 |
| 관계 ↔ 식별자 | 서비스에 **서로를 맞추는 규칙이 없다** (식별 관계라고 자식의 주 식별자를 검사·변경하지 않는다) → 2.3 대로 **자동 동기화를 만들지 않았다** (8장) |
| 논리 ERD 관계선 (M-6) | 실선 = 식별, 점선 = 비식별. 양 끝에 그 엔터티 쪽의 참여 수 글자(`1`, `0..N`). 연결점은 왼쪽(도착)·오른쪽(출발)·자기 참조용 2개, 모두 연결 불가로 고정. 관계선을 누르면 관계 패널이 열린다. 같은 쌍의 관계선은 **완전히 겹쳐 그려졌다** → 2차에서 띄웠다 |
| 재사용 컴포넌트 | 관계 폼(`RelationshipForm`, 논리 모델 관리 파일 안)·식별자 폼(`IdentifierForm`, 엔터티 상세 안) → **export 해서 같은 컴포넌트**를 쓴다. 관계 폼은 `relationshipForm.tsx` 로 옮겼다 |

## 7. 2차 : 관계 편집

### 7.1 연결은 등록의 시작일 뿐이다

```text
편집 모드에서 오른쪽 연결점(출발) → 다른 엔터티·자기 자신의 왼쪽 연결점(도착)으로 끌기
   → onConnect : 선을 추가하지 않고 관계 등록 대화상자를 연다 (출발·도착을 미리 채움)
        ├─ 취소·닫기        → 아무것도 생기지 않는다
        └─ 저장 → POST /relationship
              ├─ 실패 → 서버 메시지 알림, 선 없음
              └─ 성공 → ERD 다시 조회 → 관계선 표시, 새 관계 선택
```

- React Flow 의 임시 연결선은 놓는 순간 사라진다. 화면의 선은 언제나 조회 결과(`graph.relationships`)에서만 만든다 — `edges` 상태에 직접 넣지 않는다.
- **방향** : 끌어 놓은 방향이 곧 부모·자식이라고 보지 않는다. 대화상자에서 출발·도착을 확인·변경하고 **[방향 바꾸기]**(엔터티와 양쪽 참여 수를 함께 맞바꿈)를 쓸 수 있다. "출발 = 참조되는 쪽(부모), 도착 = 참조하는 쪽(자식)" 안내를 넣었다.
- 연결점은 편집 모드에서만 활성(파란 점)이다. 조회 모드·VIEWER 는 연결할 수 없다 (`nodesConnectable={editing}`, 연결점 `isConnectable`).
- 끌기 말고도 엔터티 패널의 **[관계 추가]**(선택한 엔터티가 출발)로 같은 대화상자를 연다.

### 7.2 수정·삭제

- 관계선(또는 엔터티 패널의 관계 목록)을 누르면 관계 패널 : 이름, 승인 상태, 식별·비식별, 카디널리티, 출발·도착 엔터티와 참여 수. 편집 모드에서 **[관계 수정]·[관계 삭제]**, 승인 권한자에게 **[승인]·[승인취소]**(편집이 아니라 승인 절차라 조회 모드에서도 보인다 — 엔터티 상세와 같다).
- 수정은 등록과 같은 폼 : 관계명·설명·식별 여부·참여 수, 그리고 **출발·도착 엔터티도 바꿀 수 있다** (서버가 허용한다. 삭제 후 재등록을 요구하지 않는다).
- 삭제 확인 : `'{관계명 또는 출발 → 도착}' 관계를 삭제하시겠습니까? (출발 : A, 도착 : B) 엔터티·속성·식별자는 바뀌지 않습니다.` 성공 후 다시 조회, 실패하면 선이 그대로다.
- 승인된 관계는 [관계 수정]·[관계 삭제] 가 비활성이고 사유가 보인다 (승인취소 후 가능). 서버도 `APPROVED_DATA_CANNOT_BE_UPDATE`·`_DELETED` 로 거절한다.
- Delete·Backspace 키로 관계선이 지워지지 않는다 (`deleteKeyCode={null}`).

### 7.3 표시

| 항목 | 표현 |
|---|---|
| 식별·비식별 | 실선 / 점선 (M-6 규칙 그대로) |
| 참여 수 | 양 끝의 글자(`1`, `0..1`, `1..N`, `0..N` — M-6 그대로) + **선 끝 표기(Crow's Foot)** : 최대 1 = 세로 막대, 여러 건 = 까치발, 최소 0 = 원(선택), 1 이상 = 막대(필수). 출발 쪽은 출발 엔터티의 참여 수, 도착 쪽은 도착 엔터티의 참여 수다. 표기는 그림일 뿐 데이터는 글자와 같다 (최대가 2 이상인 `2..5` 같은 값도 "여러 건"으로 그린다) |
| 같은 쌍의 여러 관계 | 관계마다 16px 씩 띄워 그린다 → 선마다 따로 누를 수 있다. 엔터티 패널의 관계 목록에서도 고를 수 있다. 선이 많을 때의 자동 경로 정리는 하지 않았다 (후속) |
| 자기 참조 | 오른쪽 위에서 나가 오른쪽 아래로 들어오는 기존 표현 그대로 |

## 8. 2차 : 식별자 편집과 관계 ↔ 식별자 정책

- 엔터티 패널에 **식별자 목록** : `PI`/`AI`, 식별자명, 주·보조, 구성 속성을 순서대로(`A + B`, 복합 표시). 조회 모드에서도 보인다 (식별자 이름·구성은 ERD 조회에 없어 엔터티 상세와 같은 `GET /entity/{id}` 로 받는다 — 엔터티를 고를 때와 편집 뒤에 1번).
- 편집 모드에서 **[식별자 추가]**, 식별자마다 **[수정]·[삭제]**. 폼은 엔터티 상세의 식별자 폼 그대로 : 식별자명, 주 식별자 여부, 구성 속성을 고른 순서대로 넣고 ↑↓ 로 순서 변경. 저장 후 다시 조회하면 노드의 `PI`/`AI` 표시가 바뀐다.
- 엔터티 상세 대화상자의 식별자 탭도 그대로 있다 (같은 폼, 같은 API).

**관계와 식별자는 서로를 자동으로 바꾸지 않는다.**

| 변경 | 자동으로 하지 않는 것 |
|---|---|
| 식별 관계 등록·비식별 → 식별 변경 | 자식 엔터티에 속성·식별자를 추가하지 않는다 |
| 식별 → 비식별 변경, 관계 삭제 | 식별자·속성을 빼지 않는다 |
| 식별자 등록·수정·삭제 | 관계의 식별 여부를 바꾸지 않는다 |

관계 패널에 "식별 여부는 관계에만 저장됩니다. 관계를 바꿔도 엔터티의 식별자는 자동으로 바뀌지 않습니다" 를 적었고, 두 정보는 엔터티 패널(식별자 목록·관계 목록)에서 나란히 볼 수 있다. **일관성 검사는 없다** — 지금 모델로는 "부모의 주 식별자 속성이 자식의 어느 속성에 해당하는지"를 알 수 없다 (관계에 속성 쌍이 없다, M-6 결정). 검사하려면 관계 속성 매핑이나 "같은 표준 용어" 같은 기준을 먼저 정해야 한다 (10장).

## 10. 후속 (2차 이후)

### 10.1 M-8 3차 선행 조건

> 3차는 구현됐다. 기록은 [physical-erd-editing-m8.md](physical-erd-editing-m8.md). M-8 완료 정리와 그 뒤의 서버 검증 보강은 [model-integrity-hardening.md](model-integrity-hardening.md).

- 편집 기반(모드 전환, 새 노드 위치, "연결 → 폼 → 저장 → 다시 조회")은 논리 ERD 에서 검증됐고 `features/erd/editing.tsx` 에 있다. 물리 쪽 API(테이블·컬럼·관계·인덱스·제약)와 대화상자(테이블 폼·컬럼 일괄 편집)도 이미 있다 → 선행 조건은 충족돼 있다.
- 물리 관계는 **컬럼 쌍**을 가진다(`TB_TBL_REL_COL`). 연결만으로는 FK 컬럼을 정할 수 없으므로 논리 ERD 와 같이 "연결 → 폼에서 컬럼 쌍·방향 확인 → 저장" 이어야 한다. 컬럼의 참조 테이블명과 관계의 동기화(`syncReferenceRelations`)를 우회하면 안 된다.
- 물리 ERD 는 조회 범위가 부분이고 배치가 프로젝트 단위다 — 범위 밖 테이블과의 관계, 새 테이블의 위치를 정해야 한다.
- 로드맵의 M-8 완료 조건(편집 결과가 테이블·컬럼 관리·DDL 과 일치, 승인된 컬럼 수정 거부, 레이아웃 복원)은 3차의 검증 항목이다.

### 10.2 관계·식별자 일관성 검증 (후속 과제)

- 지금 판단할 수 있는 것 : "식별 관계인데 자식 엔터티에 주 식별자가 없다" 정도 (사실 표시 수준). 부모 식별자가 자식 식별자에 포함되는지는 관계에 속성 쌍이 없어 판단할 수 없다.
- 하려면 ① 관계 속성 매핑(부모 속성 ↔ 자식 속성)을 논리 모델에 추가하거나 ② "같은 표준 용어를 쓰는 속성"을 대응으로 본다는 정책을 정해야 한다. 정해지면 M-7 정합성 비교처럼 조회 전용 진단으로 두는 것이 맞다 (자동 수정 없이).

### 10.3 남은 기술적 위험

- 동시 편집(D-09) : 잠금 없이 마지막 저장이 이긴다. 다른 사람이 지운 엔터티로 관계를 만들려 하면 서버 오류를 받고 직접 새로고침해야 한다.
- 관계선 경로 : 같은 쌍의 선을 일정 간격으로 띄울 뿐이다. 엔터티 사이를 가로지르는 선·겹치는 글자는 정리하지 않는다.
- 편집마다 모델 전체 + 선택한 엔터티 상세를 다시 조회한다.
- Undo/Redo·편집 이력이 없다 (M-9).
