# M-4b 원본 DB ERD

> 2026-11-13. [M-4](data-modeling-roadmap.md#m-4-역공학-결과의-물리-모델-가져오기erd-자동-생성)의 두 번째 단계.
> 수집해 둔 원본 카탈로그로 읽기 전용 ERD 를 그린다.
> 원본 DB 에 접속하지 않고, 물리 모델을 바꾸지 않는다. 신규 Flyway 마이그레이션은 없다.
> 앞 단계는 [M-4a 원본 DB 관리 화면](source-management-ui-m4a.md).

## 1. 사전 분석

### 1.1 기존 물리 ERD (`features/erd`)
- **라이브러리** : React Flow(`@xyflow/react` 12)와 ELK(`elkjs` 0.12)를 쓴다.
- **자동 배치** : `layout.ts`. 공식 ELK 워커(`elk-worker.min.js`)에서 계산하므로 Web Worker 로 메인 스레드를 막지 않는다.
  - 새 요청이 오면 진행 중인 계산을 버린다.
  - 30초가 넘으면 격자로 배치한다.
  - 관계 없는 노드는 ELK 에 넣지 않고 격자로 놓는다.
- **노드** : `TableNode.tsx`. 폭 280, 헤더 52, 행 24. 컬럼은 최대 20행이고 나머지는 "외 n개" 로 줄인다.
  - 축소해 노드가 140px 아래가 되면 컬럼을 생략한다 (`useSimpleNodes`).
  - 컬럼 연결점은 그린 관계에 쓰인 컬럼에만 만든다.
- **관계선** : `edges.ts`. 컬럼이 보이면 복합 FK 의 컬럼 쌍마다 선을 긋고, 아니면 테이블 연결점에 하나만 긋는다.
- **대규모 대응** : `onlyRenderVisibleElements`(화면 안 노드·선만 그린다)와 서버 쪽 범위 조회(100개 쪽, 이웃 조회 300개 한도)를 쓴다.
- **화면 모양** : 다크 모드는 Primer 토큰을 따른다(`erd.css`). 문구는 i18n 을 쓴다.
- **물리 ERD 전용이라 쓰지 않은 것** : 노드 데이터 모양(`ErdTable` : 논리명·승인 상태), 배치 저장(`/api/erd/layout`), 편집 모드.

### 1.2 원본 카탈로그 API
- **N+1 문제** : 기존 API 로 ERD 를 그리려면 스키마 목록(`catalogAt`) → 스키마마다 테이블 목록(`tablesAt`, 컬럼·FK 없음) → **테이블마다 `tableAt`**(버전 JSON) 순으로 불러야 한다. 3,000 테이블이면 3,000번 넘게 호출한다.
- **현재 카탈로그 조회** (`/api/source/tables/{id}`) : 테이블 하나 단위이고, 과거 시점이 아니라 최신 행이다.
- **과거 시점의 기준** : 반영 순서 R 의 상태는 테이블 버전(`TB_SRC_TBL_VER`)에서 "테이블마다 R 이하의 마지막 버전" 이다.
  - 이미 연결 전체를 한 번에 읽는 쿼리가 있었다 (`SourceTableVersionRepository.at(connectionId, order)`).
  - 버전 JSON 에 컬럼·제약조건·FK 가 모두 있다.
- **FK 대상의 저장 방식** : 버전 JSON 에 원본 이름(카탈로그·스키마·테이블)으로 적혀 있다. 대상 테이블의 ID 가 없다.
  - 그래서 수집기가 참조를 잇는 규칙(`SourceCollectionPreparer`)으로 (스키마 경로, 테이블 비교 이름)을 만들어, 같은 시점의 테이블에서 찾는다.
- **결론** : 기존 데이터를 그대로 읽는 **읽기 전용 ERD API 하나**를 더했다. 저장 구조·수집은 바꾸지 않았다.

## 2. API

`GET /api/source/connections/{id}/snapshot/erd?order=` (VIEWER 이상, `SourceSnapshotService.erd`)

- **시점** : order 가 없으면 마지막 반영이다. COMPLETED 수집만 반영 순서를 가진다. 실패·취소 수집의 order 나 없는 order 를 주면 `SOURCE_COLLECTION_NOT_FOUND` 다. 반영된 수집이 없으면 `reflectedOrder: null` 과 빈 목록을 준다.
- **조회 방식** : 스키마 버전 1번, 테이블 버전 1번만 읽는다(연결 전체). 버전 JSON 을 메모리에서 풀어 응답을 만든다.
- **응답 (`SourceErdDto.Graph`)**
  - 스키마 : 테이블 수·VIEW 수.
  - 테이블·VIEW : 원본 이름, 비교 이름, COMMENT, 컬럼(이름·비교 이름·타입·NULL·PK·FK).
  - FK
    - ID : 참조하는 테이블 ID + 관계 키라 연결 안에서 하나다.
    - 출발·대상 테이블 ID : 대상이 그 시점 카탈로그에 없으면 null 이고 이름만 남는다.
    - 컬럼 쌍 : 복합 FK 순서 그대로, 표시 이름과 비교 이름을 함께 준다.
    - ON DELETE·ON UPDATE.
  - 연결의 DBMS·식별자 비교 규칙 : 화면 검색에 쓴다.
- **응답에 없는 것** : 비밀번호·호스트·JDBC 정보는 없다. `/api/source/**` 라 요청 로그에 본문이 남지 않는다.
- **이름 공간 규칙** : FK 대상의 스키마·카탈로그가 생략된 경우는 수집기와 같은 규칙으로 해석한다 (같은 카탈로그·같은 스키마).

## 3. 화면 (`/sourceErd`, 메뉴 원본 DB 관리 > 원본 DB ERD)

- **위 막대** : 연결, 수집 시점(마지막 반영 / 완료된 수집의 반영 순서).
- **상태 줄**
  - 반영 순서·수집·시각, 보기 범위, 객체·FK 수, 화면 밖 FK 수를 보여 준다.
  - [자동 배치]·[전체 보기] 가 있고, 확대·축소·화면 맞춤은 React Flow 컨트롤로 한다.
- **왼쪽 객체 탐색**
  - 스키마마다 체크박스(복수 선택)와 테이블·VIEW 수를 보여 준다. 고른 스키마의 객체 목록이 나온다(스키마마다 200개까지, 나머지는 검색으로 좁힌다).
  - 검색 : 테이블·VIEW·스키마 이름. 원본 DBMS 의 비교 규칙을 따른다 (PostgreSQL 은 소문자로 접고, 따옴표로 감싸면 그대로 비교).
  - 목록에서 객체를 누르는 경우
    - 그려진 범위에 있으면 그 노드를 고르고 가운데로 옮긴다 (zoom 1).
    - 없으면 그 객체 중심 보기(FK 이웃 1~3단계, 스키마와 무관)로 바꾼다.
- **ERD**
  - 노드 : 스키마명(여러 스키마가 보일 때), 테이블명, COMMENT, 컬럼(PK·FK·PF 표시, 타입, NN). 20행이 넘는 컬럼은 줄인다.
  - VIEW : 점선 테두리에 `VIEW` 표시, "정의 SQL 미수집". VIEW 의 참조 관계는 그리지 않는다 (추정하지 않는다).
  - 노드를 옮길 수 있지만 이 탭에서만 기억하고 서버에 저장하지 않는다.
- **아래 상세 패널**
  - 관계선을 고르면 FK 상세를 보여 준다 : 제약조건명, 출발·참조 테이블(이동), 컬럼 쌍(순서), ON DELETE·ON UPDATE, 자기 참조·복합 FK 표시.
  - 테이블을 고르면 원본 카탈로그 화면의 상세(`TableDetailView`)를 그대로 쓴다 : 컬럼·PK·UNIQUE·CHECK·인덱스·FK·COMMENT·변경 이력·버전.
    - 마지막 반영이면 현재 카탈로그를 읽고, 과거 시점이면 그때의 버전을 읽는다.
    - 화면 밖 FK 목록이 위에 있다.
- **URL 상태** : `connectionId`·`order`·`schemas`(`all` 또는 ID 목록)·`focus`·`depth`·`table`. 버전을 바꿔 고른 객체가 그 시점에 없으면 선택을 푼다.

## 4. FK 표현

- **그리는 것** : 원본에 정의된 FK 만 그린다. 이름이 비슷하다고 관계를 만들지 않는다.
- **물리 모델의 관계와 무관** : 물리 모델의 관계(`TableRelation`, IMPORTED 포함)와 섞지 않는다.
- **방향** : 참조하는 테이블(오른쪽 연결점)에서 참조되는 테이블(왼쪽 연결점, 화살표)로 긋는다.
- **자기 참조** : 같은 노드의 오른쪽 연결점으로 되돌아온다.
- **복합 FK** : 컬럼이 보이면 컬럼 쌍마다 선을 긋는다 (`관계ID#순번`). 축소했거나 20행 밖의 컬럼이면 테이블 연결점 사이에 하나만 긋는다. 상세 패널은 항상 컬럼 순서대로다.
- **여러 FK 가 같은 테이블을 참조** : 관계마다 따로 긋는다.
- **화면 밖 FK (양쪽이 모두 보일 때만 선을 긋는다)**
  - 한쪽이 필터로 숨었거나 수집 범위 밖이면 선 대신 표시한다 : 노드 부제의 "화면 밖 FK n", 상태 줄의 합계, 상세 패널의 목록(관계 상세로 이동).
  - 스키마 간 FK 는 양쪽 스키마를 고르면 선으로 보인다. 아니면 목록에서 대상 테이블로 이동한다(객체 중심 보기).

## 5. 수집 버전별 스냅샷

- **반영 순서 R 의 ERD** : 테이블마다 R 이하의 마지막 버전(REMOVED 제외)만 쓴다. 최신 카탈로그 행을 섞지 않는다.
  - 그때 없던 테이블·컬럼·FK 는 나오지 않는다.
  - 그 뒤 지워진 FK·테이블은 그 시점에 보인다.
- **PARTIAL 수집 뒤** : 범위 밖 테이블은 앞 버전이 그대로 유효하다. 그래서 R 의 ERD 는 그 실행의 변경분이 아니라 그 시점의 전체 카탈로그다 (`catalogAt`·`tableAt` 과 같은 규칙).
- **FK 대상도 같은 시점** : 대상 테이블도 같은 R 의 테이블에서 찾는다. 대상이 그 시점에 없으면 범위 밖으로 표시한다.
- **같은 이름의 다른 테이블** : 스키마마다 같은 이름이 있어도 노드 ID 는 원본 테이블 ID(`TB_SRC_TBL`)다. 테이블은 스키마 경로·비교 이름으로 식별되므로 섞이지 않는다.
- **알려진 제약** : 연결의 DBMS·식별자 비교 규칙이 수집 뒤에 바뀌면, 과거 FK 의 대상 해석도 지금 규칙을 따른다. 수집은 규칙이 바뀐 실행을 거절하지만 과거 버전은 그대로다. PostgreSQL 은 규칙을 바꿀 수 없어 해당이 없다.

## 6. 권한·보안

- **조회** : ERD 조회는 VIEWER 이상이다. 메뉴 `source-erd` VIEWER, API `@PreAuthorize("hasRole('VIEWER')")`.
- **관리 권한 불필요** : 연결 관리 권한(프로젝트 관리자·ADMIN)이 없어도 볼 수 있다. M-4a 정책 그대로다.
- **다른 프로젝트** : 다른 프로젝트의 연결 ID 는 `SOURCE_CONNECTION_NOT_FOUND`(404) 다. 수집 실행·테이블 ID 는 원래 API 와 같은 검사를 거친다.
- **원본 DB 접속 없음** : 저장된 카탈로그만 읽고, 원본 DB 에 SQL 을 실행하지 않는다.
- **물리 모델과 분리** : 물리 모델·물리 ERD 배치(`TB_ERD_LYT`)를 읽거나 쓰지 않는다. 브라우저 확인에서 원본 ERD 를 탐색한 뒤에도 물리 ERD 배치는 저장된 적 없는 그대로였다.

## 7. 대규모 성능 (측정)

**측정 조건**

- 원본 : 로컬 PostgreSQL 18.6 의 임시 DB 3개.
  - 테이블마다 컬럼 10개, PK, 스키마 안 사슬 FK, 스키마 간 FK.
  - 300 = 3 스키마, 1,000 = 4 스키마, 3,000 = 10 스키마.
- 수집 : 실제 수집 도구로 FULL 수집. 3,000 테이블이 0.4초.
- 브라우저 : headless Chrome 1440×1000. Lexorma 서버는 bootJar, `h2-local`.

| 규모 | API (응답 크기) | 첫 화면 | 자동 배치 | DOM 노드·선 (화면 안) | 검색 반응 | 스키마 바꾸기 | JS 힙 |
|---|---|---|---|---|---|---|---|
| 300 (전체 그리기) | 25–43 ms (441 KB) | 0.71 s | 0.15 s | 135 · 148 | 17–26 ms | 0.21 s | 42 MB |
| 1,000 (전체 그리기) | 32–41 ms (1.48 MB) | 1.1 s | 0.32 s | 180 · 196 | 20–24 ms | — | 80 MB |
| 3,000 (기본 : 스키마 3개, 900 객체) | 72 ms (4.46 MB) | 1.07 s | 0.26 s | 135 · 148 | 26 ms | 0.26 s | 105 MB |
| 3,000 ([그래도 모두 그리기]) | 68 ms | 2.1 s | 0.96 s | 450 · 505 | 26 ms | — | 224 MB |

- **서버만 잰 시간** : 3,000 테이블 `erd()` 는 H2 84 ms, PostgreSQL 114 ms 였다 (`SourceErdIntegrationTest.large`, `LEXORMA_PERF=true`).
- **결정**
  - 한 번에 그리는 한도(`RENDER_LIMIT`)를 **1,000** 으로 했다 (처음 500 → 측정 후 1,000).
  - 넘으면 안내와 함께 [그래도 모두 그리기]를 둔다. 3,000 에서도 2초 남짓이다.
  - 기본 범위는 객체가 있는 스키마를 순서대로 한도까지 담는다. 측정 중 빈 `public` 스키마를 "첫 스키마" 로 골라 아무것도 안 그리던 문제를 고쳤다.
- **적용한 최적화** : 스키마 단위 범위, 객체 중심(FK 이웃) 보기, `onlyRenderVisibleElements`, 축소 시 컬럼 생략, ELK 워커, 범위별 배치 결과 캐시(탭 안 20개), 탐색 목록 스키마마다 200개.
- **하지 않은 것** : 지연 로딩과 노드 가상화는 하지 않았다. 측정상 응답(4.5 MB, 70 ms)과 그리기가 한도 안이었다.
- **FK 를 빠뜨리지 않는 방식** : 그리지 않는 FK 도 데이터에는 모두 있다. 수로 표시하고 목록에서 이동할 수 있다.
- **주의**
  - 측정 그래프는 사슬 모양이라 ELK 에 유리하다. 관계가 촘촘한 실제 스키마는 배치가 더 오래 걸릴 수 있다 (30초 시간 초과 시 격자 배치).
  - 응답이 압축되지 않는다(서버 `server.compression` 미설정). 3,000 테이블이면 4.5 MB 를 받는다. 느린 네트워크용으로 압축 설정을 후속 과제로 남긴다.
