### DEC-08 — 모델 동시 편집 정책 (D-09)

**현재 상태**
- 기존 정책: D-09 미결정 — 낙관적 잠금 / 편집 잠금. 모델 엔터티에 `@Version` 없음.
- 현재 구현: 기본은 나중 저장 우선. 기능별 기준값 비교가 이미 있다 — 업무 설명(`base` → 409), 표준 용어 재연결(`baseTermId` → 409), ERD 배치(409), AI 제안(`VER_NO`), 가져오기(`planToken`·`SOURCE_COMPARE_STALE`), 원본 매핑, 인덱스 변경 요청. `@DynamicUpdate` 로 다른 칸은 되돌리지 않는다.
- 남은 문제: 같은 일반 속성(설명·타입 등)을 두 사람이 동시에 고치면 나중 것이 이긴다.

**선택지**
- A안: 현행 유지.
- B안: 낙관적 검사 — 화면이 읽은 `MDFCN_DT` 를 함께 보내고 다르면 409 (`@Version` 추가 없이, 마이그레이션 없음). 화면별 단계 적용.
- C안: 편집 잠금(체크아웃).

**최종 추천안**
- 추천: A안 유지, 필요해지면 B안으로 별도 설계.
- 근거: 모든 모델 수정 API 의 요청 형식이 바뀐다 (pending 8.2 "DEC-08 → 모든 모델 수정 API"). 위험이 큰 칸(업무 설명·용어 연결)은 이미 막혀 있다. C안은 단일 서버 세션·잠금 해제 문제로 비용이 크다.
- 장점: 회귀 위험 없음.
- 위험: 동시 편집 팀에서는 덮어쓰기가 남는다.
- 구현 필요 여부: A안 없음. B안은 큰 작업(API·화면·테스트 전반).
- 영향 범위: B안이면 테이블·컬럼·관계·인덱스·VIEW·논리 모델 API 와 화면, DEC-13.

**결정 유형**: 사용자 승인 필요 — 대규모 구조 (C)
**결정 요청**: 동시 편집 설계(B안)를 별도 작업으로 시작할 필요가 지금 있는가?

### DEC-09 — 무효 FK·`REF_COLUMN` 타입·`refTableName`

**현재 상태**
- 기존 정책: D-04 `refTableName` 호환용 유지, 폐기는 관계 편집 UI(M-8) 뒤 재검토. 안정화 8장 — 사후 무효 FK 는 DDL 경고만.
- 현재 구현: FK 등록 시 참조 무결성 검증(안정화 3장). 참조 테이블명으로 만든 FK 는 타입 검사 없음, `unresolvedReferences`·DDL 경고. M-8 관계 편집 UI 있음. 엑셀 업로드·Export 가 `refTableName`(컬럼 템플릿 L열)을 쓴다.
- 남은 문제: 사후에 무효가 된 FK 를 막을지, 진단으로 보일지, `refTableName` 을 없앨지.

**선택지**
- A안: 막지 않고 DDL 경고만 (현행).
- B안: A안 + 품질 진단(M-5)·물리 모델 화면에 "무효 FK" 표시.
- C안: 무효를 만드는 변경(PK 해제·타입 변경 등)을 거부.
- (`refTableName`) 유지 / 폐기.

**최종 추천안**
- 추천: 막지 않음(A) + `refTableName` 유지. B안 진단 표시는 선택 후속(P2).
- 근거: C안은 모델 수정 순서(타입 변경 → FK 수정)를 강제해 작업을 막는다. `refTableName` 은 엑셀 업로드·Export 계약(L열)에 들어 있어 폐기하면 업로드 호환이 깨진다.
- 장점: 기존 흐름·엑셀 계약 유지.
- 위험: 무효 FK 를 DDL Export 때 늦게 발견한다 (B안이 줄인다).
- 구현 필요 여부: A안 없음, B안 작음~중간 (진단 규칙 1종).
- 영향 범위: B안이면 M-5 품질 진단 API·화면, `SmokeTest` 예제 진단 0건 조건.

**결정 유형**: 추천안 승인 (B)
**결정 요청**: 무효 FK 를 막지 않고 `refTableName` 을 유지하는가? 진단 표시(선택)를 후속으로 둘까?
