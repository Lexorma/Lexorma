# AI-1c 원본 카탈로그 수집 실행 · 스냅샷 · 변경 이력

> 2026-11-13. AI 메타데이터 로드맵 1단계의 세 번째 작업([작업 분할](ai-metadata-roadmap.md#1단계-메타데이터-모델-보강--변경-이력--상세-설명-분리)).
> AI-1b 의 원본 카탈로그([source-catalog-ai1b.md](source-catalog-ai1b.md))에 **수집 결과를 안전하게 반영하고 과거 상태를 재구성하는 계층**을 더했다.
> **원본 DB 에 접속하지 않는다** : 실제 수집 도구(JDBC)는 AI-2 다. AI-1c 는 수집 결과(`SourceCollectionSpec`)를 받는 내부 경로·버전·이력·조회 API 까지다.
> 코드는 `lexorma-source` 의 `collection/` 패키지다 (`lexorma-data` 와 의존하지 않는다).


> **AI-2b (2026-11-13)** : PostgreSQL 수집 도구가 이 수집 실행을 부른다 ([source-postgresql-collection-ai2b.md](source-postgresql-collection-ai2b.md)). 이 문서의 규칙은 바뀌지 않았고 두 가지만 더했다 —
> ① 인덱스 정규화 JSON 에 `expressions`·`sorts`·`predicate` 를 **값이 있을 때만** 넣는다 (표현식·부분·정렬 인덱스). 컬럼만의 오름차순 인덱스는 지금 JSON·해시 그대로라 `FORMAT`(1)·해시 접두사(`v1:`)를 올리지 않았고, 저장된 버전을 고치지 않는다.
> ② `fail` 이 실행 컨텍스트 재확인에 실패하면 실행을 그 권한 오류 코드로 FAILED 로 닫은 뒤 예외를 던진다 (예전에는 RUNNING 으로 남아 그 연결의 수집을 다시 시작할 수 없었다).
## 1. 구조 (U-06 : 현재 상태 + 변경분 이력 + 기준 상태)

```text
TB_SRC_CNTN (외부 DB 연결)
 ├─ 현재 상태   TB_SRC_SCHM · TB_SRC_TBL · TB_SRC_COL · TB_SRC_CNSTRT(_COL) · TB_SRC_IDX(_COL) · TB_SRC_REL(_COL)   (AI-1b 의 9개, 마지막 반영 상태)
 └─ TB_SRC_CLCT_EXCN (수집 실행)                      한 번의 수집 : 상태, 범위, 반영 순서, 건수, 오류
     ├─ TB_SRC_CLCT_TRGT (수집 대상)                  실행이 대상으로 한 이름 공간과 결과 (COMPLETED · FAILED · NOT_FOUND · SKIPPED)
     ├─ TB_SRC_SCHM_VER (스키마 버전)                  스키마가 처음 수집·생김·바뀜·사라짐일 때만 1행
     ├─ TB_SRC_TBL_VER  (테이블 버전)                  테이블(하위 객체 포함)이 처음 수집·생김·바뀜·사라짐일 때만 1행 = 테이블 단위 Copy-on-Write
     └─ TB_SRC_CHG_HSTRY (변경 이력)                   객체(스키마·테이블·컬럼·제약조건·인덱스·관계)별 추가·수정·삭제, 바뀐 항목, 변경 전후 JSON
```

- **매번 전체를 복사하지 않는다.** 바뀐 테이블만 그 테이블 전체(컬럼·PK·UNIQUE·CHECK·인덱스·FK·원본 COMMENT)를 정규화한 JSON 으로 새 버전에 담는다.
  바뀌지 않은 테이블은 이전 버전이 계속 유효하다 : 변경 없는 수집은 실행 행만 남는다.
- **기준 상태** = 처음 수집한 이름 공간의 BASE 버전. 이후 보관 정책을 더할 때 "보관 경계 시점에 유효한 버전"을 남기면 그것이 새 기준이 된다 (롤링 기준, 7장). 지금은 아무것도 지우지 않는다.
- **시점의 순서**는 연결별 **반영 순서**(`RFLT_ORD` = 1, 2, 3 …)다. COMPLETED 실행에만 연결 행 잠금 아래에서 붙인다.
  일련번호는 시퀀스가 50개씩 나눠 줘 인스턴스가 여럿이면 시간 순서가 아니고, 등록 일시는 같을 수 있어 순서로 쓰지 않는다.
- 버전·이력에는 비교 경로(`PATH_CN`)·비교 명과 JSON 이 있어 **현재 행 없이도 과거를 재구성**한다. 현재 행의 일련번호는 조회 편의로 함께 둔다 :
  스키마·테이블·컬럼 행은 원본에서 사라져도 지우지 않으므로(EXST_YN = false) 버전이 가리키는 행은 연결이 지워질 때까지 남는다 (연결 삭제는 버전도 함께 지운다).
- 버전·이력 엔티티에는 setter 가 없다 : 만든 뒤 고치지 않는다.

### 1.1 현재 카탈로그와 스냅샷의 책임 (2026-11-13 정합성 보완)

| | 무엇인가 | 누가 바꾸나 |
|---|---|---|
| **마지막 확정 버전** (테이블·스키마마다 반영 순서가 가장 큰 버전) | 원본 DB 에서 마지막으로 확인한 사실. **원본 변경 감지의 기준** | 수집 반영만 (추가만, 고치지 않는다) |
| **현재 카탈로그** (9개 테이블) | 화면·조회·AI(이후)가 읽는 지금 상태. 마지막 확정 버전과 같아야 한다 | 운영 : 수집 반영만. 테스트 : AI-1b 의 `SourceCatalogWriter` 도 |

- **운영 코드에서 원본 카탈로그를 바꾸는 경로는 수집 반영(`SourceCollectionService.apply`) 하나**다. 그 밖에는 연결·프로젝트 삭제(`SourceCatalogCleanup`, 지우기만)가 있다.
  `SourceCatalogWriter` 는 테스트가 카탈로그를 준비할 때만 쓴다 — 운영 코드에 호출이 없고(컨트롤러·내부 도구 포함), `ModuleBoundaryTest.catalogWritePaths` 가 `lexorma-source` 운영 코드의 Writer 호출과
  카탈로그 저장소의 저장·삭제 호출(Writer 밖)을 막는다. AI-2 는 Writer 가 아니라 수집 반영을 쓴다.
- 처음 구현은 원본 변경을 **현재 카탈로그**와 비교했다. Writer 로 현재 카탈로그가 바뀐 뒤에는 원본이 바뀌어도 버전이 생기지 않거나(같은 값 수집), 원본이 그대로인데 버전·이력이 생기거나(원래 값 수집),
  이력의 변경 전 값이 Writer 의 값이 되는 문제가 있었다 (테스트로 재현 : `SourceCatalogConsistencyIntegrationTest` 시나리오 A·B·C·D). 지금은 아래 4.3 처럼 둘을 나눈다.

## 2. 수집 실행

```text
1. 등록 (start)        짧은 트랜잭션 : 요청자 확인 → 프로젝트(공유) → 연결(배타) 잠금 → 같은 연결의 진행 중 실행 확인 → 실행 RUNNING (+ PARTIAL 은 대상 SKIPPED)
2. 결과 준비           트랜잭션 밖 : (AI-2 원본 DB 조회) → 구조 검증 · 범위 · 완결성 · 크기 · 정규화 · 해시 (SourceCollectionPreparer)
3. 반영 (apply)        한 트랜잭션 : 프로젝트 → 연결 잠금 → 실행 컨텍스트·연결·실행 상태 재확인 → 비교 → 현재 카탈로그 · 버전 · 이력 · 반영 순서 · COMPLETED
   실패하면            전부 롤백 → 별도 트랜잭션에서 실행 FAILED (+ 대상별 결과). 연결·프로젝트가 지워졌으면 기록하지 않는다
```

| 상태 | 뜻 |
|---|---|
| `CREATED` | (예약) 등록만 된 실행. 지금은 등록과 동시에 RUNNING 이다 |
| `RUNNING` | 진행 중. 같은 연결에 하나뿐이다 |
| `COMPLETED` | 반영됐다. 반영 순서가 있다. **이것만 과거 상태 조회의 시점이 된다** |
| `FAILED` | 반영하지 않았다 (일부 스키마 실패, 없는 스키마, 검증 오류, 반영 도중 오류, 권한 회수, 멈춘 실행 정리) |
| `CANCELLED` | 취소했다 |

- 부분 실패는 **전체 보류**다 (U-26 결정) : `PARTIAL_FAILED` 상태가 없다. 실패한 실행의 대상 행에 스키마별 결과가 남는다.
- **작업 식별** : 작업 아이디(`JOB_ID`, UNIQUE)는 서버가 만든다 — 사용자 요청은 UUID, 비동기·배치는 서버가 만든 실행 컨텍스트의 작업 ID. 실행은 같은 프로젝트에서,
  사람의 요청이면 같은 요청자, 작업 컨텍스트면 같은 작업 ID 로만 찾을 수 있다 (다른 실행의 아이디를 알아도 결과를 넣거나 볼 수 없다).
- **멱등성** : 같은 작업을 다시 등록하면 같은 실행, 이미 반영된 작업을 다시 반영하면 아무것도 바꾸지 않고 그 실행을 돌려준다. 끝난(FAILED·CANCELLED) 작업은 다시 반영할 수 없다 — 새 작업으로 다시 수집한다.
- **권한** : 사람의 요청(사용자·비동기)은 등록·반영 때마다 지금도 그 프로젝트의 관리자이거나 ADMIN 인지 DB 로 다시 본다. 정기 배치는 프로젝트 상태만 본다 (`ExecutionContextVerifier`).
- **입력 경로** : 수집 결과를 받는 공개 API 는 없다. `SourceCollectionService` 는 서버 안의 수집 경로(AI-2)와 테스트만 부른다.

## 3. 전체 수집 · 부분 수집

| | FULL | PARTIAL (스키마 단위) |
|---|---|---|
| 등록 | 스키마를 지정하지 않는다 | 대상 스키마를 지정한다 (대상 행 SKIPPED 로 만든다) |
| 결과 | 스키마 하나 이상 (빈 결과는 실패 : 전체 삭제로 이어지지 않게) | 요청한 스키마와 같아야 한다. 요청하지 않은 스키마가 있으면 거절 |
| 비교 범위 | 결과의 스키마 + 현재 있는 모든 스키마 | 요청한 스키마만 |
| 사라진 스키마 | 결과에 없으면 EXST_YN = false + REMOVED 버전 | 판정하지 않는다. 요청한 스키마가 원본에 없으면 NOT_FOUND → **실행 실패** (스키마를 지우지 않는다) |
| 사라진 테이블·컬럼 | 완전하게 수집한 스키마 안에서만 판정 | 같음 (범위 밖은 건드리지 않는다) |

- 수집 도구는 스키마마다 **완결 여부**를 알린다 (`SourceCollectionSpec.Schema.status`). 그 스키마의 모든 객체를 빠짐없이 읽었을 때만 COMPLETED 다.
  하나라도 COMPLETED 가 아니면 실행 전체를 반영하지 않는다 → 일부만 읽힌 스키마를 삭제로 잘못 판정하지 않는다.
- **급격한 객체 감소** : 감소율 임계값은 정하지 않았다 (결정 사항, 10장). 지금 있는 검증 지점은 범위·완결성 확인과 빈 FULL 결과 거절이다. 실행의 건수(`TBL_CNT`·`COL_CNT`)와 변경 이력으로 감소량을 볼 수 있다.

## 4. 변경 감지

### 4.1 식별 (비교 키)

| 객체 | 비교 키 |
|---|---|
| 스키마 | 비교 경로 (`PATH_CN`) |
| 테이블 | 스키마 + 비교 명 |
| 컬럼 | 테이블 + 비교 명 |
| 제약조건 | 유형 + 이름. 이름이 없거나 DBMS 가 붙인 이름(Oracle `SYS_…`)이면 유형 + 구성 컬럼(+ CHECK 조건식) |
| 인덱스 | 이름. DBMS 가 붙인 이름이면 고유 여부 + 구성 컬럼 |
| 관계 | 이름. 이름이 없거나 DBMS 가 붙인 이름이면 구성 컬럼 → 참조 카탈로그·스키마·테이블(구성 컬럼) |

- 비교 명은 AI-1b 의 `SourceIdentifiers` 그대로다 (DBMS 별 대소문자 접기, 따옴표 여부를 모르면 접지 않음, MySQL·MariaDB 는 연결의 비교 규칙).
- 같은 키가 둘이면(이름 없는 같은 구성) 정렬한 뒤 `#2`, `#3` 을 붙인다 — 수집 결과와 현재 행이 같은 키를 갖는다.
- 제약조건·인덱스·관계는 적재 때마다 내부 일련번호가 바뀌므로(종류별로 통째로 바꾼다) 이력은 일련번호가 아닌 비교 키(`TRGT_IDNTFR_CN`)로 가리킨다.

### 4.2 정규화 JSON · 해시 (`SourceCatalogCanonical`, 형식 1)

- 해시 = `v1:` + SHA-256(정규화 JSON). 테이블 해시(`TB_SRC_TBL.HASH_VL`)는 테이블과 하위 객체 전체, 컬럼 해시(`TB_SRC_COL.HASH_VL`)는 컬럼 하나.
- **넣는 것** — 컬럼 : 원본 이름, 비교 명, 따옴표 여부, 순서, 타입 표현, 길이, 정밀도, 소수 자릿수, NULL 허용, 기본값 원문, 원본 COMMENT.
  테이블 : 원본 이름, 비교 명, 따옴표 여부, 유형, 원본 COMMENT, 스키마 비교 경로, 컬럼·제약조건(키·이름·유형·조건식·구성 컬럼)·인덱스(키·이름·방식·고유·구성 컬럼)·관계(키·이름·참조 카탈로그·스키마·테이블·규칙·컬럼 쌍).
  스키마 : 비교 경로, 카탈로그·스키마 이름.
- **넣지 않는 것** — Lexorma 일련번호, 감사 컬럼, 수집 실행·시각, 존재 여부, Lexorma 가 이은 내부 참조(관계의 `RFRNC_SRC_TBL_SN` 등). 테이블 JSON 에 스키마 이름(표기)을 넣지 않는다 : 스키마 표기가 바뀌어도 모든 테이블이 바뀐 것으로 보이지 않게.
- **정규화 규칙** : 필드 순서 고정. 컬럼은 원본 순서(같으면 비교 명), 하위 객체는 비교 키 순서, 구성 컬럼 순서는 그대로. 문자열은 다듬지 않고 NULL 과 빈 문자열을 구분한다
  (단 저장 규칙상 빈 값을 NULL 로 바꾸는 이름·규칙은 미리 바꾼다). 타입 표현·기본값은 원본 표현 그대로 쓰고 다시 쓰지 않는다. 정밀도는 뒤쪽 0 을 지운 숫자 문자열(`64`, `64.00` → `"64"`).
  하위 객체가 가리키는 컬럼은 비교 명. 정밀도는 저장 칸(NUMERIC(38,2))에 그대로 들어가는 값만 받는다 (반올림 저장으로 다음 수집이 바뀐 것으로 보이지 않게).
- **규칙이 바뀌면** 형식 번호와 접두사를 올린다. 접두사가 다른(또는 없는) 해시는 비교하지 않고 현재 행으로 새 규칙의 JSON 을 만들어 비교한다 : 같으면 해시만 고치고(버전·이력 없음) 다르면 변경이다.

### 4.3 비교 절차 (`SourceCatalogLoader`) : 원본 변경 감지와 현재 상태 복구를 나눈다

**원본 변경 감지 (버전·이력)** — 마지막 확정 버전 ↔ 수집 결과. 현재 카탈로그는 보지 않는다.

| 마지막 확정 버전 | 수집 결과에 있다 | 수집 결과에 없다 (완전하게 수집한 범위) |
|---|---|---|
| 없다 | 처음 수집한 이름 공간이면 `BASE`, 아니면 `ADDED` | 버전·이력 없음 (원본에서 확인한 적이 없다) |
| 삭제 표시 | `ADDED` (새 생명주기 : 생성 차수 + 1) | 없음 (다시 삭제 표시를 만들지 않는다) |
| 원본에 있던 것 | 해시가 같으면 없음, 다르면 `MODIFIED` (변경 전 = 마지막 버전 내용) | `REMOVED` (삭제 표시 내용 = 마지막 버전 내용) |

- 마지막 버전은 요약(해시·유형·형식)만 한 번에 읽고, 바뀌거나 사라진 테이블의 내용만 따로 읽는다. 형식 번호가 다른 버전은 해시를 비교하지 않고 `MODIFIED` 로 본다 (형식을 바꿀 때 변환 규칙이 필요하다).
- 스키마도 같다 : 마지막 스키마 버전과 비교한다.

**현재 상태 복구 (현재 카탈로그만)** — 현재 카탈로그 ↔ 수집 결과. 버전·이력을 만들지 않는다.

1. 범위 안의 스키마·테이블을 한 번에 읽는다 (읽기 전용 : 영속성 컨텍스트가 스냅숏을 두지 않는다).
2. 테이블 해시가 지금 규칙의 것이고 수집 결과의 해시와 같으면 **읽지도 고치지도 않는다**. 해시가 다르거나 없는 테이블(Writer 가 고치면 해시를 지운다), 다시 생긴 테이블, 사라진 테이블만 컬럼·하위 객체를 1,000개 단위로 나눠 읽는다.
3. 현재 행으로 만든 JSON 과 수집 결과의 JSON 을 비교해 바뀐 칸·바뀐 하위 객체 종류만 고친다. 같으면 해시만 고친다.

반영이 끝나면 원본에 있는 테이블마다 **현재 해시 = 마지막 확정 버전의 해시**이고, 사라진 테이블의 마지막 버전은 삭제 표시다 (테스트가 확인한다).

| 시나리오 (v1 = 100) | Writer 로 고친 현재 카탈로그 | 수집 결과 | 결과 |
|---|---|---|---|
| A | 200 | 200 | 현재 카탈로그는 그대로(해시만), **v2 = 200, 이력 100 → 200** |
| B | 200 | 100 | 현재 카탈로그를 100 으로 복구, **버전·이력 없음** |
| C | 200 | 300 | 현재 카탈로그 300, **v2 = 300, 이력 100 → 300** (Writer 의 200 은 이력에 없다) |
| D | 고친 뒤 FULL 에서 사라짐 | 없음 → 없음 → 다시 있음 | 삭제 표시 한 번(원본 마지막 상태), Writer 가 되살린 행이 다시 빠져도 중복 없음, 재등장 `ADDED` 생성 차수 2 |

### 4.4 이름 변경 · 재등장

- 비교 키가 달라지면(이름 변경) 기존 객체 `REMOVED` + 새 객체 `ADDED` 다. **같은 객체라고 자동으로 확정하지 않는다** (후보 테이블·화면은 범위 밖, 10장).
- 사라졌던 같은 이름이 다시 생기면 `ADDED` 를 남기고 같은 현재 행을 되살리며 **생성 차수**(`CRT_CYCL`)를 1 올린다. 버전·이력에 생성 차수가 있어 이전 생명주기와 구분된다.
  지난 버전은 덮어쓰지 않는다 (반영 순서가 다른 새 행이다).

## 5. 현재 카탈로그 갱신

| | 현재 카탈로그 | 버전 | 변경 이력 |
|---|---|---|---|
| 처음 수집한 이름 공간 (기준) | 추가·갱신 | 스키마·모든 테이블 `BASE` | 없음 |
| 생긴 스키마·테이블 | 추가 (EXST_YN = true, 해시) | `ADDED` | `ADDED` (테이블 행 하나에 그 테이블 전체가 이후 값) |
| 바뀐 테이블 (마지막 버전과 다르다) | 바뀐 칸만 UPDATE, 하위 객체는 바뀐 종류만 통째로 교체 | `MODIFIED` | 마지막 버전 대비 바뀐 객체마다 `ADDED`·`MODIFIED`(바뀐 항목·전후)·`REMOVED` |
| 현재 카탈로그만 다르다 (Writer 등) | 수집 결과로 복구 | 없음 | 없음 |
| 사라진 스키마·테이블 | EXST_YN = false (테이블은 컬럼도 false, 제약조건·인덱스·관계는 지운다 : 마지막 상태는 삭제 표시 버전에 있다) | `REMOVED` (삭제 표시, 마지막 상태 JSON) | `REMOVED` (이전 값) |
| 사라진 컬럼 | EXST_YN = false | 테이블 `MODIFIED` | 컬럼 `REMOVED` |
| 변경 없음 | **UPDATE 없음** | 없음 | 없음 |

- "처음 수집한 이름 공간" = 그 연결에 반영된 FULL 수집이 없었고, 그 이름 공간을 완전하게 수집한 반영된 실행도 없었다. FULL 수집이 한 번 반영된 뒤 새로 보이는 스키마는 `ADDED` 다.
- 사람이 고치는 값(업무 설명·물리 모델)은 읽지도 쓰지도 않는다.

## 6. 과거 상태 재구성 (`SourceSnapshotService`, 읽기 전용)

- 반영 순서 R 의 상태 = 스키마·테이블마다 **R 이하의 마지막 버전** (`REMOVED` 면 그때 없던 것). 빈 스키마도 스키마 버전으로 재구성된다. 시각으로 물으면 그 시각까지 반영된 마지막 실행의 반영 순서다.
- 응답에는 객체마다 **마지막 확인 반영 순서**(`lastConfirmedOrder` : R 까지 그 이름 공간을 완전하게 수집한 마지막 실행)가 있다. 부분 수집 뒤에는 스키마마다 다르다.
- 이것은 **"R 시점에 Lexorma 가 확인해 둔 카탈로그"** 다. 원본 DB 를 그 시점으로 되돌린 것이 아니고, 원본 DB 를 되돌리는 기능(DDL 생성·실행)은 없다.

| API (VIEWER 이상, `/api/source/**` → 요청 로그 본문 `[PROTECTED]`) | 내용 |
|---|---|
| `GET /connections/{id}/collections` | 수집 실행 목록 (최근 것부터, 쪽 단위) |
| `GET /collections/{executionId}` | 실행 상세와 대상별 결과 |
| `GET /collections/{executionId}/changes` | 그 실행의 변경 이력 (쪽 단위) |
| `GET /connections/{id}/snapshot?order=&at=` | R 의 스키마 목록 |
| `GET /connections/{id}/snapshot/schemas/{schemaId}/tables?order=&at=` | R 의 한 스키마의 테이블 목록 |
| `GET /tables/{tableId}/snapshot?order=&at=` | R 의 테이블 하나 (정규화한 내용) |
| `GET /tables/{tableId}/versions`, `GET /tables/{tableId}/changes` | 테이블의 버전·변경 이력 (여러 실행에 걸쳐) |

## 7. 보관

- **지금은 아무것도 자동으로 지우지 않는다** : 실행·대상·버전·이력을 모두 보관한다. 연결·프로젝트 영구 삭제 때만 함께 지운다 (U-25).
- 나중에 보관 기간을 더할 때의 규칙 (미구현) : 경계 반영 순서 C 를 정하면 테이블·스키마마다 **C 이하의 마지막 버전 하나를 남기고**(새 기준 상태) 그 이전 버전과 C 이하의 변경 이력을 지운다.
  C 이전에 사라진 객체(마지막 버전이 REMOVED)는 버전을 모두 지울 수 있다. 이렇게 하면 C 이후의 모든 시점이 그대로 재구성된다. AI 결과의 근거로 쓰인 실행을 남길지는 정할 일이다.

## 8. 동시성

- **잠금 순서는 모든 경로에서 프로젝트(공유) → 연결(배타)** 다 : 수집 등록·반영·실패 기록·취소, 연결 수정·삭제, AI-1b 의 `SourceCatalogWriter`.
  프로젝트 영구 삭제는 프로젝트 행을 배타 잠금으로 잡은 뒤 하위 행을 지우므로 같은 순서다. `ProjectWriteGuard.lock(projectId)` 가 프로젝트 행을 바로 잠근다 (AI-1c 에서 core 에 더했다).
  - 예전 `SourceCatalogWriter` 는 연결을 먼저 잠그고 커밋 직전에 프로젝트를 잠가, 프로젝트 삭제(프로젝트 → 연결)와 서로를 기다릴 수 있었다 → 고쳤다 (테스트 : 한 건 단위 경로와 프로젝트 삭제의 동시 실행).
  - H2 는 공유 잠금이 배타 잠금으로 동작해 같은 프로젝트의 반영끼리도 차례로 돈다 (PostgreSQL 은 `FOR SHARE` 라 서로 막지 않는다).
- **연결 삭제 ↔ 반영** : 반영이 먼저 커밋하면 삭제가 그 결과(실행·버전·이력 포함)까지 지우고, 삭제가 먼저면 반영은 연결이 없어 `SOURCE_CONNECTION_NOT_FOUND` 로 롤백된다.
- **프로젝트 삭제 ↔ 반영** : 반영이 먼저면 삭제가 다 지우고, 삭제가 먼저면 반영은 `PROJECT_NOT_FOUND` 로 롤백된다. 실행 행도 함께 지워지므로 실패 기록을 다시 만들지 않는다.
- **같은 연결의 중복 수집** : 진행 중인 실행만 `PRGRS_CNTN_SN` 에 연결 ID 를 넣고 UNIQUE 로 묶는다 (NULL 은 여럿 : H2·PostgreSQL 같음). 등록은 연결 행을 잠근 채 확인하고 DB 제약이 한 번 더 막는다.
- **연결 수정** : 연결 행을 잠근 뒤 카탈로그 유무를 본다 — 진행 중인 반영과 DB 유형·비교 규칙 변경이 엇갈리지 않는다. 반영은 시작할 때의 규칙과 지금 규칙이 다르면 거절한다.
- **동시성 테스트** : 고정 대기에 기대지 않는다. 앞의 트랜잭션을 래치로 열어 둔 채 뒤의 것을 시작하고, **DB 가 알려 주는 잠금 대기**(PostgreSQL `pg_stat_activity.wait_event_type = 'Lock'`,
  H2 `INFORMATION_SCHEMA.SESSIONS.BLOCKER_ID`)가 생길 때까지 기다린 뒤 앞의 것을 커밋한다. 기다리는 문장이 어느 테이블의 잠금인지로 잠금 순서를 확인한다 (프로젝트 삭제와의 경합은 `TB_PRJ` 에서 기다린다 = 앞의 것이 프로젝트를 먼저 잡았다).
  뒤의 것이 잠금을 기다리지 않고 끝나면 테스트가 실패한다 (경합이 일어나지 않은 통과를 막는다).
- **멈춘 실행** : 실행 행에 맡은 서버(`EXCN_SRVR_ID` = 호스트명/기동마다 바뀌는 값)와 살아 있음 확인 시각(`LAST_IDNTY_DT`)을 둔다. 정리는
  ① 이 서버의 실행인데 이 서버에서 돌고 있지 않을 때(바로), ② 다른 서버(재시작 전의 이 서버 포함)의 실행인데 확인 시각이 `lexorma.source.collection.stale-after`(기본 10분)보다 오래됐을 때만 한다.
  정리는 읽은 확인 시각이 그대로일 때만 바뀐다(조건부 UPDATE) — 그사이 살아 있음 확인이 들어오면 정리하지 않는다. 새 등록이 막힐 때와 `recoverAbandoned` 에서 판단한다. 긴 수집(AI-2)은 `heartbeat` 를 불러야 한다.

## 9. 성능

`SourceCollectionPerformanceTest` (기본 빌드에서 제외, `LEXORMA_PERF=true`). 테이블마다 PK 1, 2컬럼 인덱스 1, 앞 테이블로 가는 FK 1. 1% 변경 = 테이블 1% 의 모든 컬럼 COMMENT 수정 + 테이블 1개 추가 + 1개 삭제.
SQL 문 = Hibernate 통계의 준비한 문장 수(배치는 묶음 하나), 할당 = 그 스레드가 할당한 바이트 합(남아 있는 메모리가 아니다). 2026-11-13 정합성 보완 뒤, 개발 PC(Apple Silicon), JVM 기본 설정, 측정 1회.

|---|---|---:|---:|---:|---:|---:|---:|
| 100 / 1,000 | 최초 적재 | 293 | 345 | 71 | 101 | 0 | 59 |
| | 변경 없음 | 32 | 51 | 21 | 0 | 0 | 8 |
| | 1% 변경 | 53 | 82 | 50 | 3 | 12 | 10 |
| 1,000 / 20,000 | 최초 적재 | 924 | 1,236 | 610 | 1,001 | 0 | 344 |
| | 변경 없음 | 67 | 82 | 21 | 0 | 0 | 119 |
| | 1% 변경 | 108 | 146 | 46 | 12 | 202 | 127 |

- 같은 측정을 보완 전에 한 번 했을 때 PostgreSQL 3,000/60,000 최초 적재가 7,853ms 였다 (나머지는 비슷). 한 번씩만 재서 이 차이가 코드 때문인지 측정 편차인지는 가리지 않았다.
- 변경 없는 수집은 규모와 상관없이 SQL 문이 21개다 (테이블 해시로 걸러 하위 객체를 읽지 않는다). 할당의 대부분은 트랜잭션 밖의 정규화·해시 계산이다.
- 같은 내용을 AI-1b 의 한 건 단위 경로로 넣으면 SQL 문이 약 110배(71 → 8,034), 시간이 약 5배(PostgreSQL)다.
- **JPA 배치를 택했다** (JDBC 배치 대신) : 읽은 행을 읽기 전용으로 두고 새 행은 `hibernate.jdbc.batch_size: 500` 배치 INSERT 로 쓰면 위 수치가 나온다.
  JDBC 로 직접 쓰면 감사 컬럼·시퀀스 할당·`ProjectWriteGuard.guard`·영속성 컨텍스트 정리를 손으로 맞춰야 하고, 9개 테이블의 SQL 을 따로 관리해야 한다. 수십만 컬럼 규모에서 다시 볼 일이다.
- 최초 적재 3,000/60,000 (PostgreSQL 3~8초)은 한 트랜잭션이다 (그동안 그 연결의 삭제·다른 반영이 기다린다). 원인 분석·튜닝(`reWriteBatchedInserts` 등)은 하지 않았다.

## 10. 남은 일 · 결정할 일

- **AI-2 가 지킬 계약** : `SourceCollectionService.start → (원본 조회, 도는 동안 heartbeat) → apply` 또는 `fail(errorCode)`. 스키마마다 완결 여부와 오류 코드(대문자·숫자·밑줄만 남는다)를 알린다.
  결과는 `SourceCollectionSpec` (테이블 내용은 AI-1b 의 `SourceCatalogSpec`). 원본 DB 조회는 반영 트랜잭션 밖에서 한다.
- 결정 사항 : 급격한 감소 경고·승인 정책(임계값), 보관 기간과 기준 상태 갱신 주기(7장), 이름 변경 후보(테이블·화면), 사라진 객체의 행을 언제 물리 삭제할지, 컬럼 순서를 해시에 넣는 것의 영향(MySQL 은 컬럼 하나를 지우면 뒤 컬럼 순서가 모두 바뀐다), 대형 최초 적재를 나눠 반영할지.
- 미구현 : 멈춘 실행의 주기적 정리 스케줄러(지금은 새 등록·`recoverAbandoned` 에서만), 화면, 시점 비교(두 반영 순서의 차이) API, 관계의 내부 참조를 사라진 테이블에서 떼어 내는 정책.
