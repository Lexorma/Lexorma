## 1. 작업 배경

M-6 은 슈퍼타입·서브타입을 논리 모델에만 구현했고(D-30·D-32·D-45), 물리 생성 미리보기는 상속 참여 엔터티를 `UNSUPPORTED`, 부모가 참여하는 관계 FK 를 `INHERITANCE_UNSUPPORTED` 로 건너뛴다. 이번 작업은 그 변환 전략·매핑·보호 정책을 설계한다.

## 5. 기존 물리 생성기 분석 (`mapping/service/PhysicalGenerationService`)

- API : `POST /api/modelMapping/generate/preview`·`/generate` (USER, 메뉴 `model-mapping-edit`). 한 요청 엔터티 최대 100 (`ENTITY_MAX`).
- 흐름 : `computePlan` — 엔터티 일괄 로드 → 매핑 조회 → `subtypeService.hierarchyOf(modelIds)` → **상속 참여면 `UNSUPPORTED`(매핑돼 있어도), 매핑돼 있으면 `SKIP`** → 테이블명(`generateTableName`) → `relationPlans`(짝 COMPLETE 만 FK, 부모 참여면 `INHERITANCE_UNSUPPORTED`) → 컬럼(`columnOrder` : 주 식별자 순서 → 속성 순서, `columnSpec` : 표준 용어 영문 약어·도메인 타입) → 식별자 진단(`DbIdentifierCheck`) → planToken.
- 상속 제외 위치 : 엔터티(`inheritance.participates(entity)`), 관계(`inheritance.participates(parent)`). 짝 판정은 이미 유효 주 식별자(`inheritance.root`)로 한다.
- 생성 : `apply` — 프로젝트 행 배타 → 논리 모델 행·대상 스키마 행 NOWAIT(409) → 계획 재계산·planToken 비교(409 `MODEL_CONFLICT`) → `GENERATE-<uuid>` 모델 버전 → 테이블·컬럼·엔터티 매핑·속성 매핑(모두 미승인) → FK (단일 = 자식 컬럼 `refTableName` → 커밋 직전 REF_COLUMN 동기화, 자기 참조·복합 = `createGeneratedForeignKey` TableRelation). 실패하면 버전까지 전체 롤백.
- planToken v6 : 스키마·DBMS·엔터티 `MDFCN_DT`·상태·제외 속성·속성/용어 `MDFCN_DT`·컬럼 계획·관계 계획(짝·컬럼명·부모 테이블·FK 이름)·식별자 진단. **상속은 "UNSUPPORTED" 상태로만 들어간다** — 그룹 구성·분류 값·Disjoint/Total 은 토큰에 없다 (그룹 변경은 엔터티 `MDFCN_DT` 를 바꾸지 않지만, 참여 여부가 바뀌면 상태가 바뀌어 409 가 된다).
- 기존 매핑된 부모의 컬럼 찾기 : `attributeMappings.findByAttribute_Id(짝의 부모 속성)` → 그 컬럼이 부모 테이블 것이어야 한다. **속성 ID 만으로 컬럼을 찾는다** — 부모가 서브타입이면 짝의 부모 속성은 루트 PK 속성이라 루트 테이블 컬럼이 나와 서브타입 테이블과 맞지 않는다(24장의 충돌).
- **보조 식별자 → UNIQUE 생성은 없다** (현재 생성기는 PK·FK 만). 정합성도 "대체 식별자·UNIQUE 는 보지 않는다". pending [M-7] 의 "보조 식별자 ↔ UNIQUE 비교" 후속과 같은 범위.

| 정합성 비교 | 엔터티 ↔ 테이블 다대일 비교 필요 | 직접 속성 그대로 + 상속 PK 연결만 추가 | 속성 ↔ 다수 컬럼 비교 필요 |
| DB 변경 | 필요 (매핑 UNIQUE) | 상속 PK 매핑 방식에 따라 (12장) | 필요 (속성 매핑 UNIQUE) |
| 구현 복잡도 | 중 | 중 (PK 복사·FK·매핑) | 상 |

권장 지원 순서 : **B 먼저, A·C 는 후속** (M-6 D-30·D-32 와 같다). B 만 기존 1:1 매핑·D-11(가상 상속)·D-18(관계 복제 없음)·D-19 를 그대로 둔다. A·C 를 위한 전략 테이블·추상화는 지금 만들지 않는다.

## 7. B형 상세 변환

예 (영문 컬럼명은 실제 표준 용어 영문 약어를 쓴다 — 아래는 설명용) :

```
고객(루트)       : 고객 ID(주 식별자), 고객명          → TB_CUST       : CUST_ID PK, CUST_NM
개인 고객(서브) : 생년월일                            → TB_INDV_CUST : CUST_ID PK + FK→TB_CUST, BRDT
법인 고객(서브) : 사업자등록번호                      → TB_CORP_CUST : CUST_ID PK + FK→TB_CUST, BRNO
```

- 테이블명 : 기존 규칙(엔터티명 → 표준 단어, `generateTableName`) 그대로.
- 서브타입 테이블 컬럼 = **상속 PK 컬럼(루트 주 식별자 속성마다, 루트 식별자 순서)** + 직접 속성 컬럼(기존 `columnOrder`). 상속 PK 컬럼은 원본 속성의 표준 용어·약어·도메인(`columnSpec(원본 속성)`)으로 만들어 루트 PK 와 이름·타입·길이가 같다. NOT NULL·PK.
- 상속 일반 속성 : 복제하지 않는다 (정의 엔터티 테이블에만). 서브타입 테이블에 없어도 정상.
- 중간 슈퍼타입 : 자기 테이블 = 상속 PK + 직접 속성, 직계 부모로 FK.

### 7.1 3단계 상속 — 상속 FK 대상

| 대안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **직계 부모 (권장 M7-D04)** | TB_일반개인 → TB_개인 → TB_고객 | 논리 단계 보존, 부모 타입 존재 보장(일반 개인이면 개인 행도 있다), 중간 엔터티 의미 표현 | 루트 조회에 조인 단계 증가 |
| 루트 직접 | 모든 하위 → TB_고객 | 조인 단순 | 중간 타입 행 없이 손자 행 가능 — 계층 의미 손실 |

PK 유일성은 두 방식 모두 같다. DDL 은 FK 를 `ALTER TABLE` 로 따로 내므로(`TableDdlGenerator`) 생성 순서 문제 없음. 삭제 무결성은 기본 NO ACTION (기존 생성 FK 와 같이 규칙 없음).

### 7.2 복합 주 식별자

루트 PK(기관 ID, 고객 ID) → 서브 PK 같은 두 컬럼(루트 식별자 순서), **복합 FK 하나** → 부모(직계) PK. 기존 `createGeneratedForeignKey`(복합·TableRelation, 미승인) 와 M-2 "FK 하나 = 선 하나" 를 그대로 쓴다. 단일 PK 는 기존처럼 자식 컬럼의 `refTableName`(REF_COLUMN 동기화) — PK 이면서 FK 인 컬럼도 지금 지원된다. 제약 이름은 기존 `DbIdentifierRules.foreignKeyName`·PK 이름 규칙과 식별자 진단(길이·충돌)을 그대로 거친다.

### 7.3 복수 그룹

슈퍼타입 하나에 그룹이 여럿이어도 B 는 그룹과 무관하게 서브타입마다 테이블 1개·직계 FK 1개. 서브타입은 그룹 하나에만 속하므로(단일 상속) 충돌 없음.

## 8. 상속 PK 및 FK — 요약 (M7-D03·D04)

| 항목 | 권장 |
|---|---|
| 서브타입 PK | 루트 주 식별자 속성 집합, 루트 식별자 순서 (D-15 그대로) |
| 상속 FK | 직계 슈퍼타입 테이블 PK 참조, 복합이면 FK 1개 |
| 루트에 주 식별자가 없음 | 서브타입 생성 불가(ERROR — 상속 PK 를 만들 근거 없음). 지금 비상속 엔터티는 "PK 없이" 경고로 만들지만 서브타입은 FK 를 만들 수 없다 |
| 물리 관계 유형 | 새 유형 없이 기존 FK(REF_COLUMN 단일 / USER TableRelation 복합). 상속 FK 를 표시해야 하면 "생성 출처" 문제(M7-D21)로 따로 결정 |

## 9. 대체 식별자 (M7-D06)

- 현재 생성기는 보조 식별자 → UNIQUE 를 **만들지 않는다** (상속과 무관한 기존 범위).
- B 에서 상속 보조 식별자 : 정의 엔터티 테이블에만 (D-17 "물리 UNIQUE 는 속성이 놓이는 테이블에서만"). 하위 테이블에 복제하지 않는다 — 상위 집합에서 유일하면 부분집합에서도 유일.
- 서브타입 자체 보조 식별자 : 직접 속성만(D-17) → 서브타입 테이블에 놓인다.
- 권장 : **이번 B 구현에서 UNIQUE 생성은 넣지 않는다** (보조 식별자 → UNIQUE 는 상속 없는 엔터티도 안 되는 기존 후속 — pending [M-7] "보조 식별자 ↔ UNIQUE"). 넣기로 하면 모든 엔터티에 같은 규칙으로 (NULL 허용 속성 포함 시 DBMS 별 NULL 유일성 차이 경고).

## 10. 상속 일반 관계 (M7-D14·D15)

| 경우 | B 물리 FK |
|---|---|
| 일반 엔터티(주문) → 슈퍼타입(고객) | 주문의 FK → **TB_고객** (관계가 정의된 부모 엔터티의 테이블). 서브타입마다 복제하지 않는다 (D-18) |
| 서브타입(개인 고객)이 부모인 관계 (개인 고객 → 인증) | FK → **TB_개인고객** PK. 짝의 부모 속성 = 루트 PK 원본 속성 ID (D-19) |
| 서브타입이 자식 (개인 고객 → 다른 엔터티 참조) | 자식 속성 = 서브타입 직접 속성 → 기존과 같다 |

**엔터티 문맥이 필요하다** : 원본 속성 ID 하나가 TB_고객.CUST_ID·TB_개인고객.CUST_ID·TB_법인고객.CUST_ID 를 모두 가리킨다. 물리 컬럼 = (관계의 부모 엔터티 → 그 엔터티의 테이블, 원본 속성 ID) 로 정해야 한다. 지금 `relationPlans` 의 기존 부모 경로(`findByAttribute_Id` + 테이블 필터)는 서브타입 부모에서 실패하므로 바꿔야 한다 — 새 테이블이면 "계획의 상속 PK 컬럼", 기존 테이블이면 12장의 상속 PK 매핑으로 찾는다.

생성 순서 (기존 재사용) : ① 대상·상태 확정 ② 테이블·컬럼(상속 PK 포함) 계획 ③ PK ④ 상속 FK 계획 ⑤ 일반 FK 계획(부모 테이블·컬럼을 엔터티 문맥으로) ⑥ 식별자 진단·충돌 ⑦ 미리보기·planToken ⑧ 반영 : 테이블·컬럼 → flush → FK(상속·일반) → 매핑. 지금 `apply` 가 "모든 테이블·컬럼 → FK" 순서라 상속 FK 를 같은 루프에 넣을 수 있다.

## 11. 그룹 제약조건 보장 (M7-D09~D13)

| 조합 | 기본 PK·FK 로 보장 | 보장 안 됨 | 추가 구조 후보 |
|---|---|---|---|
| Disjoint + Total | 서브 행 → 부모 행 존재 | 여러 서브 테이블에 같은 키(배타), 부모 행에 서브 행 1개 이상(완전) | 배타 : 분류 컬럼 + 부모 UNIQUE(PK, 분류) + 서브 테이블 고정값 CHECK + 복합 FK. 완전 : 트리거·지연 제약 |
| Disjoint + Partial | 존재 | 배타 | 위 배타 구조 |
| Overlapping + Total | 존재 | 완전 | 트리거 |
| Overlapping + Partial | 존재, 중복 허용·선택 참여 (FK 의 성질과 같다) | — | — |

- 배타(Disjoint) 구조는 (a) 서브 테이블에 논리 모델에 없는 분류 컬럼을 더하고 (b) 분류 값을 SQL `CHECK` 리터럴로 바꿔야 한다 → M-6 "실행 SQL 조건 입력 금지"·D-11(복제 없음)과 충돌한다. 트리거 생성·배포는 범위 밖(메타데이터 도구, 업무 DB 에 실행하지 않음).
- 권장 : **PK·FK 만 만들고 그룹 제약은 "물리 미보장" 으로 미리보기·결과에 표시** (Overlapping+Partial 은 FK 로 의미가 그대로라 표시 불필요). 저장하지 않는 계산 값 :

| 표시 (제안, 기존 코드와 겹치지 않는 이름) | 뜻 |
|---|---|
| `ENFORCED` | 만든 PK·FK 로 보장 (부모 존재) |
| `NOT_ENFORCED` | 만든 물리 제약으로 보장하지 않음 (Disjoint 배타, Total 완전) |
| `NOT_APPLICABLE` | 그 조합에 해당 없음 (Overlapping 의 배타, Partial 의 완전) |

  `PARTIALLY_ENFORCED`·`NOT_COMPARABLE` 은 B 의 PK·FK 만으로는 쓸 경우가 없어 두지 않는 것을 권장. "생성 가능 여부(creatable)" 와 "업무 제약 보장" 은 따로 둔다 (미보장은 경고, 생성을 막지 않는다).
- 구분 속성 : 원본 정의 위치(슈퍼타입 또는 그 조상의 직접 속성)의 테이블 컬럼으로만 존재. 자동 생성·복제·값 CHECK 하지 않는다. 구분 속성이 없는 그룹도 B 는 만들 수 있다.

## 12. 상속 PK 매핑 대안 (M7-D08·D26 — 핵심)

| 기준 | 대안 1 조회 시 계산 (저장 없음) | 대안 2 별도 저장 (새 테이블) | 대안 3 기존 속성 매핑 확장 |
|---|---|---|---|
| 방법 | 서브 테이블 PK 컬럼 ↔ 원본 속성을 "직계 부모로 가는 FK 의 컬럼 쌍 → … → 루트 테이블 매핑 컬럼" 으로 따라가 계산 | `(엔터티 매핑, 원본 속성, 컬럼)` 행을 생성 때 저장 | `UX_ATRB_COL_MPNG_01` 을 (엔터티 매핑, 속성)으로 바꾸고 소속 검증을 "유효 속성" 으로 |
| DB 변경 | 없음 | V4 새 테이블 | V4 인덱스 변경 |
| 정확성 | FK 가 지워지거나 바뀌면, 부모가 다른 테이블에 매핑되면, FK 가 둘이면 계산 불가·오판. 이름으로 대신하면 불안정 | 컬럼·테이블 이름 변경과 무관하게 정확 (ID) | 정확 |
| 기존 데이터·소비자 | 영향 없음 | 영향 없음 (직접 매핑 그대로) | **속성 → 컬럼 하나를 가정하는 곳 전부** : 생성기 `findByAttribute_Id`, 매핑 화면, 정합성, 교환 가져오기, AI 도구 응답 |
| 매핑 UI | 표시만 (편집 없음) | 표시 + (선택) 수동 연결 | 기존 화면에서 상속 속성 선택 허용 |
| 정합성 | 계산 실패를 "판단 불가" 로 | "상속 PK 연결 확인" 별도 상태 | 직접 매핑과 섞임 |
| 스냅샷·교환 | 변경 없음 | 새 자식 행 → 스냅샷 9·교환 6 필요 (형식 1~5 읽기 유지) | 행 의미 변경 → 형식 판단 필요 |
| 삭제·해제 | 고려 없음 | 엔터티 매핑 삭제 시 함께 삭제, 원본 속성 삭제·상속 해제 보호 규칙 추가 | 기존 규칙 수정 |
| 재생성·수동 수정 | 불가 | 가능 | 가능 |
| A·C 확장 | 불가 | C 의 "속성 → 여러 컬럼" 에 그대로 쓸 수 있다 | A·C 모두 기반 |
| 복잡도 | 낮음(구현) / 높음(정확성) | 중 | 상 |

권장 : **대안 2** (기존 직접 매핑 무변경 + 상속 PK 매핑을 명확히 구분, 추론 없음). 후보 테이블 (기존 단어만 — 서브타입 `SBTYP`·식별 `IDNTF`·컬럼 `COL`·매핑 `MPNG`, 새 단어 없음) :

```
TB_SBTYP_IDNTF_COL_MPNG  (서브타입 식별 컬럼 매핑)
  SBTYP_IDNTF_COL_MPNG_SN  bigint PK (SQ_SBTYP_IDNTF_COL_MPNG)
  PRJ_SN                   bigint not null (프로젝트 격리·ProjectWriteGuard)
  ENTT_TBL_MPNG_SN         bigint not null FK → TB_ENTT_TBL_MPNG (서브타입 엔터티 ↔ 테이블)
  LGCL_ATRB_SN             bigint not null FK → TB_LGCL_ATRB (루트 주 식별자의 원본 속성)
  COL_SN                   bigint not null FK → TB_COL (서브타입 테이블의 상속 PK 컬럼)
  REG/MDFCN/RGTR/MDFR
  UX_..._01 (ENTT_TBL_MPNG_SN, LGCL_ATRB_SN), UX_..._02 (COL_SN), IX (PRJ_SN)
```

- 규칙 : 엔터티 매핑이 서브타입(상속 참여, 루트 아님)일 때만, 속성은 그 엔터티의 루트 주 식별자 속성, 컬럼은 매핑 테이블의 컬럼. `TB_ATRB_COL_MPNG` 와 같은 컬럼을 동시에 쓸 수 없다(검증).
- 영향 : V4(H2·PostgreSQL 같은 내용), 테이블·컬럼 COMMENT, **예제 메타데이터**(단어 기존·용어/테이블/컬럼/논리 엔터티·인덱스 — `V0SeedMigrationTest`·`SmokeTest` 의 표준화 품질 0건), `ModelChangeRecorder` 추적(새 TargetType 또는 COLUMN_MAPPING 하위), 스냅샷 형식 9, 교환 형식 6(재매핑·원자 롤백·객체 수 포함), 프로젝트·엔터티 매핑·속성·컬럼 삭제 정리, `ModelSnapshotFieldCoverageTest`.
- 대안 1 을 고르면 DB 변경은 없지만 "상속 PK 컬럼 연결" 은 FK 가 그대로일 때만 판단되고, 서브타입이 부모인 관계를 **기존 서브타입 테이블**로 FK 생성할 때(10장) 컬럼을 확정할 근거가 FK 구조 추론뿐이다.

## 13. 기존 물리 모델 보호 (M7-D17·D18·D19)

| 상태 | 권장 처리 |
|---|---|
| 상속 참여 엔터티 모두 미매핑 | B 생성 가능 |
| 루트만 매핑 | 루트 = SKIP(기존 테이블 사용). 서브타입 생성 가능 **조건** : 루트 테이블 PK 가 루트 주 식별자 속성의 매핑 컬럼과 정확히 같음(지금 `PARENT_KEY_NOT_TABLE_KEY` 와 같은 검사). 아니면 서브타입 ERROR(사유) |
| 일부 서브타입만 매핑 | 매핑된 것은 SKIP, 나머지 생성. 매핑된 서브타입 테이블에 상속 PK·FK 가 없으면 **고치지 않는다** — 그 아래 자손은 부모 키 불일치로 ERROR |
| 전체 매핑 | 모두 SKIP (생성 없음). 상속 PK 매핑(대안 2)이 없으면 "상속 PK 연결 미확인" 경고만 |
| 기존 테이블 PK ≠ 상속 PK / FK 없음 / 승인됨 / 다른 관계에서 사용 | 자동 수정 없음(PK 교체·FK 추가·승인 취소·이름 변경 금지). 사유 표시 → 사용자가 물리 모델을 고치거나 수동 매핑 |
| 이름이 같은 다른 테이블 | 지금처럼 ERROR (덮어쓰지 않음, 이름만 같다고 재사용하지 않음) |

기존 테이블을 "B 구조에 맞게 고치는" 기능(상속 FK 추가 등)은 신규 생성과 범위가 다르다 → 별도 결정(pending [M-7] 별도 정책 ① "이미 만든 테이블에 나중에 FK 더하기" 와 같은 문제). 이번 권장 범위 밖.

### 13.1 부분 생성 (M7-D16)

| 방식 | 장점 | 단점 |
|---|---|---|
| 계층 전체 강제 | 불완전 구조 없음 | 큰 그룹(구성원 1,000+)은 요청 100 제한(`ENTITY_MAX`)을 넘는다 |
| **선택 엔터티 + 필요한 조상 (권장)** | 사용자가 고른 만큼만, 조상 테이블은 반드시 있음 | 조상을 자동으로 넣을지(요청 확장) vs 없으면 ERROR 할지 결정 필요 |
| 엔터티 단위 자유 | 단순 | 부모 테이블 없는 서브타입 → FK 없는 불완전 PK |

권장 규칙 : 서브타입은 **모든 조상이 이번 계획에서 만들어지거나 이미 B 형태로 매핑돼 있을 때만** CREATE, 아니면 ERROR("상위 엔터티 X 를 함께 고르거나 먼저 만드세요"). 조상을 자동 추가하지 않는다(요청 수 제한·예측 가능성). 루트만 고르면 루트만 만든다(서브타입은 나중에). 복수 그룹·일반 엔터티 혼합은 같은 규칙. 100 제한은 유지 — 큰 그룹은 조상 먼저, 구성원은 여러 요청으로.

### 13.2 재실행·중복

이미 매핑된 엔터티 SKIP, 이미 있는 FK·상속 PK 매핑은 다시 만들지 않음, 삭제된 테이블(매핑도 FK 로 같이 삭제됨)은 미매핑으로 다시 생성 가능, 논리 상속 구조가 바뀌었으면 planToken 이 달라져 409.

- 그룹 제약 보장 표(11장) — 경고 영역.

- 전략 선택 UI : B 만 지원하는 동안 선택 상자 없이 표시만 (A·C 가 생기면 그때 선택).

## 15. planToken (M7-D24)

v7 로 올리고 근거에 더할 것 : 전략(B), 참여 엔터티의 그룹 ID·슈퍼타입·구성원(순서)·그룹 행 `MDFCN_DT`, 루트 주 식별자(식별자 행·속성 순서), 상속 PK 컬럼 계획(원본 속성 ID·컬럼명·타입), 상속 FK 계획(자식·부모 테이블·컬럼·이름), 기존 조상 테이블 ID·PK 구성. 분류 속성·분류 값·Overlapping/Total 은 생성 결과(PK·FK)를 바꾸지 않지만 미리보기 경고를 바꾸므로 넣는 것을 권장(그룹 `MDFCN_DT` 로 포함). 표준 용어 약어·도메인은 지금처럼 용어 `MDFCN_DT`.

## 16. 동시성 및 트랜잭션

- 지금 순서 재사용 : 프로젝트 행 배타 → 논리 모델 행(NOWAIT) → 스키마 행(NOWAIT) → 재계획·planToken 비교 → 모델 버전 → 생성. 상속 그룹·구성원 쓰기도 논리 모델 행 잠금을 먼저 잡으므로(`LogicalSubtypeService`) 생성과 직렬화된다.
- 미리보기 뒤 그룹·루트 PK·직접 속성·용어·기존 테이블·매핑이 바뀌면 planToken 불일치 409 (자동 재시도 없음). 기존 조상 테이블 행은 지금 잠그지 않는다 — 기존 테이블 PK 를 근거로 쓰므로, 반영 때 그 테이블 행을 NOWAIT 로 잠글지(M7-D24 와 함께) 결정 필요.
- 원자성 : 테이블·컬럼·PK·FK·매핑·상속 PK 매핑·이력·모델 버전이 한 트랜잭션, 실패 시 전체 롤백 (지금과 같다). 새 전역 잠금 없음.

## 17. 승인 및 권한

- 지금 : 미승인 논리 엔터티도 생성(경고), 생성 객체는 모두 미승인, 논리 승인 ≠ 물리 승인, 기존 승인 객체를 바꾸지 않음. B 도 그대로 (M7-D25).
- 권한 : 미리보기·생성 USER(`model-mapping-edit`), 조회 VIEWER. 매핑 변경 USER, 물리 모델 변경은 각 API 권한. 확대하지 않는다.
- 프로젝트 격리 : 엔터티·모델은 `findAllByIds(ids, projectId)`, 스키마 `resolveSchema(projectId, …)`, 매핑·테이블·용어는 프로젝트 행에서 따라온다. 계획은 서버가 매번 다시 만든다(클라이언트의 상속 PK·컬럼을 받지 않는다 — 요청은 엔터티 ID·스키마·제외 속성뿐).

## 18. DB 변경 필요성 (M7-D20·D21·D26)

| 항목 | 필요 | 근거 |
|---|---|---|
| 상속 PK 매핑 | 대안 2 이면 필요 (12장) | 기존 UNIQUE·소속 검증으로 표현 불가 |
| 변환 전략 저장 | 불필요 (권장) | B 만 지원, D-30 "저장하지 않음". A·C 도입 때 다시 |

## 19. ERD·진단 연계

- 물리 ERD (M-2) : B 결과는 일반 테이블·FK. 서브 테이블 FK 는 FK = 자식 PK → M-2 카디널리티 "부모 정확히 1 · 자식 최대 1 · 식별" 로 그려진다 (PK 단일·복합 모두 `PhysicalCardinality` 규칙). 복합 FK 선 1개, 이웃·찾기·범위 밖 관계 그대로. 논리 ERD 의 D/O 원 기호는 넣지 않는다. 상속 출처 표시가 필요하면 관계 상세에 대안 2 매핑 기반 문구로 (후속).
- 물리 구조 진단 (M-DIAG-PERF, 요청당 8문) : 상속 FK 는 일반 FK 이므로 `referencesKey` 판단 그대로 — 부모 PK 전체를 참조하므로 정상. 논리·물리 상속 정합성은 구조 진단에 넣지 않고 매핑 정합성(`ModelMappingQualityService`)에 둔다.
- 매핑 정합성 : 지금 행 = 직접 속성 → 상속 PK 컬럼이 "누락" 으로 나오지 않는다. 다만 서브타입은 자기 주 식별자가 없어 IDENTIFIER 검사가 "엔터티에 주 식별자가 없습니다" NOT_COMPARABLE 이 된다 → B 지원 때 서브타입은 유효 주 식별자(루트)로 판단하고, 상속 PK 연결(대안 2 행 유무·PK 일치)은 **직접 매핑률과 따로** "상속 구조" 항목으로 (M7-D22). MATCH/MISMATCH/NOT_COMPARABLE/UNMAPPED 체계는 유지.
- 논리 ERD : 매핑 연계 표시는 지금 없다 — pending [M-7] "ERD 의 매핑 표시" 후속 그대로. 주제 영역·그룹·배치 변경 없음.

## 20. DDL

`TableDdlGenerator` 가 PostgreSQL·Oracle·MySQL·MariaDB 에 대해 복합 PK·복합 FK·스키마 간 FK(스키마명.테이블)·`ALTER TABLE … ADD CONSTRAINT` FK(순서·순환 무관)·제약 이름 규칙·무효 FK 경고를 이미 낸다 → B 결과를 그대로 출력할 수 있다 (새 DDL 기능 불필요). DDL 은 문자열 출력만 — 업무 DB 실행 없음.

DDL Export 성능 : `DdlExportService` 가 테이블마다 `tableDesignService.referencedKeys`·`physicalModelService.ddlExtras` 를 부른다 (코드 확인, 136~140행) — M-DIAG-PERF 이전 진단과 같은 구조. **측정하지 않았다** → 후속 과제 등록 제안 `M-DDL-PERF` (측정 후 판단).

## 21. 스냅샷·교환

- 스냅샷 형식 8 (`ModelVersionService.FORMAT_VERSION`) : 그룹·매핑을 이미 담는다. 대안 1 이면 변경 없음, 대안 2 면 새 행 종류 → 형식 9 (8 이하는 상속 PK 매핑 없음으로 읽기).

## 22. 화면 설계 (M7-D23)

진입점 대안 : ① 기존 매핑 화면의 물리 생성 확장 (**권장**) ② 생성 대화상자에 전략 선택 ③ 그룹 상세 → 생성 화면 연결(① 위에 보조 링크로 후속) ④ 전용 화면(비권장 — 메뉴 증가). 흐름 : 모델 → 엔터티 선택(그룹 단위 "구성원 함께 고르기" 보조) → 스키마 → 미리보기(상속 표·FK·보장 표·오류/경고) → 확정 → 결과(테이블 수·FK 수·모델 버전) → 물리 ERD·매핑 화면 이동. 성공은 토스트, 경고·미보장·상세 결과는 대화상자. 한·영·다크·375·동작 줄이기·키보드 기존 정책.

**2차에서 수정됨 (M7-D38, 29.8)** — 아래는 1차 확인 당시의 내용이다. `PhysicalCardinality` 는 `PK_YN`·`UNQ_YN` 이 비어 있으면(null) **아닌 것으로 본다** (클래스 주석 "DDL·모델 구조 진단과 같다"). 그래서 자식 쪽 유일성 근거가 null 뿐이면 자식 최대가 **N** 이 된다. M-2 개선 지시의 "메타데이터 불완전으로 판단할 수 없는 경우 N 으로 단정하지 않는다" 와 다르다 (부모 최소는 `NULL_ALWNC_YN` null 을 판단 불가로 처리). `PhysicalCardinalityTest` 에 null `PK_YN`·`UNQ_YN` 사례 테스트는 **없다**. 영향 : 예제·생성 경로는 항상 true/false 를 넣으므로(생성기 `isUnique(false)`, 예제 데이터) 실제로는 JDBC·과거 데이터에서만 생긴다. 수정하지 않았다 — 정책 결정 필요 (null = DDL 처럼 "아님" 으로 볼지 / 판단 불가로 볼지).

### 29.2 구현 범위 — 계획만, 반영 차단

- `PhysicalGenerationService.computePlan` : 상속 참여 엔터티를 `UNSUPPORTED` 로 건너뛰던 분기를 없애고 일반 엔터티와 같은 규칙(이미 매핑 → SKIP, 이름·컬럼 계산)에 B형 정보를 더한다. 요청 단위 정보는 `mapping/service/SubtypePlanContext` (저장하지 않음).
- **반영 차단** : `Plan.executable` = `creatable` 이고 상속 참여 엔터티를 `CREATE` 하지 않을 때만 참. 아니면 `executionBlockedReason = INHERITANCE_GENERATION_NOT_AVAILABLE`. `apply` 는 토큰 재계산·`creatable` 검사 뒤, **모델 버전 생성 전**에 400 `INVALID_PHYSICAL_MODEL` 로 거절한다 — 섞인 계획(일반 + 상속)도 전체 거절, 일부만 만들지 않는다. 루트만 골라도(SKIP 이 아니면) 막는다 : 루트 테이블만 먼저 만들면 3차의 상속 PK 매핑 없이 만들어진 구조가 남기 때문. 상속 엔터티가 없는 계획은 예전과 같다.
- 막는 것은 서버다. 화면 버튼은 `executable` 을 따르고 안내 문구를 보여주지만 근거는 아니다.

| `constraintWarnings` | 고른 참여 엔터티(SKIP 제외)가 구성원·슈퍼타입인 그룹마다 Disjoint 면 `DISJOINT`, Total 이면 `TOTAL` (`NOT_ENFORCED`) — 그룹·제약당 1건 |

오류 사유 (서브타입 `ERROR`) : `ROOT_KEY_MISSING`(루트 주 식별자 없음), `ANCESTOR_MISSING`(조상이 계획·매핑 모두 없음), `ROOT_KEY_MAPPING_MISSING`(매핑된 루트의 주 식별자 속성이 그 테이블 컬럼에 직접 매핑되지 않음), `PARENT_KEY_MISMATCH`(매핑 컬럼 집합 ≠ 루트 테이블 PK 전체), `INHERITED_KEY_MAPPING_MISSING`(조상인 중간 엔터티가 매핑돼 있음 — 상속 PK 매핑이 3차라 그 테이블의 PK 를 확인할 수 없다, 컬럼명·FK 로 추론하지 않는다). 기존 테이블은 고치지 않는다 (D18).

### 29.4 엔터티 문맥 컬럼 참조 (M7-D15)

같은 원본 속성(루트 주 식별자)이 루트·각 서브타입 테이블 컬럼을 모두 가리키므로 속성 ID 만으로 컬럼을 찾지 않는다.
- 새로 만들 부모 : 원본 속성의 `columnSpec` (상속 PK 컬럼과 같은 이름).
- 기존 부모의 직접 속성 : 예전처럼 직접 매핑을 부모 테이블로 거른다.
- 기존 서브타입 테이블 부모의 상속 속성 : `COLUMN_UNAVAILABLE` + `INHERITED_KEY_MAPPING_MISSING` (FK 없이 — 관계 계획이 생성을 막지 않는 기존 규칙 그대로). 3차의 상속 PK 매핑으로 해결한다.
- 부모가 상속 구조에 참여해도 관계가 정의된 부모 엔터티의 테이블을 참조한다 (D14, `INHERITANCE_UNSUPPORTED` 를 더 쓰지 않는다 — 메시지 키는 예전 응답 호환으로 남김). 관계마다 루트를 다시 읽던 `findById` 는 요청 문맥의 엔터티 지도로 바꿨다.

### 29.5 계획 토큰 v7

`v7|` + 기존 항목 + 서브타입의 상속 PK 속성·용어 버전(`k…`), 상속 사유, 상속 FK 계획(자식>부모·그룹·상태/사유·유형·부모(새 테이블/기존 테이블 ID@수정 시각)·제약조건명·참조 테이블명·기존 루트 매핑 컬럼의 ID·이름·PK 여부·컬럼 쌍), 관련 그룹(슈퍼타입·Overlapping·Total·분류 속성·수정 시각·고른 구성원), 고른 구성원의 분류 값, 필요한 조상. 같은 상태면 같은 토큰(정렬된 지도·ID 순), 예전 v6 토큰과 바뀐 상태의 토큰은 409 `MODEL_CONFLICT`. 구조 변경 자체는 논리 모델 행 잠금(M-6 상속 쓰기)과 반영의 모델 행 NOWAIT 로 직렬화된다.

### 29.6 잠금 분석

- 미리보기 : 읽기 전용, 잠금 없음 (예전과 같다).
- 반영 : 프로젝트 행 배타 → 논리 모델·대상 스키마 행 NOWAIT → 재계획·토큰 비교 → `creatable` → **상속 계획 거절** → 버전 → 생성. 2차에서는 상속 계획이 버전·생성까지 가지 않으므로 새 잠금이 필요 없다. 상속 그룹·구성원 쓰기는 논리 모델 행을 잠그므로 반영과 직렬화된다.
- 3차 결정 사항 : 기존 조상 테이블(루트 테이블 행·PK 컬럼 행)을 반영 때 NOWAIT 로 잠글지. 지금은 토큰이 테이블 수정 시각·매핑 컬럼의 PK 여부·판정 사유를 담아 재계획 때 바뀐 PK 를 잡지만, 재계획과 커밋 사이의 PK 변경은 막지 못한다 — 3차에서 소스 가져오기와 같은 순서(프로젝트 → 모델 → 스키마 → 테이블 → 컬럼, NOWAIT)로 잠그는 것을 권장 (PostgreSQL 에서 재현 확인 필요).

### 29.8 M-2 카디널리티 수정 (M7-D38)

화면·엑셀·원본 가져오기·생성기는 PK_YN·UNQ_YN 에 늘 참/거짓을 넣는다 — 비어 있으면 "기록되지 않은 값" (예전 데이터·직접 SQL·필드가 없는 교환 파일). `PhysicalCardinality` :
- 자식 최대 1 = 확정된 유일성 (PK 플래그가 모두 기록된 테이블의 PK ⊆ FK · 참인 UNQ_YN · UNIQUE 제약 · 고유 인덱스).
- N = 자식 테이블의 PK_YN 이 모두 기록되고 FK 컬럼의 UNQ_YN 이 모두 기록됐는데 유일성이 없을 때만.
- 그 밖에는 null + 새 사유 `KEY_METADATA_UNKNOWN`. FK 컬럼의 PK_YN 이 비면 식별 여부도 null.
- 부모 쪽 참조 키 판단(무효 FK)은 DDL·모델 구조 진단과 같게 null = 아님 그대로 (화면마다 무효 FK 판정이 달라지지 않게).
- 화면 : `features/erd/cardinality.ts` 사유 문구, `model.ts` 타입.

### 30.3 도메인·API

- 엔티티 `mapping/domain/entity/SubtypeIdentifierColumnMapping`, 리포지토리 `SubtypeIdentifierColumnMappingRepository` (매핑별·여러 매핑 일괄·컬럼·속성 참조 조회).
- 판정 : `SubtypePlanContext` 하나가 물리 생성(기존 조상 재사용)과 조회 API(정합성 사유)를 함께 맡는다 (M7-D36, 규칙 복제 없음). `SubtypePlanContexts`(컴포넌트)가 요청 단위로 만들고 `prepare(엔터티들)` 가 조상 체인의 엔터티·엔터티 매핑·루트 키 직접 매핑·상속 PK 매핑·서브타입 테이블에서 나가는 관계를 종류마다 한 번에 읽는다.
- 기존 서브타입(중간 엔터티) 유효 조건 : 지금 루트 주 식별자 전체의 상속 PK 매핑(일부만 = 미완성), 그 컬럼 집합 = 테이블 PK 전체, 직계 부모 키 컬럼과 순서대로 FK 타입 호환(`TableDdlGenerator.isReferenceTypeCompatible`), 직계 부모 테이블을 그 쌍 그대로 참조하는 FK(출처 무관 — REF_COLUMN 관계도), 직계 부모도 유효. 사유 : `INHERITED_KEY_MAPPING_MISSING`·`PARENT_KEY_MISMATCH`·`INHERITED_KEY_TYPE_MISMATCH`·`INHERITANCE_FK_MISSING`·`ANCESTOR_INVALID`(부모 쪽 원인 — 목록에서는 원인만 보인다). 컬럼명·FK 이름으로 추론하지 않는다.

| API (`/api/modelMapping`) | 권한 | 내용 |
|---|---|---|
| `GET /entity/{mappingId}/subtypeKeys` | VIEWER | 지금 루트 주 식별자 속성마다 1행(없으면 컬럼 null) + 지금 주 식별자가 아닌 기존 매핑(`current=false`), `subtype`·부모·루트, `status`(VALID 또는 사유, 지금 서브타입이 아니면 `NOT_SUBTYPE`)·`statusMessage`·`complete`. 저장하지 않고 계산한다 |
| `GET /entity/{mappingId}/subtypeKeys/candidates` | VIEWER | 그 테이블의 컬럼 중 속성 매핑·다른 상속 PK 매핑에 안 쓰인 것 (`currentId` 의 컬럼은 포함). 그리드 목록 규칙(`PageableUtil`, 크기 1~100, 정렬 허용 `columnName`·`sortOrder`, 검색 컬럼명·설명) |
| `POST /subtypeKey` | USER | 등록(id 없음)·변경(id 있음 — 컬럼만). 오류 : `INVALID_MODEL_MAPPING`(서브타입 아님·루트 주 식별자 아님·다른 테이블 컬럼), `SAVED_DATA_EXISTS`(같은 (매핑, 속성)·컬럼 중복·속성 매핑에 쓰인 컬럼), `MODEL_MAPPING_IS_NOT_DEFINED`(없음·다른 프로젝트) |
| `DELETE /subtypeKey/{id}` | USER | 매핑만 해제 (불일치 상태여도). 물리 PK·FK·컬럼·논리 식별자 그대로 |

- 등록은 참조 유효성만 본다. 물리 구조(PK·타입·부모 FK)는 막지도 바꾸지도 않고 조회의 `status` 로만 보인다 — 속성 매핑의 기존 계약과 같다 (새 정책 아님). 승인 상태는 매핑과 무관하다 (속성 매핑과 같음). 같은 값 변경은 이력이 남지 않는다.
- 새 메뉴·화면 없음 (4차). 화면 최소 호환 : 생성 결과 알림에 상속 FK·상속 PK 매핑 수, 관계·상속 FK 사유 문구, 이력·버전·교환 화면의 종류 이름 `SUBTYPE_KEY_MAPPING`.

### 30.4 교차 무결성·생명주기

| 경로 | 처리 |
|---|---|
| 속성 매핑 등록·변경 (`saveAttributeMapping`) | 상속 PK 매핑에 쓰인 컬럼 거부. 후보 목록(`findUnmappedColumns`)에서도 뺀다 |
| 상속 PK 매핑 등록·변경 | 속성 매핑·다른 상속 PK 매핑에 쓰인 컬럼 거부 |
| 자동 생성 | 새 테이블의 새 컬럼만 쓰므로 충돌하지 않는다. 상속 PK 컬럼은 상속 PK 매핑에만, 직접 속성은 속성 매핑에만 저장 |
| 교환 가져오기 | 파일 안에서 교차 중복·중복·참조를 확인 (30.7) |
| 엔터티 매핑 해제·테이블 변경 | 상속 PK 매핑이 있으면 거부 (속성 매핑과 같은 문구 형식) |
| 컬럼 삭제 (`releaseColumns` — 개별 삭제·일괄 저장 삭제·원본 삭제 확정) | 상속 PK 매핑에 쓰인 컬럼 거부. 원본 삭제 후보 판정(`SourceDeletionService`)도 매핑된 컬럼으로 본다 |
| 테이블 삭제 | 엔터티 매핑이 있으면 이미 거부 (상속 PK 매핑은 엔터티 매핑이 있어야 존재) |
| 원본(루트) 속성 삭제 | 상속 PK 매핑이 있으면 거부 (식별자 사용 검사 다음). 엔터티·모델 삭제는 기존 규칙(엔터티 매핑·엔터티 있음 거부)이 먼저 막는다 |
| 상속 해제·그룹 삭제·주 식별자 변경·물리 PK 변경 | 매핑 보존, 조회에서 `NOT_SUBTYPE`·`current=false`·`INHERITED_KEY_MAPPING_MISSING`·`PARENT_KEY_MISMATCH` 로 보이고 명시적으로 해제할 수 있다. 테이블을 지우지 않는다 |
| 프로젝트 삭제 | `ProjectDataCleanup` : 속성 매핑 다음, 엔터티 매핑 전에 지운다 (같은 트랜잭션) |

동시성 : 속성 매핑·상속 PK 매핑 등록은 모두 그 엔터티 매핑의 논리 모델 행 → 테이블 행을 잠근 뒤 양쪽을 확인한다 (테이블 하나는 엔터티 매핑 하나에만 쓰이므로 같은 컬럼을 두고 다투는 두 등록은 같은 잠금에서 줄 선다). 컬럼 삭제는 테이블 행, 속성 삭제·엔터티 매핑 해제는 논리 모델 행을 잡으므로 등록과 직렬화된다. 추가 테이블·트리거 없음.

### 30.5 실제 B형 생성

- `Plan.executable` = `creatable` (2차의 `INHERITANCE_GENERATION_NOT_AVAILABLE` 차단 해제). 필수 상속 FK 가 `BLOCKED` 인 서브타입은 사유와 함께 ERROR (M7-D42 — 2차에는 `TYPE_INCOMPATIBLE`·`COLUMN_UNAVAILABLE` 로 막힌 상속 FK 가 테이블을 ERROR 로 만들지 않았다).
- 반영 순서 : 프로젝트 행 배타 → 논리 모델 행·대상 스키마 행 NOWAIT → 재계획·토큰 비교 → `creatable` → **계획이 쓰는 기존 테이블 행 NOWAIT (ID 순)** → 생성 직전 모델 버전 → 테이블·엔터티 매핑 → 컬럼(상속 PK 먼저) + 속성 매핑 / 상속 PK 매핑 → 복합 상속 FK → 관계 FK → 참조 동기화(단일 FK) → **최종 FK 확인** → 커밋(이력).
- 상속 PK 컬럼의 원본 = 루트 주 식별자 속성 (중간 부모의 컬럼 ID 를 원본처럼 쓰지 않는다). 컬럼은 엔터티 문맥(엔터티 ID → 속성 ID → 컬럼)으로 찾는다 — 같은 원본 속성이 여러 테이블에 있어 속성 ID 만으로 찾으면 다른 테이블 컬럼을 잇는다 (2차 반영 코드의 잠재 결함, 반영 차단 때문에 드러나지 않았다).
- 최종 FK 확인 : 계획의 READY 상속 FK·관계 FK 마다 만든 테이블에서 그 부모 테이블로 같은 컬럼 쌍의 FK 관계가 실제로 있는지 본다. 없으면 400 으로 전체 롤백 — 단일 FK 가 참조 동기화에서 풀려(예 : 같은 이름 테이블이 여러 스키마) 조용히 빠지는 일을 막는다.
- 결과 `Result` 에 `inheritanceForeignKeys`·`inheritedKeyMappings` 추가 (예전 생성자 유지).
- 일반 관계 : 기존 서브타입 부모는 그 엔터티 매핑의 상속 PK 매핑 컬럼을 참조한다 (루트 컬럼이 아님). 상속 PK 매핑이 없거나 일부면 `COLUMN_UNAVAILABLE`·`INHERITED_KEY_MAPPING_MISSING` (FK 없이 생성, 기존 규칙). 짝의 자식 속성은 자식 엔터티의 직접 속성만 가능하므로(M-6) 일반 FK 와 상속 FK 가 같은 자식 컬럼을 쓰는 경우는 생기지 않는다 (지시서 47절 검토 결과).
- 그대로인 것 : 기존 테이블·매핑은 SKIP·수정 없음, 같은 이름 테이블 자동 매핑 없음, 요청당 100개, 그룹 구성원 한도 없음 (1,001개 그룹 분할 생성 확인), 트리거·CHECK·구분 컬럼 없음, 상속 일반 속성·대체 식별자 미복제.

### 30.6 계획 토큰 (v7 유지)

3차 근거를 같은 `v7|` 에 더했다 : 기존 조상마다(조상 ID 순, 한 번) 판정 사유·테이블 ID@수정 시각·PK 컬럼 ID@수정 시각(타입·PK 여부 변경)·키 컬럼 ID@수정 시각·엔터티 매핑 ID·상속 PK 매핑(ID·원본 속성·컬럼)·그 테이블에서 나가는 FK(ID@수정 시각·대상·컬럼 쌍), 관계 FK 의 기존 부모 컬럼 ID@수정 시각·부모 PK 컬럼 집합. 토큰은 저장하지 않는 미리보기 ↔ 반영 비교값이라 형식 번호를 올리지 않아도 2차 토큰·예전 v6 토큰은 그대로 409 다 (올려도 결과가 같다 — 사용자 보고 사항 없음). 일반 계획의 토큰도 관계 기존 부모 근거가 더해져 3차 이전 토큰과 다르다 (같은 상태에서는 결정적).

### 30.7 스냅샷 9·교환 6 (M7-D43)

- `ModelChangeRecorder` 추적 대상 `SUBTYPE_KEY_MAPPING` (`ModelChangeHistory.TargetType` 새 값, 필드 mapping·attribute·column, 프로젝트는 엔터티 매핑으로, 표시 이름 `속성 ↔ 컬럼`). 원본 속성 자체의 이력은 속성 이력에만 남는다 (중복 저장 없음). 서브타입 문맥 = 엔터티 매핑 ID.
- 스냅샷 형식 9 (`ModelVersionService.FORMAT_VERSION`) : 대상 종류 `SUBTYPE_KEY_MAPPING`. 형식 8 이하 버전은 고치거나 채우지 않는다 (없는 종류는 비교에서 빈 것과 같게 — 기존 규칙).
- 교환 형식 6 : `TYPES` 에 `SUBTYPE_KEY_MAPPING`, 가져올 수 있는 형식 1~6. `validateSubtypeKeys` : 형식 5 이하 파일에 있으면 거절, 엔터티 매핑·속성·컬럼이 파일에 있어야 하고, 엔터티는 파일 안에서 서브타입, 속성은 그 루트의 주 식별자, 컬럼은 그 매핑 테이블, (매핑, 속성)·컬럼 중복 없음, 속성 매핑(COLUMN_MAPPING)과 교차 중복 없음 — 어기면 파일 전체 거절. 객체 수 제한(50,000)에 포함(종류 목록에 있으므로). 가져오기는 모델·TABLE 을 함께 새로 만드는 엔터티 매핑 아래에만 새 ID 로 다시 잇고, 이어지지 않으면 빼지 않고 전체를 되돌린다. 계획 counts 에 `SUBTYPE_KEY_MAPPING`(있을 때만 — 예전 파일의 계획은 그대로). 기존 COLUMN_MAPPING 의 "대상 없으면 건너뜀" 동작은 바꾸지 않았다.

### 30.8 잠금 분석 (M7-D39)

| 경로 | 잠금 (순서) | NOWAIT | 비고 |
|---|---|---|---|
| 물리 생성 반영 | 프로젝트(배타) → 논리 모델 → 대상 스키마 → **기존 부모 테이블 행 (ID 순, 3차)** | 프로젝트 뒤 모두 NOWAIT → 409 | 프로젝트 배타를 쥔 동안 다른 쓰기는 커밋 못 한다(커밋 직전 프로젝트 공유 잠금). 그 전에 시작한 미커밋 변경은 아래 잠금을 쥐고 있어 NOWAIT 가 잡는다 |
| 논리 모델·상속 그룹·식별자 편집 | 논리 모델 행 | 기다림 | 반영의 모델 NOWAIT 와 직렬화 |
| 테이블 편집 | 테이블 행 | 기다림 | |
| 컬럼 일괄 저장 | **테이블 행(3차, 맨 먼저)** → 바꾸는 컬럼 행(ID 순) | 기다림 | 예전에는 컬럼 행만 잠가 새 PK 컬럼 추가를 잡을 수 없었다 |
| 컬럼 단건 등록·엑셀 업로드 | **새 컬럼이 PK 일 때만 테이블 행 (3차)** → **2026-11-21 부터 모든 등록이 테이블 행 (이름 중복 검사 전)** | 기다림 | 3차 당시 : PK 가 아닌 컬럼은 부모 키를 바꾸지 않는다 — 업무 설명 직접 편집(테이블 행)과 기다리지 않는 AI-5 계약. **물리명 일괄 적용 2차 후속에서 넓혔다** (같은 이름 등록·이름 변경과의 경쟁, [physical-name-recommendation-m7.md 10장](physical-name-recommendation-m7.md)) — 이제 업무 설명 직접 편집을 기다린다 (`BizDescriptionExcelIntegrationTest` 갱신) |
| 컬럼 삭제 (`releaseColumns`) | 테이블 행 (ID 순) | 기다림 | 기존 |
| PK·인덱스·제약조건·관계 편집 | 테이블 행 | 기다림 | 기존 (PK 는 컬럼의 PK 여부) |
| 속성 매핑·상속 PK 매핑 등록·변경·해제, 엔터티 매핑 해제 | 논리 모델 행 → 테이블 행 | 기다림 | 기존 순서 |
| 원본 가져오기·삭제 | 프로젝트 → … → 테이블 → 컬럼 | NOWAIT | 기존 |
| 프로젝트 삭제 | 프로젝트 행 배타 | 기다림 | 기존 |

선택 이유 : 부모의 PK 집합 변경(새 PK 컬럼 삽입)은 행 잠금으로는 잡을 수 없으므로 "부모 테이블 행"을 컬럼 구성·PK 변경의 공통 잠금으로 삼았다. 반영은 그 행을 NOWAIT 로 잡고, 컬럼 쪽 경로는 테이블 → 컬럼 순으로 잡아 순서가 반대인 경로가 없다. 부모의 모든 컬럼을 잠그지 않는다. 생성이 끝난 뒤의 부모 변경은 막지 않는다 (불일치로 보일 뿐 — §56, 단일 상속 FK 는 부모 PK 가 복합이 되면 기존 참조 동기화 규칙대로 풀린다).

| `POST /generate/preview` | `ancestors` : 고른 서브타입의 조상마다 SELECTED·REUSE·REVIEW(사유·`mappingId`)·MISSING, `requiredBy` | 이미 한 조상 판정을 다시 쓴다 (새 조회 없음, 토큰 근거 변경 없음 — 조상 근거는 3차에 이미 들어 있다) |

예전 필드·생성자는 그대로다 (`EntityRow`·`SubtypeKeyDetail` 은 보조 생성자 유지, `requiredAncestors` 유지).

### 31.3 구조 정합성 = 기존 부모 재사용 판정 (M7-D36)

`SubtypePlanContext.inspect(엔터티)` 가 매핑된 서브타입 하나를 점검한다. 전체 판정(`code`)은 3차의 `ancestor()` 그대로이고(생성 미리보기의 기존 부모 재사용과 같은 값), 항목 점검은 같은 보조 판정(`inTable`·`isTableKey`·`isReferenceTypeCompatible`·`hasForeignKey`)을 항목별로 나눈 것이다. **판정이 VALID ⇔ ERROR·MISSING·UNKNOWN 점검이 없음** (항목에 잡히지 않은 판정 사유가 있으면 그 사유를 ERROR 로 더한다 — 어긋나지 않게).

| 점검 | 수준 | 비고 |
|---|---|---|
| KEY_COMPLETE 상속 PK 매핑 완전성 | MISSING | 일부·없음 = 미완성 (연결 수와 구조는 따로) |
| COLUMN_OWNER 컬럼 소속 | ERROR | |
| STALE_MAPPING 유효하지 않은 기존 매핑 | WARNING | 판정에 쓰지 않음 — 해제 가능 |
| PK_SET 물리 PK 구성 · NOT_NULL | ERROR | 연결이 완전할 때만 (아니면 UNKNOWN) |
| PK_ORDER 물리 PK 순서 | WARNING | 상속 FK 는 식별자 순서로 짝지으므로 판정은 집합 비교 그대로 — 정책 변경 없이 참고로만 |
| PARENT_TABLE 직계 상위 테이블 | UNKNOWN | 상위가 매핑되지 않음 = 판단 정보 부족 |
| ANCESTOR_PATH 상위 상속 경로 | ERROR / UNKNOWN | 가장 가까운 원인이 정보 부족(ANCESTOR_MISSING·ROOT_KEY_MISSING·ROOT_KEY_MAPPING_MISSING)이면 UNKNOWN |
| KEY_TYPE 데이터 타입 · KEY_LENGTH 길이·정밀도 | ERROR · WARNING | 타입은 PK 여부와 따로 본다 (브라우저 확인 중 고침 — 31.9) |
| PARENT_FK 부모 FK | ERROR | 사유를 나눈다 : 상위 테이블 FK 의 쌍 일부 누락·다른 컬럼 / 상속 PK 컬럼이 다른 테이블 참조 / FK 없음 |

정합성 비교 상태 연결 (전역 `CheckStatus` 그대로) : ERROR → MISMATCH, 그 밖에 MISSING → UNMAPPED, UNKNOWN → NOT_COMPARABLE, 아니면 MATCH. 유효하지 않은 기존 매핑은 매핑마다 MISMATCH 행 (구조 행과 따로). 루트·일반 엔터티는 INHERITANCE 행이 없다 (대상 아님 — 미매핑·불일치로 세지 않는다). Disjoint·Total 물리 미보장은 상세의 안내(`constraintNote`)일 뿐 판정을 바꾸지 않는다. 직접 속성 매핑률(`mappedAttributes / totalAttributes`)은 상속 PK 를 넣지 않는다 — 상속 PK 현황은 `inheritance` 로 따로 센다 (`mappedKeys ≤ requiredKeys`, 무효 매핑은 `invalidKeys`).

요약 카드의 일치·불일치·비교 불가·미매핑 수에는 INHERITANCE 행도 들어간다 (카드를 누른 목록 수와 같게 — 카드 아래 문구 "진단 건수 (상속 구조 포함)"). 속성명·컬럼명 검색에서는 엔터티 단위 구조 행을 빼고, 이름이 맞는 기존 매핑 행은 그 속성이 없는 엔터티의 것도 보인다.

### 31.4 화면 (기존 매핑 메뉴 안 — 새 메뉴 없음)

- 매핑 목록 : 엔터티 이름 옆 역할 라벨(루트 슈퍼타입·중간 슈퍼타입·서브타입·상속 해제됨 — 생성 미리보기와 같은 이름, 여러 그룹이어도 하나), [속성 매핑 (직접 · 상속 PK)] 열에 직접 매핑 수와 `상속 PK a / b`·`무효 매핑 n`·구조 상태 라벨을 따로. 상속 PK 매핑이 있으면 엔터티 매핑 해제·테이블 변경 전에 안내 (서버도 거절).
- 속성 ↔ 컬럼 매핑 대화상자 : [직접 속성 매핑](기존 그대로) + [상속 PK 매핑](`subtypeKeys.tsx`) — 루트 주 식별자 순서대로 원본 엔터티·용어·타입·매핑 컬럼·컬럼 타입·PK·매핑 상태·점검, 유효하지 않은 기존 매핑은 따로 묶어 보이고 해제할 수 있다. 등록·변경은 그 테이블 후보(서버 페이징·검색, 속성 매핑·다른 상속 PK 매핑 컬럼 제외, 변경이면 지금 컬럼 포함)에서 고르고 PK 아님·NULL 허용이면 저장 전에 안내 (막지 않는다 — 3차 계약). 해제 확인 문구는 "연결만 지운다 — 속성·컬럼·PK·FK·상속 관계 그대로". 상태는 엔터티 매핑 문맥(mappingId)으로만 관리한다. 아래에 [상속 물리 구조 정합성] 상세와 관련 화면 이동(현재·원본·직계 상위 엔터티 상세, 테이블·상위 테이블 상세, 물리 ERD).
- 정합성 비교 : 유형 [상속 구조], 상속 PK 현황 한 줄과 [상속 구조만 보기], 행 상세는 같은 구조 상세를 그때 불러온다. D-48 안내 문구를 "직접 속성 비교 + 상속 구조 유형 별도"로 바꿨다.
- 물리 생성 대화상자 : 엔터티 고르기를 모델 전체 목록에서 매핑 목록 API 의 서버 페이징·검색(20개)으로 바꿨다 (고른 것은 ID → 이름으로 따로 들고 페이지·검색이 바뀌어도 남는다, 역할·매핑 상태 표시, 고른 수 n / 100, 고른 엔터티 보기·빼기·모두 빼기). 필요한 상위 엔터티는 `ancestors` 로 상태별(이번에 생성·기존 테이블 재사용·기존 매핑 검토 필요 + [매핑 검토] 이동·선택 필요)로 보이고, [필요한 상위 엔터티 함께 선택 (n개)] 은 '선택 필요' 만 더한 뒤 다시 미리보기만 한다 (생성은 사용자가). 합이 100 을 넘으면 아무것도 더하지 않고 지금·추가·합계·최대를 안내 (일부 추가·기존 선택 해제·요청 분할 없음). 선택·스키마가 바뀌면 이전 계획(planToken)을 버리고 진행 중 미리보기 응답도 무시(요청 번호), 속성 제외만 바뀌면 기존처럼 다시 미리보기 요구. 테이블 계획은 접기(5개 이하·오류는 펼침)와 상속 PK·직접 속성 수, 요약 줄에 건너뜀·상속 FK·관계 FK·FK 없이 만드는 관계 수. 409·실패는 오류로 보이고 선택·제외 속성은 그대로.
- 공통 대화상자 (`DialogProvider`) : 닫힌 뒤 연 버튼으로 포커스를 돌려준다 — 대화상자 요소가 빠진 뒤 `close()` 가 불려 브라우저가 스스로 돌려주지 못하던 기존 동작을 4차 확인 중 발견해 고쳤다 (모든 대화상자 공통).

### 31.9 조회 성능 (측정용 임시 프로브 — 격리 복사본에서만 실행하고 저장소에 넣지 않음)

모델 = 가족(루트 1·중간 3(하나는 자기 속성 없음)·말단 6, 복합 루트 키 2개) 반복을 모두 생성(매핑·상속 PK 매핑·상속 FK 있음), 3,000·10,000 에는 구성원 1,009명 그룹(미생성) 포함. 워밍업 2 + 7회 중앙값, SQL = Hibernate 준비된 문장 수, 적재 = 엔티티 적재 수, 응답 = JSON 바이트. 같은 MacBook, 개발 앱과 별개 JVM.

**처음 구현에서 찾은 병목과 수정** : 정합성 비교(요약·목록)가 모델의 매핑된 서브타입 전부를 판정하면서 테이블 컬럼 전체·관계 엔티티를 적재하고, 엔터티 수천 개의 긴 `IN` 목록으로 읽었다 — H2 3,000 에서 요약 235ms·SQL 76·적재 23,087 (상속 행을 끈 기준값 8ms), PostgreSQL 10,000 에서 1,704ms·SQL 300·적재 104,287 (기준값 82ms). JFR 로 보니 H2 시간의 대부분이 긴 `IN` 목록 비교였다. 판정 규칙은 그대로 두고 재료만 바꿨다 :
- 가벼운 판정 (`SubtypePlanContexts.light` — 매핑 목록·상세·정합성 비교) : 테이블 PK 컬럼과 나가는 FK 컬럼 쌍을 ID·이름 투영(`ColumnInfoRepository.findPrimaryKeyColumns`, `TableRelationRepository.findForeignKeyPairs`)으로 읽는다. 물리 생성은 계획 토큰이 관계 엔티티를 쓰므로 예전 방식 그대로 (`create`). 판정 함수(`isTableKey`·`hasForeignKey`)는 두 방식이 같은 모양(`KeyCol`·`Fk`)으로 채운 재료만 본다 — `SubtypeMappingUiIntegrationTest` 가 상세(가벼운)와 생성 미리보기(엔티티)의 판정이 같은지를 사례마다 확인한다.
- 모델 전체 판정 (`lightForModel` — 정합성 비교) : 엔터티·엔터티 매핑·상속 PK 매핑·FK 쌍·PK 를 모델 조건(조인·하위 질의)으로 한 번씩 읽고 요청한 ID 만 남긴다.
- 점검 문구는 읽을 때 만든다 (목록·비교는 대부분 읽지 않는다).

### 32.1 실제 구현 범위 확인 (지시서와 다른 점)

- **모델 버전 복원은 없다** : M-9·M-7 기록대로 버전은 조회·비교용이며 복원·Undo 는 범위 밖이다 (`ModelVersionService` 에 복원 API 없음, 화면 없음). 새로 만들지 않았다 — 지시서 9장·32장의 복원 항목은 "미지원"으로 기록한다.
- **"프로젝트 복사" 는 따로 없다** : DEC-22 3장대로 복사 = 지금 프로젝트의 Export 를 관리하는 다른 프로젝트로 가져오기 (교환 plan → apply, 화면 [모델 가져오기 · 다른 프로젝트로 복사]). 그래서 복사 검증 = 교환 가져오기 검증이다.
- 비교는 내부 ID 로 짝짓는다 (기존 계약) — 지우고 같은 값으로 다시 만든 상속 PK 매핑은 삭제 + 추가로 보인다.

### 32.2 보존 계약 확인 결과

| 경로 | 결과 |

### 32.3 제한

- 객체 수 50,000 : 상속 PK 매핑도 센다 (종류별 행 수 합 + 서브타입 그룹 구성원 행 = 전체). 49,999·50,000 통과, 50,001 거절, 상속 PK 매핑을 빼면 이내인 파일도 넣으면 초과해 거절, 참조 검사보다 수가 먼저 (`ModelExchangeLimitsTest`). 같은 루트 속성을 8,332개 서브타입이 각자 쓰는 파일.
- 파일 30MB : 컨트롤러가 본문 바이트로 판단 — 정확히 30MB(공백 채움·한글 3바이트 채움 모두) 는 읽어 계획하고 30MB + 1바이트는 거절, 한글은 글자 수가 30M 의 절반도 안 돼도 바이트로 넘으면 거절, 길이 머리글이 30MB 를 넘으면 읽기 전에 거절.
- 참고 (측정) : 엔터티 10,000개 모델의 내보내기 파일은 94,511개 객체·30.4MB 라 두 제한을 모두 넘어 다시 가져올 수 없다 (기존 계약 — 제한은 바꾸지 않았다).

### 32.4 원자성 · 동시성

- 가져오기 실패 주입 (테스트 전용 Hibernate 저장 후 리스너 — 운영 코드 없음) : 직전 모델 버전·논리 모델·속성·테이블·컬럼·엔터티 매핑·직접 매핑·상속 PK 매핑(첫 행 뒤·마지막 행)·커밋 직전 변경 이력 10단계 — 모든 프로젝트의 모델 행 수(16개 테이블)가 그대로, 실패 뒤 같은 계획으로 그대로 성공.
- 같은 파일·같은 대상 동시 가져오기 (3회) : 매번 하나만 반영, 다른 하나는 업무 오류, 한 벌만 남는다.
- 상속 PK 매핑 해제가 커밋 전일 때 버전 만들기 : 기다리지 않고 해제 전 상태로 저장하고, 해제는 그 뒤 커밋된다 (버전의 프로젝트 배타 잠금 · 변경의 커밋 직전 프로젝트 공유 잠금 — 기존 계약).
- 대상 프로젝트의 직접 매핑 등록이 커밋 전일 때 가져오기 : 교착 없이 둘 다 반영, 같은 컬럼이 두 종류에 쓰이지 않는다.
- H2·PostgreSQL 18.6 모두 통과. 잠금 정책은 바꾸지 않았다.

### 32.5 이력 · 승인

- 상속 PK 매핑 등록·변경·해제·같은 값 재저장은 3차 테스트 그대로 (같은 값은 이력 없음). 가져오기는 `CHG_SRC_CD = IMPORT` 의 CREATE 행. 복원은 없다.
- 가져온 TABLE·엔터티는 원본이 승인이어도 미승인 (기존 계약). REF_COLUMN 승인 상태는 바꾸지 않았다.

33.2 의 전체 테스트(H2·PostgreSQL)로 재실행 확인 : `SubtypeGenerationConcurrencyIntegrationTest` 10 (상속 PK 동시 등록, 직접·상속 교차 경쟁, 부모 테이블·루트 식별자 변경과 생성, 같은 대상 동시 생성 — 별개 DB 연결 실제 경합), `SubtypeGenerationRollbackIntegrationTest` (생성 중간 실패 전체 롤백), `SubtypePreservationIntegrationTest` 10 (스냅샷 9·8 호환·버전 비교·교환 왕복·무효 매핑 거절·형식 1~5·위장·잘못된 참조 14종·가져오기 실패 주입 10단계·동시 가져오기·버전과 매핑 변경 경쟁·30MB), `ModelExchangeLimitsTest` (50,000 경계). 실패 주입은 테스트 전용 리스너 — 운영 코드에 장애 주입 설정 없음. 잠금 순서·NOWAIT 정책은 바꾸지 않았다.

무효 상속 PK 매핑 계약은 지시대로 **유지 확정** : 조회·명시적 해제 가능, 스냅샷 9·교환 6 내보내기에는 보존, 교환 6 가져오기는 파일 전체 거절 (자동 삭제·보정 없음 — 원래 프로젝트에서 해제하거나 고친 뒤 다시 내보내 가져온다). 모델 버전 **복원은 없고**(조회·비교만), **독립된 프로젝트 복사 기능도 없다**(복사 = 교환 내보내기 → 다른 프로젝트로 가져오기).

### 33.8 성능 재측정 (측정용 임시 프로브 — 성능용 격리 복사본에서만, 저장소에 없음)

**회귀 판단 (같은 조건 대조)** :
- 생성 반영이 30.11 보다 큰 이유 : 30.11 은 루트·중간만 생성한 모델(테이블 약 3,600~4,000), 이번 기준값은 말단까지 모두 생성한 모델(테이블 8,990·상속 PK 매핑 16,182)이라 생성 직전 전체 모델 스냅샷 비용이 크다 (같은 모델의 버전 만들기 583ms). 30.11 과 같은 "부모만 생성" 조건으로 다시 재면 PostgreSQL 10,000 : 미리보기 1 / 100 = 36 / 148ms, 반영 1 / 100 = 474 / 1,481ms (SQL 159 / 1,147).
- 그래도 남는 차이(예전 프로브 SQL 514 vs 1,147)가 코드 때문인지 보려고 **3차 커밋(`5729b01`) 소스에서 같은 프로브**를 돌렸다 (H2 1,000, 부모만 생성) : 3차 코드 미리보기 100 = 31ms·428 SQL, 반영 100 = 380ms·1,084 SQL / 지금 코드 30ms·428 SQL, 379ms·1,084 SQL — **같다**. 차이는 측정 모델(단어·용어 구성 등 프로브 차이)이며 코드 회귀가 아니다. 서버 코드는 4차 커밋 이후 그대로(5차는 화면 이름표만)라 정합성·스냅샷·교환도 코드 변화가 없다. 정합성 10,000 의 963ms(4차 743ms)는 같은 코드에서 측정 모델·동시 부하(측정 중 브라우저·Docker 검증 병행) 차이로 보며 원인을 더 확인하지 않았다.
- 결론 : 유의미한 코드 회귀 없음 → 수정하지 않았다. 남은 병목은 후속 과제로 : 생성 고정 비용 [M-GEN-PERF], 정합성 모델 전체 진단 [M-MAPPING-PERF], 가져오기 할당·대형 모델 교환 한계 [M-EXCHANGE-PERF] (10,000 엔터티 모델은 내보낼 수 있지만 객체 95,520 개라 다시 가져올 수 없다 — 제한값은 바꾸지 않았다).
- 프로브의 객체 수는 서브타입 그룹 구성원 행까지 센다(서비스 검사 D-53 과 같음) — 32.6 의 3,000 = 21,711 은 구성원 1,009 를 빼고 센 값이다 (같은 모델).

### 33.9 M7-D01~D43 대조 · 완료 판단

- 전략·매핑·DB (D01·D02·D07·D08·D20·D21·D26~D28) : B형만, A·C 보류, 1:1 매핑, 상속 PK 매핑 별도 테이블(V4), 전략·출처 저장 없음, 스냅샷 9·교환 6 (1~5 가져오기) — 33.3 ⑰~㉑, 33.2.

- 생성 범위·기존 모델 (D16~D19·D30·D35·D36) : 필요한 조상 서버 미추가, 사용자가 고른 조상만 추가, 기존 부모 재사용·이미 매핑 SKIP, 자동 수정·동기화 없음, 100개 제한 — 33.3 ⑧~⑪b, 전체 테스트(서버 101개 거절). 화면의 '함께 선택하면 100개를 넘을 때 아무것도 추가하지 않음' 은 4차 구현 그대로이며 6차 브라우저에서는 다시 확인하지 않았다 (33.10).
