### 0.2 데이터 (V3)

- `TB_LGCL_SBTYP_GROUP` : `LGCL_SBTYP_GROUP_SN`, `PRJ_SN`, `LGCL_MDL_SN`, `SPRTYP_ENTT_SN`, `SBTYP_GROUP_NM`(255), `SBTYP_GROUP_EXPLN`(1000), `DPCN_PSBLTY_YN`(참 = Overlapping), `TOTL_YN`(참 = Total), `CLSF_ATRB_SN`(선택), `SORT_ORD`, 감사 컬럼. 승인 상태 없음 — 그룹 변경은 관련 엔터티 승인으로 막는다.

### 0.3 API

- VIEWER : `GET /api/logical/model/{modelId}/subtypeGroup/data` (검색·정렬 허용 목록 groupName/supertypeEntityName/modifiedAt, size 1~100), `GET /api/logical/subtypeGroup/{groupId}`, `GET /api/logical/entity/{id}/inheritance`, `GET /api/logical/entity/{id}/effectiveAttributes`.
- USER : `POST /api/logical/subtypeGroup` (등록·수정, 수정은 `modifiedAt` 필수), `DELETE /api/logical/subtypeGroup/{id}?modifiedAt=`.
- 논리 ERD `erd/part`·`erd/neighbors` 응답에 `subtypeGroups`, `outsideInheritances`, 엔터티별 `supertypeEntityId`·`inheritedKey` 추가 (기존 필드 불변).

### 0.4 성능

- 상속이 없는 모델도 관계 목록 조회에 그룹 조회 1개가 더해진다 (상수 1건, `LogicalModelManagementIntegrationTest` SQL 상한 7 → 8).
- 계층은 모델 단위로 그룹·구성원을 한 번 읽어 메모리(`LogicalHierarchy`)에서 계산한다 (재귀 SQL 없음).
- (후속 5차, 소규모) 임시 앱(H2 파일 DB, 로컬)에서 10회 중앙값 : 예제 모델(엔터티 88, 상속 없음) `erd/part` 41.7ms, 검증 모델(엔터티 11, 그룹 3) `erd/part` 14.2ms, `inheritance`(3단계) 8.2ms, `effectiveAttributes` 6.4ms, `neighbors depth=3` 8.5ms, 그룹 목록 3.9ms.
- 대규모 측정과 그에 따른 조회 구조 개선은 0.7절 (최종 보완).

#### 0.8.1 D-17 — 서브타입 자체 보조 식별자 (현재 구현 유지)

- 화면·API(`saveIdentifier`)는 처음부터 같은 엔터티의 직접 속성만 받았다 — 코드 변경 없음, 테스트 근거를 더했다 : 직접 속성 등록·자체 복합 보조 식별자 구성 순서, 상속 속성만·직접 + 상속 혼합·형제 엔터티·다른 논리 모델·다른 프로젝트 속성 거절(행 없음), 상위 보조 식별자의 직접(2단계)·간접(3단계) 가상 상속과 원본 식별자 ID (`LogicalSubtypeIntegrationTest.attributesAndIdentifiers`). 화면의 식별자 폼은 그 엔터티의 직접 속성만 고르게 한다 (기존).
- **교환 가져오기에서 발견·수정한 결함** : 파일 검사가 식별자 구성 속성의 소속을 보지 않았고, 가져오기는 모델 전체의 속성 번호로 찾아 이었다 → 서브타입 보조 식별자가 (먼저 만든) 슈퍼타입 속성을 가리키게 저장되거나, 뒤에 만들 엔터티의 속성이면 그 구성 행이 조용히 빠질 수 있었다. 파일 검사에 `validateIdentifiers` 를 더해 **식별자 구성 속성은 그 식별자 엔터티의 속성**이어야 하고, 어기면 파일 전체를 거절한다 (`MODEL_EXCHANGE_INVALID`, 한·영 문구). 정상적으로 내보낸 파일은 늘 이 조건을 지킨다 — 예제 프로젝트·형식 1~5 기존 테스트 통과. 저장 구조·교환 형식 그대로.

#### 0.8.2 D-53 — 교환 파일의 서브타입 구성원 목록

- 원인 : 파일 검사의 값 모양 검사(`flat`)가 모든 자식 목록을 1,000행으로 막았다 → D-51 로 저장할 수 있게 된 구성원 1,001개 이상 그룹이 내보내기는 되고 가져오기에서 `SUBTYPE_GROUP.subtypes` 로 거절됐다 (최종 보완 측정).
- 수정 (`ModelExchangeService.validate`, 형식·필드·처리 순서 그대로) : 자식 목록 한도를 인자로 받게 하고, `SUBTYPE_GROUP` 의 `subtypes` 필드만 1,000행 대신 전체 객체 한도로 본다. **전체 객체 수 = 종류별 객체 합계 + 서브타입 구성원 행** — 구성원 행은 모양 검사·참조 검사보다 먼저, 그룹마다 바로 더해 50,000 을 넘는 순간 거절한다(여러 그룹에 나눠도 합계, 한 번만 센다). 다른 자식 목록(식별자 구성·속성 짝·컬럼 구성 등)은 예전처럼 객체 수에 넣지 않고 객체 하나에 1,000행. 다른 종류의 같은 이름 필드(`subtypes`)는 예외가 아니다.
- 자원 보호 : 요청 본문 30MB 한도는 역직렬화 전(`ModelExchangeRestController.read` — 길이를 알리지 않은 요청도 한도에서 멈춤), 객체 수 검사는 서브타입 검사·계획·DB 쓰기 전. 구성원 행 안의 목록(중첩)·목록이 아닌 행은 모양 검사로 거절, 같은 엔터티 중복은 단일 상속 검사로 거절. 합계는 `int` 이고 한 목록을 더할 때마다 50,000 과 비교하므로 넘치지 않는다 (목록 길이는 30MB 본문 안의 원소 수).

## 1. 작업 목적

논리 모델에 일반화·특수화(IS-A) 구조를 더한다 : 슈퍼타입이 공통 속성·주 식별자를 정의하고, 서브타입은 그것을 상속하면서 고유 속성을 가진다. 상속은 **모델링 메타데이터**이며 Lexorma 가 업무 인스턴스를 관리하거나 원본 DB 데이터로 배타성·완전성을 강제하지 않는다.

### 2.3 서비스 규칙 (근거 메서드)

- **잠금** : 모든 논리 쓰기는 논리 모델 행을 먼저 잠근다 — `LogicalModelService.lockModel` → `LogicalModelRepository.findForUpdate`, `lockEntity`(엔터티의 모델 잠금 뒤 재조회), 관계·속성 짝 저장도 같은 잠금. 주제 영역(`LogicalSubjectAreaService`)도 같은 모델 행 잠금. 커밋 직전 `ProjectWriteGuard` 가 프로젝트 행을 공유 잠금한다. 물리 생성(`PhysicalGenerationService.apply`)은 프로젝트 행 배타 → 논리 모델 행·스키마 행 NOWAIT.
- **낙관적 충돌 (DEC-08)** : 잠금 뒤 `entityManager.refresh` + `ModelBase.verify(row, modifiedAt, name)` → 409 `MODEL_CONFLICT`. 구성만 바뀌면 `markModified()` (`saveIdentifier`, `saveRelationshipPairs`).
- **승인** : `saveEntity`/관계 저장·삭제는 `rejectApproved` (승인되면 누구도 수정 불가 → 승인 취소 후), 속성·식별자·속성 순서는 `rejectApprovedDetail` (승인 권한자는 승인 상태 그대로 수정 가능). 승인 토글 `updateEntityApproval` 은 `requireApprover` + 모델 잠금, 기준값 검사 없음. 주제 영역 소속은 승인과 분리(엔터티 `MDFCN_DT` 불변).
- **속성 소속 검증** : 식별자 구성 속성은 "같은 엔터티의 속성만" (`saveIdentifier`), 속성 짝은 부모 속성 ∈ 부모 엔터티 주 식별자(`LogicalRelationshipPairs.primaryKey(parent)`), 자식 속성 ∈ 자식 엔터티 속성(`saveRelationshipPairs`), 속성 매핑은 "매핑된 엔터티의 속성만" (`ModelMappingService.saveAttributeMapping`).
- **삭제** : 엔터티 삭제는 관계·테이블 매핑이 있으면 `RELATION_EXISTS` 거절, 속성·식별자·주제 영역 소속은 함께 삭제 (`deleteEntity`). 속성 삭제는 식별자·컬럼 매핑·관계 속성 짝에서 쓰면 거절 (`deleteAttribute`). 모델 삭제는 엔터티가 있으면 거절. 주제 영역 삭제는 하위 영역·소속 엔터티가 있으면 거절 (`LogicalSubjectAreaService.delete`).
- **이름 중복** : 엔터티명(모델 안)·속성명(엔터티 안)·식별자명(엔터티 안) 모두 대소문자 무시, 서비스 검사 (DB UNIQUE 는 대소문자 구분).
- **ERD 조회** : `selectGraphPart`/`graphPart` (최대 300, 범위 밖 관계는 엔터티별 수 `outsideRelationships`), `selectNeighbors` (1~3단계, `relationshipRepository.findLinks` 로 BFS, 300 상한), `searchEntities` (최대 50). 상수 `ERD_MAX_ENTITIES=300`, `ERD_MAX_DEPTH=3`.
- **물리 생성** : 엔터티마다 테이블 하나·속성마다 컬럼 하나, 이미 매핑된 엔터티는 건너뜀, PK = 주 식별자 속성, FK 는 완성된 속성 짝만, planToken v5 (`PhysicalGenerationService` 클래스 주석·`relationPlans`·`columnSpec`).
- **변경 이력** : `ModelChangeRecorder.TRACKED` 에 `LogicalModel/Entity/Attribute/Identifier/Relationship`, `EntityTableMapping`, `AttributeColumnMapping`, `LogicalSubjectArea`, `LogicalSubjectAreaEntity`; `CHILDREN` 에 `LogicalIdentifierAttribute`, `LogicalRelationshipAttribute` (부모 이력의 배열).
- **프로젝트 삭제** : `ProjectDataCleanup` 이 네이티브 SQL 로 배치 → 주제 영역 → 관계 짝 → 관계 → 식별자 속성 → 식별자 → 속성 → 엔터티 → 모델 순서로 지운다.
- **권한** : `LogicalModelRestController` 조회 VIEWER, 쓰기 USER, 승인 토글 USER + `requireApprover`. 레이아웃 저장 VIEWER(본인 것).
- **AI·MCP** : AI 메타데이터 도구는 논리 모델을 다루지 않는다. MCP 전용 `getLogicalModel` (`lexorma-ai` `McpServerService`) 이 엔터티·속성을 직접 JPQL 로 읽는다 → 서브타입을 추가하면 **상속 속성이 빠진 채 노출**된다 (D-35).
- **화면** : `features/logical/LogicalModelPage.tsx`(649줄), `LogicalErdPage.tsx`(951), `SubjectAreaPanel.tsx`, `entityDetail.tsx`(탭 `basic/attributes/identifiers/relationships`), `erdNodes.tsx`(`EntityNode`, `RelationshipEdge`, Crow's Foot `marker`), `features/erd/relationLanes.ts`(평행 차선), `features/erd/layout.ts`(ELK `layered`, 방향 **RIGHT**, 워커).

| 슈퍼타입·서브타입 | 같은 업무 인스턴스의 일반화·특수화 (IS-A) | **신규** — 별도 저장, 별도 표기 |
| 식별 관계 | 부모 식별자가 자식 식별자에 포함 | 상속 식별자와 별개 |
| 물리 FK | 물리 참조 무결성 | 상속이 특정 FK 구조가 된다고 가정하지 않는다 (D-30) |
| ERD 레이아웃 | 시각 배치 | 상속 변경이 좌표를 초기화하지 않는다 |

용어 통일 : 화면·문서·코드 모두 **슈퍼타입 / 서브타입 / 서브타입 그룹(분류 그룹)** 으로 쓴다. "상위 유형", "부모 엔터티" 는 쓰지 않는다 (상위 = 주제 영역 계층, 부모 = 일반 관계 출발 쪽에서 이미 쓰고 있다).

| D-33 | 품질 진단 | 기존 진단 변경 / 최소 검증 / 신규 규칙 / AI-6 | **기존 진단 의미 불변** + 상속 구조 점검(신규, 상속 API 의 경고 목록 — 표준화 품질 finding 에 넣지 않음) | `StandardizationFindingGoldenTest` 고정, 중복 집계 없음 | 신규 응답 |
| D-34 | 이력·버전·교환 | — | 이력 TRACKED `LOGICAL_SUBTYPE_GROUP` + CHILD 구성원, 스냅샷 형식 8, 교환 형식 5 (1~4 그대로 가져오기) | 파생 속성 이력 중복 없음 | §16 |
| D-35 | AI·MCP | 이번에 포함 / 후속 | **후속** (단, MCP `getLogicalModel` 의 상속 누락을 후속 항목에 명시) | 주제 영역과 같은 결정, AI·MCP 정책 불변 | 없음 |

### 4.1 서로 묶어 정해야 하는 결정

- **상속 모델 핵심 (D-02·D-03·D-04·D-05)** : 그룹 구조 C + 단일 상속 UNIQUE 를 고르면 다중 그룹(D-05)은 공짜이고 깊이 상한(D-04)만 서비스 검사다.
- **속성·식별자·짝 (D-11·D-15·D-16·D-19·D-23)** : 가상 상속(D-11)을 고르면 서브타입은 상속 PK 를 행으로 갖지 않으므로, 서브타입이 부모인 관계의 짝은 루트의 PK 속성 ID 를 써야 한다(D-19). 그 때문에 해제·슈퍼타입 변경은 그 짝이 있으면 거절해야 한다(D-23). 자체 주 식별자 금지(D-16)를 풀면 "유효 주 식별자" 가 두 개가 될 수 있어 D-19 판정이 모호해진다.
- **승인·동시성 (D-21·D-22)** : 모델 행 잠금 하나로 모든 경쟁을 직렬화하므로 승인 검사는 잠금 뒤 다시 읽은 상태로 한다.
- **물리 (D-30·D-31·D-32)** : D-32 = A 면 D-30·D-31 은 이번 5차에서 결정하지 않아도 된다.

### 5.4 서비스 검증 (모델 행 잠금 뒤)

같은 프로젝트·같은 모델(그룹·슈퍼타입·서브타입·구분 속성), 서브타입 ≠ 슈퍼타입, 순환 없음(슈퍼타입의 조상에 서브타입 없음), 깊이 ≤ 상한(이동하는 서브타입의 하위 트리 깊이 포함 — 주제 영역 이동 검사와 같은 방식), 이미 다른 그룹 구성원이면 거절(DB UNIQUE 는 최후 방어 → `DataIntegrityViolationException` 을 409 로 변환), 서브타입 자체 주 식별자 없음, 유효 속성명 충돌 없음(서브타입과 그 후손 ↔ 새 조상), 구분 속성 ∈ 슈퍼타입 유효 속성, Disjoint 그룹 구분값 중복 없음, 승인 검사(D-21).

## 7. 속성·식별자 상속

### 7.1 유효 속성 계산

`조상 체인 = [루트, …, 직접 슈퍼타입]` (깊이 ≤ 3). 유효 속성 = 루트부터 순서대로 각 엔터티의 직접 속성(속성 `SORT_ORD`) + 자신의 직접 속성. 한 모델의 그룹·구성원을 한 번에 읽어(쿼리 2번) 메모리에서 체인을 만든다 — 그룹은 모델당 수백 건 규모.

조회 응답 (`effectiveAttributes`) 항목 후보 :

```json
{ "entityId": 12, "entityName": "개인 고객", "modifiedAt": "…",
  "ancestors": [ { "entityId": 3, "entityName": "고객", "depth": 1, "groupId": 7, "groupName": "고객 유형" } ],
  "attributes": [
    { "attributeId": 31, "attributeName": "고객 ID", "definedEntityId": 3, "definedEntityName": "고객", "depth": 1,
      "inherited": true, "editable": false, "primary": true, "termId": 101, "dataType": "…", "isRequired": true },
    { "attributeId": 55, "attributeName": "생년월일", "definedEntityId": 12, "depth": 0, "inherited": false, "editable": true, "primary": false } ],
  "primaryKey": [31], "alternateIdentifiers": [ { "identifierId": 9, "definedEntityId": 3, "attributeIds": [33], "inherited": true } ],
  "warnings": [ "SUPERTYPE_PRIMARY_KEY_MISSING" ] }
```

`editable` = 직접 속성이고 현재 사용자가 수정 가능(승인 규칙). 기존 `/entity/{id}/attribute`, `entity/data`, ERD 응답은 바꾸지 않는다.

### 7.2 수정·충돌

- 상속 속성은 정의 엔터티에서만 수정 (D-13).
- 속성 등록·이름 변경 : 현재 엔터티의 **후손 전체**와 **조상 체인** 의 직접 속성과 이름 비교 (대소문자 무시). 모델 잠금 안이라 경쟁 없음. 후손이 많아도 깊이 3 상한으로 범위가 작다.
- 연결 : 서브타입(과 그 하위 트리)의 직접 속성 ↔ 새 조상 체인 유효 속성 이름 비교 → 충돌 목록과 함께 400 `INVALID_LOGICAL_MODEL`.
- 같은 표준 용어·다른 업무 의미 : 이름이 다르면 허용, 진단 경고 후보(후속).

### 7.3 식별자

- 서브타입 유효 주 식별자 = 루트 슈퍼타입 주 식별자 (중간 슈퍼타입도 자체 주 식별자 금지 → 체인 전체에서 루트 하나).
- 서브타입에서 `saveIdentifier(isPrimary=true)` 거절. 보조 식별자는 자기 속성으로만(현행 "같은 엔터티의 속성만" 유지).
- 슈퍼타입 주 식별자 변경·삭제 : 현 규칙 그대로 허용하되, 그 키를 쓰는 짝은 `evaluate` 가 PARENT_KEY_MISMATCH/MISSING 으로 이미 판정한다 (서브타입이 부모인 관계 포함 — 유효 키로 판정하면 자동으로 따라온다).
- 주 식별자 없는 슈퍼타입 : 허용(편집 중), 경고.

## 8. 관계 상속

- 슈퍼타입의 관계는 서브타입에 복제하지 않는다. 엔터티 상세 "관계" 탭은 기존 목록(직접) + "상속 관계" 구역(조상의 관계, 읽기 전용, 정의 엔터티 표시).
- 서브타입 고유 관계는 지금처럼 서브타입에 직접 등록.
- **서브타입이 부모(출발)인 관계의 속성 짝** : 부모 속성 후보 = 유효 주 식별자(루트의 PK 속성). 저장 행은 지금 구조 그대로(`ORGNL_ATRB_SN` = 루트 속성 ID). 검증·`pairsView` 후보·`evaluate` 를 `primaryKey(parent)` → `effectivePrimaryKey(parent)` 로 바꾼다. 다른 서브타입 관계들이 같은 원본 속성 ID 를 참조해도 관계 행이 문맥을 구분하므로 UNIQUE(관계, 부모 속성)와 충돌하지 않는다.
- 자식 쪽 상속 속성은 짝에 쓸 수 없다 (현행 유지).
- 슈퍼타입 ↔ 자신의 서브타입 사이 일반 관계 : 막지 않고 경고(`INHERITANCE_DUPLICATED_BY_RELATIONSHIP` 후보) — 자동 변환 없음.

## 9. 승인·동시성

### 9.1 승인 (D-21 권장안 상세)

| 상황 | 권장 동작 |
|---|---|
| 승인된 슈퍼타입에 서브타입 추가 / 그룹 생성·정책 변경·삭제 | 슈퍼타입에 `rejectApprovedDetail` (승인 권한자만, 승인 상태 유지) |
| 승인된 엔터티를 서브타입으로 지정·해제·이동 | 서브타입과 (옛·새) 슈퍼타입 모두 `rejectApprovedDetail` |
| 승인된 서브타입이 있는 슈퍼타입의 속성 변경 | 현행(슈퍼타입만 검사) + 화면에 "승인된 후손 n개에 영향" 확인 대화상자. 차단 여부는 **사용자 결정** (차단 시 후손 전체 승인 상태를 읽어야 함) |
| 슈퍼타입 승인 취소 | 서브타입 승인 상태 그대로 (일괄 변경 없음) |

그룹·구성원 행에는 승인 컬럼을 두지 않는다 (별도 승인 흐름을 만들지 않음). 대안 "그룹 별도 승인" 은 승인 화면·이력·교환 처리량이 늘어 비권장.

### 9.2 동시성·경쟁 상황

모든 상속 쓰기 : `lockModel` → 대상 행 refresh → DEC-08 기준값(그룹 `modifiedAt`, 연결은 그룹의 `modifiedAt` + 서브타입 엔터티 존재) → 검증 → 쓰기 → 구성 변경 시 그룹 `markModified()`.

| 경쟁 | 결과 |
|---|---|
| A→B, B→A 를 동시에 등록 (순환) | 둘 다 같은 모델 행을 잠그므로 직렬화, 뒤 요청이 순환 검사에서 400 |
| 같은 서브타입에 다른 슈퍼타입 | 직렬화 + 이미 구성원 → 400, 잠금 우회 입력은 `UX_LGCL_SBTYP_01` 위반 → 409 |
| 슈퍼타입 변경 ↔ 엔터티 삭제 | 직렬화, 뒤 요청이 404 또는 `RELATION_EXISTS` |
| 연결 ↔ 속성 추가 (이름 충돌) | 직렬화, 뒤 요청이 이름 충돌 400 |
| 승인 토글 ↔ 연결 | 승인 토글도 `lockEntity` 로 같은 모델 행 → 직렬화, 뒤 요청이 승인 검사 |
| 오래된 그룹 수정 | 409 `MODEL_CONFLICT` |
| 물리 생성 ↔ 상속 변경 | 생성은 모델 행 NOWAIT → 409, planToken 에 상속 구조 포함(단계 6) |

잠금 순서는 기존과 같다 (프로젝트(생성·가져오기만 배타 선행) → 모델 → 행 → 커밋 시 프로젝트 공유). 일괄 연결 API 를 두면 주제 영역 일괄 분류처럼 전부 아니면 전무.

## 12. API 설계 (후보)

공통 : `/api/logical/**`, 조회 VIEWER·쓰기 USER(`@PreAuthorize`), `MenuAuthorization.MENU_ROLES` 에 버튼 id 추가, 다른 프로젝트·모델 대상은 404 `LOGICAL_MODEL_IS_NOT_DEFINED`("…을(를) 찾을 수 없습니다" — 존재 여부를 노출하지 않음), 검증 실패 400 `INVALID_LOGICAL_MODEL`, 참조 존재 `RELATION_EXISTS`, 기준값 400 `MODEL_BASE_REQUIRED`·409 `MODEL_CONFLICT`, 승인 `APPROVED_DATA_CANNOT_BE_UPDATE/DELETED`. 컨트롤러 파라미터는 이름 명시(`-parameters` 없음), 선택 플래그는 `Boolean`.

| Method | 경로 | 내용 |
|---|---|---|
| GET | `/model/{modelId}/subtypeGroup` | 모델의 그룹 + 구성원 (슈퍼타입 이름순, 페이지 없음 — 수백 건 상한 검토, 넘으면 `list-query-policy` 의 그리드 규칙) |
| GET | `/subtypeGroup/{groupId}` | 상세 |
| POST | `/subtypeGroup` | 등록·수정 (`id` 유무, 수정은 `modifiedAt` 필수) |
| DELETE | `/subtypeGroup/{groupId}?modifiedAt=` | 구성원 없을 때만 |
| PUT | `/subtypeGroup/{groupId}/subtypes` | 구성원 전체 교체 (`modifiedAt`, `[{entityId, value}]`, 순서 = 배열 순서), 전부 아니면 전무 |
| GET | `/entity/{entityId}/inheritance` | 조상 체인 + 직접 하위 그룹·구성원 + 후손 수 (깊이 상한) |
| GET | `/entity/{entityId}/effectiveAttributes` | §7.1 |
| GET | `/subtypeGroup/{groupId}/impact?…` | 해제·이동 영향 (짝·후손·승인된 엔터티) — 미리보기 |

등록 예 :

```json
POST /api/logical/subtypeGroup
{ "modelId": 1, "supertypeEntityId": 3, "groupName": "고객 유형", "groupDescription": "고객유형코드로 구분",
  "exclusive": true, "complete": true, "discriminatorAttributeId": 34 }
```

기존 API 확장 (모두 선택 필드·선택 파라미터, 없으면 지금 동작) : 엔터티 등록 `subtypeGroupId`(+`subtypeValue`), `Entity.detail` 에 `supertypeEntityId`/`subtypeGroupId`(읽기), `erd/part`·`erd/neighbors` 응답 `inheritances`(범위 안 그룹·구성원)·`outsideInheritances`, `erd/neighbors?includeInheritance=true`, 속성 짝 조회·저장(유효 키), 모델 버전 비교(그룹 항목), 이력(새 대상 유형). 전체 조회 `/model/{id}/erd` 에는 넣지 않거나 넣더라도 화면 의존성으로 다시 쓰지 않는다 ([COMMON-LIST] 결정과 함께).

## 13. 관리 화면·ERD

### 13.1 관리 화면 (`/logicalModel`)

- 모델 화면 : 주제 영역 패널과 같은 위치에 "서브타입 그룹" 탭/패널 — 슈퍼타입별 그룹 트리, 그룹 정책 배지(배타/중복, 완전/부분), 구분 속성, 구성원(구분값·순서), 연결 대화상자(엔터티 찾기는 `/erd/entities` 검색 재사용), 영향 미리보기 → 확인 대화상자. 성공은 Toast, 409·검증 오류는 대화상자(UI-1 §7).
- 엔터티 상세 : 새 탭 "상속"(슈퍼타입·그룹·직접 하위·전체 계층), 속성 탭에 "상속 속성" 구역(출처 엔터티 링크, 읽기 전용, 색 외 "상속" 글자 표시), 식별자 탭에 상속 주 식별자·보조 식별자(읽기 전용), 관계 탭에 상속 관계 구역.
- 신규 의존성 없음. 스켈레톤·reduced motion·키보드·i18n(`en.ts`)·다크 모드 기존 규칙.

### 13.2 ERD 표기 비교 (D-26)

| 표기 | 슈퍼/서브·방향 | 그룹 | 배타 | 완전 | 다단계 | 평가 |
|---|---|---|---|---|---|---|
| EER (원 + d/o, 이중선) | 선 + 부분집합 기호 | 원 = 그룹 | d/o 글자 | 이중선 | 가능 | 정보 모두 표현, 글자 기반이라 색 의존 없음 |
| UML 일반화 (빈 삼각형) | 명확 | 삼각형 공유 | `{disjoint}` 글자 | `{complete}` 글자 | 가능 | 친숙, 제약은 글자 라벨 필요 |
| IE / Crow's Foot 계열 | 도구마다 상이 | 박스 안 박스 또는 반원 | 도구마다 상이 | 상이 | 상이 | 일관 표준 없음, Crow's Foot 기호와 혼동 위험 |
| IDEF1X (원 + 밑줄) | 명확 | 원 | **배타만** | 한 줄/두 줄 | 가능 | Overlapping 표현 불가 |

권장 : **EER 식 그룹 원** — 지름 ~20px, 원 안 `D`(배타)/`O`(중복) 글자(영어 화면 동일 기호, 툴팁 "배타적 분류/중복 가능 분류"), 슈퍼타입 ↔ 원 선은 Total 이면 이중선, 원 ↔ 서브타입 선은 단일 실선·끝 기호 없음, 구분값이 있으면 서브타입 쪽 선 라벨. 일반 관계선(Crow's Foot, 실선/점선)과 겹치지 않도록 상속선은 굵기·끝 모양으로 구분, 범례에 "상속" 항목 추가. 그룹 이름은 원 툴팁·선택 시 패널.

### 13.3 노드 속성 (D-27)

서브타입 노드 상단에 상속 주 식별자(“상속 PK” 배지 + 정의 엔터티명 툴팁), 그 아래 직접 속성. 슈퍼타입이 범위 밖이어도 상속 PK 표시를 위해 조상 PK 속성만 추가 조회(조상 ID 집합 1쿼리). 전체 상속 속성 표시는 후속(D).

### 13.4 부분 조회·이웃 (D-28)

- `inheritances` : 슈퍼타입과 구성원 중 **범위 안에 있는 것만** 그린다. 그룹 원은 슈퍼타입이 범위 안이고 구성원 1명 이상이 범위 안일 때 그린다. 슈퍼타입만 있거나 서브타입만 있으면 엔터티별 `outsideInheritances` 수 배지("범위 밖 상속 n").
- 이웃 탐색 : `includeInheritance=false`(기본) 는 지금과 같음. true 면 상속 링크도 한 단계로 센다 (같은 300·1~3 한도, 잘리면 `truncated`).
- 계층 전용 : 엔터티 상세의 "계층 열기" → 그 엔터티의 조상 체인 + 후손을 범위로 ERD 열기 (300 상한).
- 자동 확장 없음, 전체 그래프 전송 없음.

### 13.5 자동 배치·레이아웃 (D-29)

그룹 원은 저장하지 않는 계산 요소 : 위치 = 슈퍼타입 노드와 범위 안 서브타입 노드 중심들의 사이(슈퍼타입 쪽 1/3 지점). ELK 계산에는 상속 간선(슈퍼타입 ↔ 서브타입)을 일반 간선과 함께 넣는다 — 방향은 지금 RIGHT 그대로(초기). 슈퍼타입 위·서브타입 아래 배치를 원하면 상속 간선만 별도 계층 제약을 주는 방식을 단계 4 에서 측정 후 결정. 레이아웃 JSON·`VER_NO`·409·영역별 배치·범위 밖 좌표 병합 모두 불변, 상속 변경이 좌표를 지우지 않는다.

## 14. 물리 모델 생성 전략 비교 (D-30·D-32)

| 항목 | A 단일 테이블 | B 슈퍼·서브 테이블 | C 구체 타입 테이블 |
|---|---|---|---|
| 테이블 | 루트 하나 | 엔터티마다 하나 | 말단 서브타입마다 하나 (Partial 이면 슈퍼타입도) |
| PK | 루트 PK | 서브 테이블 PK = 루트 PK 복사 + FK(슈퍼) | 각 테이블 루트 PK 복사, 테이블 간 유일성 보장 불가 |
| 구분 속성 | 필수 컬럼 (Overlapping 은 여부 컬럼 여러 개 필요) | 선택 | 불필요 (테이블이 구분) |
| NOT NULL | 서브타입 필수 속성도 NULL 허용(CHECK 필요) | 그대로 | 그대로 |
| 배타·완전 강제 | CHECK 가능(Disjoint) | DDL 로 강제 어려움 (트리거 영역, 범위 밖) | 배타는 구조상, 완전은 불가 |
| 일반 관계 FK | 루트 테이블로 | 관계가 정의된 엔터티의 테이블로 | 슈퍼타입 관계는 테이블마다 복제 |
| 매핑 영향 | 여러 엔터티 → 한 테이블 : `UX_ENTT_TBL_MPNG_02` 변경 | 엔터티 ↔ 테이블 1:1 유지. 상속 PK 컬럼의 속성 매핑만 문제 (`UX_ATRB_COL_MPNG_01`·소속 검증) | 한 속성 → 여러 컬럼 : `UX_ATRB_COL_MPNG_01` 변경 |
| 표준화 변경 전파 | 단순 | PK 복사본만 | 공통 속성 전부 복제 |

권장 진행 : **5차 = 생성 미리보기가 상속 구조에 속한 엔터티(슈퍼타입·서브타입)를 사유 `INHERITANCE_UNSUPPORTED` 로 표시하고 생성하지 않는다** (오류 엔터티 처리와 같은 방식 — 나머지 엔터티는 생성 가능, planToken 에 상속 여부 포함 → v6). 이미 매핑된 엔터티는 지금처럼 건너뜀. 다음 단계 후보는 B (1:1 매핑을 유지하므로 영향이 가장 작다).

## 15. 기존 매핑 영향 (D-31)

- 현재 카디널리티 : 엔터티 ↔ 테이블 1:1 (양쪽 UNIQUE), 속성 ↔ 컬럼 1:1 (양쪽 UNIQUE), 속성 매핑은 같은 엔터티 매핑 아래 그 엔터티의 속성만 (`saveAttributeMapping`).
- 논리 전용 단계(5차) : 변경 없음. 슈퍼타입·서브타입을 각각 기존 테이블에 수동 매핑하는 것은 지금처럼 가능하다. 서브타입 테이블의 상속 PK 컬럼은 매핑할 속성이 없어 매핑 정합성 화면에서 "매핑 안 된 컬럼" 으로 보인다 → 품질 화면에 "상속 키 컬럼" 안내만 추가할지 결정 필요.
- B 전략 구현 시 선택지 : (1) 상속 PK 컬럼은 매핑하지 않음(진단이 상속 키로 인식) — 구조 변경 없음, (2) `UX_ATRB_COL_MPNG_01` 을 `(ENTT_TBL_MPNG_SN, LGCL_ATRB_SN)` 으로 바꾸고 소속 검증을 "매핑 엔터티의 유효 속성" 으로 넓힘 — 마이그레이션·M-7 규칙 변경. 권장 (1) 우선.
- 기존 UNIQUE 를 서브타입 때문에 바로 제거하지 않는다.

## 16. 품질 진단 (D-33)

- 기존 표준화 품질·매핑 정합성 : 상속 속성은 행이 아니므로 결과·건수·지문 불변 (`StandardizationFindingGoldenTest` 영향 없음).
- 신규 "상속 구조 점검"(경고, 상속 API·그룹 목록 응답의 `warnings`) : 슈퍼타입 주 식별자 없음, 빈 그룹, Total 인데 구성원 1명, Disjoint 구분값 중복(저장 시 거절이므로 교환·레거시 대비), 구분 속성은 있는데 구분값 없는 구성원, 슈퍼타입 ↔ 서브타입 일반 관계, 물리 생성 미지원 안내.
- AI-6 로 넘길 것 : 같은 용어·다른 의미, 물리 전략과 실제 모델 차이, 상속 키 ↔ 물리 PK 정합성.

## 17. 변경 이력·모델 버전·Import·Export (D-34)

- 이력 : `TargetType.LOGICAL_SUBTYPE_GROUP` 추가, TRACKED 필드 `model, supertypeEntity, groupName, groupDescription, exclusive, complete, discriminatorAttribute, sortOrder`, 구성원은 CHILD(`subtypes` 배열 : `subtypeEntity, value, sortOrder`) — 속성 짝과 같은 방식이라 연결·해제·순서·구분값 변경이 그룹 이력 한 줄에 남는다. 파생 속성·식별자 이력은 만들지 않는다. `NAME_FIELDS` 에 그룹명. 엔터티 이력에는 남기지 않는다 (주제 영역 D-25 와 같은 이유 — 엔터티 행이 바뀌지 않음).
- 버전 : 스냅샷 형식 **8** (`ModelChangeRecorder.currentState` 가 같은 필드 목록을 쓰므로 자동 포함, `ModelSnapshotFieldCoverageTest`). 형식 7 이하 스냅샷은 그룹 없음으로 읽고 비교한다. 가상 속성은 스냅샷에 넣지 않는다.
- 교환 : 형식 **5** — `LOGICAL_SUBTYPE_GROUP` 항목(구성원 배열 포함). 가져오기 : 슈퍼타입·서브타입·구분 속성 ID 를 새 ID 로 재매핑, 파일 안 참조 누락·다른 모델·순환·단일 상속 위반·깊이 초과·서브타입 자체 주 식별자·유효 속성명 충돌·구분 속성이 슈퍼타입 유효 속성 아님·Disjoint 구분값 중복이면 파일 거절(400), 형식 1~4 파일에 그룹이 있으면 거절, 형식 1~4 는 그대로 가져옴. 주제 영역·식별자·관계·짝은 지금 순서대로, 그룹은 엔터티·속성 다음·관계 짝 앞(짝 검증이 유효 키를 쓰므로)에 만든다. 기존 모델 이름 충돌 규칙(CONFLICT) 그대로, 전체 트랜잭션 롤백.
- 이번 단계에서는 형식 번호를 바꾸지 않았다.

## 18. 권한·프로젝트 격리

별도 ACL 없음. 그룹·구성원은 `PRJ_SN` 을 갖고 모든 조회가 로그인 프로젝트 + 모델로 거른다. 보안 시나리오 → 기대 결과 : 다른 프로젝트 슈퍼타입/서브타입/그룹 ID → 404(존재 숨김), 같은 프로젝트 다른 모델 엔터티 → 400 "같은 논리 모델", 다른 모델·다른 엔터티 속성을 구분 속성으로 → 400, 다른 사용자 레이아웃 → 기존처럼 본인 것만, 상속 응답은 같은 모델 엔터티만 담으므로 정보 노출 없음, Import 의 ID 조작 → 파일 안 ID 만 해석(DB ID 를 받지 않음).

## 19. 성능 설계

- 조회 방식 권장 : **모델 단위 일괄 조회 + 메모리 계층 계산** (그룹·구성원 2쿼리, 깊이 3 상한). 엔터티 상세는 조상 체인 엔터티 ID ≤ 3개의 속성·식별자 추가 1~2쿼리. 재귀 CTE 는 H2·PostgreSQL 문법 차이·플랜 불확실성으로 비권장, Closure Table·캐시 불필요.
- 측정 계획 (격리 DB, `LEXORMA_PERF=true` 류 선택 테스트) :

| 규모 | 엔터티 | 그룹 | 구성원 | 측정 |
|---|---:|---:|---:|---|
| 소형 | 100 | 10 | 30 | 기능 회귀 |
| 중형 | 1,000 | 100 | 300 | 상세·유효 속성·그룹 목록 |
| 대형 | 3,000 | 300 | 900 | ERD 100·300 부분 조회, 이웃, 버전 생성, 교환 |
| 확장 | 10,000 | 1,000 | 3,000 | 그룹 목록·연결 검증(후손 이름 비교) |

  항목 : 계층 일괄 조회, 유효 속성, 상속 키 계산, 짝 후보, 영향 분석, ERD 범위 조회(추가 쿼리 수가 엔터티 수와 무관한지), 모델 버전, 교환. 수치는 공식 지원 한계가 아니다.

## 23. 사용자 결정 필요 사항 (우선순위 순)

1. **단일/다중 상속** (D-03) — 권장 단일, DB UNIQUE.
2. **다단계 깊이** (D-04) — 권장 최대 3 (2·4 도 가능).
3. **슈퍼타입별 복수 그룹** (D-05) — 권장 허용, 서브타입은 한 그룹에만.
4. **상속 속성 관리** (D-11·D-12·D-13·D-14) — 권장 가상 조회·재정의 금지·이름 충돌 거절.
5. **주 식별자·자체 식별자** (D-15·D-16·D-17) — 권장 루트 PK 상속, 서브타입 주 식별자 금지(연결 시 거절), 보조 식별자 허용.
6. **승인** (D-21) — 권장 "상세 변경" 규칙(`rejectApprovedDetail`), 그룹 승인 없음. 추가 결정 : 승인된 후손이 있을 때 슈퍼타입 속성 변경을 막을지.
7. **관계 상속·짝** (D-18·D-19·D-23) — 권장 복제 없음, 서브타입 부모 짝은 루트 PK ID, 짝이 있으면 해제·이동 거절.
8. **ERD 표기** (D-26·D-27·D-28) — 권장 EER 그룹 원(D/O, Total 이중선), 상속 PK 표시, 범위 밖 상속 수 별도.
9. **논리·물리 매핑 확장 필요성** (D-31) — 권장 5차는 변경 없음, B 구현 시 "상속 키 컬럼 미매핑" 우선.
10. **물리 변환 전략·범위** (D-30·D-32) — 권장 5차는 미지원 안내만, 다음 작업으로 전략 B.
11. 그 밖 : 배타·완전 기본값 없음(D-07), 구분 속성 선택(D-08), 빈 그룹 허용(D-09), 명명(슈퍼타입 `SPRTYP`·서브타입 `SBTYP` 기관 표준단어 여부, 배타·완전 단어 또는 `DPLCT_ALWNC_YN`/`ESNTL_YN` 대안), 서브타입 이동 시 같은 PK 체인이면 허용할지(§10).
