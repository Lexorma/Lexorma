# M-4c 원본 DB 스키마·TABLE 매핑

> 2026-11-13. [M-4](data-modeling-roadmap.md#m-4-역공학-결과의-물리-모델-가져오기erd-자동-생성)의 세 번째 단계로, 정책은 [M-4c 착수 전 정책](m4-foundation.md) 5장을 따른다.
> 수집한 원본 카탈로그와 물리 모델 사이의 **매핑만** 관리한다.
> 원본 DB 와 물리 모델은 바꾸지 않는다. 가져오기(M-4e)·비교(M-4d)는 하지 않는다.
> **상태 : 완료 (2026-11-13).** 완료 판정과 후속 검증 항목은 12장, 구현 중 정한·바뀐 정책은 [m4-foundation.md 5.11](m4-foundation.md#511-m-4c-구현에서-정한바뀐-것). M-4d 는 미착수다.

## 1. 기존 구조 분석

### 1.1 원본 객체 식별
- **안정 식별자**
  - 원본 스키마·테이블 행(`TB_SRC_SCHM`·`TB_SRC_TBL`)은 수집마다 비교 이름(`CMPR_NM`, 스키마는 비교 경로 `PATH_CN`)으로 같은 행을 다시 쓴다.
  - 그래서 행 일련번호(`SRC_SCHM_SN`·`SRC_TBL_SN`)가 안정 식별자다.
  - 버전 행(`TB_SRC_TBL_VER`)의 ID 는 수집마다 새로 생기므로 매핑 키로 쓰지 않는다.
- **재생성** : 원본에서 사라졌다가 같은 이름으로 다시 생기면 **같은 행**에 생성 차수(`CRT_CYCL`)가 1 오른다. 매핑은 확정 때의 생성 차수를 저장하고, 다르면 재확인 대상으로 본다.
- **이름 변경** : 수집이 `REMOVED` + `ADDED` 로 기록한다 (같은 객체로 단정하지 않음, AI-1c). 매핑은 "원본 없음" 이 되고, 새 이름은 미매핑으로 보인다.
- **OID** : PostgreSQL OID 는 수집하지도 저장하지도 않는다.
- **삭제 판정** : "그 시점에 있는가" 는 마지막 반영(COMPLETED) 수집의 반영 순서 R 에서 객체마다 R 이하의 마지막 버전이 삭제 표시(`REMOVED`)인지로 정한다 (`catalogAt`·`tableAt`·M-4b ERD 와 같은 규칙). PARTIAL 수집의 범위 밖 객체는 앞 버전이 유효하므로 삭제로 보지 않는다.

### 1.2 모델 쪽
- `SchemaInfo`(프로젝트마다 기본 스키마 `DEFAULT` 하나, 예제 프로젝트의 기본 스키마 ID 는 0)·`TableInfo`(스키마 단위 이름 공간, `UX_TBL_01`)를 그대로 쓴다. 바꾸지 않는다.
- 권한 판정은 `ExecutionContextVerifier.verifyProjectManager` 다 (프로젝트 관리자 또는 ADMIN, 지금의 DB 기준). 원본 연결·수집과 같다.
- 잠금 순서는 프로젝트(`ProjectWriteGuard.lock`, 공유) → 하위 행이다. 연결 삭제 쪽은 프로젝트 → 연결 순서다.

## 2. 모듈 간 계약

| 위치 | 내용 |
|---|---|
| `lexorma-core` `core/source/SourceCatalogReader` | 읽기 전용 계약 (아래) |
| `lexorma-core` `core/source/SourceConnectionDeletedEvent` | 원본 연결 삭제 직전 이벤트 |
| `lexorma-source` `collection/service/SourceCatalogReaderService` | 계약 구현 |
| `lexorma-data` `sourcemapping/*` | 매핑 저장·상태 계산·API·이벤트 처리 |

- **`SourceCatalogReader` 의 메서드**
  - `connection(projectId, id)` · `connections(projectId)` : 프로젝트의 연결. 다른 프로젝트 것은 비어 있다.
  - `latest(projectId, connectionId)` : 마지막 반영 시점의 스키마·테이블·VIEW 를 돌려준다.
    - 담기는 것 : 안정 ID, 비교 경로, 비교 이름, 생성 차수, 유형, COMMENT.
    - 반영된 수집이 없으면 `reflectedOrder = null` 이다.
  - `compareName(connection, kind, name)` : 따옴표 없이 쓴 모델 이름을 원본 DBMS 비교 규칙으로 바꾼다. 규칙은 원본 모듈의 `SourceIdentifiers` 한 곳에만 있다.
  - `Connection.defaultSchemaCompareName` : DBMS 의 기본 스키마로, PostgreSQL 은 `public` 이다. 다른 DBMS 는 정하지 않는다.
- **계약의 성격**
  - 값(record)만 오가고 원본 DB 에 접속하지 않는다.
  - `lexorma-source` ↔ `lexorma-data` 직접 의존은 없다 (`ModuleBoundaryTest` 통과).
  - 원본 ERD(`SourceSnapshotService.erd`)와 같은 버전 조회(`SourceTableVersionRepository.at`)를 쓰고, 수집·카탈로그 API 는 복제하지 않았다. 화면의 원본 상세는 기존 `/api/source/**` 로 이동한다.

## 3. 테이블·마이그레이션 (`V2__source_mapping.sql`, PostgreSQL·H2)

**이 파일부터 증분 마이그레이션이다.** V0·V1 은 고치지 않았고 체크섬도 그대로다. 개발 DB 는 다시 만들지 않는다.

| 테이블 | 내용 | 제약 |
|---|---|---|
| `TB_PRJ_SRC_CNTN` 프로젝트 출처 접속 | 프로젝트의 가져오기 기준 연결 (`PRJ_SN`, `SRC_CNTN_SN`) | `UX_PRJ_SRC_CNTN_01 (PRJ_SN)` — 프로젝트마다 하나 |
| `TB_SRC_SCHM_MPNG` 출처 스키마 매핑 | 원본 스키마(`SRC_SCHM_SN`) ↔ 모델 스키마(`SCHM_SN`), 확정 때의 `PATH_CN`·`SCHM_NM`·`CRT_CYCL`·`RFLT_ORD` | `UX_…_01 (SRC_CNTN_SN, SRC_SCHM_SN)`, `UX_…_02 (SRC_CNTN_SN, SCHM_SN)` — 연결 안에서 1:1 |
| `TB_SRC_TBL_MPNG` 출처 테이블 매핑 | 원본 TABLE(`SRC_TBL_SN`, 소속 `SRC_SCHM_SN`) ↔ 모델 TABLE(`TBL_SN`), 확정 때의 `PATH_CN`·`CMPR_NM`·`CRT_CYCL`·`RFLT_ORD` | `UX_…_01 (SRC_CNTN_SN, SRC_TBL_SN)`, `UX_…_02 (SRC_CNTN_SN, TBL_SN)` — 연결 안에서 1:1 |

- **원본 쪽 FK 없음** : 원본 쪽(`TB_SRC_*`)은 값만 두고 FK 를 걸지 않는다 (모듈·생명주기 분리, 정책 5.1). 원본 연결 삭제는 이벤트로 정리한다.
- **모델 쪽 FK** : `FK_SRC_SCHM_MPNG_01 → TB_SCHM`, `FK_SRC_TBL_MPNG_01 → TB_TBL` 모두 **ON DELETE SET NULL** 이다.
  - 모델 객체를 지워도 매핑 행이 남아 "모델 없음" 으로 보이고, 사용자가 해제한다.
  - 모델 삭제 API 의 권한·동작은 바꾸지 않았다.
- **1:1 은 유니크 인덱스로도 막는다**. `SCHM_SN`·`TBL_SN` 이 NULL 인 행(모델 없음)은 서로 겹쳐도 된다.
- **예제 데이터** : 기존 규칙대로 V2 에 데이터 사전·물리·논리·매핑·자체 인덱스 예제를 넣었다.
  - 새 단어는 없고, 새 용어 3개(`PRJ_SRC_CNTN_SN`·`SRC_SCHM_MPNG_SN`·`SRC_TBL_MPNG_SN`)를 더했다.
  - LEXORMA 예제가 있을 때만 넣는다.
  - 결과 : 예제 인덱스 100개(컬럼 143개). 마이그레이션 수·인덱스 수를 확인하는 테스트 기준값을 고쳤다.
- **프로젝트 삭제** : `ProjectDataCleanup` 이 세 테이블을 지운다 (`ProjectDeletionIntegrationTest` 의 테이블 목록에 추가).
- **기존 설치 업그레이드 확인**
  - 개발 DB(`lexorma`, V0·V1 적용 상태)에 V2 가 2026-11-13 20:39:15 에 적용됐다. 사용자가 IDE 에서 띄운 애플리케이션이 새 파일로 다시 시작하며 적용한 것으로 보인다.
  - 이 세션의 `bootRun` 은 그때 기동에 실패해 적용하지 않았다.
  - 결과 : V0·V1 체크섬 불일치 없이 V2 만 적용됐고 예제 테이블 3·인덱스 100이 들어갔다. 이후 그 애플리케이션이 같은 DB 로 계속 실행 중이다 (검증 통과).
  - **그래서 V2 는 이제 고칠 수 없다 — 바꿀 것이 생기면 V3 로 더한다.**

## 4. 기준 원본 연결

- **고를 수 있는 연결** : 프로젝트의 연결 중 하나만 된다. 다른 프로젝트의 연결은 `SOURCE_CONNECTION_NOT_FOUND` 다.
- **완료된 수집이 없을 때** : 연결로 지정할 수는 있지만, 매핑 확정은 `SOURCE_MAPPING_INVALID` 로 거절한다. 화면도 안내하고 수집으로 이동하게 한다.
- **변경·해제**
  - 지금 기준 연결에 매핑이 있으면 `acknowledge` 없이는 `SOURCE_MAPPING_CONFLICT`(409) 로 남는 매핑 수를 알린다. 화면은 확인 대화상자를 띄운다.
  - 확인하면 **매핑을 지우지 않고 그 연결의 매핑으로 남긴다.** 다른 연결에 옮기지 않으므로 서로 다른 원본 DB 의 객체가 섞이지 않는다.
  - 그 연결을 다시 기준으로 고르면 남긴 매핑이 다시 쓰이고, 상태는 그때 다시 계산된다.
  - 현황 화면에 "다른 연결에 남아 있는 매핑" 수를 보여 준다.
- **연결 삭제** : `SourceConnectionService.delete` 가 카탈로그를 지우기 전에 `SourceConnectionDeletedEvent` 를 발행한다. `lexorma-data` 의 `SourceMappingCleanup` 이 같은 트랜잭션에서 그 연결의 TABLE·스키마 매핑과 기준 지정을 지운다.
  - 이벤트는 동기 리스너로 처리한다. 리스너가 실패하면 연결 삭제 전체가 롤백되므로 무효 매핑이 남지 않고, 따로 재시도할 작업이 없다.
  - 단, 이것은 삭제가 매핑 확정과 겹치지 않을 때의 이야기다. 동시에 일어나는 경우는 테스트하지 않았다 (12.1).

## 5. 스키마·TABLE 매핑

- **후보 (저장하지 않음, 자동 매핑 없음)**
  - 스키마 : 원본 DBMS 비교 규칙으로 이름이 같은 모델 스키마를 찾는다. 없고 원본이 DBMS 기본 스키마(PostgreSQL `public`)면 모델 기본 스키마(DEFAULT)를 후보로 낸다.
  - TABLE : 매핑된 모델 스키마 안에서 이름이 같은 테이블이 후보다. 이름 비교는 원본 DBMS 규칙을 따른다 (PostgreSQL 은 모델 `TB_USER` ↔ 원본 `tb_user`).
  - 후보가 이미 다른 원본에 매핑되어 있으면 `taken` 으로 표시하고, 확정하면 거절된다.
- **확정** (`PUT /api/sourceMapping/schemas`·`/tables`) : 사용자가 실행해야 저장된다. 원본은 마지막 반영 시점에 있어야 한다.
  - TABLE 은 VIEW 가 아니어야 한다 (VIEW 매핑 없음, 정책 5.9).
  - 원본 스키마의 매핑이 유효해야 하고, 모델 테이블이 그 매핑된 모델 스키마에 있어야 한다. 잘못된 스키마는 거절한다.
  - 같은 원본을 다시 확정하면 모델 쪽을 바꾸고 확정 시점(생성 차수·반영 순서)을 새로 적는다.
- **해제**
  - 스키마 매핑 해제는 그 원본 스키마의 TABLE 매핑도 함께 해제한다. 화면 확인 문구에 적었다.
  - TABLE 매핑 해제는 매핑 행만 지운다.
- **하지 않는 것** : 원본에만 있는 스키마는 미매핑으로 둔다. 모델 스키마를 자동으로 만들지 않고, DEFAULT 스키마를 바꾸지 않는다.

## 6. 상태 (저장하지 않고 조회 때 계산)

| 상태 | 조건 (위에서부터 먼저 맞는 것) | 이유 코드 |
|---|---|---|
| 모델 없음 `MODEL_MISSING` | 매핑된 모델 스키마·테이블이 지워짐 (FK SET NULL) | `MODEL_DELETED` |
| 원본 없음 `SOURCE_MISSING` | 마지막 반영 시점에 원본이 없음 (삭제 표시) | `REMOVED` |
| 재확인 필요 `RECHECK` | 생성 차수가 확정 때와 다름 (같은 이름으로 재생성) | `RECREATED` |
| 충돌 `CONFLICT` | (TABLE) 스키마 매핑이 없거나 유효하지 않음, 모델 테이블이 다른 스키마로 옮겨짐, 원본이 VIEW 로 바뀜 | `SCHEMA_UNMAPPED`·`SCHEMA_MISMATCH`·`NOT_TABLE` |
| 매핑됨 `MAPPED` | 그 밖 | — |
| 미매핑 `UNMAPPED` | 매핑 행 없음 (스키마가 매핑되지 않은 TABLE 은 `SCHEMA_UNMAPPED` 를 함께 표시) | — |

- **저장하는 것** : 사용자 확정과 확정 시점의 원본 식별 정보뿐이다.
- **계산하는 것** : 원본 삭제·재생성, 모델 삭제·이동은 매번 계산한다. 수집·모델 변경 뒤에 따로 갱신할 것이 없고 계산 결과가 어긋나지 않는다.
- **1:1 위반** : 유니크 인덱스와 확정 검증이 막으므로 저장된 상태로는 생기지 않는다. 화면에서는 후보의 `taken` 과 확정 거절로 보인다.

## 7. 동시성

- **변경 직렬화** : 변경 API 는 기준 연결 행(배타, `findForUpdate`)을 잠근다 (앞의 잠금 순서는 아래). 그래서 같은 프로젝트의 매핑 변경은 한 번에 하나씩 처리된다.
- **연결 삭제와의 차례 (2026-11-14 보강, 12.1)** : 매핑 변경은 프로젝트(공유) → 원본 연결 행(공유, `SourceCatalogReader.lockConnection`) → 기준 연결 행(배타) 순서로 잠근다. 연결 삭제는 프로젝트 → 연결 행(배타) → (이벤트) 매핑 정리 순서다. 같은 방향이라 교착 순환이 없고, 삭제와 겹친 저장은 삭제가 지우거나 삭제 뒤에 거절된다.
- **마지막 방어선** : 유니크 인덱스가 1:1 을 지키고, 위반은 `SOURCE_MAPPING_CONFLICT` 로 바꾼다.
- **테스트로 확인한 것** (H2·PostgreSQL)
  - 같은 모델 테이블을 두 원본에 동시에 확정 → 하나만 성공하고 하나는 409.
  - 같은 원본을 두 모델 테이블에 동시에 확정 → 행 하나만 남는다.
  - 연결 삭제·기준 변경·스키마 해제와 확정의 경합 (12.1, T-01~T-08).

## 8. API (`/api/sourceMapping`, `SourceMappingRestController`)

| 메서드 | 경로 | 권한 | 내용 |
|---|---|---|---|
| GET | `/api/sourceMapping` | VIEWER | 현황 : 기준 연결, 연결 목록, 마지막 반영, 스키마 행(후보), 상태별 건수, VIEW 수, 다른 연결에 남은 매핑, 모델 스키마 |
| GET | `/api/sourceMapping/tables` | VIEWER | TABLE 행 (`sourceSchemaId`·`status`·`keyword`, 쪽 단위 최대 500) + 상태별 건수 |
| GET | `/api/sourceMapping/modelTables?schemaId=` | VIEWER | 매핑할 모델 테이블 고르기 (200개까지, 이미 매핑된 것 표시) |
| PUT | `/api/sourceMapping/base` | USER + 프로젝트 관리자·ADMIN | 기준 연결 설정·해제 (`acknowledge`) |
| PUT·DELETE | `/api/sourceMapping/schemas`, `/schemas/{sourceSchemaId}` | 같음 | 스키마 매핑 확정·변경·해제 |
| PUT·DELETE | `/api/sourceMapping/tables`, `/tables/{mappingId}` | 같음 | TABLE 매핑 확정·변경·해제 |

- **새 오류 코드**
  - `SOURCE_MAPPING_INVALID`(400) : 확정할 수 없음.
  - `SOURCE_MAPPING_CONFLICT`(409) : 1:1 충돌 또는 확인 필요.

### 12.1 연결 삭제와 매핑 변경의 경합

> **해결 (2026-11-14, P1 후속 안정화).** PostgreSQL 에서 재현했고, 매핑 변경이 원본 연결 행을 공유 잠금으로 잡도록 고쳤다. 스키마·마이그레이션·API·오류 코드는 바꾸지 않았다.

- **재현 (수정 전 코드, PostgreSQL 18.6 임시 DB)**
  - 방법 : 한 트랜잭션을 저장(flush)까지 마치고 커밋 전에 멈춘다. 다른 트랜잭션을 시작해 DB 잠금 대기(`pg_stat_activity`, H2 `SESSIONS.BLOCKER_ID`)를 확인한 뒤 앞 트랜잭션을 커밋시킨다. 고정 대기(`Thread.sleep`)로 순서를 짐작하지 않는다.
  - **T-01 (확정이 먼저)** : 확정 A 가 기준 연결 행을 잡고 TABLE 매핑을 저장 → 연결 삭제 B 가 TABLE·스키마 매핑을 일괄 삭제(A 의 커밋 전 행은 보지 못함) → 기준 연결 행에서 대기 → A 커밋 → B 가 기준 연결 행과 연결을 지우고 커밋. **결과 : 지워진 연결을 가리키는 TABLE 매핑 1건이 남았다.**
  - **T-02 변형 (삭제가 먼저, 기준 지정)** : 삭제 B 가 커밋 전인 사이에 기준 지정 A 가 그 연결로 기준 행을 넣었다. A 는 어떤 잠금도 기다리지 않고 커밋했다 (B 의 정리는 A 의 행을 보지 못함). **결과 : 지워진 연결을 기준으로 가리키는 프로젝트 1건이 남았다.** 분석 때 예상하지 못한 두 번째 경로다.
  - H2 에서는 같은 테스트가 수정 전에도 통과했다. H2 는 프로젝트 행 공유 잠금(`PESSIMISTIC_READ`)이 배타 잠금처럼 동작해, 같은 프로젝트의 쓰기가 모두 프로젝트 행에서 줄을 선다. **H2 통과만으로는 이 경합을 검증할 수 없다.**
- **원인** : 연결 삭제(프로젝트 → 원본 연결 행 배타 → 정리)와 매핑 변경(프로젝트 → 기준 연결 행 배타)이 **같은 행을 잠그지 않았다.** 프로젝트 행은 양쪽 모두 공유 잠금이라 서로를 막지 않는다. PostgreSQL READ COMMITTED 에서 정리의 일괄 삭제는 커밋되지 않은 새 행을 보지 못한다. 이벤트는 동기 리스너로 같은 트랜잭션에서 처리되므로 원자성 문제는 아니다 (이벤트 순서만 바꿔서는 기준 지정 경로가 남는다).
- **검토한 방식**
  - 정리 리스너가 기준 연결 행을 먼저 잠근다 : 기준 행이 아직 없는 프로젝트의 기준 지정(새 행 INSERT)을 막지 못한다. 채택하지 않음.
  - 매핑 → 원본 연결 FK : 5.1 정책(원본 쪽 FK 없음) 변경과 V3 마이그레이션이 필요하다. 사용자 결정 사항이라 채택하지 않음.
  - **매핑 변경이 원본 연결 행을 공유 잠금으로 잡는다 (채택)** : 연결 삭제의 배타 잠금과 같은 행에서 차례가 정해진다. DB 잠금이므로 여러 애플리케이션 인스턴스에서도 유효하다. 스키마 변경이 없다.
- **바꾼 것**
  - core 계약 `SourceCatalogReader.lockConnection(projectId, connectionId)` : 연결 행을 공유 잠금으로 읽고 있으면 true. `SourceCatalogReaderService` 가 구현한다 (`SourceConnectionRepository.findForShare`, `PESSIMISTIC_READ`, 쓰기 트랜잭션 필수 `MANDATORY`). 모듈은 여전히 core 계약으로만 만난다.
  - 잠금 순서 : **프로젝트(공유) → 원본 연결 행(공유) → 기준 연결 행(배타)**. 연결 삭제(프로젝트 → 연결 행 배타 → 정리)와 같은 방향이라 교착 순환이 없다.
  - 스키마·TABLE 확정·해제 (`lockBase`) : 기준 연결 ID 를 읽고(엔티티를 올리지 않는 조회) 그 연결 행을 공유 잠금 → 기준 연결 행 배타 잠금 → 그 사이 기준이 바뀌었으면 `SOURCE_MAPPING_CONFLICT`(409). 연결이 없어졌으면 `SOURCE_CONNECTION_NOT_FOUND`.
  - 기준 지정 (`setBase`) : 새 기준 연결을 공유 잠금으로 확인한다 (이전에는 잠금 없는 존재 확인). 지금 기준 연결은 잠그지 않는다 : 지워지면 기준 지정도 함께 지워진다.
  - 연결 삭제·정리 리스너 : 코드는 그대로, 잠금 관계를 주석에 적었다.
  - 결과 : 확정이 먼저 잠그면 삭제가 그 커밋을 기다렸다가 방금 저장한 매핑·기준 지정까지 지운다. 삭제가 먼저면 확정·기준 지정은 기다렸다가 거절된다.
  - 오류 응답 : 새 코드 없음. 경합 시 기존 `SOURCE_CONNECTION_NOT_FOUND`·`SOURCE_MAPPING_INVALID`·`SOURCE_MAPPING_CONFLICT` 중 하나다.
- **테스트 (`SourceMappingIntegrationTest`, +5)**

  | 번호 | 테스트 | 수정 전 PostgreSQL | 수정 후 H2·PostgreSQL |
  |---|---|---|---|
  | T-01 | `deleteWaitsForConfirm` : 확정·기준 지정 먼저 → 삭제 | 실패 (고아 TABLE 매핑 1) | 통과, 고아 없음 |
  | T-02 | `confirmWaitsForDelete` : 삭제 먼저 → 확정·기준 지정 | 실패 (기준 지정이 기다리지 않음, 고아 기준 1) | 통과, 거절·고아 없음 |
  | T-03·04·05 | `deletionOrderAndRollback` : 확정 후 삭제, 삭제 후 확정, 삭제 롤백 | 통과 | 통과 |
  | T-06 | `concurrentConfirm` (기존) : 1:1 동시 확정 | 통과 | 통과 |
  | T-07 | `baseChangeWhileConfirming` : 기준 변경 ↔ TABLE 확정 | 통과 | 통과 (다른 연결 원본 혼합 없음, 409 또는 400) |
  | T-08 | `unmapSchemaWhileConfirming` : 스키마 해제 ↔ TABLE 확정 | 통과 | 통과 |

  - 전체 : H2 `./gradlew build --rerun-tasks` 616 통과·실패 0·건너뜀 20, PostgreSQL 18.6 새 임시 DB 616 통과·실패 0·건너뜀 14, `ModuleBoundaryTest` 통과.
- **기존 데이터 (개발 DB, 읽기 전용 조회)** : 원본 연결·기준 지정·스키마 매핑·TABLE 매핑이 모두 0건이다. 고아·다른 프로젝트 연결 참조·다른 연결에 남은 매핑 모두 0건이라 보정할 것이 없다.
- **남은 위험**
  - 매핑 변경이 진행 중인 수집 반영(연결 행 배타 잠금)을 기다린다. 반영 트랜잭션은 짧지만 큰 원본에서는 대기가 길어질 수 있다 (12.4 와 함께 잰다).
  - 앞으로 원본 연결에 기대는 저장 경로를 lexorma-data 에 더하면 같은 `lockConnection` 을 거쳐야 한다 (M-4d·M-4e).
  - FK 가 없으므로 이 잠금 규칙을 우회하는 직접 SQL 은 막지 못한다 (5.1 정책 그대로).

### 12.2 기준 연결 복귀

- **확인한 것**
  - `baseConnectionAndDeletion` 과 브라우저 검증 : 기준을 바꿨다가 되돌리면 남아 있던 매핑이 다시 쓰인다.
- **구조상 보장되는 것**
  - **원본 생성 차수 재검증** : 상태는 조회할 때마다 그 연결의 마지막 반영 시점과 저장된 생성 차수로 계산한다. 다른 연결이 기준이던 동안 원본이 재생성·삭제됐다면, 복귀한 뒤 "재확인 필요"·"원본 없음" 으로 보여야 한다.
  - **다른 연결과의 혼합 방지** : 매핑 행에 연결 ID 가 있고, 유니크 인덱스와 조회·변경이 모두 연결 단위다. 변경 API 는 현재 기준 연결의 매핑만 다룬다.
  - 한 모델 TABLE 이 두 연결에 각각 매핑되어 남아 있는 것은 허용된다 (연결 단위 1:1).
- **후속 작업** : "기준 변경 → 원래 연결에서 원본 재생성·삭제를 수집 → 복귀" 를 한 번에 확인하는 테스트를 추가한다. 지금은 같은 계산을 쓰는 `statuses` 테스트로 간접 확인한 상태다.

### 12.3 V2 예제 데이터

- **목적** : 기존 규칙(새 `TB_` 테이블의 예제)에 따라 Lexorma 자기 스키마 예제(프로젝트 0 `LEXORMA`)에 새 테이블 3개를 넣는다. 데이터 사전 용어 3개, 테이블·컬럼, 논리 엔터티·매핑, 자체 인덱스가 들어간다. `V0SeedMigrationTest`·`SmokeTest` 의 표준화 품질 0건을 유지하기 위한 것이다.
- **기존 설치 DB 에 적용해도 안전한가 (파일 검토)**
  - 모든 행이 프로젝트 0 에만 들어간다.
  - ID 는 시퀀스(`nextval`)로 받는다. 고정 ID 가 없어 사용자 행과 ID 가 겹치지 않는다.
  - 각 INSERT 는 같은 이름이 이미 있으면 넣지 않는다 (`not exists`).
  - 예제 프로젝트·기본 스키마·참조할 도메인이나 단어가 없으면 해당 행은 들어가지 않는다.
  - 실제 개발 DB 에서 문제 없이 적용됐다 (3장).
- **기존 예제와 중복되지 않는가** : 새 테이블·용어 이름이라 기존 예제와 겹치지 않는다. `not exists` 가 다시 실행하거나 이미 있는 경우를 막는다.
- **운영 데이터와 충돌할 가능성 (낮음, 후속 확인)**
  - 컬럼 INSERT 는 프로젝트 0 의 테이블 이름으로 대상을 찾는다.
  - 사용자가 V2 이전에 프로젝트 0 에 같은 이름의 테이블(`TB_PRJ_SRC_CNTN` 등)을 직접 만들었다면, 테이블 INSERT 는 건너뛴다. 하지만 컬럼은 그 테이블에 더해질 수 있다.
  - 스키마 단위 이름이라 여러 스키마에 같은 이름이 있으면 각각에 더해질 수 있다.
  - 예제 행은 SQL 로 들어가므로 모델 변경 이력(`ModelChangeRecorder`)에 남지 않고, 그 전에 만든 모델 버전에도 없다. 예제 프로젝트에서 버전을 비교하면 "추가" 로 보인다.
- **V2 는 이미 적용되어 수정 금지다** (개발 DB 에 적용됨).
- **실제 데이터 영향 검증 필요** : V2 를 적용한 DB 에서 프로젝트 0 에 같은 이름의 TABLE 이 V2 이전부터 있었는지, 그 TABLE 에 예제 컬럼이 더해졌는지 조회로 확인한다. 개발 DB 의 경우는 V2 이전에 그런 TABLE 이 없었을 것으로 보이지만 확인하지 않았다.
- **문제가 확인되면** V3 이후의 보정 마이그레이션을 검토한다. 데이터 삭제나 DB 초기화로 해결하지 않는다.
- **결정 필요 (후속)**
  - 예제 데이터를 스키마 마이그레이션과 분리할지 정한다. 예 : 예제 전용 마이그레이션, 또는 애플리케이션이 예제 프로젝트를 만들 때 넣기.
  - 정하기 전까지는 지금 규칙(같은 마이그레이션)을 유지한다.

### 12.4 대규모 매핑 성능

- **측정함 (2026-11-14, M-4d 와 함께, [M-4d 기록 9장](source-compare-m4d.md#9-성능-sourcecompareperformancetest-lexorma_perftrue))** : PostgreSQL 18.6, TABLE 마다 컬럼 10개. 매핑 현황 14 / 34 / 90 ms, TABLE 목록(50건) 12 / 32 / 92 ms (300 / 1,000 / 3,000 TABLE), SQL 문 9~12개(TABLE 수와 무관), 요청당 할당 약 10 / 34 / 101 MB. 기준 연결 전환과 모델 TABLE 고르기는 따로 재지 않았다.
- **이전 상태** : 수천 개 원본 TABLE 에서 현황 조회, 상태 계산, 후보 조회, 검색·필터·페이징, 기준 연결 전환의 응답 시간과 메모리를 재지 않았다.
- **지금 구조**
  - TABLE 목록은 요청마다 그 연결의 마지막 반영 스냅샷과 매핑 전체로 상태를 계산한 뒤 쪽으로 나눈다 (최대 500).
  - 모델 TABLE 고르기는 200개까지다.
- **후속** : 상태 계산이 매 요청 모든 테이블 버전 JSON 을 읽는다(할당량의 대부분). 개선은 M-4d 의 할당량 개선과 함께 검토한다. 성능 개선은 구현하지 않았다.

## 13. 매핑 예외 (M-4g, 2026-11-14)

원본 DB 에는 모델로 관리할 필요가 없는 시스템성 테이블(`flyway_schema_history`, Liquibase `databasechangelog`, Spring Batch `BATCH_*`, Quartz `QRTZ_*`, `SPRING_SESSION` 등)이 있다. 이런 TABLE 을 매핑 화면에서 **예외**로 표시해 매핑 누락으로 보지 않는다. 원본 수집 정책이 아니라 매핑 정책이다.

- **상태 전환** : 미매핑 → [예외 처리] → 예외 → [예외 취소] → 미매핑. 매핑된 TABLE 은 먼저 해제해야 예외로 만들 수 있고, 예외 TABLE 은 매핑할 수 없다. 자동 예외·추천·일괄 처리는 없다.
- **저장 (V5 `V5__source_mapping_exclusion.sql`)** : `TB_SRC_TBL_MPNG.MPNG_EXCL_YN`(매핑 예외 여부, 기본 false). 예외 = 모델 테이블 없이(`TBL_SN` null) 남긴 매핑 행이다. 원본 TABLE 당 행이 하나뿐이라(`UX_SRC_TBL_MPNG_01`) 같은 원본이 매핑이면서 예외일 수 없다. 기존 행은 매핑(false) 그대로다. 예제(단어 `예외`/EXCL, 용어 `매핑_예외_여부`, 물리 컬럼·논리 속성·매핑)를 같은 마이그레이션에 넣었다.
- **식별** : 매핑과 같은 원본 TABLE 행 ID 에 붙는다. 스키마가 다르면 다른 행이라 같은 이름이어도 섞이지 않는다.
- **사용자 결정 (2026-11-14)**
  - 원본에서 사라지면 예외를 지우지 않고 "매핑 예외 · 마지막 수집에서 원본이 사라졌습니다" 로 남긴다 (사용자가 예외 취소로 정리). 스키마가 통째로 사라지고 스키마 매핑도 없으면 저장한 비교 경로의 스키마 이름으로 보인다.
  - 같은 이름으로 다시 생기면(생성 차수 변경) 예외를 유지하고 재생성 안내만 보인다 (매핑의 재확인과 다르다).
  - 스키마 매핑과 무관하다 : 스키마가 매핑되지 않은 TABLE 도 예외로 둘 수 있고, 스키마 매핑을 해제해도 예외는 남는다 (TABLE 매핑만 함께 해제).
  - 기준 연결을 바꾸면 매핑처럼 그 연결에 남고, 연결을 지우면 매핑과 함께 지워진다.
- **API** : `PUT /api/sourceMapping/exclusions` (`{sourceTableId}`) · `DELETE /api/sourceMapping/exclusions/{mappingId}`. 권한·잠금(프로젝트 → 원본 연결 공유 → 기준 연결 행 배타)·오류(`SOURCE_MAPPING_INVALID`, 동시 저장 `SOURCE_MAPPING_CONFLICT`)는 TABLE 매핑과 같다. 기존 `DELETE /tables/{mappingId}`(매핑 해제)는 예외 행을 지우지 않는다.
- **상태 `EXCLUDED`** : 매핑 화면의 상태별 건수에 따로 보이고 미매핑(누락) 건수에서 빠진다. 원본 TABLE 총수에는 들어간다. "다른 연결에 남은 매핑" 수에는 세지 않는다.
- **다른 기능**
  - 원본 수집·최신화·원본 카탈로그·원본 변경 이력 : 그대로 (예외 TABLE 도 수집한다).
  - M-4d 비교 : 비교 목록에서 빠지고 요약에 `excludedTables` 건수만 보인다. 예외 TABLE 을 참조하는 FK 는 미매핑 대상과 같이 판단 불가다.
  - M-4e·M-4f 가져오기 : 대상이 아니다 (`EXCLUDED` 로 거절, 비교 목록에 없어 고를 수도 없다).
- **화면** : TABLE 매핑 표에서 미매핑 행에 [예외 처리], 예외 행에 [예외 취소]. 상태 "매핑 예외", 원본 없음이면 원본 링크 대신 이름만 보인다. 원본 매핑 관리 화면 안에서만 다루고 새 메뉴는 없다.
- **검증** : `SourceMappingIntegrationTest.exclusions`·`concurrentExcludeAndMap` (H2·PostgreSQL), `SourceMappingServiceTest`, `V0SeedMigrationTest`·`LexormaIndexSeedTest`(마이그레이션 6개).

## 14. COMMENT 표시 (2026-11-14)

- TABLE 매핑 표는 COMMENT 를 출처별로 따로 보인다 (`SourceMappingDto.TableRow`) : 원본 COMMENT `sourceComment`(수집값, "원본 COMMENT : …"), 모델 업무 설명 `tableDescription`("모델 설명 : …"), 모델의 원본 COMMENT 칸 `tableSourceComment`("모델 원본 COMMENT 칸 : …", 가져온 값). 한쪽으로 다른 쪽을 채우지 않고 값이 없으면 줄을 보이지 않는다. 한글명(논리명)은 이름 아래에 그대로 보이며 COMMENT 로 쓰지 않는다. 미매핑·예외 행에는 모델 값이 없다.
- 컬럼 단위 COMMENT 는 원본·모델 비교 화면의 TABLE 상세(속성 "COMMENT ↔ 모델 설명", TABLE 은 "COMMENT ↔ 모델 테이블 코멘트", "원본 COMMENT 칸")에서 본다. 비교 기준은 [source-compare-m4d.md](source-compare-m4d.md) 4.2.
- 최신화는 원본 COMMENT 만 바꾸고 모델 값은 보존한다 (`SourceMappingIntegrationTest.commentsAreSeparate`).
- [선택] 버튼의 영어는 문맥 키 `tc('버튼', '선택')` → "Select" (같은 한국어 `선택` 이 관계 참여·VIEW 입력칸에서는 "optional" 이다).
