# 프로젝트 삭제 정합성 (2026-11-12)

M-9 최종 검증에서 확인된 문제 — 프로젝트를 지워도 프로젝트 행과 멤버 행만 지워지고 나머지 데이터가 DB 에 남는다 — 를 고친 기록이다. M-9 이후의 공통 데이터 생명주기 보완이며 M-9 의 상태는 바뀌지 않는다.

## 1. 정책

| | 비활성화 | 영구 삭제 |
|---|---|---|
| 데이터 | 전부 남는다 | 프로젝트에 딸린 데이터를 전부 지운다 |
| 되돌리기 | 다시 활성화 (활성 프로젝트가 없으면 복구 로그인) | 없다 |
| 접근 | 로그인·조회 불가, 관리 화면에서 수정만 | 프로젝트 자체가 없다 |

삭제할 수 있는 조건은 그대로다 : 프로젝트 관리자 본인, 관리자 외 멤버가 없을 때, 기본 프로젝트(ID 0)는 불가. 백업·내보내기·복원은 만들지 않았다.

## 2. 지우는 범위

테이블 40개(세션 2개 제외)를 모두 분류했다. `PRJ_SN` 이 없는 하위 테이블도 부모를 따라 지운다.

| 모듈 | 지우는 테이블 (실행 순서) |
|---|---|
| `lexorma-data` (`ProjectDataCleanup`) | 매핑 `TB_ATRB_COL_MPNG` → `TB_ENTT_TBL_MPNG` / 논리 모델 `TB_LGCL_ERD_LYT`, `TB_LGCL_REL` → `TB_LGCL_IDNTFR_ATRB` → `TB_LGCL_IDNTFR` → `TB_LGCL_ATRB` → `TB_LGCL_ENTT` → `TB_LGCL_MDL` / 물리 모델 `TB_TBL_REL_COL` → `TB_TBL_REL`, `TB_TBL_IDX_COL` → `TB_TBL_IDX`, `TB_TBL_CNSTRT_COL` → `TB_TBL_CNSTRT`, `TB_ERD_LYT`, `TB_COL` → `TB_TBL` → `TB_SCHM` / 데이터 사전 `TB_CMN_COL`, `TB_STD_TRM_WORD`, `TB_STD_TRM_SYNM` → `TB_STD_TRM`, `TB_STD_WORD_SYNM`, `TB_STD_WORD_PRHBT` → `TB_STD_WORD` → `TB_STD_DMN` / `TB_MDL_CHG_HSTRY`, `TB_MDL_VER` |
| `lexorma-operation` (`NoticeProjectCleanup`) | `TB_PST_ACNT`, `TB_ATCH_FILE` → `TB_PST`. 다른 프로젝트 공지의 대상 목록(`PRJ_SN_LIST`)에서 지워진 프로젝트 ID 를 뺀다 |
| `lexorma-core` (`LogsServiceImpl`) | `TB_LOG` |
| `lexorma-system` (삭제 서비스) | `TB_PRJ_MBR` → `TB_PRJ` |

**지우지 않는 것 (공통 데이터)** : 계정 `TB_ACNT`, 역할 `TB_ROLE`·`TB_ACNT_ROLE`, 게시물 범주 `TB_PST_CTGRY`, 세션 테이블. 다른 프로젝트의 데이터.

판단이 갈릴 수 있었던 두 가지 :
- **요청 로그(`TB_LOG`)** : 지운다. 로그는 프로젝트 안에서만 조회되는 데이터라 남겨도 볼 방법이 없다. 삭제 요청 자체의 로그는 요청한 사람이 로그인해 있던 프로젝트에 남는다(자기 프로젝트를 지운 경우는 남지 않는다).
- **여러 프로젝트에 함께 등록한 공지** : 프로젝트마다 행이 따로 있으므로 지워진 프로젝트의 행만 지우고 다른 프로젝트의 공지는 둔다.

## 3. 처리 방식

- **기존 이벤트를 쓴다.** 삭제 서비스는 프로젝트 행을 지우기 전에 `ProjectDeletedEvent` 를 발행하고, 각 모듈의 `@EventListener` 가 자기 데이터를 지운다. `system` 이 `data`·`operation` 을 참조하지 않아도 되어 모듈 의존 방향(`common ← core ← system/operation/data ← app`)이 그대로다.
- **한 트랜잭션이다.** `@EventListener` 는 발행한 스레드에서 바로 실행되므로 삭제 서비스의 트랜잭션 안에서 돈다. 리스너의 예외는 그대로 올라가 전체가 롤백되고, 뒤 단계가 실패하면 리스너가 지운 것도 되돌아간다. `@TransactionalEventListener`(커밋 뒤 실행)나 비동기 실행은 "프로젝트만 지워지고 데이터가 남는" 상태를 만들 수 있어 쓰지 않는다.
- **SQL 로 지운다.** 행이 많을 수 있어 엔티티를 읽지 않는다. 그래서 삭제는 모델 변경 이력에 남지 않는다(이력도 지운다). 순서는 FK 를 따르고, `ON DELETE CASCADE` 는 더하지 않았다. DB 스키마 변경은 없다.

## 4. 동시성

- **같은 프로젝트의 삭제가 겹칠 때** : 삭제는 먼저 프로젝트 행을 배타 잠금으로 읽는다. 뒤에 온 요청은 기다렸다가 "삭제할 수 없음" 으로 끝난다.
- **삭제와 등록이 겹칠 때** : 프로젝트 데이터 테이블은 프로젝트로 FK 를 걸지 않아, 삭제가 끝나기 직전에 다른 트랜잭션이 넣은 행이 남을 수 있었다. `ProjectWriteGuard`(core) 가 막는다 — 프로젝트 ID 를 가진 엔티티를 저장한 트랜잭션은 커밋 직전에 그 프로젝트 행을 공유 잠금으로 읽고, 없으면 `PROJECT_NOT_FOUND` 로 롤백한다.
  - 삭제가 먼저 잠갔으면 : 등록은 삭제가 끝날 때까지 기다렸다가 실패한다.
  - 등록이 먼저 커밋하면 : 삭제는 그 뒤에 시작하므로 방금 넣은 행까지 지운다.
  - 부모가 있는 등록(테이블 → 스키마, 컬럼 → 테이블 등)은 FK 로도 막힌다. 이 경우 삭제 쪽이 실패해 롤백될 수 있고, 다시 시도하면 된다.
- 잠금은 커밋 직전에만 잡아 평소의 쓰기끼리 서로 기다리지 않는다. 트랜잭션마다 프로젝트당 조회 1번이 늘어난다.
- 한계 : JPA 로 저장하는 경로만 해당한다. 네이티브·JDBC 로 직접 넣는 코드는 지금 없지만, 만들면 이 보호를 받지 못한다.

## 5. 삭제 뒤

- 지워진 프로젝트로는 로그인할 수 없다(`PROJECT_ACCESS_DENIED`).
- 그 프로젝트에 로그인해 있던 세션은 다음 요청에서 끊긴다(`ProjectAccessInterceptor`, 401 `PROJECT_ACCESS_REVOKED`). 자기가 로그인한 프로젝트를 지운 경우도 같다.
- 다른 프로젝트에서 지워진 프로젝트의 버전·이력 ID 를 넣어도 "없음" 이다 — 데이터가 실제로 없다.

## 6. 화면

프로젝트 관리의 [삭제] 가 확인 한 번에서 **프로젝트명 입력**으로 바뀌었다 : 지워지는 범위와 "남기려면 비활성화" 안내, 프로젝트명을 그대로(대소문자까지) 입력해야 [영구 삭제] 가 눌린다. 진행 중에는 다시 보내지 않는다. 입력은 실수를 줄이는 장치일 뿐이고 권한·조건은 서버가 다시 확인한다.

## 7. 모델 버전 오류 메시지

버전을 찾지 못하면 관계·인덱스 오류 문구("관계·인덱스·제약조건 정의가 올바르지 않습니다. [대상을 찾을 수 없습니다.]")가 나왔다. 물리 모델의 오류 코드를 빌려 쓴 탓이다.

| 경우 | 전 | 후 |
|---|---|---|
| 없는 버전, 다른 프로젝트의 버전 (상세·내용·비교) | 400 `INVALID_PHYSICAL_MODEL` | 404 `MODEL_VERSION_NOT_FOUND` "모델 버전을 찾을 수 없습니다." / "Model version not found." |
| 버전명·설명 검증, 같은 버전끼리 비교 | 400 `INVALID_PHYSICAL_MODEL` | 400 `INVALID_MODEL_VERSION` "모델 버전 요청이 올바르지 않습니다. [사유]" |
| 숫자가 아닌 ID | 400 | 400 (그대로) |

다른 프로젝트의 버전도 "없는 버전" 과 똑같이 답하므로 격리는 그대로다. 관계·인덱스·제약조건의 오류는 바뀌지 않았다. 모델 변경 이력 조회는 같은 방식(`INVALID_PHYSICAL_MODEL`)을 아직 쓴다 — 범위 밖이라 두었다.

## 8. 테스트

- `ProjectDeletionIntegrationTest` (H2·PostgreSQL) 3건
  1. 모든 테이블에 행이 있는 프로젝트를 지운 뒤 `PRJ_SN` 이 있는 22개 테이블에 그 프로젝트의 행이 0건이고, **모든 `TB_` 테이블의 전체 행 수가 그 프로젝트를 만들기 전과 같다**(하위 테이블과 다른 프로젝트·공통 데이터까지 한 번에 본다). 비활성화는 아무것도 지우지 않는다. 지워진 프로젝트로는 버전·논리 모델·단어가 저장되지 않는다.
  2. 삭제 조건(관리자 아님, 멤버 있음, 기본 프로젝트)과 **중간 실패 시 전체 롤백**(FK 로 테이블 삭제 단계를 막아 확인).
  3. 동시 삭제 4건 중 1건만 성공, 삭제와 겹친 등록은 `PROJECT_NOT_FOUND` 로 실패하고 남는 행이 없다.
- 스스로 지키는 장치 : `PRJ_SN` 컬럼이 있는 테이블 목록이 실제 스키마와 다르거나, 준비 데이터가 없는 테이블이 있으면 실패한다 → 프로젝트 데이터 테이블을 더하면 삭제 처리와 테스트를 함께 고치게 된다.
- 전체 : H2 410건(실패 0, 건너뜀 2), PostgreSQL 18.6 410건(실패 0, 건너뜀 1). 기존 407건에서 3건 늘었다.
- 브라우저(헤드리스 Chrome, PostgreSQL) : 확인 대화상자(이름이 다르면 버튼 비활성, 연속 클릭에도 요청 1번), 다른 프로젝트 삭제 뒤 목록 갱신, 로그인한 프로젝트 삭제 뒤 세션 차단, 삭제 뒤 DB 잔여 0행, 버전 오류 문구.

## 9. 남은 것

- 삭제 전 내보내기(백업)는 없다. 필요하면 별도 과제다.
- 프로젝트 데이터 테이블에 프로젝트 FK 를 거는 방법은 쓰지 않았다(스키마·예제 데이터 변경이 크다). DB 수준의 보장이 필요해지면 그때 검토한다.
- 큰 프로젝트(컬럼 수만 개)의 삭제 시간은 재지 않았다.
