# M-4f — 원본 메타데이터 선택적 재가져오기

> 상태 : **구현 (2026-11-14)**. 선행 : [M-4c 매핑](source-mapping-m4c.md), [M-4d 비교](source-compare-m4d.md), [M-4e 가져오기](source-import-m4e.md). 정책 : [m4-foundation.md 5.14](m4-foundation.md).
> 신규 테이블·마이그레이션·API 없음. M-4e 의 `candidates → plan → apply` 를 그대로 쓰고, 응답에 판정 정보를 더했다.

## 1. 목적

한 번 모델에 가져온 원본 메타데이터가 바뀐 뒤(다시 수집한 뒤), **원본만 바뀐 속성은 골라서 다시 반영**하고, **가져온 뒤 모델에서 바꾼 속성은 덮어쓰지 않는다**. 원본 상태를 모델에 통째로 덮어쓰는 기능은 만들지 않는다.

## 2. M-4e 와의 차이

| 구분 | M-4e (그대로) | M-4f 에서 더한 것 |
|---|---|---|
| 흐름 | 대상 → 미리보기(계획, planToken) → 최종 확인 → 확정(잠금 후 재계획) | 같다. 재가져오기 전용 엔진·API·메뉴 없음 |
| 비교 | 지금 원본(S) ↔ 지금 모델(M), 속성 단위 | + 마지막으로 가져온 값(B) 으로 **3자 판정** |
| 고를 수 있는 것 | 차이가 있고 막는 이유가 없는 속성 | 그중 **모델에서 바꾼 속성·둘 다 바뀐 속성은 제외** |
| 이미 같은 값 | (비교가 같으면 항목 없음) | 비교는 다르다지만 반영해도 그대로인 속성은 `SAME` (빈 변경 방지) |
| 원본에서 없어진 객체 | 모델에만 있는 객체 — 표시 안 함 | 전에 가져온 객체면 **원본에서 삭제됨** 알림 (지우지 않는다) |
| 화면 | 가져오기 패널 | 처음/재가져오기 표시, 마지막 가져오기·현재 수집, "마지막 가져온 값" 열, 판정 라벨, 확인이 필요한 변경·원본에서 삭제됨 영역, 확인 대화상자 보강 |

M-4e 만으로 이미 되던 것 : 재수집 뒤 비교·계획·확정, 기존 TABLE 속성(타입·NULL·DEFAULT·원본 COMMENT)·TABLE COMMENT 재반영, 새 컬럼·PK·UNIQUE·CHECK·FK·인덱스 추가, 교체가 필요한 변경 표시(`REPLACE_REQUIRED`), 승인 객체 보호, 미지원 원본 속성 차단, 재전송 방지, 직전 모델 버전·IMPORT 이력·실행 이력.

## 3. 원본 객체 식별

- M-4c 에서 확정한 **원본 스키마·TABLE 매핑**만 쓴다. 이름이 같다고 같은 객체로 보지 않는다.
- 원본 TABLE 은 안정 식별자(`TB_SRC_TBL` 일련번호) + **생성 차수**로 식별한다. 같은 이름으로 다시 생기면 차수가 늘고 매핑은 `RECHECK` (가져오기 불가, 매핑 관리에서 재확인). 이름 변경 = 삭제 + 새로 생김 (이름 변경 후보는 제안만).
- 기준 연결이 바뀌거나 매핑이 풀리거나 모델 TABLE 이 지워지면 가져오기 불가 이유를 보여 준다. 새 매핑을 자동 확정하지 않는다.

## 4. 마지막 반영 기준값(B) — 기존 데이터만으로 만든다

**결론 : 신뢰할 수 있게 복원된다 (새 저장 구조 불필요).** 근거 :

- 실행 이력(`TB_SRC_IMPRT_EXCN.IMPRT_CN`)에 TABLE(`S<원본 TABLE ID>`)마다 고른 항목 ID 가 남는다.
- 같은 트랜잭션의 모델 변경 이력(`TB_MDL_CHG_HSTRY`, 변경 그룹 = 요청 식별자, 출처 IMPORT)은 기록 대상 필드의 **변경 후 전체 상태**를 남긴다.
- 그래서 B = "그 속성을 덮는 항목을 고른 가장 최근 실행"이 "이 모델 객체 ID"에 남긴 변경 후 상태의 해당 필드.

| 속성 | 덮는 항목 | B 의 필드 (변경 이력 상태) |
|---|---|---|
| TABLE 원본 COMMENT | `TABLE:COMMENT` | 테이블의 `sourceComment` |
| 컬럼 타입 | `COLUMN:c:TYPE`, `COLUMN:c:ADD` | `dataType`·`maxLength`·`precision`·`scale` (모델 DDL 타입 표현으로 비교) |
| 컬럼 NULL | `COLUMN:c:NULLABLE`, `COLUMN:c:ADD` | `isNullable`·`isPk`·`isRequired` (DDL 과 같은 실제 NULL 허용) |
| 컬럼 DEFAULT | `COLUMN:c:DEFAULT`, `COLUMN:c:ADD` | `defaultValue` |
| 컬럼 원본 COMMENT | `COLUMN:c:COMMENT` | `sourceComment` |

B 가 **없다**고 보는 경우 (안전하다고 표시하지 않는다) : 가져온 적 없음(직접 만든 모델), 다른 기준 연결의 실행만 있음, 다시 매핑해 모델 객체 ID 가 다름(그 ID 의 이력이 없음), 덮는 항목을 골랐지만 실제로 값이 바뀌지 않아 이력이 없음.

같은 모델 객체에 대한 기준값이므로 원본 생성 차수와는 무관하다 : 재생성 후 사용자가 같은 모델 TABLE 로 매핑을 다시 확정했다면, 모델에 쓴 값(B)은 그대로 의미가 있다.

## 5. 판정 (속성 단위, `SourceImportDto.Judgement`)

값은 모두 모델 표현이다 (S 는 M-4e 와 같은 변환으로 바꾼 값).

| 판정 | 조건 | 처리 |
|---|---|---|
| `SOURCE_CHANGED` 원본 변경 | B ≠ S, M = B | 고를 수 있다 |
| (항목 없음) 변경 없음 | S = M | 비교에서 같음 → 항목이 없거나 `SAME` |
| `MODEL_EDITED` 모델 수정됨 | B = S, M ≠ B | 고를 수 없다 (`Reason.MODEL_EDITED`) — 모델 값을 되돌리지 않는다 |
| `BOTH_CHANGED` 양쪽 변경 충돌 | B ≠ S, M ≠ B, M ≠ S | 고를 수 없다 (`Reason.BOTH_CHANGED`) — 자동 해결 없음 |
| `NO_BASELINE` 기준값 없음 | B 를 확인할 수 없음 (또는 셋이 같은데 비교가 다르다고 봄) | 안전하다고 표시하지 않는다. 미승인 객체는 M-4e 처럼 **명시적으로 고를 때만** 반영. 한 번 반영하면 그 뒤부터는 B 로 판정 |

- 다른 이유(승인 `APPROVED`, 판단 불가 `UNKNOWN`, 표현 불가 등)가 있으면 그 이유가 앞선다. 판정은 표시용으로 남는다.
- 추가(`ADD`·`CREATE`)·제약조건·인덱스 항목은 판정 대상이 아니다 (`judgement = null`).
- 판정·기준값은 planToken 에 들어간다 : 미리보기와 확정 사이에 다른 가져오기가 반영되어 기준값이 바뀌면 409.

## 6. 지원 범위

- TABLE : 원본 COMMENT (이름 변경 제외).
- 컬럼 : 타입(길이·정밀도·소수 포함)·NULL 허용·DEFAULT·원본 COMMENT. 속성마다 따로 고른다. 고르지 않은 속성은 바뀌지 않는다.
- 새 컬럼·PK·UNIQUE·CHECK·FK·인덱스 : M-4e 그대로.
- 기존 제약조건·인덱스의 구성 변경(예 : UNIQUE (A,B) → (A,B,C)) : `REPLACE_REQUIRED` 로 표시만 (삭제 후 재생성 없음).
- 원본 삭제 : TABLE·컬럼·제약조건·인덱스·FK 를 모델에서 지우지 않는다. 전에 가져온 컬럼·UNIQUE·CHECK·인덱스·FK 가 원본에 없으면 `REMOVED_IN_SOURCE` 항목(고를 수 없음)으로 알린다. TABLE 이 없어지면 TABLE 단위 `SOURCE_REMOVED` (M-4c).
- 미지원 원본 속성 (IDENTITY·생성 컬럼·표현 못 하는 DEFAULT·NO ACTION 이 아닌 FK 규칙·지원 안 하는 인덱스 유형) : M-4e 정책 그대로. 기존 컬럼의 독립 속성(원본 COMMENT 등)만 반영할 수 있고, IDENTITY 를 반영했다고 표시하지 않는다.

## 7. 승인

M-4e 와 같다 : 승인된 TABLE·컬럼의 속성(원본 COMMENT 포함)은 바꾸지 않는다 (`APPROVED`, 승인 취소 후 다시). 승인을 자동으로 풀지 않고, 우회 API 도 없다. 만든 객체는 미승인.

## 8. plan / apply 계약 (M-4e 와 공통)

- `GET /api/sourceImport/candidates` 응답(`TableCandidates`)에 `reflectedAt`(지금 기준 수집 시각), `lastImport`(같은 기준 연결로 이 TABLE 을 마지막으로 가져온 실행 : 실행 ID·반영 순서·실행자·시각·직전 버전 이름)를 더했다. `lastImport` 가 있으면 재가져오기.
- 항목(`Item`)에 `baseline`(B 의 표시 값)·`judgement` 를 더했다. 필드를 덧붙이기만 했으므로 기존 클라이언트와 호환된다.
- `plan`·`apply`·이력 API 는 그대로다. 확정은 잠금 뒤 다시 계획해 planToken 이 같을 때만 반영하고, 아니면 `409 SOURCE_COMPARE_STALE`. 고른 항목이 모두 적용 가능해야 하고(아니면 400), 이미 반영된 항목은 비교에 없거나 `SAME` 이라 실제 변경 없는 확정은 생기지 않는다 (버전·이력도 만들지 않는다).
- 권한 : 비교·대상·미리보기·이력 VIEWER 이상, 확정은 프로젝트 관리자·ADMIN(USER 역할 이상), 서버에서 다시 검사.

## 9. 모델 버전·이력

M-4e 그대로 : 확정마다 반영 직전에 프로젝트 전체 모델 버전 `IMPORT-<요청>` (같은 트랜잭션), 모델 변경 이력은 출처 IMPORT·변경 그룹 = 요청 식별자, 실행 이력에 요약·버전 ID. 이 실행 이력과 IMPORT 이력이 다음 재가져오기의 기준값이 된다.

## 10. 동시성

M-4e·T-07·T-09 정책 그대로 : 확정은 프로젝트 배타 → 원본 연결 공유 → 기준 연결 행 → 스키마 이름 공간 → TABLE → 컬럼, 프로젝트 이후 행 잠금은 NOWAIT (PostgreSQL 55P03·H2 50200 만 409, 교착은 그대로 오류), 한 트랜잭션·전체 롤백. 기준값은 확정 안의 재계획에서 다시 읽으므로 잠금 아래의 상태로 판정한다. 사용자 버전 만들기는 READ COMMITTED + 프로젝트 배타 잠금.

재가져오기는 M-4e 와 같은 `apply` 경로라 기존 PostgreSQL 동시성 테스트가 그대로 회귀 검증이다 : 일반 모델 저장(T-07)·승인 변경(T-08)·같은 계획 동시 확정·서로 다른 두 가져오기 동시·다른 프로젝트(T-06)·연결 삭제 양방향·사용자 버전 만들기(T-09)·매핑/기준 연결 변경(409).

- 같은 실행의 M-4e 확정(`snapshotScales`, 기준값 조회 포함) 3,000 TABLE 744 ms·537.9 MB, 참고값 851 ms·537 MB : 회귀 없음. 기준값 조회는 실행 이력 1문장 + 변경 이력 1문장(계획마다)이라 확정당 SQL 이 3문장 늘었다.
- 3,000 TABLE 비교 조회의 최대 3,003 ms 는 1회 튐(중앙 673 ms). M-4d 코드는 바꾸지 않았다.
- 측정 코드는 테스트에만 있다 (`LEXORMA_PERF=true`).

## 12. 미지원·후속

- **원본 삭제 동기화** : 원본에서 없어진 객체를 모델에서 지우는 기능은 없다 (정책 결정 필요).
- **교체가 필요한 변경** : 기존 제약조건·인덱스의 구성·식 변경은 표시만 한다 (삭제 후 재생성 정책 필요).
- **기준값 없음의 범위** : M-4f 이전에 모델에 손으로 맞춘 속성, 다른 기준 연결로 가져온 속성은 B 가 없다. 다시 한 번 명시적으로 반영하면 그 뒤부터 판정한다.
- **PK·FK 규칙의 기준값** : PK 추가로 NOT NULL 이 된 컬럼처럼 다른 항목이 바꾼 속성은 그 속성 항목의 기준값이 아니다 (덮는 항목만 본다).
- **TABLE 이름 변경·VIEW 가져오기·다른 DBMS 규칙** : 범위 밖.
- **M-4c 매핑 상태 이중 계산** 최적화 : 범위 밖 (확정에 남은 비용의 대부분).
- **3,000 TABLE 비교 조회 지연 분석** : 측정에서 1회 3,003 ms 로 튐 (중앙 673 ms). 원인 미분석 (M-4d 비교, 이번에 바꾸지 않음).
- **재가져오기 전용 테스트 보강** : 동시성은 M-4e 와 같은 확정 경로라 기존 PostgreSQL 테스트로 회귀 검증했고 재가져오기 전용 동시성 테스트는 없다. 기준 연결을 바꾼 뒤·다른 모델 TABLE 로 다시 매핑한 뒤 기준값을 쓰지 않는 것은 코드(같은 기준 연결의 실행만 읽고, 모델 객체 ID 로 이력을 찾는다)로 보장하지만 전용 테스트는 없다.
