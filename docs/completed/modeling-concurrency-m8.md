## 4. 핵심 시나리오 판정

- **A 같은 엔터티 수정** : B 는 409 `MODEL_CONFLICT`, 아무것도 바뀌지 않는다 (모델 행 잠금 → 다시 읽기 → 기준값 비교). 저장은 객체 전체(이름+설명)지만 기준값이 지킨다. A 의 변경은 사라지지 않는다 — **안전 (P3)**. 남은 것 : B 가 409 뒤 다시 시도할 수 없다(U-01).
- **B 컬럼 일괄 수정** : 목록 전체 교체가 아니어서 A 가 더한 컬럼은 **지워지지 않는다**. B 가 기존 행 값을 고친 경우 A 의 추가는 기존 행 `MDFCN_DT` 를 바꾸지 않아 B 저장은 성공한다(정상). 남은 것 : 순서 번호 겹침(P-05), 다른 컬럼의 사소한 변경에도 전체 409(U-02). 같은 이름을 더하면 B 행 오류.
- **C ERD 배치** : 배치는 **사용자별** 행이라 다른 사용자끼리는 충돌하지 않는다. 같은 사용자의 두 탭은 `version`·`@Version` 으로 409, 저장은 요청 노드를 저장된 노드에 병합(다른 노드 보존). 남은 것 : 화면 복구(U-03).
- **D 논리 → 물리 생성** : planToken 이 엔터티·속성·용어 `modifiedAt`, 제외 속성, 컬럼 계획 전체 문자열(도메인 유래 타입 포함), UNIQUE·관계 계획, 기존 부모 테이블·PK·컬럼·FK `modifiedAt`, 서브타입 그룹, 변환 기록을 담는다. apply 는 프로젝트 배타 → 모델·스키마 NOWAIT → 다시 계획(다르면 409) → 참조 테이블 NOWAIT → `GENERATE-` 버전 → 생성, 한 트랜잭션 — **안전 (P3)**. 빈틈은 이력 대상이 아닌 도메인·단어가 apply 와 동시에 커밋되는 경우뿐이고 순차 실행과 같다(K-02).
- **E 물리명 일괄 적용** : 프로젝트 배타 → 모델·스키마·테이블·컬럼 키 잠금 NOWAIT → 다시 계획·토큰 → 항목별 기준값 → 막힘 있으면 400 → 버전 → 적용, 한 트랜잭션. 다른 테이블의 동시 수정은 NOWAIT 대상이 아니면 막지 않는다 — **안전 (P3)**.
- **F 삭제 ↔ 수정** : 삭제 뒤의 수정은 대상 없음 400 (`LOGICAL_MODEL_IS_NOT_DEFINED`·`TABLE_IS_NOT_DEFINED` 등)이고 id 가 있는 요청은 등록 분기로 가지 않아 **다시 만들어지지 않는다**. 단 일부 경로는 500 (U-05). 수정 뒤의 삭제는 기준값이 없어 새 내용을 지운다(X-01, 정책). 연결된 관계·매핑은 삭제 쪽 의존 검사(관계 사용 중·매핑 있음 → `RELATION_EXISTS`)와 DB FK 가 지킨다.

## 9. 사용자 결정이 필요한 사항

1. **삭제의 충돌 정책** : (a) 지금처럼 "삭제가 이긴다" (b) 삭제도 기준값 필수 → 409 (c) 확인 대화상자에서 "그 사이 바뀜" 경고만. 엔터티 삭제가 그 사이 더해진 속성·식별자까지 지우는 것을 막을지.
2. **승인·승인 취소의 기준값** : 표준 용어처럼 "본 내용만 승인"(기준값 필수, 오래되면 409)으로 넓힐지, 잠금만 넣고 기준값은 두지 않을지.
3. **승인된 표준 도메인 수정** : 지금은 승인 검사 없이 USER 가 수정할 수 있다 (용어·테이블·컬럼은 승인되면 수정 불가). 같은 규칙으로 막을지 — 동시성 밖의 정책이지만 D-01 수정과 같이 정해야 한다.
4. **컬럼 일괄 편집기 기준값 범위** : 기존 행 전부(지금, 엄격) vs 고친 행·지운 행만(다른 컬럼의 사소한 변경으로 409 가 나지 않음).
5. **409 뒤 화면 동작** : 최신을 다시 읽어 사용자의 입력을 위에 다시 적용(필드 단위 병합, 충돌 필드 표시) vs 다시 읽기만(입력은 복사할 수 있게 보존).
6. **같은 두 엔터티 사이 관계의 중복** : 중복 제출만 막을지, (모델, 원본, 대상, 이름) 중복을 서버에서 거절할지 (거절이면 기존 데이터 확인 필요 — DB UNIQUE 는 기존 중복이 있으면 마이그레이션이 실패할 수 있어 잠금 뒤 검사 권장).
7. **M8-C1~C4 순서·범위** 승인.

## 10. 검증 계획 (구현 단계용)

- **실제 동시성** : 두 DB 연결·두 스레드(`CountDownLatch`/`CyclicBarrier`) 또는 두 HTTP 세션(두 계정)으로 같은 대상을 동시에 — 순차 호출은 동시성 테스트로 세지 않는다. 기존 `ModelVersionConcurrencyIntegrationTest`·`RelationSyncDeadlockIntegrationTest` 의 틀을 재사용.
- **재현 먼저** : L-01(승인 T1 읽기 → T2 관계 수정 커밋 → T1 커밋 뒤 관계 값 = T2 인지), D-01·D-02(도메인·단어 동일), P-01(순서), P-02(스키마 이름 변경 ↔ 참조 컬럼 일괄 저장) 를 수정 전 코드로 실패시켜 기록.
- 같은 대상 / 다른 대상(서로 막지 않는지) / 수정 ↔ 삭제 / 일괄 저장 경합 / ERD 배치(같은 사용자 두 탭, 다른 사용자) / 미리보기 ↔ 적용 사이 변경 / 충돌 시 전체 롤백(이력·버전 행 없음) / 잠금 대기·NOWAIT 409·교착 없음.
- **H2·PostgreSQL 비교** : PostgreSQL 이 판정 기준. H2 는 KEY SHARE 가 없고 프로젝트 공유 잠금이 배타처럼 동작하며 대기 대신 시간 초과(50200)가 날 수 있다 — 교착·NOWAIT 시나리오는 지금처럼 PostgreSQL 전용으로 두고, H2 는 결과(409·롤백·값) 만 비교.
- 화면 : 두 계정 브라우저로 409 문구·입력 보존·최신 다시 읽기·다시 저장 성공·연타 1회 요청 (6차 E2E 방식).

### 12.1 수정 전 재현 (`ConcurrentEditP1IntegrationTest`, 수정 전 코드)

두 트랜잭션을 실제로 엇갈렸다 : A 가 트랜잭션 안에서 할 일을 마친 뒤 커밋 전에 B 를 다른 스레드(다른 DB 연결)에서 실행하고, B 가 끝났거나 잠금을 기다리기 시작한 것을
DB 세션 정보(PostgreSQL `pg_stat_activity.wait_event_type = 'Lock'`, H2 `INFORMATION_SCHEMA.SESSIONS.BLOCKER_ID`)로 확인한 뒤 A 를 커밋한다 — 시간 대기(sleep)에 기대지 않는다.
불변식 "B 가 성공했다고 답했으면 B 의 값이 남아 있다" 가 **H2·PostgreSQL 모두 6건 실패** (조용한 손실 재현) :

| 경로 | 실행 순서 | 수정 전 결과 |
|---|---|---|
| L-01 관계 승인 | A 승인(잠금 없이 읽음) → B 관계 이름 수정 커밋(OK) → A 커밋 | 이름이 '원래' 로 되돌아가고 승인됨 |
| D-01 도메인 승인 | A 승인 → B 길이 99 수정 커밋(OK) → A 커밋 | 길이 10 으로 되돌아감 |
| D-01 도메인 동시 수정 | A 길이 11 → B 길이 22 커밋(OK) → A 커밋 | 22 사라짐 (마지막 저장이 이김) |
| D-02 단어 승인 | A 승인 → B 설명 수정 커밋(OK) → A 커밋 | 설명 '처음' 으로 되돌아감 |
| P-01 컬럼 순서 | 다른 사용자가 C 를 1번으로 저장 → 오래된 팝업 저장(OK) | C 가 조용히 3번으로 |
| P-02 스키마 이름 변경 | A 이름 변경(참조 컬럼 잠금 없이 읽음) → B 가 그 컬럼 참조를 바꿔 커밋(OK) → A 커밋 | B 의 참조가 `MART.TB_TGT` 로 덮임 |

(처음 실행에서 D-02 가 통과한 것은 테스트 준비 코드의 지연 로딩 오류(B 가 `LazyInitializationException`)였다 — 고친 뒤 재현됨. 결과 파일은 작업 사본에만 둔다.)

### 12.2 고친 경로

- **L-01 논리 관계 승인** (`LogicalModelService.updateRelationshipApproval`) : 모델 행 잠금(관계 수정과 같은 잠금) → 관계 다시 읽기(지워졌으면 대상 없음 400) → 이미 그 상태면 바꾸지 않음 →
  `ModelBase.verify`(modifiedAt) → 승인 여부만 변경. API `PATCH /api/logical/relationship/{id}/approval/{b}?modifiedAt=` — 승인 권한자면 기준값 필수(권한 오류가 먼저, 표준 용어 승인과 같은 순서).
  승인 조건 검증은 예전에도 없었다 (엔터티 승인의 상속 조건 같은 관계 승인 조건은 이번에 만들지 않았다).
- **D-01 표준 도메인** (`StandardDomainService`, `StandardDomainRepository.findForUpdate`) : 수정·승인·승인 취소가 행을 잠그고(승인은 ID 순) 다시 읽어 `modifiedAt` 과 비교(409, 상황 문구),
  **승인된 도메인 수정은 400 `APPROVED_DATA_CANNOT_BE_UPDATE`** (M8-D03). 승인 일괄은 하나라도 다르면 전체 롤백, 다른 프로젝트 행은 예전처럼 건너뛴다. 조회 응답(`StandardDomainDto`)에 `modifiedAt`.
- **D-02 표준 단어** (`StandardWordService`, `StandardWordRepository.findForUpdate`) : 도메인과 같은 잠금·기준값. 금칙어만 바뀐 수정도 기준값이 움직이게 `markModified()`.
  **승인된 단어 수정은 지금처럼 서버가 허용한다** (화면은 승인된 항목의 수정 버튼을 숨긴다 — 단어 승인 정책은 이번에 바꾸지 않았다, 13장).
- **P-01 컬럼 순서** (`ColumnManageServiceImpl.updateSortOrder`) : 한 테이블의 컬럼 전체를 보내야 한다 → 테이블 행 잠금(컬럼 구성을 바꾸는 쓰기의 공통 잠금) → 그 테이블 컬럼 전체를
  ID 순으로 `refresh(PESSIMISTIC_WRITE)` → 컬럼이 더해지거나 지워졌으면 409, 행마다 **팝업이 본 순서(`baseSortOrder`, 없던 순서는 0)** 와 지금 순서가 다르면 409 → 승인된 컬럼 400 → 전체 반영.
  기준값을 MDFCN_DT 가 아니라 순서 값으로 둔 이유 : 다른 사용자가 같은 테이블 컬럼의 설명 등 순서 밖의 값만 고친 것을 충돌로 보지 않기 위해 (지시 7장 주의 사항). 다른 테이블 컬럼을 섞으면 400.
- **P-02 스키마 이름 변경** (`SchemaServiceImpl.saveSchema`) : 이름을 바꾸는 저장만 테이블 이름 변경과 같은 구조 변경 경로 — 프로젝트 행 배타 + `ProjectWriteGuard.lock` → 스키마 행 NOWAIT →
  기준값 비교 → 참조 컬럼(`"스키마명."` 으로 시작) NOWAIT(ID 순) → 다시 읽어 **지금도 이 스키마를 가리키는 컬럼만** 고친다. 바쁘면 409, 한 트랜잭션(전체 롤백). 설명만 고치는 저장은 예전 잠금 그대로.
  잠그기 전과 잠근 뒤의 이름이 다르면 409. 관계는 내부 ID 라 그대로이고 참조 동기화 정책은 바꾸지 않았다.
- **동시 삭제 뒤 500** : 없는 테이블 삭제(`TableDesignServiceImpl.deleteTable` NPE), 없는 컬럼 삭제·승인(`ColumnManageServiceImpl.deleteColumn`·`updateColumnApproval` NPE) → 대상 없음 400
  (`TABLE_IS_NOT_DEFINED`·`COLUMN_IS_NOT_DEFINED`), 관계 규칙 수정·관계 삭제·제약조건 삭제가 다시 읽을 때 지워진 행(`EntityNotFoundException`·0행 DELETE) → 대상 없음 400
  (`INVALID_PHYSICAL_MODEL` "대상을 찾을 수 없습니다", 인덱스·VIEW 와 같은 처리). 관계 삭제는 이제 행을 잠그고 다시 읽은 뒤 지운다. 논리 모델 수정(프로젝트 행 잠금) ↔ 삭제(모델 행 잠금)의
  0행 UPDATE 500 은 잠금 구조를 바꿔야 해서 C2 로 남겼다.

  승인된 용어가 미승인 도메인을 가리킬 수 있다 (예전부터, 이번에 바꾸지 않음) ③ `saveSchema` 응답의 `updated` 는 반영 전 값이다 (화면은 목록을 다시 읽어 영향 없음 — 그대로 둠).

## 14. M8-C2 구현 (2026-11-23) — 삭제·승인·매핑 기준값

새 마이그레이션·새 오류 코드·새 설정 없음 (14.8). 기존 `ModelBase`(MDFCN_DT 기준값, 잠근 뒤 비교, 409 `MODEL_CONFLICT`, HTTP 기준값 없으면 400 `MODEL_BASE_REQUIRED`)를 삭제·승인·매핑으로 넓히고,
하위 객체를 함께 지우는 삭제에만 **구성 기준값** `common/jpa/ModelComposition` 을 더했다. 내부 호출(서비스를 직접 부르는 생성·가져오기·테스트 준비)은 지금처럼 기준값 null = 검사 밖 (DEC-08 3차 경계 — HTTP 만 필수).
검사 순서 : 권한 → 잠금 → 다시 읽기(대상 없음 = 기존 '찾을 수 없음' 400) → 승인된 대상 거절(기존 규칙) → 기준값·구성 (409) → 기존 의존 검사 (테이블 삭제만 기존 의존 검사 뒤 — 기존 오류 순서 유지).
승인·승인 취소는 "이미 그 상태면 바꾸지 않음" (C1 관계 승인과 같은 멱등성 — 상태가 바뀌지 않으므로 기준값을 건너뛰는 우회가 아니다), 상태를 바꿀 때만 비교한다.

### 14.1 수정 전 재현 (`ConcurrentEditC2IntegrationTest` 첫 판, 수정 전 코드·지금 API)

C1 과 같은 방식 (A 의 트랜잭션 안에서 B 를 다른 연결로, B 가 끝났거나 잠금을 기다리는 것을 DB 세션 정보로 확인 — 시간 대기 없음). 불변식 "화면이 본 뒤 바뀐 대상을 지우거나 바꾸거나 승인하는 요청은 성공하면 안 된다" 가
**H2·PostgreSQL 18.6 모두 7건 실패** (재현 6 은 수정 전에도 안전) :

| # | 시나리오 | 수정 전 결과 |
|---|---|---|
| 1 | 속성 조회 → 다른 사용자가 설명 수정 → 예전 화면이 삭제 | 삭제 성공 (고친 속성이 사라짐) |
| 2 | (동시) 속성 추가 커밋 전 엔터티 삭제 요청 → 기다렸다가 | 엔터티 삭제 성공 — 확인한 적 없는 새 속성까지 지워짐 |
| 3 | (동시) 컬럼 승인 커밋 전 같은 컬럼 설명 일괄 저장 | 둘 다 성공 — 승인자가 본 적 없는 설명이 승인됨 (승인이 잠그지 않음) |
| 4 | (동시) 속성 매핑을 다른 컬럼으로 변경 커밋 전 해제 요청 | 해제 성공 — 바뀐(본 적 없는) 매핑이 지워짐 |
| 5 | 매핑 조회 → 다른 사용자가 컬럼 변경 → 예전 화면이 다른 컬럼으로 변경 | 성공 — 다른 사용자의 변경을 덮어씀 |
| 6 | (동시) 매핑 해제 커밋 전 같은 속성 재매핑 → 예전 화면이 예전 ID 해제 | **안전** — 재매핑은 새 ID, 예전 ID 해제는 대상 없음 |
| 7 | (동시) 속성 수정 커밋 전 같은 속성 삭제 | 삭제 성공 — 방금 고친 속성이 사라짐 |
| 8 | (동시) 빈 테이블에 CHECK 등록 커밋 전 테이블 삭제 | 삭제 성공 — 확인 뒤 더해진 제약조건까지 지워짐 (DB CASCADE) |

### 14.3 하위 구성 변경 감지 · 동시 삽입 방지 (지시 5장)

- **구성 기준값** `ModelComposition` : 부분(section)마다 자식 (ID, MDFCN_DT 마이크로초) 를 ID 순으로 늘어놓은 정규 문자열의 SHA-256 (`v1:` + 16진수). 개수만 비교하지 않는다 — 같은 수의 다른 자식, 고친 자식, 다른 부분도 다르다 (`ModelCompositionTest`).
  부분 : 엔터티 = `attributes`·`identifiers`, 논리 모델 = `subjectAreas`, 테이블 = `indexes`·`constraints`·`relations`(나가는·들어오는), 변환 기록 = `conversions`.
  삭제를 막는 의존(관계·매핑·상속·컬럼·VIEW 참조)은 지우는 것이 아니라 거절 사유라 넣지 않았다. 사용자별 ERD 배치는 화면 설정이라 넣지 않았다.
- **삭제 확인 조회** : `GET /api/logical/entity/{id}/deletion`, `GET /api/logical/model/{id}/deletion`, `GET /api/deleteTable/preview?tableIds=` (테이블 ID 목록) → `{ id, name, modifiedAt, cascade[{kind, count}], composition }`.
  화면은 확인 대화상자를 열기 전에 부르고 "속성 2개, 식별자 1개도 함께 삭제됩니다." 를 보여 준 뒤, 화면이 처음 읽은 `modifiedAt` 과 이 `composition` 을 삭제 요청에 싣는다 (변환 기록은 목록 응답 `ConversionTree.composition`).
- **원자성 (지시 5.5 — 재계산만으로 막는다고 가정하지 않았다)** : 삭제는 자식을 더하는 모든 쓰기와 **같은 부모 잠금**을 쥔 뒤 다시 계산해 비교하고, 같은 트랜잭션 안에서 지운다.
  엔터티의 속성·식별자 등록·수정과 주제 영역·엔터티 등록은 모두 논리 모델 행을 잠근다 (`lockEntity`·`lockModel`, 주제 영역 서비스), 인덱스·제약조건 등록은 테이블 행을 잠근다 (`saveIndex`·`saveConstraint`·누락 UNIQUE 보정 NOWAIT),
  관계는 컬럼이 있어야 만들 수 있는데 컬럼이 있는 테이블은 삭제가 거절된다, 변환 기록은 생성 적용(논리 모델 행 NOWAIT)만 만든다. 그래서 비교한 뒤 지울 때까지 새 자식이 들어올 수 없다 —
  "삭제 중 삽입" 시나리오로 확인 : 삭제가 잠금을 쥔 동안의 속성 추가는 기다렸다가 대상 없음, 제약조건 등록은 PostgreSQL 대상 없음 400 / H2 등록 실패(H2 가 기다린 잠금 조회에 지워진 행을 돌려줘 Hibernate 오류 — 예전 동작, 이번 범위 밖) — 두 DB 모두 고아 자식 없음.
- 테이블 구성은 (ID, 수정 일시) 투영으로만 읽는다 : 엔티티로 올리면 DB 가 CASCADE 로 지운 인덱스·제약조건이 영속성 컨텍스트에 남아 커밋 때 flush 가 실패한다 (구현 중 발견 — 재현 8 의 두 번째 시나리오).
- 테이블 삭제는 이름 공간 선잠금 전에 같은 행을 읽어 두므로 행 잠금 뒤 `refresh` 하고 비교한다 (잠금 전 값으로 비교하지 않도록 — 매핑 잠금·스키마 삭제도 같은 이유로 `refresh`).

### 14.5 매핑 변경·해제 (M8-C2-M01)

- 기준값 : **매핑 행의 MDFCN_DT** (네 매핑 엔터티 모두 `BaseEntity` — 새 컬럼 없음, 지시 8.2 대안 1). 매핑 행의 바뀌는 값은 대상 테이블·컬럼뿐이라 수정 일시는 실제 매핑 변경과 같이 움직인다 (같은 컬럼으로 저장하면 그대로).
  다른 대안(모델 버전, 구성 값 `expectedColumnId`)은 쓰지 않았다 — 모델 버전은 매핑 변경마다 생기지 않고, 구성 값은 A→B→A 를 놓친다.
- 매핑 변경은 논리 엔터티·물리 테이블의 기준값을 바꾸지 않는다 (별도 행). 정합성 결과·생성 후보는 조회 때 계산이라 다음 조회에 반영된다. 변경 이력은 기존 기록 경로 그대로. 새 자동 연쇄 삭제 없음.
- 조회 응답 : 엔터티 매핑 행 `mappingModifiedAt` (`EntityRow` — 목록·상세·lookup), 속성 매핑 행 `modifiedAt` (`AttributeRow`), 상속 PK·상속 일반 속성 행 `modifiedAt`, 저장 응답 `modifiedAt`.
- 요청 : 변경(id 있음) 본문 `modifiedAt`, 해제 `?modifiedAt=` — HTTP 필수. 등록(id 없음)은 기존 중복 검사(잠금 뒤 + DB UNIQUE)가 지킨다.
- 잠금 : 기존 순서 그대로 (논리 모델 행 → 테이블 행 → 매핑 행 `refresh`), 다른 프로젝트 매핑은 대상 없음(기존), 연결 대상 존재·매핑 가능 여부 검사는 그대로 다시 한다.

### 14.6 API 계약 변경 (외부 호출 영향 : 아래 HTTP 요청이 기준값 없이 오면 400 `MODEL_BASE_REQUIRED`)

| 메서드·경로 | 기존 요청 | 변경 요청 | 기준값 출처 | 충돌 |
|---|---|---|---|---|
| `DELETE /api/logical/model/{id}` | 없음 | `?modifiedAt=&composition=` | 모델 조회 · `GET …/model/{id}/deletion` | 409 |
| `DELETE /api/logical/entity/{id}` | 없음 | `?modifiedAt=&composition=` | 엔터티 상세 · `GET …/entity/{id}/deletion` | 409 |

| `PUT /api/saveColumn/bulk` | `deletedIds` | + `deletedBaseModifiedAt {id: 수정 일시}` (deletedIds 전부) | 편집기 행 | 409 |

### 14.7 화면 (최소 수정 — 409 복구 UX 는 C3)

- 공통 `lib/deletion.ts` : `baseQuery(modifiedAt, composition?)`, `withDeletion(url, open)` (삭제 확인 조회 → 대화상자), `cascadeText` (함께 지워질 수 — 한국어·영어).
- 삭제 확인 대화상자에 함께 지워질 수 표시 : 엔터티(상세·논리 ERD), 논리 모델, 테이블(목록·물리 ERD). 기준값 전달 : 속성·식별자·관계·스키마·VIEW·인덱스·제약조건·FK, 엔터티·관계·VIEW·인덱스·제약조건 승인, 매핑 변경·해제(엔터티·속성·상속 PK·상속 일반 속성), 변환 기록, 컬럼 일괄 편집기의 삭제.
  테이블·컬럼 목록의 승인·삭제는 이미 목록 행(`modifiedAt` 포함)을 그대로 보내 화면 변경이 없다.
- ERD 조회 응답에는 수정 일시가 없어, 논리·물리 ERD 의 엔터티·테이블·속성 삭제는 확인 대화상자를 열 때 읽은 최신 값을 기준값으로 쓴다 (ERD 의 수정 폼이 열 때 상세를 읽는 것과 같은 방식) — 그 사이(대화상자 → 확인) 바뀌면 409.
- 409 는 기존 공통 오류 알림, 승인·삭제 실패 뒤 목록·상세를 다시 읽고 성공 알림을 띄우지 않는다. 권한·국제화 : 기존 버튼 권한 그대로, 새 문구 4개 en.ts.

### 14.8 마이그레이션

없음. 모든 기준값은 기존 MDFCN_DT 와 기존 행에서 계산한다 (매핑·변환 기록 행도 `BaseEntity`).

### 14.9 남은 범위 · 결정이 필요한 것 (C2 이후)

- **결정 필요** : ① 승인의 기준값은 대상 행의 수정 일시만 본다 — 엔터티 승인은 그 사이 바뀐 속성·식별자를, 테이블 승인은 바뀐 컬럼을 잡지 않는다 (엔터티·테이블의 MDFCN_DT 는 자식 변경에 움직이지 않는다). 승인에도 구성 기준값을 쓸지 (승인 화면이 구성을 보여 줘야 한다)
  ② 범위 밖으로 둔 삭제 — 표준 단어·도메인·용어 삭제(잠금·기준값 없음, FK 가 참조를 지킴)와 원본 매핑 해제류를 같은 계약으로 넓힐지 ③ (C1 에서 넘어온 것) 승인된 표준 단어의 서버 수정 허용, 표준 도메인 승인 취소의 참조 영향.
- **C2 문서 13장에 있었지만 이번 지시에 없어 하지 않은 것** : 논리 속성 순서(L-02).
- **C3** : 409 복구 UX(U-01, M8-D05), 일괄 편집기 기준값 범위(U-02, M8-D04), ERD 배치 409(U-03), 중복 제출 방지(U-04, M8-D06) — 이번에 넓힌 삭제·승인·매핑 409 도 같은 복구 흐름이 필요하다.
- **C4** : 잠금 순서(K-01 — 테이블 승인·삭제의 요청 순서 잠금은 그대로 두었다), 컬럼 엑셀 테이블명(P-03), FK 등록 대상 잠금(P-04), 순서 번호(P-05), 스키마 등록(P-06).
- H2 에서 삭제된 테이블을 기다린 등록이 Hibernate 오류(500)로 끝나는 것 (14.3) — PostgreSQL 은 400. 이번 범위 밖, C4 후보.

## 15. M8-C3 구현 (2026-11-23) — 409 충돌 복구 UX · 일괄 편집 기준값 범위

확정 정책 M8-C3-D01~D05 (지시) : 자동 병합·자동 재시도·최신 기준값으로 조용히 다시 보내기 금지(D01), 409 뒤 입력 보존 — 폼·대화상자를 닫지 않고 실패를 성공으로 보이지 않음(D02),
최신 데이터 재조회 — 조회 실패(대상 없음·권한)는 409 와 구분(D03), 사용자가 고른 변경만 최신 값 위에 다시 적용한 뒤 직접 다시 저장(D04), 요청 중 중복 제출 방지 — 서버 검증을 대신하지 않음(D05).
새 마이그레이션·새 오류 코드·외부 라이브러리 없음. 백엔드 변경은 일괄 편집기의 `unchanged` 행(15.6, M8-D04) 하나뿐이다.

### 15.1 기존 구조 (분석)

- 오류는 `lib/api.ts` → `ApiErrorBridge`(App.tsx) 가 모두 공통 알림 대화상자로 보였다. 409 를 따로 다루는 곳은 C1 의 관계 승인(목록 다시 읽기)과 사전 승인뿐이었다.
- 확인 대화상자(`DialogProvider.confirm`)는 [확인] 을 누르는 순간 닫히고 콜백을 부른다 — "확인 화면 유지" 는 새 검토 대화상자로 대신한다 (DialogProvider 는 바꾸지 않았다).
- 폼 대부분은 저장 중 버튼을 막지 않았다 (인덱스·VIEW·상속 매핑만 `saving`/`busy` 가 있었다).

### 15.2 공통 구조 (`components/conflict/`)

- `lib/api.ts` : 요청 옵션 `conflict: 'handled'` — 409 `MODEL_CONFLICT`·`ERD_LAYOUT_CONFLICT` 만 공통 알림을 띄우지 않는다 (다른 오류는 그대로 알림). `isConflict(error)`.
- `ConflictRecovery.tsx`
  - `useSubmitting()` : 요청 중 같은 작업을 다시 시작하지 않는 [busy, run] (성공·실패·예외 모두 풀림) — 저장 버튼 `disabled` + "처리 중…".
  - `useConflictRecovery({ initial, base, fields, load })` : 수정 폼용. 409 → 입력 유지 + 안내 → [최신 내용 확인] → `load` 로 최신 값 → **편집 시작 시 · 현재 서버 값 · 내 변경 · 내 변경 적용** 표(바뀐 항목만 + 수정 일시) →
    [최신 내용에 내 변경 다시 적용] = 내가 바꾼 항목 중 고른 것만 내 값, 나머지(다른 사용자가 바꾼 항목 포함)는 최신 값으로 새 편집 상태 + 기준값을 최신으로 → 사용자가 [저장]. 재충돌이면 같은 절차.
    조회 실패는 `loadFailure`/`isGone` 으로 대상 없음·권한(다시 저장 불가, 버튼 잠금)과 그 밖(다시 불러오기)을 나눈다. 비교는 trim 한 값·구조는 JSON 비교라 바꾸지 않은 칸을 내 변경으로 보지 않는다.
  - `CompareTable` (공통 비교 표), `openConflictReview` (삭제·승인·매핑 해제 검토 대화상자 — 최신 재조회·비교·[다시 실행]·재충돌이면 다시 읽기), `MappingConflictNotice` (기존 매핑 · 최신 매핑 · 내 선택).
- `conflictActions.tsx` : `runWithReview` (단건) · `runListWithReview` (여러 건 한 요청 — 바뀐 행만 보여 줌) — 처음 요청은 화면이 본 기준값, 409 면 검토 대화상자, 다시 실행은 사용자가 누를 때 최신 기준값으로 한 번.
  승인은 최신이 이미 목표 상태면 다시 보내지 않고 "다른 사용자가 이미 승인했습니다" (멱등성 유지), 하위 구성 기준값이 달라지면 "삭제 대상의 하위 항목이 변경되었습니다" — 구성 기준값은 서버 값만 쓴다.
- 화면별 상태 읽기 : `features/logical/conflictSnapshots.ts` (엔터티·속성·식별자·관계·삭제 확인), `features/table/physicalConflicts.ts` (테이블·컬럼 목록, 관계·인덱스·제약조건, VIEW, 스키마).
- 스타일 `styles/conflict.css` : primer 토큰만 써서 라이트·다크 자동, 좁은 화면은 표 가로 스크롤.

### 15.4 ERD 조회 응답 (지시 11장)

바꾸지 않았다. ERD 의 엔터티·테이블 삭제는 어차피 삭제 확인 조회(구성 기준값)를 불러야 하고, 속성 수정·삭제는 엔터티 상세를 읽는다(수정 폼과 같은 방식) — 추가 필드는 그 조회를 없애지 못한다. 배치 버전(`version`)과 객체 수정 일시는 섞지 않는다.

### 15.5 ERD 배치 저장 충돌 (`features/erd/layoutConflict.tsx`)

409 `ERD_LAYOUT_CONFLICT` (같은 사용자의 다른 탭) → 옮긴 위치는 버리지 않고 최신 서버 배치(버전 포함)를 읽어 **편집 시작 시(불러온 배치) · 최신 저장 위치 · 내 위치** 비교 :
내가만 옮긴 노드 = 내 위치 유지, 다른 탭만 옮긴 노드 = 최신 위치로 화면을 맞춤(논리 ERD 는 보이는 노드 좌표를 함께 보내므로 그대로 두면 덮어쓴다), 둘 다 옮긴 노드 = 노드마다 [내 위치]/[최신 위치] 선택(기본 내 위치).
[최신 배치 기준으로 다시 준비] 가 최신 버전·기준 배치로 바꾸고 저장 대기를 다시 만든다 — 저장은 사용자가 [배치 저장]. 물리 ERD 의 자동 배치(저장된 좌표가 없어 화면이 정한 위치)는 사용자 이동으로 세지 않는다.
저장 형식·`version` 필드·React Flow/ELK 구조는 그대로, 다른 사용자 배치와는 원래 충돌하지 않는다.

### 15.6 컬럼 일괄 편집기 (M8-D04)

- 서버 (`ColumnBulkSaveDto.Row.unchanged`) : `unchanged=true` 인 기존 행은 값·순서를 읽지도 쓰지도 않고 기준값도 보지 않는다 (비어 있는 순서도 채우지 않음, 뒤 행 번호는 이 행 다음부터). HTTP 기준값 필수는 `unchanged` 가 아닌 기존 행만.
- 화면 : 순서 변경·추가·삭제가 **없는** 저장은 고친 행만 기준값과 값을 보내고 나머지는 `{id, unchanged: true}` — 그 사이 다른 사용자가 고친 다른 컬럼은 409 없이 그 값이 남는다.
  순서 변경·추가·삭제가 있는 저장은 예전처럼 모든 기존 행을 기준값과 함께 보낸다 (번호가 다시 매겨질 수 있는 테이블 단위 검증 — 지시 10장 예외). 원자성·테이블 행 잠금은 그대로.
- 409 복구 : 편집 내용 유지 → [최신 내용 확인] → 행별 비교(편집 시작 시 수정 일시 · 지금 · 내 수정/삭제) → 고른 행은 **내가 고친 칸만** 최신 값 위에 다시 적용, 나머지 칸·행은 최신 값,
  그 사이 삭제된 컬럼은 편집에서 빼고 알림, 다른 사용자가 더한 컬럼은 끝에 붙임, 그 사이 승인된 컬럼은 최신 값(고칠 수 없음). 순서 기준도 최신 서버 순서로 바뀐다.

  삭제는 지금처럼 이름 공간(스키마) 잠금이 먼저 — 스키마 → 테이블 순서를 지킨다.
- `ModelMappingService.saveEntityMapping` (변경) : 논리 모델 행 → 지금 테이블·새 테이블을 ID 오름차순으로 잠근 뒤 매핑을 다시 읽는다 (`lockMapping(…, otherTableId)`). 등록·해제는 그대로.

### 16.3 H2 테이블 삭제 ↔ 제약조건 등록 "500" (지시 7장)

재현되지 않았다. 지금 코드에서 H2·PostgreSQL 모두 삭제가 테이블 행을 잡은 동안 들어온 CHECK 등록은 기다렸다가 `TABLE_IS_NOT_DEFINED`(400), 지워진 컬럼의 UNIQUE 등록은 기존 `INVALID_PHYSICAL_MODEL`(400)이다 (H2 5회 반복 동일, 고아 제약조건 없음).
C2 때 H2 에서 본 예외(`TransientPropertyValueException` → 500)는 그때 구현 중이던 테이블 구성 계산이 인덱스·제약조건을 **엔티티로** 읽어, DB 가 CASCADE 로 지운 자식이 영속성 컨텍스트에 남아 커밋 flush 가 실패한 것이었다 (14.3 에서 투영 조회로 고침).
고친 뒤에는 B 의 실제 결과를 다시 확인하지 않고 "H2 는 500" 으로 기록하고 단언을 느슨하게(`isNotEqualTo("OK")`) 둔 것이 잘못이었다 — 이번에 C2 테스트를 두 DB 모두 400 으로 엄격히 바꿨다. 서비스 코드 변경 없음.

### 16.4 `entityApprovalVsEdit` 간헐 시간 초과 분석 (지시 4장) — **원인 미확정 (미해결)**

### 17.2 C4b-1 FK 등록 대상 잠금 (P-04)

- `saveRelation` 이 **원본·대상 테이블 행을 처음부터 함께, 중복 없이 ID 오름차순으로** 잠근다 (`lockTablesInIdOrder` — 자기 참조는 한 번). 잡은 뒤 대상 컬럼·PK·UNIQUE 제약조건·고유 인덱스를 다시 읽어 기존 검증(`buildRelation`·`validateForeignKey`)을 그대로 한다.
  대상 컬럼 삭제(단건·일괄)·PK/고유값 변경(일괄 저장)·UNIQUE 제약조건 등록/삭제·인덱스 등록/수정/삭제는 모두 대상 테이블 행을 먼저 잡으므로 서로 직렬화된다.
- 원본 테이블만 잡은 뒤 대상을 더 잡는 순서가 아니다 (지시 4.4) — 두 행을 같은 단계에서 ID 순으로 잡아, A → B 와 B → A 동시 등록이 교착하지 않는다.
- 다른 경로와의 순서 : 프로젝트 배타를 쥐는 구조 변경(테이블 이름 변경·PK 컬럼 삭제·스키마 이름 변경·생성·FK/UNIQUE/상속 FK 보정·물리명 적용)은 테이블 행을 NOWAIT 로 잡는다 → 등록이 쥔 동안에는 409, 그들이 쥔 동안 등록은 기다린다 (교착 없음).
  커밋 때 `ProjectWriteGuard` 공유 잠금은 그대로 마지막. 관계 동기화(REF_COLUMN)는 대상 행에 KEY SHARE 만 잡아 `FOR NO KEY UPDATE` 와 충돌하지 않는다.
- **행동 변화** : 대상 테이블에 FK 를 등록하는 동안 그 테이블의 이름 변경은 409 (예전에는 이름 변경이 먼저 끝났다 — D09 의 '겹치면 409' 계약과 같다).
- 다른 FK 생성 경로 : 논리 → 물리 생성·누락 FK 보정·상속 FK 보정은 이미 프로젝트 배타 → 자식·부모 테이블 NOWAIT (바꾸지 않음). FK 수정은 규칙만 바꾸고(관계 행 잠금) 키를 바꾸지 않는다. 엑셀·일괄 저장·단건 등록의 FK 는 참조 테이블명 → REF_COLUMN 동기화다 (17.11 ①).
- 검증 정책(자기 참조·순환·복합·참조 가능한 키·승인 상태)은 바꾸지 않았다.

### 17.3 C4b-2 논리 속성 순서 L-02 (API 계약 변경)

- `PUT /api/logical/entity/{entityId}/attribute/order` 본문 : **`[{ "id": 속성ID, "baseSortOrder": 화면이 읽은 그 속성의 정렬 순서(없던 순서는 0) }, …]`**, 목록 위치가 새 순서(1부터). 예전 형식 `[id, …]` 와 기준값 빠진 행은 400 `MODEL_BASE_REQUIRED`.
- 서버 (`LogicalModelService.reorderAttributes`, 물리 컬럼 순서 P-01 과 같은 계약) : 빈 목록·null·중복 ID 400 → 모델 행 잠금(속성 등록·수정·삭제와 같은 잠금) → 승인 검사(기존) → 속성 행 ID 순 잠금·다시 읽기 →
  같은 프로젝트 다른 엔터티의 속성 400 `INVALID_LOGICAL_MODEL` / 속성이 더해지거나 지워짐(다른 프로젝트 ID 포함 — '없는 속성') 409 / 한 행이라도 지금 순서 ≠ 기준값 409 → 순서가 달라지는 행만 `sortOrder` 변경 (다른 칸은 잠근 뒤 읽은 값 그대로, 순서가 같으면 UPDATE·이력 없음).
- 기준값을 MDFCN_DT 가 아니라 순서 값으로 둔 이유 : 다른 사용자가 설명·데이터 유형만 고친 것을 순서 충돌로 보지 않기 위해서다 (지시 5.4). 단, 순서가 바뀐 속성 행은 `MDFCN_DT` 가 움직여, 그 속성을 열어 둔 다른 사용자의 속성 대화상자 저장은 409 다 (컬럼 순서 P-01 과 같음 — 바꾸지 않았다).
- "중복 순서 번호 요청" 은 요청에 순서 번호가 없어(위치가 순서) 생길 수 없다 — 결과 순서는 항상 1..n.
- 내부 호출(서비스 직접 호출)은 `AttributeOrder.withoutBase(ids)` (기준값 null = 검사 밖, DEC-08 경계). 이력은 기존 `ModelChangeRecorder` 그대로.
- 화면 (`features/logical/model.ts` `attributeOrderBody`, 엔터티 상세 속성 탭·논리 ERD 엔터티 패널) : 보고 있는 순서의 `sortOrder` 를 기준값으로 보내고, 요청 중 ↑/↓ 를 잠근다(`useSubmitting`).
  409·그 밖의 오류는 공통 알림 — 보이던 순서를 그대로 두고 성공으로 보이지 않는다, 자동 재전송 없음. 비교·다시 적용 대화상자는 C4c 범위로 남겼다.

### 17.4 C4b-3 컬럼 엑셀 업로드 테이블명 해석 (P-03)

- 조사 : 파일을 한 번 읽어 테이블명만 모음(DB 잠금 없음) → 이름 → ID 해석(잠금 없음) → 해석된 테이블을 ID 순 잠금(M7-U07) → 청크(500행)마다 검증·저장, 업로드 전체 한 트랜잭션·하나라도 오류면 전체 롤백. 미리보기·planToken 없음 (새로 만들지 않았다).
- 고친 것 (`ColumnManageServiceImpl.confirmUploadTables`) : 잠근 뒤 영속성 컨텍스트를 비우고(아직 쓴 것 없음) **처음 찾은 이름만 최신 데이터로 다시 해석**한다.
  같은 테이블 → 최신 테이블명(대소문자만 바뀐 이름 변경 포함)을 사본으로 쓴다 / 이제 없음·여러 스키마 → 행 검증의 기존 오류(대상 없음 400 — 그 변경 뒤에 올린 파일과 같은 결과) / 같은 이름이 **다른 테이블**(지우고 같은 이름으로 다시 만듦 등) → 409 `MODEL_CONFLICT`, 이름만 보고 다른 테이블에 넣지 않는다.
  처음에 못 찾은 이름은 그대로 대상 없음 (그 사이 생긴 테이블은 잠그지 않았으므로 쓰지 않는다). 잠근 행은 이후 이름 변경(NOWAIT 409)·삭제(대기)되지 않는다.
- 파일 파싱 동안 잠금을 늘리지 않았다 (첫 읽기는 잠금 전 그대로). 전체 롤백·열 순서·템플릿·스키마명 해석 규칙은 바꾸지 않았다.

### 17.5 C4b-4 스키마 동시 등록 (P-06)

- 등록(`saveSchema`, id 없음)이 **프로젝트 행을 배타로 먼저** 잡는다 — 없는 스키마 행은 잠글 수 없고 `UX_SCHM_01` 은 대소문자를 구분한다. 잡은 뒤 기존 대소문자 무시 중복 검사가 최신 상태를 본다 → 400 `SAVED_DATA_EXISTS`.
  이름 변경(이미 프로젝트 배타)·기본 스키마 지연 생성(`createDefaultSchema`, 프로젝트 행 잠금)과 같은 행으로 직렬화된다. 스키마 등록은 승인 권한자의 드문 작업이라 프로젝트 전체를 잠깐 막는 비용이 작다고 판단했다 (표준 도메인 등록 DICT-2 와 같은 방식).
- DB 제약조건 위반을 중복 오류로 바꾸는 처리는 넣지 않았다 (잠금 뒤 검사가 앱 안의 모든 등록 경로 — 화면 등록·기본 스키마·모델 Import(프로젝트 배타) — 를 막는다).
- 정책 유지 : 대소문자 규칙, 프로젝트별 유일, 다른 프로젝트의 같은 이름 허용, 기본 스키마 이름 고정·삭제 금지, 권한(승인 권한자). 삭제 중 같은 이름 등록은 삭제 커밋 전 상태를 보고 400 (직렬 순서 '등록 → 삭제' 와 같은 결과).
  기본 스키마는 지정 API 가 없다 (지연 생성만 — 동시 생성 회귀 테스트로 하나만 생기는 것을 확인).

### 17.7 기존 순서 번호 중복 데이터 조사

새로 설치한 DB(PostgreSQL 18.6, V0~V3 — 예제 프로젝트 0)에서 위 범위별 겹침 : **모두 0** (논리 속성·물리 컬럼·순서 없는 컬럼·식별자 구성원·주제 영역·서브타입 그룹·서브타입·공통 컬럼·테이블).

### 18.2 M7-U08 · M7-FK-D11 검토 (지금 잠금 구조를 고른 이유)

- 관계 동기화는 관계 INSERT 의 FK 검사로 **대상 테이블 행과 대상 PK 컬럼 행에만 KEY SHARE** 를 건다 (D11 14.3). KEY SHARE 는 일반 쓰기의 FOR NO KEY UPDATE 와 함께 잡히므로, 서로를 참조하는 일반 저장끼리(양방향 포함)는 교착하지 않는다 (U08 후속 결과).
- 그 행을 **키 강도**(FOR UPDATE — 이름·스키마 변경, PK 컬럼 삭제)로 바꾸는 쓰기만 KEY SHARE 와 충돌한다. 그래서 그런 쓰기는 모두 프로젝트 행을 배타로 먼저 잡고 행을 **NOWAIT** 로 잡는다 — 프로젝트를 쥔 채 행을 기다리면 커밋 직전에 프로젝트 공유 잠금을 기다리는 일반 저장과 교착하기 때문이다 (S4·S6b·D11).
- 참조 대상을 기존에 미리 잠그지 않은 이유 (U08·D11 방안 B 기각) : 동기화가 참조할 대상은 다른 트랜잭션의 커밋 전 상태에 따라 바뀌어 첫 변경 전에 확정할 수 없고, 대상 행을 배타로 잡으면 그 테이블의 일반 저장까지 막으며, 두 번째 잠금 규칙이 생긴다.
- D11 이 일부러 남긴 것 : PK **여부**(`PK_YN`) 변경은 키 강도가 아니라 일반 경로 — 서로 PK 여부를 바꾸면 '사후 무효 FK'(DEC-09 진단)가 남을 수 있다. 지우는 중인 PK 를 참조하던 일반 저장은 FK 위반(500)으로 끝났다 (바꾸지 않았다).

### 18.4 선택한 방식 — 동기화가 이미 걸던 KEY SHARE 를 '읽기 전' 으로 당긴다

처음 시도한 방식(동기화마다 프로젝트 공유 잠금을 먼저 잡기)은 **되돌렸다** : H2 에서는 공유 잠금이 배타처럼 동작해 관계없는 테이블의 컬럼 등록끼리 서로 기다렸고(`ColumnInsertConcurrencyIntegrationTest` 등 5건), PostgreSQL 에서는 엑셀 업로드가 첫 청크부터 프로젝트 공유 잠금을 쥐어 이름 변경·FK 보정·PK 삭제가 D09 계약(409)대신 업로드 끝까지 기다렸다(`RelationSyncDeadlockIntegrationTest` 5건) — 기존 NOWAIT·직렬화 정책 변경이라 쓰지 않았다.

최종 (`PhysicalModelServiceImpl.syncReferenceRelations`) :

1. flush → 대상 컬럼 수집 → **최신화** (`freshColumns`·`freshRelations`·`freshTables`) : 참조 테이블명·소속 테이블, 관계의 대상 테이블·관계명·대상 컬럼, 테이블 이름·스키마·스키마명을 스칼라 조회 한 번씩으로 DB 와 비교해 **다른 엔티티만** 다시 읽고 지워진 것은 뺀다 (flush 뒤라 이 트랜잭션의 변경은 잃지 않는다, 전체 clear 없음).
2. 계획 계산 (`referencePlan`) : 새로 만들거나 대상이 바뀌는 관계(`newTargets`)만 골라낸다.
3. **PostgreSQL** : 그 관계의 대상 **스키마 행 → 테이블 행 → PK 컬럼 행**을 `FOR KEY SHARE` 로 (종류 순서 · ID 오름차순, 1,000개씩) 잡고 1~2 를 다시 한다. 다시 계산한 대상이 늘면 그것도 잡고 다시 (네 번째에도 바뀌면 409). 대상이 그대로인 관계·지울 관계는 잠그지 않는다.
4. 쓰기 (기존과 같은 생성·대상 변경·삭제 규칙, 역방향 중복 검사 그대로).

순환이 없는 이유 : KEY SHARE 와 충돌하는 것은 키 강도 잠금(FOR UPDATE)뿐이고, 그것을 쥐는 쓰기는 모두 프로젝트 배타를 먼저 잡은 뒤 **기다리지 않는다**(NOWAIT). 그래서 동기화는 그 쓰기의 커밋을 기다릴 수는 있어도 그 쓰기가 동기화를 기다리는 일은 없다. 동기화가 먼저 잡았으면 그 쓰기는 기존대로 409 다. 일반 쓰기의 FOR NO KEY UPDATE·다른 동기화의 KEY SHARE 와는 함께 잡힌다 — 양방향·다중 테이블 참조 일반 저장끼리 기다리지 않는다.
잠금 강도·대상은 원래 관계 INSERT 의 FK 검사가 걸던 것과 같고 시점만 '읽은 뒤' 에서 '읽기 전' 으로 당겼다 (스키마 행은 18.5 로 더해진 것). 프로젝트 공유·배타 정책, NOWAIT 정책은 바꾸지 않았다.

**H2** 에는 KEY SHARE 가 없다 (같은 문장이 배타 잠금이라 양방향 참조 일반 저장끼리 교착). 대신 `ReferenceSyncBoundary` 가 커밋 직전 루프 뒤 **H2 일 때만** 프로젝트 행을 잡고(커밋 직전 `ProjectWriteGuard` 가 잡던 같은 잠금을 조금 앞당김) 이 트랜잭션이 동기화한 테이블(직접 부른 것 포함)을 최신화와 함께 한 번 더 맞춘다 — 진행 중인 구조 변경이 있으면 그 커밋을 기다린 뒤 예전 상태로 만든 관계를 지우거나 고친다 (H2 에서 지워진 PK 를 가리키던 고아도 이 단계가 지운다). 커밋 단계에서만 잡으므로 일반 저장끼리의 동시성은 예전과 같다.

### 18.5 스키마 이름 변경의 키 강도 선잠금 (`ModelRowLocks.schemasForKeyChange`)

`SCHM_NM` 은 `UX_SCHM_01` 의 열이라 그 UPDATE 는 PostgreSQL 에서 키 강도다. 그런데 스키마 이름 변경만 스키마 행을 NO KEY UPDATE NOWAIT 로 미리 잡아(`schemasNoWait`), 다른 트랜잭션이 그 스키마 행에 KEY SHARE 를 쥐고 있어도(테이블 등록의 FK 검사, 이번 동기화) 선잠금은 통과하고 커밋 때 UPDATE 가 프로젝트 배타를 쥔 채 기다렸다 (구조상 교착 가능 — 재현하지 않음).
테이블 이름 변경(`tablesForKeyChange`)과 같은 규칙으로 이름 변경 때 스키마 행을 `FOR UPDATE NOWAIT` 로 한 번 더 잡는다 — 바쁘면 기존 409. 이름 공간 잠금(`ObjectNamespace`)은 그대로 NO KEY UPDATE.

### 18.6 바뀐 잠금 범위

| 경로 | 예전 | 지금 | 이유 |
|---|---|---|---|
| 동기화 (PostgreSQL) — 새로 만들거나 대상이 바뀌는 REF 관계 | 대상 테이블·PK 컬럼 KEY SHARE (INSERT 때) | **같은 행 + 대상 스키마 행** KEY SHARE (읽기 전) | 18.4 |
| 동기화 — 대상 그대로·삭제 | 없음 | 없음 | 범위를 넓히지 않음 |
| 동기화 (H2) | 없음 | 커밋 직전 프로젝트 행 (원래 커밋 직전에 잡던 잠금) | 18.4 |
| 스키마 이름 변경 | 스키마 NO KEY UPDATE NOWAIT | + FOR UPDATE NOWAIT | 18.5 |

관계없는 테이블의 컬럼 등록·수정은 더 직렬화되지 않는다 (`ColumnInsertConcurrencyIntegrationTest` 회귀 통과, R1 테스트의 관계없는 두 테이블 동시 등록). 다른 프로젝트 작업은 서로 막지 않는다.

### 18.7 응답 계약 변화 (HTTP API 형식은 그대로)

- 지우는 중인 PK 를 참조하는 컬럼 등록·일괄 저장·엑셀 : 예전 커밋 때 FK 위반 500 (전체 롤백) → **기다린 뒤 성공, 관계 없음** (참조 테이블명은 남는다 — PK 가 없는 테이블을 가리키는 참조와 같은 상태). D11 테스트 2건(`d11PkDeleteVersusReferencingSave`·`d11SingleDeleteOfPk`)의 기대값을 이 계약으로 바꿨다 (교착 없음·대기 확인·잘못된 관계 0건 단언은 그대로).
- 이름·스키마 이름 변경과 겹친 예전 이름 참조 : 예전에는 성공 + 어긋난 관계 → 성공 + 관계 없음 (그 변경 뒤에 저장한 것과 같은 결과).
- 동기화가 대상 행을 잡은 사이의 스키마 이름 변경 : 409 (테이블 이름 변경과 같은 D09 계약).

### 18.8 테스트 (`ConcurrentEditC4bRefColumnIntegrationTest` 10건, H2·PostgreSQL)

### 19.3 실제 PK 구성 변경 판정 (`ColumnManageServiceImpl.changesPrimaryKey`)

잠그기 전 DB 의 저장 상태를 스칼라 조회(`findPkColumnIds`·`findPkStates` — 영속성 컨텍스트에 옛 상태를 남기지 않는다)로 읽어 비교한다 : 지금 PK 인 컬럼 삭제 / 기존 행의 PK 여부 ≠ 지금 값 / PK 여부 Y 인 새 행 → 변경.
`unchanged` 행(M8-D04)·승인된 컬럼의 행(값을 쓰지 않는다)·요청에 없는 기존 컬럼·다른 테이블의 행은 보지 않는다 (부분 요청을 PK 전체 교체로 해석하지 않는다).
**잠근 뒤 재검증** : 일반 경로로 판정했는데 잠근 뒤 다시 읽은 컬럼으로 보면 PK 를 바꾸는 저장이면(그 사이 다른 저장이 PK 를 바꿨다) 잠금을 승격하지 않고 409 (`ModelRowLocks.busy()`, 전체 롤백 — D11 의 '판정 뒤 PK 가 된 삭제 대상' 규칙을 넓힘). 구조 변경으로 판정했는데 잠근 뒤 아니면 그대로 진행 (더 강한 잠금일 뿐). 자동 재시도 없음.

### 19.4 구조 변경 경로의 잠금 (`lockForKeyChange`, D11 경로 재사용)

프로젝트 행 배타(맨 먼저) → 테이블 행 NOWAIT → **테이블 행 키 강도 NOWAIT (`tablesForKeyChange` — R2 추가)** → 지울 컬럼 FOR UPDATE NOWAIT → 소속 컬럼 NOWAIT → 이 테이블을 참조 테이블명으로 가리키는 컬럼 NOWAIT.
테이블 키 강도는 R1 의 동기화가 대상 테이블 행에 거는 KEY SHARE 와 충돌시키기 위해서다 : 동기화가 먼저면 PK 변경이 기다리지 않고 409, PK 변경이 먼저면 동기화가 커밋을 기다렸다가 바뀐 PK 로 다시 계산한다 (R2-D03). 그 테이블을 참조하는 컬럼 NOWAIT 덕분에 '참조 해제 ↔ PK 변경' 도 차례가 정해진다 (수정 전 : PK 변경 쪽 `OptimisticLockException` 500).
H2 는 같은 문장이 배타 잠금이고, R1 의 커밋 직전 재확인이 프로젝트 행에서 PK 변경 커밋을 기다린다.

### 19.5 엑셀 업로드 잠금 범위 (R2-D02)

- 첫 읽기(잠금 없음)에서 테이블명과 **PK 여부 열만** 모은다 — PK 여부 Y 인 행이 있는 테이블 = PK 가 바뀌는 테이블.
- PK 행이 없는 업로드 : 예전 그대로 (업로드 테이블 ID 순 대기 잠금, 프로젝트 배타 없음).
- PK 행이 있는 업로드 : 테이블명 해석이 끝난 뒤 프로젝트 배타 → 업로드 테이블 NOWAIT → PK 테이블 키 강도 NOWAIT → 그 테이블을 참조하는 컬럼 NOWAIT. 업로드 전체가 한 트랜잭션(전체 롤백 그대로)이라 배타는 커밋까지 쥔다 — 파일 첫 읽기 동안에는 쥐지 않는다. 청크 사이 추가 잠금도 NOWAIT. C4b 의 테이블명 재해석은 그대로.

### 19.6 동기화 쪽 보완 · PostgreSQL 반복 잠금 안전성 (R2-D05)

- R1 은 '새로 만들거나 대상이 바뀌는 관계' 의 대상만 잠갔다. 그래서 PK 가 없거나 복합이라 관계를 만들지 않는 대상의 PK 가 단일이 되는 변경(N→Y, 복합 일부 해제)과 겹치면 관계가 빠졌다. 이제 **참조가 그 테이블로 해석되지만 PK 가 하나가 아니어서 관계가 없는 대상**의 테이블 행(+ 스키마 행)도 KEY SHARE 로 잡는다 (`ReferencePlan.keyless`).
- 잠금 호환 : KEY SHARE 는 KEY SHARE·FOR SHARE·FOR NO KEY UPDATE 와 함께 잡히고 FOR UPDATE 와만 충돌한다. 대상 행에 FOR UPDATE 를 쥐는 쓰기 = ① 구조 변경(PK 구성 변경·PK 삭제·이름 변경·스키마 이름 변경·물리명 적용·원본 삭제 반영) — 모두 프로젝트 배타 뒤 **NOWAIT** 라 다른 트랜잭션을 기다리지 않는다 ② 일반 테이블 삭제 — **빈** 테이블만 지우고 ID 순으로 잡는다 (PK 가 있는 테이블은 컬럼이 있어 지울 수 없다 — `keyless` 대상 중 빈 테이블만 해당) ③ 스키마 삭제 — 테이블이 있는 스키마는 지울 수 없다.
- 그래서 동기화가 기다릴 수 있는 상대는 ①(기다리지 않는다 — 순환 불가)과 ②(ID 순 획득)뿐이다. 반복 계산으로 **이미 잡은 것보다 작은 ID 를 새로 잡으면** ②와 순서가 뒤집혀 순환할 수 있으므로 그 행만 `FOR KEY SHARE NOWAIT` (바쁘면 409), 큰 ID 는 기다린다 (`keyShare` — R2 추가). 종류가 다른 행(스키마·컬럼)의 FOR UPDATE 보유자는 ①뿐이라 종류 사이 역순도 순환하지 않는다.
- 반복 제한(네 번째에도 바뀌면 409)은 안전 근거가 아니라 무한 반복 방지다. 근거는 위 대기 그래프다 : 동기화 → (구조 변경 | ID 순 빈 테이블 삭제) 로만 기다리고, 구조 변경은 아무도 기다리지 않으며, 빈 테이블 삭제와는 ID 순서 규칙으로 역방향 대기가 생기지 않는다.

### 19.7 H2 커밋 직전 재확인 검증 (R2-D04)

- 재확인이 관계를 **지우는** 경우(PK 삭제·PK 해제와 겹쳐 예전 상태로 만든 관계) : R1·R2 테스트가 H2 에서 실제로 지나간다 (`pkDeleteVsInsert`·`pkOffVsInsert` 등 — 지우는 관계는 그 트랜잭션이 만든 것이라 자기가 쥔 행이다). 시간 초과 없음.
- 재확인이 **다른 트랜잭션이 쥔 관계 행을 고쳐야 하는** 경우 : 그 관계는 다른 트랜잭션이 그 참조 컬럼(또는 대상)을 바꾸는 중일 때만 쥐이는데, R2 이후 참조 대상을 바꾸는 쓰기는 모두 구조 변경(프로젝트 배타 + 참조 컬럼 NOWAIT)이고 일반 쓰기는 다른 테이블의 REF 관계 결과를 바꿀 수 없다. 재현 시나리오를 구성하지 못했다 — **코드상 위험(잠재), 재현 실패**로 남긴다. 재확인 기능·H2 잠금 시간은 바꾸지 않았다.

### 19.8 R1 계약 '지우는 중인 PK 를 참조한 저장 = 관계 없이 성공' 검토 (R2-8)

기존 정책과 같다 : 참조 테이블명은 정의이고 해석되지 않거나 PK 가 하나가 아니면 관계가 생기지 않을 뿐 저장은 받는다 (엑셀 `없는 테이블은 예전처럼 허용한다 (관계가 생기지 않을 뿐)`, `referencedPk` 가 null). 관계 없는 참조는 테이블 모델의 `unresolvedReferences`(물리 모델 화면)에 보이고, DEC-09 진단(`ModelStructureDiagnosticService.foreignKeys`)이 참조 테이블명 자체를 판정해 `FK_TARGET_NO_PK`(대상 PK 없음 — 지워진 PK 를 참조한 경우)·`FK_TARGET_COMPOSITE_PK`·`FK_TARGET_NOT_FOUND` 오류로 표시한다 (코드 확인 — 진단은 바꾸지 않았다).
참조 대상이 나중에 유효해지면(같은 이름의 PK 생김) 그 대상의 저장 때 동기화가 이 참조를 다시 맞춘다 (R1 `tableDeleteAndRecreate` 테스트). 명시적 FK 는 참조 테이블명이 있는 컬럼에 만들 수 없어(`buildRelation`) 섞이지 않는다. 새 계약을 만들지 않았다.

### 19.11 간헐 실패 재발 (PostgreSQL, 묶음 실행 1회 — `entityApprovalVsEdit`) — 원인 미확정

R2 중간 묶음 실행(`runs/…-r2-post2-pg`)에서 C2 `entityApprovalVsEdit` 가 재발했다. 결과는 보존했다. 이번에 처음 확보한 근거 :

- 진단(별도 연결 — C4b 에서 보완)에서 B 는 `wait_event_type=Lock` 상태로 20초 동안 논리 모델 행 잠금을 기다리고 있었다.
- PostgreSQL 로그(`log_lock_waits`)에 `process 512 still waiting for ShareLock on transaction … Process holding the lock: 369` 가 남았다 (369 = A 의 연결). 잠금은 A 가 시간 초과로 롤백한 뒤 20,095ms 만에 얻었다.
- 즉 **B 는 DB 밖에서 멈춘 것이 아니라 처음부터 A 를 기다렸고, A 쪽 감시가 그 대기를 감지하지 못한 것이다.** C4a 의 "B 가 DB 에 없었다" 는 판단(같은 트랜잭션 연결로 본 진단)은 틀렸다.
- 가설 '트랜잭션 안의 `pg_stat_activity` 스냅샷이 고정된다' 는 실험 두 번(B 의 연결이 감시 전부터 있는 경우 포함)에서 같은 트랜잭션의 반복 조회가 대기를 바로 봐 **기각**했다 (임시 실험 테스트는 지웠다. 결과는 `runs/…-r2-pgstat-probe*`).
- 원인은 확정하지 못했다. 다음 재발 때 감시 연결과 별도 연결의 잠금 대기 수를 함께 남기도록 진단을 보완했다 (`ConcurrencyDiagnostics.lockWaitCounts`). 시간 제한·단언·실행 순서는 바꾸지 않았고, 해결로 보지 않는다. `s4TwoRenames`(공용 ForkJoin 풀을 쓰는 다른 구조)는 이번에 재발하지 않았다.

### 20.3 엔터티 승인 구성 기준값 (C4c-D01)

- 대상 판단 : 엔터티 승인은 그 엔터티가 **직접 정의한 속성·식별자**를 함께 승인한다(승인된 엔터티는 승인 권한 없는 사용자가 속성·식별자를 고칠 수 없다 — `rejectApprovedDetail`). 그래서 엔터티만 구성 기준값을 받는다. 구성은 삭제 확인과 같은 `LogicalModelDto.Entity.composition` (`attributes`·`identifiers` 의 (ID, 수정 일시), 식별자 구성 변경은 식별자 수정 일시를 올린다 — M8-C2). 관계·매핑·주제 영역 분류·배치·상속 그룹은 넣지 않는다(각자 승인·기준값이 따로).
- **테이블 승인은 구성 기준값을 넣지 않았다** : 물리 컬럼·인덱스·제약조건·관계는 각자 승인되는 독립 단위다 (C4c-D01). 논리 모델에는 승인이 없다.
- 상세 조회(`GET /api/logical/entity/{id}`)가 `composition` 을 준다(목록·ERD 응답에는 없음 — null). 승인 `PATCH /api/logical/entity/{id}/approval/true?modifiedAt=&composition=` 은 composition 필수(승인 권한자에게만 — 권한 오류가 먼저), 승인 취소는 아무것도 새로 승인하지 않으므로 `modifiedAt` 만.
- 순서 (`LogicalModelService.updateEntityApproval`) : 승인 권한 → 모델 행 잠금(속성·식별자 추가·수정과 같은 잠금) → 다시 읽기 → 이미 그 상태면 그대로(예전 구성이어도 409 아님) → 엔터티 기준값 → (승인일 때만) 구성 → 기존 상속 승인 조건.

### 20.4 표준 사전 삭제 (C4c-D02)

`dictionary/service/DictionaryRowLocks.lockForDeletion` → 도메인·단어·용어 삭제 공통 :
1. **프로젝트 행 배타**(맨 먼저) — 표준 용어 등록·키를 바꾸는 용어 수정·도메인 등록(DICT-2·M-5 5차)이 같은 행을 먼저 잡으므로, 참조 검사부터 삭제까지 새 참조가 끼어들지 않는다 (`deleteWhileNewReference` : A 의 용어 등록 커밋 뒤 B 는 참조를 보고 `RELATION_EXISTS`).
2. 지울 행 `FOR UPDATE NOWAIT` (ID 오름차순, 1,000 개씩) — 프로젝트를 쥔 뒤에는 기다리지 않는다(ModelRowLocks 규칙 — 모델 쓰기가 그 용어의 FK 검사 KEY SHARE 를 쥔 채 커밋 때 프로젝트 공유 잠금을 기다리므로 기다리면 교착). 바쁘면 409.
3. 다시 읽기(`refresh`) → 승인된 도메인·단어 거절(기존 400) / 승인된 용어는 예전처럼 건너뜀 → **화면이 본 `modifiedAt` 비교 409** (행별 문구) → 참조 검사 → 삭제. 하나라도 거절되면 전체 롤백, 없는(다른 프로젝트·이미 지운) 행은 예전처럼 건너뜀.
- 용어 삭제에 **물리 컬럼 참조 검사** 추가 (`RELATION_EXISTS` — 예전 500).
- HTTP `DELETE /api/deleteDataDictionary/{standardDomains|standardWords|standardTerms}` 본문 행마다 `modifiedAt` 필수 (목록 조회가 이미 주는 값 — 화면은 체크한 행을 그대로 보낸다).
- 반대 순서 일괄 삭제끼리는 프로젝트 행에서 차례로 — 교착 없음 (`oppositeOrderBulkDelete` : 둘 다 OK, 늦은 쪽은 이미 없는 행을 건너뜀).

### 20.5 원본 매핑 해제 (C4c-D03)

- 매핑 변경(`mapTable`·`confirmColumn`)은 같은 행을 고쳐 쓴다(다른 모델 TABLE·컬럼으로). 그래서 해제는 매핑 행 수정 일시를 기준값으로 받는다 : `DELETE /api/sourceMapping/tables/{mappingId}?modifiedAt=`, `DELETE /api/sourceMapping/renames/columns/{id}?modifiedAt=`, 스키마는 `DELETE /api/sourceMapping/schemas/{sourceSchemaId}?modifiedAt=&composition=` — composition = 함께 해제하는 그 원본 스키마의 TABLE 매핑(예외 제외)의 (ID, 수정 일시) (M8-D01 하위 구성 규칙). 목록 응답(`SchemaRow.modifiedAt/composition`, `TableRow.modifiedAt`, 컬럼 매핑 `modifiedAt`)이 준다.
- 순서 : 기준 연결 행 배타(`lockBase` — 매핑 쓰기 공통 잠금, 기존) → 매핑 행 → 기준값 → (스키마) 구성 → 해제. 지우고 다시 만든 매핑은 새 ID 라 예전 요청은 '찾을 수 없음'(400 `SOURCE_MAPPING_INVALID`), 다른 프로젝트 매핑도 같다.
- 매핑 예외 : 해제 대상이 아니다(예외 행 ID 로 TABLE 해제 → 400). 예외 추가·취소는 스키마 해제 구성에 들지 않는다. **예외 취소에는 기준값을 넣지 않았다** — 예외 행은 고쳐 쓰지 않으므로(취소 = 삭제, 다시 만들면 새 ID) ID 만으로 같은 행이다.
- 서비스의 기준값 없는 오버로드는 내부 호출용(null = 비교 생략, M8-C2 와 같은 규칙).

### 20.6 승인된 표준 단어 직접 수정 차단 (C4c-D04)

`StandardWordService.updateStandardWords` : 행 잠금(M8-C1) → 없음 → **승인된 단어 `APPROVED_DATA_CANNOT_BE_UPDATE`** (기준값 비교보다 먼저 — 도메인 M8-D03 과 같은 순서) → 기준값. 금칙어는 별도 API 가 없는 이 수정의 한 칸이라 승인된 단어의 금칙어도 승인 취소 → 수정 → 재승인 절차다 (금칙어 정책 자체는 바꾸지 않음). 엑셀 단어 업로드·등록은 바꾸지 않았다.

### 20.7 도메인 승인 취소 영향 범위 (C4c-D05)

- 승인 취소는 예전처럼 도메인 승인 여부만 바꾼다 — 참조 용어·속성·컬럼과 그 승인 상태는 그대로 (`domainRevokeImpact`).

### 21.3 C4c-2B 잠금 충돌 ↔ 데이터 변경 충돌 구분

- 응답 : 기존 `{status, code, message}` 에 **선택 칸 `reason`** 만 더했다 (`GlobalExceptionHandler.ErrorResponse`, `@JsonInclude(NON_NULL)` — 원인이 없으면 칸 자체가 없다). HTTP 상태·오류 코드는 그대로라 기존 클라이언트·테스트와 호환된다.
- 서버 : `CustomException.locked(code, message)` = 원인 `LOCKED`. 실제로 NOWAIT 잠금 실패(PostgreSQL 55P03 · H2 50200)가 확인된 곳에서만 쓴다 — `ModelRowLocks.busy()`(모든 `noWait`·키 강도 잠금·`ObjectNamespace.lockNoWait`), `DictionaryRowLocks`(문구 '다른 작업이 같은 표준 사전 항목을 처리하는 중'), `PhysicalGenerationService`·`PhysicalNameRenameService`·`SourceImportService`·`SourceDeletionService`(코드는 각자 그대로 — `MODEL_CONFLICT`/`SOURCE_COMPARE_STALE`). 잠금 실패의 문구에서 'MODEL_CONFLICT 공통 문구(다른 사용자가 먼저 수정했습니다)' 접두를 뺐다.
- **잠금 실패가 아닌데 `busy()` 를 쓰던 3곳**은 원인 없는 409 로 바꿨다 (`ModelRowLocks.changedMeanwhile()`) : 컬럼 삭제·일괄 저장에서 잠근 뒤 PK 구성이 달라진 경우 2곳(D11·R2), REF_COLUMN 동기화가 세 번 다시 계산해도 대상이 바뀐 경우 1곳 — 모두 데이터가 바뀐 것이다. 대기형 잠금(`lockBase`·모델 행 잠금 등) 뒤의 기준값 불일치도 원인 없음 (원인을 모르는 409 를 잠금으로 분류하지 않는다).
- 화면 : `isLocked(error)` (409 + reason LOCKED), `isConflict()` 는 잠금 충돌을 뺀다 → 복구 화면(비교·재적용)으로 가지 않고, 공통 알림이 '다른 작업이 같은 데이터를 처리하고 있어 이번 요청을 처리하지 못했습니다 · 입력과 처음 기준은 그대로 · 같은 버튼으로 직접 다시 시도 · 그 사이 바뀌었으면 변경 확인으로 안내' 를 보인다 (`app/App.tsx` `ApiErrorBridge`). 기준값은 바꾸지 않으므로 다시 시도가 실제 변경을 만나면 데이터 변경 409 → 기존 복구 흐름 (`lockedVersusChanged` : LOCKED → 잠금 해제 뒤 같은 기준값 → 원인 없는 409 → 최신 기준값 → 성공). 요청 중 중복 제출은 기존 `useSubmitting`.
- 이번 실행의 실제 원인 (H2·PostgreSQL 같음) : 도메인 수정 ↔ 삭제, 단어 승인 ↔ 삭제, 용어 승인 ↔ 삭제, 스키마 행 잠금 ↔ 이름 변경 = `MODEL_CONFLICT:LOCKED`; 속성 추가 ↔ 엔터티 승인, TABLE 매핑 변경 ↔ 해제 = 기다린 뒤 원인 없는 `MODEL_CONFLICT`. C4c-1 테스트 2건의 기대값을 이 정확한 값으로 고쳤다.

### 21.4 C4c-2C 표준 사전 삭제 충돌 복구

`DataDictionaryPage` 삭제가 승인과 같은 `runListWithReview` 를 쓴다 : 처음 요청은 체크한 행의 기준값, 409 면 바뀐 행만(승인 상태·수정 일시) 보여 주고 '선택한 N건 중 바뀐 항목만' 안내, [최신 내용으로 삭제] 는 선택 전체를 최신 기준값으로 다시 보낸다. 최신에서 **승인된 항목**이 있으면(`block`) 그 항목만 빼고 지우지 않고 선택을 바꾸라고 안내, 없어진 항목도 막는다 (기존). 새 참조가 생긴 항목은 다시 삭제할 때 서버 400 이 공통 알림으로 보이고 대화상자는 그대로. 잠금 충돌·참조 제한 뒤에는 목록을 다시 읽지 않아 체크 선택이 남는다.

### 21.5 C4c-2D 원본 매핑 해제 충돌 복구

- TABLE·컬럼 : `runWithReview` — 확인한 매핑(모델 TABLE·상태 / 원본 컬럼·모델 컬럼) ↔ 최신. 매핑이 해제되었거나 다시 만들어져 ID 가 다르면 다시 해제할 수 없다(목록에서 다시), 지금 예외 상태면 막는다. 최신 조회는 기존 목록 API (`/tables?sourceSchemaId&keyword`, `/renames/columns`).
- 스키마 : [해제] 를 누르면 그 원본 스키마의 TABLE 매핑 목록을 기존 목록 API 로 읽어(500 씩) 확인 창에 보여 주고(최대 10줄 + 외 n개), 그 상태의 `modifiedAt`·`composition` 으로 해제한다. 409 면 TABLE 매핑마다 한 줄 (`table:<원본 TABLE ID>`) — 처음 확인한 하위 매핑 수 · 최신 수, 추가된 줄('없음 (새로 추가됨)'), 없어진 줄('삭제됨'), 바뀐 줄(다른 모델 TABLE). 구성 기준값만 다르고 보이는 줄이 같으면 '목록에 보이지 않는 TABLE 매핑(원본에서 사라진 TABLE 의 매핑 등)이 바뀌었다' 고 따로 안내한다 — 해시만 비교해 숨기지 않는다. 새 비교 API 없음.
- 공통 : `snapshotRows` 가 최신에만 있는 줄도 보이게 넓혔다 (`fields[].removable` — 없어진 하위 항목은 '삭제됨').

### 21.6 C4c-2E 도메인 승인 취소 영향 안내

`features/dictionary/domainImpact.tsx` : 도메인 탭의 승인 취소는 확인 창 대신 영향 범위 대화상자 — 지금 승인된 선택 도메인만 `/api/dictionaryUsage/domain/{id}/impact` 를 10개씩 조회, 도메인마다 '직접 참조 표준 용어 n개 (승인 m개) · 간접 참조 논리 속성 · 간접 참조 물리 컬럼 n개 (승인 m개)' — 종류를 합치지 않는다. '승인을 취소해도 참조와 그 승인 상태는 유지, 참조는 삭제되지 않는다' 를 먼저 보인다. 조회가 끝나야 [승인 취소] 가 보이고, 실패는 0 이 아니라 실패 문구 + [다시 조회]. 취소 자체는 기존 계약 (기준값·권한·잠금, 영향 수로 거절하지 않음). 일괄 조회 API 는 만들지 않았다 (선택이 많으면 도메인마다 요청 — 한 페이지 최대 100건, 10개씩 나눠 보낸다).

### 21.7 C4c-2F 승인된 표준 단어 수정 화면

수정 진입점은 상세 대화상자의 [수정] 하나이고, 승인된 항목(단어·도메인·용어)에는 이미 보이지 않았다 (`DataDictionaryPage.onRowClick`, '승인된 항목은 수정할 수 없습니다'). 일괄 수정·엑셀 수정 경로는 없다 (엑셀은 등록). 이번에 더한 것 : 수정 폼을 연 사이 다른 사용자가 승인하면 서버 400 `APPROVED_DATA_CANNOT_BE_UPDATE` 뒤 폼에 '다른 사용자가 이 항목을 승인했습니다' 안내와 저장 잠금 — 입력은 그대로, 승인을 자동으로 취소하지 않는다 (`DictionaryForm`, 도메인·용어에도 같은 동작).

### 21.8 C4c-2G 나머지 모델링 화면

| 화면 | 이전 | 이번 |
|---|---|---|
| 주제 영역 저장 | 공통 알림 | `useConflictRecovery` (이름·상위·설명·순서, 없어지면 저장 잠금) |
| 주제 영역 분류 변경 | 공통 알림 후 닫고 선택 초기화 | `runListWithReview` (엔터티마다 확인한 영역 ↔ 지금 영역, [최신 소속으로 다시 분류] 가 지금 소속을 기대값으로), 잠금 충돌이면 대화상자·선택 유지 |

### 21.9 C4c-2H 엔터티 승인 구성 검토

`entitySnapshot` 이 속성·식별자를 이름 이어 붙이기 대신 **한 줄씩** 비교한다 (속성 : 이름·유형·필수·용어·설명, 식별자 : 주/보조·구성 속성). 승인 검토에서 구성이 바뀌면 '승인하면 함께 승인되는 속성·식별자가 바뀌었다 — 바뀐 줄을 검토한 뒤 다시 승인할지 정하고, 닫으면 상세 화면이 최신 구성으로 바뀐다' 를 보인다. [최신 내용으로 승인] 은 사용자가 검토 뒤 누르는 명시적 선택이다 (최신 composition 으로 조용히 다시 보내지 않는다). 승인 취소는 기존 (modifiedAt 만), 범위(직접 정의 속성·식별자)도 그대로.

### 21.10 C4c-2I 수정 일시 표시 정밀도

`lib/format.formatTimestampPrecise` : 서버 기준값 문자열(LocalDateTime, 시간대 없음)을 Date 로 바꾸지 않고 `yyyy-MM-dd HH:mm:ss` + 서버가 준 소수 자리 그대로 (예 `2026-11-24 15:30:42.123456`) — 반올림·가짜 정밀도·시간대 변환 없음. 충돌 비교 표(`modifiedAtRow`), 목록 검토(`runListWithReview`), 컬럼 일괄 편집 충돌 비교에 적용. 기준값으로는 원문을 그대로 보낸다. 일반 목록 표시는 그대로. ERD 배치 충돌은 배치 버전 번호로 비교해 수정 일시를 보이지 않는다 (해당 없음).

| 컬럼 매핑 확정·변경 `PUT /api/sourceMapping/renames/columns` | 같은 원본 컬럼의 기존 행을 고쳐 씀 → 코드상 같은 위험 (화면 후보는 미매핑 컬럼뿐) |
| TABLE 이름 변경 확정 `PUT …/renames/table` | 기존 정책으로 보호됨 (원본이 사라진 매핑만 옮기므로 두 번째 요청은 400) |
| 매핑 예외 ↔ 등록 | 기존 정책으로 보호됨 (예외 원본은 400 — 재현 확인) |
| 매핑 ↔ 모델 TABLE 삭제 | 기존 정책으로 보호됨 (없는 모델 TABLE 400) |
| 매핑 ↔ 원본 재수집 | 재수집은 매핑 행을 고치지 않는다 (C4c-2 `unmapAfterRecollect`) |
| 일괄·자동 매핑 | 해당 기능 없음 (후보는 제안뿐, 확정은 한 건씩) |

**수정 전 재현** (임시 재현 테스트, 결과 보존 후 삭제 — H2·PostgreSQL 같음, `runs/…final-repro-*`) : TABLE 재지정 ↔ 재지정 = B OK·A 의 변경 사라짐, 신규 등록 ↔ 신규 등록 = 나중 요청이 덮어씀, 해제 ↔ 오래된 재지정 = 새 행으로 재생성, 스키마 매핑 등록 ↔ 등록 = 덮어씀, 예외 ↔ 등록 = 400 (보호됨).

**수정** : 요청 DTO 에 선택 칸 `mappingId`·`modifiedAt` (화면이 본 그 원본의 기존 매핑 행 — 없었으면 둘 다 null = 신규 등록). `SourceMappingService.verifyMappingBase` : 화면이 매핑을 보지 않았으면 지금도 없어야 하고, 보았으면 지금 그 행(같은 ID — 지우고 다시 만든 행은 다른 행)이고 수정 일시가 같아야 한다, 아니면 409 `MODEL_CONFLICT` (문구 4종 — 그 사이 매핑됨 / 해제됨 / 다시 만들어짐 / 바뀜). 지금 그대로 같은 대상이면 덮어쓸 것이 없어 통과(멱등). 잠금은 기존 기준 연결 행 배타(`lockBase`) 그대로, 예외 원본 거절이 기준값보다 먼저(예외 정책 그대로). HTTP 는 `mappingId` 만 있고 `modifiedAt` 이 없으면 400 `MODEL_BASE_REQUIRED`, 기준값 칸이 없는 예전 요청은 '신규 등록'으로 보므로 기존 매핑을 덮어쓰지 않는다(409). 서비스의 두 인자 오버로드는 내부 호출용이고 운영 코드는 부르지 않는다 (소스 검사 테스트에 추가). 실패한 요청은 매핑 이력을 남기지 않는다 (테스트로 확인).

**화면** : 스키마·TABLE 매핑 확정은 화면에 보인 행의 기준값을 보내고, 409 면 `runWithReview` — 확인한 매핑 ↔ 최신 매핑, '내가 고른 대상' 안내, [최신 매핑에서 다시 정하기]. 본 매핑이 해제되었거나 다시 만들어졌으면 막는다(오래된 변경을 신규 등록으로 바꾸지 않음), 예외 상태면 막는다. 모델 TABLE 고르기 대화상자가 이름도 넘긴다. 컬럼 확정(후보 = 신규 등록)은 409 면 공통 알림 뒤 후보를 다시 읽는다.

### 22.3 FINAL-B 동시성 계약 최종 점검

- 기준값을 받는 쓰기 HTTP 핸들러 46개 모두 필수 검사(`ModelBase.require` 등)가 있다 (조사 스크립트). 기준값 없는 내부 오버로드는 운영 코드에서 부르지 않는다 (`noProductionCallerOfBaseLessOverloads`, 원본 매핑 등록·재지정 패턴 추가).
- 승인·삭제 구성 기준값 범위는 그대로 (엔터티 승인 = 직접 정의 속성·식별자, 테이블은 독립 승인, 스키마 해제 = 하위 TABLE 매핑, 승인 취소는 modifiedAt 만, 일괄 요청 전체 롤백, 승인 멱등).
- 변경 이력 : 모델 변경 이력은 커밋 직전 같은 트랜잭션에 기록되므로 409 로 롤백된 요청은 남지 않는다 (C1~C4 통합 테스트의 이력 단언), 원본 매핑 이력도 같다 (FINAL 테스트 `schemaAndHttpContract`·`SourceSyncIntegrationTest` 이력 단언). 요청 로그(TB_LOG)는 실패한 요청도 상태 코드와 함께 남긴다 (기존 정책 — 브라우저 검증 중 S1 원인 분석에 사용).
- 권한·격리 : 다른 프로젝트 매핑 ID·기준값 재사용은 409/400 (테스트), 권한 변경 시 세션 만료 (브라우저 S7-3).

### 22.4 FINAL-C 잠금 체계 최종 점검

코드 변경 없음. 18·19장 (REF_COLUMN·PK 구성 변경 — 실제 PK 구성 변경만 구조 변경 경로, PK 없는 대상 KEY SHARE, 반복 잠금의 작은 ID NOWAIT, 명시적 FK 유지, H2 커밋 직전 재확인, 엑셀 등록 전용) · 20.4 (`DictionaryRowLocks`) 그대로. `DictionaryRowLocks` 호환성 : 삭제는 프로젝트 행 배타를 **맨 먼저** 잡고 그 뒤에는 NOWAIT 만 쓴다 — 용어 등록·키 변경 수정·도메인 등록은 같은 프로젝트 행을 먼저 잡아 차례로 지나가고, 모델 쓰기(속성·컬럼의 표준 용어 참조)는 행을 쥔 채 커밋 때 프로젝트 공유 잠금을 기다리므로 삭제가 그 행을 NOWAIT 로 만나면 즉시 409 LOCKED 로 끝나 순환 대기가 생기지 않는다 (C4c-1 동시 테스트, 이번 브라우저 L1·L2 실측). 다중 행 잠금은 ID 오름차순·중복 제거(TreeSet), 잠근 뒤 다시 읽기, 일괄 전체 롤백 그대로.

### 23.2 원인 (결정적 재현으로 확인)

PostgreSQL 은 한 트랜잭션 안에서 `pg_stat_activity` 의 **백엔드 목록**을 처음 읽은 때로 고정한다. 목록에 있던 백엔드의 대기 상태(`wait_event_type`)는 읽을 때마다 새로 보이지만, 첫 조회 뒤에 연결된 백엔드는 그 트랜잭션이 끝날 때까지 보이지 않는다 (`pg_stat_clear_snapshot()` 을 부르면 다시 읽는다).

M-8 의 감시(`awaitDoneOrLockWait`)는 A 의 트랜잭션(`tx.execute`) 안에서 A 와 같은 연결로 `pg_stat_activity` 를 2ms 마다 읽는다. B 가 풀에 이미 있던 연결을 쓰면 B 의 대기가 보이지만, 풀이 다 쓰여 B 가 **새 연결**을 열면(그 새 백엔드는 A 의 첫 조회 뒤에 생겼다) A 의 연결에서는 끝까지 보이지 않아 20초 뒤 실패한다. 실패 때 진단의 Hikari 는 매번 `active=6 idle=0` 이었다 — 테스트 묶음·컨텍스트 수에 따라 풀 상태가 달라져 간헐적이었다.

| 조건 (PostgreSQL 18.6) | 같은 트랜잭션 재조회 | 다른 연결 | 같은 연결에서 `pg_stat_clear_snapshot()` 뒤 |
|---|---|---|---|
| psql, B 가 A 의 첫 조회 뒤 접속 | 0 | 1 | 1 |
| JDBC(Spring 트랜잭션, 같은 pid·같은 `now()`·같은 xid 확인), B 가 첫 조회 **전부터 있던** 연결 | **1** | 1 | 1 |
| JDBC, B 가 첫 조회 **뒤 새로 연** 연결 | **0** | 1 | 1 |

19.11 의 탐침이 가설을 '기각' 한 것은 B 의 연결이 감시 전부터 있던 조건(두 번째 줄)만 봤기 때문이다 — 같은 트랜잭션에서도 이미 목록에 있던 백엔드의 대기는 보인다. 그 결론은 그 조건에서는 맞았고, 원인은 '스냅숏이 통째로 고정' 이 아니라 '목록이 고정' 이었다. 같은 pgJDBC 문장을 10번 되풀이해도(서버 준비문 전환) 결과는 같았다 — 준비문은 원인이 아니다.

### 23.3 수정 (테스트 코드만)

- `ConcurrencyDiagnostics.lockWaitCount(jdbc, sql, postgres)` : `JdbcTemplate.execute(ConnectionCallback)` 로 **같은 연결**(트랜잭션 안이면 그 트랜잭션에 묶인 연결)을 받아 PostgreSQL 이면 `select pg_stat_clear_snapshot()` 뒤에 감시 sql 을 실행한다. H2 는 sql 만 (PostgreSQL 함수를 부르지 않는다). 감시 조건·20초 제한·단언·대기 간격은 그대로.
- 진단 `lockWaitCounts` 에 '호출 연결(스냅숏 초기화 뒤)' 값을 더했다.
- 대기 시간 늘리기·재시도·제외·실행 순서 고정·sleep 추가·격리 수준이나 잠금 정책 변경은 하지 않았다.
