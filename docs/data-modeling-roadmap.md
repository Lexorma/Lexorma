# Lexorma 데이터 모델링 로드맵

> **상태: 계획 문서.** 이 문서의 신규 기능(ERD, 논리 모델, 모델 비교 등)은 **아직 구현되지 않았다.** "현재 구현 상태"는 작성 시점(2026-11)의 저장소 코드로 확인한 내용이다.
>
> Lexorma 는 **Data Modeling, Standardization & AI Metadata Management Platform** 을 지향한다. AI 는 모델링·메타데이터 관리를 대체하지 않고, 그 품질과 생산성을 높이는 **보조 계층**이다.

**경계 규칙**

- **원본 DB 에서 수집한 사실(원본 카탈로그·스냅샷)** 은 AI 로드맵(AI-1, AI-2)이 정의하고, 이 문서는 그것을 **모델로 가져오고 비교·시각화하는 방법**을 정의한다.
- **관계 유형(실제 FK / 추정 / 승인)의 저장 모델과 ERD 표시**는 이 문서(M-1, M-3)가, **관계를 추정하는 AI·규칙 로직**은 AI 로드맵(AI-12)이 담당한다.
- 표준화 **규칙과 데이터**는 이 문서(M-5)가, 그 규칙을 실행하는 **품질 검사 체계**는 AI 로드맵(AI-6~9)이 담당한다.

## 2. React 전환의 의미

Thymeleaf·jQuery 서버 렌더링을 React + TypeScript + Vite(CSR)로 바꾼 것은 **기존 화면의 UI 마이그레이션**이며, ERD·모델링 기능의 구현을 뜻하지 않는다. 전환의 후속 목표는 다음을 가능하게 하는 것이다.

- 대규모 DB 구조의 인터랙티브 시각화, ERD 기반 모델링(드래그 앤 드롭 편집)
- 테이블·컬럼 관계 탐색, 구조 변경의 시각적 비교
- 메타데이터 관리 화면과 ERD 간 이동, AI 분석 결과의 시각적 표현

| 구분 | 상태 | 근거 |
|---|---|---|
| 기존 화면의 React 전환 (로그인·회원가입·내 정보, 대시보드, 공지, 사용자·프로젝트·시스템 로그, 데이터 사전, 테이블·컬럼 관리, 도움말) | **완료** — 로드맵에 다시 등록하지 않는다 | `lexorma-web/src/app/App.tsx`, `src/features/*` |
| 공통 UI (프론트 정의 컬럼 그리드, 다이얼로그, 반응형, 다크 모드) | 완료 | `components/grid/Grid.tsx`(TanStack Table), `components/dialog`, `styles/*` |
| ERD·다이어그램 라이브러리 | **미도입** | `lexorma-web/package.json` 에 그래프/다이어그램 의존성 없음 |
| ERD 화면, 논리 모델 화면, 모델 비교 화면 | **미구현** | — |

| 공백 | 현재 | 영향 |
|---|---|---|
| 관계 모델 | FK 는 `ColumnInfo.refTableName`(참조 테이블명 문자열)뿐. 참조 컬럼은 DDL 생성 시 참조 테이블의 PK 로 추정 | ERD 관계선·복합 FK·관계 유형 구분 불가 |

| 사용 현황 화면 | 삭제 차단만 있고 조회 화면 없음 | 단어·용어·도메인 영향 파악 어려움 |

## 4. 개념 모델과 핵심 결정

### 4.1 모델 계층

```text
논리 모델 (M-6)             물리 모델 (기존 TableInfo/ColumnInfo 확장)        원본 카탈로그 (AI-1, AI-2)
엔터티 ─ 속성 ─ 관계   ◀─매핑(M-7)─▶  테이블 ─ 컬럼 ─ 관계 ─ 인덱스/제약  ◀─비교(M-10)·가져오기(M-4)─▶  수집한 스키마·테이블·컬럼·FK·인덱스·COMMENT
   │                                    │                                       (원본 DB 의 사실, 읽기 전용)
   └── 표준 용어·도메인 (기존 데이터 사전) ──┘
```

- **물리 모델 = 현재의 테이블·컬럼 관리 데이터**를 확장한다(새로 만들지 않는다). DDL 생성은 이 모델을 기준으로 한다.
- **원본 카탈로그**는 외부 DB 에서 수집한 사실이며 물리 모델과 **별도로 저장**한다(AI 로드맵 U-03 권고와 같음). 사용자가 선택해 물리 모델로 **가져오기**(M-4)하거나, 물리 모델과 **비교**(M-10)한다.
- 모든 생성·수정·삭제는 **Lexorma 내부 모델에 대한 작업**이다. 원본 DB 에 DDL 을 실행하지 않는다.
- 원본 카탈로그는 **외부 DB 연결별**로 존재한다(프로젝트 1 : 연결 N, 식별 구조는 [AI-1](ai-metadata-roadmap.md#1단계-메타데이터-모델-보강--변경-이력--상세-설명-분리)). 물리 모델 하나가 여러 연결(개발·운영 등)과 비교·매핑될 수 있으며, 그 관계는 D-17 에서 정한다.

**생명주기 — 서로를 자동으로 덮어쓰지 않는다**

| 데이터 | 누가 바꾸는가 | 언제 바뀌는가 | 이력 | 다른 데이터에 미치는 영향 |
|---|---|---|---|---|
| 원본 카탈로그·스냅샷 | 수집(AI-2) | 사용자 최신화 요청 시 (`COMPLETED` 만 확정) | 스냅샷·변경분 (AI-1) | 물리 모델을 바꾸지 않는다. 비교 결과(M-10)·재검토 표시(AI-5)만 만든다 |
| 물리 모델 | 사용자 (관리 화면, ERD 편집 M-8, 가져오기 M-4) | 사용자 저장 시 | 편집 이력 (M-9) | 원본 DB 에 반영하지 않는다 (DDL 은 출력만) |
| 논리 모델 | 사용자 (M-6) | 사용자 저장 시 | 편집 이력 (M-9) | 매핑(M-7)으로 물리 모델과 연결, 자동 변경 없음 |
| AI 결과 (설명·관계·개선안) | AI 생성 → 사용자 승인 | 생성 시 제안, 승인 시에만 반영 | 제안·검토 이력 (AI-5, AI-9) | 승인 전 모델·데이터 사전에 영향 없음, 근거 버전 변경 시 재검토(AI-5) |
| ERD 레이아웃 | 사용자 (M-2, M-8) | 배치 저장 시 | 이력 없음(최신만) | 모델 데이터와 별도, 모델 이력을 만들지 않음 |

**변경 경로와 권한 — 섞지 않는다**

| 경로 | 바꾸는 대상 | 권한 (검토안) |
|---|---|---|
| 원본 최신화 | 원본 카탈로그·스냅샷만 | 연결 관리 권한 (프로젝트 관리자 이상, U-04) |
| 원본 → 물리 모델 가져오기 | 물리 모델 (사용자 확인 후) | 모델 편집 권한 |
| 모델 편집 | 물리·논리 모델 | 모델 편집 권한 (기존 테이블·컬럼 편집 역할) |
| AI 결과 승인 | 업무 설명·데이터 사전·모델 관계 | 기존 승인 권한 (`AuthUtil.isApprovalAvailable`) |

### 4.2 관계 유형 — 반드시 구분

| 유형 | 의미 | 출처 | ERD 표시(검토안) |
|---|---|---|---|
| **실제 FK** | 원본 DB 에서 수집한 FK | 원본 카탈로그 (AI-2) | 실선 |
| **모델 관계** | 사용자가 Lexorma 모델에서 정의한 관계 (DDL 의 FK 근거) | 물리 모델 (M-1, M-8) | 실선 + 모델 표식 |
| **추정 관계** | AI·규칙이 제안한 후보, 미승인 | AI-12 | 점선 + "추정" 배지, 기본 숨김 토글 |
| **승인 관계** | 추정 관계를 사용자가 검토해 모델에 반영 | 모델 관계로 전환, 출처 = 추정 | 모델 관계와 같은 선 + 출처 표시 |

**추정 관계는 실제 FK 로 취급하지 않는다.** 승인되어도 "원본에 FK 가 있다"는 뜻이 아니며, 원본 카탈로그의 실제 FK 와 섞이지 않는다.

### 4.3 불변 원칙 (AI 로드맵 2장과 공통)

- DDL **생성·출력**은 하지만 **실행**하지 않는다. 원본 DB 에 대한 쓰기 경로를 만들지 않는다.
- 역공학은 사용자 요청 시 Lexorma 의 내부 JDBC 수집 도구로만 수집한다(AI-2, 별도 서버 없음). ERD·모델·비교는 자체 DB 만 읽는다.
- AI 가 만든 관계·표준 용어·설명은 승인 전에는 모델·데이터 사전에 확정되지 않는다.
- **독립성:** 원본 DB·Ollama 가 없어도 저장된 메타데이터·모델·ERD·표준화·데이터 사전은 그대로 관리할 수 있다. 없는 기능만 "사용 불가"로 안내한다.

## 6. 단계별 상세

각 단계는 `목적 / 현재 구현 상태 / 작업 범위 / 기존 코드 재사용 가능성 / 기술적 고려사항 / 선행 작업 및 의존성 / 완료 조건 / 테스트 및 검증 시나리오 / 우선순위 / 미확정 사항` 순서로 적는다.

### M-0. ERD 기술 검토·라이브러리 선정

- **목적:** 인터랙티브 ERD(탐색·배치·편집)를 만들 렌더링·레이아웃 방식을 정한다. 정적 이미지 생성보다 React 에서 직접 조작하는 UI 를 우선 검토한다.
- **현재 구현 상태:** PoC 검증 완료(2026-11-10). 운영 화면 변경 없음, PoC 는 `lexorma-web/poc/erd`(별도 Vite 진입점, Mock 데이터, `devDependencies` 고정 버전). 상세는 [M-0 결과](erd-poc-m0.md).
- **작업 범위:**
  - 후보 비교(예시이며 사전 확정 아님): **React Flow**(노드·엣지 렌더링, 커스텀 노드로 테이블·컬럼 표현), **ELK.js**(계층·직교 레이아웃 엔진), **Dagre**(방향 그래프 레이아웃). 렌더링과 자동 레이아웃은 역할이 달라 **조합**으로 볼 수 있다.
  - 평가 기준: 수백~수천 테이블 렌더링 성능(가상화·축소 시 단순 표시), 테이블·컬럼 단위 커스텀 UI, 컬럼 단위 관계선 연결점, 드래그 앤 드롭, 자동 레이아웃 품질·속도(웹 워커 실행 가능 여부), 저장된 레이아웃 복원, 다크 모드·기존 Primer 스타일 적용, 번들 크기, **유지보수 상태와 라이선스**.
  - 300·1,000·3,000 테이블 규모의 시제품(PoC)으로 측정.
- **기존 코드 재사용 가능성:** 디자인 토큰(`--gh-*`, 다크 모드), 아이콘(`@primer/octicons-react`), TanStack Query(데이터 조회).
- **기술적 고려사항:** 프론트엔드 의존성은 `package.json` 에 정확한 버전으로 고정한다. 라이선스는 도입 시점에 각 패키지에서 확인한다(예: 레이아웃 엔진 중 MIT 가 아닌 라이선스가 있을 수 있음). 런타임 외부 네트워크 없이 번들에 포함한다.
- **선행 작업 및 의존성:** 없음.
- **완료 조건:** 비교 결과·측정값·선정 사유가 이 문서(10장)에 기록되고, 선정 조합으로 M-2 의 최소 시제품이 동작한다.
- **테스트 및 검증 시나리오:** 규모별 초기 렌더링·줌/이동 프레임, 자동 레이아웃 소요 시간, 레이아웃 저장 → 새로고침 후 복원, 다크 모드 표시.
- **우선순위:** P1
- **미확정 사항:** D-01 (라이브러리 조합), D-02 (대규모 ERD 표시 전략)
- **PoC 결과 (2026-11-10, [상세](erd-poc-m0.md)):**
  - 권고 조합: **React Flow(`@xyflow/react` 12.12.0) + ELK.js(0.12.0, layered, 공식 Web Worker)**. 대안 Dagre(`@dagrejs/dagre` 3.1.1)는 어댑터 교체로 바꿀 수 있게 분리.
  - 자동 레이아웃(워커, headless Chrome / Apple M1): ELK 0.30·0.75·3.5초, Dagre 0.13·0.86·15.0초 (300·1,000·3,000 테이블). 워커 실행 중 프레임 16.7ms 유지(UI 멈춤 없음), 메인 스레드 실행 시 같은 시간만큼 멈춤.
  - 렌더링(3,000): 기본 DOM 220,103·힙 145MB·이동 20fps → 화면 밖 생략 + 축소 시 단순 표시로 DOM 11,585·힙 43MB·이동·드래그 60fps. 전체 개요 줌은 13fps, 계층 배치는 허브 테이블 때문에 매우 길쭉함 → 전체 표시보다 부분 로딩이 기본.
  - 기능: 테이블·컬럼 노드, 컬럼 단위 관계선(전 규모 100% 정위치), 자기 참조·순환·복합 FK, 관계 유형 4종 시각 구분, 검색·포커스, 레이아웃(X·Y·Zoom·Viewport) 저장·복원(새로고침 포함), 다크 모드 확인.
  - 남은 확인: ELK EPL-2.0 고지 방식, 실데이터·저사양 PC·Safari/Firefox 측정, 수동 휠 체감(**미측정**).
  - 완료 조건 중 "선정 조합으로 M-2 의 최소 시제품 동작"은 Mock 데이터 PoC 로 확인했고, 실제 API 연동은 M-2 범위다.

### M-1. 물리 모델 보강: 스키마·관계·인덱스/제약

- **목적:** ERD·역공학·비교의 기반이 되도록 물리 모델이 관계·스키마·인덱스를 표현하게 한다.
- **현재 구현 상태:** 기반 모델·API·DDL·V2 마이그레이션 구현. 스키마·FK 컬럼 쌍·복합 인덱스·UNIQUE/CHECK 를 저장한다. 화면 UI 와 아래 후속 안정화·단기 검증은 남아 있다.
- **작업 범위:**
  - **관계 엔티티**: 원본 테이블·컬럼 ↔ 대상 테이블·컬럼(복합 키 지원), 관계 이름, 카디널리티(선택), **유형·출처**(4.2). 기존 `refTableName` 데이터의 이전(마이그레이션) 방안.
  - **스키마(또는 네임스페이스)** 속성: 프로젝트 안 테이블의 소속. 기존 데이터는 기본 스키마로 이전.
  - **인덱스·제약조건**: 복합 인덱스, 유니크 제약, (DBMS 지원 범위의) CHECK. 기존 boolean 과의 호환.
  - 설명 분리(원본 COMMENT / 업무 설명)는 **AI-1** 과 같은 마이그레이션으로 설계한다.
  - `TableDdlGenerator` 가 새 관계·인덱스 모델을 쓰도록 확장(M-11 과 연계).
- **기존 코드 재사용 가능성:** `TableInfo/ColumnInfo` 엔티티와 화면, `refPkColumns` 계산 로직(관계 이전 시 참고), 대량 처리 패턴.
- **기술적 고려사항:** Flyway 를 PostgreSQL·H2 **양쪽**에 추가, `ddl-auto: validate`. 기존 테이블·컬럼 화면, 엑셀 업로드(`tableTemplate`, `columnTemplate`), DDL 결과가 회귀 없어야 한다. 대량 적재 대상 엔티티는 `SEQUENCE` id. 물리 모델 객체는 **내부 식별자**로 참조하고, 원본 객체와의 매핑(연결·스키마·이름)은 별도로 둔다 — 같은 이름의 테이블이 여러 연결·스키마에 있어도 모델이 섞이지 않는다(AI-1 식별 구조, U-24). 뷰 외의 DB 객체(Sequence, Trigger 등)는 초기 모델에 넣지 않는다([AI 로드맵 U-21](ai-metadata-roadmap.md#9-미확정-사항-종합)).
- **선행 작업 및 의존성:** 없음. AI-1(설명 분리·이력)과 한 번에 설계한다.
- **완료 조건:** 복합 FK·복합 인덱스·스키마를 저장할 수 있고, 기존 `refTableName` 기반 데이터가 관계로 이전되며, 기존 DDL 결과가 동일하거나 더 정확하다.
- **테스트 및 검증 시나리오:** 마이그레이션 전후 DDL 비교(기존 테스트 데이터), 복합 FK DDL 생성, 참조 테이블 삭제 시 관계 처리, 두 벤더 기동.
- **우선순위:** P1
- **미확정 사항:** D-03 (스키마를 프로젝트 하위 개념으로 둘지), D-04 (`refTableName` 유지·폐기)
- **구현 결과 (2026-11-10, [상세](physical-model-m1.md)):**
  - Flyway `V2__physical_model_schema_relation_index.sql`(postgresql·h2): `schema_info`(프로젝트 하위, 기본 스키마 `DEFAULT`), `table_info.schema_info_id`, `table_relation`/`table_relation_column`(복합 FK, 컬럼 순서), `table_index`/`table_index_column`, `table_constraint`/`table_constraint_column`(UNIQUE·CHECK). 기존 컬럼 값은 바꾸지 않는다.
  - 관계 유형(`FK`/`LOGICAL`)과 출처(`USER`/`REF_COLUMN`/`IMPORTED`/`AI_APPROVED`)를 별도 축으로 저장. 원본 DB 의 실제 FK 와 미승인 AI 추정 관계는 내부 모델에 넣지 않는다(4.2).
  - `refTableName` 은 단일 FK 약식 입력으로 유지하고, 참조 대상이 확정되는 경우(같은 프로젝트에 그 이름의 테이블 1개 + 단일 PK + 자기 PK 아님)만 관계(`REF_COLUMN`)로 이전·동기화. 모호·누락·PK 없음·복합 PK 는 이전하지 않고 값만 남긴다.
  - DDL: 기존 입력의 출력은 변경 전과 글자까지 동일(4개 DBMS 골든 파일), 비기본 스키마 접두어, 복합 UNIQUE·CHECK, 복합·고유 인덱스, 사용자 정의 복합 FK 추가. 다중 테이블 DDL·Export 는 M-11.
  - API: `/api/schema`, `/api/physical/**`(관계·인덱스·제약 등록·삭제·승인, 테이블 물리 모델 조회). 테이블 저장 API 에 선택 필드 `schemaId`.
  - 검증: PostgreSQL 18·H2 신규 설치(`ddl-auto: validate`)와 V1 → V2 업그레이드(불완전 데이터 포함), 프로젝트 격리·승인 제한·컬럼 삭제 정책 통합 테스트, 전체 테스트 284건 통과.
  - 남은 일: 스키마 관리(목록·등록·수정·삭제)와 테이블·컬럼 화면의 스키마 선택·표시 UI 는 **M-3**, 관계/인덱스 편집 UI 는 M-3·M-8, 다른 스키마 동명 테이블 허용·엑셀 템플릿 스키마 열은 아래 D-03 후속(P2), 카디널리티.

**M-1 후속 안정화·단기 검증 (미완료)**

기존 단계 ID 를 유지하고 M-1 안에서 관리한다. 아래 우선순위는 단계 전체의 완료 선언과 별개이며, 구현 결과의 284건 통과 기록이 단기 검증 완료를 뜻하지 않는다.

### M-2. ERD 조회 (물리 ERD)

- **목적:** 프로젝트·스키마별 물리 모델을 인터랙티브 ERD 로 탐색한다.
- **현재 구현 상태:** 구현 (조회 API·화면·사용자별 레이아웃). 검증 범위와 미검증 항목은 [M-2 기록](physical-erd-m2.md).
- **작업 범위:** 프로젝트·스키마별 ERD, 테이블 노드(컬럼·타입·PK/FK 표시), 관계선(유형별 표현, 4.2), 관련 테이블 탐색(N 단계 이웃 펼치기), 테이블 검색·필터(이름·스키마·승인 상태·마스터 여부), 확대·축소·이동, 노드 이동, 자동 레이아웃, 선택 테이블 상세 패널, 미니맵(검토), **레이아웃 최소 저장(노드 위치·줌·뷰포트)**.
- **기존 코드 재사용 가능성:** 테이블·컬럼 조회 서비스, 프로젝트 범위 필터, `MenuAuthorization`(새 메뉴), 다이얼로그·상세 화면 컴포넌트.
- **기술적 고려사항:**
  - ERD 용 **일괄 조회 API**(테이블·컬럼·관계를 한 번에, 페이지·스키마 단위) 신규. 대규모 프로젝트는 스키마·검색 결과 단위로 부분 로딩.
  - **레이아웃 저장 시점 (D-15, 권고: M-2 에서 최소 저장):** 노드를 옮길 수 있는데 새로고침하면 사라지면 예측하기 어렵다. M-2 에서 **노드 위치·줌·뷰포트만** 저장하고, 테이블·컬럼 변경은 M-8 에서 다룬다. 레이아웃은 모델 데이터와 **별도 저장**한다(예: `물리 모델 → 다이어그램 레이아웃 → 노드 위치·줌·뷰포트`) — 모델이 바뀌어도 레이아웃이 깨지지 않고(새 테이블은 자동 배치, 삭제된 테이블의 위치는 무시), 레이아웃 저장이 모델 편집 이력(M-9)을 만들지 않는다. 저장 단위(프로젝트 공유 / 사용자별)는 D-10. 저장하지 않기로 결정하면 "배치는 저장되지 않음"을 화면에 표시한다.
  - 새 API 는 `@PreAuthorize`, 메뉴 최소 역할은 페이지 역할과 API 역할 중 높은 쪽(`MENU_ROLES`).
- **선행 작업 및 의존성:** M-0, M-1.
- **완료 조건:** 기존 테이블·컬럼 데이터로 ERD 가 그려지고, 검색·필터·탐색·줌·자동 레이아웃이 동작하며, 다른 프로젝트 데이터가 보이지 않는다. 노드 이동 결과의 저장 여부가 D-15 대로 동작하고 사용자에게 예측 가능하다(저장 시 새로고침 후 유지).
- **테스트 및 검증 시나리오:** 관계 없는/순환 관계/자기 참조 테이블 표시, 1,000 테이블 규모 조회 응답 시간·렌더링, 권한 없는 역할 접근 차단, 다크 모드. 노드 이동 → 새로고침 → 위치 유지, 테이블 추가·삭제 후 기존 배치 유지와 새 테이블 자동 배치.
- **우선순위:** P1
- **결정 (M-2):** D-02 부분 로딩, D-05 데이터 관리 → 물리 ERD·VIEWER, D-10 사용자별, D-15 명시적 저장 버튼
- **M-3 연계:** ERD 의 스키마 선택은 기존 `GET /api/schema` 목록을 그대로 쓴다. 스키마 등록·수정·삭제 UI 와 그 결과의 ERD 반영(목록·필터 갱신)은 M-3 에서 다룬다.

### M-3. ERD ↔ 메타데이터 관리 연동

- **목적:** ERD 를 단순 그림이 아니라 메타데이터 관리의 진입점으로 만들고, 사용자가 스키마를 직접 관리하며 테이블을 스키마별로 다룰 수 있게 한다 (기본 스키마 관리).
- **현재 구현 상태:** 구현 (2026-11-11, [기록](physical-erd-m3.md)) — 스키마 관리 화면(`/schemaManage`), 테이블 관리의 스키마 열·필터·등록 시 선택, 컬럼 관리의 스키마 표시, ERD ↔ 테이블 관리·컬럼 관리·데이터 사전 이동, 기본 스키마 이름 고정, 권한 오류 코드 `SCHEMA_PERMISSION_DENIED`. 브라우저 화면 동작은 미검증이고, AI 생성 설명·추정 관계 표시(M-13)와 테이블 스키마 이동 UI 는 하지 않았다. 아래는 착수 전(M-1) 상태의 기록이다:
  - `TB_SCHM`(`SchemaInfo`) : 프로젝트 하위, 스키마명·설명·기본 여부. 프로젝트마다 기본 스키마(`DEFAULT`) 1개를 최초 요청 시 만든다(행 잠금, M-2 완료). DDL 은 기본 스키마 테이블에 접두어를 붙이지 않는다(이름이 아니라 기본 여부로 판단).
  - `GET /api/schema`(VIEWER, 기본 스키마 먼저, 기본 스키마가 없으면 만든다), `POST /api/schema`(등록·수정, `id` 유무로 구분), `DELETE /api/schema/{id}`. 변경 API 는 `USER` 역할 + 승인 권한(`AuthUtil.isApprovalAvailable()` : 관리자·매니저·프로젝트 관리자)만 통과한다.
  - 검증 : 이름 형식(`INVALID_SCHEMA_NAME`, 따옴표 없는 식별자·63자), 같은 프로젝트 대소문자 무관 중복(`SAVED_DATA_EXISTS`), 기본 스키마·테이블이 있는 스키마 삭제 거절, 다른 프로젝트 ID 거절(`SCHEMA_IS_NOT_DEFINED`).
  - 테이블 : 등록·수정 API 의 선택 필드 `schemaId`(없으면 등록은 기본 스키마, 수정은 현재 스키마 유지 — 값을 보내면 스키마 이동). 엑셀 업로드는 항상 기본 스키마.
  - 화면 : 물리 ERD 의 스키마 선택만 있다. 스키마 관리 화면, 테이블 관리의 스키마 선택·필터·표시, 컬럼 관리의 스키마 표시는 없다. 응답(`SchemaDto`)에 소속 테이블 수·생성/수정 정보가 없다.
- **작업 범위:**
  - **ERD ↔ 메타데이터:** 테이블 선택 → 상세(설명, 승인 상태, DDL), 컬럼 선택 → 데이터 사전(표준 용어·도메인·설명), 연관 테이블 탐색, 테이블·컬럼 관리 화면 ↔ ERD 상호 이동(선택 상태 유지), AI 생성 설명(AI-5)·추정 관계(AI-12)의 **표시만**(검토는 각 기능 화면).
  - **스키마 관리 UI (기본):**
    - 목록 : 현재 프로젝트의 스키마명·설명·기본 여부·소속 테이블 수·생성/수정 정보. 목록 API 에 테이블 수 등 필요한 항목을 추가한다(쓰기 없이 조회).
    - 등록·수정 : 기존 `POST /api/schema` 와 M-1 검증을 재사용한다. 수정은 이름·설명만 바꾸고 내부 ID(`SCHM_SN`)는 그대로 — 소속 테이블·관계·인덱스·제약·ERD 레이아웃은 ID 로 참조하므로 바뀌지 않는다. 이름 변경은 비기본 스키마 테이블의 DDL 접두어에 즉시 반영된다.
    - 삭제 : 기본 스키마·테이블이 있는 스키마는 거절(현행). 삭제 전 확인 대화상자. 소속 테이블 자동 삭제·다른 스키마로 일괄 이동은 하지 않는다.
  - **테이블·컬럼 관리 연동:** 테이블 관리 그리드의 스키마 열·스키마 필터(스키마별 조회), 등록 시 스키마 선택(기본 스키마 자동 선택), 상세의 소속 스키마 표시. `schemaId` 를 보내지 않는 기존 화면·API·엑셀 업로드는 지금처럼 동작한다. 컬럼 관리에는 선택한 테이블의 스키마를 표시만 한다(컬럼에 스키마 ID 를 따로 저장하지 않는다).
  - **ERD 연동:** 스키마 등록·이름 변경·삭제 후 ERD 의 스키마 목록·필터·범위 표시가 갱신된다(TanStack Query 무효화). 현재 프로젝트 유지, 레이아웃(`TB_ERD_LYT`, 테이블 ID 기준 좌표)은 보존.
- **기존 코드 재사용 가능성:** `SchemaService`(`saveSchema`·`deleteSchema`·`resolveSchema`, 이름 패턴·중복 검사), `SchemaRestController`, `TableInfoDto.schemaId`, `selectColumnDetail`, 표준 용어·도메인 연관(`ColumnInfo.standardTerms`), 기존 테이블 상세·DDL 컴포넌트(`TableDdl.tsx`), 데이터 사전 상세(`DictionaryDetail.tsx`), 프론트 정의 그리드(`Grid`, `GridColumn`), ERD 의 스키마 조회(`PhysicalErdPage.tsx`).
- **기술적 고려사항:**
  - 화면 간 이동은 URL 파라미터(예: 테이블 ID)로 상태를 넘긴다. AI 결과가 없거나 AI 미설정이어도 ERD 는 정상 동작.
  - 스키마 이름 비교는 대소문자 무관(서비스)이나 DB 유니크 인덱스(`UX_SCHM_01`)는 대소문자를 구분한다. 동시 등록 경합 처리 수준을 정한다.
  - `GET /api/schema` 가 기본 스키마를 만드는 쓰기 트랜잭션이다. 목록 확장 시 VIEWER 조회가 쓰기를 일으키는 점을 유지할지 정한다.
  - 권한 부족 시 현재 오류 코드가 `DATA_CANNOT_BE_DELETED` 라 등록·수정에도 "삭제할 수 없음" 성격의 메시지가 나간다. UI 연동 전에 의미에 맞는 코드로 정리할지 정한다.
  - 테이블 스키마 이동 : 현재 수정 API(`PUT /api/saveTable` 의 `schemaId`)로 가능하다. 서버 검증은 이동 대상이 같은 프로젝트 스키마인지(`resolveSchema`)뿐이고, 승인된 테이블은 서버가 수정을 거절한다(2026-11-12 부터. 그전에는 화면의 수정 버튼 숨김뿐이었다) — 승인된 테이블을 옮기려면 승인취소가 먼저다. 테이블명은 프로젝트 단위로 유일하므로 이동 시 이름 충돌은 없다. 관계·인덱스·제약·레이아웃은 테이블 ID 기준이라 유지되고, DDL 의 스키마 접두어와 다른 테이블 DDL 의 FK 참조 이름(`REFERENCES`)이 바뀐다. 승인된 테이블의 이동 허용 여부와 UI 제공 범위를 정한다(아래 미확정).
- **권한 정책 (권고):**
  - 스키마 목록·ERD 조회 : VIEWER 이상 (현행).
  - 스키마 등록·수정·삭제 : 현행 유지 — USER 역할 + 승인 권한(관리자·매니저·프로젝트 관리자). 프로젝트 구조 변경이므로 일반 USER 는 조회만. 메뉴를 새로 두면 `MenuAuthorization.MENU_ROLES` 에 페이지·API 역할 중 높은 쪽을 등록하고, 승인 권한이 없으면 변경 버튼을 숨긴다(그리드 소문자 `crudActions` 규칙).
  - 테이블의 스키마 선택·이동 : 테이블 등록·수정 권한(USER)을 따른다. 승인된 테이블의 이동은 승인 권한자만 허용하는 방향을 우선 검토.
  - 프로젝트는 항상 `accountDto.getProjectId()` 로 정하고, 요청의 스키마 ID 는 `findByIdAndProjectId` 로 다시 확인한다(클라이언트 값 불신).
- **선행 작업 및 의존성:** M-2 (ERD 연동). 스키마 관리 UI·테이블 스키마 선택은 M-1 API 만 필요해 ERD 연동과 별도로 먼저 진행할 수 있다. 서로 다른 스키마의 동일 테이블명·엑셀 스키마 열은 M-3 범위가 아니다(M-1 후속 D-03, P2).
- **완료 조건:**
  - ERD 에서 테이블·컬럼의 데이터 사전 정보를 확인하고 관리 화면으로 이동·복귀할 수 있다.
  - 스키마 관리 : ① 프로젝트별 스키마 목록 조회 ② 등록 ③ 수정 ④ 삭제 제한(기본·사용 중) 및 정상 삭제 ⑤ 기본 스키마 보호 ⑥ 테이블 관리 화면의 스키마 선택 ⑦ 스키마별 테이블 조회 ⑧ 컬럼 화면의 소속 스키마 표시 ⑨ ERD 스키마 필터와 관리 데이터 일치 ⑩ 프로젝트 간 데이터 격리 ⑪ 역할별 조회·수정 권한 검증 ⑫ 기존 테이블·컬럼·DDL 기능 회귀 없음.
  - 스키마별 동일 테이블명 허용은 완료 조건에 포함하지 않는다(D-03 후속에서 검증).
- **테스트 및 검증 시나리오:**
  - ERD 연동 : 용어가 없는 컬럼·삭제된 용어 표시, 관리 화면 → ERD 이동 시 해당 테이블 포커스, AI 미설정 상태.
  - 스키마 관리 : 등록·조회·수정·삭제, 같은 프로젝트 스키마명 중복(대소문자만 다른 이름 포함) 차단, 다른 프로젝트의 같은 스키마명 허용, 기본 스키마 삭제 차단, 테이블이 있는 스키마 삭제 차단, 승인 권한 없는 사용자(USER·VIEWER)의 변경 차단, 다른 프로젝트 스키마 ID 로 조회·수정·삭제 차단, 이름 변경 후 내부 ID·소속 테이블·관계·레이아웃 유지와 DDL 접두어 변경.
  - 테이블 연동 : 등록 시 스키마 선택, 미지정 시 DEFAULT 적용, 스키마별 테이블 조회, 스키마 변경 후 ERD 갱신, 컬럼 관리의 스키마 표시, 기존 단일 테이블 DDL 호환.
  - 회귀 : 기존 테이블·컬럼 API, 엑셀 업로드(기본 스키마), 승인 기능, ERD 조회, 레이아웃 저장·복원.
- **우선순위:** P1 (기본 스키마 관리 UI 포함)
- **미확정 사항:**

### M-4. 역공학 결과의 물리 모델 가져오기·ERD 자동 생성

- **목적:** 내부 JDBC 도구로 수집한 원본 카탈로그(AI-2)를 원본 DB 연결 없이 모델링·ERD·데이터 사전·AI 분석에 쓰게 한다.
- **현재 구현 상태:** **M-4a 구현 (2026-11-13, [기록](source-management-ui-m4a.md))**
  - 화면 : 사이드바 "원본 DB 관리" 아래 연결 관리·메타데이터 수집·원본 카탈로그.
  - 이미 있는 원본 API(AI-1b·AI-1c·AI-2b)를 그대로 쓴다 : 연결 등록·수정·삭제·테스트, FULL·PARTIAL 수집·진행 상태·취소, 수집 이력·변경 내역, 수집 시점별 카탈로그·테이블 버전.
  - 서버 변경은 메뉴 권한과 `/api/auth/me` 의 `projectManageable` 뿐이다. 신규 마이그레이션은 없다.
  - 선행인 수집은 PostgreSQL 만 있다 (AI-2b : 테이블·뷰(정의 SQL 제외)·컬럼·제약조건·인덱스·FK).
  - **M-4b 원본 DB ERD 구현 (2026-11-13, [기록](source-erd-m4b.md))** : `GET /api/source/connections/{id}/snapshot/erd`(반영 순서의 테이블 버전으로 연결 전체를 한 번에, 실제 FK 만), 화면 "원본 DB ERD"(스키마 선택·FK 이웃 보기·검색·수집 시점·관계 상세·카탈로그 상세 재사용). 300/1,000/3,000 테이블 측정 후 한 번에 그리는 한도 1,000.
  - **M-4c 착수 전 기반 정비 (2026-11-13, [기록](m4-foundation.md))** : JSON·정적 파일 응답 압축(원본 ERD 3,000 테이블 4.46 MB → 103 KB), Git 자동 스테이징 원인(IntelliJ 자동 추가) 분석·정리 방법, DBMS 확대 시점, **M-4c~M-4f 설계 정책 확정** (core 읽기 전용 계약, 별도 매핑 테이블·사용자 확정, 스키마 매핑(public → DEFAULT 제안), 프로젝트 관리자·ADMIN 실행 + 미승인 가져오기, 필드 소유권·원본 COMMENT 별도 속성, 삭제 후보만, 기준 연결 1개, PostgreSQL → PostgreSQL 타입 보존, VIEW 가져오기 보류, IMPORT 이력).
  - **M-4c 원본 스키마·TABLE 매핑 — 완료 (2026-11-13, [기록](source-mapping-m4c.md))**

    | 구분 | 구현 결과 |
    |---|---|
    | 기준 연결 | 프로젝트별 가져오기 기준 원본 DB 연결 1개 (`TB_PRJ_SRC_CNTN`, `UX (PRJ_SN)`) |
    | 스키마 매핑 | 원본 스키마 ↔ 모델 스키마 1:1 (`TB_SRC_SCHM_MPNG`, 연결 단위 유니크 2개) |
    | TABLE 매핑 | 원본 TABLE ↔ 모델 TABLE 1:1 (`TB_SRC_TBL_MPNG`, 연결 단위 유니크 2개). VIEW 는 매핑하지 않는다 |
    | 매핑 후보 | 이름 기반 후보 제안(원본 DBMS 비교 규칙), 저장은 사용자 확정만 — 자동 매핑 없음 |
    | 기본 스키마 | PostgreSQL `public` → 모델 `DEFAULT` 를 후보로 제안 (DEFAULT 스키마는 바꾸지 않음) |
    | 매핑 저장 | 매핑 관계와 확정 시점의 원본 식별 정보만 저장. 원본 DB·물리 모델은 바꾸지 않는다 |
    | 원본 식별 | 원본 카탈로그 행 일련번호(`SRC_SCHM_SN`·`SRC_TBL_SN`) + 생성 차수(`CRT_CYCL`). OID 미사용 |
    | 원본 재생성 | 생성 차수가 확정 때와 다르면 "재확인 필요" |
    | 원본 이름 변경 | 삭제 + 신규 객체 (기존 매핑은 "원본 없음", 새 이름은 미매핑) |
    | 부분 수집 | 마지막 완료 수집 시점의 버전으로 판정 — PARTIAL 범위 밖을 삭제로 보지 않음 |
    | 기준 연결 변경 | 기존 매핑은 원래 연결에 보존 (다른 연결로 옮기지 않음) |
    | 원본 연결 삭제 | `SourceConnectionDeletedEvent` 로 같은 트랜잭션에서 기준 지정·매핑 정리 |
    | 동시성 | 프로젝트 잠금(공유) → 기준 연결 행(배타) 직렬화 + DB 유니크 제약 (위반은 409) |
    | 권한 | 변경은 프로젝트 관리자 또는 전역 ADMIN, 조회는 VIEWER 이상 |
    | 화면 | 원본 DB 관리 → 원본 매핑 관리 (`/sourceMapping`) |

    - **상태는 저장하지 않고 조회할 때 계산한다** : 매핑됨·미매핑·모델 없음·원본 없음·재확인 필요·충돌. 원본 삭제 여부는 마지막으로 완료된 수집 결과(반영 순서의 버전)로 판정한다.
    - **기준 연결 정책** : 완료된 수집이 없어도 지정할 수 있지만 그 상태에서는 매핑을 확정할 수 없다. 바꿔도 기존 매핑은 지우지 않고, 다른 연결의 매핑을 현재 기준으로 자동 이전하지 않는다. 이전 연결로 돌아오면 남아 있던 매핑의 상태를 그때 다시 판정한다.
    - **모듈 구조** : `lexorma-core` 의 읽기 전용 계약 `SourceCatalogReader` 와 이벤트 `SourceConnectionDeletedEvent`, 구현은 `lexorma-source` 의 `SourceCatalogReaderService`. `lexorma-source` ↔ `lexorma-data` 직접 의존 없음 (`ModuleBoundaryTest`).
    - **마이그레이션** : `V2__source_mapping.sql`(PostgreSQL·H2, 증분). 개발 DB 에 적용됨 — 수정 금지.

- **작업 범위:**
  - **최초 사용 흐름 (단계별 화면):**

    ```text
    프로젝트 선택 → 외부 DB 연결 등록 → 연결 확인 → 수집 대상(스키마·테이블) 선택
      → 최초 수집 (진행률·처리 건수) → 수집 결과·오류 확인 → 원본 구조 미리보기(ERD)
      → 기존 물리 모델과 비교 (충돌 항목 사전 안내) → 가져올 테이블·컬럼 선택
      → 물리 모델에 반영 → ERD 자동 생성 → 데이터 사전·표준 용어 연결 → (선택) AI 분석 요청
    ```

    - 연결 실패 시 원인별 안내(접속 불가, 인증 실패, 드라이버 없음, 권한 부족).
    - **원본 카탈로그 수집 완료와 물리 모델 가져오기 완료는 다른 상태다.** 수집 결과는 가져오기 없이 바로 조회·ERD 미리보기할 수 있고, 가져오기를 취소해도 수집한 원본 카탈로그는 보존한다.
    - AI 미설정 상태에서도 마지막(AI 분석)을 제외한 모든 단계를 수행할 수 있다.
    - 이미 등록한 연결은 **재최신화 → 변경 비교(M-10 ①) → 필요한 변경만 가져오기** 흐름을 제공한다.
  - 원본 카탈로그 → 물리 모델 **가져오기**: 대상 선택(스키마·테이블), 기존 테이블과 매핑(이름 기준 자동 + 수동 연결), 새 테이블 생성, 원본 COMMENT 는 원본 COMMENT 속성에만 반영(업무 설명 보존).
  - 원본 카탈로그만으로 **ERD 바로 보기**(가져오기 전 미리보기), 실제 FK 를 관계로 표시.
  - **미등록 식별**: 원본에는 있으나 모델에 없는 테이블·컬럼, 모델에는 있으나 원본에 없는 항목 목록.
  - 컬럼명 → 표준 용어 자동 매칭 후보(기존 `resolveTerms` 재사용), 미매칭 목록.
- **기존 코드 재사용 가능성:** `resolveTerms`, 대량 저장 패턴, 테이블·컬럼 저장 서비스.
- **기술적 고려사항:** 가져오기는 사용자 확인 후 실행하며 기존 업무 설명·승인 상태·표준 용어 연결을 덮어쓰지 않는다. 가져온 테이블이 테이블명 규칙(접두어·표준 단어)과 맞지 않을 수 있으므로 위반은 M-5 검증 결과로 표시하고 가져오기는 막지 않는다. 가져오기 이력은 **작업 이력**(수집·가져오기 작업, [AI-8 작업 모델](ai-metadata-roadmap.md#8단계-정기-배치-및-수동-검사-실행))으로 남기며 P2 인 M-9 를 기다리지 않는다. 여러 연결(개발·운영)을 하나의 물리 모델에 매핑할 때 기준 연결과 비교 대상 연결을 구분한다(D-17). MCP 를 쓸 수 없는 환경을 위한 파일 기반 가져오기(DDL·표준 파일)는 **선택적 대안**으로만 검토한다(D-16, 내부 JDBC 수집이 기본 방향).
- **선행 작업 및 의존성:** M-1, AI-1(원본 카탈로그 모델), AI-2(수집).
- **완료 조건:** 원본 DB 연결 없이 수집 결과로 물리 모델·ERD 를 만들 수 있고, 재가져오기에서 사용자 데이터가 보존되며, 미등록 항목이 식별된다. 최초 연결부터 수집·가져오기·ERD 조회까지 하나의 화면 흐름으로 수행할 수 있고, 수집 완료와 가져오기 완료가 구분되어 표시된다.

M-4e 전 : 이름 변경 후보 확정 저장 여부(V3+), 원본 COMMENT 칸(V3+), 가져오기 트랜잭션 경계·가져오기 전 모델 버전 보존, 승인된 객체를 원본 기준으로 바꾸는 방식, 매핑 변경 이력 저장 여부

### M-5. 데이터 표준화 유지·확장

- **목적:** 기존 표준 단어·용어·도메인 기능을 유지하면서, 모델링·AI 가 근거로 쓸 수 있게 사용 현황과 명명 규칙 검증을 보강한다.
- **현재 구현 상태:** 일부 구현. 단어·용어·도메인 등록·수정·승인·엑셀, 중복 검사, 단어 수·`_` 검증, 사용 중 삭제 차단, 승인 단어 기반 테이블명 생성은 있다.
  - **1차 — 사용 현황 조회 API·UI : 구현 (2026-11-11, [기록](standardization-usage-m5.md)).** 용어 → 컬럼, 도메인 → 컬럼(용어를 거친 간접 참조), 단어 → 용어(+용어별 컬럼 수), 데이터 사전 목록의 사용 건수, 사용 현황에서 테이블 상세 대화상자·물리 ERD 로 이동. 브라우저 화면 동작은 2차 때 확인했다.
  - **2차 — 표준화 품질 진단 : 구현 (2026-11-11, [기록](standardization-quality-m5.md)).** 표준 용어 미연결 컬럼, 컬럼명 ↔ 용어 영문약어 불일치, 도메인 ↔ 컬럼 타입·길이·정밀도·소수 자릿수 불일치(DDL 타입 매핑 기준)를 조회 시 계산하는 요약·목록 API 와 독립 화면(`/standardizationQuality`). 조회 전용이며 결과를 저장하지 않는다.
  - **미구현 (잔여) :** 테이블명 규칙(접두어·승인 단어) 검사, 용어 중복·유사어, 비표준 컬럼명 개선안 후보, 등록 시점 검증과의 규칙 공유, AI-6 호출 연결. 브라우저 미검증 항목(VIEWER·USER 계정 화면, 세션 만료 알림, 영어·좁은 화면)과 예제 데이터의 도메인 불일치 215건 처리 방침은 [기록 5.2·6장](standardization-quality-m5.md) 참고.
- **작업 범위:**
  - **사용 현황**: 단어 → 용어, 용어 → 컬럼·(향후) 속성, 도메인 → 용어·컬럼 조회 화면/API.
  - **명명 규칙 검사(규칙 정의)**: 테이블명(접두어·승인 단어), 컬럼명(표준 용어 약어 일치), 표준 약어 준수, 용어 중복·유사어(이음동의어·금칙어 활용), 도메인과 컬럼 타입·길이 불일치, 비표준 컬럼명 개선안(규칙 기반 후보).
  - 검사 **실행·결과 저장·보고**는 AI-6(규칙 기반 품질 검사)이 담당하고, 이 단계는 **규칙과 표준 데이터**를 제공한다.
- **기존 코드 재사용 가능성:** `generateTableName`(단어별 `NOT_FOUND` 상태), `validateWordCount`, `validateNoUnderscore`, `resolveTerms`, `toEnglishTermName`, 프로젝트의 `isDicAbbrUsed`·`tablePrefix`.
- **기술적 고려사항:** 규칙은 한 곳에서 정의하고 화면 등록 시 검증·일괄 검사·AI 근거가 같은 규칙을 쓴다. **코드 규칙 관리·메서드명 생성과 혼동하지 않는다**(8장).
- **선행 작업 및 의존성:** 없음 (독립 진행).
- **완료 조건:** 단어·용어·도메인 사용 현황을 조회할 수 있고, 명명 규칙이 목록화·구현되어 AI-6 에서 호출된다. 기존 기능이 회귀 없이 동작한다.
- **테스트 및 검증 시나리오:** 규칙별 통과/위반 사례, 이음동의어로 등록된 컬럼명의 표준 용어 후보 제시, 도메인 길이보다 큰 컬럼 길이 탐지.
- **우선순위:** P1
- **미확정 사항:** AI 로드맵 U-16 (규칙 목록·심각도)

### M-6. 논리 데이터 모델

- **목적:** 업무 관점의 엔터티·속성·관계를 정의하고 표준 용어·도메인과 연결한다.
- **현재 구현 상태:** **1차 구현** — 논리 모델·엔터티·속성·식별자(복합)·관계(양쪽 최소·최대 참여 수) 저장 구조와 `/api/logical/**` 관리 API, 논리 ERD 조회 API, 표준 용어 연결(도메인은 용어의 도메인), 엔터티·관계 승인 ([결과](logical-model-m6.md)). **2차 구현** — 논리 모델 관리 화면(`/logicalModel`), 논리 ERD(`/logicalErd`, 참여 수 표기, 모델별·사용자별 레이아웃 `TB_LGCL_ERD_LYT`), 관리 화면 ↔ ERD 포커스, 사이드바를 시스템 관리 / 데이터 사전(표준 도메인·단어·용어 화면 분리) / 논리 모델 관리 / 물리 모델 관리 / 데이터 품질 관리 / 운영 관리로 개편, 승인 권한자가 등록한 엔터티·관계는 바로 승인. 주제 영역·서브타입·엔터티 유형은 후속(D-07).
- **작업 범위:** 엔터티(논리명, 설명, 주제 영역), 속성(논리명, 설명, 식별자 여부, 표준 용어·도메인 연결), 엔터티 관계(식별/비식별, 카디널리티), 논리 ERD(M-2 컴포넌트 재사용), 승인 흐름(기존 승인 권한 기준).
- **기존 코드 재사용 가능성:** 표준 용어·도메인 검색, 승인 권한(`AuthUtil.isApprovalAvailable`), ERD 렌더링(M-2), 그리드·다이얼로그.
- **기술적 고려사항:** 초기 범위는 엔터티·속성·관계와 논리 ERD 조회까지로 하고, 서브타입·주제 영역 계층 등은 후속으로 둔다. 논리 모델은 DBMS·물리명과 독립적이어야 한다.
- **선행 작업 및 의존성:** M-1(관계 모델 설계 공유), M-2(ERD 컴포넌트).
- **완료 조건:** 엔터티·속성·관계를 등록·조회하고 표준 용어·도메인과 연결하며 논리 ERD 로 볼 수 있다.
- **테스트 및 검증 시나리오:** 표준 용어 연결 속성의 도메인 표시, 승인 권한 검증, 프로젝트 격리.
- **우선순위:** P1
- **미확정 사항:** D-07 (논리 모델 초기 범위, 주제 영역 필요 여부)

### M-7. 논리·물리 모델 매핑

- **목적:** 논리 모델과 물리 모델을 구분하되 연결해, 표준 기반 물리 설계와 불일치 확인을 지원한다.
- **현재 구현 상태:** **1차 구현** — 엔터티 ↔ 테이블, 속성 ↔ 컬럼 매핑(1:1, 속성 매핑은 엔터티 매핑에 종속) 저장 구조(`TB_ENTT_TBL_MPNG`·`TB_ATRB_COL_MPNG`, Flyway V2)와 `/api/modelMapping/**` 관리 API, 모델별 매핑 현황, 매핑 후보(엔터티·테이블·속성·컬럼) 조회, 매핑된 원본의 삭제 차단 ([결과](logical-physical-mapping-m7.md)). **2차 구현** — 매핑 관리 화면(`/modelMapping` : 현황, 엔터티 ↔ 테이블·속성 ↔ 컬럼 매핑 등록·변경·해제), 정합성 비교(매핑 여부·표준 용어·명칭·데이터 타입·길이·필수 여부·식별자, 일치/불일치/비교 불가/미매핑, 조회 시 계산) API·화면, 엔터티 상세·논리 ERD·테이블 상세·물리 ERD 연동 ([결과](model-mapping-quality-m7.md)). **3차 구현** — 표준 사전 기반 물리명 추천(컬럼명 = 논리 속성의 표준 용어 영문약어, 테이블명 = 엔터티명의 승인된 표준 단어 영문약어 + 접두어, 추천 가능/일치/추천 불가/충돌, 조회 전용) API·화면, 정합성 명칭 진단과 같은 계산 사용, 컬럼 상세 연동 ([결과](physical-name-recommendation-m7.md)). **미구현(후속)** — 논리 → 물리 일괄 생성(D-08), 추천명 적용.
- **단계:** **M-7 1차** 매핑 도메인 및 API (구현) → **M-7 2차** 매핑 관리 UI 및 정합성 비교 (구현) → **M-7 3차** 표준 사전 기반 물리명 추천 (구현). 아래 완료 조건의 "매핑 상태 확인"은 1차 API·2차 화면, "불일치 목록"은 2차 정합성 비교, "물리명 추천이 표준 용어 기준으로 동작"은 3차로 충족했다. 테스트 시나리오의 "용어 없는 속성의 추천 불가 표시"(3차), "도메인 타입과 컬럼 타입 불일치 탐지"(2차), "매핑 해제 후 상태"(1·2차)도 자동 테스트와 화면에서 확인했다.
- **작업 범위:** 엔터티 ↔ 테이블, 속성 ↔ 컬럼 연결(1:1 우선, 1:N 은 검토), **표준 용어로 물리명 추천**(속성의 용어 → 컬럼명, 엔터티 → 테이블명), 도메인 → 데이터 타입 매핑(DBMS 별), 불일치 확인(매핑 없는 엔터티·테이블, 타입·NULL 차이).
- **기존 코드 재사용 가능성:** `generateTableName`, 용어의 영문약어명(물리명), 컬럼 등록 시 도메인 → 타입 결정 로직(`features/column/terms.ts`), `TableDdlGenerator` 의 DBMS 별 타입 처리.
- **기술적 고려사항:** 논리 모델에서 물리 모델을 **생성**(포워드)과 물리 → 논리 **역추출**은 범위를 나눈다(초기: 연결과 추천, 후속: 일괄 생성).
- **선행 작업 및 의존성:** M-6.
- **완료 조건:** 매핑 상태와 불일치 목록을 확인할 수 있고, 물리명 추천이 표준 용어 기준으로 동작한다.
- **테스트 및 검증 시나리오:** 용어 없는 속성의 추천 불가 표시, 도메인 타입과 컬럼 타입 불일치 탐지, 매핑 해제 후 상태.
- **우선순위:** P1
- **미확정 사항:** D-07, D-08 (논리 → 물리 일괄 생성 범위)

### M-8. ERD 편집 (내부 모델)

- **목적:** ERD 에서 Lexorma 내부 모델을 직접 만들고 고친다. **원본 DB 를 변경하지 않는다.**
- **현재 구현 상태:** **1차 구현** — ERD 편집 기반(조회·편집 모드, 모델 데이터는 기존 API 로 즉시 저장 후 다시 조회, 배치는 따로 저장)과 논리 ERD 의 엔터티 생성·수정·삭제, 속성 추가·수정·삭제·순서 변경·표준 용어 연결. **2차 구현** — 논리 ERD 에서 연결점을 이어 관계 등록(연결은 폼을 열 뿐, 저장 성공 후에 선이 생긴다), 관계 수정·삭제·승인, 식별·비식별과 참여 수 표시(선 끝 표기 포함), 같은 쌍의 여러 관계 구분, 식별자(주·보조·복합) 추가·수정·삭제. 관계와 식별자는 서로 자동으로 바꾸지 않는다 ([결과](erd-editing-m8.md)). **3차 구현** — 물리 ERD 의 조회·편집 모드, 테이블 등록·수정·삭제, 기존 컬럼 일괄 편집기 연결, 연결점을 이어 FK 등록(컬럼 쌍·방향 확인, 복합·자기 참조), FK 삭제·승인, 관계선 선택, 인덱스·제약조건 관리 대화상자, 범위 밖 새 테이블 안내. 관계는 수정 API 가 없어 삭제 후 다시 등록한다 ([결과](physical-erd-editing-m8.md)). **완료 (2026-11-12).** 안정화 : 승인된 테이블 수정의 서버 차단, FK 참조 키·타입 검증, DDL 의 승인 대기 안내, PostgreSQL 전체 테스트 ([기록](model-integrity-hardening.md)). 레이아웃 확장·동시 편집 정책은 구현하지 않았고 아래 후속 표로 옮겼다.
- **단계:** **M-8 1차** 편집 기반 + 논리 엔터티·속성 (구현) → **M-8 2차** 논리 관계·식별자 편집 (구현) → **M-8 3차** 물리 테이블·컬럼·관계 편집 (구현). 처음 로드맵은 M-8 을 물리 모델 편집으로만 적었다. 논리 ERD(M-6)가 생긴 뒤 같은 편집 기반을 논리 ERD 에 먼저 적용하도록 단계를 나눴고, 아래 작업 범위·완료 조건(물리)은 3차의 것이고, 완료 조건은 3차에서 확인했다 (ERD 조회 = 테이블 물리 모델 = DDL, 범위 밖 배치 보존). 작업 범위의 "레이아웃 확장" 과 테스트 시나리오의 "동시 편집 충돌" 은 완료 조건에 들어 있지 않으며 하지 않았다 → 아래 후속 표.
- **작업 범위:** 테이블 생성·삭제, 컬럼 추가·수정(표준 용어 선택, 데이터 타입), PK·관계 정의(드래그로 연결), 테이블·컬럼 설명, **레이아웃 확장**(M-2 의 최소 저장 위에 노드 접힘·그룹·여러 다이어그램 뷰), 편집 이력(M-9).
- **기존 코드 재사용 가능성:** 테이블·컬럼 저장 서비스와 검증(표준 용어, 승인 여부, 중복), 컬럼 일괄 저장(`saveColumn/bulk`), 다이얼로그 폼(`TableForm`, `ColumnForm`).
- **기술적 고려사항:** 편집은 기존 서비스 검증을 그대로 거친다(ERD 전용 우회 저장 금지). 승인된 객체의 수정 제한 규칙을 따른다. 여러 사용자가 같은 모델을 편집할 때의 충돌(낙관적 잠금) 검토.
- **선행 작업 및 의존성:** M-2, M-3, M-1. **M-1 후속의 관계 동기화 누락 방지를 완료한 뒤 M-8 구현에 착수한다.**
- **완료 조건:** ERD 편집 결과가 테이블·컬럼 관리 화면·DDL 과 일치하고, 레이아웃이 복원된다.
- **테스트 및 검증 시나리오:** ERD 에서 만든 테이블의 DDL 생성, 승인된 컬럼 수정 시도 거부, 동시 편집 충돌, 레이아웃 저장 후 복원.
- **우선순위:** P2
- **미확정 사항:** D-09 (동시 편집 정책), D-10 (레이아웃 저장 단위: 사용자별/프로젝트 공유)

### M-9. 모델 버전·변경 이력

- **목적:** 모델 변경을 추적하고 이전 상태와 비교할 수 있게 한다.
- **현재 구현 상태:** **1차 구현 (2026-11-12)** — 공통 변경 이력 테이블 `TB_MDL_CHG_HSTRY`(변경 전후 JSON, 변경 그룹), 물리 모델 5종의 변경 기록(Hibernate 저장 이벤트 → 커밋 직전 같은 트랜잭션으로 저장, 실제로 달라진 것만), 조회 API `/api/modelHistory`(목록·객체별·그룹·상세, VIEWER 이상, 프로젝트 격리). 이력 화면은 없다 ([결과](model-change-history-m9.md)). **남은 것(2차 이후)** : 논리 모델·매핑 이력, 이력 화면, 모델 버전·비교, 보관 정책. **2차 구현 (2026-11-12)** — 논리 모델(모델·엔터티·속성·식별자·관계)과 매핑(엔터티 ↔ 테이블, 속성 ↔ 컬럼) 이력, 연관 대상의 이름 스냅샷, 변경 이력 조회·전후 비교·변경 그룹 화면, 대량 업로드 성능 측정. 완료 조건의 "편집 이력" 은 충족, "버전 비교" 는 미구현. **3차 구현 (2026-11-12)** — 모델 버전 : 명시적 생성(버전명·설명, 프로젝트 안에서 이름 하나), 생성 시점의 모델 전체를 JSON 한 건으로 저장(스키마 + 변경 이력과 같은 12종, 같은 필드), 저장된 버전의 읽기 전용 조회, 버전 ↔ 버전·버전 ↔ 현재 모델 비교(객체 ID 로 짝지어 추가·삭제·수정). 수정·삭제·복원·자동 생성은 없다. 완료 조건의 "버전 비교" 충족 ([기록 12장](model-change-history-m9.md)).
- **작업 범위:** **초기**: 테이블·컬럼·관계 편집 이력(누가, 언제, 무엇을 전후로). **후속**: 모델 버전(명명된 기준점), 버전 간 비교, 이전 버전 조회, 변경 검토.
- **기존 코드 재사용 가능성:** `BaseEntity` 감사 필드, AI-1 의 변경 이력 설계(같은 방식 공유).
- **기술적 고려사항:** 원본 카탈로그 스냅샷(AI-1)과 모델 버전은 **다른 개념**이다(원본의 사실 vs 사용자가 설계한 모델). 이력 저장량과 보관 기간.
- **선행 작업 및 의존성:** M-1, M-8 과 함께.
- **완료 조건:** 편집 이력이 남고(초기), 버전 비교가 가능하다(후속).
- **테스트 및 검증 시나리오:** 컬럼 타입 변경 이력, 삭제된 테이블 이력 조회, 버전 간 차이 계산.
- **우선순위:** P2
- **미확정 사항:** ~~D-11~~ → 결정 : 공통 변경 이력 테이블 + 변경 전후 JSON. 이력 보관 기간·프로젝트 삭제 시 처리는 미정 ([기록 9장](model-change-history-m9.md))

### M-10. 구조 변경 비교·시각화

- **목적:** 최신화 전후, 그리고 모델과 원본 DB 구조의 차이를 사용자가 이해할 수 있게 보여준다.
- **현재 구현 상태:** **③ 만 구현 (2026-11-12)** — 차이 계산·목록·전후 비교는 M-9 3차, 변경 전후 ERD 표시는 [M-10 ③ 1차](model-version-erd-m10.md)(`GET /api/modelVersion/compare/erd`, 버전 비교 대화상자의 [ERD 비교]). ①② 는 미구현 : 원본 스냅샷(AI-1·AI-2)과 가져오기(M-4)가 없다. **M-10 전체는 완료가 아니다.**
- **작업 범위:**
  - 비교 대상: ① 원본 스냅샷 A ↔ B(최신화 전후, AI-2 변경분 재사용) ② 물리 모델 ↔ 최신 원본 스냅샷 ③ 모델 버전 A ↔ B(후속, M-9).
  - 변경 항목: 스키마·테이블·컬럼 추가·삭제, **컬럼명 변경 후보**(자동 확정 안 함), 타입·NULL·PK·FK·인덱스·제약조건·COMMENT 변경.
  - 시각화: 변경 테이블 강조, 추가·삭제 컬럼 표시, 전후 속성 비교 표, ERD 내 관계 변경 표시, 상세 화면 이동.
- **기존 코드 재사용 가능성:** ERD 컴포넌트(M-2), 그리드, AI-2 의 비교 결과.
- **기술적 고려사항:** 비교는 자체 DB 의 스냅샷·모델만 사용(원본 DB 접속 없음). 대규모 변경은 목록 우선, ERD 는 변경 영역만.
- **선행 작업 및 의존성:** ① AI-2, M-2 (모델 편집 이력 불필요 — 먼저 개발 가능) ② M-4 ③ M-9. 부분 최신화의 범위 밖 객체는 비교에서 "변경 없음"으로 처리한다([AI-2 삭제 판정](ai-metadata-roadmap.md#2단계-mcp-기반-외부-db-메타데이터-수집동기화)).

### M-11. DDL·Export 확장

- **목적:** 기존 DDL·Export 기능을 유지하면서 모델 단위 산출물을 제공한다. **DDL 은 생성·출력만 하고 실행하지 않는다.**
- **현재 구현 상태:** 일부 구현. DDL 은 테이블 1개 단위 조회·복사, Export 는 데이터 사전 엑셀과 템플릿. **2026-11-13 통합 DDL Export 완료** — 프로젝트·스키마 단위 한 스크립트(SCHEMA → TABLE → INDEX → FK → VIEW, 순환 FK 는 ALTER 분리), DBMS 선택, 승인 기준 모드, 미리보기·복사·`.sql` 다운로드, PostgreSQL 실행 검증 ([기록](integrated-ddl-export-m11.md)). 선택 테이블 단위, 엑셀·ERD 이미지·모델 정보 Export, 재가져오기는 남았다.
- **작업 범위:** 물리 모델(전체·스키마·선택 테이블) 기반 **다중 테이블 DDL**(생성 순서: FK 의존 순서), DDL 미리보기·복사·`.sql` 파일 다운로드, 테이블·컬럼 정보 엑셀 Export(기존 템플릿 형식과 맞춤), 모델 정보 Export, **ERD 이미지(PNG/SVG) Export**, 기존 DDL 조회와 통합.
  - **이식성(폐쇄망·이전):** 모델·메타데이터 Export 를 다시 가져올 수 있는 형식으로 정의(재가져오기), 프로젝트 간 이동 정책, **DB 연결 비밀값을 제외한** 설정 백업·복구. 원본 DB 연결 없이 저장된 메타데이터를 계속 관리할 수 있어야 한다(D-18).
- **기존 코드 재사용 가능성:** `TableDdlGenerator`, `ExcelExportUtils`/`PagedReader`, 템플릿 형식(`tableTemplate.xlsx`, `columnTemplate.xlsx`).
- **기술적 고려사항:** Export 는 **필요한 산출물에 한정**하고 범용 설계서 생성으로 확장하지 않는다(8장). 대량 Export 는 스트리밍.
- **선행 작업 및 의존성:** M-1 (ERD 이미지는 M-2).
- **완료 조건:** 모델 단위 DDL 파일과 테이블·컬럼 Export 를 받을 수 있고, 기존 DDL 조회·엑셀 기능이 그대로 동작한다. DDL 실행 경로가 없다.
- **테스트 및 검증 시나리오:** 순환 FK 가 있는 DDL 순서·`ALTER` 분리, DBMS 별 결과, Export 파일 재업로드(테이블·컬럼 업로드 형식 호환).
- **우선순위:** P2
- **미확정 사항:** D-12 (Export 형식·범위), D-18 (재가져오기 형식·프로젝트 간 이동)

### M-12. 영향 분석 (+ SQL Lineage 검토)

- **목적:** 변경된 모델·컬럼의 관련 객체를 찾는다.
- **현재 구현 상태:** 미구현.
- **작업 범위:** **메타데이터 기반**: 특정 컬럼을 참조하는 관계, 연결된 표준 용어·도메인, 관련 데이터 사전 항목, 재검토가 필요한 설명(AI-5 무효화 조건), 영향 범위 보고. **SQL Lineage**: 수집 가능성(뷰 정의·프로시저 텍스트 등)과 정확도를 검토한 뒤 별도 과제로 정의 — **초기에 완전한 SQL 계보 분석을 확정하지 않는다.**
- **기존 코드 재사용 가능성:** 관계 모델(M-1), 사용 현황(M-5), 변경 비교(M-10).
- **기술적 고려사항:** 추정 관계(미승인)는 영향 분석에서 별도 표시.
- **선행 작업 및 의존성:** M-9, M-10.
- **완료 조건:** 컬럼을 선택하면 관계·용어·데이터 사전 영향 목록이 나온다. SQL Lineage 는 검토 결과 문서화.
- **테스트 및 검증 시나리오:** 다단 FK 체인, 용어를 공유하는 여러 컬럼.
- **우선순위:** P3 (SQL Lineage 는 P3 / 검토)
- **미확정 사항:** D-13 (Lineage 범위)

### M-13. 모델링 관련 AI 확장

- **목적:** AI 가 모델링·표준화의 생산성을 높이도록 연결한다. AI 로직은 AI 로드맵이 담당하고, 이 단계는 **모델링 쪽 요구(데이터·표시·승인 반영)** 를 정의한다.
- **현재 구현 상태:** 미구현.
- **작업 범위:**
  - **AI 데이터 사전 생성(AI-5)**: 표준 용어·도메인·연관 테이블을 근거로 사용, 결과를 ERD 상세 패널에 표시(M-3).
  - **AI 관계 추론(AI-12, P2)**: 근거(컬럼명 유사성, 타입, PK 후보, 표준 용어, 데이터 사전, 설명)를 갖춘 추정 관계를 4.2 유형으로 저장·ERD 표시, 승인 시 모델 관계로 전환.
  - **AI 표준화 검사(AI-6·7)**: M-5 규칙과 표준 데이터를 근거로 비표준 용어·약어, 도메인·타입 불일치, COMMENT ↔ 업무 설명 불일치. **새 표준 용어는 승인 전 확정 금지.**
  - **AI ERD 분석(AI-13, P3)**: ERD 구조·테이블 역할·관계 요약, 불명확한 관계 탐지, 설계 개선 조언(텍스트, 자동 반영 없음).
  - **AI SQL 조언(AI-10)**: 물리 모델·관계 기반 JOIN 추천 (실행 불가).
- **기존 코드 재사용 가능성:** ERD(M-2·3), 관계 모델(M-1), 표준화 규칙(M-5).
- **기술적 고려사항:** AI 미설정·장애 시 모델링 기능은 독립적으로 동작. AI Tool 은 자체 DB 만 조회, SQL 실행 Tool 없음.
- **선행 작업 및 의존성:** M-3, AI-4.
- **완료 조건:** AI 결과가 근거·검토 상태와 함께 모델 화면에 표시되고, 승인된 것만 모델·데이터 사전에 반영된다. 추정 관계가 실제 FK 와 구분된다.
- **테스트 및 검증 시나리오:** 추정 관계 승인 → 모델 관계(출처 = 추정) 전환, 반려 시 ERD 미표시, AI 미설정 시 ERD 정상.
- **우선순위:** P2 (관계 추론·표준화 검사) / P3 (ERD 분석)
- **미확정 사항:** D-14 (추정 관계 기본 표시 여부)

### M-14. 인덱스 관리 (기존 인덱스 기능의 관리 화면 확장)

> **성격 :** 새 모델을 만드는 단계가 아니다. M-1 의 인덱스 모델·API 와 M-8 의 ERD 인덱스 편집을 **별도 관리 화면으로 넓히는** 단계다. (VIEW 를 새로 들이는 M-15 와 다르다.)

- **목적:** 테이블 단위로 흩어져 있는 인덱스를 프로젝트 단위로 모아 조회·관리하고, ERD·테이블 관리·DDL 과 같은 데이터를 보게 한다.
- **1차 구현 결과 (2026-11-13, 부분 완료) :** [index-management-m14.md](index-management-m14.md)
  - **D-19** : `TB_TBL_IDX` 단일 저장. 컬럼 `IDX_YN` 은 약식 입력으로 남고 출처 `COLUMN` 인덱스(`IDX_SRC_CD`·`DRVN_COL_SN`)로 자동 동기화, 기존 데이터는 V3 가 예전 DDL 규칙 그대로 이관. DDL 은 인덱스 모델만 읽는다 (예전 출력 골든 테스트 동일).
  - **D-20** : `PUT /api/physical/index/{id}` — 미승인은 직접 수정, 승인된 인덱스는 변경 요청(`TB_IDX_CHG_DMND`, 전·후 정의) → 승인 시 반영·반려 시 유지, 승인 대기 중 중복 요청·승인 취소 거절, 테이블 행 잠금.
  - **D-21 1차** : 유형을 DBMS 별 문법으로 DDL 에 반영, 지원하지 않는 유형은 저장 거절·기존 값은 DDL 주석 + 경고.
  - **화면** : `물리 모델 관리 > 인덱스 관리`, ERD 대화상자와 양방향 이동.
  - **2차 잔여** : 표현식·부분 인덱스 조건·ASC/DESC·NULLS·INCLUDE, 고급 속성의 DBMS 별 변환, AI-2b 원본 인덱스와의 전체 호환(M-4·M-10 ② 와 연계). 아래 "현재 구현 상태" 는 착수 전 기록이다.
- **현재 구현 상태 (2026-11-13 코드 확인):** 관리 메뉴는 없다. 인덱스는 다음과 같이 있다.
  - **모델** (M-1) : `TB_TBL_IDX`(`TableIndex` : 이름, 유형 문자열 `IDX_TYPE_NM`, 고유 여부, 승인 여부) + `TB_TBL_IDX_COL`(`TableIndexColumn` : 컬럼, 순서). 표현식·정렬 방향·부분 인덱스 조건·INCLUDE 컬럼은 **자리가 없다**.
  - **컬럼 속성으로 만드는 인덱스** : 컬럼의 `IDX_YN`(인덱스 여부)·고유 여부가 DDL 에서 단일 컬럼 인덱스(`IX_<테이블>_<컬럼>`)·UNIQUE 로 나온다. `TB_TBL_IDX` 행이 아니어서 인덱스 목록 API 에는 없다 — **인덱스의 출처가 두 갈래다**.
  - **API** (`/api/physical`) : 테이블 하나의 물리 모델 조회 `GET /table/{tableId}`(VIEWER, 인덱스 포함), 등록 `POST /index`(USER, 복합·고유), 삭제 `DELETE /index/{id}`(USER, **승인된 인덱스는 삭제 불가**), 승인·승인 취소 `PATCH /index/{id}/approval/{bool}`(USER + `AuthUtil.isApprovalAvailable()`). **수정 API 와 프로젝트 단위 목록·검색 API 는 없다** (이름·컬럼을 바꾸려면 지우고 다시 등록한다).
  - **규칙** : 같은 테이블에서 같은 컬럼 구성·같은 이름 중복 거절, PK·고유 컬럼과 같은 구성 거절, 이름이 없으면 `IX_`/`UX_` + 테이블 + 컬럼으로 만든다, 승인 권한자가 등록하면 바로 승인, 인덱스에 쓰인 컬럼은 삭제 불가(`releaseColumns`), 변경 이력(`PHYSICAL_INDEX`, M-9)·모델 버전에 포함.
  - **화면** (M-8) : 물리 ERD 테이블 패널의 [인덱스·제약조건] 대화상자(등록·삭제, 조회 모드는 목록만).
  - **DDL** (`TableDdlGenerator`, 테이블 1개 단위 `GET /api/selectTable/ddl/{id}`) : `CREATE [UNIQUE] INDEX 이름 ON 테이블 (컬럼…)`. **저장된 인덱스 유형(`IDX_TYPE_NM`)은 DDL 에 쓰이지 않는다.** 승인 대기 인덱스도 포함한다(M-8 안정화의 정책).
  - **원본 카탈로그 인덱스** (AI-2b, `lexorma-source` 의 `TB_SRC_IDX`·`TB_SRC_IDX_COL`) : 방식(btree 등)·고유·구성 요소(컬럼 또는 표현식)·정렬(DESC·NULLS·INCLUDE)·부분 인덱스 조건을 읽기 전용으로 담는다. 물리 모델과 이어져 있지 않다.
- **작업 범위:**
  - **메뉴** : `물리 모델 관리` 그룹(`physical-modeling`, 현재 사이드바의 데이터 관리 영역)에 **인덱스 관리**(예: `/indexManage`, 메뉴 id `index-manage`). 화면 최소 역할 VIEWER, 변경 버튼은 기존 액션 `physical-model-edit`(USER)로만 노출 — `MENU_ROLES`·`MENU_GROUPS`·`menu.ts` 를 함께 고친다.
  - **목록** (Grid 패턴) : 프로젝트의 인덱스, 스키마·테이블 필터, 이름·컬럼 검색, 고유·승인 여부·유형 필터, 정렬·페이징. 컬럼 속성(`IDX_YN`·고유)으로 만든 인덱스를 **함께 보일지·구분 표시할지** 결정(D-19).
  - **상세·편집** : 구성 컬럼 선택과 순서 바꾸기, 고유 여부, 유형(DBMS 별 선택지와 지원 범위 표시), 이름. 등록·삭제·승인은 기존 API. **수정**은 새 API 로 둘지, 화면에서 삭제 + 등록으로 처리할지 결정(D-20) — 승인된 인덱스는 승인 취소 뒤에만 바꾼다(기존 정책).
  - **DDL** : 선택 인덱스·테이블 단위 `CREATE INDEX` 미리보기·복사. 저장된 유형을 DBMS 별 문법(`USING gin` 등)으로 낼지, 지원하지 않는 DBMS 에서 어떻게 알릴지 결정 (DDL 은 생성·출력만, 실행 없음).
  - **이동** : 목록 ↔ 테이블 관리(그 테이블 상세)·물리 ERD(그 테이블 포커스) 양방향.
  - **정합성** : 관리 화면·ERD 대화상자·테이블 물리 모델 조회·DDL 이 같은 인덱스를 보인다 (저장소는 `TB_TBL_IDX` 하나).
  - **원본 인덱스와 비교 (분석만)** : 아래 표의 차이를 화면 안내와 후속 결정으로 남긴다. 원본 인덱스를 물리 모델로 옮기는 것은 M-4, 원본 ↔ 모델 차이 비교는 M-10 ② 다.

  | 속성 | 물리 모델 (`TB_TBL_IDX`) | 원본 카탈로그 (AI-2b) | M-14 처리 |
  |---|---|---|---|
  | 이름·고유·구성 컬럼 순서 | 있음 | 있음 | 그대로 |
  | 유형(방식) | 문자열만, DDL 미반영 | `btree`·`gin` 등 | DDL 반영 여부 D-21 |
  | 표현식 요소 | 없음 | 있음 | **미지원** — 모델 확장 여부 D-21 |
  | 정렬 방향·NULLS | 없음 | 있음 | **미지원** — D-21 |
  | 부분 인덱스 조건 | 없음 | 있음 | **미지원** — D-21 |
  | INCLUDE 컬럼 | 없음 | 있음 | **미지원** — D-21 |
  | 승인 상태 | 있음 | 없음 (원본 사실) | 물리 모델만 |

- **기존 코드 재사용 가능성:** `PhysicalModelService.saveIndex`·`delete`·`updateApproval`, `PhysicalModelDto.Index`, `TableIndexRepository`, ERD 의 `TableKeys` 대화상자(`features/erd/physicalEditing.tsx`)의 입력 부분, `Grid` + `columns.ts`, `TableDdlGenerator`, `ModelChangeRecorder`(이미 `PHYSICAL_INDEX` 추적). **화면 전용 저장 구조를 만들지 않는다.**
- **기술적 고려사항:**
  - 프로젝트 단위 목록 API 는 새 조회 API(`GET /api/physical/index/data`, `PageableUtil` 그리드 형식, VIEWER)가 필요하다 — 기존 화면 패턴대로 `@PreAuthorize`·프로젝트 범위.
  - 수정 API 를 만들면 같은 구성·이름 중복, PK·고유 컬럼 구성 거절, 승인 정책, 변경 이력(수정 1건으로 남는지)을 등록과 같은 기준으로 맞춘다. 삭제 + 등록 방식이면 이력이 삭제·추가 2건이고 내부 ID 가 바뀐다 (모델 버전 비교에서 REMOVED + ADDED).
  - 컬럼 속성 인덱스와 `TB_TBL_IDX` 의 같은 구성은 DDL 에서 한 번만 나온다(현행). 관리 화면에서 둘을 어떻게 보이고 어느 쪽에서 고치게 할지가 D-19 다.
  - 표현식·정렬·조건·INCLUDE 를 넣으려면 마이그레이션(새 버전 파일, 예제·COMMENT 포함)·DDL·이력 필드 목록(`ModelSnapshotFieldCoverageTest`)·모델 버전 `FORMAT_VERSION` 이 함께 바뀐다 — M-14 1차 범위에 넣지 않고 결정만 받는다.
  - 원본 인덱스 표시는 `lexorma-data` ↔ `lexorma-source` 가 서로 참조하지 않는 규칙 때문에 core 의 계약(또는 M-4 의 가져오기)을 거친다. M-14 에서는 표시하지 않는다.
- **선행 작업 및 의존성:** M-1(모델), M-8(ERD 편집·정합성 검증), M-9(이력), AI-2b 의 배포 패키징 검증 종료(5.3). M-4·M-10 ② 와는 독립 (원본 인덱스 가져오기·비교는 그쪽 책임).
- **완료 조건:**
  - 인덱스 관리 메뉴가 역할에 맞게 보이고(VIEWER 조회, USER 이상 + 액션 권한일 때만 변경 버튼), 프로젝트의 인덱스를 스키마·테이블로 찾아 조회·등록·(수정)·삭제·승인할 수 있다.
  - 관리 화면·물리 ERD·테이블 물리 모델 조회·DDL 이 같은 인덱스를 보인다. 변경이 DDL 과 변경 이력·모델 버전에 반영된다.
  - 승인·프로젝트 격리 정책이 기존과 같다 (다른 프로젝트 인덱스 ID 접근 거절, 승인된 인덱스 삭제 거절).
  - H2·PostgreSQL 테스트와 브라우저 검증(역할별, 다크·라이트, 좁은 화면, 영어) 통과.
- **테스트 및 검증 시나리오:** 목록 필터(스키마·테이블·고유·승인)와 페이징, 복합 인덱스 컬럼 순서 변경 → DDL 의 컬럼 순서, 관리 화면에서 등록한 인덱스가 ERD 대화상자에 보이고 ERD 에서 지운 인덱스가 목록에서 사라짐, 같은 구성·같은 이름·PK 구성 거절, 승인된 인덱스 삭제·수정 거절, 승인 권한 없는 USER 의 승인 거절, VIEWER 의 변경 버튼 미노출과 API 403, 다른 프로젝트 ID, 인덱스에 쓰인 컬럼 삭제 거절, 변경 이력·모델 버전 비교에 인덱스 변경이 나타남, 컬럼 속성 인덱스 표시 규칙(D-19).
- **우선순위:** P1 (모델링 보강 — AI 후속 재개 전에 진행, 5.3)
- **미확정 사항:** D-19 (컬럼 속성 인덱스와 인덱스 목록의 관계), D-20 (수정 API 또는 삭제 + 등록), D-21 (표현식·정렬·조건·INCLUDE·유형의 모델·DDL 반영 범위)

### M-15. VIEW 관리 (VIEW 모델링 신규 도입)

> **성격 :** 기존 기능의 화면 확장이 아니라 **내부 물리 모델에 VIEW 라는 새 객체를 들이는** 단계다. 테이블 모델에 섞지 않는다.

- **목적:** 설계 중인 VIEW 를 테이블과 구분되는 객체로 관리하고(이름·설명·정의 SQL·출력 컬럼·참조 객체), CREATE VIEW DDL 을 만들어 쓸 수 있게 한다.
- **1차 구현 (2026-11-13)** — [기록](view-management-m15.md). 아래 "현재 구현 상태" 는 착수 전 확인 내용이다.
  - **결정 :** D-22 VIEW 는 TABLE 과 독립 모델(`TB_VIEW`·`TB_VIEW_COL`·`TB_VIEW_RFRNC`·`TB_VIEW_CHG_DMND`), 출력 컬럼은 **직접 입력만**(SQL 에서 추출하지 않음). D-23 정의 SQL 은 조회 문 **원문 저장** + 정적 검사(파서 없음), 어디서도 실행하지 않음. D-24 참조 객체는 **사용자가 지정하는 객체 수준 메타데이터**(추출하지 않음), 내부 참조(테이블·VIEW) + 미확인 참조, 자기 참조·순환 거절, 참조된 테이블·VIEW·스키마 삭제 거절(자동 정리 없음). DDL 은 `CREATE VIEW`(CREATE OR REPLACE 없음), PostgreSQL 실행 검증, Oracle·MySQL·MariaDB 는 생성만.
  - **이름 공간 :** 프로젝트 단위(테이블명이 원래 프로젝트 안에서 하나다), 대문자 비교, 이름 공간 잠금으로 동시 등록·승인 직렬화.
  - **1차에서 하지 않은 것 :** 원본 VIEW 와 나란히 보기(②, M-4·M-10 과 함께), ERD 의 VIEW 편집·배치 저장, 버전 비교 ERD 의 VIEW, 출력 컬럼의 표준 용어 연결·품질 진단, 테이블+VIEW 통합 Export(M-11 — 2026-11-13 구현, [기록](integrated-ddl-export-m11.md)), Materialized View, 컬럼 수준 Lineage(M-12).
- **현재 구현 상태 (2026-11-13 코드 확인, 착수 전):**
  - **내부 물리 모델에 VIEW 가 없다.** `TableInfo`(`TB_TBL`)에는 객체 유형이 없고 모든 행이 테이블이다. VIEW 엔티티·API·화면·DDL 생성이 없다. 데이터 사전 예제에 단어 `뷰` 도 없다.
  - **원본 카탈로그** (AI-1b·AI-2b) : `TB_SRC_TBL.TBL_TYPE_CD = VIEW` 로 원본 VIEW 의 **존재·이름·COMMENT·출력 컬럼(이름·순서·타입·NULL·COMMENT)** 을 담는다. **VIEW 정의 SQL 은 수집·저장하지 않는다** (`SourceTableType` 의 주석, AI-2b 기록 4장). 구체화 뷰는 수집 대상이 아니다. 읽기 전용이고 물리 모델과 이어져 있지 않다.
- **세 가지를 구분한다:**

  | 구분 | 내용 | 상태 |
  |---|---|---|
  | ① 내부 VIEW 정의 | 사용자가 Lexorma 에서 작성하는 VIEW (정의 SQL 포함) | 미구현 — **M-15 의 대상** |
  | ② 원본 카탈로그의 VIEW 메타데이터 | 원본 DB 에서 수집한 VIEW 의 존재·컬럼·COMMENT | 구현 (AI-2b, 정의 SQL 없음) |
  | ③ 원본 VIEW 정의 SQL 수집 | `pg_get_viewdef` 등으로 정의를 읽어 원본 카탈로그에 저장 | 미구현 — 별도 작업 (아래) |

  **분석 : M-15 초기 구현에 ③ 은 필요 없다.** ① 은 사용자가 직접 쓰는 정의이고, ② 와의 연계는 이름·출력 컬럼 비교로 시작할 수 있다. ③ 이 필요한 것은 원본 VIEW 를 내부 모델로 **가져오기**(M-4)와 정의 차이 **비교**(M-10 ①②)다. 그래서 ③ 은 **"PostgreSQL VIEW 정의 수집"(AI-2 후속 작업, M-15 연계·M-4 의 VIEW 가져오기 선행)** 으로 따로 둔다. AI-2b 의 완료 범위는 바꾸지 않는다. ③ 을 할 때는 정의에 비밀값(접속 문자열·키)이 들어 있을 수 있어 저장·표시·AI 전달 정책([AI 로드맵 U-21](ai-metadata-roadmap.md#9-미확정-사항-종합))을 함께 정하고, 원본 카탈로그의 정규화 JSON·해시(AI-1c FORMAT)에 미치는 영향을 검토한다.
- **작업 범위:**
  - **메뉴** : `물리 모델 관리` 그룹에 **VIEW 관리**(예: `/viewManage`, 메뉴 id `view-manage`, 조회 VIEWER), 변경 액션 id 신설 여부(예: `view-edit`, USER) — `MENU_ROLES`·`MENU_GROUPS`·`menu.ts`.
  - **모델 설계** (테이블 모델과 분리) : VIEW(프로젝트·스키마 소속, 이름, 한글명·설명, 정의 SQL, 승인 상태, 감사 컬럼) / 출력 컬럼(이름·순서·타입(선택)·설명·표준 용어 연결(선택)) / 참조 객체(VIEW 가 읽는 테이블·VIEW, 사용자가 지정하거나 정의에서 추출 — D-23). 같은 스키마 안에서 테이블과 VIEW 의 이름 충돌 규칙(DBMS 는 같은 이름 공간). 테이블·컬럼 엔티티와 공유할 것(스키마, 감사 컬럼, 표준 용어 연결 방식)은 재사용하되 정의 SQL 을 테이블 모델에 넣지 않는다.
  - **관리 기능** : 목록(프로젝트·스키마별, Grid), 등록·수정·삭제·승인, 정의 SQL 편집·조회, 출력 컬럼 관리 범위(직접 입력 / 정의에서 추출 / 둘 다 — D-22), 참조 테이블·VIEW 표시와 그 테이블로 이동.
  - **DDL** : 지원 DBMS 의 `CREATE VIEW 스키마.이름 [(컬럼…)] AS 정의` 생성·조회·복사 (`CREATE OR REPLACE` 여부·DBMS 별 차이 정리). **원본 DB 에 CREATE·ALTER·DROP VIEW 를 실행하지 않는다.**
  - **SQL 처리 정책** : 정의 SQL 은 내부 모델에 텍스트로 저장한다. 검증은 별도 설계 대상이다 — 후보는 형식 검사(길이·문장 하나·`SELECT`/`WITH` 로 시작·문장 구분자 금지, M-1 의 CHECK 식 검증과 같은 방식), 서버 안 SQL 파서(새 의존성이라 별도 결정), 참조 객체 이름 확인. **어떤 DB 에서든 SQL 을 실행해 검증하지 않는다** (원본 DB·Lexorma DB 모두).
  - **원본 VIEW 와의 연계** : 원본 카탈로그 VIEW(②)를 같은 스키마·이름의 내부 VIEW 와 나란히 보이는 비교(존재·출력 컬럼)까지. 원본 → 내부 가져오기는 M-4, 정의 비교는 ③ 이후 M-10.
  - **ERD·데이터 사전 연결 (검토)** : 물리 ERD 에 VIEW 노드(참조 관계를 점선 등으로 구분)를 둘지, 출력 컬럼을 표준 용어에 이어 표준화 품질 진단(M-5)에 넣을지 — 1차 범위 밖으로 두고 결정만 받는다.
- **기존 코드 재사용 가능성:** 스키마(`SchemaInfo`)·프로젝트 범위·승인(`AuthUtil.isApprovalAvailable()`) 패턴, `Grid`·`useDialog`, `TableDdlGenerator` 의 이름·스키마 접두어 규칙(DBMS 별), M-1 의 CHECK 식 검증(문장 구분자 거절), 모델 변경 이력(`ModelChangeRecorder` 에 새 대상 유형 추가), 모델 버전(대상 유형 추가), 프로젝트 삭제 정리(`ProjectDataCleanup`), 원본 카탈로그 조회 API(②).
- **기술적 고려사항:**
  - 새 테이블은 새 버전 마이그레이션(PostgreSQL·H2) + `COMMENT ON` + 예제(물리·논리 모델 행, 용어)를 한 파일에 둔다. 단어 `뷰` 등은 데이터 사전에 없어 명명 규칙([db-naming-standard.md](db-naming-standard.md))의 단어 추가가 필요하다.
  - 이력·버전 : `ModelChangeRecorder` 의 필드 목록과 대상 유형 코드(20자 이내), `ModelSnapshotFieldCoverageTest`, `ModelVersionService.FORMAT_VERSION`, 모델 버전 비교·ERD(M-10 ③) 에 VIEW 를 넣을지.
  - 참조 객체의 무결성 : VIEW 가 참조하는 테이블·컬럼의 삭제·이름 변경을 막을지, 경고만 할지 (D-23). 출력 컬럼과 참조 컬럼의 관계는 M-12(영향 분석·SQL Lineage)와 겹치므로 M-15 는 객체 단위 참조까지만.
  - 프로젝트 삭제 시 VIEW 데이터도 지운다 (`ProjectDeletionIntegrationTest` 가 `PRJ_SN` 테이블을 확인한다).
  - 지원 DBMS : DDL 생성은 `DbType` 4종의 VIEW 문법 차이(스키마 접두어, `WITH CHECK OPTION`, MySQL 의 `ALGORITHM` 등)를 정리한 뒤 초기 범위를 정한다 (D-24).
  - 모듈 경계 : 원본 VIEW(②)는 `lexorma-source`, 내부 VIEW(①)는 `lexorma-data` 다. 둘의 비교는 core 의 계약을 거친다.
- **선행 작업 및 의존성:** M-1(스키마), M-3(관리 화면 패턴), M-9(이력·버전), M-14 완료 후 착수(5.3). ③ 원본 VIEW 정의 수집은 M-15 의 선행이 아니다 (M-4 의 VIEW 가져오기와 M-10 의 정의 비교에 필요).
- **완료 조건:**
  - VIEW 관리 메뉴에서 프로젝트·스키마의 VIEW 를 등록·조회·수정·삭제·승인할 수 있고, 정의 SQL 을 저장·조회할 수 있다.
  - 지원 DBMS 범위에서 CREATE VIEW DDL 을 생성·복사할 수 있다. 어떤 경로로도 원본 DB 에 SQL 을 실행하지 않는다.
  - 내부 VIEW 와 원본 카탈로그 VIEW 가 저장·화면에서 구분된다.
  - 프로젝트 격리·권한(VIEWER 조회, 액션 권한일 때만 변경)·승인·변경 이력·프로젝트 삭제 정책이 적용된다.
  - H2·PostgreSQL 테스트와 브라우저 검증 통과.
- **테스트 및 검증 시나리오:** VIEW 등록·수정·삭제와 정의 SQL 보존(줄바꿈·주석 포함), 같은 스키마의 테이블·VIEW 이름 충돌, 문장 구분자·비 SELECT 정의 거절(검증 방식 결정 후), DBMS 별 DDL 골든 파일, 정의 SQL 이 어디서도 실행되지 않음(SQL 실행 경로 부재 확인), 승인된 VIEW 수정·삭제 거절, 다른 프로젝트 ID, VIEWER 변경 403, 변경 이력·모델 버전에 VIEW 가 나타남, 프로젝트 삭제 후 잔존 없음, 원본 카탈로그 VIEW 와 나란히 보기(이름·출력 컬럼 차이).
- **우선순위:** P1 (모델링 보강 — M-14 다음, AI 후속 재개 전, 5.3)
- **미확정 사항:** ~~D-22 (출력 컬럼 관리 범위), D-23 (참조 객체 지정·추출과 무결성), D-24 (지원 DBMS·DDL 문법 범위와 SQL 검증 방식)~~ → 2026-11-13 결정 (위 1차 구현, 번호는 지시서 기준 D-22 독립 모델·D-23 정의 SQL·D-24 참조 객체). D-25 이름 공간은 프로젝트 단위로 확정(스키마 단위 식별자는 M-4 에서 재검토) → **2026-11-13 스키마 단위로 변경** ([기록](schema-scoped-naming.md)), D-26 승인 대기 이름은 선점하지 않음(승인 때 재검증), D-27 SQL 파서 미도입. 남은 결정 : 원본 VIEW 비교 범위, 미승인 VIEW 직접 수정의 버전 충돌 검증 ([기록 11장](view-management-m15.md#11-잔여위험)), [AI 로드맵 U-21](ai-metadata-roadmap.md#9-미확정-사항-종합) (원본 VIEW 정의 수집 시 비밀값 처리)

## 7. AI 기능과의 의존관계

| 관계 | 내용 |
|---|---|
| AI-1 ↔ M-1 | 설명 분리·이력(AI-1)과 관계·스키마·인덱스(M-1)는 **같은 마이그레이션 묶음**으로 설계 |
| AI-2 → M-10 ① / AI-2 → M-4 → M-10 ② | 최신화 전후 비교는 수집 결과만으로(①), 모델 ↔ 원본 비교는 가져오기 이후(②). 모델 버전 비교(③)는 M-9 후속 |
| AI-8 작업 모델 → M-4 | 수집·가져오기 이력은 작업 이력으로 남긴다(M-9 를 기다리지 않음) |
| AI-1 메타데이터 버전 → AI-5 | 근거 버전이 바뀐 AI 제안은 승인 시 재검증 |
| M-5 → AI-6 → AI-7 | 표준화 규칙(M-5)을 품질 검사 체계(AI-6)가 실행하고, 의미 검사(AI-7)는 후보만 LLM 에 전달 |
| M-1·M-2 → AI-12 → M-13 | 관계 모델·ERD 가 있어야 추정 관계를 저장·표시 |
| M-2·M-3 → AI-13 | AI ERD 분석은 기존 ERD·관계 모델을 재사용 |
| AI-5 → M-3 | AI 설명은 ERD 상세에 표시만, 승인은 AI-5 흐름 |
| M-12 ← AI-5 | 영향 분석은 AI 설명 재검토 대상 식별에 쓰임 |
| AI-2b → M-14 | 원본 인덱스의 표현식·정렬·조건·INCLUDE 는 물리 모델 확장 여부의 근거(D-21). 원본 인덱스는 읽기 전용이고 물리 모델과 서로 덮어쓰지 않는다 |
| AI-2b → M-4c | 원본 매핑은 수집한 카탈로그(완료된 수집의 버전)만 읽고 core 계약(`SourceCatalogReader`)으로 잇는다. 원본 DB 에 다시 접속하지 않는다 |
| SEC-1 → M-4 원본 연결 | 외부 연결 접근 정책(AI 로드맵 SEC-1)이 바뀌면 기존 원본 연결의 전환 절차가 필요하다. M-4c 완료 조건에는 넣지 않는다 |
| AI-2b → M-15, AI-2 후속(VIEW 정의 수집) → M-4·M-10 | 원본 VIEW 의 존재·컬럼은 M-15 의 비교에 쓰고, 정의 SQL 수집은 VIEW 가져오기·정의 비교의 선행이다 (M-15 선행 아님) |

**병렬 진행 원칙:** P1 에서 모델링 트랙(M-0 → M-1 → M-2 → M-3, M-5, M-6 → M-7)과 AI 트랙(AI-0 → AI-3 → AI-4 → AI-5)은 서로 기다리지 않는다. 합류 지점은 M-1 ↔ AI-1(모델 설계)과 M-4 ↔ AI-2(역공학)이다.

## 8. 제외 범위

다음은 제품 방향 변경으로 **제거된 기능**이며 로드맵에 다시 넣지 않는다. 저장소 확인 결과 관련 코드(`codeRule`, 메서드명 생성, 설계서·테스트 시나리오 출력, `lexorma-design`, `lexorma-chat`)는 남아 있지 않다.

- 코드 규칙 관리, 메서드명·함수명 자동 생성
- 코드 생성용 템플릿 중심 기능
- 설계서 생성 중심 기능, 설계 문서 생성에만 종속된 메뉴·기능
- 원본 DB 에 대한 DDL·DML·SQL 실행 (DDL 은 생성·출력만)

**제외 대상이 아닌 것:** 데이터 표준화 명명 규칙, 표준 단어·용어·도메인 관리, 테이블·컬럼 물리명 정의, 데이터 모델링, ERD, DB 역공학, DDL 생성·Export, 데이터 사전 Export. *코드 생성 기능과 데이터 모델링·표준화 기능을 혼동하지 않는다.*

- 스키마와 예제 데이터는 Flyway 가 관리한다 (`lexorma-app/src/main/resources/db/migration/{postgresql,h2}`). JPA 는 `ddl-auto: validate` 다.
- **기준선** : `V0__init.sql`(스키마)·`V1__seed_data.sql`(예제)는 고정이다. M-4c 의 `V2__source_mapping.sql` 이 첫 증분 파일이다.
- **적용 상태 (2026-11-13 확인)** : PostgreSQL·H2 모두 V2 가 있다. 개발 DB `lexorma` 에 V2 가 적용됐고, V0·V1 체크섬 불일치 없이 V2 만 증분으로 들어갔다 ([M-4c 기록 3장](source-mapping-m4c.md#3-테이블마이그레이션-v2__source_mappingsql-postgresqlh2)).
- **원칙**
  1. 이미 적용된 마이그레이션(V0·V1·V2 와 이후 모든 파일)은 고치지 않는다.
  2. 스키마 변경은 다음에 쓸 수 있는 버전(지금은 `V3__…`)의 새 파일로 더한다.
  3. PostgreSQL·H2 두 벤더의 파일은 같은 버전·같은 내용으로 함께 만든다.
  4. 개발 DB 를 다시 만드는 것을 전제로 구현하지 않는다.
  5. 기존 데이터를 보존하고, 기존 DB 의 증분 업그레이드(이전 버전까지 적용된 DB → 새 버전)를 검증한다.
  6. 적용된 파일의 체크섬이 바뀌는 변경(주석·공백 포함)을 하지 않는다.
  7. 데이터 이전이 필요하면 그 이전을 새 마이그레이션에 명시적으로 쓴다.
- 새 `TB_` 테이블의 COMMENT·예제 데이터(데이터 사전 용어 → `TB_TBL`·`TB_COL` → 논리 엔터티, 예제 인덱스)는 **그 테이블을 만드는 같은 새 마이그레이션**에 넣는다 (`V0SeedMigrationTest`·`SmokeTest`). 예제 데이터를 스키마 마이그레이션과 분리할지는 후속 검토다 ([M-4c 기록 12.3](source-mapping-m4c.md#123-v2-예제-데이터)).
- 정식 출시 때 이 정책을 그대로 유지하고 README 의 "Database migrations" 를 그때 다시 맞춘다.

### 지난 경과 (기록용 — 지금은 유효하지 않다)

- **~2026-11-12 (출시 전 단순화)** : `V0`·`V1` 두 파일만 두고 스키마가 바뀌면 두 파일을 고쳤다. 그 파일로 만든 DB 는 체크섬이 달라져 개발·검증 DB 를 다시 만들어야 했다. **M-4c 부터 폐기.**
- **AI-2b (2026-11-13)** : 소유자 결정으로 새 버전 파일을 더하기 시작했다 (`V2__source_index_expression.sql`, 이어서 M-14 `V3__index_management.sql`·`V4__index_advanced.sql`, M-15 `V6__view_management.sql` 등).
- **2026-11-13 V0·V1 재통합 (소유자 결정)** : M-4 를 앞두고 예전 V2~V6 의 스키마 변경을 V0 에, 예제를 V1 에 합쳤다 (같은 예제 ID, 스키마 단위 TABLE·VIEW 이름 정책 반영). 예전 V2~V6 을 적용한 DB 는 Flyway 검증에서 멈춰 재생성했다 ([기록 7장](schema-scoped-naming.md#7-기존-db-호환성-주의)). 그래서 **예전 V2~V6 과 지금의 `V2__source_mapping.sql` 은 다른 파일이다.**
- **M-4c (2026-11-13, 소유자 지시)** : 다시 증분 방식으로 돌아와 위의 "현재 유효한 정책" 이 시작됐다.
