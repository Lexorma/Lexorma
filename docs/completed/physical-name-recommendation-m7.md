# M-7 3차. 표준 사전 기반 물리명 추천 — 설계 결정과 구현 기록

> [데이터 모델링 로드맵](../reference/data-modeling-roadmap.md) M-7 의 마지막 단계(물리명 추천)와 2차 UI 보완의 기록이다. 1차 : [logical-physical-mapping-m7.md](logical-physical-mapping-m7.md), 2차 : [model-mapping-quality-m7.md](model-mapping-quality-m7.md).
> 작성일 2026-11-11 (2026-11-21 일괄 적용 1차 — 8장 : 일괄 적용 판정, 아래 1·2·7장의 바뀐 부분은 8장 표시. 같은 날 일괄 적용 2차 — 9장 : 서버 적용 API, 2차 후속 — 10장 : 컬럼 등록 동시성, 3차 — 11장 : 화면·최종 검증 — **물리명 추천 일괄 적용 완료**). **DB 변경 없음** (Flyway V0~V4 그대로, 새 마이그레이션 없음). 추천 목록은 조회 전용이고, 이름을 바꾸는 것은 9장의 일괄 적용 API(미리보기 → planToken → 적용) 하나다.

## 1. 기존 구조 분석과 결정

| 확인 항목 | 결과 → 결정 |
|---|---|
| 표준 용어의 영문약어 | `TB_STD_TRM` 에 **저장된 값**이다. 화면 등록은 용어명과 단어 수가 같은 약어를 입력받아 각 약어가 표준 단어인지 검증하고(`validateWordCount`·`getStandardTermDomain`), 엑셀 업로드는 약어를 쓰지 않는 프로젝트에서 단어 영문명을 조합해(`toEnglishTermName`) 저장한다. 약어 없이 용어를 등록하는 경로는 없다 → **컬럼명 추천 = 저장된 영문약어.** 약어가 비어 있는 용어(직접 넣은 데이터)는 다시 조합하지 않고 추천 불가로 둔다 — 조합 규칙의 결과가 곧 저장된 약어이기 때문이다 |
| 컬럼명 규칙 | "컬럼명 = 연결한 표준 용어의 영문약어" 하나뿐 (컬럼 등록·일괄 저장·업로드, [M-5 2차](standardization-quality-m5.md)). M-7 2차의 명칭 진단이 이미 이 값을 기대 컬럼명으로 썼다 → 그 계산을 추천 서비스로 옮겨 **한 곳에서** 한다 |
| 테이블명 규칙 | **있다.** 테이블 등록이 쓰는 `TableDesignService.generateTableName` : 한글명을 공백·밑줄로 나눈 단어가 모두 **승인된 표준 단어**면 `프로젝트 접두어 + 단어 영문약어(_ 연결, 대문자)`. 단어 순서는 적은 순서 그대로, 같은 이름의 단어가 여럿이면 승인된 것 우선 → **엔터티명에 같은 규칙을 적용한다.** 결정적이지 않은 부분(붙여 쓴 엔터티명을 단어로 쪼개기, 약어 추측)은 하지 않는다 |
| 논리 엔터티 | 표준 용어·단어를 참조하지 않는다 (이름·설명·승인 상태만). 근거는 **엔터티명 문자열**뿐이다 → 위 규칙으로 나뉘지 않으면 추천 불가 (사유에 걸린 단어를 적는다) |
| 이름 중복 기준 | 컬럼명은 **같은 테이블** 안, 테이블명은 **같은 스키마**의 테이블·VIEW (M-15 에서 스키마 단위로 바뀌었다 — 저장 경로 `ObjectNamespace.conflict`). 3차 작성 당시 이 칸은 "같은 프로젝트" 였고 코드는 그 뒤 스키마 단위로 고쳐졌다 (VIEW 이름은 일괄 적용 1차에서 추가, 8.3) → 충돌 판정도 같은 범위 |
| DBMS 식별자 규칙 | `TableDdlGenerator` 는 식별자를 따옴표로 감싸지 않는다 → 지원하는 모든 DBMS 에서 대소문자만 다른 이름은 같은 객체다 → **대소문자 무시**로 비교. 3차 당시 식별자 길이 제한·예약어 규칙이 저장소에 없어 판정하지 않았다. 길이·문자 규칙은 M-7 보강 1차의 `DbIdentifierRules` 로 생겼고 일괄 적용 판정이 그것을 쓴다 (8.4). 예약어는 여전히 없다 (P13) |
| 이름 변경 기능 | 테이블은 한글명을 고치면 테이블명이 다시 만들어지고(`updateTable`), 컬럼은 컬럼 편집(일괄 편집)·컬럼 관리에서 용어를 바꾼다 → 추천 화면은 그 화면들로 **이동만** 시킨다. 새 적용 API 는 만들지 않았다 |
| 문서 | `CLAUDE.md` 는 저장소에 없다 (다른 문서가 인용만 한다) → 갱신하지 않았다 |

## 2. 추천 정책

### 2.1 컬럼명 (`source = STANDARD_TERM`)

추천 컬럼명 = 논리 속성에 연결된 표준 용어의 영문약어 (앞뒤 공백 제거). 속성 1개가 1행이며 매핑 여부와 관계없이 나온다.

| 순서 | 조건 | 상태 | 사유 |
|---|---|---|---|
| 1 | 속성에 표준 용어가 없다 / 용어에 영문약어가 없다 | `UNAVAILABLE` (추천명 없음) | 논리 속성에 표준 용어가 없어… / …영문약어가 없어 기대 컬럼명을 알 수 없습니다 |
| 2 | 매핑된 컬럼의 이름 = 추천명 (대소문자 무시) | `ALREADY_MATCHED` | 현재 컬럼명이 표준 용어의 영문약어와 같습니다 |
| 3 | 엔터티에 매핑된 테이블에서 **이 속성의 컬럼이 아닌 다른 컬럼**이 추천명을 쓴다 | `CONFLICT` | 그 컬럼이 속성 X 에 매핑됨 / 논리 속성에 매핑되지 않은 컬럼 (구분) |
| 4 | 그 밖 | `AVAILABLE` | 현재 컬럼명과 다름 / 속성이 컬럼에 매핑되지 않음 / 엔터티가 테이블에 매핑되지 않음 (구분) |

- 매핑하지 않은 속성도 추천명은 나온다 (현재 컬럼명 없음). 같은 이름의 컬럼이 테이블에 이미 있으면 "새 컬럼으로 만들 수 없는 이름"이라 충돌이다 — 그 컬럼이 매핑 대상일 수 있다는 것은 사유로 알 수 있지만 **자동으로 매핑하거나 후보로 제안하지 않는다.**
- 한 엔터티의 두 속성이 같은 용어를 쓰면 둘 다 같은 추천명이 나온다. 아직 그 이름의 컬럼이 없으면 둘 다 `AVAILABLE` 이다 (추천끼리의 충돌은 보지 않는다 — 7장).

### 2.2 테이블명 (`source = STANDARD_WORD`)

추천 테이블명 = `generateTableName(엔터티명)`. 엔터티 1개가 1행.

| 순서 | 조건 | 상태 |
|---|---|---|
| 1 | 엔터티명에 단어가 없다 / 표준 단어로 등록되지 않은 단어가 있다 / 승인되지 않은 표준 단어가 있다 | `UNAVAILABLE` (걸린 단어를 사유에 적는다) |
| 2 | 매핑된 테이블의 이름 = 추천명 (대소문자 무시) | `ALREADY_MATCHED` |
| 3 | 같은 스키마(매핑된 테이블의 스키마, 매핑이 없으면 기본 스키마)의 **다른 테이블 또는 VIEW** 가 추천명을 쓴다 | `CONFLICT` (엔터티 X 에 매핑된 테이블 / 매핑되지 않은 테이블 / VIEW — VIEW 는 1차에서 추가, 8.3) |
| 4 | 그 밖 | `AVAILABLE` |

응답의 `words` 에 단어별 변환 결과(단어 → 영문약어, 승인·미승인·미등록), `tablePrefix` 에 프로젝트 접두어가 들어 있다 (추천 근거).

**테이블명 추천이 가능한 조건 :** 엔터티명을 표준 단어를 공백(또는 `_`)으로 띄어 적었을 때. 예제(LEXORMA)의 엔터티명은 물리 예제의 테이블 한글명이라 37개 전부 `ALREADY_MATCHED` 다. "회원등급"처럼 붙여 쓴 이름은 그 문자열이 표준 단어가 아니면 추천 불가다.

### 2.3 정합성 명칭 진단과의 관계

```text
표준 용어(영문약어) ─▶ PhysicalNameRecommendationService.recommendColumnName ─┬─▶ 물리명 추천 API (상태·근거·충돌)
                                                                              └─▶ 정합성 비교 NAME 진단 (기대 컬럼명)
```

| 추천 상태 | 명칭 진단 (매핑된 속성만) |
|---|---|
| `ALREADY_MATCHED` | `MATCH` |
| `UNAVAILABLE` | `NOT_COMPARABLE` (불일치로 세지 않는다) |
| `AVAILABLE`·`CONFLICT` | `MISMATCH` — 충돌은 명칭 일치 여부와 다른 개념이라 진단은 "다르다"까지만 본다 |

명칭 진단의 판정·사유 문구는 2차와 같다. M-5 품질 진단(`StandardizationQualityService`)은 건드리지 않았다.

## 3. 백엔드 (`lexorma-data` `mapping/`)

| 구성 | 내용 |
|---|---|
| `GET /api/modelMapping/recommendation/column/summary?modelId` (VIEWER) | `total`(모델의 속성 수)·`available`·`alreadyMatched`·`unavailable`·`conflict`. 네 상태의 합 = `total` |
| `GET /api/modelMapping/recommendation/column/data` (VIEWER) | 그리드 형식. 조건 `modelId`·`entityId`·`attributeId`·`columnId`·`status`, 검색 `entityName`(기본)·`logicalName`·`currentPhysicalName`·`recommendedPhysicalName`, 정렬은 같은 네 필드 (기본 엔터티명 → 속성 순서). `modelId` 는 `attributeId`·`columnId` 가 없으면 필수. 1행 : `logicalAttributeId`·`logicalName`·`termId`·`termName`·`termAbbreviation`·`physicalColumnId`·`currentPhysicalName`·`recommendedPhysicalName`·`status`·`source`·`reason` + 모델·엔터티·스키마·테이블 |
| `GET /api/modelMapping/recommendation/table/data` (VIEWER) | 그리드 형식. 조건 `modelId`·`entityId`(`modelId` 는 `entityId` 가 없으면 필수), 검색 `logicalName`(엔터티명)·`currentPhysicalName`(테이블명). 1행 : `logicalEntityId`·`logicalName`·`physicalTableId`·`currentPhysicalName`·`recommendedPhysicalName`·`status`·`source`·`reason`·`tablePrefix`·`words` |
| `GET /api/modelMapping/entity/data` 에 `entityId` 조건 추가 | 그 엔터티 1건만 (4장의 ID 포커스). 기존 조건·응답은 그대로 |
| `PhysicalNameRecommendationService` | 읽기 전용. `recommendColumnName`·`sameName`(static)은 정합성 비교와 공용 |
| `PhysicalNameRecommendationQueryRepository` | 컬럼명 추천은 **상태 조건까지 DB 에서** 걸러 페이징한다 (추천명이 저장된 약어라 SQL 로 판정할 수 있다). 충돌 사유용으로 한 쪽 분량의 "그 이름을 쓰는 컬럼(테이블)"을 1번 더 읽는다 |
| `TableDesignService.generateTableNames` | 여러 한글명을 표준 단어 조회 1번으로 변환. `generateTableName` 과 같은 내부 규칙을 쓴다 (단어 조회 방법만 다르다) |

- 단건 조회용 엔드포인트(`/column/{attributeId}`·`/table/{entityId}`)는 따로 만들지 않고 목록의 `attributeId`·`columnId`·`entityId` 조건으로 대신한다.
- **조회 수 :** 컬럼명 목록 = 모델 확인 1 + 행 1 + 건수 1 + 충돌 이름 1. 요약 = 모델 확인 1 + 상태별 건수 4. 테이블명 목록 = 모델 확인 1 + 엔터티 행 1 + 건수 1 + 표준 단어 1 + 프로젝트(접두어) 1 + 충돌 이름 1. 행마다 조회하지 않는다 (N+1 없음). 정합성 비교와 달리 모델 전체를 메모리에 올리지 않는다.
- 테이블명 목록은 표준 단어 변환이 자바 규칙이라 **상태 조건을 받지 않는다** (엔터티 수는 속성 수보다 훨씬 적다).
- **프로젝트 격리 :** 프로젝트는 항상 로그인 프로젝트. 다른 프로젝트의 `modelId` 는 `LOGICAL_MODEL_IS_NOT_DEFINED`(400), 다른 프로젝트의 `entityId`·`attributeId`·`columnId` 는 결과 0건. 표준 단어·접두어·충돌 테이블도 로그인 프로젝트 것만 본다.

| 컬럼 관리 | 주소의 `?searchColumn=&searchQuery=` 를 처음 검색 조건으로 받는다 (데이터 사전과 같은 방식) |
| 매핑 상세 대화상자 | [물리명 추천 보기] 추가 (그 엔터티로 좁힌 추천 탭) |

### 4.1 2차 UI 보완

| 항목 | 내용 |
|---|---|
| 엔터티 ID 포커스 | 2차는 엔터티명 부분 일치 검색으로 좁혀 이름이 겹치는 엔터티가 함께 보였다 → 목록 API 의 **`entityId` 조건**으로 그 엔터티 1건만 조회한다 (서버 페이징·다른 조건과 함께 DB 에서 거른다). `entityId` 는 세 탭 모두의 엔터티 범위다. 없는 ID·숫자가 아닌 값·다른 프로젝트·다른 모델의 엔터티는 무시하고 전체를 보여 준다 (lookup 이 null) |
| ERD 미저장 배치 확인 | 코드는 2차에서 기존 `leave` 를 쓰도록 되어 있었고 화면 검증만 빠져 있었다 → 6.2 에서 논리 ERD(엔터티 패널·엔터티 상세)·물리 ERD(테이블 상세·컬럼 상세)의 이동을 확인했다. 수정한 코드는 없다 |

## 7. 제약 · 후속

- **식별자 길이·예약어** : ~~DDL 생성에도 같은 검사가 없다~~ → M-7 보강 1차에 `DbIdentifierRules`(길이·문자, 예약어 없음)가 생겼고, 일괄 적용 1차부터 추천 행의 적용 판정이 그것을 쓴다 (8.4). 추천 상태(`status`)는 그대로 길이를 보지 않는다. 예약어는 판정하지 않는다.
- **추천끼리의 충돌** : 상태(`status`)는 지금도 판정하지 않는다 (둘 다 추천 가능). 일괄 적용 1차부터 적용 판정의 `RECOMMENDATION_DUPLICATE` 로 알린다 (8.5).
- **붙여 쓴 엔터티명** : 표준 단어 사전으로 문자열을 분해하는 규칙(최장 일치 등)은 모호해서 만들지 않았다. 엔터티에 테이블 한글명이나 표준 단어 구성을 직접 저장하면(논리 모델 확장) 근거가 명확해진다.
- **추천 적용** : 일괄 적용은 1~3차로 진행 중이다 — 1차(판정)만 끝났다 (8장). 자동 적용은 없다. 만들 경우 테이블은 `updateTable`(한글명 → 테이블명 재생성, 참조 컬럼·관계 동기화), 컬럼은 승인 정책·관계·인덱스 참조를 거쳐야 한다.
- **테이블명 추천의 상태 조건·요약** : 표준 단어 변환이 자바 규칙이라 없다. 필요해지면 단어 조합 결과를 SQL 로 계산하거나 추천 결과를 저장해야 한다.
- 정합성 비교의 메모리 기반 페이징은 그대로다 (2차 문서 7장).

FK·인덱스·UNIQUE 구성 컬럼, 논리·물리 매핑, 상속 PK 매핑, ERD 배치, 원본 컬럼 확정 매핑(DEC-06)은 모두 ID 참조라 이름 변경의 영향이 없다.

### 8.3 이름 공간 (같은 스키마의 테이블·VIEW)

- 테이블명 추천의 `CONFLICT` 에 **같은 스키마의 VIEW** 를 더했다 (사유 "같은 스키마에 추천 테이블명과 이름이 같은 VIEW … 이(가) 있습니다"). 다른 스키마의 같은 이름 테이블·VIEW 는 충돌이 아니다 (M-15).
- 상태의 의미는 그대로다 ("추천명을 다른 물리 객체가 지금 쓴다"). 3차의 테이블 상태는 자바 판정이라 요약·조건 계약이 없다 — 컬럼 상태·요약·SQL 조건은 바뀌지 않았다.

### 8.4 응답 (기존 필드 그대로 + `applicability` 하나 추가)

`GET /api/modelMapping/recommendation/column/data`·`/table/data` 의 행 끝에 `applicability` 를 더했다 (새 API 없음, 기존 필드·상태·요약·검색·정렬·페이징·권한 그대로) :

```text
applicability : { selectable : boolean, blockers : [ { code, reason, related[] } ], warnings : [ … ] }
```

| 코드 | 의미 | 막음 |
|---|---|---|
| `NOT_RECOMMENDED` | 추천명이 없다 (상태 UNAVAILABLE) | ✓ |
| `NO_CHANGE` | 현재 이름 = 추천명 (ALREADY_MATCHED) | ✓ |
| `NOT_MAPPED` | 바꿀 물리 객체가 없다 (속성·엔터티 미매핑 — 만드는 것은 물리 테이블 생성) | ✓ |
| `NAME_CONFLICT` | 다른 객체가 지금 그 이름을 쓴다 (CONFLICT) | ✓ |
| `RECOMMENDATION_DUPLICATE` | 같은 이름 공간의 다른 후보도 같은 새 이름을 받는다 (8.5) | ✓ |
| `IDENTIFIER_INVALID` | 프로젝트 DBMS 의 비인용 식별자 문자·길이 위반 (`DbIdentifierRules.check`, 사유 문구도 같은 함수) | ✓ |
| `IDENTIFIER_NOT_RECOMMENDED` | DBMS 는 받지만 Lexorma 권장 형식이 아니다 | 경고 |
| `TABLE_APPROVED` / `COLUMN_APPROVED` | 승인된 테이블 / 컬럼 (P-04) | ✓ |
| `TERM_MISMATCH` | 컬럼 용어 ≠ 속성 용어 (P-03) | ✓ |
| `COLUMN_TERM_MISSING` | 컬럼에 용어가 없다 — P-03 범위 밖이라 **결정 전까지 보수적으로 막는다** (8.10) | ✓ |
| `CHECK_REFERENCE` / `INDEX_REFERENCE` / `VIEW_REFERENCE` | 옛 이름을 쓰는 CHECK·인덱스 식/조건·VIEW 정의 (8.6) | ✓ |
| `REFERENCE_UNVERIFIABLE` | SQL 을 낱말로 나눌 수 없어 참조 여부를 판정할 수 없다 | ✓ |

- 판정 대상 = 매핑된 물리 객체가 있고 추천명이 현재 이름과 다른 행 (상태 AVAILABLE·CONFLICT). 나머지는 상태에서 바로 정해지는 코드 하나만 붙는다.
- 컬럼 이름 변경은 **컬럼의 승인만** 본다 — 컬럼 일괄 저장이 승인된 테이블에만 컬럼을 등록하게 하므로, 테이블 승인까지 막으면 거의 모든 컬럼이 막힌다 (8.10 확인 요청). → **2차에서 P-10 으로 바뀌었다** : 컬럼 + 소속 테이블 승인을 모두 본다 (목록 판정도 같이, 9.1).
- 판정은 조회 시점의 계산이며 저장하지 않는다. 2차 적용은 잠금 뒤 같은 판정을 다시 해야 한다 (P-04).

### 8.5 추천끼리 충돌

- `RenameSafety.duplicates(후보 목록)` : 같은 이름 공간(컬럼 = 테이블 ID, 테이블 = 스키마 ID)에서 같은 새 이름(앞뒤 공백·대소문자 무시)을 받는 서로 다른 대상. 후보 목록만 받는 순수 함수라 2차가 **선택 집합**으로 다시 부를 수 있다.
- 1차의 후보 = **전체 추천 후보** : 컬럼은 그 테이블의 매핑된 컬럼 전체, 테이블은 그 스키마의 매핑된 테이블 전체 중 추천명이 현재 이름과 다른 것 (페이지·검색 조건과 무관 — 한 건만 조회해도 페이지 밖의 후보를 본다). 다른 이유로 막힌 후보도 넣는다 (보수적).
- 이름 맞바꾸기·연쇄 변경(A → B, B → A)은 대상 이름을 지금 다른 객체가 쓰므로 `NAME_CONFLICT` 로 막힌다. 지원하지 않는다.
- 매핑되지 않은 속성(나중에 생성으로 만들 컬럼)은 후보가 아니다.

### 8.6 이름 문자열 참조 (CHECK · 인덱스 · VIEW)

새 범용 SQL 파서를 만들지 않았다. `table/ddl/SqlIdentifierTokens` 는 **낱말 분리기**다 — `ViewDefinitionSql` 과 같은 규칙으로 문자열('' · MySQL·MariaDB `\` · PostgreSQL `E'…'`·`$태그$` · Oracle `q'[…]'`)과 주석(`--`·`#`·`/* */`, PostgreSQL 겹친 주석)을 건너뛰고, 남은 낱말과 따옴표 식별자 내용(`"…"`·백틱)을 대문자로 모은다. 판정(`mapping/service/RenameSafety`, 순수 함수)은 "옛 이름이 낱말로 **나오면** 참조로 본다" 는 보수적 규칙이다 — 함수명·별칭·다른 테이블의 같은 이름도 막는다(거짓 양성 허용), 리터럴·주석 안의 이름은 막지 않는다. 낱말을 확실히 나눌 수 없는 SQL(닫히지 않은 따옴표·주석, PostgreSQL 유니코드 이스케이프 식별자 `U&"…"`, 읽을 수 없는 변경 요청 JSON)은 `REFERENCE_UNVERIFIABLE`.

| 대상 | 테이블 이름 변경을 막는 것 | 컬럼 이름 변경을 막는 것 |
|---|---|---|
| CHECK (그 테이블) | 식에 테이블명 낱말 | 구성 컬럼에 그 컬럼(ID) 또는 식에 컬럼명 낱말 |
| 인덱스 식·부분 인덱스 조건 (그 테이블) | 테이블명 낱말 | 컬럼명 낱말 |
| VIEW (프로젝트 전체, 스키마 무관, 처리 전 변경 요청의 정의·참조 포함) | 그 테이블을 **직접** 참조 (참조 객체 메타데이터의 테이블 ID 또는 정의에 테이블명 낱말) | 그 테이블을 직접 또는 VIEW 를 거쳐 참조하는 VIEW 의 정의에 컬럼명 낱말, `*`, `NATURAL` |
| 판정할 수 없는 VIEW 가 하나라도 있음 | 모든 이름 변경 `REFERENCE_UNVERIFIABLE` | 같음 |

- 인용 식별자는 대소문자를 구분하지 않고 비교한다 (보수적). MySQL 의 `"…"` 는 기본 설정에서 문자열이지만 식별자로 본다 (보수적).
- `*` 는 `SELECT *` 와 곱셈을 구분하지 않는다. 별칭·JOIN·서브쿼리는 낱말 규칙으로 함께 잡힌다.
- **검증 범위 밖** (참조했다고도 안 했다고도 주장하지 않는다) : Lexorma 가 저장하지 않은 실제 DB 의 VIEW·함수·프로시저·트리거·동의어·시퀀스 기본값, 원본 DB 수집 VIEW 정의(DEC-16 — 모델 객체가 아니다), 애플리케이션 SQL.

### 8.7 그 밖의 이름 문자열 경로 (1차는 판정하지 않음 — 2차 결정)

| 경로 | 이름 변경 서비스 동기화 | 위험 |
|---|---|---|
| 다른 테이블 컬럼의 `refTableName` | 테이블 변경이 고친다 (승인된 컬럼도 — 기존 동작) | P-04 와의 관계 결정 필요 (8.10) |

| 저장된 제약조건·인덱스 이름 (`UK_옛테이블_…`, `IX_…`) | 고치지 않는다 | 기능 영향 없음, 이름만 옛 테이블명을 담는다. DDL 이 만드는 `PK_`·`UK_`·`FK_` 는 새 이름으로 나가며 잘림·충돌 판정은 1차에 넣지 않았다 |
| 원본 비교·가져오기(M-4d/e, 확정 컬럼 매핑이 없는 컬럼은 이름으로 짝) | — | 바꾼 컬럼이 원본 전용 / 모델 전용으로 보이고 삭제 후보(DEC-04)에 나타날 수 있다 (삭제는 사용자 확인 필요) |
| AI 설명 제안 (`ProposalVersions`) | — | 대상 컬럼·테이블의 수정 시각·이력이 바뀌어 처리 전 제안이 재검토(REVIEW_REQUIRED)된다 |
| 컬럼 기본값 | — | 컬럼을 참조할 수 없다 (표준 SQL) — 판정하지 않음 |

### 8.10 2차 전 결정이 필요한 것 (2026-11-21 사용자 확정 P-09~P-15 로 모두 정해졌다 — 9.1)

1. **컬럼에 표준 용어가 없는 경우** (`COLUMN_TERM_MISSING`) : 지금은 보수적으로 막는다. 허용할지 (P-03 은 "서로 다른 용어" 만 정했다).
2. **컬럼 이름 변경의 승인 기준** : 컬럼 승인만 볼지(현재), 소속 테이블 승인도 볼지.
3. **테이블 이름 변경이 다른 승인된 컬럼의 `refTableName`·테이블명 사본을 고치는 기존 동작** : 그대로 둘지, 그런 참조가 있으면 막을지 (P-04).
4. **추천끼리 충돌의 2차 기준** : 전체 후보 기준(현재, 보수적) 그대로 막을지, 선택 집합 안에서만 볼지 (같은 이름의 후보 중 하나만 고르면 허용).
5. **식별자 규칙** : 문자·길이 위반만 막고 권장 형식 아님은 경고(현재). DDL 이 만드는 `PK_`·`UK_`·`FK_` 이름의 잘림·충돌을 막을지 경고할지 (지금은 판정 안 함). 예약어 검사는 별도 정책 (P13 유지).
6. **컬럼 이름 변경 쓰기 경로** : 기존에 없다 — 2차에서 새 서비스 메서드(잠금 순서 : 프로젝트 → 테이블 행 → 컬럼 행 ID 순, DEC-08 기준값, 변경 이력, 참조 관계 동기화)를 만든다.
7. **원본 매핑된 테이블·컬럼** : 원본 비교에서 이름이 달라지는 것을 경고로 알릴지, 막을지.

## 9. 일괄 적용 2차 (2026-11-21) : 서버 적용 API

> 미리보기 → planToken → 적용으로 물리 테이블명·컬럼명을 실제로 바꾼다. **화면(선택·적용 대화상자)과 브라우저 검증은 3차.** DB 변경 없음 (V0~V4, 다음 V5), 새 오류 코드 없음, 새 이력 출처 없음.

### 9.2 API (`ModelMappingRestController`, 둘 다 USER — 기존 매핑·물리 생성 쓰기와 같은 권한)

| | 경로 | 하는 일 |
|---|---|---|
| 미리보기 | `POST /api/modelMapping/recommendation/rename/preview` | 판정과 planToken. 아무것도 바꾸지 않는다 (읽기 전용 트랜잭션) |
| 적용 | `POST /api/modelMapping/recommendation/rename` | 잠근 뒤 다시 판정해 같을 때만 버전 → 이름 변경 |

요청 (`PhysicalNameRenameDto.Request`) : `items[]` = `{ type : TABLE|COLUMN, id : 물리 테이블·컬럼 ID, recommendedName : 화면이 본 추천명 (필수), baseModifiedAt : 미리보기의 modifiedAt (적용에서 필수) }`, `planToken` (적용에서 필수).

- 0건·501건 이상(테이블 + 컬럼 합, P-07)·같은 대상 두 번·빈 종류/ID/추천명 → 400 `INVALID_PHYSICAL_MODEL` (중복을 조용히 빼지 않는다). 알 수 없는 종류(예 `VIEW`)는 JSON 바인딩에서 400.
- 없는 ID·다른 프로젝트 ID → `TABLE_IS_NOT_DEFINED`·`COLUMN_IS_NOT_DEFINED` (둘을 구분하지 않는다 — 프로젝트 격리).
- 적용에 기준값이 없으면 400 `MODEL_BASE_REQUIRED` (DEC-08), 토큰이 없으면 400.
- **새 이름은 서버가 지금 추천 규칙으로 다시 계산한다** (테이블 = 매핑된 엔터티명 → 표준 단어 + 접두어, 컬럼 = 매핑된 속성의 표준 용어 영문약어, 대문자). 요청의 `recommendedName` 이 다르면 `RECOMMENDATION_CHANGED` 로 막고, 요청 값으로는 절대 바꾸지 않는다.

미리보기 응답 (`Plan`) : `items[]` = `{ type, id, schemaId, schemaName, tableId, tableName, logicalId, logicalName, currentName, recommendedName, requestedName, modifiedAt, noChange, applicability }` (요청 순서), `total`·`tables`·`columns`·`selectable`·`blocked`·`warned`, `applicable`(모두 적용 가능), `dbType`, `planToken`.

적용 응답 (`Result`) : `tables`·`columns`·`total`, `versionId`·`versionName`(`RENAME-<요청 ID>`), `warnings[]`(경고가 있던 대상과 경고).

실패 : 막힌 대상이 하나라도 있으면 400 `INVALID_PHYSICAL_MODEL` (첫 대상의 이름과 사유를 메시지에), 오래된 계획·기준값 불일치·다른 사용자가 같은 행을 바꾸는 중이면 409 `MODEL_CONFLICT`, 권한 403. 부분 적용·부분 결과·자동 재시도는 없다. 막힌 대상(승인·용어·충돌·식별자·참조·제약조건명)의 구분은 미리보기의 `applicability` 코드로 한다 — 적용 응답의 오류 코드는 기존 계약(400/409)을 그대로 썼다.

### 9.3 판정 (미리보기·적용 공용 `PhysicalNameRenameService.compute`)

대상마다 1차의 `applicability` 계약(코드·사유·related, `selectable` = 막는 사유 없음)을 그대로 쓴다. 순서 :

1. 상태에서 정해지는 것 : 매핑 없음 `NOT_MAPPED`, 추천 없음 `NOT_RECOMMENDED`, 이미 같음 `NO_CHANGE` (`noChange=true`) — 이 셋은 다른 판정을 하지 않는다.
2. `RECOMMENDATION_CHANGED` (요청 추천명 ≠ 서버 추천명, 앞뒤 공백·대소문자 무시).
3. 지금 이름 충돌 `NAME_CONFLICT` : 테이블 = 같은 스키마의 다른 테이블·VIEW, 컬럼 = 같은 테이블의 다른 컬럼 (앞뒤 공백·대소문자 무시 — 저장 규칙보다 넓다). **선택과 관계없이** 지금 쓰는 이름이라 이름 맞바꾸기·연쇄 변경도 막힌다 (임시 이름으로 돌아가지 않는다, P-12 지시 14).
4. 선택 집합 안의 추천끼리 충돌 `RECOMMENDATION_DUPLICATE` (P-12 — 고르지 않은 후보는 보지 않는다). 지시서 예시는 `NAME_CONFLICT` 였지만, 1차 계약에 같은 뜻의 코드가 있어 그것을 재사용했다 (지금 다른 객체가 쓰는 이름 = `NAME_CONFLICT`, 함께 고른 다른 대상과 겹침 = `RECOMMENDATION_DUPLICATE`).
5. 식별자 `IDENTIFIER_INVALID` / 경고 `IDENTIFIER_NOT_RECOMMENDED` (`DbIdentifierRules.check`, Oracle 30바이트 유지).
6. 승인 : 테이블 `TABLE_APPROVED`, 컬럼 `COLUMN_APPROVED` + 소속 테이블 `TABLE_APPROVED` (P-04·P-10). 용어 : `COLUMN_TERM_MISSING`(P-09)·`TERM_MISMATCH`(P-03).
7. 이름 문자열 참조 (P-08, 1차 `RenameSafety` 그대로) : CHECK 식·구성 컬럼, 인덱스 식·부분 인덱스 조건, VIEW 정의(직접·간접·`*`·`NATURAL`·처리 전 변경 요청), 판정 불가 `REFERENCE_UNVERIFIABLE`.
8. DDL 자동 제약조건명 (P-13, 9.6).
9. 원본 매핑 경고 (P-15, 9.7).

경고 코드는 `PhysicalNameRecommendationDto.WARNING_CODES` = 권장 형식 아님·원본 매핑. 나머지는 모두 막는다.

### 9.4 이름 변경 경로

- **테이블** (`TableDesignService.renameLockedTable`, 새 내부 메서드) : `updateTable` 의 이름 변경 부분과 같다 — 소속 컬럼의 `TBL_NM` 사본 → `TBL_NM` → 이 테이블을 이름으로 가리키던 컬럼(`columnsReferencingTable` = `updateTable` 이 쓰는 private `columnsReferencing` 그대로, 바꾸기 전 이름으로 찾음)의 `refTableName` (스키마를 적어 둔 참조는 스키마명 유지). 한글명·설명·스키마·승인 상태는 그대로다 (P-02). 참조 관계 동기화(`syncReferenceRelations`)는 바꾼 테이블 전체로 한 번. `updateTable` 자체는 바꾸지 않았다.
- **컬럼** (`ColumnRenameService.renameLockedColumn`, 새 서비스 — 이 기능에서만 부른다, P-14) : `COL_NM` 하나만 바꾼다. 논리 속성·표준 용어·도메인·설명·업무 설명·승인 상태·매핑 대상 ID 는 그대로다. 기존 컬럼 저장 API(등록·일괄 저장·용어 재연결)의 의미는 바꾸지 않았다. 부르는 쪽의 판정과 같은 불변식(미승인 컬럼·미승인 테이블·같은 테이블 이름 중복 없음)을 한 번 더 확인한다.
- **ID 참조라 고칠 것이 없는 것** : PK·FK·복합 FK·UNIQUE·인덱스 구성 컬럼, 논리·물리 매핑, 상속 PK 매핑, 원본 확정 컬럼 매핑(DEC-06), 원본 테이블 매핑, ERD 배치, AI 설명 제안의 대상 ID. DDL 은 생성할 때 이름을 쓰므로 바뀐 이름으로 나온다 (9.9 확인).
- **고치지 않는 문자열** : 저장된 제약조건·인덱스 이름(예 `IX_옛테이블_…`, 지시 26), VIEW 정의·CHECK 식·인덱스 식 (그래서 그것이 옛 이름을 쓰면 막는다).

### 9.5 적용 순서 · 잠금 · 동시성

1. 요청 검사 → **프로젝트 행 배타** (`findByIdForUpdate` + `ProjectWriteGuard.lock`, 기다린다 — 같은 적용 두 번은 여기서 줄을 선다).
2. 기다리지 않는 행 잠금 (NOWAIT — 일반 저장은 행을 잠근 채 커밋 직전에 프로젝트 행을 공유 잠금으로 확인하므로 기다리면 교착. 물리 생성·원본 가져오기와 같은 규칙, 못 잡으면 409) : 대상의 논리 모델 행(ID 순) → 기본 스키마 행(= VIEW 참조 그래프 — VIEW 의 등록·수정·변경 요청 처리·삭제가 함께 잠근다) → 이름을 바꿀 테이블의 스키마 행(ID 순) → 테이블 행(이름을 바꿀 테이블 + 이름을 바꿀 컬럼의 테이블, ID 순 — 승인·CHECK·인덱스·관계·PK 변경과 컬럼 일괄 저장이 먼저 잠그는 행) → 컬럼 행(이름을 바꿀 컬럼 + 이름을 바꿀 테이블의 컬럼, 한 질의 ID 순).
3. 같은 판정을 다시 계산 → planToken 비교 (다르면 409) → 대상 행 기준값(DEC-08 `ModelBase.verify`, 다르면 409) → 막힌 대상이 있으면 400.
4. 이 테이블을 이름으로 가리키는 다른 컬럼을 찾아 NOWAIT 로 잠근다 (바꾸기 전).
5. 직전 모델 버전 `RENAME-<UUID>` (`ModelVersionService.createBeforeModelChange`, 스냅샷 형식 9 그대로, P-06).
6. 테이블명(ID 순) → 컬럼명(ID 순) → 참조 관계 동기화 → flush. 이력은 커밋 직전에 일반 쓰기처럼 남는다.

planToken (`physical-rename/1`, 물리 생성 토큰과 섞지 않는다) = SHA-256(프로젝트·DBMS + 대상별 종류·ID·지금 이름·새 이름·수정 시각(µs)·판정 코드와 related). 미리보기 뒤 이름·승인·용어(연결·약어)·매핑·VIEW·CHECK·인덱스가 바뀌면 같은 계산이 달라져 409 다. 서명은 없다 — 위조한 토큰은 잠근 뒤 계산과 맞지 않을 뿐이고, 토큰만으로 할 수 있는 것은 없다 (물리 생성과 같은 방식).

알려진 남은 경쟁 (기존 구조) : ① ~~단일 컬럼 등록(`insertColumn`)은 PK 가 아니면 테이블 행을 잠그지 않는다~~ → **10장(2차 후속)에서 해결** : 컬럼 단건 등록·엑셀 업로드가 테이블 행을 먼저 잠근다. ② 참조 관계 동기화가 다른 트랜잭션이 쥔 관계 행을 만나면 기다린다 — 그 관계를 바꾸는 쓰기는 테이블 행을 먼저 잠그므로 위 2단계에서 대부분 409 가 되지만, 모든 경로를 증명하지는 않았다. PostgreSQL 교착 감지가 한쪽을 되돌린다 (데이터는 원자적).

### 9.6 DDL 자동 제약조건명 (P-13)

고른 이름을 모두 바꾼 뒤의 모델(`DdlIdentifierQueryRepository.model` 에 새 이름을 덮음)로 `DbIdentifierCheck.check` 를 부른다 — DDL 생성기와 같은 이름 규칙(`PK_테이블`, `UK_테이블_컬럼`, `FK_테이블_컬럼`)·DBMS 별 잘림·이름 공간(`sameNamespace`). **바뀌는 자동 이름**(이름을 바꿀 테이블의 PK_·UK_·FK_, 이름을 바꿀 컬럼의 UK_·FK_)에 걸린 잘림은 `CONSTRAINT_NAME_INVALID`, 충돌(저장된 이름·다른 자동 이름·함께 고른 다른 대상의 새 자동 이름)은 `CONSTRAINT_NAME_CONFLICT` 로 그 대상에 붙인다. 저장된 이름 자체의 문제는 이름 변경이 만든 것이 아니라 붙이지 않는다. 테이블과 그 컬럼을 함께 바꾸면 최종 조합으로 본다. 예 : 같은 스키마의 두 테이블을 같은 이름으로 고르면 `RECOMMENDATION_DUPLICATE` 와 함께 `PK_` 충돌도 나온다.

### 9.7 원본 DB 매핑 (P-15)

테이블이 원본 테이블과 매핑(`TB_SRC_TBL_MPNG.TBL_SN`, 제외 표시 포함)되어 있으면 그 테이블과 그 테이블의 컬럼 이름 변경에 `SOURCE_MAPPED` 경고 — 원본 DB 이름과 달라지고 원본 비교에서 다르게 보이거나 원본 전용·모델 전용으로 나올 수 있다(확정 컬럼 매핑이 없는 컬럼은 이름으로 짝을 짓는다). 막지 않는다. 원본 매핑·카탈로그는 바꾸지 않고, 원본 DB 에 DDL 을 실행하지 않는다.

### 9.8 이력 · 버전 · 롤백

- 이력은 기존 `ModelChangeRecorder` 가 남긴다 (출처 `USER`, 참조 관계 동기화가 만든 관계는 `AUTO_SYNC`). 새로 더한 `markChangeGroup` 으로 변경 그룹 ID 를 버전명 `RENAME-<요청 ID>` 와 같게 남긴다 — 한 번의 적용을 이력에서 찾을 수 있다. 바뀌기 전·후 이름, 사용자, 시각이 기존 칸에 있다. 새 출처 값(예 RENAME)은 만들지 않았다 (예제 코드 용어 정의를 새 마이그레이션으로 고쳐야 해서 — 지시 56).
- 버전·이름 변경·참조 동기화·이력은 한 트랜잭션이다. 하나라도 실패하면 버전도 남지 않는다 (9.9 실패 주입). 버전은 비교용이며 복원 기능은 없다.

## 10. 일괄 적용 2차 후속 (2026-11-21) : 컬럼 등록 동시성 보완

> 9.5 의 남은 경쟁 ① 을 고쳤다. 새 기능·API 계약 변경·DB 변경(UNIQUE 포함)은 없다. 화면은 여전히 3차.

### 10.1 문제 (재현)

PK 가 아닌 컬럼의 단건 등록(`insertColumn`)과 엑셀 업로드는 테이블 행을 잠그지 않고 이름 중복을 확인했다 (커밋된 행만 본다). TB_COL 에 이름 UNIQUE 가 없어 마지막 방어선도 없다. 고치기 전 코드(HEAD 의 `ColumnManageServiceImpl`)로 10.5 의 PostgreSQL 테스트를 돌리면 6건 중 4건이 실패했다 — 등록이 먼저일 때 같은 이름으로 바꾸는 일괄 적용이 성공(T-01), 일괄 적용이 먼저일 때 같은 이름 등록이 성공(T-02), 같은 이름 동시 등록의 둘째가 기다리지 않음(T-03), 엑셀 업로드가 먼저일 때 일괄 적용이 성공 — 모두 같은 테이블에 같은 이름이 둘 남는 경우다.

### 10.3 잠금 순서와 교착

- 컬럼 등록 : **테이블 행(배타, 기다림)** → 중복 검사 → INSERT → 커밋 직전 프로젝트 행 공유 잠금(`ProjectWriteGuard`, 기존).
- 물리명 일괄 적용 : 프로젝트 행(배타, 기다림) → … → 테이블 행 NOWAIT → 컬럼 행 NOWAIT.
- 교차해도 교착이 없다 : 등록이 테이블을 쥐면 적용은 NOWAIT 로 바로 409 (프로젝트 배타를 놓는다 → 등록이 커밋). 적용이 테이블까지 쥐면 등록은 테이블 행을 기다리고, 적용이 커밋한 뒤 최신 이름으로 중복을 본다. 적용이 프로젝트만 쥔 순간에 등록이 테이블을 잡으면 적용의 NOWAIT 가 409.
- 프로젝트 행은 등록에서 새로 잠그지 않았다 — 프로젝트 단위로 직렬화하지 않는다. 같은 테이블의 등록만 서로 기다린다 (다른 테이블은 기다리지 않음, T-04).
- 엑셀 업로드는 청크마다 그 청크의 테이블을 ID 순으로 잠근다 (청크 사이에는 전역 순서가 아니다 — 두 업로드가 서로 다른 청크 순서로 같은 테이블들을 건드리면 PostgreSQL 교착 감지가 한쪽을 되돌릴 수 있다. 예전 PK 테이블 잠금과 같은 성질이며 이번에 범위만 넓어졌다).

### 10.4 바뀐 계약 (AI-5 · M-7 3차)

예전에는 "PK 가 아닌 컬럼 등록은 테이블 행을 쥔 다른 작업(업무 설명 직접 편집·AI 제안 승인)을 기다리지 않는다" 였다 (M-7 3차 M7-D39 기록 30.8, `BizDescriptionExcelIntegrationTest`). 이제는 **같은 테이블의 그런 짧은 쓰기가 커밋될 때까지 기다린다** — 지시(같은 테이블 작업은 테이블 행 잠금으로 직렬화)를 따른 결과다. 교착·값 손실은 없다 (`BizDescriptionExcelIntegrationTest.concurrentDirectEditAndUpload` 를 "기다렸다가 이어서 반영, 직접 편집 값 유지" 로 고쳤다). 오류 코드·HTTP 상태는 그대로다 (중복 = `SAVED_DATA_EXISTS`, 잠금 대기는 오류가 아니다).

### 10.5 이름 비교

등록은 기존 규칙(같은 테이블, 정확 일치)을 그대로 쓴다 — 새 정규화를 더하지 않았다. 이름 변경(9.3)은 앞뒤 공백·대소문자 무시라 더 넓다. 그래서 이름 변경이 만드는 이름은 언제나 대문자이고, 등록이 대소문자만 다른 이름(예 `cust_nm` 과 `CUST_NM`)을 받는 것은 예전과 같다 (등록 화면은 용어 영문약어를 쓰므로 실제로는 대문자). 이 차이를 맞출지는 정하지 않았다.

### 10.7 남은 위험

- DB UNIQUE 가 없다 (지시 20 — 추가하지 않음). 보장 범위 = 위 표의 애플리케이션 쓰기 경로(단건 등록·엑셀 업로드·일괄 저장·이름 변경·원본 가져오기). 직접 SQL·아직 조사하지 않은 앞으로의 경로·테스트용 JDBC 쓰기는 보호하지 않는다. 기존 데이터에 대소문자만 다른 같은 이름이 있을 수 있어 UNIQUE(정확 일치든 대소문자 무시든)는 기존 데이터 점검 뒤 새 증분 마이그레이션으로 따로 결정할 과제다 (pending-work [M-7] 에 제안). → 2026-11-22 V5(`UX_COL_01`, 대소문자·앞뒤 공백 무시)와 경로별 비교 통일로 해결 — [column-name-uniqueness-m7.md](column-name-uniqueness-m7.md).
- 엑셀 업로드 두 개의 청크 순서 교착 (10.3) — 감지되면 한쪽이 실패하고 데이터는 원자적이다. 측정·재현은 하지 않았다.
- 3차(화면)는 그대로 남았다 (9.10).

> **2026-11-22 잠금 보완 ([physical-fk-correction-m7.md](physical-fk-correction-m7.md) 8장, M7-FK-D06)** : 적용은 이름을 바꿀 테이블·컬럼 행을 먼저 `FOR UPDATE NOWAIT`(키 강도)로 잡고, 새 이름을 미리 참조하던 컬럼도 NOWAIT 로 잠근다. 다른 트랜잭션이 그 행을 부모로 하는 관계를 만든 채(엑셀 청크 동기화 등) 있으면 기다리지 않고 409 다 (예전 : 이름 UPDATE 가 KEY SHARE 를 기다리다 교착 S6b). 9장의 잠금 순서 설명은 그 전 기록이다. 같은 날 후속(M7-FK-D11, [physical-fk-correction-m7.md 14장](physical-fk-correction-m7.md))에서 PK 컬럼을 지우는 컬럼 일괄 저장·삭제도 같은 규칙(프로젝트 배타 → NOWAIT)을 따르게 했다 — 물리명 적용과는 프로젝트 행에서 직렬화되며 적용 코드는 바뀌지 않았다 (성능 측정 문장 수 같음).

### 11.2 선택

- 키 = `TABLE:<물리 테이블 ID>` / `COLUMN:<물리 컬럼 ID>` (같은 ID 라도 섞이지 않는다). 고를 때 본 추천명·현재 이름을 함께 둔다.
- **고를 수 있는 행** = 서버 `applicability.selectable`, 또는 **막는 사유가 `RECOMMENDATION_DUPLICATE` 뿐인 행** (P-12 — 목록의 추천끼리 충돌은 전체 후보 기준이라 고른 집합으로 미리보기에서 다시 판정한다). 그 밖의 차단 행은 체크박스가 비활성이고 aria-label·title 에 사유가 있다.
- 페이지 이동·검색·상태 필터·컬럼명/테이블명 탭 전환에도 선택을 유지하고, 지금 쪽에 보이지 않는 선택 수를 알린다. 모델이 바뀌면 비워진다(화면이 모델 ID 로 다시 만들어짐). 프로젝트가 바뀌면 화면 전체가 새로 열린다.
- [이 쪽의 적용 가능 항목 선택]은 지금 쪽만 (검색 결과 전체를 서버에서 고르지 않는다 — 새 API 없음). 해제도 지금 쪽만.
- 최대 500 (테이블 + 컬럼 합, P-07) : 넘는 선택은 하지 않고 알린다. 0건이면 미리보기 버튼 비활성. 서버도 다시 검사한다.
- 목록이 새로 고쳐져 추천명이 바뀌어도 고른 값을 덮어쓰지 않는다 → 미리보기가 `RECOMMENDATION_CHANGED` 로 막는다.

### 11.3 미리보기 · 확인 · 적용 (`RenamePreview`, 팝업)

1. 열면 고른 집합으로 `POST …/rename/preview` 를 한 번 부른다 (요청 = 종류·ID·고를 때 본 추천명).
2. 요약(전체·적용 가능·적용 불가·경고), 원본 DB 매핑 경고 안내(P-15 — 차단 아님, 원본 매핑 해제·원본 DDL 없음), 대상별 표(종류, `스키마.테이블[.컬럼]` + 논리명, 변경 후, 판정, 차단 사유·경고 전문).
3. 적용 불가가 하나라도 있으면 [이름 변경 적용] 비활성 (P-05). 선택은 조용히 바꾸지 않는다 — 사용자가 [적용 불가 항목을 선택에서 빼고 다시 미리보기]를 눌러야 빠지고 새 미리보기를 받는다.
4. [이름 변경 적용] → 확인 대화상자(테이블·컬럼·전체 수, 직전 `RENAME-…` 버전, 전체 롤백, 한글명·용어·매핑 불변, 경고 수) → 확인한 경우에만 `POST …/rename` (미리보기의 `planToken` + 대상별 `baseModifiedAt` = 미리보기의 `modifiedAt` — 화면이 시각을 만들지 않는다).

6. 성공 : 팝업을 닫고 선택을 비우고, 추천 목록·요약과 매핑·테이블·컬럼·ERD 계열 캐시를 무효화한 뒤 결과 알림(변경 수, 버전명, 경고 목록 — 여러 결과라 토스트가 아니라 대화상자, UI-1 §7).
7. **409** : 계획(planToken)을 버리고 "다른 사용자가 모델을 변경했거나 추천 결과가 달라졌습니다. 다시 미리보기를 진행해 주세요." 를 보여 주며 목록·요약을 새로 고친다. 적용 버튼은 비활성, [다시 미리보기]로만 새 토큰을 받는다 (자동 재시도 없음). 그 밖의 오류는 서버 메시지 그대로.

### 11.5 남은 위험 · 후속

- DB UNIQUE(같은 테이블 컬럼명)와 컬럼명 비교 규칙 통일(등록 = 정확 일치, 이름 변경 = 대소문자 무시)은 별도 후속 (10.5·10.7, pending-work [M-7]). → 2026-11-22 완료 ([column-name-uniqueness-m7.md](column-name-uniqueness-m7.md)). 비교 규칙은 같은 날 최종 보완(V7, M7-U06 B3)으로 로캘 중립 유니코드 확장 대문자가 됐다 — 일괄 변경 미리보기의 `NAME_CONFLICT` 도 같은 기준 (같은 문서 14장). 이어서 M7-U10 으로 추천 목록의 컬럼 `CONFLICT` 상태·필터·요약·충돌 사유·추천끼리 겹침과 미리보기·적용이 모두 저장된 `COL_NM_CMPR_VL` ↔ 추천명의 DB 비교 값으로 판정한다 (같은 문서 15.5 — 표준화 일치·테이블명 충돌은 그대로).
- 검색 결과 전체 선택은 없다 (지시 — 쪽 단위). 500건을 고르려면 쪽마다 고른다.
- Chromium 외 브라우저, 실제 Oracle·MySQL·MariaDB DDL 실행은 확인하지 않았다.
