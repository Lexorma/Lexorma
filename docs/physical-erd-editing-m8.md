# M-8 3차. 물리 ERD 직접 편집과 물리 모델·DDL 정합성 — 설계 결정과 구현 기록

- 범위 : 물리 ERD 의 조회·편집 모드, 테이블 등록·수정·삭제, 컬럼 편집 연결, FK(관계) 연결·등록·삭제, 인덱스·제약조건 관리, 부분 조회·배치 처리, 테이블·컬럼 관리 화면과 DDL 과의 정합성 검증.
- 편집 기반(모드 전환, 새 노드 위치, "연결 → 폼 → 저장 → 다시 조회")은 [M-8 1차·2차](erd-editing-m8.md) 의 것을 그대로 쓴다.
- **백엔드 코드·DB 스키마·마이그레이션 변경 없음.** 화면은 기존 API 만 쓴다. 백엔드에서 바뀐 것은 메뉴 권한 표의 화면용 항목 1개(`physical-model-edit`)와 테스트뿐이다.
- 하지 않은 것 : 논리 → 물리 자동 생성·동기화, 물리명 추천 자동 반영, 실제 DB 에 DDL 실행, Undo/Redo, 변경 이력(M-9), 실시간 공동 편집, 새 DBMS, 큰 ERD 성능 최적화.

## 1. 기존 구조 분석과 결정

| 항목 | 기존 구조 | 결정 |
|---|---|---|
| 테이블 | `POST/PUT /api/saveTable`, `DELETE /api/deleteTable`, 화면 `TableForm` | 그대로 쓴다. 테이블명은 한글명을 표준 단어로 바꿔 만든다(직접 입력 불가) — ERD 에서도 같다 |
| 컬럼 | `PUT /api/saveColumn/bulk`, 화면 `ColumnBulkEditor`(표준 용어 검색·추가·수정·삭제·순서·PK·NULL·참조 테이블) | 편집 모드에서 같은 편집기를 연다. ERD 전용 컬럼 폼을 만들지 않는다 |
| 관계 | `POST /api/physical/relation`, `DELETE /api/physical/relation/{id}`, 승인 `PATCH`. **수정 API 없음**(서비스 정책 : 삭제 후 다시 등록) | 등록·삭제·승인만 제공한다. "수정" 버튼을 만들지 않고 화면에 그 사실을 적는다 |
| 인덱스·제약 | `POST /api/physical/index`·`/constraint`, 삭제·승인. **화면이 없었다** (API 만 존재) | ERD 테이블 패널에 [인덱스·제약조건] 대화상자를 추가했다 (같은 API). PK·단일 컬럼 고유값·인덱스는 컬럼 설정 그대로 |
| 참조 테이블명 관계 | 컬럼의 `refTableName` → `REF_COLUMN` 관계 자동 동기화. API 로 삭제 불가 | ERD 에서도 삭제 버튼을 막고 "컬럼 편집에서 참조 테이블을 비우면 없어진다" 고 안내. 동기화를 우회하지 않는다 |
| 배치 | `PUT /api/erd/layout` : 사용자 × 프로젝트 1건, 요청 좌표를 저장된 좌표에 **합친다** | 그대로. 화면은 옮긴 노드만 보낸다 → 조회 범위 밖 좌표가 보존된다 (4.3 에서 확인) |
| DDL | `GET /api/selectTable/ddl/{id}` : 컬럼 + 인덱스·제약 + 사용자 FK(`relationType = FK`) | 그대로. ERD 편집은 같은 테이블에 저장하므로 별도 변환이 없다 |

## 2. 편집 정책

### 2.1 조회 모드 · 편집 모드

- 기본은 조회 모드. 편집 모드는 물리 모델 변경 권한(USER 이상, 화면용 메뉴 항목 `physical-model-edit`)이 있을 때만 전환 버튼이 보인다. 서버 API 가 같은 기준으로 다시 검사한다.
- 조회 모드 : 연결점 비활성(끌어도 아무 일도 없다), 테이블 패널에 편집 버튼 없음, 테이블 상세는 조회 전용(`readOnly`), 인덱스·제약조건은 목록만.
- 편집 모드 : [테이블 추가], 패널의 [컬럼 편집]·[테이블 수정]·[FK 추가]·[테이블 삭제], 테이블 연결점, 관계 패널의 [관계 삭제], 인덱스·제약조건 등록·삭제.
- 승인·승인취소는 편집이 아니라 승인 권한(관리자·매니저·프로젝트 관리자)의 일이라 모드와 무관하게 권한자에게 보인다.

### 2.2 저장 정책

- 모델 데이터(테이블·컬럼·관계·인덱스·제약)는 기존 API 로 **바로 저장**하고, 성공한 뒤 ERD 를 다시 조회한다. 낙관적 갱신을 하지 않는다 — 실패하면 서버 사유를 알리고 화면은 그대로다.
- 배치는 따로 [배치 저장]. 모델 저장은 배치 API 를 부르지 않고, 저장하지 않은 배치는 모델 변경 뒤에도 남는다. 다시 조회해도 기존 노드 위치는 바뀌지 않는다(자동 재배치 없음).
- 새 테이블은 보고 있는 화면 가운데에서 다른 노드(범위 밖에 저장된 좌표 포함)와 겹치지 않는 자리에 놓고 "저장하지 않은 배치" 로 표시한다.
- 새 테이블이 지금 조회 범위(스키마·검색·페이지)에 들어오지 않으면 **범위를 조용히 바꾸지 않는다.** 등록됐지만 보이지 않는다고 알리고, 그 테이블 기준 이웃 조회로 바꿀지 묻는다.

### 2.3 FK(관계)

- 연결점을 잇는 것은 등록의 시작일 뿐이다. 선을 추가하지 않고 등록 대화상자를 연다. 취소하거나 저장에 실패하면 아무것도 생기지 않고, 저장에 성공해 다시 조회한 뒤에야 선이 생긴다.
- 방향 : 오른쪽 연결점(참조하는 테이블, FK 컬럼이 있는 쪽) → 왼쪽 연결점(참조되는 테이블). 끈 방향을 그대로 확정하지 않고 대화상자에서 확인하며 [방향 바꾸기] 로 바꿀 수 있다.
- 컬럼 쌍 : 참조되는 테이블의 PK 컬럼 수만큼 행을 미리 만들고(참조되는 쪽은 PK), 참조하는 컬럼은 사용자가 고른다. 여러 쌍이면 복합 FK 이고 순서가 저장·DDL 순서다.
- 자기 참조(같은 테이블을 양쪽에), 같은 두 테이블 사이 여러 FK, 논리 관계(DDL 제외)를 등록할 수 있다. 이름을 비우면 서버가 `FK_{테이블}_{첫 컬럼}` 으로 정한다.
- 조회 범위에 있는 테이블만 고를 수 있다. 범위 밖 테이블과의 관계는 테이블 패널 목록에 "조회 범위 밖" 으로 나오고 선은 그리지 않는다.
- **수정은 없다** — 삭제 후 다시 등록. 승인된 관계는 승인취소 후 삭제. 참조 테이블명 관계는 컬럼에서 관리.
- 서버가 검사하지 않는 것(참조되는 컬럼이 PK·고유인지, 양쪽 타입이 같은지)은 대화상자가 **저장을 막지 않고 알려 주기만** 한다. ERD 에서만 더 엄격하게 막지 않는다(3장 "서버 검증 공백" 참고).

### 2.4 삭제·승인 보호 (기존 정책 그대로)

| 대상 | 조건 | ERD 에서 |
|---|---|---|
| 테이블 삭제 | 컬럼이 있으면, 승인됐으면, 논리 엔터티에 매핑됐으면(M-7) 불가 | 앞의 둘은 버튼 비활성 + 사유, 매핑은 서버 오류로 알림. CASCADE 삭제 없음 |
| 테이블 수정 | 승인된 테이블은 화면에서 수정 불가 (테이블 상세와 같다) | 버튼 비활성 |
| 컬럼 삭제 | 승인된 컬럼, 속성에 매핑된 컬럼(M-7), 사용자 관계·인덱스·제약에 쓰인 컬럼 불가 | 컬럼 편집기·서버가 그대로 거절 |
| 관계·인덱스·제약 삭제 | 승인된 항목 불가 | 버튼 비활성 + 사유 |
| 승인 | 승인 권한자만 | 권한자에게만 버튼, 서버도 거절 |

백엔드 : `MenuAuthorization` 에 화면용 항목 `physical-model-edit`(USER) 추가와 그 테스트. API·서비스·엔티티·마이그레이션은 바꾸지 않았다.

**서버 검증 공백 (3차에서는 기록만 했다. 이후 안정화 작업에서 처리 : [model-integrity-hardening.md](model-integrity-hardening.md))**

- 관계 등록 시 참조되는 컬럼이 PK·UNIQUE 인지, 양쪽 컬럼의 타입이 호환되는지 검사하지 않는다 → 실행할 수 없는 FK DDL 이 나올 수 있다. 화면은 안내만 한다. → **해결** : 서버가 FK 등록에서 검사한다.
- DDL 은 승인 대기 중인 FK·인덱스·제약도 포함한다(승인 여부로 거르지 않는다). → **정책 확인** : 설계용 DDL 이라 그대로 두고, 승인 대기 항목을 따로 알려 준다.
- 테이블 수정 API 는 승인된 테이블을 거절하지 않는다(화면만 막는다). ERD 도 테이블 상세와 같은 조건으로 버튼을 막을 뿐이다. → **해결** : 서버가 거절한다.

## 4. 검증

개발 DB 와 IDE 에서 실행 중인 애플리케이션은 건드리지 않았다. 작업 트리를 임시 폴더에 복사해 빌드·실행했다.

### 4.1 자동 테스트

- `PhysicalErdEditIntegrationTest`(신규, 4건) — ERD 가 쓰는 호출 순서를 컨트롤러로 실행한다.
  - FK : 단일·복합(쌍 순서)·같은 두 테이블 사이 두 번째 FK·자기 참조·논리 관계 등록, 중복·다른 테이블 컬럼·쌍 없음 거절, **ERD 조회 = 테이블 물리 모델 = DDL**(이름·컬럼 순서·대상), FK 에 쓰인 컬럼 삭제 거절, 승인된 관계 삭제 거절 → 승인취소 후 삭제 → 세 곳에서 모두 사라짐.
  - 참조 테이블명 관계의 삭제·중복 등록 거절, 인덱스·UNIQUE·CHECK 등록·삭제가 물리 모델·DDL 에 반영, CHECK 조건식 거절.
  - 배치 : A·B·C 저장 → A 만 보내 저장 → B·C 보존, 모델 변경은 배치 버전을 바꾸지 않음, 테이블 삭제 조건(컬럼·승인), 삭제된 테이블 좌표 정리.
  - 권한(VIEWER 변경 불가, USER 는 승인 대기·승인 불가), 프로젝트 격리.
- H2 : 저장소 전체 `./gradlew clean build` — 362건 중 실패 0, 건너뜀 2.
- PostgreSQL(격리 DB 를 만들어 실행하고 지움) : `metamora-app` 의 통합·시드·스모크 테스트(`*IntegrationTest`·`V0SeedMigrationTest`·`SmokeTest`) 112건 중 실패 0. 필터 없이 `metamora-app` 전체를 PostgreSQL 설정으로 돌리면 124건 중 1건(`ProjectAccessRevokeTest`)이 컨텍스트를 띄우지 못한다 — 이 테스트는 H2 주소를 고정해 쓰는 테스트라 PostgreSQL 드라이버 설정과 맞지 않는 것이고, 이번 변경과 무관하다(H2 빌드에서는 통과).

### 4.2 브라우저 검증 (인메모리 H2 로 따로 띄운 애플리케이션, 헤드리스 Chrome)

59개 확인 항목이 모두 통과했다. 실행 중 자바스크립트 예외는 없었다(콘솔의 4xx 는 거절을 일부러 일으킨 호출이다).

- 조회 모드 : 기본 모드, 연결점 비활성(끌어도 대화상자 없음), 편집 버튼 없음, 관계선·목록에서 관계 상세, 인덱스·제약조건 조회 전용, 테이블 상세 조회 전용.
- 테이블 : 추가(저장 → 다시 조회 → 선택·포커스, 겹치지 않는 위치, 배치 API 미호출), 범위 밖 새 테이블(알림 후 닫기 → 범위 그대로 / 확인 → 이웃 조회), 수정, 삭제(확인 문구에 스키마.테이블명), 승인·컬럼 있는 테이블의 버튼 비활성과 API 직접 호출 거절.
- 컬럼 : 편집 모드의 [컬럼 편집] 이 기존 일괄 편집기를 연다. 컬럼 저장 뒤 ERD 노드·패널이 컬럼 관리 데이터(이름·순서·PK)와 같다.
- FK : 연결점 끌기 → 대화상자(방향·PK 기본값, 선 없음), 취소, 컬럼 미선택 거절, 저장 후 선·관계 패널, 중복 저장 실패 시 화면 유지, 방향 바꾸기, 복합 FK(쌍 순서), 자기 참조·논리 관계, PK 아닌 컬럼 안내, 승인취소 후 삭제, 참조 테이블명 관계 삭제 불가.
- 정합성 : ERD 관계 = 테이블 물리 모델, DDL 의 FK 2건(단일·복합, 컬럼 순서)과 논리 관계 제외, ERD 의 [DDL 보기], 인덱스(고른 순서)·CHECK 의 목록·물리 모델·DDL 반영, FK 삭제 후 DDL 에서 제거.
- 배치 : 전체 저장 → `TB_STD` 만 조회해 한 테이블 이동·저장 → 범위 밖 테이블 좌표 그대로 → 전체 조회에서 저장된 위치에 그려짐. 저장하지 않은 배치가 있는 채로 FK 저장 → 위치·미저장 표시 유지, 배치 버전 그대로.
- 역할 : VIEWER(조회만, 변경 API 403), USER(승인 대기로 등록, 승인 불가), DBA·MANAGER(편집, 승인 버튼은 MANAGER 만), 미승인 사용자(403).
- 다크·라이트, 820px 폭, 영어(편집 화면·FK 폼·인덱스·제약조건 대화상자에 한글 없음).

### 4.3 확인하지 않은 것

아래는 3차 시점의 목록이다. 컬럼 일괄 편집기 안에서의 조작, ERD 화면에서의 M-7 매핑 보호, 스키마가 여러 개인 화면은 이후 안정화 작업에서 브라우저로 확인했다 ([model-integrity-hardening.md](model-integrity-hardening.md) 7.2).

- 컬럼 일괄 편집기 **안에서의** 조작(표준 용어 검색·추가, 순서 변경, PK 변경)은 이번 브라우저 실행에서 다시 하지 않았다. 편집기가 열리는 것과, 편집기가 쓰는 API(`saveColumn/bulk`)로 저장한 결과가 ERD 에 같게 나오는 것만 확인했다(편집기 자체는 기존 기능).
- M-7 매핑 보호(매핑된 테이블·컬럼 삭제 거절)는 기존 통합 테스트로만 확인했고 ERD 화면에서 다시 해 보지 않았다.
- 스키마가 여러 개인 프로젝트의 화면(브라우저는 기본 스키마 하나), 100개를 넘는 페이지 경계에서의 새 테이블.
- 두 사용자의 동시 편집, 큰 ERD 에서의 반응 속도, Chrome 이외 브라우저, 터치 입력, 820px 보다 좁은 화면, PostgreSQL 을 붙인 상태의 화면.
- 생성한 DDL 을 실제 DB 에 실행해 보지 않았다(범위 밖). DDL 문자열이 저장된 모델과 같은지만 확인했다.

## 5. 후속

- 서버 검증 공백(3장) : FK 대상의 PK·UNIQUE·타입 호환 검사, 승인 대기 항목의 DDL 포함 여부 정책, 승인된 테이블 수정의 서버 차단. → 안정화 작업에서 처리 ([model-integrity-hardening.md](model-integrity-hardening.md)).
- 관계 수정 API 가 생기면 ERD 에 수정 버튼을 붙인다. 지금은 삭제 후 다시 등록.
- 범위 밖 테이블과의 FK 등록(지금은 범위 안 테이블만 고른다), 컬럼 연결점 사이를 직접 이어 컬럼 쌍을 미리 채우기.
- 로드맵 M-8 작업 범위에 있던 **레이아웃 확장**(노드 접힘·그룹·여러 다이어그램 뷰)과 **동시 편집 정책(D-09)** 은 구현하지 않았다 → M-8 에서 떼어 로드맵 M-8 후속 표로 옮겼다. 편집 이력·Undo/Redo 는 M-9.
