## 1. DBMS 지원 정책 (확정)

- **순서 : 전체 핵심 기능과 AI 기능 개발 → 통합 안정화 → DBMS 확대.**
- **지금 개발·검증 기준**

  | DBMS | 용도 |
  |---|---|
  | PostgreSQL | 원본 DB 수집 대상이자 애플리케이션 DB |
  | H2 | 기존 테스트 환경 |

- **보류하는 것** : EDB·MySQL·MariaDB·Oracle 에 대해 아래를 하지 않는다.
  - 수집기, JDBC 드라이버 추가, Docker 검증 환경
  - DBMS 별 타입 변환
  - 연결 기능 확대, 관련 Flyway 변경
- **지금 상태를 유지하는 것**
  - 연결 설정은 DBMS 를 고를 수 있다. 화면은 PostgreSQL 이외를 "설정만 저장" 으로 표시하고 테스트·수집 버튼을 끈다 (M-4a).
  - 서버도 그 DBMS 의 도구가 없으면 테스트·수집을 거절한다 (`SOURCE_TOOL_NOT_AVAILABLE`).
  - 지원하지 않는 DBMS 를 정상 지원처럼 보이게 하지 않는다.
- **결합을 늘리지 않는 규칙** : 원본 쪽은 이미 DBMS 중립 계약이다 (`SourceMetadataTool`·`SourceToolRegistry`, `SourceIdentifiers` 의 DBMS 별 비교 규칙, 원본 타입 문자열 그대로 저장). M-4c~M-4f 도 다음을 지킨다.
  - PostgreSQL 전용 판단(타입 이름 해석 등)은 한곳(타입 해석기)에만 둔다. 매핑·비교·가져오기 로직에 흩뿌리지 않는다.
  - 원본 이름 비교는 저장된 비교 이름(`CMPR_NM`)과 `SourceIdentifiers` 로만 한다. 문자열을 직접 소문자로 바꾸지 않는다.
  - core 계약(3장 5.1)에 DBMS 이름을 넣지 않는다.

## 3. HTTP 응답 압축

### 3.1 적용 (`application.yml`, 모든 프로필 공통)

```yaml
server:
  compression:
    enabled: true
    mime-types: application/json,application/problem+json,text/html,text/css,text/javascript,application/javascript,text/plain,text/markdown,image/svg+xml
    min-response-size: 4KB
```

- **방식** : Spring Boot 내장 Tomcat 의 gzip 이다. 필터·라이브러리는 추가하지 않았다. 기존 설정과 겹치는 것도 없었다 (압축·ETag 필터 없음, 프록시 설정은 `forward-headers-strategy` 뿐).
- **MIME 타입**
  - JSON API 를 압축한다.
  - React 정적 파일(js·css·html·svg)과 공지·도움말 텍스트(text/plain·markdown)도 압축한다.
  - 엑셀(xlsx = zip)·이미지·`application/octet-stream` 은 이미 압축된 형식이라 넣지 않았다.
- **최소 크기 4KB** : CSRF 토큰·로그인 결과·`/api/auth/me` 같은 짧은 응답(비밀값이 든 응답 포함)은 압축하지 않는다.
  - BREACH(HTTPS 압축 응답 길이로 비밀값을 추측하는 공격)의 대상인 "비밀값 + 공격자가 넣은 입력이 한 응답에" 조건이 CSRF 토큰 응답에는 없다.
  - 그 응답이 압축되지 않는 것을 테스트로 고정했다.
- **동작 조건** : 요청에 `Accept-Encoding: gzip` 이 있을 때만 압축한다. 압축한 응답에는 `Content-Encoding: gzip`, 모든 대상 응답에는 `Vary: accept-encoding` 이 붙는다.

### 3.2 측정 (bootJar `h2-local`, 로컬 PostgreSQL 18.6 원본, 같은 서버에서 Accept-Encoding 만 바꿔 20번씩)

| 원본 ERD JSON | 압축 전 | 압축 후 | 줄어든 비율 | 응답 시간 중앙값 (루프백, 전 → 후) | 서버 CPU (20회, 전 → 후) |
|---|---|---|---|---|---|
| 300 테이블 | 440,777 B | 11,231 B | 97.5 % | 6.4 → 8.0 ms | 0.24 → 0.28 s |
| 1,000 테이블 | 1,478,785 B | 35,910 B | 97.6 % | 24.6 → 23.3 ms | 1.61 → 1.03 s* |
| 3,000 테이블 | 4,463,462 B | 102,799 B | 97.7 % | 44.5 → 58.0 ms | 1.23 → 1.33 s |

\* 1,000 행의 CPU 는 JIT·GC 영향으로 오차가 크다. 압축 비용은 3,000 테이블 기준 요청당 약 5~15 ms 다.

- **해석**
  - 같은 컴퓨터(루프백)에서는 전송이 공짜라 압축 비용만 보인다 (3,000 테이블 +13 ms).
  - 실제 네트워크에서는 4.46 MB 가 100 Mbps 기준 약 0.36 s, 20 Mbps 기준 약 1.8 s 걸린다. 압축 후 103 KB 는 각각 약 8 ms·41 ms 다.
- **브라우저 (headless Chrome)** : 원본 ERD 3,000 테이블 응답의 전송량이 103 KB 였다 (`decodedBodySize` 4.46 MB, `content-encoding: gzip`).
  - 메인 JS 번들 1.27 MB → 367 KB, CSS 도 gzip 으로 받았다.
  - 대시보드·테이블 관리·물리 ERD·VIEW 관리·DDL 내보내기·원본 DB 4개 화면이 정상 동작했고 콘솔 오류가 없었다.
- **압축하지 않은 응답 (의도대로)**

  | 응답 | 이유 |
  |---|---|
  | `/api/auth/csrf` (100 B), `/api/auth/me` (1 KB), 404 오류 JSON (Content-Length 있음) | 4KB 미만 |
  | 엑셀 템플릿 (`application/octet-stream`) | 대상 MIME 아님 |
  | `index.html` (3.3 KB) | 4KB 미만 |
  | gzip 을 보내지 않은 요청 | `Accept-Encoding` 없음 |

- **알아 둘 것** : Content-Length 가 없는(chunked) 응답은 Tomcat 이 크기를 미리 몰라 4KB 미만이어도 압축한다 (예 : 없는 경로의 404 JSON 137 B). 비밀값을 담은 짧은 응답은 모두 Content-Length 가 있어 압축되지 않음을 확인했다.
- **리버스 프록시(nginx 등)가 따로 압축하는 운영 환경** : 둘 중 하나만 켠다. 이중 압축은 일어나지 않지만(이미 `Content-Encoding` 이 있으면 프록시가 건너뜀) CPU 를 두 번 쓸 수 있다.
- **회귀 테스트** : `SmokeTest.responseCompression` (실제 서버)
  - 4KB 넘는 JSON 은 gzip 이고, 풀면 압축하지 않은 응답과 같다.
  - `Vary` 가 붙는다.
  - gzip 을 보내지 않으면 압축하지 않는다.
  - CSRF 토큰은 압축하지 않는다.

## 4. M-4c~M-4f 단계

| 단계 | 내용 | 선행 |
|---|---|---|
| **M-4c** | core 원본 카탈로그 계약, 기준 연결, 스키마 매핑, TABLE 매핑 테이블·API·화면 (후보 탐색 + 사용자 확정) — **완료 (2026-11-13, [기록](source-mapping-m4c.md))**. 구현 중 정한·바뀐 것은 5.11, 후속 검증은 [기록 12장](source-mapping-m4c.md#12-완료-판정과-후속-검증) | 이 문서 |
| **M-4d** | 원본 ↔ 모델 비교 — **읽기 전용, 물리 모델을 바꾸지 않는다.** M-4c 의 명시적 매핑 기준으로 매핑된 TABLE 의 컬럼·물리 속성, PK·FK·UNIQUE·CHECK·인덱스 차이, 원본에만·모델에만 있는 객체, 원본 재생성·삭제·충돌 상태 반영, FULL/PARTIAL 범위 고려, 필드 소유권별 차이, 타입 해석 경고, 차이 결과 조회. 이름 변경 후보는 제안만(자동 확정 없음) — **구현 (2026-11-14, [기록](source-compare-m4d.md))**. 정한 것은 5.12 | M-4c |
| **M-4e** | 가져오기 실행 (사용자가 명시적으로 고른 항목만, 가져오기 전 모델 버전 보존, 미승인 생성·승인 상태 정책, IMPORT 이력, 실행 이력, 트랜잭션·실패 시 롤백, 원본 COMMENT ↔ 업무 설명 분리, 자동 삭제 없음, 매핑 변경 이력 저장 여부 결정) — **구현 (2026-11-14, [기록](source-import-m4e.md))**. 정한 것은 5.13 | M-4d |
| **M-4f** | 재최신화 (새 수집 이후 변경분만 비교·가져오기, 사용자 소유 필드 보존, 삭제 후보 처리) | M-4e |

- **M-4d 와 M-4e 는 하나의 구현 작업으로 합치지 않는다** (비교 결과를 검토한 뒤 가져오기를 따로 구현한다).

## 5. 설계 정책 (확정)

### 5.1 모듈 연결

- **계약** : `lexorma-core` 에 **읽기 전용 원본 카탈로그 계약**(인터페이스 + 값 DTO)을 둔다.
  - 예 : `core/source/SourceCatalogReader` — 연결의 반영 순서 R 시점 스키마·테이블·컬럼·제약조건·인덱스·FK 를 원본 ID 와 함께 돌려준다.
  - `lexorma-source` 가 구현하고, `lexorma-data` 가 쓴다.
  - M-4b 의 `SourceSnapshotService.erd` 와 같은 "버전 기준 한 번에 읽기" 를 재사용한다.
- **직접 의존 금지** : `lexorma-source` ↔ `lexorma-data` 직접 의존을 추가하지 않는다. `ModuleBoundaryTest` 가 지킨다.
- **값만 오간다** : 계약의 DTO 는 엔티티가 아니라 값이다. 프로젝트 범위는 호출하는 쪽의 검증된 실행 컨텍스트(`ExecutionContext`)에서 받는다.
- **정리 이벤트** : 원본 쪽 삭제(연결 삭제·카탈로그 정리)는 core 이벤트(예 : `SourceConnectionDeletedEvent`)로 알린다. `lexorma-data` 가 같은 트랜잭션에서 자기 매핑을 정리한다. 기존 `ProjectDeletedEvent` 와 같은 방식이다.
- **매핑 테이블의 위치** : 모델 쪽 데이터라 `lexorma-data` 에 둔다. 원본 ID 는 값으로만 들고 DB FK 를 걸지 않는다 (모듈·생명주기가 다르다).

### 5.2 객체 매핑

- **매핑 테이블** : 원본 객체와 모델 객체의 연결은 **별도 매핑 테이블**로 관리한다.
  - 대상 : 테이블·컬럼, 필요하면 제약조건·인덱스·FK.
  - 저장 값 : 연결, 원본 객체 ID(`TB_SRC_TBL`·`TB_SRC_COL` 일련번호), 원본 식별 키(스키마 경로 + 비교 이름), 생성 차수, 모델 객체 ID, 상태, 확정자·확정 시각.
- **후보와 확정**
  - 첫 후보는 (매핑된 스키마, 비교 이름)으로 찾는다.
  - **이름이 같다고 자동 연결하지 않는다.** 후보를 보여 주고 사용자가 확정한다.
  - 1:1 이 아니면 확정할 수 없고 사용자가 고른다. 예 : 하나의 원본에 후보 모델 객체가 여럿, 이미 다른 원본에 매핑된 모델 객체.
- **식별자**
  - PostgreSQL OID 는 저장하지 않는다. 덤프·복원·재생성 때 바뀐다.
  - 원본 쪽 식별은 Lexorma 의 원본 객체 ID 와 (스키마 경로, 비교 이름, 생성 차수)다.
- **이름 변경·삭제·재생성**
  - **이름 변경** : 수집은 이름이 바뀌면 `REMOVED` + `ADDED` 로 기록한다 (같은 객체로 단정하지 않음, AI-1c). 매핑은 "원본에서 사라짐" 상태가 된다. 새 객체를 같은 모델 객체에 다시 잇는 것은 사용자가 확정한다. 구조가 비슷한 "이름 변경 후보" 를 보여 줄 수 있다 (M-4d).
  - **재생성** : 같은 이름으로 다시 생기면 생성 차수가 올라간다. 이전 차수의 매핑은 자동으로 이어 붙이지 않고 확인을 요구한다.
- **충돌** : 모호하거나 충돌하는 매핑은 저장하지 않고 사용자 확인을 요구한다.

### 5.3 스키마 매핑 (DEFAULT 포함)

```text
PostgreSQL public   →  Lexorma DEFAULT (기본 스키마)
PostgreSQL archive  →  Lexorma archive
```

- **연결 방식** : 원본 스키마와 모델 스키마(`TB_SCHM`)를 **명시적으로** 잇는 스키마 매핑을 둔다. 기준 연결(5.7)마다 1:1 이다.
- **기본값** : 원본 `public` → 모델 기본 스키마(DEFAULT)를 **제안**만 하고 사용자가 확정한다. 다른 원본 스키마는 같은 이름의 모델 스키마를 제안한다. 없으면 "새로 만들기" 를 제안하고 만드는 것은 가져오기 때 한다.
- **보호** : 기존 DEFAULT 스키마의 이름·기본 여부는 바꾸지 않고 지우지 않는다. 모델의 DDL "스키마명 포함" 동작도 그대로다.
- **충돌 검사**
  - 두 원본 스키마가 같은 모델 스키마로 가지 않는다 (1:1).
  - 이미 다른 원본 스키마에 매핑된 모델 스키마는 고를 수 없다.
  - 새로 만들 모델 스키마 이름이 기존과 겹치면 거절한다.
  - 모델 스키마 안의 TABLE·VIEW 이름 충돌(D-25, 스키마 단위 이름 공간)은 가져오기 전 비교(M-4d)에서 충돌로 보여 준다.
- **변경** : 스키마 매핑을 바꾸면 그 스키마의 객체 매핑은 다시 확인이 필요하다고 표시한다 (자동 이동 없음).

### 5.4 가져오기 권한과 승인

- **수집과 설계는 다르다** : 원본에서 수집한 사실과 Lexorma 에서 승인한 설계를 구분한다.
- **실행 권한**
  - 가져오기·스키마 매핑·객체 매핑 확정 같은 모델을 바꾸는 실행은 **그 프로젝트의 관리자 또는 ADMIN** 만 한다.
  - 판정은 `ExecutionContextVerifier.verifyProjectManager`(= `ProjectAuthority.canManage`, 지금의 DB 기준)다. 수집과 같다.
  - 전역 MANAGER 역할만으로는 안 된다. 화면은 `source-manage` + `projectManageable` 을 쓴다 (M-4a 와 같다).
- **조회** : VIEWER·USER 는 기존 권한 범위 안에서 조회한다 (매핑·비교 결과 조회는 VIEWER).
- **승인 상태**
  - 가져온 테이블·컬럼·제약조건·인덱스·관계는 **미승인**(`APRV_YN = false`)으로 만든다.
  - 승인은 기존 승인 API·화면(승인 권한 `approvalAvailable`)으로만 한다. 가져오기가 승인을 대신하거나 우회하지 않는다.
  - 이미 승인된 모델 객체를 원본 기준으로 바꾸는 경우는 기존 규칙을 따른다 : 승인된 객체는 변경 요청이 되거나(인덱스·VIEW 방식), 승인 취소 후 수정해야 한다. 구체 방식은 M-4e 에서 객체 종류별로 기존 규칙에 맞춘다.

### 5.5 필드 소유권

| 원본 DB 기준 (최신화 대상) | Lexorma 사용자 관리 (최신화가 덮어쓰지 않음) |
|---|---|
| 물리명 (`TBL_NM`·`COL_NM`) | 논리명 (`TBL_KORN_NM`, 컬럼은 표준 용어명) |
| 데이터 타입·길이·정밀도·소수 자릿수 | 업무 설명 (`TBL_EXPLN`·`COL_EXPLN`) |
| NULL 허용 (`NULL_ALWNC_YN`) | 표준 용어 연결 (`STD_TRM_SN`) |
| DEFAULT (`BSC_VL`) | 표준 도메인 (용어를 통해 정해진다) |
| PK·UNIQUE·CHECK, FK(관계 `IMPORTED`), 인덱스 | 승인 상태, 마스터·민감·암호화 여부 등 사용자 작성 메타데이터 |
| 원본 COMMENT (**별도 속성**) | 논리 모델·매핑, ERD 배치 |

- **원본 COMMENT 는 새 속성**으로 둔다 (예 : `TB_TBL`·`TB_COL` 의 원본 설명 칸).
  - 지금 모델에는 이 칸이 없다. 업무 설명 칸에 넣지 않는다.
  - 칸 추가는 M-4d 또는 M-4e 의 **새 버전 마이그레이션(V3 이후)** 에서 한다 (M-4c 에서는 하지 않았다).
  - 예제 데이터와 용어·도메인도 같은 새 마이그레이션에서 더한다. V0·V1·V2 는 고치지 않는다 (2026-11-13 변경, 5.11 · [마이그레이션 정책](data-modeling-roadmap.md#마이그레이션-정책)).
- **최신화** : 원본 기준 칸만 비교·반영 대상이다. 사용자 관리 칸은 처음 가져올 때만 채운다 (예 : 논리명이 비어 있으면 원본 COMMENT 를 제안). 그 뒤에는 자동으로 덮어쓰지 않는다.
- **물리명 변경** : 기존 모델 참조와의 충돌을 먼저 검증한다.
  - 대상 : 참조 테이블명 약식 입력(`RFRNC_TBL_NM`), VIEW 참조, 스키마 단위 이름 공간, 매핑.
  - 반영은 기존 테이블 수정 경로(이름 공간 잠금·참조 재지정 포함)를 그대로 쓴다.

### 5.6 삭제 정책

- **자동 삭제 없음** : 원본에서 사라진 객체에 매핑된 모델 객체는 **삭제 후보**로 표시만 한다.
- **판정 근거** : 원본 쪽 "사라짐" 은 수집 버전의 `REMOVED` 로만 판정한다. 이 판정은 수집이 이미 **완전하게 수집한 범위 안에서만** 한다.
  - PARTIAL 수집의 범위 밖 객체는 `REMOVED` 가 되지 않는다 (AI-1c). 그래서 PARTIAL 에서 조회되지 않은 객체를 삭제 후보로 잘못 판단하지 않는다.
  - 비교(M-4d)는 반드시 이 버전 상태를 쓰고, "최신 수집 결과에 없다" 로 판단하지 않는다.
- **실제 삭제** : 사용자 확인과 기존 승인 정책(승인된 객체는 바로 지우지 않음)을 따른다.
- **고아 매핑** : 삭제 후보를 지우지 않고 남겨 두면 매핑은 "원본에서 사라짐" 상태로 남는다.

### 5.7 여러 원본 연결

- **기준 연결** : 프로젝트마다 **가져오기 기준 연결 하나**를 명시적으로 고른다 (D-17 결정). 스키마·객체 매핑과 가져오기는 그 연결 기준이다.
- **유지되는 것** : 연결을 여러 개 등록하고 각각 수집·카탈로그·ERD 를 보는 기능은 그대로다.
- **기준 연결 바꾸기** : 매핑이 있으면 확인을 받는다. 기존 매핑은 지우지 않고 "다른 연결의 매핑" 으로 남긴다.
- **후속 검토** : 여러 연결을 한 모델에 동시에 매핑하기(개발·운영 비교 등)는 M-10 ② 와 함께 검토한다.

### 5.8 타입 변환

- **범위** : PostgreSQL 원본 → PostgreSQL 대상 모델만 다룬다.
- **보존** : 원본 타입 문자열(`format_type` 결과)을 최대한 보존한다.
  - 모델의 타입·길이·정밀도·소수 자릿수 칸으로 나눌 수 있으면 나눈다.
  - 나눌 수 없는 타입(배열, 사용자 정의 타입, `timestamp(3) with time zone` 등)은 원문 그대로 둔다.
- **경고** : 모델 DDL 생성기(`TableDdlGenerator.mapType`)가 같은 DDL 로 되돌릴 수 없는 타입은 정보 손실 경고로 비교(M-4d) 화면에 보인다. 경고가 있어도 가져오기는 막지 않는다.
  - IDENTITY·GENERATED 는 원본 DEFAULT 문자열로 들어온다 (M-4a 확인).
- **나중에 할 것** : DBMS 간 타입 변환은 DBMS 확대 단계(1장)에서 한다.

### 5.9 VIEW 가져오기

- **지금은 하지 않는다** : 원본 수집기가 VIEW 정의 SQL 을 수집하지 않는다. 정의 SQL 이 없는 불완전한 VIEW 모델(`TB_VIEW` 는 정의 SQL 이 필수)을 만들지 않는다.
- **선행 조건** : VIEW 가져오기는 다음이 마련된 뒤에 한다.
  - 정의 SQL 수집 (AI-2 후속)
  - 비밀값 처리 정책 (U-21)
  - 카탈로그 정규화 해시 영향 검토
- **유지되는 것** : 원본 VIEW 의 카탈로그 조회와 원본 ERD 표시는 지금처럼 유지한다. 비교(M-4d)에서 VIEW 는 "가져오기 미지원" 으로 표시만 한다.

### 5.10 가져오기 이력

- **변경 출처** : 모델 변경 이력(`TB_MDL_CHG_HSTRY`)의 변경 출처에 **`IMPORT`** 를 더한다.
  - 지금은 `USER`·`AUTO_SYNC` 뿐이다. 이력 기록 자체는 `ModelChangeRecorder` 를 그대로 쓴다.
  - 가져오기 트랜잭션은 출처를 IMPORT 로 표시한다.
- **실행 이력** : 가져오기 실행 이력(새 테이블)을 둔다.
  - 기록 : 실행자, 기준 연결, **적용한 수집 실행·반영 순서**, 대상 수와 결과(성공·건너뜀·충돌·실패), 실패·충돌 사유.
  - 모델 변경 이력의 변경 묶음(`CHG_GROUP_ID`)과 잇는다.
- **아직 정하지 않은 것 (M-4e 구현 전에 검증)**
  - **트랜잭션 경계** : 실행 하나를 한 트랜잭션(전부 또는 없음)으로 할지, 테이블 단위 묶음으로 나눌지. 대량(수천 테이블)일 때 잠금 시간과 이력 크기를 측정해 정한다. 권장은 한 실행 = 한 트랜잭션이고, 한도를 넘으면 범위를 나눠 실행한다.
  - **모델 버전 보존** : 가져오기 직전에 모델 버전(M-9 3차 스냅샷)을 자동으로 만들지, 사용자가 고르게 할지. 권장은 자동 생성 + 이름 규칙이다.

### 5.11 M-4c 구현에서 정한·바뀐 것

M-4c 를 구현하며 위 정책을 더 구체적으로 정하거나 바꾼 것이다. 실제 동작은 [M-4c 기록](source-mapping-m4c.md)이 기준이다.

| 항목 | 이 문서의 처음 정책 | M-4c 구현 | 구분 |
|---|---|---|---|
| 매핑의 "상태" (5.2 저장 값) | 매핑 테이블에 상태를 저장 | **상태를 저장하지 않고 조회 때 계산** (매핑됨·미매핑·모델 없음·원본 없음·재확인 필요·충돌). 저장은 확정 관계와 확정 시점의 원본 식별 정보(경로·비교 이름·생성 차수·반영 순서)뿐 | 변경 |
| 매핑 대상 (5.2) | 테이블·컬럼, 필요하면 제약조건·인덱스·FK | 스키마·TABLE 만. 컬럼 이하 단위의 영속 매핑 필요 여부는 M-4d 착수 전에 정한다 | 범위 축소 (보류) |
| 스키마 매핑 변경 (5.3) | 그 스키마의 객체 매핑은 "다시 확인 필요" 로 표시 | 모델 스키마를 바꾸면 그 스키마의 TABLE 매핑은 **충돌**(`SCHEMA_MISMATCH`)로 보이고 자동 이동하지 않는다. 스키마 매핑을 **해제**하면 그 원본 스키마의 TABLE 매핑도 함께 해제한다 | 구체화 |
| 모델 스키마가 없을 때 (5.3) | "새로 만들기" 를 제안, 만들기는 가져오기 때 | M-4c 는 제안하지 않고 미매핑으로 둔다 (모델 스키마를 만들지 않음). "새로 만들기" 제안은 M-4d·M-4e 에서 | 보류 |
| 기준 연결 지정 (5.7) | 기준 연결 하나를 명시적으로 선택 | **완료된 수집이 없어도 지정할 수 있다.** 단 그 상태에서는 매핑 확정을 거절한다 (`SOURCE_MAPPING_INVALID`) | 구체화 |
| 기준 연결 변경 (5.7) | 매핑이 있으면 확인, 기존 매핑은 "다른 연결의 매핑" 으로 남김 | 같음. 확인 없이 바꾸면 409 로 남는 건수를 알린다. **다른 연결의 매핑을 현재 기준으로 자동 이전하지 않는다.** 이전 연결로 돌아오면 남은 매핑의 상태를 그때 다시 판정한다 | 구체화 |
| 원본 연결 삭제 (5.1) | core 이벤트로 같은 트랜잭션에서 정리 | `SourceConnectionDeletedEvent` (동기 리스너) 로 TABLE·스키마 매핑과 기준 지정을 지운다 | 같음 |
| 원본 COMMENT 칸 (5.5) | V0·V1 을 고치고 개발 DB 재생성 | 새 버전 마이그레이션(V3 이후)으로 더한다. V0·V1·V2 수정 금지 | 변경 (마이그레이션 정책 변경에 따름) |

### 5.12 M-4d 구현에서 정한·바뀐 것

| 항목 | 이전 정책·계획 | M-4d 에서 | 구분 |
|---|---|---|---|
| 컬럼 이하 영속 매핑 (5.2) | 대상에 컬럼, 필요하면 제약조건·인덱스·FK. M-4d 착수 전 결정 | 만들지 않는다. TABLE 매핑 안에서 비교 이름(컬럼·CHECK·인덱스·이름 있는 UNIQUE/FK) 또는 구조(PK, 모델이 이름을 만드는 UNIQUE·FK)로 비교 때 계산. 이름이 다르면 이름 변경 후보로 제안만 | 결정 |
| 가져오기 계획 조회 (4장 M-4d) | 차이 결과·가져오기 계획 조회 | 비교 결과만. 가져오기 실행 계약을 미리 만들지 않고 M-4e 에서 정한다 (비교 DTO 는 객체·속성 단위라 M-4e 가 그대로 쓸 수 있다) | 범위 축소 |
| 원본 COMMENT 칸 (5.5) | M-4d 또는 M-4e 의 V3 이후 | M-4d 는 DB 를 바꾸지 않는다 : 비교에서 원본 COMMENT 는 표시만(NOT_COMPARED). 칸 추가는 M-4e | 보류 |
| 타입 비교 (5.8) | 정보 손실 경고 | 모델 타입을 PostgreSQL DDL 로 바꾼 표현과 비교. 별칭만 같게 본다. 모델 타입이 DDL 에서 바뀌면 경고 | 구체화 |
| 필드 소유권 (5.5) | 원본 기준 칸만 비교 | 원본 기준 칸(물리명·타입·NULL·DEFAULT·제약·인덱스·FK)만 비교. 논리명·업무 설명·표준 용어·승인 상태는 보지 않는다 | 그대로 |
| VIEW (5.9) | "가져오기 미지원" 표시 | 비교 대상에서 빼고 개수만 표시. 미매핑 원본 TABLE 이 모델 VIEW 와 이름이 같으면 충돌 (D-25) | 구체화 |
| 비교 일관성 | — | 한 요청 = REPEATABLE READ + 반영 순서 고정. 요청 사이 기준·반영 순서가 바뀌면 409 `SOURCE_COMPARE_STALE` | 새로 정함 |

## 6. 남은 위험과 미결정

- **스테이징 정리** : 2.4 를 승인해야 한다. 그 전에 지금 인덱스로 커밋하면 V6 가 다시 들어간다.
- **IntelliJ 자동 추가 설정** : 사용자가 바꿔야 재발하지 않는다 (2.3).
- **응답 압축**
  - chunked 응답의 작은 크기 압축은 Tomcat 동작이다. 비밀값 응답은 Content-Length 가 있어 해당 없음을 확인했다.
  - 운영 프록시와의 이중 설정 여부는 배포 환경에서 확인한다.
- **M-4e 전에 정할 것** : 5.10 의 트랜잭션 경계와 모델 버전 보존. 5.4 의 승인된 객체를 바꾸는 방식(객체 종류별).
- **원본 COMMENT 칸 추가 마이그레이션** : 새 버전 파일(V3 이후)로 더한다. 개발 DB 를 다시 만들지 않는다 (2026-11-13 변경 — 처음에는 V0·V1 을 고치고 DB 를 다시 만드는 안이었다).
- **M-4c 후속 검증** : 연결 삭제 ↔ 매핑 확정 경합, 기준 연결 복귀, V2 예제 데이터, 대규모 성능 ([기록 12장](source-mapping-m4c.md#12-완료-판정과-후속-검증)).
- **외부 연결 접근 정책** : 관리자 허용 목록 관리·AI Endpoint 공통 적용은 [AI 로드맵 SEC-1](ai-metadata-roadmap.md#sec-1-외부-연결-접근-정책-및-관리자-허용-목록-관리) 이다. M-4 단계의 완료 조건이 아니다.
- **원본 ERD 의 VIEW 참조 관계·VIEW 가져오기** : 정의 SQL 수집 이후.
